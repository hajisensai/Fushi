## BUG-3818 · 删 Profile 后 srs.db 里该 uid 的复习数据与媒体目录残留（无主副本）
- **报告**：2026-10-27（用户：应用内反馈 8TaOy2i-lL 现象 3，Windows `3.0.1-debug.20797`；`fushi_cli profile rm 5 --yes` 后残留 1820 笔记缓存 / 1820 卡缓存 / 7309 复习日志 / 1826 实体 / 整个 `srs_media/<uid>`）。分诊见 `docs/reviews/2026-10-27-feedback-triage.md` 第五节第 1 项，所有者 2026-10-27 批准方案 A。现象 1 见 BUG-3809。
- **真实性**：✅ 真 bug。`fushi/lib/src/profile/profile_repository.dart:92-105` `deleteProfile` 只删主库 `profiles` 行（`packages/fushi_core/lib/src/database/database_tags_sync.part.dart:990`）；`srs.db` 是所有 profile 共用的另一个文件，行按 `profile_uid`（= `profiles.uid`）归属，主库外键级联管不到——`srs_*` 投影 / 缓存、`sync2_*` 操作与本机身份、`srs_meta` 里按 profile 记的键（`sync2_migrating/<uid>`、`sync2_digest/<uid>` …）、`<support>/srs_media/<uid>`（媒体与释义样式同目录）、`<support>/srs_rwkv/state/rwkv-<uid>-*.snap` 全部留下，且 uid 只记在被删的那行里，之后无入口可清。同类缺口：`packages/fushi_engine/lib/srs/srs_backup_merge.dart:237` `_kSrsProfileTables` 手抄的 10 张表不含任何 `sync2_*`（采用对端 uid 时旧 uid 的同步 v2 行同样留下，本条的一次性扫描会兜住，未改那条路径）。
- **[x] ① 已修复** — 方案 A：
  - Rust 胖核心 `native/fushi_fsrs/src/store/profile_data.rs`（经 `ffsrs_store_sync2` 分派，无新 C ABI）：`profile_footprint`（读快照里一次数出笔记 / 卡 / 复习记录 / 总行数）、`profile_purge`（一个 savepoint 里删该 uid 在**每张**带 `profile_uid` 列的 `srs_*` / `sync2_*` 表的行——表清单按 `sqlite_master` + `pragma_table_info` 现查，含按需建的 `sync2_migrate_queue`；删 `srs_meta` 里以 `/<uid>` 结尾的键；回收没人引用的 `sync2_deps`；作废该 uid 的收段会话）、`profile_uids` / `orphan_sweep_done`（存量扫描）。只删本机，远端集合不碰。
  - Dart：`fushi/lib/src/srs/srs_profile_cleanup.dart`（`SrsProfileCleanup`，经 `ProfileDeletionCascade` 接口注入 `ProfileViewModel`）。删除顺序：统计 → **先备份**（现有 `srsExportFushiSrs`，`.fushisrs` 含被引用媒体，落 `<documents>/srs_profile_backups/fushi-review-<profile 名>-<yyyyMMdd-HHmmss>.fushisrs`；失败抛 `ProfileDeletionBackupException`，删除中止）→ 删 `profiles` 行并切走当前 Profile → `SrsDbStore.retire` 下 Rust 一条命令删光 → 删媒体目录与 RWKV 快照。所有对共用写连接的操作排进当前副本的独占区（Rust 命令在写连接上是 savepoint，夹进别的副本开着的事务会随它回滚）。`SrsDbStore.runExclusive` 排队后再查一次作废标记，迟到写入不会把行写回已删 uid。
  - 确认框（`profile_management_page.dart` `ProfileDeleteDialog`）写明「N 张卡、M 条复习记录」与自动备份；成功提示给出备份路径；控制通道 `settings.profile.delete` 返回 `srs:{notes,cards,reviews,backup}`，备份失败回 `rejected`。
  - 存量：进 Profile 管理时 `sweepOrphanProfileData` 扫一次 srs.db 里不属于任何现存 profile 的 uid，逐个先备份再清，全部完成后在 `srs_meta.profile_orphan_sweep_v1` 记完成标记，之后不再扫；失败不写标记、进错误日志，下次进来重扫。
- **[x] ② 已加自动化测试** — Rust `native/fushi_fsrs/src/store/profile_data.rs` 4 条（删光该 uid 每张表 + 按 profile 的 meta 键、另一 profile 与其因果上下文不动且照常可写；除 `srs_meta`/`sync2_deps` 外每张 `srs_*`/`sync2_*` 表都在删除面里；`profile_uids` 与完成标记；作废收段会话）。Dart `fushi/test/srs/srs_profile_cleanup_test.dart` 5 条（真 ProfileViewModel + 真 srs.db：确认框规模与 SQL 实数一致、删后 srs.db/媒体/RWKV 快照清空且另一 profile 不变、备份名与内容正确且**能导回**同 uid；备份失败中止且一切原样；删当前 Profile 先切走再清、旧副本作废；无数据不备份；一次性扫描只跑一次）；`fushi/test/pages/profile_management_page_test.dart` 2 条（确认框写明卡数 / 复习记录数；无数据时不显示）。
- **备注**：
  - 撤销途径目前是**文件**：备份是被删 uid 的 `.fushisrs`，导入要求目标 profile 的 uid 相同（`srs_fushisrs.dart:132`，集合 ID 由 uid 确定性派生）。测试证明「同 uid 的 profile 导回」可行，但 app 里还没有「从备份恢复已删 Profile」的入口（需新建 profile 并 `adoptProfileUid(manifest.profile)` 再导入）；未做。
  - 备份目录 `<documents>/srs_profile_backups` 不自动清理，也不进 app 备份。
  - 只剩媒体目录、库里没有该 uid 任何行的情况：没有笔记引用这些文件，不备份直接删。
  - 未在真机 / 真 app 上点过确认框与 CLI `profile rm`（只有 widget 测试与 ViewModel 层测试）。
