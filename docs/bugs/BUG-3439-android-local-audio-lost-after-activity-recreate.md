## BUG-3439 · Android 查词本地音频库「某时起」失效，重启才恢复
- **报告**：2026-10-16（用户反馈 `ErauJiJNuc`，OnePlus Android 16：「明明有音频数据库，但漫画里不知道什么时候起查词没有音频，重启 Fushi 恢复」）
- **真实性**：✅ 真 bug（沿代码路径定位，未在设备复现）。原生本地音频库状态挂在 Activity 上：`fushi/android/app/src/main/java/app/fushi/reader/MainActivity.java` 每次 `onCreate` 新建 `TtsChannelHandler`（`localAudioDbs` 为空）、`configureFlutterEngine` 里 `register`、`onDestroy` 里 `destroy()` 关库；而引擎由 audio_service 缓存、比 Activity 活得久（BUG-2280 已实测 Activity 重建时 PID 与 Dart VM 不变）。Dart 只在 `AppModel.initialise()` → `_prepareLocalAudioForPlayback` → `LocalAudioManager.bindForNativeHandler`（`fushi/lib/src/models/local_audio_manager.dart`）推一次库配置。于是：(A) 根页返回 / 系统回收 Activity 后重开，复用旧引擎、注册的是空库新 handler，`TtsChannelHandler.handleQueryLocalAudio` 在 `localAudioDbs.isEmpty()` 时直接 `result.success(null)`，查词静默当作「库里没这个词」；(B) 引擎先于 Activity 被后台拉起（AudioService）时，初始化那次 `setLocalAudioDb` 还没有 handler，日志里每次启动的 `MissingPluginException(No implementation found for method setLocalAudioDb on channel app.fushi.reader/tts)`（`tts_channel.dart` `setLocalAudioDbs`）就是这条路径，之后整个会话都没有本地音频。重启进程才会重新 `initialise()` 绑定。
- **[x] ① 已修复** — 原生 `TtsChannelHandler.register` 挂上后主动 `invokeMethod("nativeHandlerAttached")`；Dart `TtsChannel.onNativeHandlerAttached`（`main()` 在 `initialise()` 之前装）收到即调 `AppModel.rebindLocalAudioForNativeHandler` 重推配置（管理器未建好时 no-op，由 `initialise()` 自己绑）。两条路径都在新 handler 挂上那一刻补推。提交见本分支 `fix(audio): rebind local audio DBs when the Android TTS handler reattaches`。
- **[x] ② 已加自动化测试** — `fushi/test/utils/misc/tts_channel_native_attach_test.dart`：经测试 binary messenger 从平台侧发 `nativeHandlerAttached`，断言每次都触发重绑、其它调用不触发；源码守卫钉住 Java `register` 发通知、`main()` 在 `initialise()` 前装回调。
- **备注**：未做真机 E2E（保活下根页返回再重开 → 漫画查词有本地音频；`adb shell cmd media_session dispatch play` 先拉起服务再开 app）。`AnkiChannelHandler` / `MihonChannelHandler` 同样随 Activity 重建，若它们持有 Dart 只推一次的状态会有同类问题，未逐一核实。
