## BUG-1015 · 桌面首次查词自动发音无声·media_kit播放器冷启动
- **报告**：2026-07-22（用户：Hanwill，电脑看动画/视频，本地音频源）
- **真实性**：✅ 真 bug。桌面（Windows/macOS/Linux）本次 app 启动后**第一次**查词时自动发音没声音，再查一次（或手点 ♪）就正常。
  - 沿真实代码路径逐段排除：触发链无首次门控（`dictionary_page_mixin.dart:771` 首次即调 `autoReadWord`）；本地音频解析是同步 SQLite（`local_audio_db.dart:87 queryMeta`），`.timeout(500ms)` 对同步体是死代码、不会把结果变空；去重协调器首次不吞（`lookup_auto_read_coordinator.dart:34`）；查词流程无 `TtsChannel.stop()` 调用者→`_play` 不会被 `preempt` 抢占。解析成功、`_play` 也会真正 play，唯一剩下的是**播放管线本身**的冷启动。
  - 根因 `desktop_audio_playback.dart` `DesktopAudioPlayback._player`（just_audio + just_audio_media_kit 单例）：进程内**第一次**平台激活（`_setPlatformActive(true)` → media_kit `Player.init`）会吞掉第一段真实播放的音频输出。因 `_player` 是进程单例、永不 dispose，「第一次」= 本次启动后第一次发音（恰好用户在看视频时首查），之后播放器已热 → 第二次起正常。与「制卡 expressionAudio 空白」不同源（那条另有人跟进）。
- **[x] ① 已修复** — 启动时静音预热查词播放器，把冷启动首帧空窗在无声中消耗掉。`desktop_audio_playback.dart` 新增 `warmUp()`：写一段 ~0.1s、8kHz、单声道、16-bit **全零 PCM 静音** WAV（`_silentWavBytes()`）到临时目录，走既有 `_play(...,'warmUp',0.0)` 完整 `stop→load→play` 周期（复用同一 `_player` + `_activation` 串行队列，绝不与后续真实播放交错）；`tts_channel.dart` 新增 `warmUpLookupAudioPlayer()` 做平台门控（Android 走原生 MediaPlayer，直接 no-op）；`main.dart` 在 `MediaKit.ensureInitialized()` 后 `unawaited(...)` fire-and-forget 调用（桌面块内、不阻塞启动、失败内部吞掉）。volume 0 + 全零采样双重保证无任何可听声响。提交：<pending>
- **[x] ② 已加自动化测试** — `hibiki/test/utils/misc/desktop_lookup_audio_warmup_test.dart`：① 断言预热 WAV 是合法且 data 区**全零**（绝对无声）的 16-bit PCM WAV（头标记/PCM 参数/尺寸自洽/逐字节零）；② 源码守卫接线（main 在 media_kit 初始化后调用预热、`TtsChannel.warmUpLookupAudioPlayer` 对 Android `_isSupported` 短路、`DesktopAudioPlayback.warmUp` 复用 `_play` 且 volume 0）。播放实际是否出声属 media_kit 平台行为，须**桌面真机复测原始失败路径**（本次启动后第一次查词即应出声）。
- **备注**：静态已排除解析/触发/抢占三类可确定原因，媒体层冷启动吞首帧无法离屏复现（Windows known-folder prefs 限制挡住配置本地音频库离屏跑），故按已知类问题做根因预热修法，落地后须桌面真机验收。
