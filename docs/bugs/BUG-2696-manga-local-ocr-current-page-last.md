## BUG-2696 · 本地 OCR 整卷任务不从当前页开始，读到第 30 页要等前 29 页识别完
- **报告**：2026-09-26（用户：Windows 用户（7800X3D）反馈在线源漫画「为什么要先下载、先把整章 OCR 完才能查词」）
- **真实性**：✅ 真 bug。阅读器进入即整卷识别时传了 `startPage: _currentPage`（`fushi/lib/src/media/manga/reader/manga_reader_auto_ocr.dart`），Lens / 系统 OCR 路径按它旋转顺序，但本地 ONNX 路径把它丢了：`mangaOcrLocalEvents` 调 `spec.engines.service.ocrFolder(imageDirPath, volumeTitle)` 不带起点（`fushi/lib/src/media/manga/manga_ocr_job_stream.dart:177`），`MangaOcrService.ocrFolder` 根本没有这个参数（`packages/fushi_engine/lib/ocr/manga_ocr_service.dart:32`），`MangaOcrPipeline.processBook` 恒 `for page in 0..N`（`packages/fushi_engine/lib/ocr/manga_ocr_pipeline.dart:110-119`）。job stream 还假设 `pageIndex = pagesDone - 1`（`manga_ocr_job_stream.dart:190`），一旦顺序变了就会把结果贴到错页。结果：停在第 30 页的读者要等 0..29 页全部识别完才能查当前页。
- **[x] ① 已修复** — `8aa70974cd1`：`ocrFolder` 加 `startPage`，经 `SelectedMangaOcrService` → `MangaOcrVolumeJobRequest` → isolate 参数 → `runMangaOcrFolderJob` → `processBook`，按 `mangaOcrPageOrder`（当前页 → 末页 → 绕回 0，Lens / 系统 OCR 路径也改用同一个函数）处理；`processBook` 结果仍按页序返回，manga.json 内容与起点无关；进度回调与 `MangaOcrVolumeEvent.page` 带真实 `pageIndex`，job stream 优先用它（不报页号的实现才退回 `pagesDone - 1`）；整卷已缓存的快路径也按起点顺序回放；已有逐页缓存的页在旋转顺序里直接命中、不跑推理。导入向导的本地引擎分支同样透传 `startPage`。远端主机 / 外部 mokuro 做不到按序，照旧忽略起点。
- **[x] ② 已加自动化测试** — `fushi/test/ocr/manga_ocr_pipeline_test.dart`（startPage 处理顺序 / 进度页号 / 结果页序、缓存页跳过推理、`mangaOcrPageOrder` 越界夹取）；`fushi/test/ocr/manga_ocr_folder_job_test.dart`（真目录任务：当前页先检测、manga.json 与从头跑逐字节一致）；`fushi/test/media/manga/manga_ocr_job_stream_start_page_test.dart`（job stream 起点透传、事件 pageIndex 与该页文字层对应、全缓存快路径按起点回放、不报页号实现的回退）；`fushi/test/ocr/manga_ocr_service_impl_test.dart`、`manga_ocr_selected_service_test.dart`（起点与页号穿过服务层）。
- **备注**：未在真 app 里复测「停在第 30 页、先出第 30 页文字层」的原始路径（本机未装本地 manga-ocr 模型）。用户同时抱怨的「本地 OCR 走 CPU 很慢」「多列竖排框识别不对」不在本条范围，见同分支后续提交 / 报告。
