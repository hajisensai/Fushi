## BUG-4045 · 游戏制卡整张卡串行：上一张卡编码 / 写库期间下一张卡无法采样（无后台制卡队列）
- **报告**：2026-11-03（应用内反馈 EJhUrX_mHY「Fushi 制卡（srs 目标）缺少后台批量队列，制卡时阻塞查词」；U9k4hlYaNZ「游戏制卡卡顿」同根的一半）
- **真实性**：✅ 真 bug（结构缺陷）。`GalHookMiningCoordinator.mineLine` 把**整张卡**排进同一条 `SerialJobQueue`（改前 `fushi/lib/src/mining/gal_hook_mining_coordinator.dart:321` `_miningQueue.enqueue(() => _mineLineNow(...))`，`_mineLineNow` 在 `:350`）：行校验 → 窗口采样（动图 ≤ 8 s）→ 句音收口（引擎 PCM 等语音播完）→ ffmpeg 编码（`galgame_window_gif.dart` 每种格式 ≤ 60 s，首选格式失败再编一次 GIF）→ 词典媒体落盘 → `_engine.mine` 写 Anki / Fushi 复习（`:664` 起，复习目标还要下载单词音频、存媒体、落库）全部在一个作业里。连续挖词时第二张卡的**画面采样**要等第一张卡写完才开始：等到时台词早已推进（截到别的画面 / `staleScene`），游戏内查词卡也多半已关，取 capture lease 直接 `GalHookCaptureSuppressionException` 失败——用户看到的就是「制卡未完成时不能制 / 查下一个词」。这与目标是 Anki 还是 SRS 无关，SRS 目标只是收尾更慢、更明显。
- **[x] ① 已修复** — 提交 `2bad96ce91`。制卡拆成两段队列：`_captureQueue`（`gal_hook_mining_coordinator.dart:190`，只做必须在台词仍在屏上时完成的事：行校验、窗口像素、句音启动、同步片段导出）与 `_finishQueue`（`:194`，动图编码、打码 / 降采样、句音收口、词典媒体、写卡），收尾在采样作业**之内**同步入队（`:366-374`），所以收尾顺序严格等于采样顺序、仍是一条有序串行写库队列，但采样队列不再等它。动图拆成 `sampleWindowAnimationFrames`（`galgame_window_gif.dart:159`，capture lease 只包采样循环）+ `encodeWindowAnimationFrames`（`:288`）；收尾编码失败时用**采样时 lease 内抓到的第一帧**降级静图（`gal_hook_mining_coordinator.dart:702`），不再在编码失败那一刻重抓窗口（排在别的卡后面时那一刻的画面已不是这句台词）。`captureWindowGifBytes` 保留为「采样 + 编码」组合，外部语义不变。
- **[x] ② 已加自动化测试** — `fushi/test/mining/gal_hook_mining_pipeline_test.dart`：①「上一张卡还在写库时下一张卡的画面立刻采样；写卡仍按采样顺序串行」（Completer 挂住第一张卡的写库，断言第二张卡的采样照常发生、写库顺序 = 采样顺序、同时在写的只有 1 个、每张卡的封面属于自己的采样）；②「收尾编码失败时用采样到的第一帧降级静图，不在收尾时重抓窗口」（真实 `window_capture` MethodChannel mock + 失败的 ffmpeg 后端）。变异实测：把收尾改回在采样作业里 await，① 红（「第二张卡的采样被第一张卡的写库挡住了」）。连同 `gal_hook_mining_coordinator_test.dart` / `gal_hook_mining_parallel_capture_test.dart` / `gal_hook_video_clip_mining_test.dart` / `gal_mining_animation_duration_wiring_guard_test.dart`（锚点改为 `sampleWindowAnimationFrames(`）/ `gal_window_gif_duration_wiring_test.dart` 共 45 个测试，exit 0。
