## BUG-4186 · 网页视频（Netflix）跳转后站点卡住，进度条仍按外推往前走
- **报告**：2026-11-04（用户：开发者自报，应用内反馈 Ia-GMxq2dQ / sSLXGfcQWH，Windows，Netflix）
- **真实性**：✅ 部分真 bug（进度条假走）。`fushi/lib/src/media/video/web_video_platform_player.dart:185` `_extrapolatedPosition()` 只看 `state.playing`，不看页面上报的 `buffering`（glue 的 `buf` = `<video>.seeking || readyState < 3`），也没有外推上限。seek 在途时上报不回灌（为了不把 Netflix 慢落地的进度条拽回去），外推成了唯一位置来源：站点卡在缓冲 / 黑屏时进度条照走，直到 4 s seek 超时或用户暂停才跳回跳转点——与反馈描述一致（日志里有 `seek failed (id=…): timeout`）。
- **[x] ① 已修复** — 页面报缓冲时外推冻结，进出缓冲都从当前显示位置重新起算；离最近一次权威位置最多外推 `kWebVideoMaxExtrapolation`（1 s，上报周期约 250 ms），上报停了 / seek 迟迟不落地时进度条不再凭空前进。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/web_video_platform_player_test.dart`：seek 在途 + 缓冲时停在目标、出缓冲从冻结处接着走；非 seek 期间缓冲冻结；上报停了外推到顶即停、新上报照常跟随。
- **备注**：「黑屏只有声音」与「多次跳转后越来越卡」**未修、未定位**。代码里查过的部分：Dart `seek` 不加监听；非 Netflix 的 glue seek 用一次性 `seeked` 监听，触发即摘；Netflix 走 `netflix-bridge.js` `nfSeek`，新 seek 让旧轮询回 `superseded`（2026-11-04 日志里确有 superseded，说明作废在生效），没有找到按 seek 累积的监听器 / 定时器 / 会话。2026-11-01 日志里 id 2–15 共 14 条 `timeout` 落在同一微秒，按单实例 bridge 的代际作废逻辑本该是 superseded，说明当时要么页面主线程 / Dart 侧消息长时间堵住后一次性投递，要么 bridge 被注入了不止一份——现有日志区分不了。要定位还缺：每次 seek 前后页面里 `netflix-bridge` 实例数、`<video>` 元素数与 `readyState` / `networkState` / `videoWidth`、Netflix 播放器会话数、WebView2 进程内存，以及黑屏时 `video.getVideoPlaybackQuality()` 的丢帧数；需要真实 Netflix（PlayReady DRM）环境复现。
- **追加（2026-11-10，黑屏 / 越跳越卡的诊断与结构收口）**：
  - **结构缺口（已修）**：`tools/browser-extension/netflix-bridge.js`（镜像 `fushi/assets/browser_extension/`）没有「同文档只装一份」守卫（`youtube-bridge.js` 有）。它改的是页面全局（`JSON.parse` / XHR / `Response` 原型、`message` 监听、2 s 一拍的状态遍历），而「同一时刻最多一次 `player.seek` 在途」是**实例内**状态（`nfSeekInFlight` / `nfSeekQueued`）——装两份就是两套互不知情的在途状态，同一条 seek 消息被各发一次 `player.seek`（正是 #2837 要避免的叠发重定位），钩子套两层、每个 id 回两条 seekDone。修复：脚本开头按 `window.__fushiNetflixBridge`（不可写、不可枚举）判重，第二份直接退出并计数告警。本仓代码里没找到会把它送进同一文档两次的路径（网页播放器 document-start 注入每文档一次；扩展宿主整栈自带同文档守卫；Windows fork 的 user script 走 CDP `Page.addScriptToEvaluateOnNewDocument`，iframe 是各自的 window），所以这是收口而不是已证实的根因。
  - **诊断（已加）**：每条 seek 回执带页面侧快照 `diag`（`nfDiag`）：bridge 实例 id 与重复注入次数 `dup`、页面 `<video>` 数、主 `<video>` 的 `readyState` / `networkState` / `seeking` / `paused` / 画面尺寸、`getVideoPlaybackQuality()` 丢帧/总帧、未关的 EME 会话数/累计（`MediaKeys.prototype.createSession` 纯透传计数，`session.closed` 兑现才算关）、JS 堆 MB（`performance.memory`）、页面侧 `waitMs`（收到请求到回执，含排队）与 `at`（回执时刻）。Dart 侧 `WebVideoSeekDoneLog`（`fushi/lib/src/media/video/web_video_bridge.dart`，播放器后端与制卡页共用）：失败每次带诊断记，成功 30 s 最多记一条，superseded 不记。用 `at` 分得清 11-01 那种「14 条 timeout 同一微秒」是页面真同时回的，还是页面早回了、消息被堵后一起送到；`dup` 直接回答「bridge 是不是多份」；`videos` / `keySessions` / `frames` / `heapMB` 随时间涨就是站点会话在累积。
  - **仍未定位 / 未做**：黑屏只有声音没有复现证据（本轮按批次约束不跑 app、不做真机），未确认是 PlayReady 解码 / 渲染卡住，所以**没有**加任何「重载播放器」之类的兼容层；拿到带 `diag` 的日志后若确认是硬件 DRM 层的外部限制，再按根因规则单独评估。WebView2 进程内存没有采（需要原生侧 `ICoreWebView2Environment.GetProcessInfos` + 进程内存查询），只有 JS 堆作近似。
  - 测试：`tools/browser-extension/netflix-bridge.test.js`（注入两次只装一份 / 一条 seek 只发一次只回一次 / 标记不可覆盖 / 诊断各项与 EME 会话计数 / 页面缺 document 时诊断降级）；`fushi/test/media/video/web_video_glue_js_test.dart`（glue + 两份 bridge 端到端）；`fushi/test/media/video/web_video_bridge_test.dart`（diag 解析与截断、日志判据与限流）。
