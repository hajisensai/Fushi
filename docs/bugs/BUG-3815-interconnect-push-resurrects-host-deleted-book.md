## BUG-3815 · 互联客户端把主机「从所有设备删除」的书推回主机并清掉删除墓碑
- **报告**：2026-10-27（用户：应用内反馈 Et3pmRzo0k —— Windows 互联主机上勾「从所有设备删除」删了 6 本书，Android 客户端同步后书没在手机上删，反而重新出现在主机上，主机 `book_tombstones` / 同步删除墓碑都没了）
- **真实性**：✅ 真 bug（沿代码路径确认，并在 `interconnect_push_respects_host_tombstone_test.dart` 以真实 HTTP 链路复现）。根因是两层同时缺失：
  1. **client 推送不看删除意图**：互联一轮 `SyncOrchestrator.run()` 先跑内容推送 `_syncBooksContentLive`（`fushi/lib/src/sync/sync_orchestrator.dart:711`），删除墓碑的拉取与确认 `_syncDeletionTombstonesLive` 排在整轮最后（同文件 `:899`），且确认要等 UI 逐条点——推送时本机那份旧副本必然还在。推送清单 `computeBookSyncDiff`（`fushi/lib/src/sync/sync_orchestrator/books.part.dart:46`）只认「本端有 ∧ host 无」，host「无」正是因为被删了。有声书（`sync_orchestrator/audiobooks.part.dart:194-218`，按 bookKey union）与视频（`sync_orchestrator/videos.part.dart:326-349`，按 bookUid）是同一形状，同病。
  2. **host 推送导入无条件清墓碑**：`PUT /api/library/books/<title>`（`packages/fushi_engine/lib/sync/fushi_sync_server/library.part.dart:247`）→ `LocalLibraryHostService.importBook`（`local_library_host_service/books.part.dart:283`）不看墓碑直接导入，`insertEpubBook`（`packages/fushi_core/lib/src/database/database_content_misc.part.dart:275-278`）把重新入库当新的加入意图，`clearBookTombstone` + `clearSyncDeletionTombstone('book', …)`。视频同理（`importVideo` → `upsertVideoBook` 清 `video` 墓碑，`database_prefs_media.part.dart:523`）。有声书略有不同：`importAudiobook` → `importAudioDatabasePackage`（`sync_asset_package_service.dart:421` 直接 `upsertAudiobook`）不清墓碑，但照样把已删的有声书在 host 复活；书被删时（只立 `book` 墓碑）还会落成无书可绑的孤儿有声书。于是 client 到 `:899` 拉墓碑时已经没有墓碑，本机不弹删除确认，第三台设备也收不到。
  - 仅调换顺序修不了：删除候选要用户确认后才删本机，推送仍会在确认前发生。字幕书（standalone SRT）不进自动推送（`audiobooks.part.dart:175` 注释），本地音频只经显式上传，词典走另一套删除传播（BUG-086），均无此路径。
- **[x] ① 已修复** — 提交 `fix(interconnect): host deletion intent vetoes content push`。删除意图在推送之前生效、两层各守一道，判据统一为新纯函数 `peerTombstoneVetoesPush`（`packages/fushi_engine/lib/sync/deletion_propagation.dart`，与删除确认候选同源的 `tombstoneAppliesTo` 时刻仲裁）：
  - client：书 / 有声书 / 视频三个推送阶段开推前先 `GET /api/tombstones`（`_loadHostPushVetoTombstones`，含 `aliasPeerBookTombstones` 别名换算），被墓碑覆盖且本机存在起始时刻早于删除（或未知）的条目不进推送清单；读失败则本阶段不推（不知道删除意图就推正是本 bug），老 host 404 照旧。书用 `localAddedAt`，视频用 `localAddedAt`，有声书用其 srt 行的 `localAddedAt`，并同时认 `book` 墓碑（删书只立 `book` 墓碑却连带删掉 host 的有声书，推回会落孤儿）。删除确认候选照常在整轮末尾产出。
  - host：新可选能力 `PeerPushDeletionGate`（`LocalLibraryHostService.vetoesPeerPush`），server 在书 / 有声书 / 视频 PUT 落盘前问一次，否决 → 读完 body 回 409、不导入、墓碑保留。推送方经新 header `X-Fushi-Present-Since`（`kPeerPushPresentSinceHeader`）报存在起始时刻；**旧版 client 不报 = 未知 = 拒收**，所以反馈里的 Android 3.0.0 客户端连新主机也推不回已删的书。
  - 合法的「删了又重新导入」不受影响：host 本机重新导入不经推送路径；client 删后重新导入 `localAddedAt` 晚于删除 → client 照推、host 放行并按原语义清墓碑。
- **[x] ② 已加自动化测试** — `fushi/test/sync/interconnect_push_respects_host_tombstone_test.dart`（真实 `FushiSyncServer` + `LocalLibraryHostService` + `InterconnectSyncBackend` HTTP 链路）：整轮 `run()` 不推回已删书、host 墓碑保留、本机产出 deleteLocal 候选；删后重新导入照推并清墓碑；host 闸门对未报 / 早于删除的书、有声书（自身墓碑与所属书墓碑）、视频推送回 409；纯判据单测。
- **备注**：相关 BUG-2945（host 删除补写同步墓碑）——那次修好了「host 删了能传出去」，本 bug 是「传出去之前被推送抹掉」。未覆盖：① client 与 host 时钟偏差——`localAddedAt`（client 时钟）与 `deletedAt`（host 时钟）跨机比较，与删除确认候选的既有仲裁同一局限；② 旧版 client 在「删后重新导入」时也会被 host 拒收，升级 client 后自愈；③ 有声书 / 视频的 client 推送过滤未在本测试里走整轮 `run()`（host 闸门已经 HTTP 覆盖），未在真机复测。
