## BUG-4833 · 漫画来源索引只在扫描结束时落盘，中途被杀后同名卷再导一份 Vol 1 (3)
- **报告**：2026-11-17（nmv 优化清单 gap-scanner-7，代码路径复核时发现，非用户实报）
- **真实性**：✅ 真 bug（判据逐行走通，未在真机复现）。来源扫描索引（源相对路径 → 书 uid + 负向表）只在 `_importManga` 的 `finally` 里保存一次（修前 `fushi/lib/src/media/source_library/source_library_scanner.dart:1854-1863`），`record` / `reject` 只改内存（修前 `:412`、`:456-459`）。`finally` 管得了异常，管不了进程被杀——手机上扫描中切后台被系统回收、远端首扫下载几个小时被打断都是。索引丢了之后：
  - `系列A/Vol 1.cbz`、`系列B/Vol 1.cbz`（上一轮已导成 `Vol 1` 与 `Vol 1 (2)`）：A 认领 `Vol 1`（`sameSource`）；轮到 B，标题同为 `Vol 1`、那一行已被在场的 A 认领 → `otherSourceFile` → `DuplicatePolicy.suffix()`（修前 `:435-436`）→ 再导一份 `Vol 1 (3)`，旧的 `Vol 1 (2)` 永远没人认领；
  - 负向表同样丢：判过「不是漫画」的包全部重新开包，远端是重新下载。
- **[x] ① 根因修复** — `1f9ad3f6a23`：`_MangaVolumeTally.attempt` 每卷结束后调 `_MangaSourceIdentity.checkpoint`——这一卷有**丢了找不回来**的索引改动（入库登记 / 记负向表）就落盘一次（一条 preferences 写入），没有是空操作。认领旧行不触发落盘：索引丢了下一轮按同一条查询原样再认领，而索引是整份重写，逐卷落盘认领会让「索引丢失后重扫几千卷已在库的来源」变成几千次整份重写；认领的改动随下一次落盘或收尾保存一起写。卷的结局先记账再落盘，落盘抛错不把已入库的卷记成失败（收尾的整份保存会再写，那次失败照常让扫描报错）。末尾 `finally` 的整份保存保留。游戏扫描器不用改（丢索引后按目录认领已有游戏，不会重复登记）。
- **[x] ② 自动化测试** — `fushi/test/media/source_library/source_library_scanner_test.dart`「索引逐卷落盘：扫到第三卷时进程被杀，重扫仍是两本、不出 Vol 1 (3)」：两个目录各一本同名卷 + 第三卷走 7z 替身，在替身里（前两卷已导完）读出此刻**已落盘**的索引；把库还原成那一刻的索引后重扫，断言仍是 `Vol 1` 与 `Vol 1 (2)`。修前那一刻索引为空、测试即红。同文件「索引丢失后重扫：认领不逐卷落盘，整轮结束时一次写回」钉住认领期间零写入、收尾写回。
- **备注**：导入器写书行与索引落盘之间仍有一个很小的窗口（一卷的量级）。首扫（每卷都是新导入）仍是每卷一次整份重写，总写入量随卷数平方增长——每卷本来就要拷整卷页图，没有实测过几千卷时的占比；要根治得把索引改成逐条存储。逐卷落盘抛错的分支没有自动化测试（没有让 preferences 写入失败的注入点）。待真机：手机上远端漫画来源首扫中途切后台杀进程后重扫。
