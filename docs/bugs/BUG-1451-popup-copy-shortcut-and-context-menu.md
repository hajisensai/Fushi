## BUG-1451 · 查词弹窗无法复制（Ctrl+C 与右键「复制」都无效）

- **报告**：2026-08-02（用户：Windows，阅读器/视频页内查词弹窗，`app_ui_scale=1.5`）
- **真实性**：✅ 真 bug，两条独立根因。
  - **① Ctrl+C：弹窗从来就没有复制兼容层。** 平台事实见 BUG-402——Windows 端 WebView2 走合成模式，fork 的 `flutter_inappwebview_windows` 只转发**鼠标**、不转发**键盘**（`packages/flutter_inappwebview_windows/windows/in_app_webview/in_app_webview.cpp:105` + `custom_platform_view` 无 `setKey`/`SendKeyInput`），所以弹窗 DOM 里永远收不到 `keydown`，浏览器原生 `copy` 永不触发。BUG-402 当年只在**阅读器正文**（`reader_hibiki/caret.part.dart` 的 `_handleKeyEvent`）加了应用层兼容层，**查词弹窗这条路径整个漏修**：`dictionary_popup_webview.dart` 里没有任何按键处理，`assets/popup/popup.js:2950` 的 `__hoshiPopupKeyListener` 也只认制卡/切词条三个动作（`HOSHI_POPUP_KEY_DEFAULT_BINDINGS`），没有 copy。按下 Ctrl+C 后既到不了 WebView2、Flutter 侧也无人接管 → 完全无反应。
  - **② 右键「复制」：选区在 `await showMenu` 之后才读，且失败完全静默。** `dictionary_popup_webview.dart` 的 `_showWindowsContextMenu` 旧实现是「弹菜单 → `await` 用户点击 → **此时才** `_selectedTextAcrossFrames()` 读选区 → `if (text.isEmpty) return`」。选区是**易失状态**，而 `showMenu` 是一个真实 route：打开到点中项之间会发生焦点转移、弹窗可能被 dismiss / 热槽换页、WebView2 也可能因右键落在选区外而清掉 caret。读到的是「菜单关闭那一刻」而非「用户右键那一刻」的状态，任一环变动就拿空串，再被那句裸 `return` 静默吞掉——用户看到的正是「菜单弹出来了，点复制没反应」。同一处的成功路径也**毫无反馈**（Android 的 `ContextMenuItem` 分支一直有 toast，Windows 分支没有），成功与失败在用户眼里长得一模一样，这正是这个 bug 长期被当成偶发忍下来的原因。
  - **附带排除项（非 bug，留作记录）**：用户同时报「菜单位置跑到下面的视频上」。实测复现（`test/pages/popup_context_menu_anchor_test.dart`，scale=1.0/1.5/0.8 三档）证明锚点算法**是对的**——`overlay.globalToLocal(globalPosition)` 精确吸收了 `HibikiAppUiScale` 的 FittedBox 缩放（1.5 档实测 `anchor=(266.7,200)` = `(400,300)/1.5`），菜单左上角与点击点同列、只隔 8×scale 的菜单 padding。用户看到的「跑到下面」是 `showMenu` 正常的向下展开盖住了下方视频画面，不是 BUG-260/261/381/781 那族的坐标回归。该测试已转成常驻守卫，锁住这条以后不许回归。
- **[x] ① 已修复** — `hibiki/lib/src/pages/implementations/dictionary_popup_webview.dart`：
  - **选区在事件源头取快照**：`_showWindowsContextMenu` 进入即 `final Future<String> selectionAtRightClick = _selectedTextAcrossFrames();`（右键按下那一刻发起），菜单只负责选动作；选中后 `await selectionAtRightClick`，快照为空才回退实时读一次（WebView 尚未就绪等边缘情况）。消除对「菜单关闭时刻状态」的依赖。
  - **Windows Ctrl+C 兼容层**：Windows 分支的 WebView 外层新挂 `Focus(canRequestFocus: false, skipTraversal: true, onKeyEvent: _handleDesktopCopyKey)`。平台视图的 FocusNode 是它的后代，`KeyEvent` 沿焦点链冒泡必经此节点。判据复用与阅读器**同一个纯谓词** `readerShouldHandleDesktopCopy`（Windows + 仅 Ctrl + 键 C，`lib/src/shortcuts/reader_space_override.dart`），两条路径不会漂开；未命中一律 `KeyEventResult.ignored` 继续冒泡，制卡 Ctrl+Enter / 切词条 / 宿主关词典键全部不受影响。取的是浏览器原生选区（`_selectedTextAcrossFrames` 穿透同源 iframe），刻意不碰 `window.hoshiSelection`（查词高亮的另一套状态，BUG-368/402 注释）。
  - **消除静默失败**：写剪贴板与成功反馈收口到单一 `_copySelectionToClipboard`，空选区走 `_showCopyToast(copied: false)` 明确提示（新 i18n key `selection_copy_empty`）。三条入口（Windows 右键菜单 / Windows Ctrl+C / Android 原生菜单）统一同一反馈语义；Android 分支也一并收口，不再自己裸调 `Clipboard.setData`。空选区不覆盖剪贴板已有内容这一行为不变。
- **[x] ② 已加自动化测试** —
  - `hibiki/test/pages/popup_copy_shortcut_and_menu_guard_test.dart`（8 例，源码扫描 + 谓词边界）：① 选区读取必须出现在 `showMenu` **之前**、且快照被消费；② 空选区必须有反馈、裸 `Clipboard.setData` 全文件只许出现 1 处（防某条入口绕过统一反馈）；③ Windows 必须挂 `onKeyEvent` 兼容层、判据必须复用同一纯谓词、未命中必须 `ignored`；④ 谓词真值表（Ctrl+Enter / 裸 C / Ctrl+Shift+C / 非 Windows 均不命中）。
  - `hibiki/test/pages/popup_context_menu_anchor_test.dart`（3 例，widget 行为）：复刻真实层级（根 Overlay 手动 entry + `HibikiAppUiScaleNeutralizer` + 弹窗 Positioned 盒），断言 scale=1.0/1.5/0.8 三档菜单左上角都贴住点击点。
  - **两个守卫都做了变异实测**：摘掉源头快照 + 摘掉 `onKeyEvent` → 前者 3 条断言精确变红；把 `overlay.globalToLocal(g)` 改成裸 `g` → 后者 1.5/0.8 两档变红（1.0 档数学等价、不红是正确的）。还原一律用反向替换，未对未提交文件用 `git checkout --`。锚点守卫第一版用「点到菜单矩形的距离」度量，变异实测发现 scale<1 时菜单矩形会把点击点包进去 → 距离恒 0 → **假绿**，已改成对两个方向都敏感的「菜单左上角偏移」。
- **备注**：真机最终验收门（Windows）：弹窗内拖选释义 → ① Ctrl+C → 粘贴到记事本得到所选文字；② 右键 →「复制」→ 同上；③ 什么都不选直接右键复制 → 应看到「未选中文本」提示而不是无反应；④ 回归：制卡 Ctrl+Enter、切词条、Esc 关词典、拖选框选、滚轮滚动均不变。widget/源码扫描测试照不到真实 WebView2 选区与系统剪贴板，故实现状态记为 `implemented_unverified` 直到真机跑完上述四条。
