## BUG-3663 · VN 模式有声书高亮推进时排版变化
- **报告**：2026-10-23（用户：Windows 录屏 `2026-10-23 17-44-22.mp4`，七つの魔剣が支配するII `p-002.xhtml` 段落「　<ruby>赤<rt>しやく</rt>銅<rt>どう</rt></ruby>色の髪をした彼の従兄が、…」，竖排 VN，Klee One 43px / 行高 1.65 / 字重 600）
- **真实性**：⚠️ 录屏实锤，根因未定位。逐帧测量：只在 4.15 s 当前句从第一句换到第二句那一刻变一次——带注音的首列行宽少 6px，VN 墨迹居中随之整体平移 3px（首列 −3px、其余各列 +3px），首列注音的块向起点上移 5px。放大看，第一句高亮时「しやくどう」像一组注音排在「赤銅」旁、没有悬挂到前面的全角空格上；不高亮后变回「しやく」对「赤」、「どう」对「銅」逐字对齐。
  - 已排除（真 Chrome 153 与真 WebView2 155，生产 VN shell + 生产 VN CSS + 原书逐字配对 ruby 标记 + 用户字体设置，按 Dart 实际调用序 `applySentenceAudioCues` → `highlightSentenceAudioCue`，显现速度 0 / 45，包裹模式与 Range 模式）：高亮前 / 第一句高亮 / 第二句高亮三态逐字形坐标零差异；纯 HTML 枚举基字包 span、空格包 span、ruby 整个进 span、只切文本节点、带 active class 六种 DOM 形态，Blink 的注音几何也完全相同。即「懒包裹改了 DOM」本身在 Blink 上不改排版，真实 app 里还有探针没覆盖到的条件。
  - 未能做的：用隔离数据根起 debug 实例读真实 DOM——实例起来了，但阅读器窗口需要前台，用户当时在用桌面，没有继续抢前台。
