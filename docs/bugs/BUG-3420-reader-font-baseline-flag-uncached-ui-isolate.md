## BUG-3420 · 阅读器字体请求每次都在 UI isolate 上同步清竖排基线位、无缓存
- **报告**：2026-10-15（来源：PR #2203 合入后审查）
- **真实性**：✅ 真 bug。`fushi/lib/src/pages/implementations/reader_fushi/webview.part.dart:146`（`/fonts/` 自定义字体）与 `:227`（EPUB 内嵌字体）在 WebView 资源拦截回调里直接同步调用 `clearVerticalBaselineFlag`（`fushi/lib/src/reader/font_vertical_baseline_flag.dart`），没有任何缓存。该函数对 WOFF2 每次整包 `Woff2Decoder.toSfnt`（Brotli 解码 + glyf 重建），对带 `head.flags` 第 5 位的 sfnt / TTC 每次 `Uint8List.fromList` 整份复制 + 整文件校验和——CJK 字体 5–20MB，每章、每个 `@font-face`、每次重排的字体请求都在 UI isolate 上重做一遍。不带这一位的 sfnt 只读表目录，本身不贵。
- **[x] ① 已修复** — 待提交。新增 `VerticalBaselineFontCache`（`font_vertical_baseline_flag.dart`）：按字体身份（规范路径 + 大小 + 修改时间，`keyFor(path, FileStat)`）缓存结论，并发的同一字体请求共用同一个 Future；先在当前 isolate 只读表目录判断要不要改（`_mayCarryVerticalBaselineFlag`，与 `clearVerticalBaselineFlag` 判据一一对应），不需要改的原样返回、不进后台、缓存里只留标记；带这一位的、以及 WOFF2，交 `Isolate.run`（入参复制一次、结果经 `Isolate.exit` 零拷贝带回）。只有改过的字体持有字节，按条数（128）与总字节（96MB）封顶，命中续期。两处调用点改走全局实例 `readerVerticalBaselineFontCache`。失败不留缓存、异常照常抛出。
- **[x] ② 已加自动化测试** — `fushi/test/reader/font_vertical_baseline_flag_test.dart` 的 `VerticalBaselineFontCache` 组（7 条）：同一身份第二次不再解析、并发 5 个请求只解析 1 次、文件变了重新解析、不带这一位的字体不进后台且原样返回调用方字节、WOFF2 结论（不用改）也缓存、按总字节淘汰、默认 `Isolate.run` 路径真改字节。变异实测：把缓存查找改成恒 miss，4 条红（期望 1 次解析实得 2 / 5 次），改回全绿。
- **备注**：权衡——「是否需要改」的判定留在 UI isolate（O(表数)，纳秒级），避免每个干净字体都付一次 isolate 启动 + 整份复制；真重活（WOFF2 解码、整份复制 + 校验和）才进后台。读文件本身已是 `readAsBytes` 异步 I/O，多加一次 `stat()` 取身份。没有测试直接断言「跑在另一个 isolate 上」（纯函数，无可观测差异），靠默认 patcher 走 `Isolate.run` 的代码与那条端到端用例兜。
