## BUG-4507 · 有声书播放中 Android 无响应（ANR）：媒体通知元数据被重复推送几千次
- **报告**：2026-11-15（应用内反馈 WT9uTA4U1_：小米 Android 15，阅读页有声书播放约 16 分钟后 ANR，主线程卡在 `AudioService.buildNotification` 等锁，多条 `pool-29xx` 线程卡在 `AudioService.setMetadata`）
- **真实性**：✅ 真 bug。`fushi/lib/src/media/audiobook/audiobook_session.dart:687` 在控制器**每次** notify（进度 tick、cue 推进、播放态翻转）都调 `_syncMediaNotification`，`:761` 不比较就 `updateNotificationSubtitle`，`fushi/lib/src/utils/misc/fushi_audio_handler.dart`（旧 `updateNotificationSubtitle` 的 `mediaItem.add`）每次都往 audio_service 推一张新卡片——`ag.MediaItem` 的 `==` 只比 `id`，没有任何去重。audio_service 0.18.18 的 Android 端（`AudioServicePlugin.java` `setMediaItem` 分支）每收到一次就 `Executors.newSingleThreadExecutor()` 新开一条线程跑 `synchronized AudioService.setMetadata`，且从不关闭：ANR 时线程池编号已到 2975，几千条线程排队抢 `AudioService` 的对象锁，主线程的 `buildNotification`（同一把锁）拿不到就 ANR。音乐会话 `music_session.dart` 的 `_publishMediaSession` 挂在引擎每个进度事件上，旧实现每次先 `setMediaItemInfo`（无歌词）再 `updateNotificationSubtitle`（有歌词），两张卡交替不同，单靠比较上一张卡去重不住，有歌词时每 tick 仍真推两次。
- **[x] ① 已修复** — `FushiAudioHandler` 的三个卡片入口（`setMediaItemInfo` / `setMinimalMediaItem` / `updateNotificationSubtitle`）统一经 `_pushMediaItem`：与当前卡片按显示字段逐一比较（`mediaItemContentEquals`），内容没变就不推。cue 文本真变了才推一次，平台调用从「每 tick 一次」降到「每句一次」。`setMediaItemInfo` 加可选 `subtitle`，由 handler 一次合成「基础信息 + 当前句」的最终卡片；音乐会话改为每次 publish 只调一次 `setMediaItemInfo(subtitle: 歌词行)`，不再分两次推。
- **[x] ② 已加自动化测试** — `fushi/test/utils/misc/fushi_audio_handler_test.dart`（同一句副标题连推 500 次只发一次、换句才再发；同内容 `setMediaItemInfo` / `setMinimalMediaItem` 只发一次；`clearNotification` 后同卡片能重新推出；带歌词行的 `setMediaItemInfo` 每 tick 重复 300 次只发一次、换行才再发）。
- **备注**：播放态 `playbackState` 走 `setState`，不在本次 ANR 的锁链上，未改。未在真机复测长时间播放。
