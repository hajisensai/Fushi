## BUG-2132 · HUNEX 投影链段 3/段 4 的拒绝路径无诊断，真机读不出断在哪一环
- **报告**：2026-09-03（代理为 WoH/HUNEX 打通游戏内单击查词，准备定位原生几何 provider 的 fail-closed 位置时发现量具本身有哑口）
- **真实性**：✅ 真 bug（工具缺陷类）。HUNEX 原生 exact 几何 provider 在 WoH 上 fail closed（真机 `variants:[]`、`attached=needsCalibration`，见 BUG-2129），而 BUG-2024 已明确记录「lookup worker 在将 glyph/source descriptor 关联到最终 client quad 时 fail closed，**新增的 numeric-only projection-chain trace 尚未在最新 Fushi 构建中完成实机读取**」。投影链共 6 段、20 个显式失败码，但其中**段 3（texture upload identity）与段 4（XYZRHW sprite quad）的全部拒绝路径都直接 `return`，不发任何诊断事件**：
  - `native/galgame_hook/hook/adapters/hunex_gge_adapter.inc` 段 3 的 `!exact_surface` 早退（纹理上传的 CPU surface 与 pending chain 不逐字节相等）；
  - 段 4 的三处 `g_hunex_gge_pending_quad = {}` 早退：quad 形状被拒（返回顶点数≠4 / mode≠1 / 纹理尺寸越界 / offset 非有限）、vertex buffer 三个偏移全取不到、XYZRHW 归一化结果非有限。
  后果：真机 trace 上表现为「compositor 段成功之后就没有下文」，**无法分辨是没走到这两段、还是走到了被拒**，下一次真机会话大概率仍读不出结论。这与 BUG-2024 卡了整整一轮的原因同源。
- **[x] ① 已修复** — 只补量具，**不放宽任何 fail-closed 不变式、不改任何控制流**：
  - `native/galgame_hook/include/hunex_gge_trace.h` 新增 4 个失败码 `kTextureSurfaceMismatch=21` / `kQuadShapeRejected=22` / `kQuadVertexBufferMissing=23` / `kQuadProjectionNotFinite=24`。复用既有 V3 事件布局（`arg7=stage`、`result=failure`），**不改导出 ABI**，也在既有 `failure_value < 64` 的去重位宽内。
  - `hook/adapters/hunex_gge_adapter.inc`：段 3 早退前、段 4 三处早退前各补一次 `PublishHunexGgeProjectionDiagnostic`。两处都**只在能归属到某条语义行时才发**（surface chain 仍 `active`、同 render thread、在 2000ms 新鲜窗内），避免与「本次调用根本不属于正文链」混为一谈；去重键仍是 `(story_line_base, raw_text_hash, stage, failure)`，每行每类只报一次，不会刷爆 512 槽环。
  - `tools/ring_probe.cpp`：`HunexGgeProjectionFailureName` 补上四个可读名，`--dump-hunex-gge-trace` 直接打印。
- **[x] ② 已加自动化测试** — 本条是纯诊断补盲，行为不变式无变化，故不新增行为断言，改由既有守卫兜底并全部重跑：x64/x86 双架构 `ctest` 各 56/56 通过（含 `fushi_hunex_gge_lookup_test` / `fushi_hunex_gge_capture_bridge_test` / `fushi_hunex_gge_selected_text_test` / `fushi_hunex_gge_adapter_test` / `fushi_geometry_provider_registry_test`）；`hunex_gge_trace.h` 自带的 17 条 `static_assert` 在编译期校验布局未漂移；`adapter_structure_test.py` 的分层与 fail-closed 字面量守卫通过。
- **[x] ③ 真机首次读出（2026-09-03 14:5x，WoH pid=10060，模块 `voice_hook_runtime/eda39a62bc5cf7c3/x64/fushi_voice_hook.dll` base=0x7ffdcc150000）** — 文本链经 BUG-2131 修好后立刻用 `fushi_voice_ring_probe.exe <pid> --dump-hunex-gge-trace` 读取，这是该诊断**自实现以来第一次在 WoH 上真正读出**（BUG-2024 记的缺口就此关闭）。结论出乎意料地好：
  - **A 层 scanner=`0x0001ffff`，17 个位全部置位**：`profile_matched, pe64, draw_unique, glyph_unique, input_unique, draw_calls_valid, input_calls_valid, hooks_ready, render_item_call_valid, cursor_transform_valid, body_submit_valid, surface_compose_unique, surface_compose_calls_valid, surface_compose_hooks_ready, projection_entries_unique, projection_graph_valid, projection_hooks_ready`。即**结构扫描、callgraph/unwind/imported-API 校验、投影三入口唯一性全部通过，hook 组已完整安装**。此前 BUG-2024 猜测的「扫描期就没过」被**证伪**。
  - **B 层 `lookup_gate=0x0000000f{requested,profile_admitted,input_hook_ready,shield_ready}`** 四位全开，`capture_quarantine={reason:0(none)}` 未隔离。
  - **glyph 捕获正常**：`evidence=0x00004ffa`、`glyph_metrics={bitmap_w:26,bitmap_h:26,advance24:26.26}`、`render={x:45,y:4}`、`story_frame={line_units:12,line_hash:b51e1bf916917b79}`；`viewport={0,0,1788,1006,scale_x:0.93125,scale_y:0.931481}` 与实测客户区 1788×1006 精确一致。
  - **C 层零条 `projection_chain` 事件** —— 因为**根本没走到投影段**。所有事件都是 `kind=render_item_body_uncorrelated`、`result=4`，`lookup_worker={state:4,selected_failure:6}`，即 `HunexGgeLookupWorkerTraceState::SelectedTextRejected` + `HunexGgeSelectedTextFailure::kNoExactRawLine`。
  - **因此真正的下一个边界不是投影链，而是它上游的「选中文本绑定」**：renderer 捕到的精确 raw 行在选中的 Luna 文本 lane 里找不到逐字节相等的匹配。本条第 5 段原先排的嫌疑（段 2 compose 链 / 段 5 render_target==backbuffer）**均未被触达**，暂不成立也不排除——要等绑定通过后才谈得上。
- **备注**：本条补的四个失败码本轮**未被触发**（链止于更上游），但量具本身已验证可读、且 A/B 两层的读数正是靠它才拿到。⚠️ 原「尚未在 WoH 上真机读取过一次」的状态已解除。（历史记录）本条要解决的前置——按 SOP「每轮只修原始路径上第一个未通过边界」，几何是排在 `text_ready`（BUG-2131）之后的边界，必须等文本链先通。**下一次真机会话的固定动作**：① 确认进程加载的是本轮 helper（比哈希）；② 在 Fushi 里打开 lookup 并完成风险确认——否则 `IsHunexGgeCaptureMutationAdmitted()` 为假，投影链**一条 trace 都不会产生**；③ 推进几句剧情让 body-submit 跑起来；④ `fushi_voice_ring_probe.exe <PID> --dump-hunex-gge-trace`；⑤ 按 scanner_status → lookup_gate_mask → `projection_chain={stage,failure}` 三层定位。**在读到具体失败码之前不得改动投影链的任何一环**——这条链有 24 个失败点，盲改期望收益为负。当前按已有证据排出的嫌疑顺序：段 2（surface compose destination 链，8 个失败码最密集且无真机证据）> 段 5 的 `render_target == backbuffer`（WoH 是全屏 NVL 堆叠、很可能离屏合成后 present）> 扫描期锚点唯一性。段 1 的 glyph 度量与段 3/4 的入口模式已有真机证据支持（`hunex_gge_lookup.h` 记 WoH 1.0 trace 证实 descriptor 与 helper 输出逐位相等；`hunex_gge_adapter.inc` 的链式 unwind 修复注释写明 WoH 的 texture uploader 与 quad builder 都是 MSVC 拆片形式）。
