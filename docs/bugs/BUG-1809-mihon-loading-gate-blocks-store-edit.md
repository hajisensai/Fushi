## BUG-1809 · 漫画扩展页 loading 一位两义：初始化联网刷新期间连添加/编辑仓库都点不动

- **报告**：2026-08-24（修 BUG-1804/1806 时沿代码路径发现，非用户直报；用户在真机上
  「改不了仓库地址」的体感里有这一份）
- **真实性**：✅ 真 bug（设计缺陷，非回归）。

### 根因

`fushi/lib/src/media/manga/mihon/mihon_manager.dart:67` 的 `bool loading` 是**一个位
承担两种语义**，与 BUG-1780 的闸门混用同形：

| 写入点 | 真实语义 | 耗时 |
|---|---|---|
| `_initialise()` `:107` | 「首次进页面，正在准备」——但它盖住了整个流程，**包括最后那个联网的 `_refreshStores()`** | 目录/DB 部分很快；联网部分单请求 30s + 连接 20s 预算（`mihon_extension_store_client.dart:317`、`utils/net/app_http.dart:47`） |
| `_guarded()` `:1036` | 「有写操作进行中，别并发」 | 视操作 |

UI 侧 `mihon_extensions_page.dart:501/508/514` 三个按钮共用同一个门：

```dart
onTap: manager.loading ? null : ...   // 刷新 / 导入 APK / 添加仓库
```

而 `_initialise` 是懒建（`app_model.dart:3569` `unawaited(manager.initialise())`），
所以**每个进程第一次进这个页面，在拉不动仓库的网络下三个按钮会连续灰 20-30 秒**。

于是形成死锁式体验：**拉不到目录 → 想去改仓库地址 → 但正在拉，改不了**。
用户报的「无法修改仓库地址」里有这一份（另一半是
[BUG-1806](BUG-1806-mihon-store-url-not-editable.md) 压根没有编辑入口 +
[BUG-1804](BUG-1804-mihon-store-url-fullwidth-rejected.md) 输入被全角拒掉）。

**注意：禁用本身不是纯粹的错。** 这些操作确实互斥——`_refreshStores` 结尾是
`available = next`（`:306` 整体替换），若 `addStore` 在中途插入一条新仓库并写了
`available`，refresh 那一轮的 `next` 不含它（stores 快照是旧的），会被整体冲掉。
所以不能只是简单放开按钮。

### 修复

- **[ ] ① 未修复** —
- **[ ] ② 未加自动化测试** —
- **两条候选路径（本轮刻意未做，理由见下）**：
  1. **把互斥从 UI 层下沉到状态层**：写操作串行排队而非禁用按钮。
     ⚠ 正撞已知坑——future 链当全局锁会跨 Zone 永久死锁，症状是「第一条过、
     后面全挂」。在以 URL 修复为主题的 PR 里改并发锁，风险与收益不匹配。
  2. **先消除 `available = next` 的整体替换**（改为按 `storeUrl` 归并：保留那些
     不在本轮扫描集合里的条目），并发插入的新仓库条目就不会被冲掉；数据结构层面
     去掉这个特殊情况之后，再放开按钮才是安全的。DB 层面各行主键不同、互不覆盖，
     真正的残余风险只剩「用户恰好在这 30 秒窗口内编辑同一个仓库」——
     `editStoreUrl` 的删+插可能被 refresh 写回旧行。
     这条更干净，是推荐路径。
- **为什么本轮不做**：与 URL 全角问题完全正交；涉及并发正确性，需要独立设计验证
  （尤其路径 1 有明确的死锁前车之鉴）；BUG-1804/1805/1806/1807 那个 PR 已含 4 条
  bug、20 个文件，再堆进来会让 review 失焦。**应单独一条 PR 接手。**
