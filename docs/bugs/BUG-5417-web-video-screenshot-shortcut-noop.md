## BUG-5417 · 网页档（YouTube 等站点视频）按 S 截图 / PageUp·PageDown 换章没反应
- **报告**：2026-11-24（用户：应用内反馈 bsozOyEfi1「s 的截图快捷键好像失效了，类似失效的修一下」；yPaPsQ6JYv「方向左右键也失效」）
- **真实性**：✅ 真 bug（S 与换章部分）。原生播放器页的网页档把截图 / 带字幕截图 / 上下一章写死成「网页档诚实 no-op」：`fushi/lib/src/pages/implementations/video_fushi_page.dart` `_buildVideoShortcutActions` 里 `screenshot: web ? unsupported : …`、`screenshotSubtitled`、`previousChapter`、`nextChapter` 同样处理；控制条门控 `videoWebBackendSupportsControlItem`（`video_fushi/web_source.part.dart`）把截图按钮一律不画。这些门控写在网页档还没有页面截帧之前；后来 `WebVideoPlatformPlayer.screenshot` 已经能用页面 canvas 截非 DRM 站点的帧（暂停 OCR 就靠它，反馈日志里 `video.pause_ocr_tap` 正常），章节也有了站点来源（`setWebChapters`），门控却没跟着改，按 S / Shift+S / PageUp / PageDown 静默吞键。按键其实已经送到页面（不是焦点问题）。
- **[x] ① 已修复** — 网页档要 libmpv 的动作改由纯函数 `videoWebBackendSupportsShortcutAction` 一处判定（只剩着色器对比 / 逐帧 / 小窗）；截图与换章照常执行。`_saveScreenshot` 在 `canCaptureFrame` 为假（Netflix DRM）时给 OSD「该站点画面受版权保护，无法截图」，不再静默；截图按钮按 `canCaptureFrame` 画，与识别画面文字同一判据。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/video_web_backend_shortcut_keys_test.dart`（焦点驱动：默认注册表 → 页级 press-time 解析 → 网页档门控，S / ← / → 都落到会执行的动作；不支持集合钉死）；`fushi/test/media/video/video_web_backend_gating_test.dart`（截图按钮跟 `canCaptureFrame`）。
- **备注**：yPaPsQ6JYv 的 ←/→ 没找到同类门控：网页档的快退快进一直走 `controller.seekRelative`，按键经 Flutter 焦点或 WebView 键盘桥（`webVideoKeyBridgeScript`）都能到同一个执行体。该反馈截图里是站点自己的播放器界面，且整张截进了反馈图，说明当时在「Fushi 播放」档的内置网页播放器页（`WebVideoFushiPage`）。那一页的截图 / 识别画面文字动作本来就是 no-op（页面没有截图保存链路），←/→ 的失效原因还要真机复现才能定位，未在本条修复。已排除两条：① 站点吞键——2026-11-25 用无头 Edge + CDP 在 YouTube 新版播放器（`ytp-delhi-modern`）上实测，点进 `#movie_player` 后真实按下 ←/→/S，挂在 `document` 捕获阶段、document-start 注入的监听（与 `webViewKeyBridgeScript` 同一挂法）都先于 YouTube 拿到键；② 键位解析——默认注册表下 `ArrowLeft` / `ArrowRight` / `KeyS` 都在 `webVideoKeyBridgeScript` 的 token 表里，`resolveDictionaryPopupInputToken` 解析到 seek / 截图。剩下的嫌疑在宿主侧（WebView2 可捕获档的键盘焦点是否真的落进 Chromium、回传后 `_seekRelative` 的基准位置），需要在内置网页播放器页真机加日志复现，已拆为 BUG-5420。内置网页播放器页的截图（S / Shift+S）同样仍是 no-op，要把 `_saveScreenshot` 的去向逻辑抽成两页共用后用 glue `captureFrame` 取帧接上，已拆为 BUG-5421。
