## BUG-3913 · webview-resize-vram-leak
- **报告**：2026-10-31（用户：所有者——「歌词模式占我 7GB 显存」，4K、200% 缩放）
- **真实性**：✅ 真 bug。Release 构建屏外起实例、开有声书《無職転生 21》，窗口 3856 宽来回改尺寸 24 次，按进程采样 `\GPU Process Memory(pid_*)\Dedicated Usage`：fushi.exe 736.6 → 3912.9 MB（每次约 +132 MB），静置不回落；持续播放 / 逐字扫过 / 跨章都不涨，设置页（无 WebView）改尺寸不涨，msedgewebview2.exe 平稳。每次 WebView 改尺寸都重建两样东西，都在系统 / 引擎侧留下永不归还的显存：
  - A. 交给 Flutter 的共享目标纹理：`packages/flutter_inappwebview_windows/windows/custom_platform_view/texture_bridge_gpu.cc` `EnsureSurface`（旧 :190-215，尺寸不等就 `CreateTexture2D(MISC_SHARED)` + 新共享句柄）；引擎 `external_texture_d3d.cc:84-102` 换句柄时 `ReleaseImage` 后对新句柄 `eglCreatePbufferFromClientBuffer`，旧句柄打开的资源不归还（插件侧引用计数平衡、D3D 调试层存活对象不增）。
  - B. WGC 捕获帧池：`texture_bridge.cc` `RecreateFramePoolLocked`（旧 :434-461，判据「尺寸完全相等才跳过」）→ `CreateAndStartFramePoolLocked`（旧 :393-397）按新尺寸 `CreateCaptureFramePool`；旧帧池已 Close、注册表已回收，仍每次留下约一份帧池缓冲。
  - 对照（探针构建按环境变量分别固定两者，同一书、同一 24 次序列，`samples.csv`）：原样 +3176 MB；只固定目标纹理 +1144 MB；只固定帧池 +94 MB；两者都固定 +34 MB。主体是 WGC 帧池重建，两者有交互（只固定纹理仍 +1144），具体持有者未定位到插件以外的哪一层。
- **[x] ① 已修复** — 共享目标纹理与 WGC 帧池按容量分配：Dart `texture_capacity.dart` 算只增不减的容量（256 px 取整、放不下时两维一起 ×1.5、封顶显示器尺寸），经 `setSize` 第 4/5 参数下发；帧池按 `max(捕获源, 容量)` 创建、放得下就不重建，帧带 `ContentSize`；共享纹理按容量分配、内容拷进左上角、内容尺寸变化时把其余部分清成透明；Dart 把 `Texture` 摆成「容量 / 倍率」并 `ClipRect` + 左上 `OverflowBox` 裁回，纹理与屏幕像素 1:1。`SelectSurfaceSize` 按引擎每帧请求的盒子尺寸给对得上的那份纹理，换档那一帧不拉伸。提交 `f65fb6c43e`。
- **[x] ② 已加自动化测试** — `packages/flutter_inappwebview_windows/test/texture_capacity_test.dart`（容量策略：容量内零分配、只增不减、拖到满屏扩容 ≤5 次）；`fushi/test/build/webview_texture_capacity_guard_test.dart`（源码守卫）。只能落到这两层：native（C++ / WGC / D3D11）不在任何 Dart 测试编译面上、本仓无 Windows 原生单测框架；包测试被 CI 包测试循环当 vendored fork 跳过，所以另在 `fushi/test/build` 钉结构。显存数字本身只能真机按上面的采样法复测。
- **修复后实测**（2026-10-31，修复版 Release、同一采样法、窗口 3856 宽改宽度、正文 + 歌词两个 WebView 同在）：改尺寸 24 次 820.8 → 820.7 MB（−0.1）；`wgc_capture.log` 51 次 set-size 全部 `recreate-skip-fits`，帧池重建 0 次、共享纹理换档（`surface-realloc`）0 次。截图（置顶实例，正文 1800→1400 容量内缩小、1400→2600 扩容换档连拍、歌词 2600→1700→3400、退出歌词）：无拉伸、无残影、无边缘垃圾像素；换档期间的「别页重排 → 空白 → 恢复」是阅读器改宽后 `_syncPageSize` 重载章节的既有行为，原样构建同序列截图完全一致。
- **备注**：残余——每新建一个 WebView 仍漏一份帧池 + 共享纹理：进出歌词模式 10 轮，修复版 793.5 → 1460.1 MB（约 +66 MB/轮），原样构建 715.1 → 1226.8 MB（约 +57 MB/轮）。修复版每轮多约 17%，因为首次容量按 256 px 取整（2576×1892 → 2816×2048，面积 ×1.18），这一份泄漏量与分配面积成正比。每次扩容（一路放大最多约 5 次）同样留一份。持有者在引擎 / ANGLE 与 WGC 系统侧，插件无法回收；上游 Flutter issue 草稿在 PR 正文。
- **残余跟进（第二轮，2026-10-31，分支 `fix/batch2-webview-vram`）**：
  - **销毁路径逐项核对**（插件侧，读码 + 引擎源码 `D:/flutter_sdk/flutter_3.47.6/engine/src/flutter/shell/platform/windows/`）：WGC 帧池与捕获会话在 `texture_bridge.cc` `FinalizeFramePoolLifetime` 里都 `IClosable::Close()`，`FramePoolLifetimeRegistry::MarkRetired` 把最后一个强引用 erase 掉；共享目标纹理 / RTV 在 `TextureBridgeGpu::StopInternal` 置空，描述符 `AddRef` 由引擎 `external_texture_d3d.cc:112-115` 每帧 `release_callback` 配平；`GraphicsCaptureItem` 与 `last_frame_` 随桥析构释放；WebView2 控制器 `~InAppWebView` 里 `Close()`、宿主 HWND `DestroyWindow`。**插件侧没有找到漏 Release / 漏 Close 的持有**。
  - **真缺陷 1（生命周期，已修）**：`custom_platform_view.cc` 析构旧代码 `UnregisterTexture(texture_id_, nullptr)` 后立刻随成员释放 `flutter_texture_`（引擎回调的 user_data）与桥；而引擎 `flutter_windows_texture_registrar.cc:79-101` 的注销是异步的（栅格线程任务里才 erase `ExternalTextureD3d`），窗口内栅格线程的纹理回调会落在已释放内存上，描述符也指向桥的成员。修法：回调经 `TextureEndpoint` 找桥（析构先在锁内摘桥）、描述符拷进落点自己的存储；`flutter_texture_` 与落点移交给 `UnregisterTexture` 的完成回调，活到引擎确认注销。这是 UAF 窗口，不是显存泄漏的成因。
  - **真缺陷 2（已修）**：D3D11 延迟销毁——插件设备上 Release 掉的共享纹理 / 帧池缓冲要等立即上下文下一次 `Flush` 才归还（`ID3D11DeviceContext::Flush` 文档）；旧代码销毁 WebView 后从不 Flush，只能等别的 WebView 恰好来一帧（`CopyIntoSurface` 末尾的 Flush）。现在注销完成回调里（栅格线程，与各桥拷帧同一线程，不并发）Flush 一次。它只解释「界面静止时」的滞留，解释不了改尺寸实验里持续播放下仍涨的那部分。
  - **真缺陷 3（已修）**：`FramePoolSizeFor` 用设备倍率的容量建帧池，而着色器链开着时 WebView2 按设备倍率的一半栅格化（`capture_scale_factor = scale / 2`），帧池是捕获源的 4 倍面积。现在按「容量 × 捕获倍率 / 设备倍率」向上取整（`capture_scale_ratio_`，`SetOutputSize` / `SetShaders` 同锁更新）。
  - **首份分配贴身（已改）**：`texture_capacity.dart` `_nextDimension` 首份（current=0）直接返回 needed，不取整不放大；只有扩容才取整 + ×1.5 + 封顶显示器。歌词层 2576×1892 不再放大成 2816×2048。
  - **每实例残留的去除（已改）**：插件侧找不到能回收的持有，残留按第一轮对照实验在引擎 / ANGLE 与 WGC 系统侧。所以不再每轮新建歌词 WebView：`reader_fushi_page.dart` 把 `_lyricsController` 改成 `_lyricsMode ? _lyricsWebViewController : null` 的派生 getter，`lyrics.part.dart` `_buildLyricsOverlay` 在非歌词模式下把挂上过的歌词 WebView（同一个 `_lyricsWebViewKey` GlobalKey）停进 `fushi/lib/src/webview/parked_webview_slot.dart`（Offstage + ExcludeFocus + TickerMode 关，按离开时量到的尺寸摆），`_exitLyricsMode` 不再丢控制器，`_toggleLyricsMode` 进入时直接对复用实例 `_loadLyricsPage()`。整页存活期间歌词 WebView 只创建一次；查词弹窗等其它「频繁新建」的 WebView 仍各自有这份每实例残留，未处理。
  - **测试**：`packages/flutter_inappwebview_windows/test/texture_capacity_test.dart`（贴身首份、首次扩容才取整）；`fushi/test/webview/parked_webview_slot_test.dart`（按阅读器真实结构进出覆盖层 5 轮：同一个 State、不 dispose；停放不绘制 / 不吃点击 / 拿不到焦点 / 动画暂停 / 尺寸保持）；`fushi/test/pages/reader_lyrics_webview_reuse_guard_static_test.dart`（阅读器接线源码守卫）；`fushi/test/build/webview_texture_capacity_guard_test.dart` 新增帧池捕获倍率、析构注销顺序 + Flush、首份贴身三组源码守卫。
  - **未验证**：**显存数字没有重新实测**（本轮没有跑真 app 采样 `\GPU Process Memory`）；歌词 WebView 复用只在 widget 层验证了搬家保活，没有在真 Windows / Android / iOS / macOS app 上走进出歌词模式。`dart tool/heavy.dart -- flutter build windows --debug` 退出码 0（插件 C++ 改动编译通过，无新增 error）。
