## BUG-4241 · 互联：主机能力探测 / GET 与选路缓存不走 P2P 隧道，直连不通时远程复习找不到主机
- **报告**：2026-11-08（agent：Linux Phase 4 互联验证，Windows host（带 fushi_p2p.dll）+ Linux 客户端，客户端到 host 直连端口全部拒绝，只剩 `p2p://`）
- **真实性**：✅ 真 bug，两处根因，症状同为「直连不通时 P2P 后备用不上」。两处根因均已由修复前红的自动化测试确认（见 ②）。
  - 实测：直连被挡后，同步（书进度双向）、远端查词、制卡到 host 都经 P2P 隧道正常（直连 UDP 打洞与强制 n0 中继两种路径都过）；但「复习 › 复习已配对设备的牌组」显示「没有已配对设备提供远程复习」。放开直连后同一页立刻列出 host；先经直连进入 host 牌组再挡直连，30 秒内点开牌组报「连不上已配对设备」，超过 30 秒重试即经隧道正常复习，评分落到 host。
  - 根因 1：`fushi/lib/src/sync/interconnect_host_client.dart:185-232` `InterconnectHostClient.getFromHost` 直接遍历库里存的候选（`:200-201` `interconnectEndpointUri(candidate.url, path)`），没有像 `postJson` 走的 `InterconnectPostTransport.post`（`fushi/lib/src/sync/interconnect_post_transport.dart:153`）那样先过 `rankInterconnectCandidates`，`p2p://` 候选从不经 `_resolveTransport` 换成本地转发口，拼出 `p2p://<nodeId>/api/capabilities` 交给 `http.Client`，抛错被 `catch (_) { continue; }` 吞掉。于是 `declaresCapability`（`:166`）在只有 P2P 可达时返回 null，所有按能力探测列主机的入口都把 host 判成不可用：远程复习 `fushi/lib/src/srs/srs_remote_store_client.dart:64`（经 `fushi/lib/src/sync/video_remote_targets.dart:78` `probeInterconnectHostTargets`）、视频遥控 `fushi/lib/src/sync/video_remote_client.dart:51`、AI 中继 `fushi/lib/src/ai/ai_interconnect_relay.dart:111`；同一个 GET 通道上的远程复习媒体 `srs_remote_store_client.dart:69` 与视频遥控快照 `video_remote_client.dart:58` 也只走直连。视频遥控与 AI 中继是按代码路径推断，未单独实测。
  - 根因 2：`fushi/lib/src/sync/interconnect_peer_addresses.dart:234-236` 选路缓存命中（30 秒 TTL）时只把缓存的胜出地址 resolve 后放组首，其余成员原样返回（`:262`），其中的 `p2p://` 没有换成转发口。缓存的直连地址一旦失效，消费方「顺序试组内其余地址」试到的是不可拨的 `p2p://`，请求整体失败；`:195` 注释写的「缓存的地址失效时消费方会顺序试组内其余地址，不会因为缓存而连不上」对 P2P 不成立。直连刚断的 30 秒内，远程复习的 `postJson` 与同步首个请求都会因此失败（同步那次只在 SyncRunReport 里记了一条 `prune root spill (list root)` 连接被拒，随后会话重选路恢复）。
- **[x] ① 已修复**（06bcaba20e）— `InterconnectPostTransport` 新增唯一候选来源 `_rankedCandidates`（启用条目 → 按 `onlyCandidate` 过滤同 host 且凭据一致 → `rankInterconnectCandidates`）与基于它的 `get`；`post` 与 `get` 共用，`InterconnectHostClient.getFromHost` 改为委托 `_transport.get`，删掉 GET 自己那套候选遍历。`_rankGroup` 重写：缓存命中 / 新选路只决定组内顺序，最后整组统一过 `_dialable`（每条 `p2p://` 经 `_resolveTransport` 换成本地转发口，换不出的去掉），单地址组同样处理；胜出的 `p2p://` 这次换不出转发口时不缓存。缓存层新增 `reportInterconnectCandidateUnreachable`（缓存的胜出地址传输层失败 → 立即作废）与 `reportInterconnectCandidateReached`（缓存刚作废时记下实际到达 host 的地址），由 `post` / `get` 与同步选路 `resolveReachableFushiCandidate` 上报，失效直连不再在 30 秒 TTL 内排组首；没有延迟、重试。信任面不变：只对已配对 host 的已存地址走隧道，每个请求照带 per-device 凭据，host 照常逐请求验 token。取舍：组里有 `p2p://` 时选路会先建好本机 iroh 端点并开回环转发口（`forwardTo` 只绑 127.0.0.1 监听口，真正的隧道连接仍在第一次有请求经过时才建），这样直连刚断的那一次请求就能落到隧道。顺带：远程复习 / 视频遥控 / AI 中继的一次性能力探测 client 探完 `cancelPending()` 关连接（原 GET 每次自建自关，改走 transport 后由探测方关）。
- **[x] ② 已加自动化测试** — `fushi/test/sync/interconnect_p2p_fallback_test.dart`：真实 `FushiSyncServer`（挂远程复习库服务）+ 假 P2P resolver 把 `p2p://` 换成 host 自己的 P2P 监听口，直连是刚关掉的本机端口：① 只有 `p2p://` 可达时 `declaresCapability` 为 true，`filterSrsRemoteStoreTargets` / `probeInterconnectHostTargets` 列出该 host；② 选路缓存记着已失效的直连时，`postJson`（`hello`）与 `getFromHost`（卡面媒体）立即经组内 `p2p://` 成功，且之后选路不再探测、组首已是隧道地址；③ 经隧道口不带 / 带错配对凭据 → 401（`SyncAuthFailureKind.pairingRejected`），host 复习库一次都没被调用。修复前 ①② 红（`Expected: true Actual: null`、`unreachable`），③ 修复前后都绿（安全护栏）。真机复测（Windows host + Linux 客户端，直连端口被挡）：远程复习列出主机、出卡并评分落到主机；视频遥控暂停 / 继续主机播放；牌组打开中直连断开后立即经隧道出卡、不再报「连不上」；强制中继下同样通过。
- **备注**：P2P 隧道本身依赖 n0 公共基础设施（pkarr / DNS 发现、`*.relay.n0.iroh.link` 中继、QAD）；host 公布的 `p2p://` 带 `relay=` 与 `addr=` 拨号提示，所以有直连提示时可以不经发现直接打洞。
- **English summary**:
  - **Symptom**: with P2P on and the direct port to the host unreachable, sync, remote lookup and mining to the host all work over the P2P tunnel (both the hole-punched UDP path and the forced n0 relay path), but Review › "Review a paired device's decks" says "No paired device offers remote review". Unblocking direct lists the host at once. If direct dies while the host's decks are open, opening a deck fails with "Can't reach the paired device" for about 30 s; after that, Retry works over the tunnel and grades land on the host.
  - **Root cause 1**: `InterconnectHostClient.getFromHost` (`fushi/lib/src/sync/interconnect_host_client.dart:185-232`) iterates the stored candidates directly instead of going through `rankInterconnectCandidates` like `InterconnectPostTransport.post` (`interconnect_post_transport.dart:153`). A `p2p://` candidate is never resolved to the local forward port, so the request goes to `p2p://<nodeId>/api/capabilities`, fails, and the error is swallowed. `declaresCapability` (`:166`) therefore returns null when only P2P can reach the host, and every capability-probed feature treats the host as unavailable: remote review (`srs_remote_store_client.dart:64` via `video_remote_targets.dart:78`), video remote (`video_remote_client.dart:51`), AI relay (`ai_interconnect_relay.dart:111`), plus the GET-based review media (`srs_remote_store_client.dart:69`) and video remote snapshot (`video_remote_client.dart:58`). Video remote and AI relay are inferred from the code path, not tested separately.
  - **Root cause 2**: on a route-cache hit (30 s TTL), `interconnect_peer_addresses.dart:234-236` resolves only the cached winner and returns the rest of the group unconverted (`:262`), so the `p2p://` member is not dialable. When the cached direct address has just died, the "try the remaining addresses in order" fallback hits an undialable `p2p://` and the whole request fails; the comment at `:195` doesn't hold for P2P.
  - **Status**: fixed in 06bcaba20e; both root causes confirmed by tests that fail before the fix.
  - **Fix**: `InterconnectPostTransport` now has one candidate source, `_rankedCandidates` (enabled entries → same-host + same-credential filter for `onlyCandidate` → `rankInterconnectCandidates`), used by both `post` and a new `get`; `InterconnectHostClient.getFromHost` delegates to `get`, and its separate candidate loop is gone. `_rankGroup` was rewritten: the cache or a fresh race only decides the order, then the whole group goes through `_dialable` (every `p2p://` resolved to its local forward port via `_resolveTransport`, unresolvable ones dropped). A `p2p://` winner that can't be resolved is not cached. The cache gained `reportInterconnectCandidateUnreachable` (a transport failure on the cached winner evicts it at once) and `reportInterconnectCandidateReached` (after an eviction, remember the address that actually reached the host), reported by `post`, `get` and sync's `resolveReachableFushiCandidate`, so a dead direct address is no longer preferred for the 30 s TTL. No sleeps or retries. Trust is unchanged: only stored addresses of already-paired hosts are tunnelled, every request still carries the per-device token, and the host still checks it per request. Trade-off: when a group has a `p2p://` address, ranking starts the local iroh endpoint and opens the loopback forward port (`forwardTo` only binds a 127.0.0.1 listener; the tunnel connection itself is still made on the first request through it), so the first request after direct dies already lands on the tunnel. Also: the throwaway capability-probe clients (remote review, video remote, AI relay) now call `cancelPending()` when done.
  - **Tests**: `fushi/test/sync/interconnect_p2p_fallback_test.dart`, with a real `FushiSyncServer` (remote review store attached), a fake P2P resolver mapping `p2p://` to the host's own P2P listener port, and a just-closed local port as the direct address: (1) only `p2p://` reachable → `declaresCapability` is true and `filterSrsRemoteStoreTargets` / `probeInterconnectHostTargets` list the host; (2) cached direct winner dead → `postJson` (`hello`) and `getFromHost` (card media) succeed at once through the group's `p2p://`, and the next ranking doesn't probe and puts the tunnel first; (3) no / wrong pairing token over the tunnel port → 401 (`pairingRejected`), the host's review store is never called. Before the fix (1) and (2) fail (`Expected: true Actual: null`, `unreachable`); (3) passes before and after (security guard). Real-app re-run (Windows host, Linux client, direct port blocked): remote review lists the host, a card opens and the grade lands on the host; video remote pauses / resumes host playback; direct dying while decks are open falls over to the tunnel at once (no "Can't reach"); the relay-only variant passes too.
  - **Note**: the tunnel relies on n0's public infrastructure (pkarr / DNS discovery, `*.relay.n0.iroh.link` relays, QAD). The host's `p2p://` address carries `relay=` and `addr=` dial hints, so with direct hints it can connect without discovery. Security: the fix only routes existing features through the existing encrypted tunnel; the host still checks the per-device pairing token on every request, and the client-side forward port binds to `127.0.0.1` only.
