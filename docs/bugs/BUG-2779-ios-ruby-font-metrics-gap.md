## BUG-2779 · iOS 换字体后振假名仍偏向上一列（固定 -0.2em 只对 Hiragino 成立）
- **报告**：2026-09-29（用户：「之前修 mac 的振假名穿透到上一页好像在 ios 这里竖排的振假名靠近上一行还是没有改善」，截图为 iOS 竖排、Klee One 字体，「稀」的「まれ」贴在上一列「仕方ないだろ」的高亮边上）
- **真实性**：✅ 真 bug（WebKit，字体相关）。根因 `fushi/lib/src/reader/reader_content_styles.dart` 的 `_webKitRubyAnnotationCss`：BUG-2724 用固定 `margin-block-end: -0.2em` 把注音拉回基字，那是按 Hiragino 标定的。WebKit 里注音与基字之间夹着两截空白——① 基字内容区（ascent+descent）超出 em 盒的部分；② 注音盒 `line-height: normal` 的半行距——都由字体度量决定。Hiragino 的内容区≈1.045em，① 几乎为 0；Klee One（app 预置字体，hhea 1160/−288）内容区 1.5em，① 就有 0.25em。
  - 实测（iOS 26.5 模拟器 Safari，生产 iOS 正文 CSS + Klee One，22px、行高 1.65）：注音 em 盒离基字 em 盒 6.08px（Hiragino −0.92px）；墨迹间距竖排 8.33px / 横排 9.33px（Hiragino 1.0 / 1.33px）——注音离本列远、贴上一列，与用户截图一致。
  - 排除项：`text-box: trim-both ideographic`（加在 ruby / rt / 两者）竖排逐像素无变化；canvas `emHeightAscent` 在 WebKit 上等于字体 ascent，拿不到 em 盒。
- **[x] ① 已修复** — 新增 `fushi/lib/src/reader/reader_ruby_metrics_script.dart`（`kReaderRubyMetricsJs`，由 `webview.part.dart` 的 `__fushiEngine.install` 注入，三种 view-mode 共用）：在页面里量一个真实 `<ruby>`——基字 Range 的块轴尺寸即内容区、`<rt>` 盒的块轴尺寸即注音盒；竖排 em 盒在内容区里居中，横排 em 盒以 canvas 量的汉字墨迹中心为中线——把两截空白折成注音字号的倍数写进 `--fushi-ruby-pull`。Apple 注音规则改为 `margin-block-end: calc(-1em * var(--fushi-ruby-pull, 0.1) - 0.1em)`，变量缺省即旧的 −0.2em。字体就绪、`document.fonts` 加载完成、`#fushi-reader-style` 被实时替换时各重量一次；只在 Apple CSS 打出的 `--fushi-ruby-snap: 1` 存在时工作。注音在流中的高度早被 BUG-2472 的负 `margin-block-start` 抵消为 0，写变量不改行盒 / 分页几何。同一装置复测（真 CSS + 真脚本）：Klee One 竖排墨迹间距 1.0px、横排 1.33px（等于修前 Hiragino）；Hiragino 0.67 / 0.67px，不压字。
- **[x] ② 已加自动化测试** — `fushi/test/reader/reader_ruby_metrics_behavior_test.js`（node 真执行 `kReaderRubyMetricsJs`，喂模拟器实测矩形：Klee 竖排写 0.813、Hiragino 0.106、横排区间、无开关 / 无 ruby 不写），由 `reader_ruby_metrics_script_test.dart` 驱动并守住引擎注入点；`vertical_ruby_line_box_contain_guard_test.dart`「BUG-2779」：iOS / macOS 横竖 × 分页 / 连续 / VN 的注音规则必须吃 `--fushi-ruby-pull` 且缺省合计 0.2em、带开关，Blink 平台都不发；BUG-2724 两条正则同步认 `calc(-…)`。
- **备注**：验证在 iOS 模拟器 Safari（同一 WebKit 与字体，页面装生产 CSS 与脚本），不是阅读器 WKWebView 本体。一本书里正文与标题字体不同时只按第一个带注音的元素量（比值随字号缩放，但不随字体族变）。
