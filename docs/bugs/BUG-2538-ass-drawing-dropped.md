## BUG-2538 · ASS \p 矢量绘图被整条丢弃（招牌白底遮罩不画）
- **报告**：2026-09-14（Discord 用户 moonbeam：与 Media Player Classic 同帧对照，「the white fill not being drawn properly in Fushi」——招牌手写字在 Fushi 里糊成一团，MPC 里干净）
- **真实性**：✅ 真 bug。`packages/fushi_audio/lib/src/parsers/subtitle_markup.dart` 里 `\p<n>` 只拨一个 `bool active`，绘图模式下标签块之外的正文被逐字符丢弃（TODO-799 为了不把坐标串当文字渲染），不产出任何图形对象；随后 `ass_parser.dart` 见 `plainText.isEmpty` 直接 `continue` 跳过整条 Dialogue。典型招牌做法是先用 `{\1c&HFFFFFF&\p1}m … ` 画一块白底盖住画面原文、再在上层写译文——白底在 Fushi 里根本不存在，原文透出来叠在译文下面，观感就是「白色填充没画对 / 字糊」。
- **[x] ① 已修复** — 解析：`_DrawingState` 收集命令正文、缩放级（`\pN` 坐标 ÷ 2^(n-1)）、`\pbo` 与首个命令字符时刻的行内样式快照，扫描结束解析成 `SubtitleDrawing`（归一化路径 + 包围盒，复用 `\clip` 的命令解析 `parseAssDrawingSegments`），挂到 `SubtitleMarkup.drawing` / `drawingStyle`。产出边界：`AssParser.parseString(includeDrawings:)` 默认不产出无正文的绘图事件（字幕列表 / 制卡 / 导入持久化不见空行），只有播放路径 `video_subtitle_source.dart` `_readAndParse` 开；`VideoPlayerController.setCues`/`setSecondaryCues` 把 `AudioCue.isRenderOnly` 的事件分流到渲染专用流（`activeDrawingCues` / `secondaryActiveDrawingCues`），对白流（`cues`/`currentCue`/活动集）零污染；`VideoBookRepository.saveCues`/`saveSubtitleSelection` 落库过滤。渲染：overlay 把绘图 cue 并进同层活动集（同一套分组 / `\pos` / Layer z 序），`_buildCueBox` 对绘图 cue 出 `AssDrawingPainter`（阴影 < 描边 < 填充，`\blur` 语义与文字同款），盒尺寸 = 包围盒 × 视频内容矩形缩放、按包围盒参与 `\an` 对齐（libass/VSFilter 语义）；纯字幕模式不画。
- **[x] ② 已加自动化测试** — `fushi/test/media/audiobook/ass_drawing_parse_test.dart`（路径 / 包围盒 / 样式快照 / `\p2` 缩放 / `\pbo` / 贝塞尔 / 绘图后接文字 / 无 PlayRes 与非法串 / `includeDrawings` 双态 / 同起始时间稳定排序）；`fushi/test/media/video/video_subtitle_ass_drawing_render_test.dart`（控制器分流 + 活动集、白填充盒按 `\an7\pos` 落位 200×100、纯字幕模式不画、painter 子路径闭合与非零环绕）。
- **备注**：未做：`\t(\clip)` 动画、`\3a`/`\4a` 独立 alpha、样式表颜色高字节 alpha（`assColorToArgb` 仍一律不透明，改它会连带所有 `&H80000000` 半透明阴影，另开）。
