## BUG-1124 · local-audio-cache-weak-hash
- **报告**：2026-07-26（用户：）
- **真实性**：✅ 真 bug。根因 `hibiki/lib/src/utils/misc/local_audio_db.dart:301`（修复前）：`_localAudioCacheKey` 把 16 位 UTF-16 码元**整体** XOR 进 FNV-1a（`hash ^= codeUnit`，FNV-1a 的字节口径被喂宽单元），CJK 每字符扩散轮数从 UTF-8 的 3 轮降到 1 轮，碰撞率显著升高。生日搜索（种子 42，40 万样本内第 151719 个即命中）找到真实碰撞对：`(source='jpod', file='肌陒衎柚.mp3')` 与 `(source='jpod', file='汅肘鹾圃.mp3')` 弱键同为 `a0c11ea4`。碰撞后果沿 `extractBlob` 的「缓存已存在即早退复用」路径放大——两个不同词条塌缩到同一个 `local_audio_<key>.<ext>` 缓存文件，后查的词永远播放先查词条的音频。
- **[x] ① 已修复** — `6e9a38c46`。根因修复：`_localAudioCacheKey` 改为 UTF-8 逐字节强口径 `fnv1a32Hex(utf8.encode('$source\n$file'))`，实现收敛到新建的 hibiki_core 单一真相源 `packages/hibiki_core/lib/src/utils/stable_hash.dart`（G3：全仓 5 份 FNV-1a 手写副本一并收敛，video_manifest / deletion_propagation / audiobook_storage / hibiki_manga_ocr_host 四处输出逐字节不变，金标先行固化）。存量缓存迁移：`extractBlob` 对旧弱键文件做惰性 `renameSync`（对齐 `audiobook_storage.dart` `ensurePersistDir` 的 renameSync 先例；缓存以文件为粒度，可精确逐键迁移，无需整目录方案），保住「源库已被移除时缓存副本仍可复用」的既有语义；ASCII 键两口径同值（码元全 < 0x80），存量 ASCII 缓存零迁移。**迁移决策**：旧键文件若恰是碰撞对中先写入的另一词条的字节，rename 会把该字节带到新键名下——但这正是修复前已发生的错播字节，且新口径下另一词条此后会拿到自己独立的缓存文件，错误不再持续放大；碰撞概率（实测 15 万级样本才出现一对）远低于为此放弃「源库移除后缓存可复用」语义的代价，故选择无条件 rename。
- **[x] ② 已加自动化测试** — `hibiki/test/utils/local_audio_db_cache_migration_test.dart`（真实碰撞对经 `extractBlob` 提取到两个不同缓存文件且字节各自正确 / 旧弱键 CJK 缓存被惰性 rename 到新键名且源库缺失仍可复用 / ASCII 键文件名不漂移）+ `packages/hibiki_core/test/stable_hash_test.dart`（弱口径碰撞实证 + 强口径区分 + 全部 5 处收敛口径的金标向量锁死）。
- **备注**：与侦察计划 S5-utils-dedup-1 [G3] 的差异：原 plan 让 local_audio_db 保持弱口径输出不变，本轮按主代理指令把弱口径升级为强口径（即本 bug 的根因修复）并补惰性迁移。
