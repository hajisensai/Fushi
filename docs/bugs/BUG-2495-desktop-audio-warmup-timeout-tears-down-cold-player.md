## BUG-2495 · 桌面查词发音预热 2s 预算到期，反把正在冷启动的播放器拆掉（BUG-1015 复发）
- **报告**：2026-09-13（用户贴错误日志：`DesktopAudioPlayback.warmUp` / `TimeoutException after 0:00:02.000000: Future not completed`，栈 `desktop_audio_playback.dart:143`）
- **真实性**：✅ 真 bug。根因 `fushi/lib/src/utils/misc/desktop_audio_playback.dart:143`（修前）：惰性预热（BUG-1015/BUG-1690）在 `play()` 返回后用 `processingStateStream.firstWhere(completed).timeout(2s)` 等静音片播完。这个 2 秒表**开始得太晚、又算错了对象**——just_audio 的 `play()` 返回只代表原生 play 请求被接受，mpv 是在 `pause=false` 之后才**首次打开 WASAPI / CoreAudio 输出设备**，休眠的 HDMI / 蓝牙设备唤醒经常超过 2s。到期后异常被 catch 记成错误、串行队列放行真实播放；真实周期第一步 `stop()` 走 `just_audio.dart:1016 → _setPlatformActive(false) → disposePlayer`，把**正在冷启动的 mpv 播放器整个销毁**——预热白做，真实那次自己吃冷激活空窗，正是 BUG-1015 的原症状「本次启动第一次发音没声」。翻过 just_audio 0.9.42 / just_audio_media_kit 2.1.0 / media_kit 1.2.6 三层：`completed` 的置位链（mpv `eof-reached` → `isPlayingStateChangeAllowed` → wrapper `_currentIndex == medias.length-1`）在 `open()` 阶段由 `playlist-playing-pos` 回填、早于 `play()`，没有确定性丢事件的 bug；问题就是「设备热没热」被一个固定时钟裁决。另：just_audio 0.9.x 丢掉平台 `errorCode`，媒体后端出错只表现为 `processingState → idle`（随后自动停用平台），原实现只等 `completed`，设备打不开时也是白等到超时。
- **[x] ① 已修复** — `desktop_audio_playback.dart` `_ensureWarmUpQueued`：等待改由**播放器自己的终态**放行——`completed`（静音片播完，设备已出声）或 `idle`（平台出错被 just_audio 停用），不再有「预算」；时钟只保留为 `_warmUpStuckValve`（15s）卡死保险丝（设备永远打不开时不能把串行队列钉死、让此后所有查词发音全哑）。无论结果都 `logDiagnostic('DesktopAudioPlayback.warmUp', 'silent clip reached <state> in <ms>ms')`，下次日志能定量看到设备冷启动多慢。提交 `d42d166dc6`。
- **[x] ② 已加自动化测试** — `fushi/test/utils/misc/desktop_lookup_audio_warmup_test.dart` 新增 `BUG-2495: warm-up wait is driven by player terminal states, not a fixed budget clock`：断言预热 body 的 `firstWhere` 终态为 `completed || idle`、超时只能引用 `_warmUpStuckValve`（禁内联 `const Duration`）、保险丝 ≥10s、且 `logDiagnostic` 带 `elapsedMilliseconds`。旧代码在前两条断言上都红。提交 `d42d166dc6`。
- **备注**：播放器冷启动耗时属 media_kit 平台行为，本轮未做 Windows 真机复测（缺口）：需要冷启动 app → 首次查词发音 → 读日志页诊断分节的 `DesktopAudioPlayback.warmUp` 行，确认终态 `completed` 且首次发音有声。`stop()` 每周期销毁并重建 mpv 播放器是 just_audio 的既定行为（BUG-342 串行队列围绕它设计），进程内首次的 libmpv 加载 + 首次开设备才是「冷」的部分，本轮不改这个模型。
