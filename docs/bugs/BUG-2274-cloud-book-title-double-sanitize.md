## BUG-2274 · 云盘远端书标题未反解：书架去重二次 sanitize 成 %253A，本地已有的书仍显示为远端待下载
- **报告**：2026-09-08（用户：群内用户经 Google 云盘同步；截图：本地 `Love, Death and Robots: The Official Anthology` 与远端待下载 `Love, Death and Robots%3A The Official Anthology` 并存，删本地重下仍复现）
- **真实性**：✅ 真 bug。根因 `fushi/lib/src/sync/cloud_remote_book_client.dart:83`——`RemoteBookInfo.title` 直接取云盘书文件夹名，而文件夹名是 `sanitizeTtuFilename(title)`（`packages/fushi_engine/lib/sync/ttu_filename.dart:13-30`，`:`→`%3A`、`%`→`%25`）。书架去重 `dedupeRemoteBooks`（`packages/fushi_engine/lib/sync/fushi_library_host_service.dart:735-744`，调用点 `reader_history/remote.part.dart:103-107`）对远端 title 再跑一次 `sanitizeTtuFilename` → `%253A` ≠ 本地 `bookKey` 的 `%3A`，纯函数恒定错配，与本地是否存在这本书无关，所以「删了重下还是这样」；同一个值又直接当卡片标题渲染，所以用户看到 `%3A`。同步 diff（`sync_orchestrator/books.part.dart:31`）走同一条 `sanitize(r.title)`，云盘路同样错配（每次同步把本地书判成远端缺、远端 `%253A` 判成本地缺）。互联 host 那条路返回 raw title，没坏。
- **[x] ① 已修复** — `954fe927b1`：引擎 `ttu_filename.dart` 加成对的 `unsanitizeTtuFilename`（sanitize 时 `%` 恒编成 `%25`，单趟解码无损）；`CloudRemoteBookClient.listRemoteBooks` 把文件夹名反解成 raw title（下游去重 / diff / 卡片各自派生 key）；`sync_compare_dialog.dart` 的私有 `_unsanitize` 副本收口到引擎函数。
- **[x] ② 已加自动化测试** — `fushi/test/sync/ttu_filename_roundtrip_test.dart`（8 组标题 sanitize→unsanitize 恒等、反解后再 sanitize 等于文件夹名、直接拿文件夹名当 title 会二次编码的反例）；`fushi/test/sync/cloud_remote_book_client_test.dart`「BUG-2274：文件夹名反解成 raw title，本地同名书按 bookKey 去重得掉」（真 client + 可控后端，断言标题无 `%3A` 且 `dedupeRemoteBooks` 剔除）；`fushi/test/sync/remote_cover_dedup_test.dart`「BUG-2274：标题含冒号…」正反例。
- **备注**：用户已存在的云端文件夹名不需要迁移（文件夹名本来就是 sanitize 结果，只是读侧漏了反解）；升级后书架上那张多余的远端卡自然消失，同步 diff 也不再对这类书反复推/拉。`onedrive` / `webdav` 走同一个 `CloudRemoteBookClient`，一并修好。
