## BUG-5267 · gen4 迁移对拍：同库另一个 profile 占走了 `srs_entities` 行的实体，`entities` 判新代多出、整份撤回
- **报告**：2026-11-22（应用内反馈 n4WhWEKPtQ，同签名 hkSFKPTcsV：Android 3.4.0-debug.31429，复习库升级 `aborted` / `profileVerdict: fail`）
- **真实性**：✅ 真 bug（对拍的基准用错了口径；旧库与新代的数据都没坏）。报告签名：第二个 profile 的 `entities` onlyNew 3，三个 ID 恰是它加盐的内置实体（`v5(NS,'<uid>/builtin-deck/default')`、lapis、fushi_card 笔记类型）；主 profile 的 `imported.devices = 2`，它的操作里也有这三个 ID 的身份记录。
  - **根因**：协议 3 的 `srs_entities` 以实体 ID 为主键、全库共用（`native/fushi_fsrs/src/store/schema.rs:136`）。`project_entity`（`store/sync2/mod.rs:1271`）遇到已有行：内容相同不改写（行留给先落投影的 profile），不同按规范 JSON 小者改写、`ON CONFLICT` 连 `profile_uid` 一起换。两个 profile 的操作日志里都有同一个实体的身份记录时（收段不经本机写入的归属核对 `sync2/ownership.rs`，集合里另一台设备写的就会进来），只有一个 profile 名下有这一行。对拍 `compare.rs` `against_protocol_3` 的 `entities` 一类却按 `SELECT id FROM srs_entities WHERE profile_uid = ?` 取协议 3 一侧，新代按集合各存各的 → 丢了行的那个 profile 判「新代多出」，整份撤回。行是笔记时，协议 3 的缓存全量刷新也按 `profile_uid` 列笔记（`store/caches.rs:225`），丢了行的 profile 的缓存里没有这条笔记，`notes` 一类同样判不同。
- **[x] ① 已修复** — 只改对拍口径，不加容差：`store/gen4/compare.rs` 新增 `taken_entities`，在新代有、本 profile 名下没有的 ID 里找「行在库里、归了另一个 profile、本 profile 已应用的操作（`sync2_ops` 的身份记录，经 `load_op` 解出）里有它」的，记进 `Collisions::entities`，`entities` 一类的协议 3 一侧按本 profile 的操作集合算进它们；证不出的照常报差异。其中的笔记同时进 `Collisions::notes`，缓存层与按规范 ID 比的几类照「撞车的笔记」口径不比它与它的卡。干跑 / 迁移报告每个 profile 多一项 `collidedEntities`。
- **[x] ② 已加自动化测试** — `store/gen4/migrate_tests.rs` `entities_whose_protocol_3_row_another_profile_holds_migrate`：两 profile 的库，[P] 集合里另一台设备写过 [Q] 的默认牌组、`NTQ`（内容更小，行改写到 P 名下）、笔记 `QN1`，收段进来后跑真实迁移，断言整份提交、两个 profile `parity` 为空、`collidedEntities` 分别为 2 / 1。去掉修复时 P 报 `entities` onlyNew 2（`QN1` 与 Q 的默认牌组）、`notes` onlyNew 1。
- **备注**：与 BUG-5250（RhMpA6bn8v，卡 / 统计结果被旧重放改写）签名不同，风险标记的 duplicate 不成立。
