## BUG-3277 · Yomitan zip 的 Info-ZIP Unicode Path(0x7075) 文件名被忽略，大辞林 24 张图缺失
- **报告**：2026-10-12（用户：导入「JA-JA 大辞林　第四版.zip」后弹窗里标签图标和外字图片全部缺失）
- **真实性**：✅ 真 bug。根因 `native/fushidicts/fushidicts_src/zip/zip.cpp:403`（修复前）：`parse_central_directory()` 用 `e.name.assign(base + pos + 46, name_len)` 直接取中央目录里的原始文件名字节；extra 字段循环（修复前 `zip.cpp:358-401`）只在 ZIP64 哨兵出现时才走，且只认 0x0001，从不看 Info-ZIP Unicode Path Extra Field（0x7075，APPNOTE 4.6.9：`version:u8=1` + `crc32(原始名字节):u32` + UTF-8 名）。该词典所有条目都没设 general purpose bit 11，其中 24 个非 ASCII 名的原始字节是 Shift-JIS（如 `daijirin2/\x88\xea-default.svg` = `daijirin2/一-default.svg`、`daijirin2/gaiji/U\x8c|E0102.svg` = `U芸E0102.svg`），真正的 UTF-8 名只在 0x7075 里（Python 3.12 zipfile 能正确解出）。于是 `Zip::logical_name()` / `read_media()` 给出 Shift-JIS 路径，media.bin 以 Shift-JIS 为键落盘，而 term bank 的 `{"tag":"img","path":"daijirin2/一-default.svg"}` 按 UTF-8 查 → 24 张图全部查不到。其它词典的文件名是 ASCII 或已设 bit 11，不受影响。
- **[x] ① 已修复** — `a8a807d1d2`：`zip.cpp` 新增 `find_extra()`（按 `<id><size><data>` 走 extra 块，记录越界即停，不会读出块外）与 `resolve_entry_name()`：bit 11 已设 → 原始名即 UTF-8，直接用；否则仅当 0x7075 存在、version == 1、UTF-8 名非空、CRC32 与原始名字节一致时才采用其中的 UTF-8 名；CRC 不符（字段过期）/ 版本未知 / 记录越界一律保留原始名。条目名在解析时就定下来，`logical_name()`、`find()`、`read_media().path`、`compute_root_prefix()` 都从同一个 `ZipEntry::name` 派生，自动跟着变。ZIP64 0x0001 的解析改为复用 `find_extra()`，语义不变（找不到或越界仍判畸形）。
  - **未处理的情形（有意）**：既没有 bit 11、也没有 0x7075 的非 UTF-8 原始名不做转码。zip 格式不记录这类名字的代码页，规范默认是 CP437，而实际可能是 Shift-JIS / GBK / Big5 等；没有安全的判据，猜错会把本来能对上的名字改坏，所以保持原样。这类词典要靠打包工具写 bit 11 或 0x7075 解决。
- **[x] ② 已加自动化测试** — `a8a807d1d2`：`native/fushidicts/tests/zip_unicode_path_extra_test.cpp`（已登记进 `tests/CMakeLists.txt` 的 ctest；`zip_fixture.hpp` 的 `ZipFile` 新增可选 `extra` / `flags`）。端到端：原始名为 Shift-JIS、带 0x7075、不设 bit 11 的最小 zip 导入后，媒体可按 UTF-8 路径查到、按 Shift-JIS 路径查不到；Zip 层：CRC 不符 / bit 11 已设 / 版本 2 / 记录越界 / UTF-8 名为空都回退原始名，0x7075 排在别的 extra 记录之后仍生效。变异实测：`resolve_entry_name()` 无条件返回原始名 → 本测试 5 处 FAIL；去掉 CRC 校验 → 「CRC mismatch」用例 FAIL；恢复后 40/40 Passed（MSVC，Windows）。
- **备注**：用户已导入的大辞林需要删除后重新导入才能拿到正确的媒体键。
