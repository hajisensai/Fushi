## BUG-5056 · 复习库升级（gen4 迁移）在嵌套并入过的库上核对失败、整体撤回
- **报告**：2026-11-21（用户：「fushi复习库升级失败」，附 `srs4-migration-report.json` 与「升级没有通过核对，已全部撤回」截图）
- **真实性**：✅ 真 bug。用户的库就是设计稿 §5.3 的「样本库」（144 个「冲突变支配」的寄存器），旧库没受影响（干跑只读、失败即撤回）。报告里三项失败，两个根因：
  - **根因一（`classRegisters` 126 条：卡 `newPos` 125、笔记类型 `css` 1）**：资料库 f18df189 先并进 ef390（旧写入者 `#1` 在那里改名成 `merged-f18df189…`），ef390 又并进当前库。按类判把 `merged-…` 归回 `#1` 时，`native/fushi_fsrs/src/store/gen4/class.rs:164`（修复前的 `Canon::dvv`）把旧上下文 `{merged-…: 334270}` **整段**换成 `{#1: 334270}`，可两个名字「是同一条记录」的证据只到 seq 334235，超出的 23 条 `#1` 写入被凭空判成已被覆盖。另外 102 条（322269 < seq ≤ 334235）和 `css` 那条（seq 60243）其实有证据，但核对器的佐证收窄了：`class.rs:955`（修复前的 `writer_dots`）只扫修改的操作体，漏掉了副本记录（`op_alias`，协议 3 去重时留下的同一条记录的另一份）上的旧戳，而 resolver（`store/gen4/alias.rs` 的 `alias_evidence` → `Truth::for_each_stamp`）是算这些旧戳的；区间佐证又只认 `[lo, hi]`，`lo` 以下也判成佐证不了。
  - **根因二（`stats` / `cards` 各 2 张卡）**：同一次复习因资料库并入，在同一张卡的两份带盐副本上各留一条日志，日志 ID 没归到一起。新代的卡片历史成组键 `EventKey` 用规范卡（`native/fushi_fsrs/src/history.rs:157`，设计 §5.3），归成一个事件、只算一次；协议 3 用原值卡，算了两次。新代是对的，但核对器（`store/gen4/compare.rs:903` 的统计对拍）没有这一类已知差异，统计行和卡行里由历史重放出来的列（stability / difficulty / due_day / scheduled_days）都判成了差异。
- **[x] ① 已修复** —
  - resolver 给每个归回的写入者记下证据撑得住的范围 `WriterBound { upto, own }`（`gen4_ids/alias.rs`）：`upto` = 与最初写入者同 seq 同记录的最大 seq，`own` = 这个名字在 `upto` 以上的记录。同一条记录能证明「到这一号为止是同一段历史」。`Canon::dvv` 只换这部分：`{merged-…: n}` → `{#1: min(n, upto)}` 加上 `own` 里 ≤ n 的零散 dot，其余留在原名下。范围存在 `derive_cfg` 的 `aliasWriterUpto`，和 `alias_writer_ix` 在同一次重建里写，**不升 gen4 schema**（已迁移的库照常打开）；`CACHE_RULES` 升到 4，已迁移的库下次打开时整层重建一次补上。
  - 核对器的佐证和 resolver 用同一份证据（`writer_dots` 改用 `for_each_stamp`，含副本记录）；区间佐证改为 `s ≤ hi`（与 `WriterBound.upto` 同一口径）。
  - 核对器新增已知差异「同一次复习的副本按规范卡成了一个事件」（`compare.rs` `event_copies`）：只有新库里两条日志体的 HLC（含写入者）、发生时刻、种类、来源、评分类型、评分、Anki id 逐个相同，原值卡不同、规范卡相同时才认。这类卡的统计行整卡不比，卡行盖 `CARD_DERIVED`（与 `historyFrom` 已知差异同一口径），报告里计 `cacheStatCardsEventCopies`。
- **[x] ② 已增加自动化测试** — `store/gen4/class.rs`：`bounded_writer_rename_keeps_writes_above_the_proven_bound_concurrent`（嵌套并入：上界以上的写入保持并发、没有佐证不了的差异）、`bounded_writer_rename_splits_a_context_at_the_bound`（`Canon::dvv` 的前缀 / 零散 dot / 无范围旧库三种）、`a_copy_record_is_evidence_as_it_is_for_the_resolver`（只以副本记录存在的同记录算 `Copy` 佐证）；`native_write_sees_through_the_renamed_closure` 原先只凭 seq 1 的证据让 `merged:2` 盖掉 `(w1, 2)`，补上 seq 3 的同记录证据。`store/gen4/compare.rs`：`event_copies_are_known_only_when_the_canonical_card_is_all_that_differs`（正例、同毫秒另一次复习、同一张原值卡、两边一致）。`cache.rs` 的 `CACHE_RULES` 对表登记第 4 版。
- **验证**：用户真库副本（1.7 GB）+ 从失败的 `srs4.db-migrating` 取出的缓存配置跑 `gen4_dryrun`：修复前 `fail`（`classRegisters` 126、`stats` 3/1、`cards` 2/2）；修复后 `pass`（327 s）：已知差异 121 条全部佐证得了（`newPos` 102、笔记字段 18、`css` 1；另 23 条 `newPos` 恢复成与协议 3 相同的冲突、不再是差异），`unproven` 0，parity 无差异，`cacheStatCardsEventCopies` 2。
- **备注**：用户的 app 是安装版；修复随下一个 debug 包发出后，在「复习」页点「重新升级」即可。
