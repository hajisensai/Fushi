## BUG-4223 · 云盘漫画远端占位卡落在书籍书架
- **报告**：2026-11-07（用户：应用内反馈 ecNgkRQcTk，macOS 3.3.0-debug.24478，OneDrive 云同步）
- **真实性**：✅ 真 bug。云盘后端的远端书清单 `CloudRemoteBookClient.listRemoteBooks`（`fushi/lib/src/sync/cloud_remote_book_client.dart` 修复前 :92-109）只探测「文件夹里有没有内容资产」（`_remoteFolderHasContent` → `isRemoteBookContentName`，`.epub` 与 `.manga.zip` 一视同仁），组 `RemoteBookInfo` 时只给 `hasContent: true`，`format` 不填（缺省 `'epub'`，`packages/fushi_engine/lib/sync/fushi_library_host_service.dart:562`）、`hasMangaContent` 不填（缺省 false）。书架分架判据（`fushi/lib/src/pages/implementations/reader_history/remote.part.dart:110-118`）：书籍书架收 `hasContent`，漫画书架收 `InterconnectMangaCatalog.isReadableRemoteManga`（`format == manga && (hasMangaContent || hasMangaChapters)`）。于是云盘上的漫画包（2026-10-21 起上传成 `<title>.manga.zip`）全部以「远端 · 未下载」占位卡落进书籍书架，漫画书架一张都没有。分拣怀疑的 `sync_compare_dialog.dart:89,204` 只决定对比弹窗里能不能下载，与书架分架无关——方向不对。
- **[x] ① 已修复** — 清单按与下载同一判据（`pickRemoteBookContentEntry`）推断内容格式：新增 `cloudBookContentKindOf`（`fushi/lib/src/sync/cloud_book_content_names.dart`），探针 `_remoteFolderContentKind` 返回 `CloudBookContentKind?`；`.manga.zip` → `format=manga` + `hasMangaContent=true`、`hasContent=false`，`.epub` → `format=epub` + `hasContent=true`，与互联 host 的分键契约（`hasContent` 只表 EPUB 内容树）一致。提交见 git log（`Feedback: ecNgkRQcTk`）。
- **[x] ② 已加自动化测试** — `fushi/test/sync/cloud_remote_book_client_test.dart`「BUG-4223: a `.manga.zip` folder is listed as manga content, not EPUB」（原「`.manga.zip` has content」断言 `hasContent=true`，正是把漫画送进书籍书架的旧契约，已改）；`fushi/test/pages/reader_remote_cloud_manga_test.dart`（真实 `CloudRemoteBookClient` + 真实书架页 + 真实导入器，只替换网络）：书籍书架不收云盘漫画包、漫画书架渲染它、从漫画书架下载导入成 `format=manga` 并让位。回退修复实测 4 条红，修复后绿。
- **备注**：
  - 旧版本把漫画包也传成 `<title>.epub`：只看文件名与 EPUB 无从区分，仍会出现在书籍书架（下载导入按内容嗅探照样落成漫画）。要分清只能在上传端补元数据或改名，属另议。
  - 同条反馈里的「书架下载卡 100% 打不开、对比页下载正常」沿代码路径未复现，单列 BUG-4221。
  - 未在真机（macOS + OneDrive）复测。
