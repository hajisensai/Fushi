## BUG-4275 · Companion / popup lookups not counted: addLookupCount fails with database is locked
- **报告**：2026-11-08（双屏副屏真机巡检：AYN Thor，副屏 companion 查词约 8 次有 2 次统计没加，logcat 主进程 `[fushi-stats] addLookupCount failed: SqliteException(5) database is locked`，语句 `UPDATE lookup_mining_counters ...`）
- **真实性**：✅ 真 bug。`packages/fushi_core/lib/src/database/database_statistics.part.dart`（旧 `:1422-1443`）`addLookupCount` 在 deferred 事务里先 SELECT 再 UPDATE / INSERT（`addMineCountPerBook`、`addMiningCount` 同形）。同一个库还有别的进程在写：`:second_screen` 副屏面板（同一次查词它落查词历史，`fushi/lib/src/pages/implementations/dictionary_page_mixin.dart` → `DictionaryRepository.replaceAllDictionaryHistory`）、`:popup` 浮窗。SELECT 开了读事务后再升级写锁时撞上对方写锁，SQLite 对已持读事务的连接**不调 busy handler**（等锁可能死锁），立刻 SQLITE_BUSY，busy_timeout 5000 不生效；错误在 `fushi/lib/src/pages/base_source_page.dart` 被降级成 debugPrint，计数静默丢失。仓里已在 `database_prefs_media.part.dart` `insertPrefIfAbsent` 记过同一个坑。
- **[x] ① 已修复** — 三个计数事务的第一条语句改成写：`INSERT OR IGNORE`（存在性交给唯一键 {title, sourceType, dateKey, bookKey} / {sourceType, dateKey} 的冲突本身），没插进去才在已持写锁的事务里 `col = col + ?`；首插清统计墓碑的语义保留。面板进程继续自己写查词历史（它持有 `DictionarySearchResult`，与 `:popup` 同一契约；把 MB 级结果搬过桥给主进程写不划算）——根因是计数事务的形状，不是谁在写。
- **[x] ② 已加自动化测试** — `packages/fushi_core/test/bug4275_cross_process_counter_lock_test.dart`：真磁盘 WAL 库 + 真第二连接 `BEGIN IMMEDIATE` 持写锁 400 ms，期间 `addLookupCount`（已有行 / 新行）与 `recordMiningEvent` 必须等锁成功、计数正确。改前两条红（database is locked），改后绿。
- **备注**：副屏真机复测见双屏进度日志 S7e。面板与主进程各自整表写 dictionary_history（后写覆盖先写）是 `:popup` 起就有的既有形状，不在本条修。
