## BUG-5294 · gen4 迁移对拍：第二个 profile 的三个加盐内置实体协议 3 一侧哪儿都没有，`entities` 判新代多出、整份撤回
- **报告**：2026-11-23（应用内反馈 CQKRyvMoOC：Android 3.4.0-debug.31707，复习库升级 `aborted` / `profileVerdict: fail`；风险标记 duplicate:RhMpA6bn8v 只是正文相同，签名不同）
- **真实性**：✅ 真 bug（报告签名已核）。报告签名：主 profile `01a13f60…` 通过（`imported.devices = 3`）；第二个 profile `01a141bf…` 只有 6 条操作（1 台设备，`prev.seq = 6`），`parity` 只有 `entities` onlyNew 3，正是它按 `salt#0` 加盐的三个内置实体（`8667ab89…` fushi_card 笔记类型、`b48b18d8…` 默认牌组、`edcf6853…` lapis 笔记类型），`collidedEntities: 0`。
  - 与 BUG-5267（n4WhWEKPtQ）签名相同，但报告里已有 BUG-5267 加的 `collidedEntities` 项且为 0：`compare.rs` `taken_entities` 只认「行在库里、归了另一个 profile」的，这里三行要么根本不在 `srs_entities`，要么在却没被认出。`srs_entities` 全仓没有删除路径（只有测试），所以更可能是这三条身份记录从没投影过（`project_body` 的 `project = false` 路径或别的写入路径），需要用户的库或在报告的 `idTrace` 里补「实体行归属」才能定。
  - 与 PR #4245 的重复日志代表不一致无关（`oldSideStaleResults` 0、没有卡 / 统计差异）。
- **根因**（机制已在代码里走通并复现；用户库里那一行具体是被哪条删除路径带走的，报告证不出，见备注）：协议 3 的 `srs_entities` 以实体 ID 为主键、全库共用（`native/fushi_fsrs/src/store/schema.rs:136`），`project_entity`（`store/sync2/mod.rs:1271`）遇到已有同 ID 的行只比内容、不看归属，两个 profile 的日志里都有同一个实体的身份记录时只存一行、归先落投影的那个（BUG-5267）。而这张表只有按 `profile_uid` 整批删的路径（`store/profile_data.rs:308` `purge_on`：删 profile / 并入收尾 `profile_merge_commit` / 无主数据扫描都走它）：行的主人被删时这一行跟着删掉，另一个 profile 日志里的身份记录还在。结果是「本 profile 已应用的操作里有身份记录、整张表里哪个 profile 名下都没有这一行」——报告的 `collidedEntities: 0`（行不在别的 profile 名下）+ `entities` onlyNew 3 正是这个形态。协议 3 自己的规则下（`project_entity`：没有行就写）它就是本 profile 的实体，同一集合里别的设备收同样的操作就有这一行；对拍 `compare.rs` 的 `entities` 一类却只认 `srs_entities WHERE profile_uid = ?`，BUG-5267 加的 `taken_entities` 又只认「行归了别的 profile」，于是判新代多出、整份撤回。协议 3 测试语料里早有同一形态（`tests_channel` 的 `ch-missing-row` 手删一行内置笔记类型），以前是登记成已知差异放过的。
- **[x] ① 已修复** — 对拍口径与 BUG-5267 一致（按本 profile 的操作集合），不加容差：`store/gen4/compare.rs` `taken_entities`（:1434）在新代有、本 profile 名下没有的 ID 里，除「行归了别的 profile」外也认「整张表都没有这一行」，两种都要本 profile 已应用的操作（`sync2_ops` 身份记录）证得出；后者记进新的 `Collisions::orphaned`（:669），算进协议 3 一侧，其中的笔记同时进 `Collisions::notes`（协议 3 的缓存按 `profile_uid` 列笔记，行没了就没有这条笔记，缓存层不比它与它的卡）。报告每个 profile 多一项 `orphanedEntities`。`parity.rs` 删掉 `ch-missing-row` 那条已知差异（现在按同一口径对上，`known_is_exactly_what_the_listed_tests_hit` 守着）。另：`compare.rs` `annotate_protocol_3`（:1500，`dryrun.rs` 接到 `idTrace` 上）给 `idTrace` 每个 ID 补 `p3`：协议 3 的 `srs_entities` / `srs_field_edits` / `srs_review_logs` 行在不在、归本 profile 还是别的 profile，修改记录 / 日志的操作映射归谁、在不在本 profile 日志里。
- **[x] ② 已加自动化测试** — `store/gen4/migrate_tests.rs` `entities_whose_protocol_3_row_left_with_a_purged_profile_migrate`：两 profile 的库，[P] 集合里另一台设备写过 [Q] 的默认牌组与笔记 `QN1`（行归 [Q]），再 `profile_purge(Q)` 让行随之删掉，跑真实迁移：整份提交、[P] `parity` 为空、`orphanedEntities` 2、`collidedEntities` 0。去掉修复时在协议 3 内核关库的对拍钩子上就红：`entities` onlyNew [`QN1`, Q 的默认牌组]、`notes` onlyNew 1，与报告同签名。
- **备注**：报告只有 ID 与计数，证不出用户库里那一行是被哪条删除路径带走的（删 profile、并入收尾、无主扫描，或别的手段删了行）；修复按「操作日志证得出、行整张表都没有」这一形态判，与是哪条路径无关。下一份同类报告的 `idTrace.p3` 会写出行归属，`orphanedEntities` / `collidedEntities` 分得开两种。
