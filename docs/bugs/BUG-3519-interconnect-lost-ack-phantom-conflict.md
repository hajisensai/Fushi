## BUG-3519 · 互联进度推送「写入落地、确认丢失」被误判成冲突（远端是本机自己的旧写入）
- **报告**：2026-10-18（用户：手机同步弹「本地 vs 远端」冲突，漫画《志乃と恋 ２》本地 78.4%（131 页，16:34）、远端 52.1%（87 页，15:39），而电脑很久没开过这本书）
- **真实性**：✅ 真 bug。证据：手机日志 `[2026-10-18 15:40:16] SyncRunReport.errors live book progress "志乃と恋 ２ [e11812e5]": TimeoutException after 0:00:15 … PUT /api/library/books/…/progress`；电脑 host 库后续确实存着这本书的进度——远端那条 15:39 / 87 页就是手机 15:40 那次「超时」推送，host 已提交、确认包丢失。
  - 根因 `fushi/lib/src/sync/interconnect_book_progress_sync.dart:83-87`（修复前）：`pushLocal` 先 `putRemoteBookProgress` 再 `recordBaseline`，PUT 超时抛出时基线停在旧位置；本机接着读到 131 页，下一轮 `resolveBookProgressThreeWay` 见本地、host 都偏离旧基线 → `conflict`。播放位置同理：`interconnect_playback_position_sync.dart` 的 `pushLocal` / `reportLive`。
  - 同轮发现的相邻缺陷：`fushi/lib/src/sync/sync_utils.dart:71` `findSyncFileByPrefix`（及 `google_drive_handler.dart` 的私有副本 `_findByPrefix`）对同前缀多份 `progress_*` / `statistics_*` / `audioBook_*` 取「列表第一个」，后端返回顺序不定，云文件箱有残留旧副本时会时而读到旧进度，自动同步可能把本机进度倒退。
- **[x] ① 已修复** — 推送前在 `sync_baselines` 记「待确认」位置（书 `progress_live_pending`、播放位置 `<dimension>_pending`），任一次两端达成一致（`recordBaseline`）时清掉；新增唯一判定入口 `InterconnectBookProgressSync.decide` / `InterconnectPlaybackPositionSync.decide`：host 正停在待确认位置时把它提升为基线再三方判定。sweep（`sync_orchestrator/books.part.dart`）、对比弹窗（`sync_compare_dialog.dart`）、播放进度冲突弹窗（`playback_position_conflict_dialog.dart`）全部改走 `decide`。`findSyncFileByPrefix` 改为按文件名时间戳取最新，Drive 私有副本删除、改调公共函数。新增 `FushiDatabase.deleteSyncBaseline`。
- **[x] ② 已加自动化测试** — `fushi/test/sync/interconnect_lost_ack_conflict_test.dart`（书 / 视频 sweep / 视频实时上报三种确认丢失场景判 `pushLocal`；PUT 未到达且对端独立改动仍判 `conflict`；推送成功清待确认；`findSyncFileByPrefix` 与顺序无关取最新）；`fushi/test/sync/sync_remote_listing_test.dart` 原「取第一个」用例改为「取最新且与 `findSyncFileByPrefix` 同律」。
- **备注**：用户手上这条已出现的冲突，选「本地」即可（电脑 host 库现已是 131 页 / 16:34，与手机一致）。日志另显示当天手机到电脑 `192.168.1.30:38765` 大量 `Connection timed out` / `connection abort`（同时段手机把整卷漫画 OCR 派给电脑），推送超时本身的网络 / host 负载问题不在本条范围。
