## BUG-1572 · 聚合上行快照不过墓碑导致已删统计/收藏复活
- **报告**：2026-08-12（用户：互联/同步深审计 P1-6）
- **真实性**：✅ 真 bug。根因 `fushi/lib/src/sync/aggregate_sync_service.dart:141`（云通道 `store.putJsonAsset(ns, ownAssetName, payload)`，payload 来自**未裁剪**的 `merged`）与同文件 `:218`（互联通道 `pushMerged(merged.toJson())`）。
  不对称在于：`applySnapshotToLocal`（`:662`）写回本地时按墓碑逐条跳过——统计墓碑 `:668-671` / `:683` / `:745`，收藏词 `favoriteword` 墓碑 `:772-776`，收藏句 `favoritesentence` 墓碑 `_writeFavoriteSentences :833-845`——但 `merged = local ∪ peer`，peer 那份仍带着本机**已删**的条目，推出去的却是未裁剪的 merged。
  于是数据环路成立：本机把自己删掉的统计/收藏词/收藏句**又发布**给 host / 云 → 对端没有本机的墓碑，照单落库 → 下轮本机拉回来时虽仍被本地墓碑挡住，但一旦墓碑被清（用户重读该书 / 重新查词触发 `packages/fushi_core/lib/src/database/database_statistics.part.dart:68` 的 `clearStatisticsTombstone`），那些值就原样回到本地 = 复活。
- **[x] ① 已修复** — `aggregate_sync_service.dart` 新增 `filterTombstoned(AggregateSnapshot)`（`@visibleForTesting`），裁剪规则与 `applySnapshotToLocal` 的跳过规则**逐条同源**：reading 按 `(title, statSourceBook)`、video 按 `(title, statSourceVideo)`、`lookupMiningCounters` 按 `(title, sourceType)`、收藏词按 `favoriteWordItemKey` 的 `favoriteword` 墓碑、收藏句按 `FavoriteSentenceRepository.itemKeyOf` 的 `favoritesentence` 墓碑。逐时桶与 `miningStats` 的 wire 键不含 title、无法归因，与 apply 侧一样原样保留（两侧同样处理才谈得上「推出去的 == 会写回来的」）。三条 push 路径都改为先裁剪：云 `sync()` 的 step 5（裁剪后再算 `isEmpty` 与去重哈希）、互联 `syncOverClient()` 的 step 5、以及 host 无端点时的 push-only 退化路径。无墓碑时返回入参本身（零拷贝）。提交 `e53681ead0`。
- **[x] ② 已加自动化测试** — `fushi/test/sync/aggregate_push_tombstone_test.dart`（5 条，真实 on-disk `FushiDatabase` + `FakeAssetStore`）：`filterTombstoned` 逐条剔除且保留未立碑的 `Book B`/`w2`；无墓碑时 `identical` 原样返回；**云通道** push 的资产解回后不含 `Book A`/`Video A`/`w1`/收藏句；**互联通道** `pushMerged` 收到的 payload 同上；全部条目都立碑时不推空快照。变异实测：把两处 push 改回 `merged.toJson()` → 2 条红。
