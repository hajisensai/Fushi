## BUG-4990 · 番剧下载状态卡在「231 KB / 231 KB (100%)」
- **报告**：2026-11-20（用户：应用内反馈 e_LVlqyUd-）
- **真实性**：✅ 真 bug。字节回报的口径在一次下载里会换，但两端都没跟着换：
  - `fushi/lib/src/media/video/online/anime_episode_downloader.dart:563-588`（修前行号）：没有 `.m3u8` 后缀的地址先走 `_downloadDirect`，下回来的是播放列表文本，已按 Content-Length 报了「已收 / 总」（=播放列表大小、100%）；`:576` 认出是播放列表后改走 `_downloadHls`，而 `_downloadHls`（`:1110`）根本不接 `onBytes`，之后再没有字节回报。外挂音轨分量（`:664-671`）同样没传 `onBytes`。
  - `fushi/lib/src/sync/interconnect_download_manager.dart:106` / `:923`（修前）：`copyWith` 用 `totalBytes ?? this.totalBytes` 合并、`_updateBytes` 按 `knownTotal ?? task.totalBytes` 算比例——一次回报说「总量未知」也清不掉旧总量。
  - `fushi/lib/src/pages/implementations/interconnect_download_tasks_section.dart:306` 状态标签优先显示字节，于是整集下载期间一直显示播放列表的「231 KB / 231 KB (100%)」。
- **[x] ① 已修复** — 字节回报改成「每次都是传输原语当下的完整快照」：
  - `_downloadHls` 接 `onBytes`，起跑先报 `(已写, null)` 与续传起点比例，每写完一片再报 `(已写, null)`；嗅探出播放列表后的分片下载与直接 HLS 两处都传下去。
  - `downloadWithExternalAudio` 音轨阶段报累计字节（已就绪分量 + 当前音轨已收，总量未知）；`_downloadComponent` 复用完整分量时报一次 `(长度, 长度)`。
  - `InterconnectDownloadTask.copyWith` 加 `clearTotalBytes`；`_updateBytes` 总量未知就清掉旧总量、比例交给 onProgress，不再拿旧总量配新已收。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/online/anime_episode_downloader_test.dart`（无后缀播放列表经真 `InterconnectDownloadManager` 下完后 `receivedBytes` = 分片字节、`totalBytes` 为 null；外挂音轨阶段报累计 7000 字节）；`fushi/test/sync/interconnect_download_resume_test.dart`（传输中途总量变未知时标签只给已收、不停在 100%）。
- **备注**：HLS 起跑多报一次进度（续传起点），两条既有 HLS 进度序列断言随之更新。设备复测未做（本轮无真机），原始失败路径由回环 HttpServer + 真管理器的测试覆盖。
