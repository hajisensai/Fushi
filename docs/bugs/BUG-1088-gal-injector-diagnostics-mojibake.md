## BUG-1088 · injector 诊断按系统代码页解码：会话事件乱码且中文失败分类永久失配
- **报告**：2026-07-25（用户：「同时这个事件的编码有问题」，附「会话事件」截图，`engine.launch_injection_degraded` 的 `detail` 里出现 `[luna] LunaHook32.dll 宸叉敞鍏?pid=109292锛出瓔寰岃繛鎺?..`）
- **真实性**：✅ 真 bug，且伤害面比「显示难看」大一层。
  - **根因**：`hibiki/lib/src/mining/galgame_audio_source.dart` 的 `_beginInjectorOutputDrain` 用 `const SystemEncoding().decoder` 解 injector 的 stdout/stderr。`SystemEncoding` 在 Windows 上是系统 ANSI 代码页（本机中文 = CP936），但 injector 的输出是 **UTF-8**：其 `CMakeLists.txt` 无条件 `add_compile_options(/utf-8)`，MSVC 的 `/utf-8` 同时把 execution-charset 设为 UTF-8，所以 `"[luna] LunaHook%ls.dll 已注入 pid=%lu，等待连接...\n"` 这类字面量在二进制里就是 UTF-8 字节，`fprintf(stderr, ...)` 原样写出。两侧编码契约不一致。
  - **字节级实证**（直接跑本机已安装的 `D:\APP\Hibiki\voice_hook\x86\hibiki_voice_injector.exe`，把 stderr 按 latin1 取原始字节）：中文段按 UTF-8 解得「LunaHook(host 侧全引擎文本 hook，仅 --hold 生效)」，按 CP936 解得「LunaHook(host 渚у叏寮曟搸鏂囨湰 hook锛屼粎 --hold 鐢熸晥)」。截图里的 `宸叉敞鍏?` 正是「已注入 」的 UTF-8 字节（`E5B7B2 E6B3A8 E585A5 20`）被 CP936 拆成 `宸/叉/敞/鍏` + 落单的 `A5` → `?`。
  - **第二层伤害（比乱码严重）**：`classifyGalHookInjectorFailure`（同文件）靠**中文串**识别旧 helper 的失败原因——`位数不匹配`（`:327`）、`目标 exe 不存在`（`:343`）、`已存在但不可复用的 hook 会话`（`:346`）、`未收到就绪信号`（`:349`）、`Steam 已接受启动请求`（`:359`）。解错码后这些分支**永远匹配不上**，失败分类永久退化成 fallback，用户拿不到「位数不符 / 需要管理员 / 缺文件」这类可执行处置，只剩一个笼统的 `handshakeTimeout`。
  - **为什么藏得住**：新 helper 的机器可读行 `ERR reason=<token>` 和 `CreateProcessW failed` / `OpenProcess(` / `hook DLL not found` 全是 ASCII，两种解码都对，主路径照常工作——坏掉的只有旧 helper 的中文兼容路径。而既有单测 `galgame_audio_test.dart:824` 起的 `classifyGalHookInjectorFailure` group 直接用 **Dart 源码里的中文字符串字面量**做输入，那已经是「解码正确」的结果，所以测试恒绿、测不到解码环节。
- **[x] ① 已修复** — `galgame_audio_source.dart`：新增 `static const Converter<List<int>, String> _injectorOutputDecoder = Utf8Decoder(allowMalformed: true)`，stdout/stderr 两处 `transform` 改用它，并把「契约是 UTF-8、为什么、错解码的两层后果」写进注释。`allowMalformed` 是必须的：stderr 里 `%ls` 宽字符经 C locale 转换后可能夹带非法字节，单个坏字节不得让整条诊断流抛异常而丢掉全部证据。
- **[x] ② 已加自动化测试** — `hibiki/test/mining/gal_hook_launch_outcome_and_encoding_test.dart` 的 group `injector 诊断编码契约是 UTF-8 (BUG-1088)`：5 项。关键是**从字节造输入**（`utf8.encode`）而不是写 Dart 字符串字面量，否则测不到解码环节：① UTF-8 解码后 5 条真实中文诊断都能正确归类；② 用 `latin1` 确定性模拟「单字节代码页解 UTF-8」，断言分类**全部丢失**退化成 `unknown`（锁死伤害面，也保证本测试真的在测解码，而非平台巧合）；③ ASCII 诊断两种解码都不受影响（解释 bug 为何长期潜伏）；④ `allowMalformed` 夹杂 `0xFF 0xFE` 不抛且仍能归类；⑤ 源码守卫——正则 `SystemEncoding\s*\(` 不得命中（只禁构造调用，不禁注释里的文字提及）且必须含 `Utf8Decoder(allowMalformed: true)`。全文件 11 项通过；`flutter analyze` 全量 0 issue。
- **备注**：`galgame_helper_installer.dart:535` 也有一处 `SystemEncoding().decoder`，但那是解 HTTP 响应体、来源不同，本轮未动（守卫只作用于 `galgame_audio_source.dart`）。真机复看「会话事件」里 native 诊断不再乱码尚未做 → `implemented_unverified`。
