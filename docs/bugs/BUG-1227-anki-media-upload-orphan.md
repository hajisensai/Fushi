## BUG-1227 · 大 GIF 上传超时被吞后仍创建无图卡并留下孤儿媒体
- **报告**：2026-07-29（用户反馈 Anki 制卡时未响应，且卡片经常缺少图片、GIF）
- **真实性**：✅ 真 bug。默认 GIF + 最高质量配置会产生数 MiB 到十余 MiB 的文件；旧实现把本地媒体编码成 Base64 后通过 JSON 上传，并在上传超时或失败时吞掉异常、返回空媒体，随后仍继续 `addNote`，因此既可能阻塞 Anki，也会创建无图卡并留下已落盘但未引用的媒体。根因位于 `packages/hibiki_anki/lib/src/ankiconnect/ankiconnect_repository.dart:1186` 与 `hibiki/lib/src/mining/immersion_mining_engine.dart:141`。
- **[x] ① 已修复** — `adbb79476`：本机 AnkiConnect 改用文件路径上传，远端端点保留 Base64 回退；封面、GIF、句子音频与词典媒体全部成功后才调用 `addNote`，必需媒体失败则整次制卡失败。`54d9ac754` 补齐并行事务补偿：写前按精确文件名记录是否已存在，任一路失败只回滚本次新建文件；既存的内容哈希媒体可能被旧卡共享，绝不删除。后续补丁增加同一连接器、同一内容哈希文件的跨事务 lease：失败事务必须等待并发 peer 定案，任一 peer 提交后永久保护该文件；非致命远程音频写响应丢失且首次清理失败时，在所有媒体路收敛后重试 retained 候选。事务进一步延长到 `addNote` 结果：确认成功或 commit-unknown 才提交媒体，明确 duplicate、服务端已知拒绝或请求送达前失败则回滚本次新媒体，且绝不重试 commit-unknown 的 `addNote`。传输层不再从 public ClientException/SocketException 的类型、errno 或文本猜测交付相位；即使写着 “Connection timed out”，只要请求可能已交给 HTTP client 就按 delivery-ambiguous commit-unknown。只有 connection factory 在 HTTP 请求尚未开始时产生的可信 pre-delivery marker 才可安全重发一次并在最终失败时回滚。媒体保持用户所选质量，不按文件体积擅自降质。
- **[x] ② 已加自动化测试** — 覆盖本机路径上传、远端 Base64 回退、媒体超时禁止 `addNote`、并行一路失败删除本次新媒体、既存共享哈希媒体不删除、并发两卡同哈希时失败方不删成功卡媒体、远程音频 lost-response 后清理重试、duplicate/已知失败/commit-unknown 三类 addNote 终态、真实本地 HTTP server 已消费 addNote 后响应超时不重试且不删媒体、完整消费 addNote body 后抛同型 socket timeout 仍只调用一次并保留媒体，以及可信 pre-delivery marker 安全重试一次后回滚本次媒体。
- **备注**：`hibiki_anki` 全包 282 tests 与相邻视频 mining/FIFO 31 tests 通过，`hibiki_anki` / app 全量 analyzer 均为 0 issues。按用户要求未等待 Windows 整包编译验收；也未向用户个人 Anki 写入测试媒体。`deleteMediaFile` 持续失败仍无跨进程持久补偿，继续作为已知剩余风险明示。
