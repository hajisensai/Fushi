## BUG-4070 · 互联 / WebDAV 走 IPv6 地址时子路径丢方括号，SRS 同步每轮 Invalid port
- **报告**：2026-11-04（崩溃报告整批分诊时在 iOS 崩溃反馈 `n1i0ET11Ea` 的日志里发现，3.3.0-debug.23213，iPhone18,3；不是闪退本身，但每轮 SRS 同步都失败）。
- **真实性**：✅ 真 bug。日志 `syncChannelPostRunHook`：`FormatException: Invalid port (at character 14)  https://fd4d:ccc8:863b:4e38:5ab8:8c89:9b58:3907:38765/fushi-data/fushi-srs/...`，栈 `WebDavOps.buildRequest (webdav_ops.dart:268)` ← `propfindDepth` ← `propfindChildren` ← `InterconnectSyncBackend.listChildren` ← `SrsAssetLocationStore._childFoldersOrCreate` ← `srsPrepareLocation`。同一份日志里 ping 用的是带方括号的 `https://[fd4d:…]:38765/api/ping`，说明 base URL 本身正确，坏在相对 href 的回拼：`fushi/lib/src/sync/webdav_ops.dart:539`（旧）`'${baseUri.scheme}://${baseUri.host}$portSuffix$href'`——`Uri.host` 对 IPv6 字面量返回**不带方括号**的裸地址（本机 `dart run` 实测：`Uri.parse('https://[fd4d:ccc8::1]:38765/').host == 'fd4d:ccc8::1'`，`.origin == 'https://[fd4d:ccc8::1]:38765'`）。PROPFIND 返回的每个相对 href 都被拼成不可解析的 URL，下一跳 `Uri.parse` 抛错。同构的第二处：`fushi/lib/src/media/source_library/source_file_system.dart:582`（旧）WebDAV 来源用 `u.host` 手拼 baseUrl，IPv6 NAS 地址同样坏。
- **[x] ① 已修复** — 两处都改用 `Uri.origin`（保留 IPv6 方括号、省略默认端口，与旧逻辑的端口规则一致）：`webdav_ops.dart:538` `'${baseUri.origin}$href'`，`source_file_system.dart:580` `baseUrl: Uri.parse(anyUrl).origin`。跨源校验分支（比较 `host`/`scheme`/`port`）两侧同为裸地址，语义不变。提交见下。
- **[x] ② 已加自动化测试** — `fushi/test/sync/webdav_ops_test.dart` 组 `WebDavOps.resolveHref keeps IPv6 literals bracketed`（非默认端口 / 默认端口 / 同源绝对 href 三例，断言结果可被 `Uri.parse` 还原出原 host 与端口）；`fushi/test/media/source_library/webdav_source_file_system_test.dart` 的 `IPv6 端点：递归列目录与下载都用带方括号的 URL`（进程内假 WebDAV 绑 `::1`，真走 PROPFIND 递归 + GET）。还原两处旧实现后 3 例红（`Invalid port`，栈与用户日志同一路径），修复后两文件 15 例全绿（`dart tool/heavy.dart -- flutter test …` exit 0，15 tests ran）。
- **备注**：互联 SRS 同步用的是 `SyncAssetStore` 的 WebDAV 路径（`InterconnectSyncBackend.listChildren` → `WebDavOps.propfindChildren`），本修复覆盖它；其余直接拼 `_apiBase` 的端点本来就带方括号。真机 IPv6 互联复测未做（本机无 IPv6 互联环境），以进程内 `::1` 真链路测试代替。
