## BUG-2627 · 视频「调整上下文」确认制卡没反应
- **报告**：2026-09-22（用户：录屏「视频调整上下文制卡不行」——视频页词典弹窗点「调整上下文」→ 顶层对话框「选择句子上下文」→「前加一句」→「确认制卡」，对话框关掉、**查词弹窗整条浮层栈一起消失**、卡没制出来、一个提示都没有；同一词条上直接点弹窗里的制卡按钮正常出 toast。两次复演同一结果。）
- **真实性**：✅ 真 bug。用户录屏对应的构建是 `2.8.0-debug.15355`（更新元数据 `lastModified = Mon, 21 Sep 2026 22:54:09 GMT`，晚于悬停关栈门 `41fd58c1f2c`，故**不是**那条已修的漏）。根因在「确认制卡」这次跨 WebView 往返的**时序**与**全链静默**两处：
  - `fushi/lib/src/pages/implementations/sentence_context_dialog.dart:185`（原 `_confirm`）先 `Navigator.pop()` 再调 `onConfirm()`。制卡不是本地调用，而是「Dart → 查词弹窗 WebView 的 DOM → 回点该词条的 `.mine-button`」的一次往返（Dart 侧没有「制卡指定词条」的直接入口，`mineEntry` 契约要求 JS 先构造 payload）。而那层弹窗**只在对话框还开着时才被保护住**：宿主 `runWithLookupPopupHidden` 期间整屏 dismiss barrier 不渲染（`dictionary_popup_layer.dart:343`）、悬停离开自动关栈被 `hiddenByDialog` 挡住（`video_fushi_page.dart:5441`）、浮层停靠屏外但保持挂载（`dictionary_popup_layer.dart:360`）。`pop()` 一执行保护就开始撤，往返却才刚出发。
  - 往返途中只要任一条关栈路径跑了（视频页的关栈汇聚点 `_popNestedPopupAt`，`video_fushi_page.dart:5550`，被悬停离开 / barrier 点击 / 横滑 / 键盘 / 手柄 / 返回 / 弹窗自己的输入 token 七类入口调用），热槽被 `_restoreWarmSeed` 还原成空种子（`dictionary_popup_controller.dart:336`），容器里一个 `.entry` 都没有。
  - 此时 `popup.js:4098` 的 `fushiPopupMineEntryByIndex` 直接 `return false`（三条：无 `.entry` 容器 / `entries[idx]` 越界 / 该词条没有 `.mine-button` 或按钮 disabled），而 `dictionary_popup_webview.dart:1080` 的 `mineEntryByIndex` **既不读返回值也不 catch**、`_controller == null` 也是静默吞，调用方 `dictionary_page_mixin.dart:237` 又把 Future 整个丢掉。于是任何关栈竞态都退化成**同一个无声症状**：对话框关了、卡没制、零 toast 零日志。
  - 同族未设门通道：`onHostInputToken`（`dictionary_page_mixin.dart:784` / `base_source_page.dart:936`）落地的是关栈动作，却没有 `hiddenByDialog` 门——对话框期间弹窗虽停靠屏外仍然挂载、DOM 还可能持有系统键盘焦点，一个被绑的键就能把对话框**背后**的整条栈关掉（连带清空制卡草稿）。
- **[x] ① 已修复** — 把往返挪进保护窗口**内**完成：`_confirm()` 改为 `await onConfirm()` 落地后再 `pop()`，期间整窗进 `_busy`（与编辑态同一把锁，不能连点、不能改上下文）；`onConfirm` 契约由 `VoidCallback` 改成 `Future<bool> Function()`，`mineEntryByIndex` 如实回传「有没有真的点到那颗按钮」并对三种失败各落一条 `ErrorLogService` 日志，没点到时对话框弹 `popup_ctx_confirm_failed` 提示，不再静默。两条车道（`dictionary_page_mixin` / `base_source_page`）同步；`onHostInputToken` 补上与 barrier、浮层 `visible:` 同源的对话框门。提交见本文件所在修复提交。
- **[x] ② 已加自动化测试** —
  - `fushi/test/utils/misc/popup_asset_behavior_test.js`：真执行 `assets/popup/popup.js` 的 `fushiPopupMineEntryByIndex`——①点第 2 个词条（idx=1）必须制的是**那个**词条（与 BUG-1326 的索引同源）、②越界、③弹窗已被关栈（容器空）、④按钮 disabled 三种失败都必须回 false 且一张卡都不制。这个函数此前**全仓零断言**。为此给 harness 的 fake DOM 补了 `click()` 与 `:scope > ` 直接子节点选择器。
  - `fushi/test/pages/sentence_context_dialog_widget_test.dart`：+4 条——往返未回时对话框必须还开着且确认键禁用（钉死「先 pop 再回点」不会回来）、没点到时关窗且弹失败提示、点到了不弹提示。
  - `fushi/test/pages/sentence_context_dialog_zorder_guard_test.dart`：+3 条接线守卫（两条车道的 `onHostInputToken` 对话框门、两条车道的 `onConfirm` 回传结果、`onConfirm` 契约是 `Future<bool>`）。
  - `fushi/test/pages/sentence_context_modal_guard_test.dart`：签名守卫改钉 `Future<bool> mineEntryByIndex(`。
- **备注**：**未在真机复演原始失败路径**——本轮修复由代码路径定位 + 单测钉死，没有在装着用户那个视频/字幕/Anki 环境的真 app 上重跑一遍「调整上下文 → 确认制卡」。按 docs/agent/integration-testing.md 的口径，这条只算 `implemented_unverified`，请在真机上复测原始路径后再认定关闭。另：录屏里那次「卡片已导出到『Lapis』」的成功 toast 在 `mined_sentences` / `mining_statistics` 里都没有对应记录（今日视频制卡计数停在 4，最后一条 14:24:42，录屏发生在 14:29），这条**没有查清**，可能是另一个独立问题（成功 toast 与记账不同源），留档待查。
