## BUG-3685 · 墓碑清除回收媒体时，扫描与删除之间新加的引用照样被删
- **报告**：2026-10-23（来源：审查记录 HBK-AUDIT-014，`2026-10-23-project-review.md`）
- **现象**：删牌组 / 笔记过了安全期后维护清除墓碑，并回收不再被引用的媒体。这期间如果制卡、导入或恢复刚好重新用到同一个媒体文件（名字是内容哈希，同一张图复用同一个文件名），文件可能被删，卡面图片 / 音频丢失且无法找回。
- **真实性**：✅ 真 bug（沿代码路径确认，用测试复现了其中「存文件 → 提交笔记」那段窗口）。根因：
  - `packages/fushi_engine/lib/srs/srs_purge.dart` 的 `_deleteUnreferencedMedia` 先等 `srsAllMediaReferences` 算出存活集合，再逐个 `exists()` / `delete()`，整段不在 store 独占区里，编辑 / 恢复 / 撤销能插在扫描与删除之间。
  - 媒体文件先于引用落盘：`fushi/lib/src/srs/srs_media_store.dart` `store()` 复用已有同内容文件时直接返回名字，调用方之后才提交引用它的笔记，这一步本来就在锁外。
  - 候选只存在于那一轮的内存里：被叫停或崩溃后笔记已清、文件却永远没人回收。
- **[x] ① 已修复** — `1184d1e2fe`：
  - 扫描、删除、移出候选在同一个 `runExclusive` 里完成，库里所有引入引用的写入都走这把锁。
  - `SrsMediaStore.store` 复用文件时也刷新修改时间；回收只删修改时间早于 `kSrsMediaGcGrace`（24 h）的文件（与 git gc 对松散对象的宽限期同理）。
  - 候选随笔记清除在同一事务里写进本机状态（`SrsDbStore.pendingMediaGc`）：跳过 / 叫停 / 崩溃的，下一次维护接着处理。
- **[x] ② 已加自动化测试** — `packages/fushi_engine/test/srs/srs_purge_test.dart`「⑤ 媒体回收与并发写入」组（刚复用的文件不删、重开 store 后候选还在并照常回收；宽限期内被重新引用的移出候选；排在前面的写入重新引用后文件保留），以及 `fushi/test/srs/srs_media_store_test.dart`（复用时刷新修改时间）。变异实测：去掉宽限期判断后前两条变红。
- **备注**：宽限期是「存文件 → 提交引用」间隔的上界约定：超过 24 h 才提交的引用（实际不存在）仍有窗口。用户删牌组后，最近 24 h 内存过 / 复用过的文件要到之后的维护才释放。
