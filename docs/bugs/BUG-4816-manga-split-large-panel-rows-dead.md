## BUG-4816 · 分镜大格按行切是死代码：文字框上下排列时被切成竖条
- **报告**：2026-11-17（用户：漫画域优化复核 gap-mangamisc-6，代码审读发现）
- **真实性**：✅ 真 bug（代码路径确认 + 单测复现）。根因：`packages/fushi_engine/lib/media/manga/panel_detection.dart:226-242`（修前行号）`splitLargePanel` 把文字框按中心 y 分行时，新建的行只 `(row ??= <PanelTextBox>[]).add(box)`，从不加进 `rows`；`rows` 恒为空，`rows.length >= 2` 永不成立，所有输入都落到后面的「按列切」。占页面 75% 以上的大格里文字框上下排列时，本该切成通栏横条，实际按每个文字框的中心 x 切成竖条，分镜导航的聚焦区域与阅读顺序都不对。既有用例只断言「2 个、首条 top 为 0、末条 bottom 为 1」，竖条同样满足，所以没拦住。补用例时又暴露同函数的第二处：`:272-297`（修前行号）按列切在 rtl 下先把文字框按 x **降序**排，再按「上一个中点 → 下一个中点」算列边界，得到的宽度是负的——两个框时只是输出顺序没按 rtl 反过来（调用方随后会重排，无可见影响），三个及以上时中间的列被 `next - previous > 0.01` 丢掉、剩下的互相重叠。按行切是死代码时这是唯一会走的分支，而漫画默认就是 rtl。
- **[x] ① 已修复** — `packages/fushi_engine/lib/media/manga/panel_detection.dart:241` 新建的行加进 `rows`。同一行内左右排的文字框仍只算一行（行数 < 2 时照旧按列切）。按列切的边界改成一律按 x 升序算，阅读方向只决定输出顺序（rtl 取反）。
- **[x] ② 已加自动化测试** — `packages/fushi_engine/test/panel_detection_test.dart`：原用例补 `left == 0 && right == 1` 与两条首尾相接（修前这两条断言红）；新增「同一行两个框 → 两条竖列，rtl 时先右后左」「三行（首行两个框）→ 三条相接的通栏横条」「rtl 三个同行框 → 三列铺满整格、每列含自己的文字框」（后者修前红）。
- **备注**：分镜导航默认关，修后已开启用户看到的大格切分方向会变（修 bug 的预期结果）。未在真机上看分镜导航的实际观感。
