## BUG-2909 · 游戏串流停止时主线程 join 捕获线程死锁（WGC 设备锁与 frame_mutex_ 锁序反转）
- **报告**：2026-10-03（用户：发来两份看门狗 hang dump `hang-1464-64716421.dmp`（12:42:28）、`hang-21140-64921187.dmp`（12:45:53）与错误日志；Windows 10 19045，NVIDIA，2.9.0-debug.16811）
- **真实性**：✅ 真 bug。两份 dump 主线程都停在 `flutter_webrtc_plugin` 的 track 停止路径 → `FushiGameStreamCaptureImpl::Stop` → `thread_.join()`（`fushi/windows/runner/game_stream_webrtc_capture.cpp` `Stop()`）。被 join 的捕获线程（`ucrtbase!thread_start` → `ThreadMain` → `IdleTick` → `DeliverLatestLocked`）持 `frame_mutex_`，卡在 `d3d11!CContext::Unmap` → `CDevice::CondObjectLock` 等 D3D11 设备锁。dump 21140 中另一端可见：WGC 的 `Direct3D11CaptureFramePool::PresentThread` → `ContentUpdated` → `FirePresentEvent` → 本仓 FrameArrived 回调，栈上带着 PresentThread 的 `RtlEnterCriticalSection`（已持设备锁），正阻塞在 `frame_mutex_`（`mtx_do_lock`）。即：WGC 回调线程「设备锁 → frame_mutex_」，捕获线程 `IdleTick`「frame_mutex_ → 设备锁」——ABBA 死锁，主线程 join 跟着永久阻塞，app 无响应。dump 1464 只抓到捕获线程这一端（精简 minidump 缺持锁线程的栈内存与设备对象堆），形态与 21140 相同。另：`ThreadMain` 原在持 `frame_mutex_` 时调 `StartCapture()`，会话一开回调就带设备锁来拿 `frame_mutex_`，是同一类反转的潜在入口。
- **[x] ① 已修复** — 锁序统一为「D3D11 设备锁 → frame_mutex_」：建设备后取 `ID3D11Multithread` 并 `SetMultithreadProtected(TRUE)`；`OnFrameArrived` / `IdleTick` / `TeardownCapture` 收尾块先 `DeviceLock`（RAII `Enter/Leave`）再拿 `frame_mutex_`；`StartCapture()` 移出持锁的建会话段（`StartCaptureSession`）。提交见分支 `worktree-fix-game-stream-wgc-lock-order`。
- **[x] ② 已加自动化测试** — `fushi/test/build/game_stream_wgc_lock_order_guard_test.dart`（源码守卫：设备开启多线程保护；每个持 `frame_mutex_` 后会碰 D3D 的入口先进设备锁；全文件 `frame_mutex_` 只允许紧跟设备锁或属于不碰 D3D 的置位段；`StartCapture` 不在持锁段里）。真 WGC 死锁无法在单测里稳定复现。
- **备注**：同次日志里的 `UpdateChecker.windowsHandoff.deleteInstaller` errno=32（安装器文件仍被占用）与镜像连不上属于另外的噪声，不是本次卡死原因。`window_recorder.cpp` 只在 FrameArrived 回调里碰 immediate context，锁序与 WGC 一致，未受影响。真机复现（游戏串流开关多次）未做。
