## BUG-4177 · Android 上扩展源偏好点 SAVE 后 Token 丢失（偏好桥回传上一拍的旧值）
- **报告**：2026-10-29（用户：Encoded，Discord 经 fushi-bot 代提，应用内反馈 Njruv6JSaL；Pixel 10a / Android 17；PC 正常）
- **真实性**：✅ 真 bug（代码路径推出，与现象逐步吻合；未真机复现）。`fushi/android/app/src/main/kotlin/app/fushi/reader/mihon/MihonPreferenceBridge.kt` `applyAndRead`（修前 45–64 行）先 `setup(screen)`——偏好对象挂进 screen 时读一次持久值——之后才 `applyValue` 直接 `shared.edit().put…().commit()`，**不经偏好对象**；`serialize` 读的是对象字段，回传的永远是写入前的旧值。Dart `MihonManager.setPreference`（`fushi/lib/src/media/manga/mihon/mihon_manager.dart` ~1274）把回传值 upsert 进 `manga_source_preferences`，下次请求又把这份旧快照写回 store。用户的顺序正好：选 Provider（回传旧 Provider，库里存旧值）→ 填 Token 点 SAVE（快照把旧 Provider 写回 store，但 screen 早已读到上次写进去的 TorBox，Provider 显示对了；Token 回传空串、库里存空串）→ Token「点完就没了」，Provider 看起来正常。桌面 sidecar（`MihonInvoker.invokeSetPreference`）先写快照、再建 screen、改动项经 `callChangeListener` + `saveNewValue` 走偏好对象，所以 PC 正常。
- **[x] ① 已修复** — 拆出纯 Kotlin `MihonPreferencePlan`（快照 = 除改动项外的值，列表项按条目自带 entryValues 取值；改动项单列）。`applyAndRead` 改为：快照先落 store → 建 screen → 改动项经 change listener + 偏好对象自己的 setter（`text` / `value` / `values` / `isChecked`）保存 → 重新建 screen 读回 store 真值。非偏好请求（`apply`）只写快照，不再建偏好屏。
- **[x] ② 已加自动化测试** — `fushi/android/app/src/test/kotlin/app/fushi/reader/mihon/MihonPreferencePlanTest.kt`：改动项与快照的拆分、各类偏好取值类型、越界列表项不写。**缺口**：「快照在 setup 之前、改动项经偏好对象」这一顺序在 androidx Preference 里，app 的 JVM 单测没有 Robolectric、建不出 PreferenceScreen，没有自动化覆盖。
