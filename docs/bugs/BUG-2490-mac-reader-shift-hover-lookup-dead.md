## BUG-2490 · macOS 阅读器 Shift 悬停查词无反应（WebKit 只在 WKWebView 为最顶命中视图时才派发 mousemove）
- **报告**：2026-09-11（用户：「mac端shift不能查词」）
- **真实性**：✅ 真 bug（沿真实代码路径定位；本机无 Mac 可复测，见备注）。阅读器的 Shift-悬停查词此前**只有一条腿**：正文 WebView 文档内的 JS `mousemove` 监听（`fushi/lib/src/pages/implementations/reader_fushi/webview.part.dart:1499` → `callHandler('onShiftHover')`），门控靠 `e.shiftKey`。这条腿在 macOS 上收不到事件：
  - WebKit 把 WKWebView 的 `mouseMoved:` 交给 `WKMouseTrackingObserver`，它先对窗口 contentView 做一次 AppKit 命中测试，**只有命中视图是 WKWebView 的后代**才把事件交给页面（WebKit `Source/WebKit/UIProcess/mac/WebViewImpl.mm` `-[WKMouseTrackingObserver updateViewIsTopmostAtMouseLocation:]` / `mouseMoved:`）。
  - Flutter macOS 嵌入层把「排在平台视图之后的 Flutter 绘制」的 paint region 写进 `FlutterMutatorView._hitTestIgnoreRegion`，落在其中的点 `hitTest:` 返回 nil（`engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterMutatorView.mm`）——这是 BUG-1692 已定性的同一机制。BUG-1692 只修了「点击」并按当时的 chrome 收紧了忽略区；悬停走的是另一条更严的门（命中测试 + tracking area 仅 key window 激活），且 2026-08-17 之后阅读器 chrome 又整体改成 ッツ 形态（顶部工具栏 / 进度线 / 状态行 / 悬停热区），任何一块在 WebView 之上的绘制都会让该区域的 DOM `mousemove` 消失，而 JS 腿是**唯一**一条腿。
  - Windows 不受影响：fork 的 WebView2 是 Flutter 纹理，指针先到 Flutter 再由 fork 逐个转发（`packages/flutter_inappwebview_windows/.../in_app_webview.cpp` `setCursorPos` → `SendMouseInput`），Chromium 从真实键盘状态取 `shiftKey`。
  - 附带：与视频页 BUG-880 相同的「光标停在词上不动、按 Shift 不出词」在阅读器上从未修过（两条腿都只在指针移动时派发）。
- **[x] ① 已修复** — 给阅读器补一条**宿主（Flutter）侧**的腿，两条腿按 `hostOwnsWebViewPointerInput` 互斥（BUG-2031 纪律：一平台一条腿）：
  - `fushi/lib/src/reader/reader_host_hover_lookup.dart`（新）：`ReaderHostHoverLookupGate` 门控（Shift **或**「悬停即查词」）+ 8px 节流 + 静止反查锚点，语义与 JS 腿逐字对齐；`readerHostHoverPointInside` 盒内判定。
  - `fushi/lib/src/pages/implementations/reader_fushi/webview.part.dart`：正文 `InAppWebView` 紧包 `MouseRegion(opaque: false)`（`localPosition` == CSS 视口坐标，不改任何命中）；引擎配置下发 `hostHoverLookup: !hostOwnsWebViewPointerInput`，文档内 `mousemove` 腿按 `window.__fushiHostHoverLookup` 让路。macOS 嵌入层在每个鼠标事件上同步修饰键（`FlutterViewController.dispatchMouseEvent` → `syncModifiersIfNeeded`），故 `HardwareKeyboard.isShiftPressed` 在 hover 时可靠，哪怕 WKWebView 持有 first responder。
  - `fushi/lib/src/pages/implementations/reader_fushi_page.dart`：`onDismissBarrierHover`（弹窗开着时唯一的 hover 入口）与正文 `MouseRegion` 共用同一把门控/节流（`_hostHoverLookupAt`）；`_applyHoverAutoLookupLive` 把开关随 `__hoverAutoLookup` 一起下发给歌词页（独立文档，`lyrics_mode_html.dart` 的 mousemove 腿同样让路）；新增 `_triggerShiftLookupAtLastPointer`：Shift 按下在最后指针位置直接查词（对齐视频页 BUG-880）。
  - `fushi/lib/src/pages/implementations/reader_fushi/caret.part.dart`：`_handleKeyEvent` 入口处 Shift `KeyDownEvent` 触发上述反查，不消费按键。
  - `fushi/lib/src/reader/reader_engine_config.dart`：新增 `hostHoverLookup`（默认 false = 维持 JS 腿）。
- **[x] ② 已加自动化测试** — `fushi/test/reader/reader_host_hover_lookup_test.dart`：门控/节流/锚点/盒内判定的纯行为测试 + `ReaderEngineConfig` 序列化 + 接线守卫（MouseRegion 紧包且 `opaque:false`、两条腿按 `hostOwnsWebViewPointerInput` 互斥、正文/歌词 mousemove 腿入口让路、barrier 与正文共用门控、Shift keydown 反查、exit 清位置的弹窗例外）。reader 页含真实平台视图，hover/keydown→JS 无法在 widget 测试驱动，接线部分按源扫描（与 BUG-880 守卫同范式）。
- **备注**：本机是 Windows，`tool/run_mac_itest.ps1` 指向的 Mac（192.168.1.34）本轮不可达，**未在真机验证**——状态按 `implemented_unverified` 看待，真机验收项：① 开书后按住 Shift 在正文滑动即出词、弹窗跟着走；② 光标停在词上按一下 Shift 即出词；③ 「悬停即查词」开关开着时纯悬停出词；④ 歌词模式同 ①③；⑤ Windows 行为不变（宿主腿只记位置不查词）。已知取舍：弹窗开着时指针移到弹窗本体上再按 Shift，会用最后一次落在正文/barrier 的位置反查（与视频页 BUG-880 同形，barrier 是 `Listener` 无 exit 回调）。
