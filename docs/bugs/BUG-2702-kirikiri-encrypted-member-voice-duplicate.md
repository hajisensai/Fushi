## BUG-2702 · KiriKiri 插件层加密成员的密文被当语音落盘并与真语音拼接（喫茶ステラ）
- **报告**：2026-09-26（用户：「柚子社的krkr引擎的游戏好像星空咖啡馆有问题」）
- **真实性**：✅ 真 bug，真机复现。原版 `CafeStella.exe`（KiriKiri Z，x86，SHA-256 `0dd0b3bcc5dcdda257f50ef52f121f919a7453c2afa614f8f82124cb92351d50`，插件 `PackinOne.dll` / `yuzuex.dll`）早注入后推进序章：每句角色语音在 `%TEMP%\fushi_gal_voice` 落两份同长度文件——逻辑名 `…_noz001_001.ogg`（以 `OggS` 开头）与 32 位十六进制物理名 `…_d19605d79466b2b99c720a2c1093e22f.ogg`（**不是 Ogg**，是归档密文；两份逐字节全不同）。根因：两个按存储名开流的 detour（`hook/adapters/kirikiri_adapter.inc` `Detour_TVPCreateIStreamStub` / `Detour_TVPCreateBinaryStream`）只用宽松的 `IsVoiceStorageName` 粗筛，唯一入队函数 `EnqueueKirikiriVoiceResourceOwned` 不看字节；已有的魔数判定 `KirikiriVoicePayloadExtension` 只在存储名**没有扩展名**时用来补后缀。消费端（`fushi/lib/src/mining/gal_voice_dump_index.dart` `findPairedResourceNames`）同 tick / 同 textseq 的文件全部返回，`transcodeVoiceResourcesToMiningAudio` 首尾拼接 → 卡片音频混入不可解码数据。
- **[x] ① 已修复** — 提交 `54cc74f25b9`：`EnqueueKirikiriVoiceResourceOwned` 在占任务槽之前要求 `KirikiriVoicePayloadExtension(data, len) != nullptr`（Ogg / RIFF-WAVE），否则丢弃。判据是字节容器，与加密方案、引擎版本、文件命名无关，对任何插件层解密归档的 KiriKiri 作品成立。
- **[x] ② 已加自动化测试** — `native/galgame_hook/tests/adapter_structure_test.py::test_kirikiri_voice_enqueue_rejects_non_audio_payloads`（魔数门位于占槽之前、两个 detour 都经这一入口）；魔数判定本身已由 `tests/kirikiri_voice_storage_name_test.cpp` 覆盖。
- **备注**：修复后同一路径真机复测：`noz001_001.ogg` / `noz001_002.ogg` 正常落盘，哈希名密文副本不再出现，全部新文件 `OggS`。解码器路径（`DumpVorbisDatasourceGuarded`）本来就查 `OggS`，不受影响。制卡 E2E 未跑。
