## BUG-5121 · stall-test-preemption-noise
- **报告**：2026-11-22（用户：项目审查 2026-11-21-project-review.md）
- **真实性**：✅ 真问题（测试稳定性，非产品 bug）。`fushi/test/media/novel/lnreader_online_book_test.dart`「连载更新的重建（读旧章 + 打包）不在调用方 isolate 上同步跑」在本机多 agent 并发跑测试时红（实测 sync=234ms、stall=460ms，断言 stall < sync/2），单独跑绿（本轮复测单独跑 sync=222ms / stall=37ms、sync=255ms / stall=18ms）。根因在测度本身：`fushi/test/helpers/event_loop_stall.dart` 的 `measureEventLoopStall` 只采**一次**样，取事件循环两次轮转之间的最长间隔。自校准（`measureSync` 量同步耗时 D）只校准了机器快慢，没校准 OS 抢占 / 抢核这类正向噪声：调用方线程在任意一段几毫秒的同步段里被换下去几百毫秒，最长间隔就整个被顶高，与被测代码有没有把重活压在本 isolate 上无关。stall=460ms 比整段同步重活 D=234ms 还长，只能是抢占噪声。同一 helper 的另一个用户 `fushi/test/media/audiobook/text_to_epub_test.dart`「convert does the heavy assembly off the calling isolate」同样受影响。
- **[x] ① 已修复** — 测度改成多次采样取最小值：`event_loop_stall.dart` 新增 `kEventLoopStallSamples = 5`、`measureMinEventLoopStall(samples, body(run))`（逐次量最长卡顿，返回各次结果、各次卡顿与最小卡顿）、`measureMinSync(samples, work)`（基准 D 也取最小）。依据：抢占噪声只会让间隔变长，真压在本 isolate 上的同步重活每一次都 ≥ D，所以最小值滤掉噪声又保留区分力；D 也取最小，避免 D 被噪声顶高放宽阈值让同步回归漏网。lnreader 用例每次采样在章节列表最前面多加一章（`/new{run}`），描述符次次不同，每次 `ensureBook` 都真走 `_syncChapters` 的重建而不是「章节没变」快路径，并断言就地重建恰好被调用 `kEventLoopStallSamples` 次、最终章数 = 300 + 5、原第 0 章（现第 5 章）正文与插图跟着路径走；text_to_epub 用例 `TextToEpub.convert` 每次都重读文件、重新转换，无缓存。
- **[x] ② 已加自动化测试** — 两条用例本身即测试。变异实测：把 `fushi/lib/src/media/novel/online/lnreader_online_book.dart` `_syncChapters` 里的 `await buildLnReaderOnlineEpubInBackground(...)` 改回同步 `buildLnReaderOnlineEpub(...)`，另起 16 个满载自旋 isolate 压 CPU 跑该用例：变异后红（sync=237ms，5 次 stall=[212, 240, 237, 219, 182]ms，最小 182ms ≥ 阈值 119ms）；修复版同样压力下两次绿（sync=193ms，stall=[19, 30, 28, 68, 16]ms；sync=152ms，stall=[43, 14, 13, 11, 10]ms）。两条用例所在文件定向跑 2 个 suite / 37 个用例全过。
- **备注**：没改成「测本 isolate 的 CPU 时间」：Dart 没有按 isolate / 线程取 CPU 时间的 API，进程 CPU 时间又把后台 isolate 一起算进去，区分不了。
