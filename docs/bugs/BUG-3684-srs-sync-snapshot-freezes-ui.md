## BUG-3684 · 复习模块开着时大库同步快照与媒体引用在主线程整库处理，全 app 卡死
- **报告**：2026-10-21（来源：应用内反馈 OMWOurRQKb，Windows 3.0.0-debug.20585）
- **现象**：导入约 1.2 万张卡后，SRS「浏览」页（11826 张卡）卡死，随后反馈页、设置页也「未响应」（看门狗 main thread unresponsive ≥10 s）；清空卡组仍卡，关掉复习模块恢复。日志另有 `SrsSyncScheduler.localDirectory` 同步中 drift「connection was closed」（`SrsDbStore._loadLocal` ← `SrsSyncEngine._upload`）。
- **真实性**：✅ 真 bug。浏览页本身不是根因（`srs_browse.dart` 只读卡片缓存与笔记头）。根因在复习模块常驻的同步链路，全部跑在 UI isolate 上：
  - 同步快照 `packages/fushi_srs/lib/src/sync/sync_engine.dart` `_writeSnapshot`：`exportAll()` 全量 jsonDecode、`SrsSnapshot.encode` 整块规范 JSON + SHA-256、写完再整块 `decode` 读回校验；只要 vv 的地方也整份解码旧快照；只要 ID 的地方也 `exportAll`。
  - 快照写失败不留记录，之后每轮都从头重做全量。
  - 每轮同步后媒体同步 `srsReferencedMedia` 经 `allNoteViews()` 整库物化全部笔记修改记录。
  - 清空卡组是软删除（墓碑 90 天后才物理清除），还给每张卡 / 笔记多写事件，物化成本不降反升。
  - 关库（`AppModel.closeDatabase`）前不等 SRS 同步，在跑的一轮打在已关闭的连接上。
  - 实测（`packages/fushi_engine/test/srs/srs_sync_ui_block_bench_test.dart`：6000 笔记 / 1.2 万卡 / 3.6 万日志、8.4 万事件、快照 44 MB，库在后台 isolate）：写快照那轮主 isolate 最长单段阻塞 2483 ms（encode 958 ms、decode 1427 ms），`srsReferencedMedia` 302 ms。用户字段 HTML 更大时按正文线性放大（≥10 s 为推测，未用用户库实测）。
- **[x] ① 已修复** — `6c113034f1`：快照按页导出（同一读事务内保证一致）、冻结按批取发件箱、只要 vv 时只取快照头、全量重发只取 ID；≥256 KB / ≥500 条的编解码与 SHA-256 进 `Isolate.run`；快照失败记录尝试并退避（再攒够一轮批次或过 24 h）；媒体引用两种口径（同步视图 / GC 保守视图）都改为按页扫字段，不加表；写失败且重读也失败时副本标为作废、后续写入直接报错；`SrsSyncScheduler` 增加 `canRun`（库关着不开新一轮）与 `quiesce()`，`AppModel.closeDatabase` 经 `addDatabaseCloseQuiescer` 等在跑的一轮收尾再关连接。修后：写快照那轮最长单段阻塞 35 ms，`srsReferencedMedia` 21 ms。
- **[x] ② 已加自动化测试** — `packages/fushi_srs/test/sync_snapshot_paging_test.dart`、`packages/fushi_engine/test/srs/srs_sync_large_library_test.dart`（新旧实现在软删 / 并发候选 / 已删笔记类型夹具上口径一致；大库单条 SELECT 读回行数有上界；退避逻辑变异实测会红）、`fushi/test/srs/srs_sync_scheduler_test.dart`「关库协作」组；基准 `srs_sync_ui_block_bench_test.dart`（默认跳过）。
- **备注**：未用用户真实库复测、未真机复测原始路径。快照导出事务会让其它 DB 查询排队约 1–2 s（不卡 UI，备份同样做法）。统计页与 AnkiConnect 仍调 `allNoteViews`（另见 srs_followup_tasks C / N）。
