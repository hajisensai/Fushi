## BUG-2744 · 横排听书跨插图时视口被拽回开章落点（插图闪动被跳过）
- **报告**：2026-09-27（用户，Windows：「看轻小说，横排的排版在有图片的位置播放不正常……图片会闪动，被跳过」）
- **真实性**：✅ 真 bug。根因在 `fushi/lib/src/reader/reader_pagination_scripts.dart` 的「迟到图片语义重锚」（`registerImageLateAnchor` / `reapplyImageLateAnchor`，`_sharedJs`，分页与连续两 shell 共用）：
  - 恢复落点（`restoreToCharOffset` / `restoreProgress` / `jumpToFragment`）登记一个锚，之后每张 block 插图 load 完成，`_sharedInitImages` 的 load 回调都调 `reapplyImageLateAnchor()` 把视口对齐回这个锚。锚只在用户手动翻页（`paginate`）时作废。
  - 有声书跟读翻页走分页 `scrollToRange`（`highlightSentenceAudioCue` → `revealElement`）/ 连续 `scrollToTarget`，跨插图暂停滚到插图走 `audiobook_bridge.dart` 的 `__fushiRevealTarget` → 同一个 `scrollToRange`——**都不作废、不替换**这个锚。正文插图由清洗器写成 `loading="lazy"`，要等跟读翻到离它足够近才 load；load 一到，视口就被拽回打开本章（或跨章落地）时的那页，下一句 cue 再翻回来 = 闪屏。开了图片暂停时，刚滚到插图、插图一 load 就被拽回，暂停停在错页、恢复后直接跳到图后正文 =「图片闪一下、被跳过」。
  - 横排更容易撞上：同一张插图在横排分页里离恢复点的页距更远，恢复时通常还没进懒加载距离；竖排插图常在恢复阶段就已加载完，重锚发生在开播之前，所以少见。机制两种书写方向、分页 / 连续都相同。
  - 复现（headless Chrome + 真实引擎产物 `reader_headless_shell_dump_test` + 真实 `AudiobookBridge` JS，1000×800、22px）：横排分页恢复在第 100 段（pos=13636），跟读推进到第 112 段那页（pos=15584）时前方插图 load，同一帧视口回到 pos=13636；插图 load 恰在跨图暂停滚到插图之后完成时，视口直接落回 pos=13636。连续横排同样在平滑跟读途中被拽回恢复点。
- **[x] ① 已修复** — `01aaeec1141`（揭示目标替换迟到图片锚）+ `631af528072`（审查修正：恢复锚与迟到图片锚分开存）。锚的语义改成「阅读器**当前**正在展示的语义目标」：分页 `scrollToRange` 与连续 `scrollToTarget` 把揭示目标登记成新锚（`{target}`，Range 复制一份，活 Range 在懒图被包进 `.block-img-wrapper` 后仍选中那张图），替换恢复锚；`reapplyImageLateAnchor` 对这种锚按目标本身重对齐（分页落到其起始边所在页，连续按跟读同一安全带判据）。分页不论本次是否翻页都登记——跨图暂停时 0 尺寸占位常还在当前页，load 撑开后插图才挪到下一页，重锚把视口带过去。用户翻页仍清锚；之后新的恢复登记仍覆盖目标锚。修后同一探针：插图 load 时停在当前页，跨图暂停期间插图可见，连续模式不再回拽。
- **[x] ② 已加自动化测试** — `fushi/test/reader/reader_follow_reveal_late_image_anchor_behavior_test.dart`（驱动同名 `.js`）：Node 里真执行分页 / 连续两个 shell 对象，假 Range / 元素的几何可移动：揭示后的迟到重锚不得回退到恢复锚、揭示目标被插图挤走时要跟过去、分页跨图暂停时占位在本页而 load 后插图在下一页要翻过去、之后新的恢复登记仍生效、清锚后无重锚。变异验证：撤掉分页修复红在「paged: … must not re-apply the stale restore anchor」，只撤连续修复红在「continuous: …」。`chapter_jump_late_load_reanchor_test.dart` 的「清空全部锚」补上新字段；`reader_follow_scroll_jump_behavior_test.js` 单独切 `scrollToTarget` 方法体跑，装置补 `registerImageLateAnchor` 桩。
- **[x] Windows 真 app 端到端** — `fushi/integration_test/reader_audiobook_image_late_load_itest.dart`（自造单章 EPUB + 中段懒加载插图 + 静音音频 + 逐段 cue，横排分页，真实播放，真实 WebView2，全程不点击）。2026-09-28 在桌面会话用 `tool/run_windows_itest.ps1` 离屏跑，同一份测试 A/B：修前基线（`22e1bc72b49`）红——「跟随」「图片暂停」两个变体都在跟读推进到 pos=16760.5（恢复页 P0+8 页）时插图 load，产品 load 回调执行后视口落回 P0=5587；只套上 `01aaeec1141` 的 `reader_pagination_scripts.dart` 后绿；在含 `631af528072` 的 `upstream/develop`（`84fbc523208`）上同样绿——load 前后都停在 16760.5，之后继续推进到 19554，图片暂停窗口 37 帧稳定采样插图全程在视口内。注意：图片暂停变体的判据 ③ 修前也过（那一轮插图在暂停前就 load 完），区分修前 / 修后的是判据 ① ②。
- **备注**：**审查修正（`631af528072`）**：初版让连续 `scrollToTarget` 的 `{target}` 连带清掉 `__imgReanchorCharOffset`，而 BUG-2652 的 `beginRestoreReanchor` 正是读它——播放中恢复完成时 Dart `_onRestoreComplete` 先同步下发跟读揭示（`notifySectionRestoreCompleted` → `_updateCurrentCue` → `AudiobookBridge.highlight`），之后才调 `beginRestoreReanchorInvocation`，两次 JS 按 FIFO，begin 必然退回现场采样，iOS 同一 WKWebView 头几帧 scroll 读 0 就会钉回章首并落库。现在恢复锚另存 `__restoreCharOffset` / `__restoreCharOffsetEnd`（`_setRestoreCharAnchor`），只由恢复入口（`restoreToCharOffset` 写入；`restoreProgress` / `jumpToFragment` / 越界回退写 null）与 `paginate` 改写，揭示与迟到图片重锚不碰它；守卫 `fushi/test/reader/restore_reanchor_transient_viewport_behavior_test.js` 用例 E（修复前红在「a follow reveal before begin must not drop the restore char anchor」）、F。
- **已知限制**：连续模式下用户用滚轮 / 触摸拖动自由滚动不会作废迟到图片锚（只有 `paginate` 清）——这些滚动分散在 Dart 侧多处裸 `window.scrollBy`（`webview.part.dart` 滚轮平滑步进与鼠标拖动、`reader_fushi_page.dart` 查词弹窗关闭时的滚动转发）和移动端原生触摸滚动，没有单一入口可挂，滚远后前方懒图 load 仍可能把视口拽回最近一次揭示 / 恢复的目标。未在本条修改；要修需先把连续模式的用户滚动收敛到一个 JS 入口。
