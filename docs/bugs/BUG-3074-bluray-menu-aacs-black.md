## BUG-3074 · 加密原盘进入原盘菜单纯黑（libbluray 找不到 libaacs）
- **报告**：2026-10-09（用户：截图 + 错误日志 `No protocol handler found to open URL bd://menu` / `The protocol is either unsupported, or was disabled at compile-time.`，CI 包 2.10.0-debug.18353）
- **真实性**：✅ 真 bug。用随包同一份 `libmpv-2.dll` 打开用户的原盘 `Cosmic Princess Kaguya\Disc 1/2` 复现：`[bd:error] AACS encryption detected but cannot find libaacs.` → libbluray 返回 `STREAM_UNSUPPORTED` → mpv `stream.c` 继续找协议，最后只报出那句误导性的「协议不支持」。PR #2012 只在解密测试副本（`Disc 2 - Fushi menu test`）上验收过菜单。两处根因：
  1. 菜单会话由 libbluray 自己读整张盘（菜单 / IG / 标题码流全走 `aacs_decrypt_unit`），而 Fushi 的 AACS 解密（`AacsMediaSession`）只服务它自己打开的标题；包里没有任何 libaacs，加密原盘的菜单必然打不开。
  2. 打开失败不报错：`player.open()` 不抛异常，mpv 错误只进 `VideoFushiPage._handlePlaybackError`（只写日志，`fushi/lib/src/pages/implementations/video_fushi_page.dart` `_handlePlaybackError`），从不设 `discMenuError`；libbluray 的真实原因在 `bd` 前缀日志里，media_kit 不转发，页面停在带菜单栏的黑屏。
- **[x] ① 已修复** — 新增 `native/fushi_aacs`：自写的 libaacs ABI 子集（`aacs_open2` / `aacs_decrypt_unit` / `aacs_get_*`…），密钥沿用 Fushi 既有的「KEYDB 按盘 ID 精确匹配 VUK」策略，由 app 经 `fushi_aacs_set_disc_key` 注册，解密算法与 `AacsContentDecoder` 逐项一致；Windows 装成 exe 同级 `libaacs.dll`，Android 打成 `libfushi_aacs.so`（soname `libaacs.so.0`，app 先加载、bionic 按 soname 命中），macOS 构建阶段编进 `Contents/Frameworks/libaacs.dylib`。`_prepareDiscMenu` 在设置 `bluray-device` 前调 `prepareBlurayMenuAacs`（`fushi/lib/src/media/video/bluray_aacs_module.dart`）：有 VUK 就注册；无钥且有加密码流就抛 `AacsConfigurationException`，复用标题直放的 KEYDB 提示；明文副本按「无钥明文」注册。菜单会话里首个导航快照之前出现 `bd` / `stream` error 即置 `navigation-open-failed`，页面给出 `video_disc_menu_open_failed`，错误日志带上 libbluray 原文。有钥的加密标题不再禁止制卡（共享 FFmpeg 后端本就按同一 KEYDB 解密）。
- **[x] ② 已加自动化测试** — `native/fushi_aacs/test/fushi_aacs_test.c`（FIPS-197 / SHA-1 向量 + 合成加密盘端到端，CI 两端 ctest）；`fushi/test/media/video/bluray_aacs_module_test.dart`（准备逻辑各分支、打开失败日志判据）；`fushi/test/build/fushi_aacs_packaging_guard_test.dart`（名字 → 构建 → 入包 → Dart 预加载 → 打开前注册的整条接线）；CI 校验 Windows/macOS 包内 libaacs 与 Android 每个 ABI 的 `libfushi_aacs.so`。
- **同链路附带根因（同一 PR 修）**：`fushi/windows/CMakeLists.txt` 在 include 插件之后才把 `CMAKE_INSTALL_PREFIX` 设成 bundle 目录，`media_kit_libs_windows_video` 配置期捕获到默认的 `C:/Program Files/fushi`，`bluray/bdj`（BD-J 组件安装器）、原生许可证、运行时清单全都装不进包：非管理员本地构建 INSTALL 失败，管理员权限的 CI 静默写进 Program Files——用户装的 2.10.0-debug.18353 实测没有 `bluray/` 目录。已把前缀设置挪到所有子项目之前（c938744eba），守卫钉住顺序，发布包必需文件清单加 `bluray\bdj\bdj_runtime.ps1`。
- **验证（2026-10-09）**：
  - Windows 原生：随包 libmpv + 本模块打开加密原盘 `Disc 2`，first-play → 正片 → `discnav menu` 后 `disc-menu-active=true`，读错误 0。
  - Windows 真实 app：`integration_test/bluray_disc_menu_itest.dart` 以**加密原盘** `Disc 2`（KEYDB 放在隔离 `APPDATA\aacs`）跑通：`disc-aacs` 阶段 → 原盘顶层菜单（截图为真实菜单画面）→ Enter 进正片并推进 → 返回菜单 → 再次进入 → 退出，All tests passed（86 s）。同次全新 build 目录、非管理员权限下 `bluray/` 已装进 bundle。
  - Android（API 34 x86_64 模拟器）：原生层确认预加载 `libfushi_aacs.so` 后 `dlopen("libaacs.so.0")` 返回同一句柄；真实 app 用加密原盘前缀夹具（AACS/CERTIFICATE/BDMV 原样，正片取 400 MB 前缀，字节未改仍是密文）跑同一 itest，All tests passed（72 s），菜单截图为真实画面。
  - 顺带修 itest：开焦点导航后根部重建，再按 `find.byType(MaterialApp)` 取 container 会找不到（实测 skipOffstage:false 也是 0 个），改用 `enableFocusNavigation` 已返回的 `AppModel`。
  - macOS：远程 Mac（192.168.1.34）本次离线，未做真机验证；构建脚本、CI 包内校验与守卫已就位。
- **备注**：不支持：总线加密（需要光驱）、AACS 2 / BD+（libbdplus 未带），与标题直放能力一致。iOS 按用户要求不做。
