## BUG-1432 · TODO-2652「三处快捷键台账仍记裸 logicalKey」经查证伪：`LogicalKeyboardKey.process` 在 5 个出包平台上根本不可达
- **报告**：2026-08-02（用户：TODO-2652，PR#720 调查时顺带发现的同族问题，怀疑三处运行期台账/桥接没做 IME 归一化）
- **真实性**：❌ **未复现 / 伪需求**——三处都不该改，且**连它们要复用的前提本身都不成立**。逐条：
  1. **按住临时倍速台账**（`hibiki/lib/src/pages/implementations/video_hibiki_page.dart:4523` 记 `_holdSpeedTriggerKey = event.logicalKey`，`hibiki/lib/src/media/video/video_player_shortcuts.dart:456/461/469` 用 `activeTriggerKey == event.logicalKey` 配对）。怀疑的后果是「IME 下按下与松开的键配不上 ⇒ 倍速卡住松不开」。**证伪**：IME 消费掉的按键在 Flutter 侧连 `KeyDownEvent` 都不存在（见下「根因」），`engage` 从来不会发生，台账永远是 null，谈不上卡住；IME 不消费的键则 down/up 逻辑键由引擎强制一致（`keyboard_key_embedder_handler.cc:244/268` 的 `result_logical_key = last_logical_record`，up 恒复用 down 记录的逻辑键），也配得上。两种情况都不产生卡死。
  2. **`resolveDictionaryPopupInputToken` 不传 `physicalKey`**（`hibiki/lib/src/pages/implementations/dictionary_popup_input_bridge.dart:126`；注意实际路径在 `pages/implementations/` 不在 `lookup/`）。**证伪**：该函数的入参 token 取值域被键表钳死在 `spec.keyTokens ∪ {Mouse1..4}` 内——三个生产者（JS 桥 `dictionary_popup_webview.dart:1430`、Flutter 焦点桥 `dictionary_popup_layer.dart:732`、宿主指针 `dictionary_popup_layer.dart:769`）回传的都只能是键表里的元素，而键表每一项都是某条真实 `InputBinding` 的 `serialize()`。`deserialize(serialize(b)) == b` 恒成立 ⇒ `resolveKeyboard` 的精确相等分支必中，物理回退分支按构造不可达。传 `physicalKey` 是纯死参数。
  3. **`_resolveMangaKeyAction` 不传 `physicalKey`**（活实现在 `hibiki/lib/src/media/manga/reader/manga_hibiki_page.dart:1916`；`pages/implementations/manga_hibiki_page.dart` 只是 211 字节的 re-export 壳）。两个调用方里 `_handleNativeNavigationKey`（:1942）同第 2 条，token 来源同样被钳死；只有 `_handleReaderKey`（:1801）拿的是真实 `KeyEvent`，**形式上**确实比 `home_page.dart:551` / `global_navigation.dart:216` 少了 `physicalKey:` 透传（BUG-430 当时的漏网页面）。但补上它同样修不好任何东西——理由见下。
- **根因（真正的平台事实，与 BUG-430/853/936 的共同前提相悖）**：`LogicalKeyboardKey.process` 是 **Flutter Web 专有**的产物（DOM `KeyboardEvent.key === 'Process'`），在 `packages/flutter/lib/src/services/keyboard_maps.g.dart` 里**只出现在 `kWebToLogicalKey`（:2398）一处**；`kWindowsToLogicalKey`（:2862）/ Android / iOS / macOS / GTK / GLFW 全部没有该条目。Windows 桌面端的真实机制是：IME 消费的按键由 Win32 以 `WM_KEYDOWN wParam=VK_PROCESSKEY(0xE5)` 投递，Flutter 的 Windows 嵌入层 `engine/src/flutter/shell/platform/windows/keyboard_key_embedder_handler.cc:174-181` 在 `sequence_logical_key == VK_PROCESSKEY` 时 `callback(true); return;`——**一个 `FlutterKeyEvent` 都不发**；随后的 keyup 因 `pressingRecords_` 里没有记录，落到 :254-259 的「The physical key has been released before ... Ignore the up event」同样被丢弃（引擎单测 `keyboard_unittests.cc:2026 ImeExtendedEventsAreIgnored` 钉住该行为）。即：**IME 吃掉的键在 Flutter 侧根本不存在，既没有 down 也没有 up，更没有 `process`**。`GetLogicalKey`（:124）对 VK_PROCESSKEY 返回的还是裸 `0xE5`，而 `process` 的 keyId 是 `0x0010000070f`，即便哪天漏出来也命不中任何 `== process` 判据。
  ⇒ 由此推论：`shortcut_registry.dart:338` 的物理回退分支、`reader_space_override.dart:82-86` 的两个 override、`caret.part.dart` / `home_page.dart` / `global_navigation.dart` 的四处 `physicalKey:` 透传，**全部是永不触发的死代码**。这与 BUG-936 记录的事实完全吻合：BUG-853 加完回退后**用户证实真机仍失效**，BUG-430 至今标着「真机门禁待验」，三轮修复的测试全是合成 `(process, physicalKey)` 事件、因而永远绿、无法证伪。
- **[x] ① 不修复（结论：三处都不该改）** — 未改任何 `lib/` 代码。给三处补 `physicalKey` 透传只会在一个不可达的前提上再堆一层死代码，让错误的心智模型更像既成事实；真正的用户症状（IME 激活时字母/空格类快捷键失效）根因在**事件根本不到达 Flutter**，任何 Dart 侧 `logicalKey`/`physicalKey` 判据都看不见它，必须换方向（见备注）。
- **[x] ② 已加自动化测试** — `hibiki/test/shortcuts/ime_process_key_reachability_guard_test.dart`（新建，3 用例）：① `process` 只在 `kWebToLogicalKey` 里有条目；② 逐张遍历 15 张原生端 logical 映射（Android/iOS/macOS/Windows/GTK/GLFW/Fuchsia，含各自 NumPad/Function 表）断言都不含 `process`；③ 裸 `0xE5 != process`。三条均已变异实测转红（分别为：把 `kWebToLogicalKey` 塞进原生表清单、把断言指向 `kWindowsToLogicalKey`、把 keyId 改成 `0xE5`），变异内容不在注释里。守卫**不禁止**代码里出现 `process` 比较（存量兼容层无害、照旧），只钉「这些分支当前不可达」这条事实——Flutter 哪天真把 `process` 引进某个原生平台键表，它会立刻转红提醒重评。
- **备注**：
  - 工具链事实基于本机实际在用的 **Flutter 3.44.0**（`flutter --version`，与 CI 一致）；`.fvmrc` 钉的 3.41.6 未单独取源验证，但 `VK_PROCESSKEY` 过滤及其注释源自 2022 年 flutter/flutter#95888、#104169，跨这两个版本反转的可能性极低。
  - 唯一未从源码定论的开放变量：**日文 MS-IME 在具体输入模式下到底把哪些键标成 `VK_PROCESSKEY`**（属 OS/IME 行为）。若某键被消费 ⇒ Flutter 收不到任何事件；若不被消费 ⇒ Flutter 收到完全正常的事件。**两种情况都不会出现 `logicalKey == process`。**
