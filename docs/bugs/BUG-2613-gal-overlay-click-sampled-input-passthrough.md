## BUG-2613 · galgame 桌面字典卡 / hook 台词浮窗上的左键被采样输入引擎看见而推进台词
- **报告**：2026-09-20（用户：Wight。魔法使の夜 WoH（HUNEX GGE x64）与穢翼のユースティア（August）上点字典卡 / hook 台词浮窗，下面的游戏「随机」跟着反应；用户反馈 galgame 查词普遍有随机穿透）
- **真实性**：✅ 真 bug。三条覆盖窗口——桌面路由字典卡 `GlobalLookupWindow`、hook 台词浮窗 `FloatingLyricWindow`、穿透工具条 `HookToolbarWindow`——全是 `WS_EX_NOACTIVATE` 置顶窗，点它们时游戏仍是前台。Win32 消息型引擎（KiriKiri 等）看不到这些点击（消息投给了光标下的我方窗口），但**采样型**引擎不看消息：HUNEX / Leaf 每帧 `GetAsyncKeyState(VK_LBUTTON)`（BUG-2024 / BUG-1882 已证）、SGRE 读 DirectInput 设备状态、其它引擎走 RawInput——物理键一按它们就推进台词；按帧采样 `& 0x8000` 会漏掉短点击，这正是「随机」的来源。注入侧早有能对游戏隐藏这类采样的 v19 输入盾（`native/galgame_hook/hook/generic_input_shield.inc:112` `GenericShieldRequestActiveForSurface`、HUNEX `hunex_gge_lookup_runtime.inc:428`、smash 同类），但它只认共享内存里的 `LookupShieldRequest`；runner 里所有发布点（`flutter_window.cpp` NativeGlyph 探针、`low_level_mouse_hook.cpp` AttachedGlyph 事务）都只服务 attached 校准表面，`kLookupShieldOwnerPopup` 预留了却**没有任何调用方**。桌面路由 `Reveal`/`RevealStack` 只做异步穿透 Arm（`global_lookup_window.cpp:1193` 注释「never consumes the underlying app click」，卡内 down 在 `HookProc` 里 `ShouldConsumeGameClientClick` 恒 false）；台词浮窗与工具条对 `LowLevelMouseHook*` / `VoiceHookReader` 零引用，也不知道游戏 HWND。direct galCard 之所以没这问题，是它经 `ArmLowLevelMouseHookAndWait(hwnd_, game)` 走每引擎一份的窗口属性契约 `SampledInputShieldContract`（要求弹窗 owner==游戏、类名 `FushiGlobalLookupWindow`），这条结构上覆盖不了台词浮窗。本机实测（`WH_MOUSE_LL` 吞掉左键后 `GetAsyncKeyState` 全程读 0、控制组 0x8000）确认 host 侧吞事件只能挡采样键态、挡不住 RawInput/DirectInput，所以修法仍走注入侧护盾的请求通道。
- **[x] ① 已修复** — host 侧接入既有 v19 护盾、不改 IPC 契约、不改注入侧：`fushi/windows/runner/low_level_mouse_hook.{h,cpp}` 新增覆盖窗口登记表（`RegisterOverlayClickShield` / `UnregisterOverlayClickShield` / `SetOverlayClickShieldGameResolver`，不可变快照 + `g_binding_mutex` 下整表替换，`low_level_mouse_hook.cpp:1799`）；`HookProc` 在 `g_target` 闸门**之前**对落在登记窗口（含子窗，按 `WindowFromPoint` + `GA_ROOT`）上的 `WM_LBUTTONDOWN` 同步发布 owner=Popup、target=绑定游戏 HWND 的 down 请求（`:358` `BeginOverlayClickShieldTransaction`，事件本身**不吞**，仍照常投给我方窗口），`WM_LBUTTONUP` 发布 release（`:343`）；release 发布失败时事务保留，由下一次 up / 下一次 down / 3s 宽限期定时器物理键态对账三条路重试，绝不让请求槽停在 down（那会把游戏之后所有左键都藏掉）。钩子生命周期改问 `HookWanted()`（`:305`，`g_target` 或登记表任一非空即装着），存活性补装与宽限期卸载两处同改。`voice_hook_reader.{h,cpp}` 新增回调安全的 `TryPublishOverlayClickShieldTransaction`（`voice_hook_reader.cpp:2311`：`try_lock` + 单次 CAS、回调里不做 HWND 查询，与 attached 快路同纪律）。登记点：字典卡 `Reveal`/`RevealStack` 登记、`ReleaseDismissHooks` 先撤登记再 Disarm（`global_lookup_window.cpp:1280` / `:1407`）；台词浮窗 `Show` 登记、`Hide` / `WM_NCDESTROY` 撤、`UpdateText` 每行刷新绑定的游戏 HWND（`floating_lyric_window.cpp:526` / `:615`）；工具条 `Show` 登记、`Hide` / 析构撤（`hook_toolbar_window.cpp:691`）。游戏 HWND 由 `flutter_window.cpp:1253` `ResolveOverlayClickShieldGame` 在登记时（窗口线程）按 `VoiceHookReader::CurrentPid()` + `FindProcessClientWindow` 解出，与 direct galCard 同源；没有 galgame 会话返回 nullptr，登记退化成空操作——有声书歌词条 / 剪贴板文本窗不受影响。注入侧对 Popup owner 的接受面是既有代码：通用护盾（GetKeyState / GetAsyncKeyState / GetKeyboardState / RawInput / DirectInput 工厂）、HUNEX exact、smash 均不按 `owner_kind` 区分，只要求 target 属本进程（通用与 HUNEX 还要求 `lookup_enabled≠0`，即游戏内查词总开关，默认开）。
- **[x] ② 已加自动化测试** — `fushi/test/lookup/gal_overlay_click_shield_guard_test.dart`（14 条源码守卫：登记/撤销/解析器接口；登记表在锁外解析、无游戏不装钩子、撤空走宽限期卸载；`HookWanted` 接管存活性补装与卸载、在飞事务算进 pending 与定时器对账；`HookProc` 的 down/up 都在 `g_target` 闸门之前且只认左键；`Begin` 不 `return 1`、只走 Try 发布、快门先于 `WindowFromPoint`、新 down 先结束旧事务；命中判定用 `GA_ROOT` 不用 `GetWindowRect`；release 失败保留事务 + 物理键态对账；Reader 侧 `try_to_lock`、无 `IsWindow`/`GetWindowThreadProcessId`、owner=Popup、release 不带 Left 位；四类窗口的登记/撤销点与顺序；注入侧 generic / HUNEX / smash 激活判定不含 `owner_kind`）。既有 C++ 源码门 `fushi_windows_attached_mouse_hook_nonblocking_source_gate` 重跑通过（新函数按它的纪律放在 `TryPublishLookupShieldTransaction`→`PublishLookupShieldTransaction` 切片之外、且无 HWND 查询）。runner C++ 经 msbuild `/t:ClCompile` 全量重编通过。
- **备注**：⚠️ 真机未复验（本轮无 WoH / 穢翼 运行会话）。**覆盖面按引擎分**：① 无 exact adapter 的引擎（August 等）→ 通用护盾，随 `lookup_enabled`；② HUNEX（WoH）→ exact `HunexGgeLookupShieldRequestActiveForLeft`，随 `lookup_enabled`；③ smash/fzmedia → 不随开关；④ **Leaf/AQUAPLUS（白色相簿2）、SGRE、Siglus 的 exact 护盾完全不读 v19 请求**，只认窗口属性契约（弹窗 owner==游戏 + 类名 `FushiGlobalLookupWindow` + Ready 属性），本条对它们**不生效**——要补的是各自 `popup_shield` 判定里 OR 上「v19 左键请求指向本进程」（与 HUNEX/smash 同口径），按 `native/galgame_hook/CLAUDE.md`「一引擎一任务」拆成三个独立任务，不在本 PR 里做。`kLookupShieldOwnerDismiss` 仍无调用方。Win32 消息型引擎（KiriKiri / Ren'Py / CMVS）本来就看不到覆盖窗口上的点击，请求对它们是空转一代。
