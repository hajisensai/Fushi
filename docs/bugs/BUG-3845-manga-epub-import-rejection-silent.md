## BUG-3845 · 漫画导入 EPUB 失败且不留原因
- **报告**：2026-10-25（用户：应用内反馈 OjZ-K53WBY「漫画导入 EPUB 格式失败，无论单个文件还是整个文件夹」，正文为空、没附日志，只有截图）
- **真实性**：⚠️ 用户样本对应哪种形态仍未确认（没有样本 / 日志）。已证伪的方向：「SVG 包页图的 EPUB 判定漏掉」——每页 `<svg><image xlink:href>` 包 JPEG 的固定版式 EPUB 在旧代码上就能被 `MangaArchiveImporter.looksLikeImageArchive` 认成漫画（`fushi/test/epub/epub_svg_cover_and_manga_test.dart` 的 SVG 包图用例在修复前已经通过）。已确认的一种拒收形态：spine 直接是 SVG 内容文档（`image/svg+xml`），漫画路径已修（见 ①）；书籍 / 阅读器路径仍不收 SVG spine 项（阅读器只按 HTML 注入分页脚本，要连阅读器一起改并上真机验证，不在本次范围）。
- **[x] ① 已修 SVG spine 形态（317efb4831）** — 根因 `packages/fushi_engine/lib/epub/epub_parser.dart:580`（修复前）`_parseSpine` 只收 `isHtmlMediaType` 的 spine 项，`image/svg+xml` 内容文档逐项 `continue`，整本 0 章抛「no readable chapters」，`MangaArchiveImporter._looksLikeImageEpub`（`manga_archive_importer.dart:886` 修复前）走进 catch 判「不是漫画」，单文件和文件夹导入同一判据都拒收。修法：`EpubParser.parseSyncFromPath` / `parseFromExtracted` 加 `includeSvgSpineDocuments`（默认 false，书籍 / 阅读器口径不变，也不移位存量书 chaptersJson 章号），漫画探测与导入两处（`manga_archive_importer.dart:507`、`:894`）传 true；SVG 章节走原生扫描取 `<image href>`，文字 / 扩展名判据不变。先补的诊断：`_looksLikeImageEpub` 原来 `catch (_) { return false; }`、纯图片判定只回 bool，现在否决理由经 `engineLog.logDiagnostic('MangaArchiveImporter', …)` 进 `ErrorLogService`，真导入抛的 `MangaImportException` 也带同一理由。
- **对照常见形态（代码路径核过）**：固定版式 XHTML+`<img>` ✅接受；XHTML+`<svg><image xlink:href|href>` ✅接受（原生 `chapter_image_refs` 扫整份文档）；EPUB3 nav（`properties="nav"`）在 spine 里 ✅跳过不判；spine 直接是 SVG ❌→✅本次修；spine 直接是光栅图（`image/jpeg` itemref，规范要求带 `fallback`，解析器不跟 fallback 链）❌仍拒收，未修——没有样本证明真实存在；含文字页（奥付、未标 nav 的 EPUB2 目录页，正文 >20 字）❌按设计拒收（有文字就当书籍导入，测试「含文字页」锁定）。
- **[x] ② 已加自动化测试** — `fushi/test/epub/epub_svg_cover_and_manga_test.dart`「OjZ-K53WBY」组：SVG 包图页 → 认成漫画；SVG spine 文档 → 认成漫画且页序跟 spine；默认书籍口径仍不收 SVG spine 项；含文字页 → 日志写明是哪一章。
- **备注**：下一份带日志的反馈里搜 `EPUB not recognised as image manga` 就能定位。如果确认是 SVG spine 形态，修法是让解析器接收 SVG 内容文档、阅读器给 SVG 章节包一层 HTML 外壳。
