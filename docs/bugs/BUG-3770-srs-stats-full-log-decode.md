## BUG-3770 · SRS 统计页每次全量读复习日志逐条 jsonDecode，随日志量线性变慢
- **报告**：2026-10-23（SRS 后续任务清单 N / 审查 HBK-AUDIT-011：20 万条日志时统计页约 18.7 s / 643 MB，数字来源未记录，本次重测）
- **真实性**：✅ 真 bug。`packages/fushi_engine/lib/srs/srs_stats_loader.dart:111-124`（修复前）每次打开统计页都 `select(srs_review_logs)` 整个 profile 的全部行（每行带几百字节 json），逐条 `jsonDecode` + `SrsReviewLog.fromJson`，再按卡建 `SrsCardHistory` 重放（`:161-169`）。实测（`packages/fushi_engine/test/srs/srs_stats_bench_test.dart`，`FUSHI_SRS_STATS_BENCH=25000`：2.5 万笔记 / 5 万卡 / 20 万条日志 / 15 万条复习，后台 isolate 文件库，develop@329a739431）：读行 953–1366 ms + 解码 675–1075 ms + 重放 61–116 ms，`loadSrsStats` 冷 3.4 s / 热 3.9 s（本机，未复现 18.7 s 那个量级）。**只读现有定长列不够**：即便只取 card_id/kind/rating/occurred_at/review_type/origin/duration_ms 七列也要 638–952 ms（行搬运，不是索引问题：查询本来就是整分区扫描，已有 `(profile_uid, occurred_at)` 索引），而且有效性（undo 撤销、导入等价）、新/学习/年轻/成熟分类（依赖前序有效结果 `res`）、提前复习（依赖上一条的到期日）都在 json 里，七列算不出来。
- **[x] ① 已修复** — `157d211826`。新增可重建缓存表 `srs_stat_reviews`（schema v129，设备本地、不同步、不进备份）：每条有效复习日志一行定长列（原始 `occurred_at` + 写入时 UTC 偏移、rating、分类、时长、上一条到期日、成熟变化）。行由 `SrsDbStore._cardCacheRow` 与卡片缓存**同一次重算**产出（卡自己 + 全部前身的日志、按服务器时刻排序的有效历史），所以同 ID canonical 覆盖、后来的 undo、同步晚到 / 服务器时刻改序、恢复、重建都随卡片缓存一起重算；每条日志只由自己的卡投影（后继卡的前身日志只用来定前序状态），整卡先删后写，一条日志至多一行。日序号 / 小时 / 提前复习读时按调用方日界算（不存受日界影响的 day）。缓存修订号 1 → 2：存量库打开时整张卡片缓存重算一遍补齐投影。`loadSrsStats` 改读投影（`loadSrsStatProjection`，裸 `customSelect`）；同一次运行内对照：旧日志路径 2557 ms → 读投影 443 ms（15 万行）。
- **[x] ② 已加自动化测试** — `packages/fushi_engine/test/srs/srs_stat_projection_test.dart`（真库：增量 = `rebuildCaches` 整份重建 = 从原始日志逐卡重放；undo 撤掉 / 再答进来、原始时刻保留、换日界读时重分桶；存量库缓存修订号 1 打开时补齐；1920 条日志下统计读取路径不出现任何读 `srs_review_logs` 的 SELECT）。变异实测：去掉整卡删除 / 去掉修订号 2 补算，前三条转红。迁移 `fushi/test/database/migration_v129_srs_stat_reviews_test.dart`。
- **备注**：投影之后统计页剩下的大头是笔记物化 `store.allNoteViews()`（同一基准 2.9 s，随**笔记数**线性，只为出处分布与搜索索引），不在本条范围，另立任务。schema 号几经顺延（develop 合入期间 v125–v128 被其它 PR 占用）最终为 v129。前身卡（更改笔记类型 / Lapis 迁移后隐藏的旧卡）的复习归属与 develop `7fa09fdf88` 同一规则：投影按日志自己的卡存，`loadSrsStats` 读时经 `SrsDbStore.historyOwnerIndex()` 改记到继承它历史的可见卡。
