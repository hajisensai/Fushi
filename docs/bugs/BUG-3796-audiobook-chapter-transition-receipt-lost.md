## BUG-3796 · audiobook-chapter-transition-receipt-lost
- **报告**：2026-10-27（来源：第三方 PR #2544 描述的「跨章守卫卡住、cue / 高亮冻结」；该 PR 的自愈判据未采纳，见备注）
- **真实性**：✅ 真 bug（沿代码路径验证，未真机复现）。有声书跨章守卫 `_chapterTransition`（`fushi/lib/src/media/audiobook/audiobook_controller.dart` `_maybeEmitCrossChapter` 竖起）的契约是「只由这次导航的结局释放」：落地回执 `_onRestoreComplete → notifySectionRestoreCompleted`，或中止收尾 `_failNavigation → abortChapterTransition`。develop `bf6d664351` 上有三条导航结局不发信号：
  1. **永久卡死**：`fushi/lib/src/pages/implementations/reader_fushi/navigation.part.dart:588 / :591 / :607`（`_navigateToChapter` 的三处早退）静默 `return`——被拒时没有 `_beginNavigation`，也就没有 restore 回执、没有 `_failNavigation`、连 content-ready 兜底计时都没武装；持守卫的 `fushi/lib/src/pages/implementations/reader_fushi/audiobook.part.dart:917`（`_handleCueCrossChapter`）await 完就走，守卫永久 true，`_updateCurrentCue` / `setChapterCues` 全部早退直到重开书。可达路径：`_handleCueCrossChapter` 只在**重定向前**判目录页（`audiobook.part.dart:872`），`_navigateToChapter` 在 `_resolveNavChapter` 重定向**后**再判一次（`:606`）——开「图片合并」时，被吸收的单图片章若后接目录页（典型：封面图 → 目录），跨章目标经重定向落到目录页即被拒。
  2. **只能靠 8s 兜底释放**：`fushi/lib/src/pages/implementations/reader_fushi/webview.part.dart:3007` 起的 `onReceivedError` 主框架分支手写四行只解开 restore 态，不解守卫；且只比较两个恒等的代际，不核对出错的是不是当前导航那份文档——被新导航顶掉的旧加载报 abort 会把在飞导航的 restore 态错杀。
  3. **只能靠 8s 兜底释放**：`fushi/lib/src/pages/implementations/reader_fushi/chrome.part.dart:3180`（`_reloadWithCurrentSettings` 装载失败 catch）已把代际 +1（上一代回执此后判旧丢弃），却不走 `_failNavigation`，守卫同样白等兜底计时器。
- **[x] ① 已修复** — `_navigateToChapter` 改为 `Future<bool>`（是否真的开始导航，拒绝分支一律 `return false`）；`_handleCueCrossChapter` 被拒即 `cancelChapterTransition()`（请求取消的明确信号）；`_navigateToChapterAndWait` 被拒直接返回 false、不去等上一次导航残留的 completer；`onReceivedError` 先用 `_isCurrentChapterDocumentUrl`（与 `onLoadStop` 同口径比路径）确认是当前导航文档再 `_failNavigation()`；重载失败 catch 收敛到 `_failNavigation()`。提交见分支 `fix/audiobook-chapter-transition-ack`。
- **[x] ② 已加自动化测试** — `fushi/test/media/audiobook/chapter_transition_receipt_lost_test.dart`（接线守卫：拒绝分支全是 `return false`、跨章调用方被拒即释放守卫、AndWait 不等别人的 completer、两条失败路径收敛到 `_failNavigation`）；同步 `reader_navigation_dispose_guard_test.dart` / `chapter_jump_double_jump_atomic_chain_test.dart` / `chapter_transition_abort_on_nav_abort_test.dart` / `reader_manual_navigation_follow_guard_test.dart` 的签名锚点。阅读器页没有可驱动 WebView 回执的 widget 测试层，故最强可落地层是源码接线守卫。
- **备注**：
  - 用户可见行为：守卫卡住期间 cue 不推进、正文高亮停在旧句、上下句拿冻结索引算目标。与排版无关、三种 view mode（paginated / continuous / vn）共用同一导航与回执路径，均受影响且修复同样适用；未在真机 / 模拟器复测（缺口）。
  - 未采纳 PR #2544 的「reader 当前章 == cue 所属章即放守卫」：`navigation.part.dart` `_beginNavigation` 在导航开始时就同步写 `_currentChapter = chapter`，等式在回执到来前恒成立，会提前放掉在飞导航的守卫；它也没找出回执为什么没来。
  - 仍未处理（已知风险）：`webview.part.dart` 的 `spreadReady` 回调不带代际，晚到的旧 spread 文档就绪消息会把当前在飞导航当成已完成（清兜底计时、置 `_readerContentReady`），且不通知控制器；跨章守卫本身不会由 spread 导航持有（翻页先 `noteManualReaderNavigation`、在飞期间 `_handleCueCrossChapter` 见 `_restoreInFlight` 即取消），但要根治需给 spread 文档补代际回报。控制器侧 `skipToCue` / `playCueOnce` 等 seek 路径在 seek 后无条件 `_chapterTransition = false`，会提前放掉 reader 在飞导航的守卫（方向相反的问题），未在本条修改。
