## BUG-5075 · Windows 上 tts_text_rules_and_rate_limit_test 的 tearDown 删临时目录报 errno 145（目录非空）
- **报告**：2026-11-21（审查 PR #3755 时在 Windows 本机跑 packages/fushi_engine/test/tts/ 发现）
- **真实性**：✅ 真（测试生命周期缺口，非产品逻辑）。`packages/fushi_engine/test/tts/tts_text_rules_and_rate_limit_test.dart:224`（origin/develop cbdc2a45ed）建了 `TtsRenderQueue` 却从不 `close()`：`enqueue` 末尾 `_kick()` 立刻开跑这条任务，`_runOne` 在测试体返回后仍在 `_persist()` 写 `jobs.json.tmp` → rename（`packages/fushi_engine/lib/tts/render/tts_render_queue.dart:615` / `:655` / `:681`），与 tearDown 的 `tmp.delete(recursive: true)` 赛跑；写落在删的期间就是 errno 145（目录非空）。本机 `dart test -r expanded` 直接看得到删完之后的写：`[fushi-engine] TtsRenderQueue.persist: PathNotFoundException: Cannot open file, path = '...\tts_rl_b2815e61\jobs.json.tmp' (errno = 3)`，栈在 `_runOne → _persist`。本机 3 轮没撞上 errno 145（赛跑窗口小），但「测试结束后队列仍在写」已实证。生产侧 `TtsRenderQueue.close()`（等 drain 与落盘链）本身是对的，同类用例（`tts_render_queue_test.dart`、`fushi/test/ops/ctl_tts_routes_test.dart`）都关了队列。与 BUG-5078 / BUG-5087 不是同一根因（那两条是 sync host 的视频指纹预热），同属「删目录前没等后台写收尾」。
- **[x] ① 已修复** — 用例里在删目录的 tearDown 之后登记 `addTearDown(queue.close)`（后登记先执行）：先等队列 drain 与清单落盘，再删目录。分支 claude/fix-win-test-teardown。
- **[x] ② 已加自动化测试** — 该用例本身即回归覆盖：修复后本机连跑 3 轮（连同 `tts_render_queue_test.dart` 共 13 条）全过，且不再出现删目录后的 `TtsRenderQueue.persist` 报错日志。
- **备注**：app 侧 `ttsRenderQueueFor`（`fushi/lib/src/media/audiobook/tts/studio/tts_studio_service.dart:28`）是进程级单例、从不 close，随进程结束；不影响本条，未改。
