## BUG-2529 · 跨章导航中止不解除跨章守卫，安卓切后台后上下句/高亮跟随永久失效
- **报告**：2026-09-14（用户：「安卓切屏可能会导致小说音频键上下句失效」）
- **真实性**：✅ 真 bug（结构性缺陷，沿真实代码路径定位；触发条件是「跨章导航中止」，前台正常跨章不发作）。根因 `fushi/lib/src/pages/implementations/reader_fushi/navigation.part.dart:516` `_failNavigation()`：它是三份导航中止（`_loadChapterDirectly` 抛错 / `_navigateToChapterAndWait` 等待超时 / content-ready 8s 兜底超时 `_startContentReadyTimeout`，BUG-868 收敛于此）的**唯一收口点**，清了 `_isNavigatingToChapter` / `_restoreInFlight` / `_restoreCompleter`，却**从不解除跨章守卫** `AudiobookPlayerController._chapterTransition`（`packages/fushi_audio/lib/src/audiobook/audiobook_controller.dart:290`）。
  该守卫由 `_maybeEmitCrossChapter` 在 cue 跨章那一刻竖起（`:1490`），**唯一的正常解除路径**是 reader 在章节内容就绪后回调 `notifySectionRestoreCompleted`（`audiobook_controller.dart:1582` ← `navigation.part.dart:154` `_onRestoreComplete`）——而导航中止恰恰意味着那条回执**永远不会来**。守卫就此永久卡 true：`_updateCurrentCue`（`:1376`）与 `setChapterCues`（`:960`）双双早退，`_currentCue` / `_currentCueIndex` 冻结在旧章旧句。
  于是「上一句 / 下一句」（底栏、媒体通知、耳机/蓝牙媒体键、音量键句子导航、快捷键全部汇聚到 `skipToCue` 同一漏斗）每次都拿**冻结的索引**算目标：冻结在章末时 `_nextCueIndex` 恒返回 null → 落 `onBoundarySkip` → `_handleBoundarySkip` → 又一次同样注定超时的 `_navigateToChapter`（`audiobook.part.dart:906`），按了毫无反应；冻结在章中时 `skipToCue` 把音频 seek 回**旧章**的时间点，表现为「上下句乱跳 / 跳回很前面」。cue 高亮与跟随同时死掉，且没有任何自愈，直到用户手动翻章（`noteManualReaderNavigation`）、拖进度条（`seekMs`）或退出重开书。
  Android「切屏」正是最容易踩中的触发场景：app 切后台后前台服务里的有声书照常播到下一章、照常竖旗发起跨章导航，而后台 WebView 被 Chromium 按不可见文档节流（rAF 冻结、timer 降频——与 [BUG-2465](BUG-2465-reader-reanchor-frozen-when-page-hidden.md) 同一族），restore 回执拖过 8s 兜底窗 → 兜底超时摘遮罩并调 `_failNavigation` → 守卫永久卡死；用户切回来或在通知栏/耳机上按上下句，就是「按了不动」。
- **[x] ① 已修复** — 提交见合并记录。`audiobook_controller.dart` 新增 `abortChapterTransition()`：语义是「这次跨章的回执永远不会来，释放守卫」，与 `cancelChapterTransition()` 的唯一差别是**尊重图片章停留序列**（`if (_imageChapterPauseActive) return;`——序列自己用 `holdChapterTransition` 持着守卫挡中间章回执的重入，TODO-1037，中止其中一章的导航不得把整段序列的守卫一起放掉；序列收尾自带 hold + 最终导航正常清守卫的契约，那次若也中止时 `_imageChapterPauseActive` 已为 false，照常解除）。`navigation.part.dart` 的 `_failNavigation()` 调用它。解除后状态机自愈：下一个 position tick 重新比对 cue 所属章与 reader 当前章，回前台时 WebView 已活，跨章导航正常落地。
- **[x] ② 已加自动化测试** — `fushi/test/media/audiobook/chapter_transition_abort_on_nav_abort_test.dart`（7 条）：控制器行为层（普通跨章在飞 → abort 解除守卫；图片章序列在途 → abort 不解除，带「序列收尾后同一个 abort 正常解除」对照组证明不是死分支；**症状机制**——守卫持住时换 cue 列表不重算当前 cue、解除后立刻重算）+ 装配守卫（`_failNavigation` 必须调 `abortChapterTransition`；兜底超时与装载失败都必须经 `_failNavigation` 收口，否则解除绕不到它们；`abortChapterTransition` 必须保留 `_imageChapterPauseActive` 早退）。反向验证做过：撤掉 reader 侧调用红 1 条、把 `abortChapterTransition` 改成 no-op 红 4 条。
- **备注**：真机复测未做（本机无 Android 设备/模拟器可跑这条需要「后台跨章 + WebView 节流超 8s」的路径）。修复是纯 Dart 状态机层，行为与守卫两层测试都反向验证过，但按 CLAUDE.md 的 reader/播放类纪律，**设备肉眼复测原始失败路径仍待补**。
  同链路上另有两处**未在本条修**的既有弱点，记在这里备查：① `_handleBoundarySkip` 的 `sentenceAudioCuesForSection` 查的是 `_chapterCues`（当前章）而非全书 cue，per-chapter 模式下恒返回空，边界跳句因此总要压到依赖 WebView 的 `_navigateToChapter`；② 边界跳句在 `_navigateToChapter` 静默早退（`!mounted` / `_controller == null` / `isChapterNav`）时对用户零反馈。
