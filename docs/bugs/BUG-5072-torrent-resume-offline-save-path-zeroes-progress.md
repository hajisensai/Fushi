## BUG-5072 · 重启时 save_path 暂不可达：fast-resume 被拒后在空路径全检得 0 片，周期快照把全 0 位图写回 .resume，路径恢复后永久跳过校验从 0% 重下
- **报告**：2026-11-21（用户转来第三方报告 `fushi_download_stuck_bug_report.md` 的 Bug 2）
- **真实性**：✅ 真 bug（核心主张成立，报告的机理描述部分不准）。根因 `native/fushi_torrent/fushi_torrent_ffi.cpp:1635`（a11db40c13f，`ht_load_resume_dir`）无条件清 `paused` 开跑、不管 `save_path` 是否存在。libtorrent 2.0.11 事实：文件缺失 → `verify_resume_data` 失败（`src/storage_utils.cpp:550-575`）→ `fastresume_rejected_alert` 后做**全量哈希检查**而非直接置零（`src/torrent.cpp:2141-2165`），空路径上读 ENOENT 只算「无此片」（`:2488-2493`）→ 0 片进 downloading；检查完成后 `write_resume_data` 写全长位图（`:7093-7108`），周期 `saveResumeSnapshot`（`app_model.dart` 每分钟）把全 0 位图写回；下次加载全 0 位图算「有 resume」（`src/add_torrent_params.cpp:92-95`），`verify_resume_data` 只核置 1 的片（`src/storage_utils.cpp:555-556`）→ fast-resume 被接受、永不校验，从 0% 重下。重下的片过了哈希，写回的是相同字节，不损坏数据。另：`drain_alerts` 静默丢弃 `fastresume_rejected_alert` / `file_error_alert`（诊断缺口，未在本轮处理）。已排除「rename/move 同步序列里旧路径快照覆盖新路径」（对照用例绿）。现场究竟是盘未挂载还是跨盘 move 超时的变体，需要报告人 `.resume` 里的 `save_path` 才能定。
- **[x] ① 已修复**（2910be5e047）— `ht_load_resume_dir`：resume 声称持有数据（`have_pieces` 非全 0 或 `seed_mode`）而 `save_path` 不存在时保持 `paused` 并清 `auto_managed`。暂停的种子不开始全检（`src/torrent.cpp:9482-9489`），期间写出的是空位图（`:7087-7096`），下次路径可达时 libtorrent 对已有文件全量校验、进度找回。宿主的上传策略只对已完成种子 pause/resume，不会把它抢回跑态。
- **[x] ② 已加自动化测试** — `packages/fushi_torrent/test/resume_rejected_progress_test.dart`：对照用例（串行 rename+move+save 写新路径、重启直接做种）+ 复现用例（离线加载必须暂停、周期保存不得写全长全 0 位图、路径恢复后必须回到做种且全片；修复前红：`state=downloading have=0/128`）。
- **备注**：已经受害的种子（`.resume` 已写入部分 / 全 0 位图）本修复救不回来，需要 `force_recheck`；「重新校验」入口与自动重检列为拍板事项 `review-torrent-recheck`。保持暂停后的恢复方式（下次启动 / 手动继续 / 自动 / 显示「存储位置不可用」）写进 `review-torrent-offline-save-path`。
