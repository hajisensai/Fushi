## BUG-5311 · music-disc-art-cold-start-cache
- **报告**：2026-11-23（用户：开发者本人，应用内反馈 rXKCdG5iya「这个cd要等一会才能加载出来。没缓存吗？」）
- **真实性**：✅ 真 bug（性能）。曲库专辑卡上的 CD 盘面每次启动都要等解码：按内容判扫图（`fushi/lib/src/media/music/music_disc_art.dart` `MusicDiscArtIndex._faceHit`，逐张引擎解码）与量盘面几何（同文件 `MusicDiscFaceGeometryCache._measure`，256 见方降采样解码 + isolate 计算）的结果只存在进程内（`MusicDiscArtIndex._byRoot` / `MusicDiscFaceGeometryCache._done`，文件头原注明「不落库、进程内缓存」），冷启动时两张表都是空的，曲库页 `_resolveDiscArt`（`music_library_page.dart:585`）要把所有编号扫图重新解码判一遍才 publish，卡片画出唱片后 `MusicDiscFace` 还要再等几何量完才淡入。
- **[x] ① 已修复** — 新增 `fushi/lib/src/media/music/music_disc_art_store.dart`（`MusicDiscArtStore`）：两类解码结果按图片文件（路径 + 大小 + 修改时间）落盘到 app 缓存目录 `music/disc_art_cache.json`，带格式版本号，写入串行合并、tmp + rename 原子替换。`MusicDiscArtIndex` 列目录时在 isolate 里一并 stat 候选图，文件没变直接用落盘结论、不解码；重列过的根目录里已不是候选的结论顺手删掉。`MusicDiscFaceGeometryCache` 量之前先查落盘几何，并新增 `preload`：`resolve` 在返回（曲库页 publish）前把落盘几何认领进进程缓存，卡片首帧 `peek` 就有几何、不再淡入等待。列目录本身不缓存（便宜，且是文件增删的真相）。存放取舍：结果是本地文件推导出的可重算缓存，放缓存目录不进备份 / 同步、不升 schema；`media_images` 的归属 CHECK 挂不到 `music_albums`（原注释）。
- **[x] ② 已加自动化测试** — `fushi/test/media/music/music_disc_art_store_test.dart`：模拟冷启动（清进程缓存、从落盘重读）断言扫图不再解码、几何 `peek` 首帧可用、`resolve` 返回前几何已认领；文件被替换（大小变）只重解那一张；缓存损坏 / 版本不对当空缓存。
- **备注**：triage 建议的终局是由 Rust 扫描器（`native/fushi_music`）扫描时认出盘面图与几何并写进 `music_albums`（新列 + 升 schema），需要在 Rust 端补 JPEG/PNG/WebP/BMP 解码与两套像素判据，范围远大于本修复，未做；本修复已消除冷启动重复解码这一主因。
