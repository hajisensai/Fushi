## BUG-2603 · 书卡长按菜单快捷 chip 在移动端被截成「查…/导…/从…」
- **报告**：2026-09-19（用户：「移动端这块显示的多了字体会显示不全」，附 iOS 截图：书架长按《無職転生 24》，三个快捷按钮只剩「查…」「导…」「从…」）
- **真实性**：✅ 真 bug。`fushi/lib/src/pages/implementations/media_item_dialog_page.dart` 旧 `_buildQuickActions`（upstream `9ec58e23e66` 第 380–408 行）用常量 `_quickActionMinChipWidth = 96` 猜「一个 chip 最少要多宽」：平分后 ≥ 96 就三等分硬排一行，否则整行竖排。对话框 `FushiDialogFrame` 宽度上限 420，内边距后可用 ≈ 388，三等分 ≈ 124 ≥ 96 → 判「放得下」；而 BUG-2505 新加的第三个快捷动作 `remote_book_audiobook_download`「从互联对端下载有声书」（9 字）真实需要 ≈ 190（字 + 图标 18 + 间距 + 按钮内边距），「导入有声书」≈ 130，`FushiActionChip` 的 `Text(maxLines: 1, overflow: ellipsis)` 于是把三个标签都截掉。按截图列表行高反推像素比 ≈ 1.53 px/pt，对话框正好顶在 420 上限，与上述算式吻合；用 NotoSansSC 真字体在 widget test 里按同宽度渲染旧实现，得到与用户截图一致的「查…/导…/从…」。日语「オーディオブックをインポート」等更长标签同样命中。既有窄屏测试只断言「不抛异常」——ellipsis 不抛异常，所以从没抓到。
- **[x] ① 已修复** — `_buildQuickActions` 换成自定义 `_QuickActionGrid`（`MultiChildRenderObjectWidget` + `_RenderQuickActionGrid`）：layout 阶段量每个 chip 的 `getMaxIntrinsicWidth`（含图标、内边距、字号缩放），取最宽者为列宽下限，从「全部一行」往下试到一列，第一个「等分列宽 ≥ 最宽 chip」的列数胜出；同列宽等宽排列、放不下的换行沿用同一列宽，RTL 镜像。删掉 96 常量，不再依赖任何拍脑袋数字。提交 `6799657a10e`。
- **[x] ② 已加自动化测试** — `fushi/test/pages/media_item_dialog_quick_actions_test.dart`：用上游真实三标签在 1200（对话框顶 420 上限，即用户场景）与 390 两种屏宽下断言每个标签 `RenderParagraph.didExceedMaxLines == false`、已换行、列宽一致；另一条「两列放得下、三列放不下」断言 2+1 网格与等宽。两条对旧实现均红（已实测）。`fushi/test/settings/md3_design_system_static_test.dart` 源码守卫锚点从 `Wrap(` 改为 `_QuickActionGrid(` 且禁止 `_quickActionMinChipWidth` 回归。
- **备注**：`didExceedMaxLines` 是 Flutter 3.44 `RenderParagraph` 的公开 getter，是「属性都对、就是宽度不够」这类截断唯一可断言的信号，以后同类布局守卫直接用它。
