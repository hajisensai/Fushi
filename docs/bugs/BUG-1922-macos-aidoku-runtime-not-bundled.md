## BUG-1922 · macOS 发布包缺 Aidoku runtime，删除再添加 Aidoku 仓库报 RUNTIME_MISSING
- **报告**：2026-08-29（用户：）
- **真实性**：✅ 真 bug。macOS 上漫画 → 导入页删掉 Aidoku 仓库再添加，红字报 `AidokuRuntimeException(RUNTIME_MISSING): Bundled Aidoku runtime is missing from /Applications/fushi.app/Contents/Resources/aidoku_runtime/fushi-aidoku-runtime`。根因不在 Dart 侧而在打包：`DesktopAidokuRuntime._bundledExecutable()`（`fushi/lib/src/media/manga/aidoku/aidoku_runtime.dart:382`）只认 `Contents/Resources/aidoku_runtime/fushi-aidoku-runtime` 这个固定路径、无任何回退，文件不在就抛 `RUNTIME_MISSING`（同文件 `:484`）；而把这个二进制装进 bundle 的 `tool/aidoku/build_macos_runtime.sh` **在全仓只被本地开发脚本 `script/build_and_run.sh:62` 调用过**——`.github/workflows/release-desktop.yml` 的 `macos` job 和 `build-multiplatform.yml` 的 `macos` job 里只有 `mihon_bridge` 的构建+校验步骤，一步都没有 Aidoku 的。所以每个从 release zip 装进 `/Applications` 的 macOS 用户，Aidoku 整条链（仓库刷新、装扩展、搜索、看图）从来就没有过，而 CI 全绿——没有任何一处断言过 bundle 里得有这个 helper。iOS 不受影响（走 `EmbeddedAidokuRuntime`，静态库由 `fushi/ios/build_aidoku_runtime.sh` 挂在 Xcode build phase 上）；Windows/Linux/Android 本就不支持 Aidoku（`AidokuRuntime.isSupported => isMacOS || isIOS`），用 Mihon。
- **[x] ① 已修复** — 两条 macOS job 各加一步「Bundle and sign pinned Aidoku runtime」，落在 `Contents/Resources/aidoku_runtime`，排在 Developer ID 签名之前（那一步按 Mach-O 判定重签 bundle 里每个可执行体，runtime 因此被一并签名+公证，无需改签名段）；步骤内 ad-hoc 签名 runtime → 跑新增的硬门 `tool/aidoku/verify_macos_runtime.sh` → 重签整个 app，与相邻的 Mihon 步骤同形。同时修掉一个尚未爆发但同形的坑（BUG-1668 的 ffmpeg）：`fushi.app` 是 universal，而裸 `cargo build --release` 只出 runner 的 host 架构，发布 runner 是 Apple Silicon，照抄旧脚本会得到一份 arm64-only 的 helper——CI 全绿、Intel Mac 上被内核以 EBADARCH 拒掉。`build_macos_runtime.sh` 因此改为默认 `FUSHI_AIDOKU_ARCHS=universal`（逐 target 构建后 `lipo -create`），`host` 只留给本地开发；verify 脚本拿 app 本体的 `lipo -archs` 逐架构核对覆盖，再用无参调用打 usage 做真启动冒烟。`script/build_and_run.sh` 改用同一道 verify 门，不再手写存在性检查。
- **[x] ② 已加自动化测试** — `fushi/test/build/macos_aidoku_runtime_packaging_guard_test.dart`（6 条）：Dart 侧路径段与错误码没漂移 / 两条 macOS job 都调 build+verify 且目标目录正确 / 发布 job 的打包排在 Developer ID 签名之前 / 发布 job 给 verify 传了 app 本体做架构核对 / 构建脚本默认 universal 且带 `--target` 和 `lipo -create` / verify 脚本自身含架构门与启动冒烟。判据两侧来源不同（Dart 源码 vs workflow YAML），任一侧漂移都会红。顺序断言前先剥掉 YAML 注释——步骤注释里就写着脚本路径和「排在 Developer ID 签名之前」，不剥的话 `indexOf` 会先命中注释里的字面量，守卫恒绿。变异实测 4 条全被抓、且只红对应守卫：删掉发布 job 的步骤但保留注释（红 3 条，证明剥注释生效）/ 把步骤挪到签名之后（只红顺序守卫）/ verify 去掉 app 本体参数（只红架构守卫）/ 构建脚本默认退回 host（只红 universal 守卫）；每次变异后按 sha256 校验回滚，POST-RESTORE 绿。
- **CI 实测**（run 33193079771，本分支 workflow_dispatch，五平台全绿）：macos job 的新步骤实跑通过——产物 `Mach-O universal binary with 2 architectures: [x86_64] [arm64]`，架构门 `app archs: arm64` / `aidoku runtime archs: x86_64 arm64`，启动冒烟 `verified .../Contents/Resources/aidoku_runtime/fushi-aidoku-runtime`，重签后 `valid on disk` + `satisfies its Designated Requirement`。同时暴露一处自找的成本：这一步耗时 17 分 51 秒（cargo 从零编译 wasmer 两个架构），而 debug 构建的 app 本体只有 arm64（日志实测），多出来的 x86_64 切片不被任何断言使用。因此 debug job 改用 `FUSHI_AIDOKU_ARCHS=host`（约省 9 分钟）；x86_64 交叉编译由 release-desktop.yml 的 macos job 兜底——它在每次 push 到 develop/main 时都跑，那里 app 本体是 universal、架构门是强门。并加第 7 条守卫锁住「发布 job 不得覆写 FUSHI_AIDOKU_ARCHS」（变异实测能红）。
- **备注**：只对**下一次 macOS 发布**生效——已发出去的 macOS 包里没有这个二进制，用户升级前 Aidoku 仍不可用。修复本身未在 macOS 上真机构建验证（本机是 Windows，`build_macos_runtime.sh` / `verify_macos_runtime.sh` 只做了 `bash -n` 语法检查，两条 workflow 做了 YAML 解析 + 步骤顺序校验）；首跑风险集中在 `rustup target add x86_64-apple-darwin` 后 wasmer 6.x 交叉编译到 x86_64-apple-darwin，以及 debug job 因此增加的构建时长。
