## BUG-3993 · Android 上大 srs.db 做备份导出 / 整理时 Scudo OOM 闪退
- **报告**：2026-11-02（用户：真机实测 SRS 修复时发现——小米平板 5 上官方版导出备份、同步各闪退一次，`Scudo ERROR: internal map failure (Out of memory)`，栈在 `ffsrs_store_snapshot` / `ffsrs_store_sync2`）；同源的另一份报告 2026-11-01（手机打开 Fushi 闪退，SIGABRT，srs.db 约 1.3 GB，每次打开都重来，原关闭 PR #2735）。
- **真实性**：✅ 真 bug。① libsqlite3-sys 0.35 的 `build.rs:229` 编 Android 时固定加 `-DSQLITE_TEMP_STORE=3`（临时数据永远放内存，`PRAGMA temp_store` / `temp_store_directory` 都改不回来）。`native/fushi_fsrs/src/store/mod.rs` 的 `snapshot_into`（`VACUUM INTO` 建索引的排序 + 对快照再 `VACUUM` 的整份整理副本）、`store/compact.rs` 的打开时整理全落内存；3.17 GB 的真实库在平板上 RSS 涨到 ~2 GB 后 abort。② `store/compact.rs` 的 `compact_pending` 只在成功后删，进程死在整理中途后标记还在，下次打开又整理一遍 → 打开即崩的循环。③ 原地 `VACUUM` 在 WAL 下先写整理副本再经 WAL 写回，峰值约多占两倍有效数据的磁盘。
- **[x] ① 已修复** — `native/fushi_fsrs/.cargo/config.toml` 用 `LIBSQLITE3_FLAGS = { value = "-USQLITE_TEMP_STORE -DSQLITE_TEMP_STORE=1", force = true }` 让临时数据落文件（所有构建脚本都在该目录跑 cargo；`force` 盖过环境里残留的同名变量）；`store/compact.rs` 的 `clear_temp_dir` 在 Android 上不还原，打开时设的「库所在目录」常驻为临时目录（Android 无默认临时目录，进程只有一份 srs.db）。
  - 打开即崩循环（原 #2735）：整理前自动提交 `compact_attempts` +1，正常结束（成功或失败）都删；连着 `MAX_ATTEMPTS = 2` 次进程死在中途就放弃这次整理、库照常打开。
  - 低占用整理（原 #2735）：老库（`auto_vacuum = NONE`）先 `wal_checkpoint(TRUNCATE)` 并校验 busy / 帧数，`VACUUM INTO <库>.compact`（顺带改成 `INCREMENTAL`），在新文件里清标记、写 `compact_last`、fsync，关掉写连接后确认 `-wal` 已删（还在 = 还有别的连接，不换）、删 `-shm`、原子 rename、fsync 目录，再用 `open_writer` 重新打开写连接；读连接池在这之后才开。`INCREMENTAL` 的库分块 `incremental_vacuum`（32 MB）原地收缩，每块后截断 WAL。需要的空间从 `2 × 有效数据 + 余量` 降到 `有效数据 + 余量`（原地收缩为 `32 MB + 余量`）；上次残留的 `.compact` 打开时先删。新库在 `open_writer` 里建表前就定成 `INCREMENTAL`；`snapshot_into` 剥表后快照是 `INCREMENTAL` 就 `incremental_vacuum`，否则才整库 `VACUUM`（不改进程全局的临时目录）。
  - 产物层守卫：`native/fushi_fsrs/build_android_so.sh` / `.ps1` 构建后按字节找 `TEMP_STORE=<数字>`，去重后必须恰好是 `TEMP_STORE=1`（CI `native-fsrs-gate.yml` 走 sh）。
- **[x] ② 已加自动化测试** — `native/fushi_fsrs/src/store/compact.rs` 的 `tests::temp_store_compiled_to_files`、`tests::cargo_config_overrides_android_temp_store`；`native/fushi_fsrs/src/store/sync2/tests_footprint.rs` 的 `compaction_gives_up_after_interrupted_attempts`、`compaction_rewrites_a_legacy_db_with_one_copy_of_live_data`、`compaction_shrinks_an_incremental_db_in_place`、`compaction_does_not_swap_files_under_another_connection`、`bundled_sqlite_lets_rewrites_spill_to_files`。真机对照（小米平板 5，arm64，同一份 3.17 GB 真实库，探针直接调 `SrsCore::open` + `snapshot_into`）：修复前（`TEMP_STORE=3`）快照阶段 abort（exit 134）；修复后（`TEMP_STORE=1`）58 s 完成、产出 2.59 GB，快照阶段峰值 RSS 不涨（VmHWM 维持打开时的 660 MB）。
- **备注**：同步那次闪退（`ffsrs_store_sync2`）推测同源（大排序落内存），本次未单独复测。「升级后首次打开整理」（重写换文件）这条路径尚未在真机大库上复测。
