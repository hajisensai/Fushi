## BUG-4391 · PIN 防爆破按可伪造的自报设备 id 分桶且无总量预算，无头端可被无人值守穷举
- **报告**：2026-11-10（用户：互联 host 安全审查 V-E1 / H1b）
- **真实性**：✅ 真 bug。（行号按 94317ab6295）`packages/fushi_engine/lib/sync/fushi_sync_server/pairing.part.dart:667-675` 的 `_pinRateLimitSourceKey` 优先取 client 自报的 `dev:<clientDeviceId>`：每个会话换一个 id 就是一个新来源，按来源的 `FushiPinRateLimiter`（`pairing/fushi_pairing_protocol.dart:255-340`，`maxTrackedSources=256` 满了淘汰最旧）永远锁不住；反过来冒报受害者的 deviceId 能把受害者锁在外面。没有任何总量预算，IPv6 下一个 /64 有 2^64 个源地址，单靠按 IP 也挡不住。`_enforcePairSessionCap`（`pairing.part.dart:630-644`）全局 64 个会话满了淘汰全局最旧，不看来源，公网刷会话能挤掉局域网会话与票据会话。无头端 `headless_host.dart:789-792` 的 `_approvePairing` 对 pinRequired 直接放行，没有人工环节，于是「pair/v2 → confirm 猜一次」可无限循环。修复前新测试实测：同一 IP 每次换 `clientDeviceId` 永远 401、从不 429；20 个公网 IP 轮流猜永远 401；冒报受害者 deviceId 失败 5 次后受害者从别处带正确 PIN 被 429；`2001:db8::1..5` 各猜一次互不影响；全局 64 淘汰让 70 个公网来源挤掉票据会话、40 个公网来源挤不出分区效果。
- **[x] ① 已修复**（`dc44e2a30d0`）— 引擎：`fushi_pairing_protocol.dart` 新增 `FushiPinFailureBudget`（窗口 15 min 内累计 10 次失败锁定 `15 min × 2^level`，封顶 24 h；成功 / 管理员 reset 清零；24 h 无失败 level 归零）与 `FushiPinRateLimiter.reset()`；`FushiPairSession` 新增 `sourceKey` / `sourceKeyTrusted` / `originClass` / `protectedFromEviction`，在 `_handlePairV2` / `_startTicketPairSession` 建会话时从 BUG-4390 的 `_RequestOrigin` 填好（IP，IPv6 按 /64；可信代理解析出的转发来源；隧道 NodeId），删掉 `_pinRateLimitSourceKey`（不再有 `dev:` 分支）。`FushiSyncServer` 按来源类别各持一份 `FushiPinFailureBudget`，公开 `pairingLockouts` / `resetPairingLockout()`，新增 `pinApprovalIsManual`（默认 true）。`pair/v2` 创建阶段 pinRequired 且非票据时，本类别或本来源锁定即 429 `rate_limited`（不建会话、不生成 PIN、不弹审批）；confirm 的 PIN 失败（含缺 proof）同时记来源与类别，任一锁定回 429；成功清来源与类别计数；票据会话（192-bit secret）只记来源、不进类别预算。会话上限改成按类别分区：每类别 32、每个可信来源 4；满了先淘汰本来源最旧的，再淘汰本类别会话最多的来源的最旧会话；票据会话与人工批准过的 PIN 会话（`pinRequired && pinApprovalIsManual`）不淘汰，类别里全是受保护会话时回 429（票据会话此时不消耗票据）。无头：装配 `pinApprovalIsManual = false`，`HeadlessHost.pairingLockouts` / `resetPairingLockout()`；admin API `GET /api/admin/pairing` 加 `lockout: {lan, p2p, public}`（ISO 8601 UTC 或 null），新增 `POST /api/admin/pairing/unlock` → 204；WebUI 配对区块在任一类别锁定时显示「来自{类别}的配对因多次 PIN 错误暂停至 {时间}」与「解除」按钮（中英两表同步）。
- **[x] ② 已加自动化测试** — `fushi/test/sync/pairing/fushi_pin_failure_budget_test.dart`（阈值、窗口、逐级翻倍封顶、锁定中不累计、成功 / reset 清零、24 h 衰减）、`fushi/test/sync/fushi_sync_server_pair_bruteforce_test.dart`（计划例 1–7 + 类别全受保护回 429，经 `handleInProcess` + 假 `HttpConnectionInfo`）、`packages/fushi_server/test/admin_api_pairing_lockout_test.dart`（真 `HeadlessHost` 经可信代理 XFF 换 10 个公网来源锁住公网类别，admin API 报 `lockout.public`，unlock 后清空、可再尝试）。按新语义改写：`fushi_sync_server_pair_ratelimit_test.dart`（锁定中 pair/v2 本身回 429）、`fushi_sync_server_pair_session_prune_test.dart`（上限断言 64 → 类别上限 32）、`interconnect_p2p_tunnel_test.dart`（锁定后建会话即 429）。

- **评审修正（2026-11-11，`ea38207cdab`）**
  - 根因：`pairing.part.dart` 的按来源限速 / 锁定（建会话预检、confirm 预检、`recordFailure` / `recordSuccess`）对 `sourceKeyTrusted=false` 的键照常记账。默认配置下经本机反代进来的所有请求共用 `ip:127.0.0.1`，一个攻击者 5 次失败就把代理后的所有人（含管理员签发的票据配对）锁 15 分钟；`p2p:?` 同理。另：带转发头却不在可信名单的非回环对端被标成可信键（`_classifyRequestOrigin` 末尾 `sourceKeyTrusted: !peerIsLoopback`），代理后的人共用一个「可信」键、互相挤占每来源 4 个会话的名额。
  - **[x] ① 已修复** — `FushiPairSession` / `_RequestOrigin` 加 `trustedSourceKey`（不可信时 null）；按来源的限速与锁定、交给宿主的 `FushiPairRequest.sourceKey` 只认它，不可信键只计来源类别预算；带转发头而对端不是可信代理（或解析不出转发来源）时 `sourceKeyTrusted=false`。取舍：直连攻击者自填转发头可绕开按来源的 5 次锁定，但仍受类别预算（10 次锁整个类别）约束。
  - **[x] ② 已加自动化测试** — `fushi_sync_server_pair_bruteforce_test.dart` 例 9（经本机反代、未配可信代理：前 9 次 401、第 10 次锁公网类别，限速器不记共用键）、例 10（公网类别被锁后经同一反代的票据配对仍 200）、例 11（局域网反代后的来源不按代理 IP 锁、不受每来源 4 个会话限额）；`fushi_sync_server_pair_ratelimit_test.dart` 改用可信局域网对端（进程内请求）并补「锁定前开好的会话锁定后带正确 PIN confirm 仍 429」（评审 tests-2）；`interconnect_p2p_tunnel_test.dart` 的 `p2p:?` 用例改为由隧道类别预算兜底（第 10 次 429）。
- **复核修正（2026-11-11，评审 recheck-1）**
  - 根因：上一轮 `pairing.part.dart` `_classifyRequestOrigin` 末尾改成 `sourceKeyTrusted: !peerIsLoopback && !forwarded`，让请求方自填的转发头决定是否按来源限速：直连攻击者单个公网 IP 随手带 `X-Forwarded-For` 就绕开按来源的 5 次锁定与每来源 4 个会话限额，独自撞满公网类别预算（10 次）锁住所有人的公网 PIN 配对，最长 24 h。
  - **[x] ① 已修复** — 回退为 `sourceKeyTrusted: !peerIsLoopback`：非回环的 TCP 对端 IP 伪造不了，带不带转发头都按它分源；局域网反代背后多人共用一个 IP 的部署靠 `trusted_proxies` 登记反代解决。上一轮「取舍」作废。回环键与 `p2p:?` 只计类别预算的修正保留。
  - **[x] ② 已加自动化测试** — `fushi_sync_server_pair_bruteforce_test.dart` 例 11 改为「直连对端自填转发头第 5 次仍按来源 429、锁定期间开会话 429、公网类别未锁、其它来源照常 200」，新增例 12「直连对端带转发头也受每来源 4 个会话限额」；`fushi_sync_server_request_origin_test.dart`「审批请求只带能区分真实来源的 sourceKey」里带转发头的非回环局域网对端改期望 `ip:192.168.1.5`。
- **备注**：线上契约 B / C。app 端 pinRequired 会话在创建阶段就要人工点「允许」，攻击者不经主人点头消耗不了预算；无头端公网类别可能被持续攻击锁住（取舍 T2），局域网 / 隧道不受影响，出路是管理员签发配对链接（计划步骤 6，并入本 bug）与 WebUI「解除」。`fushi_server ctl` 未加 unlock 子命令（计划未要求）。
