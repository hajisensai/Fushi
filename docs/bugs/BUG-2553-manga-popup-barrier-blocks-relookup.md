## BUG-2553 · 漫画查词弹窗开着时点另一个词只关栈不换词
- **报告**：2026-09-15（用户：Windows 桌面版漫画阅读器，「已打开一个查词弹窗后再点另一个词，必须先把当前弹窗关掉才能点新的词；fushi.moe 的网页 Demo 上是正常的」）
- **真实性**：✅ 真 bug。弹窗不是 route，是宿主页 Stack 里的 `Positioned.fill(buildDictionary())`，弹窗可见时 `BaseSourcePageState.buildDictionary` 先铺一层全屏 `LookupDismissBarrier`（`fushi/lib/src/pages/base_source_page.dart:668-693`），它的叶子对 hit-test 实心，底下的 WebView 收不到任何指针。barrier 的 tap 走 `onDismissBarrierTap(globalPos)`，默认实现一次性清整栈（`base_source_page.dart:253`）。小说阅读器覆写了它把坐标逆映回 WebView 重新选词（`reader_fushi_page.dart:4220-4232`），漫画页 `fushi/lib/src/media/manga/reader/manga_fushi_page.dart` 修复前**没有任何** `onDismissBarrierTap` / `onDismissBarrierHover` 覆写（只覆写了滚轮用的 `onDismissBarrierPointerSignal`，原 `:2915`）——于是「点另一个 OCR 词」= 点 barrier = 清栈，第二次点击才到得了 WebView；弹窗开着时 Shift 悬停连查同样是死的。网页 Demo 没有 Flutter 全屏 barrier，所以能连点。
- **[x] ① 已修复** — 漫画页新增 `_webViewHostKey`（挂在 `WebViewDeathGuard` 重建子树**外面**，`manga_fushi_page.dart:4805`）与 `_webViewLocalFromGlobal`（`:4812`，RenderBox `globalToLocal`，与阅读器同口径）；覆写 `onDismissBarrierTap`（`:4825`）把点击转发到覆盖层新入口 `window.__mangaBarrierTapAt(x, y)`（`manga_overlay_html.dart:1292`），JS 侧 `_selectOcrCharDetail` 回三态 `'hit' / 'same' / 'miss'`（`:1260`）：命中新字走既有 `onTextSelected → processMangaSelection → prunePopupStack(0)` 复用热槽无缝换词；再点同一个字或点空白才 `clearDictionaryResult()`；判定收在纯函数 `MangaFushiPage.barrierTapClosesPopup`（`:477`，eval 失败/未知值一律关栈，宁可多关不能卡死）。顺带覆写 `onDismissBarrierHover`（`:4858`）转发 `window.__mangaBarrierHoverAt`，弹窗开着时 Shift 悬停连查恢复。提交：`44a9937c03`。
- **[x] ② 已加自动化测试** — `fushi/test/media/manga/manga_lookup_barrier_relookup_test.dart`：覆盖层文档契约（两个入口存在、三态返回、`_selectOcrChar` 仍是布尔封装、WebView 内原生点击路径不变）、纯函数 `barrierTapClosesPopup` 全分支、页面源码守卫（覆写存在、走 `_webViewHostKey` 逆映、宿主 key 在重建子树外、miss 才关栈）。
- **备注**：改动只在 Flutter barrier 与覆盖层 JS 之间的转发层，`onTextSelected` 仍是全工程唯一注册点、`pointerup` 仍是唯一监听（收敛不变式测试照常绿）。**真机复测未做**（本机 app 正在被用户使用、内存余量 5 GB 不宜再起 Windows Release 构建）：请按用户原始路径在 Windows 上开一本已 OCR 的漫画→点字出弹窗→直接点另一个字，预期弹窗原地换词；点空白/再点同字关闭。
