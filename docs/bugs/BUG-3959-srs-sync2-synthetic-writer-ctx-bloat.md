## BUG-3959 · 复习同步 v2：合成写入者 `sync2:` 进了因果上下文，本机每条新修改 ctx ≈ 780 KB
- **报告**：2026-11-01（用户：同步一直在跑、打开卡片 / 牌组设置慢，srs.db 持续膨胀）
- **真实性**：✅ 真 bug。真实库副本（22:18）：`srs_field_edits` 里 467 行 `length(jslim) > 500 KB`、共 367 MB（正常行约 2 KB），连 `deck/collapsed` 这种布尔修改也是；它们的 `ctx.vv` 带 15027 个 `"sync2:tags:<笔记>":1`。本设备在 `sync2_legacy` 的那一行 ctx 781 KB、同样 15027 项。来源：profile 并入（`packages/fushi_engine/lib/srs/srs_profile_merge.dart:743/759` 把合成标签行与其写入者按 ID 映射后照搬）走 Rust 盖戳路径，把 15027 条合成标签行包成带旧戳的操作（本设备 seq 15233–648707；另一台设备 27 条）。根因入口（修复前 develop `315f53888b`）：
  - `native/fushi_fsrs/src/store/sync2/mod.rs:307-321` `note_legacy`：投影旧戳操作时 `d.add(&l.writer, l.seq)` 不分写入者，合成写入者的 dot 进了本设备的 legacy 闭包，旧戳 ctx 里带的合成项也照单并入；
  - `mod.rs:276-305` `legacy_closure`（部分覆盖分支同样 `add`）→ `mod.rs:492-503` `edit_row`：本机每条 v2 修改的 ctx = 作者 vv ∪ 整份 legacy 闭包，于是每条都带 15027 项；
  - `mod.rs:1007-1022`（`body_of_event` 盖戳分支）与 `mod.rs:1115-1130`（迁移 `legacy_body`）：外来 / 迁移记录的 ctx 原样写进新操作载荷；`mod.rs:1062` `enqueue_legacy_rows` 按 profile 排全部修改记录（含合成行）；
  - 全仓只有 `native/fushi_fsrs/src/registers.rs:411` 在「与删除并发」里跳过合成行，因果上下文的维护从没排除它们。
  - 修正一处先前的推断：膨胀的是**本地投影**（写库 + 读库 + 打开卡片解析），**不是**上传——v2 本机修改的操作载荷只带设备版本向量，实测载荷带 `sync2:` 的只有那 15044 条合成行操作本身（平均 1.1 KB）。
- **[x] ① 已修复** — 合成写入者一律不进因果上下文：`note_legacy` / `legacy_closure` 不记它们的 dot、并剪掉旧载荷 ctx 里的它们（`Dvv::drop_writers`）；盖戳事件与迁移包操作时剪掉 ctx 里的合成项（`legacy_ctx_json`）；投影旧戳行（`edit_row`）用同一个 `strip_synthetic_ctx`。srs.db **v19** 一次性去掉存量 `sync2_legacy.ctx` 与 `srs_field_edits` ctx 里的合成项（`strip_synthetic_writers`，UPDATE 走摘要触发器，操作日志一字节不动，可重放）；摘要串前缀 `2:`→`3:`（新旧版本互不比较、同 vv 下缓存的旧根重算）；v18 之后的升级不再要求「两倍有效数据」的空闲空间。依据：合成 dot 只属于那条笔记唯一的合成 `tags` 行（`refresh_tags_row` 直接改写、标签不经 `land_edit` 支配裁剪），支配只在同一寄存器内判，「与删除并发」本就跳过合成行——所以去掉它不改变任何寄存器的胜者 / 可见败者 / 冲突。提交：见 PR。
- **[x] ② 已加自动化测试** — `native/fushi_fsrs/src/store/sync2/tests_synthetic_ctx.rs`（盖戳 + 本机写入不带合成项；修复前包的旧操作投影时剪掉；v19 迁移：注入前 / 注入后 / 剪后三份寄存器裁决相同、与新投影逐字节相同、摘要相同、可重放）、`native/fushi_fsrs/src/sync2/dvv.rs` `dropping_writers_commutes_with_merge`、`packages/fushi_engine/test/srs/srs_profile_merge_test.dart`（并入后两台设备 ctx / legacy 闭包都没有 `sync2:`；对修复前的原生库实测红：3 行）。真实库副本实测见 `real_db_v19_strip_report`（`#[ignore]`，手动）。
- **备注**：真实库副本（2.9 GB，v18→v19）：打开 + 迁移 9.3 s；>500 KB 行 467 条 / 367 MB → 0；ctx 带 `sync2:` 的行 494 → 0；`sync2_legacy` ctx 781 571 B → 167 B；修改记录 `jslim` 合计 953.7 MB → 588.1 MB；26 390 个实体（645 078 条修改记录）全量比对寄存器裁决 0 处不同；增量摘要根 = 全表扫描根；迁移后新写一条 `deck/collapsed` 的 `jslim` 549 B、写入 5.4 ms。腾出约 367 MB 页进空闲链表、由之后的写入复用，不排 VACUUM（整库重写、峰值多占约两倍有效数据）。混用旧版本的设备在升级前仍投影出带合成项的 ctx（旧版本自己的事），摘要换了前缀不会互报「不一致」；对端不会重复拉取（操作与段不变）。
