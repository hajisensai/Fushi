## BUG-5611 · music-scrape-http-cache-bypassed
- **报告**：2026-11-28（架构审计顺带发现）
- **真实性**：✅ 真 bug。`fushi/lib/src/media/music/metadata/music_scrape_service.dart:396`（旧）`_scrapeTrack` 每首都经 `_scraperFactory(sink: …)` 新建一组 provider，`scrapeLibrary` 逐首调 `scrapeTrack`（旧 :517）→ 每组 provider 各自新建 `VideoMetadataHttpClient`（`packages/fushi_engine/lib/media/video/metadata/video_metadata_transport.dart:138`，30 分钟进程内响应缓存），刮完一首就 `close()` 清掉缓存。同专辑每首都重发 Cover Art Archive 封面索引（`music_auxiliary_providers.dart` `fetchReleaseCovers`）与 VGMdb 目录编号查询，白白占 MusicBrainz 1 req/s 闸门。sink 绑在 provider 构造参数上（`onRawResponse`），是不得不每首重建的结构原因。另：`_throttle.run(() => _transport.get(...))` 让缓存命中也在闸门上排队（MB 1.1 s、VGMdb 3 s），缓存即使生效也省不下时间。
- **[x] ① 已修复** — 原始响应 sink 改成跟着调用走：`MusicRawResponseCapture.collect(sink, body)`（zone 值）+ provider 一律 `MusicRawResponseCapture.record`，删掉 provider 的 `onRawResponse` 构造参数；`MusicMetadataScraper.scrape(facts, sink: …)`。`MusicScraperFactory` 去掉 `sink`；`scrapeLibrary` 整次只建一组 provider、刮完关；封面下载也用这组的 `covers`，不再每张另建 CAA 客户端。传输层加 `VideoMetadataRequestGate`（`get/postJson/send(gate:)`），限流闸门只包住真正发出的请求（含每次重试），缓存命中不排队；MusicBrainz / CAA / VGMdb 三处统一改用 `gate: _throttle.run`。闸门本来就是进程内静态共享的，不变。刮削结果与匹配逻辑不变。
- **[x] ② 已加自动化测试** — `fushi/test/media/music/metadata/music_scrape_service_test.dart`「曲库批量：整次共用一组 provider…」：同专辑 3 首、真 CAA / VGMdb provider + 计数 MockClient，断言 provider 组只建 1 次、CAA 索引 / VGMdb 查询 / 封面图各 1 次请求，三首的 coverUrl / vgmdbJson 照常落库、快照照收。`packages/fushi_engine/test/media/music/metadata/music_metadata_test.dart`「缓存命中不过闸门；原始响应跟着调用收」：修前（闸门包住缓存）红。
- **备注**：单首识别（曲目页「识别」）仍每次按当时偏好建一组 provider，缓存只在整库识别里跨曲目生效。
