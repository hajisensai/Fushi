## BUG-4950 · 冲突中心每次重建都按条全表扫「同类」计数（O(n²)），几千条扣住的删除把主线程卡住数秒，iOS 退出被看门狗杀
- **报告**：2026-11-21（用户：应用内反馈 `_o_fq-qjXU`，iOS 3.3.0-debug.28434，iPhone14,8，崩溃 x2）
- **真实性**：✅ 真 bug。iOS 崩溃诊断 `0x8BADF00D「Failed to terminate gracefully after 5.0s」`（WatchdogEvent: process-exit），两次都停在 `SrsConflictsPage`。用 CI artifact `ios-dart-symbols-testflight-28434`（build_id 7d1145004b46ddafc604704dee0b703e）经 `native_stack_traces decode translate` 还原崩溃线程：`_StringBase._interpolate ← _SrsConflictsPageState._heldGroup (srs_conflicts_page.dart:341) ← _sameCount.<closure> (:344) ← WhereIterator.moveNext ← Iterable.length ← _sameCount (:345) ← _buildBody (:714) ← Builder.build ← … ← _MastheadFrameDelegate.performLayout`。即主线程在冲突页 build 里跑 Dart 代码，没回到 UIKit。
  根因 `fushi/lib/src/pages/implementations/srs/srs_conflicts_page.dart:343`（修复前）：`_sameCount` 每次调用都 `where(...).length` 扫整张 `_held` / `_conflicts` 列表并逐条做字符串插值，而 `_buildBody`（:714 / :780）给每张卡片各调一次 → 一次重建 O(n²)。该用户同步后有约 2800 条扣住的删除（反馈内存快照 `core:read:edits 2852x`，每条加载一次标签），一次重建约 800 万次插值 + 比较，在热降频（Thermal serious）的手机上要跑数秒；页面任何重建（布局约束变化、勾选同类、退后台）都会卡住主线程，系统要求退出时主线程 5 秒内交不回去就被看门狗杀。
  与分诊结论不符：分诊把原因归到 `main.dart _flushAndCloseForLifecycleDetach` 的退出链无总预算 / 未取消 SRS 同步。那条链全是 `await`（同步跑在后台 worker isolate 的 FFI 里），等待期间主线程空闲、不阻塞 UIKit 退出；`busy=core:ingest_commit 106.9s` 也来自另一个进程（23:14 那次）的快照。符号化后的栈证明卡住的是冲突页 build，不是退出链。
- **[x] ① 已修复** — 新增 `fushi/lib/src/srs/srs_conflict_groups.dart` 的 `srsSameGroupCounts`，冲突页在 `_load` 的 `setState` 里一趟算好 `_sameCounts`（扣住的删除按 `held/<kind>`、被替换的设置按 `_Conflict.group`），`_sameCount` 只查表（`srs_conflicts_page.dart:353`）。一次重建回到 O(n)。点「同类都按这个选」执行时仍按组过滤一次（每次点击 O(n)，不在 build 里）。
- **[x] ② 已加自动化测试** — `fushi/test/srs/srs_conflict_groups_test.dart`：计数正确、`groupOf` 对 5000 个元素恰好调用 5000 次（线性）；源码守卫 `_sameCount` 只查 `_sameCounts`、载入处两类都用 `srsSameGroupCounts` 算好。原有 `srs_conflicts_held_delete_test.dart` 覆盖页面行为无回归。
- **备注**：未在 iOS 真机复测原始失败路径（需要几千条扣住删除的真实库）。`ExitFlushRegistry` 每个回调已有 2 s 上限；lifecycle detach 退出链本身没有让主线程阻塞的同步步骤，本次不改。
