## BUG-4509 · 主库页损坏（SQLITE_CORRUPT）不进终态，启动错误屏「重试」无限循环
- **报告**：2026-11-12（应用内反馈 qOTTir_a2V，Windows 3.3.0，「异常退出 x11」；附日志 47 条 `SqliteException(11): database disk image is malformed`，Causing statement `PRAGMA journal_mode=WAL`）
- **真实性**：✅ 真 bug。日志里 `AppModel.sandboxRelocation` / `AppModel.initialise` / `AppModel.retryInitialise.close` 反复出现同一个 code 11，栈顶是 `_openWithRecovery.applyPragmas`。根因在 `packages/fushi_core/lib/src/database/database.dart`：`_isSidecarOpenError`（修复前 :234）只认 IOERR(10) / CANTOPEN(14) / NOTADB(26)，不认 CORRUPT(11)。于是 Layer 0 探测连接的 catch（修复前 :321）直接把裸 `SqliteException` rethrow。`FushiDatabaseUnrecoverableException` 没被抛出，app 层（`app_model.dart` 的 `on FushiDatabaseUnrecoverableException` 分支）也就出不了「恢复备份 / 清空数据」专屏。错误落进通用 catch，`_initError` 错误屏的「重试」一遍遍对着同一个坏文件重开。同样的错误如果是后台 isolate 里 drift 自己开库时撞上的（日志第一条就是 `Sqlite3Delegate._initializeDatabase` 路径），会被 `_TypedOpenErrorInterceptor` 原样 rethrow，同样不会进终态。用复现脚本把健康库第 1 页 b-tree 页头（偏移 100 起）写坏、文件头保持合法，`PRAGMA journal_mode=WAL` 稳定报 11。
- **[x] ① 已修复** — `database.dart:256` 新增 `_isMainDbCorruptError`（primary code == 11）。Layer 0（:334）和 Layer 1（:384）遇到它直接抛 `FushiDatabaseUnrecoverableException(kind: corrupt)`，不进恢复阶梯：WAL 帧和 wal-index 都有校验和，开库时报 CORRUPT 说明坏在主库页；checkpoint 会把坏帧折进主库，删侧车会丢掉手工恢复要用的最后写入，所以磁盘上什么都不动。`_TypedOpenErrorInterceptor`（:714）带上主库路径，把后台开库回来的 CORRUPT 也翻译成同一个终态类型。
- **[x] ② 已加自动化测试** — `fushi/test/database/db_corrupt_main_terminal_test.dart`，3 条，用真实文件跑真实开库路径：前提用例确认这种损坏在裸开库上报 11、文件头合法；开库抛 `FushiDatabaseUnrecoverableException`（kind=corrupt，cause 为 code 11）；主库字节不变、侧车不删、不生成 `.corrupt-bak`。
- **备注**：库是怎么坏的从日志里查不出来。同一用户在损坏前有一次主线程卡死（hang dump）被强杀，词典资源大量处于云占位状态（见 BUG-4510）。本修复只保证坏了之后用户能拿到恢复出口，不再无限重试。interceptor 那条路径（探测连接通过、后台连接才撞上坏页）没法确定性复现，没有单独的自动化测试。
