## BUG-1335 · 字幕出现后位置动一下才正常（高分屏，特定句子）

- **报告**：2026-08-01（用户：「这句渲染出来动了一下才正常」「只有特定的话会这样，感觉是字幕位置变动了才会」，附截图，显示器 3840×2160）
- **真实性**：✅ 真 bug（根因经数值推演闭环，尚未真机复现）。根因
  `hibiki/lib/src/media/video/video_subtitle_overlay.dart:1212`（分组判据）与
  `:2434`（渲染 padding）**两处用了不同的量，彼此矛盾**

### 现象

- 不是每一句；也**不是**只有刚打开视频的头一两句 —— 而是「特定的话」。
- 用户直觉：「感觉是字幕位置变动了才会」。
- 用户显示器 4K（截图原图 3840×2160）。

### 根因

底部锚点的 cue 有两处独立判断，本该同源，实际用了不同的量：

**① 分组键**（`_positionKey`，:1212）用**原始 MarginV**（PlayRes 像素）与用户基线比：

```dart
mv = mvRaw <= _layerBaseline(isSecondary) ? -1 : mvRaw.round();
```

**② 渲染 padding**（`_paddingFor`，:2434）用**缩放后 MarginV**（显示像素）取下限：

```dart
final double bottomBase =
    scaledMarginV == null ? userBase : math.max(userBase, scaledMarginV);
```

用户片源（`PlayResY 720`）的样式 MarginV 与 4K 显示（2160/720 = ×3）下的实际 padding：

| 样式 | MarginV | 分组键（原始值判据） | 渲染 padding（缩放值） |
|---|---|---|---|
| `Text_JP`（对白） | 30 | 30 ≤ 75 → **基线桶 mv=-1** | max(75, **90**) = **90** |
| `OP_JP`（OP 歌词） | 10 | 10 ≤ 75 → **基线桶 mv=-1** | max(75, 30) = **75** |
| `Default` | 15 | → 基线桶 | max(75, 45) = 75 |
| `ED_JP` | 10 | → 基线桶 | max(75, 30) = 75 |

于是 `Text_JP` 与 `OP_JP`/`Default`/`ED_JP` **被判进同一组**，但它们的 padding 一个 90、
一个 75。而同组共用一个 `_anchoredPadded`，其 `scaledMarginV` 取自**组代表**
（`cues.first`）—— 当活动集变化导致代表在两种 MarginV 之间切换，padding 就在 75 ↔ 90
之间跳，`AnimatedPadding`（200ms / easeOut）忠实地把这 15px 差值**动画播出来**：
**字幕渲染出来先动一下才停在正常位置**。

这精确解释了用户的两句描述：
- 「只有特定的话会这样」——只有组代表在两种 MarginV 间切换的那些交替处；
- 「感觉是字幕位置变动了才会」——位置确实变了 15px，不是错觉。

**只在高分屏触发**：1080p 时 `Text_JP` 缩放后 30×1.5 = 45 → max(75,45) = 75，与其余样式
**相同**，不跳；4K 才把 90 顶出基线。用户正是 4K。这也是它长期没被发现的原因。

### 为什么不能简单把判据改成缩放值

`:1203` 的注释写明：分组判据刻意用原始值，是为了防 BUG-709 —— 大屏下第二语言对白的
MarginV 缩放后超出基线，会被错判成「独立位置」而脱离基线桶，与仍折在基线的第一语言各自
定位却落在相邻高度，大字号盒相交、重现双语底部塌陷重叠。

所以两处必须同源，但**不能**靠「判据向 padding 看齐」来同源。

### 修复方向（未实施，涉及取舍需先对齐）

矛盾的本质：分组判据已经宣称「这些 cue 折进同一个基线桶、竖排堆叠」，那么桶内就应当
**共用同一个 padding**，而不是各按自己的 `scaledMarginV`、再由「谁当代表」来决定全组位置。
候选修法是让基线桶内的 padding 恒为 `userBase`，使 padding 与分组判据同源、代表切换不再
改变几何。

代价：`Text_JP` 在 4K 下从 90 落回 75，即作者 `MarginV=30` 的抬升被忽略（但当前实现把
MarginV=30 与 MarginV=10 强行同组，本就已偏离 libass 逐条定位的语义）。是否接受这个位置
变化需要与用户确认，故本条**先不动手**。

- **[ ] ① 未修复** — 见上方取舍
- **[ ] ② 未加自动化测试** — 修复时补：同组内不同 MarginV 的 cue，代表切换后 padding 必须
  不变（该断言在当前实现下必红，是本 bug 的最强可落地守卫）

### 备注

与同批的 BUG-1330（`\pos` 不避让控制条）、BUG-1331（`\fn@` 竖排字体）根因均不同，互不影响。
本条最初的根因候选是「首帧视频分辨率未解出 → 字号基准回退容器高」，已被用户「不是只有开头
几句」这一条**否掉**，保留在此以免后人重走：那条路只影响刚打开视频的窗口期。
