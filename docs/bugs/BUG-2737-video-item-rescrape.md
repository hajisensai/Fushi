## BUG-2737 · 视频卡长按菜单没有「重新刮削」入口（刮错的独立电影无法重刮）
- **报告**：2026-09-27（用户：截图《リズと青い鳥》被刮成挪威电影《Få meg på, for faen》的封面，长按菜单里找不到重新刮削）
- **真实性**：✅ 真 bug。视频卡菜单 `_showVideoMenu`（`fushi/lib/src/pages/implementations/home_video_page.dart`）的注释写着「重命名 → 封面/刮削 → …」，但动作列表里从来没有刮削项；单作品重刮只实现在合集菜单（`_rescrapeCollection`，经 `planScrapeWorksForCollection` 按合集定位）。独立电影不在任何合集里，于是刮错后只能整来源重刮——库页上是断头路。计划器本身早就为它产出了 `book:<uid>` 作品单元（BUG-2433），缺的只是「按单个视频定位」的入口。
- **[x] ① 已修复** — 引擎新增 `planScrapeWorkForVideoBook`（`packages/fushi_engine/lib/media/video/metadata/video_library_scrape_sweep.dart`，只问视频自己所属本机来源的同一份计划，命中 `book:<uid>` 或它所在剧集的 `collection:<id>` 单元）；视频卡菜单加「重新刮削资料与封面」（门：有刮削 controller + 本机文件；接替 PR 改为与计划器同口径，见下），手动指定 → `rescrapeWorkWithLookup` 与合集入口抽成共用的 `_rescrapePlannedWork`，不开第二条落库路径；定位不到时给可见提示。（`110de852a1d`，hajisensai）
  - **接替 PR 补修（`4c511be7814`）**：
    - **封面缓存驱逐**：sidecar 图名只按图种派生（`video_sidecar_target_resolver.dart` 封面恒 `poster.<ext>`），换身份重刮是同路径覆盖写，而 `VideoSidecarWriter._atomicWrite` 写完不驱逐宿主解码缓存（`resizedFileImage` 键 = 路径 + 宽度）。现 `VideoSidecarWriter.write` 在覆盖写（目标原本存在）成功后 `await evictImageCacheForFile(targetFile)`（app 侧接 `evictLocalCoverCache` 双键驱逐）。协调器 `_writeLegacyImages` / `updateVideoBookCover` 只改指针不写文件，无需另驱逐。
    - **默认 missingOnly 下旧封面根本不会被换**（审查未提、实测复现）：`imagePolicy` / `nfoPolicy` 默认 `missingOnly`，旧身份写下的 `poster.jpg` / NFO 在重刮时 `skippedExisting`，`coverPath` 仍指向错图。协调器 `_writeSidecars` 新增 `replaceOwnArtifacts`：调用方给了已确认身份（`confirmedLookups` 含该作品——手动指定 / 下载导入）时把 missingOnly 升为 overwrite 且不带危险覆盖授权；第三方文件与用户改过的生成物仍由所有权账本保护（protectedExisting / protectedModified），`skip` 仍是 skip。
    - **入口判据与计划器同口径**：原门借用删除判据 `videoBookHasLocalFiles`，手动导入（无 `sourceId`）/ 互联下载 / 远端来源 / 目录分组模式 / 特典都会画出点了必然「不在计划里」的按钮。抽成纯函数 `videoBookHasScrapePlan`（`video_library_scrape_sweep.dart`，组合计划器的 `videoSourcePlansScrapeWorks` / `videoBookJoinsScrapePlan` + 本机来源门），菜单与 `planScrapeWorkForVideoBook` 共用；来源行随 `_loadLibraryMaps` 同批预取。
    - **文案与形态**：入口改为与合集菜单同形态的列表行（最长标签做成 chip 会压少整格快捷 chip 的列数），复用等值的 `collection_rescrape`，删 `video_item_rescrape`；`video_item_rescrape_not_planned` 补 zh-HK 译文。
    - 定位阶段（读库 + 跑计划器）异常接住记 `ErrorLogService` 并给失败提示，不再是 `unawaited` 下无人处理的错误。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/metadata/video_library_scrape_sweep_test.dart`（`planScrapeWorkForVideoBook` 组：独立电影 / 剧集一集 / 跨来源同名 / 远端与不存在）；`fushi/test/pages/home_video_page_menu_test.dart`（「视频卡重新刮削资料与封面」组：入口出现 / 无 controller 不画 / 流媒体不画 / 定位不到给提示）。
  - 接替 PR（`4c511be7814`）：`fushi/test/media/video/metadata/video_sidecar_writer_test.dart`（「覆盖写后驱逐宿主图片解码缓存」组：覆盖写驱逐 / 新建·字节不变·被保护不驱逐 / app 装配下双键真被清）；`fushi/test/media/video/metadata/video_source_scrape_coordinator_test.dart`（手动改绑身份重刮换掉 Fushi 自己写下的旧 poster 并驱逐、用户改过的 NFO 仍受保护）；`video_library_scrape_sweep_test.dart`（`videoBookHasScrapePlan` 与计划器定位逐例同口径）；`home_video_page_menu_test.dart` 改为真本机来源正例 + 手动导入 / 流媒体 / 目录模式 / sftp / NCOP 五种不画 + 「菜单打开后来源被删」竞态给提示。
- **备注**：入口只修「能重刮」。这部片为什么会被自动刮成同名度很低的挪威电影（自动匹配过宽）是另一个问题，未在本条处理。另：已挂在屏上的卡片原地重建时 Flutter `Image` 只在 provider 不相等才重新解析（同路径 = 同 provider），所以重刮完成那一刻屏上那张卡仍是旧解码，滚出再回 / 切分区 / 重进页面后才显示新图（驱逐保证了届时不再命中旧图）；手选封面等所有同路径换图都同病，属页面级既有限制，未在本条处理。
