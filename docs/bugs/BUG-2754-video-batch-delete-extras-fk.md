## BUG-2754 · 视频批量删除：本地花絮外键冲突删不掉且逐条回收慢
- **报告**：2026-09-28（用户：视频库多选批量删除「删不掉」，且不勾「同时删除本地文件」也很慢）
- **真实性**：✅ 真 bug，三个独立根因：
  1. **删不掉**：`video_metadata_extras.book_uid` 外键 `onDelete: setNull`（`packages/fushi_core/lib/src/database/tables.dart:1941`）与 CHECK `(source_kind='local' AND book_uid IS NOT NULL) OR (source_kind='online' AND remote_url IS NOT NULL)`（`tables.dart:1967`）互斥。`deleteVideoBook`（`packages/fushi_core/lib/src/database/database_video_domain.part.dart`，原 :2650）不先删这些行 → 删被扫描器挂成本地花絮的视频（路径含 `Extras/` 目录段，`fushi/lib/src/media/video/metadata/video_source_metadata_indexer.dart:96-132`）时 FK 置空撞 CHECK，SQLite 报 `CHECK constraint failed`（code 275），整个事务回滚。已用测试复现（去掉修复即红，报错原文如上）。
  2. **半截中断、无提示**：`deleteVideoBooksAndReclaimAssets`（`packages/fushi_engine/lib/media/video/video_book_repository.dart`，原 :803/:845-866）逐条循环无 try，第一条失败直接把异常抛出循环；页面 `_batchDeleteConfirm`（`fushi/lib/src/pages/implementations/home_video_page.dart:1633`）与单删 `_confirmDelete`（`home_video_page.dart:3253`）不 catch → 前面的删了、后面的没删，没有 toast、也不退出多选。
  3. **慢**：「不删文件」分支仍逐条跑 `_reclaimDeletedVideoBookAssetsUnlocked`（原 :984-1028）——每条全表 `listAll` ×2（引用集 + `isDuplicateVideoPath`）、`getAllMediaImages`、`gcOrphanCovers` 遍历封面目录，全选即 O(N²)；每条 2~3 个独立事务（`deleteVideoBook` + `removeEntryFromAllCollections`）；删前还每条一次 `getByBookUid` + `getMediaImagesForBook`；末尾同步整库 `VACUUM`（原 :1033-1042），耗时与删几条无关、与整库大小成正比。
- **[x] ① 已修复** — 提交 `23d2b98e737`：
  - `FushiDatabase.deleteVideoBooks`（新增，`database_video_domain.part.dart`）：**一个事务**里按 400 个一块 `isIn` 删 cue / shelf entry / 标签映射 / **本地花絮行（`source_kind='local' AND book_uid IN …`，先于行本身）** / 规格缓存 / 合集成员（新增批量 `removeEntriesFromAllCollections`，`database_library.part.dart`；`removeEntryFromAllCollections` 委托给它）/ 行本身，返回删前快照。`deleteVideoBook` 委托批量版（不动合集，保持原语义）。在线花絮 `book_uid` 为空，不受影响。未改 schema。
  - `VideoBookRepository.deleteVideoBooks`（新增）：DB 批量删 + 合集 + 同步墓碑；单条 `deleteVideoBook` 委托它。
  - `_deleteVideoBooksAndReclaimAssetsUnlocked`：附加图删前快照改为全表读一次按 bookUid 分组；整批一个事务，**整批失败时退回逐条删**，坏的那条只拖累自己，失败汇总成 `VideoBooksDeleteException(deletedCount, failures)`，在所有尾活（回收 / 删原件 / 压缩）跑完后才抛；墓碑只给真删掉的行记。
  - 回收改 `_reclaimDeletedVideoBooksAssetsUnlocked`：幸存行 `listAll` 一次（与删原件护栏共用）、`getAllMediaImages` 一次、`gcOrphanCovers` 一次、重复路径判定改为幸存归一路径集合查询；每步单独 best-effort。语义不变（仍被引用的资产不删）。
  - `compactAfterVideoDeleteBestEffort`：每次只做 `wal_checkpoint(TRUNCATE)`；空闲页占整库 ≥25%（`shouldVacuumAfterVideoDelete`）才 `VACUUM`。取舍见方法注释：删得少时空闲页留给后续写入复用，真删掉一大块时照旧归还磁盘（BUG-276 的诉求）。
  - UI：`deleteVideoBooksWithDecision` 把 `VideoBooksDeleteException` 折成 `VideoLibraryDeleteResult.failed`（逐条记错误日志）；新增 `reportVideoLibraryDeleteFailures` 弹「N 个视频删除失败，仍保留在媒体库中」（i18n `video_library_delete_rows_failed`），四个视频页删除入口都改用它；批删 / 单删对整体异常 catch → 退出多选、刷新、toast `video_library_delete_failed`。
