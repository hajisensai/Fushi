## BUG-3500 · 在线视频同步片段画面花屏（缓冲副本丢掉 Matroska B 帧视频包）
- **报告**：2026-10-17（用户：Windows 10 / 2.10.0-debug.19402，Jellyfin（Linux）direct play《きみが死ぬまで恋をしたい》S01E01（mkvmerge 封装的 HEVC 10-bit `[Judas] x265 10b` + AAC），「带声音的视频片段」制卡画面花屏、声音正常；附视频诊断日志与学习诊断日志）
- **真实性**：✅ 真 bug，已在本机用同版 libmpv 复现。与 BUG-3499 同一条链路（在线视频制卡先 `dump-cache` 落本地副本），丢的是视频包。
  - 播放本身无异常：诊断日志里 d3d11va 硬解 HEVC p010、dec/vo 丢帧 0、无任何解码错误。
  - 失败全在 dump：同一会话 `dump-cache start=340.223 end=383.100` 之后 `recorder: Source stream misses DTS`、`matroska: Timestamps are unset in a packet for stream 0`，随后 `non monotonically increasing dts to muxer in stream 0: 250 >= 125` 1726 次、`Failed writing packet` 1989 次，命令照样回成功。
  - 根因链：Matroska 只存 PTS，mpv `demux/demux_mkv.c` 交出的视频包 DTS 全空。mpv `common/recorder.c` 的 `add_stream()` 只在 `!sh->codec->lav_codecpar` 时设 `avp->video_delay = 16`（让 libavformat 用重排缓冲猜 DTS），而 demux_mkv 现在给**每条**视频轨都挂 `lav_codecpar`（`demux_mkv.c` `demux_mkv_open_video()`，用来带 Dolby Vision / hvcE side data），于是 `video_delay = 0`，libavformat（`libavformat/mux.c` `compute_muxer_pkt_fields()`）令 DTS = PTS：带 B 帧的流每个重排帧的 DTS 都倒退、被 muxer 拒收。就算 `video_delay` 设上，libavformat 的缓冲也是用首包 PTS 播种的，open GOP 的前导帧（PTS 早于关键帧）照样被拒；这套猜测还是 `FF_API_COMPUTE_PKT_FIELDS2` 兼容代码，libavformat 64 起删除。
  - 复现（mkvmerge 封装的 x265 10-bit open GOP + AAC，15 秒窗）：原库写包失败 525 行，副本 360 帧里只解得出 22 帧（其余 `Could not find ref with POC`）；按 libavformat 算法离线模拟 `video_delay=0` 得 246 个包被拒，与实测吻合。H.264 带 B 帧同理。
- **[x] ① 已修复（根治在 libmpv）** — `third_party/media_kit_libs_windows_video/patches/recorder-video-dts.patch` 改 mpv `common/recorder.c`：视频包缺 DTS 时 recorder 自己推（`guess_dts()`，与 libavformat 同一个 17 格重排缓冲，但种子取本段输出起点 `rebase_ts`——它不大于本段任何 PTS，所以 open GOP 前导帧也单调），每次 `check_restart()` 开始写新的一段都重新播种；已有 DTS 的包（lavf 来源）与非视频轨原样不动。上游 master 截至 2026-10-17 未修。实测：同一样本写包失败 525 → 0，15 秒窗解码帧 22 → 381，整段 30 秒 dump 719/719 帧、时间戳与源文件逐帧一致（整体偏移 +21 ms = AAC 首包起点）。Windows / Android / iOS / macOS 随包 libmpv 全部带上本补丁与 BUG-3499 的补丁重编入库（见 ② 与提交）。
- **[x] ② 已加自动化测试** — 真库验证 `tool/bluray/verify_mkv_lace_dump.py` 新增夹具 `tool/bluray/tests/open-gop-hevc.mkv`（6 秒 HEVC 10-bit open GOP、4 B 帧、AAC，mkvmerge 封装），整段 dump 后要求 0 次写包失败且解码帧 ≥ 缓存时长的 90%（ffmpeg-min 无 wrapped_avframe，帧经 MJPEG、毫秒时间基计数）；已接进 `build_libmpv.ps1` 作为重编必经的门。原库：208 次写包失败、144 帧只解出 40 → 失败；新库：0 次、144/144 → 通过。`fushi/test/build/libmpv_mkv_laced_audio_guard_test.dart` 钉补丁内容、构建脚本顺序、移动端构建流程、Windows provenance 与补丁逐字节一致，并直接在入库的 iOS / macOS 每个 Mpv slice、Android 每个 ABI 的 `libmpv.so` 里找补丁的调试字符串 `Deriving missing DTS`；Android / Darwin 构建分支的产物校验同样 grep 这一串；`tool/bluray/platforms/test_verify_darwin_archive.py` 新增缺补丁被拒的用例。
- **备注**：应用层没有加视频内容校验（BUG-3499 的音频校验只解这句的音频窗）——四个平台随包 libmpv 同一提交换库，校验视频要把 1080p HEVC 解一遍，移动端代价不划算。Android 的 libmpv 改由 `hajisensai/libmpv-android-build-fushi`（私有，非 fork）跑 CI：`hajisensai/libmpv-android-video-build` 这个 fork 的 Actions 被 GitHub 停用，仓库设置显示已启用但任何触发都回 `HTTP 422: Actions has been disabled for this repository`。
