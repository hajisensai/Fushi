## BUG-5521 · Windows：上次最大化关掉，下次启动先显示几秒青绿色空窗
- **报告**：2026-11-26（用户：桌面端打开 Fushi 先是几秒绿屏）
- **真实性**：✅ 真 bug。普通启动主窗隐藏建窗、等 Dart 首帧光栅化后才显窗（`fushi/lib/main.dart` `_releaseStartupFrame`）。但上次最大化关掉时，启动定位 `fushi/lib/src/startup/desktop_window_placement.dart:108` 调 `windowManager.maximize()`，window_manager 0.5.1 在 Windows 上 `PostMessage(WM_SYSCOMMAND, SC_MAXIMIZE)`，最大化一个隐藏窗口必然连带显示它。此时 Flutter 还在初始化、首帧被 `deferFirstFrame` 压着，用户看到的是 runner 原生兜底底色 `kInitialBackdropColor = RGB(0x1F,0x49,0x59)`（`fushi/windows/runner/win32_window.cpp:107`，青绿），直到首页就绪才有内容。报告机器的已安装版偏好里 `desktop_main_window_maximized` 为 true，与症状吻合；非最大化启动不受影响。
- **[x] ① 修复** — runner 普通启动（隐藏建窗）的主窗建好就挂 DWM 隐身（`DWMWA_CLOAK`，`win32_window.cpp` `CreateAndShow`）——SC_MAXIMIZE 显窗这条路径实测不发 `WM_SHOWWINDOW`，只能在任何显示发生之前就隐身：窗口照常最大化、照常合成，首帧直接按最大化后的最终尺寸光栅化，只是不呈现给用户。Dart 首帧上屏后的显窗点调 `WindowCaptionChannel.showStartupWindow()`（Windows 新增，原只 macOS），runner 一次往返做完撤隐身 + `ShowWindow(SW_SHOW)` + 前置；通道失败才退回 `windowManager.show()`（先撤隐身再走 window_manager 的两次往返实测让显示晚了 3 s：第二次往返排在首帧后平台线程的忙碌之后）。看门狗改按「可见且未隐身」判主窗是否显示过，强制显窗改投注册消息 `ForceStartupRevealMessage()`（同一个撤隐身 + 显示），隐身没撤掉也会在期限后被找回。判据纯函数在 `startup_reveal_policy.h` §3。
- **[x] ② 自动化测试** — `fushi/windows/runner/tests/startup_reveal_policy_test.cpp`（`ShouldCloakAtCreation` / `IsWindowUserVisible` / 注册消息，随每次 Windows runner 构建执行）；`fushi/test/windows/runner_cold_start_black_window_guard_test.dart` 的 BUG-5521 组（runner 隐身 / 撤隐身 / 看门狗 / Dart 显窗顺序与失败不拦 show 的源码守卫）。
- **备注**：没选「把 maximize 挪到显窗时再做」：那样首帧按还原尺寸画，显窗瞬间再改尺寸，子窗 resize 闸门（BUG-2462）在首帧尺寸确认回来前会把新尺寸挂起，最长约 1 s 露出底色。
- **复测**（2026-11-26，Windows 11 debug 构建，dev 沙盒、真实数据种子，`desktop_main_window_maximized=true`，主屏 2560×1440 每约 50 ms 采样一次）：未生效的版本里主窗 2.3–3.5 s 起最大化可见，之后 5～6 s 内 88–94 帧整屏 77–97% 是 #1F4959；修复后最大化启动 0 帧青绿（0.6 s 起隐身，2.3 s 已最大化但隐身，8.0 s 首帧后显示），非最大化启动 0 帧青绿、撤隐身与显示落在同一采样点。macOS / Linux 未改动。
