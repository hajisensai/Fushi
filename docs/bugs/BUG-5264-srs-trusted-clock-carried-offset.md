## BUG-5264 · SRS 可信时钟把「可信时间 − 墙钟」偏移带到下一个进程，改过系统时间后「今天」一直多 1 天
- **报告**：2026-11-23（应用内反馈 P9zrTFV5MW：一个 profile 的 SRS「今天」比系统日期多 1 天，怎么改系统日期都甩不掉，新建的 profile 正常；用户关了同步）
- **真实性**：✅ 真 bug。`SrsTrustedClock.anchorState`（`packages/fushi_srs/lib/src/hlc.dart` 旧版 153-176）在已校时时每次现算 `offsetMs = 可信时间 − 墙钟`，`SrsDbStore._anchorArg`（`packages/fushi_engine/lib/srs/srs_db_store.dart` 旧版 1144）随每条改投影的命令写进这个 profile 的本机状态行；下一个进程在 `_loadLocal`（旧版 1086-1096）里 `restoreAnchor` 因进程身份（每进程随机的 bootId）不同，只接上这份偏移，`now() = 墙钟 + 偏移`（旧版 hlc.dart:181），直到下一次同步校时。关了同步就不再校时，偏移永久留着。用户在校时状态下把系统时间往回拨 1 天，偏移就记成 +1 天，之后每个进程的「今天」都 = 系统日期 + 1；新 profile 没有本机状态行所以正常。阅读统计走墙钟，不受影响。最初那次（系统时间 11-21 23:35 时 SRS 已显示 22 日）需要至少 4.5 小时偏移，当时系统时钟本身是否不准没有证据（自动校时是关的），未证实。
- **[x] ① 已修复** — 不再跨进程携带偏移。持久化的校时状态改为 `{s, t, e}`：校时那一刻的服务器时间、同一刻的开机时钟读数、校时时按墙钟估的开机时刻（墙钟 − 开机时钟）。新进程只在**同一次开机**里接上（开机时钟没有倒退，且此刻的「墙钟 − 开机时钟」与 e 相差不超过 `srsBootEpochToleranceMs` = 10 分钟），接上后按开机时钟精确推算、不经过墙钟；换了一次开机（开机时钟归零，或归零后又走过了读数但开机时刻变了）或校时后改过系统时间，就不接、按墙钟走，直到下一次真校时；认不下的状态也不抹掉本进程自己的校时。去掉了每进程随机的 bootId。内核 `anchor_of`（`native/fushi_fsrs/src/store/local_state.rs`）改为只收 `{s, t, e}`；库里旧版的 `{o, b, s?, t?}` 没有 e，Dart 读到不认 → 用户升级后这个 profile 卡住的 +1 天偏移自动失效，不需要另给清除入口。
- **[x] ② 已加自动化测试** — `packages/fushi_engine/test/srs/sync2/srs_trusted_clock_anchor_test.dart`：单元层复现反馈路径（校时 → 拨回 1 天 → 换进程 → 再改日期 → 改回来），重新开机（读数倒退 / 归零后又超过读数）、NTP 微调仍认同一次开机、认不下不抹掉本进程校时；`SrsDbStore` 端到端经本机状态行跨「进程」验证 `dayContext` 算出的「今天」= 系统日期而不是 +1 天、改回后精确接上、重启后按墙钟走。Rust `local_state.rs` 的 anchor 测试钉住新形态与拒收旧形态。
- **备注**：同一反馈的问题 2（`.apkg` 导入到同库另一 profile 时 9738 条被跳过，`srs_apkg_import.dart` 实体归属闸，BUG-5005 的设计）是设计限制，不在本条修，交拍板台。已断的连续天数不自动补。跨开机不防人为调时间：下一次校时前按墙钟走（SRS gen4 授权范围内自定，底线是用户不出问题）。
