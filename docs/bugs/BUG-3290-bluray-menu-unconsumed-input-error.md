## BUG-3290 · 原盘菜单方向键 / 点击没被原盘接收时报「未能执行菜单操作」
- **报告**：2026-10-10 / 2026-10-11（应用内反馈 #qynJy0Dzz9「蓝光菜单左右键报错」、#st-N1qypUF「开着一个主选项时切换另一个主选项会显示未能执行操作」；两份日志都是 `VideoDiscMenu.navigate` / `VideoDiscMenu.pointer` 抛 `Blu-ray menu: command-failed:-12`）
- **真实性**：✅ 真 bug（契约错误）。-12 是 libmpv 的 `MPV_ERROR_COMMAND`（命令执行失败的通用码）。本仓的 `third_party/media_kit_libs_windows_video/patches/disc-navigation-state.patch` 让 `stream_bluray.c` 在 `bd_user_input` / `bd_mouse_select` 返回负数时回 `STREAM_ERROR`，`cmd_discnav` 于是失败。但 libbluray 1.5.0 对这两个接口的负返回值表示「原盘没接收这次输入」而不是出错：`graphics_controller.c` `_user_input` 在弹出式菜单未打开 / IG 未打开时回 -1，`_mouse_move` 在按钮动画进行中回 -1、点到当前页没有可选按钮的位置时 `BD_VK_MOUSE_ACTIVATE` 回 -1（展开某个页签的子菜单后，其它页签按钮不在可选集合里，正是反馈里「切换另一个主选项」的情形）；BD-J 由 `bdj_process_event` 返回 Xlet 的 `processEvent` 是否消费了按键。实体播放器在这些情况下什么也不做。Dart 侧 `fushi/lib/src/media/video/video_disc_menu.dart` `runCheckedVideoDiscCommand`（修复前 `:274`）把它当异常，`disc_menu.part.dart` 的 `_runDiscNavigation` / `_clickDiscMenu` 再弹红色错误提示。
- **[x] ① 已修复** — `video_disc_menu.dart` 新增 `isVideoDiscInputCommand` / `runVideoDiscInputCommand`：方向键、确认、弹出菜单、上一级、点击这些遥控输入返回「是否被接收」（bool），未接收是正常结果、只记 debug 日志；只有 `menu` / `title-menu`（`bd_menu_call`，会被原盘的 UO 掩码真正拒绝）仍走 `runCheckedVideoDiscCommand` 报错。`video_disc_menu.part.dart` `_sendDiscCommand` 按命令类别分派。没改 native 补丁：补丁的 sha 被 Windows / Android / Darwin 三端的产物来源测试钉死，改它要三端重编并用真盘跑 `verify_menu_render.py`，超出本批；Dart 侧的分类在 native 修正后依然成立（届时这些输入不再返回负数），不需要清理。提交 cf5202a556。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/video_disc_menu_test.dart`：所有遥控输入在 -12 下返回 false 不抛、0 下返回 true，点击命令参数原样下发；`menu` / `title-menu` 不算输入、被拒仍抛 `VideoDiscMenuException`。`fushi/test/pages/video_disc_menu_and_stream_align_wiring_guard_test.dart` 钉住 `_sendDiscCommand` 的分派接线。
- **备注**：同一反馈里的「原盘菜单没法全屏」：菜单模式下的顶栏替换了整套常规控制条，只有返回 / 主菜单 / 弹出菜单，没有全屏键（F11 / F 快捷键本来就放行）。同一提交在 `_buildDiscMenuChrome` 加了与常规控制条同一执行体的全屏键（移动端不出现，与 BUG-221 一致），守卫同上。点击到当前不可选的页签本身仍然不会切换——那是原盘的编排（遥控器要先用方向键离开子菜单），客户端拿不到 IG 按钮表，无法替原盘改判；现在至少不再报错，可以用方向键切换。未在真盘上复测。
