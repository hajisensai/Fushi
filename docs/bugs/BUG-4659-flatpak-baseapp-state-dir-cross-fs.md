## BUG-4659 · CI flatpak-baseapp 未命中缓存时 flatpak-builder 报 state dir 与 target dir 不在同一文件系统
- **报告**：2026-11-15（PR #3400 审查意见：flatpak-baseapp 既有红单独跟踪）
- **真实性**：✅ 真 bug，develop 上同样红（release-desktop run 43691807435 job 132744033893、run 43654446353；PR #3400 的 run 43667097783 job 132668797602 同一报错）。日志：`The state dir (/src/build/flatpak-state) is not on the same filesystem as the target dir (/tmp/tmp.nqAteunycO)`。根因：`tool/linux/flatpak/flatpak_build.sh:64`（`cmd_baseapp`）与 `:82`（`cmd_app`）用裸 `mktemp -d` 把工作目录建在容器的 `/tmp`（overlay 根），`--force-clean "$work/build"` 的父目录就是它；而 `release-desktop.yml` 的 flatpak-baseapp / linux job 传的 `FLATPAK_STATE_DIR=/src/build/flatpak-state` 在 bind mount 的 `/src` 上（本机 `build_flatpak.sh` 的 `/work/state` 在 docker volume 上，同样跨 fs）。flatpak-builder 启动时比较 state dir 与 app dir 父目录的 `st_dev`，不同就直接退出（它要在两者间硬链接）。BaseApp 平时走 native artifact store 缓存命中、不进这一步，所以只在缓存键变化后暴露。后果：flatpak-baseapp 红 → `linux` job（`needs: flatpak-baseapp`）被跳过，CI 拿不到 Linux x64 release 构建证据。
- **[x] ① 已修复** — `flatpak_build.sh` 新增 `make_workdir`：`mktemp -d -p "$(dirname "$STATE_DIR")"`，工作目录与 state dir 同一文件系统（CI 落在 `/src/build/flatpak-work.*`），`cmd_baseapp` / `cmd_app` 都改用它，退出时 trap 清理。
- **[x] ② 已加自动化测试** — `fushi/test/build/flatpak_build_workdir_same_fs_guard_test.dart`（源码守卫：工作目录必须建在 `STATE_DIR` 旁、禁止裸 `mktemp -d`、每个 `--force-clean "$work/build"` 都取自 `make_workdir`）。
- **备注**：真实验证靠 CI（本机无 Linux/Docker）：PR 上 workflow_dispatch release-desktop（build_only）跑 flatpak-baseapp。
