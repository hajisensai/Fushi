## BUG-3797 · 带标签的已删笔记一直挂在「等你决定的笔记」里，确认删除也消不掉
- **报告**：2026-10-26（用户：手机，复习同步 v2，冲突中心「等你决定的笔记」里一条「鋾 — 一台设备删除了这条笔记，另一台设备同时修改了它。」点进去「确认删除」后回到列表依然显示）
- **真实性**：✅ 真 bug，但不在委托线索指向的 `sync2Conflicts` / `sync2_resolve` 路径上。「等你决定的笔记」读的是笔记缓存 `srs_notes_cache.pending_decision`（`srs_conflicts_page.dart` `_pending` ← `SrsDbStore.notesPendingDecision`），值来自寄存器内核 `pending_decision = deleted_at.is_some() && !concurrent_with_delete().is_empty()`（`native/fushi_fsrs/src/registers.rs` `Entity::concurrent_with_delete` / `pending_decision`）。同步 v2 把标签做成 OR-Set，每条笔记投影成**一行合成的 `tags` 修改记录**（`native/fushi_fsrs/src/store/sync2/semantics.rs` `refresh_tags_row`：写入者 `sync2:tags:<笔记>`、`s` 恒 1、`ctx` 空）。合成行没有因果 dot：任何删除的 ctx 都不含它、它的 ctx 也不含删除，内核判「谁也没看见谁」= 并发 → 只要笔记有过标签操作，删掉就被标成待裁决；「确认删除」只是再写一条删除，新删除照样「看不见」合成行，所以永远消不掉（「恢复」能消，因为 `deleted_at` 变空）。Rust 单测复现：单设备建带标签笔记后删除，物化出 `"pd":true,"x":[1]`（下标 1 就是合成 `tags` 行）。冲突中心的 `sync2_resolve`（删除 / 保留）本身没有问题：既有用例与新增「删除 ⟂ 改标签」两个方向都能清掉 `sync2_conflicts`。
- **[x] ① 已修复** — 内核 `concurrent_with_delete` 跳过写入者带 `SYNTHETIC_WRITER_PREFIX`（`sync2:`）的合成行；`tags_writer` 改用同一常量拼名。合成行与删除的并发由同步 v2 的扣住机制按底层 `#tag` 操作判定（`evaluate_holds`：真并发就扣住删除进冲突中心，删除不落投影），内核不再拿没有 dot 的行判。存量设备的错标在缓存里：笔记缓存修订号 4 → 5，`_upgradeCaches` 把标着 `pending_decision` 的笔记重算一遍（`packages/fushi_engine/lib/srs/srs_db_store.dart`）。
- **[x] ② 已加自动化测试** — Rust `native/fushi_fsrs/src/store/sync2/tests.rs`：`deleting_a_tagged_note_is_not_a_pending_decision`（删带标签笔记不待裁决、再删一次、两端同步后仍不待裁决且冲突为空）、`delete_concurrent_with_tag_change_resolves_either_way`（删除 ⟂ 改标签进冲突中心，选删除 / 保留两路都：冲突清空、`pd` 假、重复投递全部段不重新冒出、保留时标签是加胜结果）；Dart `packages/fushi_engine/test/srs/srs_pending_decision_test.dart`（真实 SrsDbStore → Rust 投影 → 笔记缓存：`notesPendingDecision` / `hasPendingDecision`；老库修订号 4 错标的待裁决打开时被重算掉）。`srs_media_refs_test` / `srs_stat_projection_test` 钉的修订号同步改成 5。
- **备注**：顺带发现（未改）：修订号 4 的注释写「老库已删笔记的 media_refs 升级时重算一遍」，但 `_upgradeCaches` 里没有 `< 4` 的步骤，只有修订号 < 3 的库会经 `< 3` 全量重算笔记缓存；3 → 4 的库已删笔记 media_refs 仍是空串。真机未复测。
