## BUG-2419 · Windows PDF 导入永久卡在「导入 EPUB…」：pdfium.dll 从未进入安装包
- **报告**：2026-09-10（用户转述他人反馈：Windows 版 PDF 导不进去，进度条下方一直停留在「导入 EPUB」；同一份 PDF 在 Android 版正常）
- **真实性**：✅ 真 bug。根因在打包侧，不在导入逻辑：`fushi/windows/CMakeLists.txt:96-100` 之后**缺少官方 Windows 模板自带的 native assets install 规则**，`pdfium.dll` 只落在 `build/native_assets/windows/` 而从未进入 bundle。
  - **为什么是「永久挂死」而不是报错**：`pdfium_dart` 裸名 `DynamicLibrary.open('pdfium.dll')` 失败时 **throw**（`pdfium_dart-0.2.5/lib/src/pdfium_loader.dart:66-72`），而 pdfrx 的 worker isolate 执行原语是 `execute() => sendPort.send(callback(message))`，**没有 try/catch**（`pdfrx_engine-0.4.4/lib/src/native/worker.dart:164`）。`callback` 同步抛出 → `sendPort.send` 整句不执行 → 主 isolate 的 `await receivePort.first`（同文件 `:98`）永不完成。于是 `import_flow_mixin.dart:64-93` 的 catch/日志/错误 toast/finally **一条都不触发**，进度条永远停在 `book_import_dialog.dart:1098` 那次 `reportProgress(0.5, ...)`。worker 死后 `_sendPort` 仍非 null，此后每次 PDF 操作都照样挂死，直到重启 app。
  - **为什么开发机复现不出来**：`pdf_engine.dart:45-46` 的第二个候选路径是 `${Directory.current}/build/native_assets/windows/pdfium.dll`。从 `fushi/` 跑 `flutter run` 时 cwd 正好命中本机那份 7.1 MB 的 DLL——这条「保险」把打包缺口伪装成了「已经修好了」。用户安装后 cwd 是安装目录，两个候选全部落空。
  - **为什么 CI 全绿**：Flutter 本该自动补这两句的 `cmake_native_assets_migration.dart` 用 `replaceFirst('endforeach(bundled_library)\n', ...)` 定位插入点，而 Windows 模板用的是 `if(PLUGIN_BUNDLED_LIBRARIES) install(FILES ...)`，没有那个 foreach → 匹配不到 → **静默 return**，不写文件不打日志。且 `sqlite3.dll` 同时由 `sqlite3_flutter_libs` 走 `PLUGIN_BUNDLED_LIBRARIES` 进 bundle，掩盖了 native-assets 这条通道从来没通过。对照组：`fushi/linux/CMakeLists.txt:122-123` **有**这两句。
  - **Android 为何正常**：Flutter 的 Gradle 插件自动把 native assets 搬进 jniLibs（`FlutterPlugin.kt:731-737`），`libpdfium.so` 随 APK 走 linker 解析。iOS/macOS 由 XCFramework 静态链接。**只有 Windows 的搬运写在项目自己的 CMakeLists 里，一定制就丢。**
  - **实测证据**：`flutter build windows --debug` 成功（exit 0）后 bundle 目录 35 个 DLL 中无 `pdfium.dll`；`build/windows/x64/cmake_install.cmake` 的 52 条 install 规则里 `native_assets` 零命中；而 bundle 内 `NativeAssetsManifest.json` 却声称 `pdfium.dll` 就在 exe 旁边——清单与产物脱节。
  - **爆炸半径远不止导入**：同一缺失让 Windows 上**所有** PDF 路径挂死——PDF 阅读器页渲染、`manga_pdf_importer.dart` 的 PDF→漫画转化，以及文件夹扫描导入（`kScanBookExtensions` 含 `pdf`，扫到第一个 PDF 就整批卡住）。
- **[x] ① 已修复** — 两处，缺一不可：
  - `fushi/windows/CMakeLists.txt`：补上官方模板的 `set(NATIVE_ASSETS_DIR "${PROJECT_BUILD_DIR}native_assets/windows/")` + `install(DIRECTORY ...)`（与 `linux/` 那份同形），并新增 `install(CODE ...)` 守卫——Profile/Release 配置下 bundle 缺 `pdfium.dll` 即 `FATAL_ERROR`，理由与同文件里 fushi_torrent 那条一字不差：**禁止产出一个「声称支持 PDF、一导入就永久转圈」的安装包**。
  - `fushi/lib/src/pdf/pdf_engine.dart`：新增 `_assertPdfiumLoadable()`，在 `pdfrxFlutterInitialize()` **之前**于主 isolate 先 `DynamicLibrary.open` 一次，失败抛 `PdfiumUnavailableException`（消息写清搜过哪里）。修不了 pdfrx 的 worker 缺陷，就把那个不可诊断的黑洞挡在门外——异常从主 isolate 正常冒泡，变成一条带原因的错误 toast，而不是无声挂死。
  - 顺带：`book_import_dialog.dart` 的 PDF 分支与 `manga_import_dialog.dart` 改用中性的 `import_step_importing_book`（见 BUG-2420），错误文案会把排查引向错误方向。
- **[x] ② 已加自动化测试** — `fushi/test/build/windows_native_assets_bundled_guard_test.dart`（4 条）：① windows CMakeLists 必须有把 native_assets 目录装进 bundle 的 install(DIRECTORY) 规则；② Profile/Release 缺 pdfium.dll 必须 FATAL_ERROR；③ linux 侧同款规则仍在（防止只保留一个平台）；④ `_assertPdfiumLoadable` 必须排在 `pdfrxFlutterInitialize` 之前。刻意钉不变式而非写法（变量名/换行/注释怎么改都不误红），并 `stripComments` 后再匹配——本次修复自己就写了大段提到 `native_assets` / `pdfium.dll` 的注释，拿散文当接线会让守卫在规则被删时照样绿。
  - **变异实测**：删掉 `install(DIRECTORY)` 那两句（注释全留）→ 精确红在第 ① 条、其余三条仍绿；还原后 4 条全绿。
- **备注**：`flutter analyze` 与 Dart 单测在结构上都看不到 bundle 里有哪些文件，验证构建 `build-multiplatform.yml` 跑的又是 `--debug`（不经 install 路径）——这与 BUG-1588/BUG-1589 是同一种病：**把验证构建的绿当成发布构建的绿**。真正的判绿标准只有一条：构建后 bundle 目录里有没有 `pdfium.dll`。
