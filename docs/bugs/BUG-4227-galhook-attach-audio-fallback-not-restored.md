## BUG-4227 · 附着已运行游戏时不读回该游戏上次的「音频降级」选择
- **报告**：2026-11-07（用户：应用内反馈 1cC6PRxZSA，Windows 3.3.0-debug.24478，「记住音频降级喜好：希望可以记住上一次在这里选了什么」）
- **真实性**：✅ 真 bug。降级策略早已按游戏持久化（`setAudioFallbackPolicy` → `_persistAudioFallbackPolicy`，记忆 key = `currentCaptureExecutable` 小写，附着时由 PID 反查 exe），但**读回**只挂在启动路径上：`fushi/lib/src/mining/gal_hook_session_controller.dart:1783`（修前，`launchGame` 里 `_beginActivitySession` 之后的 `_restoreAudioFallbackPolicy()`）。附着已运行游戏的 `startAttachedCapture`（修前 :1568-1617）在 :1601-1602 建了活动会话并写入 `_attachedCaptureExecutable`，却没有恢复这一步，于是附着会话的策略停在上一会话残留值 / 默认 `full`，用户每次附着都要重选；而在附着会话里改选又会写进该游戏的记忆，表现为「记了但读不回」。根因是「会话游戏身份确立 → 恢复按游戏记忆」这条契约散落在各启动路径里各写一遍，附着路径漏写。
- **[x] ① 已修复** — 新增唯一入口 `_beginGameSession(identity, attachedExecutable:)`（`gal_hook_session_controller.dart:1634`）：开活动会话（复位上一游戏的捕获记忆会话）→ 写入本会话捕获 exe 身份 → `_restoreAudioFallbackPolicy()`。`launchGame`（:1801）与 `startAttachedCapture`（:1601）都只调它，不再各自拼这三步。仍按每游戏记忆，不引入跨游戏全局默认；接手进程（`_followGameProcessHandoff`）是同一游戏、记忆会话不复位，不需要重恢复。
- **[x] ② 已加自动化测试** — `fushi/test/mining/gal_hook_session_controller_test.dart`「BUG-4227: audio fallback policy is restored when attaching to a running game, sharing the per-game memory with launch」：附着 A 选 cleanOnly → 新控制器再附着 A 必须读回 cleanOnly；改附着 B 回到 full（不串游戏）；再 launch A 的 exe 读回附着时的选择（两路径共用一份记忆）。去掉修复时该用例红。
- **备注**：附着时 PID 反查不到 exe（无游戏身份）就没有记忆可读，策略保持当前值，行为与修前一致（`_ensureCaptureMemoryLoaded` 返回 false）。顺带修正了同文件既有用例「text process pipeline is remembered per game」里被 BEL 控制字符（0x07）污染的路径字面量（`D:<BEL>nemoi` → `D:\anemoi`），不影响该用例语义。
