## BUG-4011 · 复习同步里同一份旧库被两台设备各包一遍，操作日志与修改记录成双
- **报告**：2026-11-03（用户：宿主与设备 01a173ca 的复习数据在同步里各有一份：`srs_field_edits` 645446 行只覆盖 336900 个寄存器，日志 254920 条、身份记录 15175 条逐字节重复）
- **真实性**：✅ 真 bug。两条根因：
  1. 迁移整库判（`native/fushi_fsrs/src/store/sync2/mod.rs` `sync2_migrate`，旧 `has_ops`）：本库里有别的设备的操作就整个不迁（本机独有的旧行永远进不了操作日志），没有就整个包一遍（两台设备迁同一份旧库 = 两条重复的操作流）；
  2. 档案合并（`packages/fushi_engine/lib/srs/srs_profile_merge.dart` `_Writers`）把每个旧写入者一律改名成 `merged-uuidV5(...)`：目标 uid 下已经有同一批修改记录（写入者名字不同、seq 与 HLC 逐条相同）时，dot 变了 → 修改记录 ID 变了，`_applyMissing` 认不出已在，31 万条修改记录在目标里成了两份（现场 `merged-f18df189…` 与 `2RIr94…#1`：314088 条同 seq 同 HLC，0 条冲突）。
- **[x] ① 已修复** — 迁移逐条判「已被任何设备的操作代表」（`mod.rs:1256` `enqueue_legacy_rows`：修改记录看 `sync2_edit_ops`、日志看 `sync2_log_meta`、身份记录 / 不认识的事件扫操作日志），一条都不缺就只补标记（`mod.rs:1632`）；`SrsDbStore.open` 加 `beforeMigrate`（迁移前在同一独占区先收一轮）；档案合并沿用目标里已有的同一身份（`srs_profile_merge.dart` `_Writers.alias`：至少一条同 seq 同 HLC、零条同 seq 不同 HLC、旧写入者最大 seq 不超过目标的，才沿用；否则照常改名）（分支 `pr/srs-sync2-migrate-dedup`）
- **[x] ② 已加自动化测试** — `native/fushi_fsrs/src/store/sync2/tests_migrate_dedup.rs`（两台设备同一份旧库、第二台先收后迁只包独有的 3 条，修复前 `ops` 为 0 = 独有旧行丢失；全部被覆盖时一条不包）；`packages/fushi_engine/test/srs/sync2/srs_sync2_migrate_dedup_test.dart`（两个真实 SrsDbStore + 内存位置：B 经 `beforeMigrate` 先收再迁，只多一条日志操作）；`packages/fushi_engine/test/srs/srs_profile_merge_test.dart`（目标已有同一批修改记录：沿用目标的写入者、只落一份；同 seq 不同 HLC 的照常改名）
- **接入（第二个提交）**：① 打开 store 迁移前先有界只拉不发（`packages/fushi_engine/lib/srs/sync2/srs_sync2_pull_first.dart`：只读握手、闸门到点关上后迟到的网络结果碰不到本机库）；调度器 `fushi/lib/src/srs/srs_sync_scheduler.dart` `pullInto` 遍历云盘 / 互联通道、本机目录、文件夹位置；`srs_providers.dart` `SrsBeforeMigrateHook` 挂到 `SrsDbStore.open` 的 `beforeMigrate`，由 `srs_app_runtime.dart` 装上，预算 10 秒（`kSrsPullBeforeMigrateBudget`），失败记日志照常迁移。② 档案合并前先收目标 uid（`srsMergeProfileUid` 的 `pullTarget`，`SrsDbProfileLinker.pullBeforeMerge`，预算 2 分钟）。③ 合并判「目标里已有」改读操作日志（内核 `legacy_dots`，`native/fushi_fsrs/src/store/sync2/mod.rs` `sync2_legacy_dots`），被支配的同 seq 记录也看得见。测试：`fushi/test/srs/srs_pull_before_migrate_test.dart`、`srs_profile_merge_test.dart`「切 uid 并入前先收目标数据」、`tests_migrate_dedup.rs` `legacy_dots_…`。
- **推迟迁移（第三个提交，用户拍板）**：首次同步确认弹框没回答前**不迁移、也不拉**（「稍后」同样不做）；回答「开始同步」后的第一轮、任何上传之前才先收再迁移。app 打开 store 改为 `deferMigration: true`（`srs_providers.dart`，去掉了 `SrsBeforeMigrateHook`）；`SrsDbStore.migrateLegacy`（拉取在独占区外、迁移在独占区内）；调度器 `SrsSyncScheduler.ensureMigrated` 挂在 `_syncAll` 开头（锁外，收全部位置）、`_syncWithBackend`（一轮里只从这条通道收）与文件夹轮次前，预算改为 2 分钟。顺带修了第二个提交的重入死锁：`pullInto` 在一轮里（拿着不可重入的通道锁 / 在 `_serially` 里）不再经 `_channels` 取通道；冲突弹窗选定候选的并入（`adoptProfile`）改在候选所在那条通道的锁里做并把通道传给 `SrsProfileLinker.adopt(within:)`。测试：`fushi/test/srs/srs_pull_before_migrate_test.dart`（未回答不迁不拉、确认后第一轮开跑前已迁移且只包独有的；锁里一轮不重入；位置卡住按预算迁移；并入拿得到那条通道）。
- **备注**：没确认前本机写入照常是操作，迁移时按「已有操作代表」跳过；没迁移期间改了旧笔记的标签，旧整列表标签行被本机 OR-Set 行替换掉、不再被包装——别的设备若各自迁出过同一行，那里的旧标签添加不会被这次删除观察到（与并发添加同语义）。已有的重复数据（现场两条流）本修复不清理（存量修复另做）。现场 `merged-f18df189` 不是由 `2RIr94…#1` 改名而来（按 `profile-merge/<uid>/writer/<W>` 算出来是 `fc797b33…`），宿主旧写入者是另一个名字。拉取有界：到点没拉完的部分仍会被包 / 改名。
