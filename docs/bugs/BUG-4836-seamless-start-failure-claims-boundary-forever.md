## BUG-4836 · 无缝衔接启动失败后三条边界换章通道被永久认领，这一章里翻不到下一章
- **报告**：2026-11-17（用户：小说阅读器优化清单复核 gap-readerjs2-3，代码审读发现，无用户报告）
- **真实性**：✅ 真 bug（真 Chrome 里用生产安装脚本复现；未在真机复现）。根因：
  - `fushi/lib/src/reader/reader_seamless_chapters_script.dart:446`（修前行号）`S.start` 置 `S._starting = true` 之后有 `await fetch(entry.url)`、`await resp.text()`、`await epubStylesOf(...)`，整段没有 try / finally，只有「找不到条目」「`!resp.ok`」两个分支复位。请求本身 reject（不是 404）、`DOMParser` / `absolutizeCssUrls` 抛异常时 `_starting` 留在 true、`started` 留在 false，还多一条未处理的 rejection。
  - `:685`（修前行号）`S.claimBoundaryTurn` 首行 `if (!S.started) return S._starting === true;` 从此恒真。连续 shell 的三条「拉过边界换章」通道（按键 `paginate` 末行、触摸边界拉动、滚轮试滚）都先问它，true = 本模块已处置、调用方不得换章，于是用户在这一章里只能走目录离开。同文件注释把「启动失败」列在「返回 false、退回整章重载」一类里，行为与写明的意图相反。
  - 同一个根的第二处：`:258`（修前行号）`epubStylesOf` 逐张 `await fetch(href)`，没有任何隔离。`absUrl` 对 http(s) 外链样式表也生成绝对地址去 `fetch`，跨域没有 CORS 头就 reject——一张样式表失败让整次启动失败（走上面那条），或让整次邻章挂载失败（`mountFailures` 记账后该方向永久退回整章重载）。
- **[x] ① 已修复**（`95100a03887`）— `fushi/lib/src/reader/reader_seamless_chapters_script.dart`：`S.start`（`:460`）把启动体拆进 `startOnce`，外层 try / catch / finally：任何一步失败都复位 `_starting`、保持 `started = false`、错误写控制台（与 `mount` 的失败处理同语义），成功后才 `ensureWindow`。失败不是终态：下一次 `notifyRestoreComplete` 会再启动。`epubStylesOf`（`:250`）里单张 `<link>` 样式表拉取失败（reject 或非 2xx）只丢这一张、按空表登记并保留签名，启动与邻章挂载照常完成。
- **[x] ② 已加自动化测试** — `fushi/test/reader/seamless_start_failure_test.dart` + `seamless_start_failure_harness.mjs`：生产安装脚本放进真 Chrome（真 `DOMParser` / shadow DOM / 样式改写，`fetch` 与引擎是替身）。断言：章节请求在途时认领边界；请求 reject 后 `_starting` 复位、前后两侧 `claimBoundaryTurn` 都回 false、控制台有 `[seamless] start failed`、没有未处理的 rejection；之后再次恢复完成能启动；一张样式表 reject 时启动成功、该张按空表登记、head 里两条 `<link>` 都被认领、邻章挂载成功且保留拉到的那张样式。修前实测同一跑手红在 `a failed start must reset _starting`（`starting:true`、两侧 claim 都是 true、多一条 unhandled rejection）。
- **备注**：真机未复测。待验：连续模式开「章节无缝衔接」，让某章的章节请求或一张 `<link rel=stylesheet>` 请求失败（非 404），滚到章末确认能换章。各平台本地资源通道对缺失的书内样式表是回 404 还是让请求失败没有查，所以真实触发率未知。被丢掉的那张样式表在无缝挂载的邻章里不生效（整章重载时浏览器原生 `<link>` 不受 CORS 限制、能加载），这是「只丢该张」的已知代价。
