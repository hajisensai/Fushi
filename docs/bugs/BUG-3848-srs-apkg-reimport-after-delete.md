## BUG-3848 · 删牌组与笔记类型后重导 apkg：0 new / restored / updated 但浏览、复习、笔记类型页全为空
- **报告**：2026-10-27（用户：所有者直报。截图：`Imported 日本語.apkg: 0 new, 3092 restored, 7854 updated, 0 unchanged`；牌组「日本語」0/0/0；笔记类型页只有 Fushi Card / Lapis，没有 Kiku）
- **真实性**：✅ 真 bug，两个独立根因叠加（夹具包已复现：三种删牌组方式 + 删笔记类型后重导，笔记计「恢复」、6/6 张卡 hidden、笔记类型页不见、牌组 total=0；「永久删除」那条笔记恢复后字段为空）。
  1. **笔记类型的删除标记导入从不清**：`packages/fushi_engine/lib/srs/apkg/srs_apkg_import.dart:855`（`_mapInto`）把已删除的笔记类型当「已存在」，只按「较新时更新」改名字 / 模板，`deleted` 寄存器原样留着。笔记那边（`:1552`）已经会清自己的删除标记，计成 restored，但卡片缓存按 `packages/fushi_engine/lib/srs/srs_db_store.dart:2107`（`noteGone = n.deletedAt != null || t.deletedAt != null`）全部 hidden；笔记类型页按 `srs_db_store.dart:1440` 过滤掉删除态 → Kiku 不出现、浏览 / 复习 0。
  2. **「永久删除」（v2 `Purge`）把实体 ID 永久拉黑**：`native/fushi_fsrs/src/store/sync2/mod.rs:583`（以及标签 `:439` / `:449`）只问 `semantics::is_purged`（`semantics.rs:361`，只看「这个 ID 被清除过」），清除之后到的同实体内容操作一律当场清除。笔记 ID 由来源 guid 派生（铁律 C），重导必然是同一个 ID → 写回的字段 / 标签全被吞掉，只有 `deleted: null` 落地：留下一条看得见删除标记已清、内容为空的空壳。此后每次导入按「较新时更新」（本机无内容记录、Anki mod > 创建时刻）判为要更新、草稿非空 → 计 **updated**，写入又被清掉，永远停在这个状态。
  - 计数：一律是 restored / updated 而非 new，是因为笔记 ID 确定性派生、删除只留墓碑（身份记录 + `deleted` 寄存器，清除还留 `sync2_purged` 标记）——这本身是对的（多设备导同一包不重复）；错在恢复不完整。截图里 7854 updated 与根因 2 的「空壳每次计 updated」吻合（**推测**：所有者之前已重导过至少一次，那次把被清除笔记的删除标记清掉了；没有所有者的库无法逐条核对），3092 restored = 删笔记类型时一并软删的其余笔记（根因 1，只清了笔记删除标记、卡因笔记类型仍删而隐藏）。
- **[x] ① 已修复** — 两处：
  - Dart（`srs_apkg_import.dart`）：`_mapInto` 遇到已删除的笔记类型 = 恢复：清 `deleted`、名字 / CSS / 模板 / 字段定义一律回到来源（不参与「较新时更新」），记进新的 `SrsImportReport.noteTypesRestored`（报告行 `srs_import_report_notetypes_restored`）；「不合并笔记模板」时删除态的同 ID 不另建副本。`_NtMap.restored` 传到笔记：笔记类型被恢复的笔记一律走恢复分支（内容 / 标签 / 首选牌组回到来源、卡回原牌组，计 restored），覆盖旧版导入留下的残局（笔记删除标记已清、笔记类型仍删除 / 空壳）。
  - Rust（sync2 语义，`semantics.rs` / `mod.rs`）：清除判据从「实体清除过」改成**因果**：`Purge` 操作进实体索引（`what = '#purge'`），内容操作只有**没见过**某次清除（与清除并发、或清除前写的迟到操作）才当场清除；见过清除的（清除之后的重导）是复活，照常落投影并经同步传到各设备。`purge_entity` 同一判据只清它没见过之后的操作 / 投影行 / 标签添加点；整列表 `tags` 写入以前绕过了清除检查，一并补上。修复前执行过的清除没有索引项：第一次碰到时从日志里的 `Purge` 操作补索引（同一事务，无 schema 升级）。
  - 取舍：复活不需要「反清除」操作，也不改历史——清除前的内容（含与清除并发的旧编辑）仍然被抹掉、无法从时间线找回，只有清除之后新写的内容活下来；对端旧墓碑（`deleted` 时刻）被重导写的 `deleted: null` 因果覆盖，不会再删掉它。再清除一次照样覆盖复活的内容。各设备收到同一批操作结论一致（判据只看 `op.saw(purge)`，与收到顺序无关；第三台新设备全量收下投影一致）。
- **[x] ② 已加自动化测试** — Rust `native/fushi_fsrs/src/store/sync2/tests.rs`：`content_written_after_seeing_a_purge_revives_the_entity_everywhere`（a 清除后重导、b 并发旧编辑：两端复活内容一致、旧编辑被抹、第三台设备一致、再清除照样清空）、`purge_recorded_before_the_index_existed_is_backfilled_from_the_log`；Dart `packages/fushi_engine/test/srs/apkg/srs_apkg_import_test.dart` group「删牌组 + 删笔记类型后重导同一个包」（三种删除方式各一条 + 旧版残局 + 两设备同步）；app 层 `fushi/test/srs/srs_import_entry_test.dart`「删掉笔记类型后重导」（报告行）。变异：`purged_for` 退回「清除过就清」→ 两条 Rust 新测与三条 purge 相关 Dart 测试变红；`_mapInto` 不清删除标记 → Dart 组 5/5 变红。
- **备注**：未在所有者真机库上复测（无库）；所有者库里已被清除的笔记重导后**媒体**取决于 apkg 是否带媒体（导入会重新落盘）。恢复分支仍按笔记逐条 `editFields`（每条一个事务，「恢复是少见路径」的旧实现），一万条级别的恢复会慢（未实测耗时）。
