## BUG-4916 · 存量样式去重扫完最后一批后游标停在最后一条命中，每次开库重扫其后整张修改记录表（开复习 20 秒）
- **报告**：2026-11-20（用户：应用内反馈 `_tdycqnr6s`，Android 3.3.0 正式版，srs.db 1.2 GB）
- **真实性**：✅ 真 bug。反馈日志里 `SrsOpLedger.heavy`：`sql:SELECT srs_field_edits 20688ms`、上一进程同项 `5x 25916ms max=19830ms`，紧跟 `core:study 21833ms`；每次冷启动都出现。
  - 根因：`packages/fushi_engine/lib/srs/srs_db_store.dart` `compactStoredStyles`（开库后台必跑，`fushi/lib/src/srs/srs_providers.dart:334`）每批调内核 `style_candidates {after: 游标, limit}`，游标只取**最后一条命中**的 rowid（旧 :1376 `final int cursor = rid[rows.rows - 1]`），命中为 0 时直接 `return`、游标不落盘。于是最后一批之后，命中之后那一大段不带样式的修改记录永远推不动游标：每次开库都从同一个旧游标起，把其后整张 `srs_field_edits` 用 `field_key LIKE 'f/%' AND instr(json, '<style>')` 逐行扫一遍（`json` 是生成列，逐行解 `jslim`；`native/fushi_fsrs/src/store/reads.rs:413` 旧 `style_candidates`、新代 `native/fushi_fsrs/src/store/gen4/cmd/reads.rs:702` 同口径）。1.2 GB 的库上一次 20 秒；3.3.0 里这条 Drift SELECT 跑在 `runExclusive` + 事务里、与内核同一条连接，开复习的 `study` 命令被它挡住，于是「卡少也加载很久」。develop 已把读改走内核读命令，但游标逻辑原样，空尾巴每次开库照扫。
- **[x] ① 已修复** — 内核两代 `style_candidates` 回包加扫描上界 `end`（开扫时最大 rowid / 修改操作主键，不小于 `after`，并作为条件绑进查询）；Dart 命中不满一批时把游标推到 `end`，即使这批没有可改写的行也经 `edits_rewrite_repr`（空 rows）把游标写进本机状态，扫完即停。
- **[x] ② 已加自动化测试** — `packages/fushi_engine/test/srs/srs_style_dedup_test.dart`「存量迁移扫完后游标推到扫描上界」（命中之后有尾巴：迁移后本机状态里的游标 = 最大 rowid，重启再跑一次读即止、游标不动）；`native/fushi_fsrs/src/store/gen4/cmd/tests.rs` `style_scan_end_lets_the_cursor_pass_an_empty_tail`（协议 3 / 新代都回 `end`：大于最后命中、从 `end` 再扫为空且不前进、不小于 `after`）。
- **备注**：首次全量扫描（新装 / 恢复备份后游标归零）仍要整段扫一遍，但只付一次。若表里最大 rowid 那行被删后再插入，新行可能复用 ≤ 游标的 rowid 而被跳过——去重只是表示层优化，漏掉的行照常按内联样式渲染，不影响正确性。真机未复测（按规则不做）。
