## BUG-3492 · 在线视频后台制卡后，同一查词弹窗里点 ✓ / 高级制卡确认没反应、不覆盖
- **报告**：2026-10-17（用户反馈 cqlujSVuxg，Android vivo，2.10.0-debug.19358；扩展里在线看的视频：制卡后马上想加上下句，在同一弹窗里再进「高级制卡」确认、或点已制卡的 ✓ 都没反应，不覆盖、不弹「已覆盖」，要划掉弹窗重新查词才能覆盖成功）
- **真实性**：✅ 真 bug。在线视频（网络流）制卡默认走后台模式（`VideoOnlineMiningMode.background`，`fushi/lib/src/mining/video_online_mining_mode.dart:30`）：`_mineVideoCard` 不等落卡、直接回 `MinePopupResult.queued()`（`fushi/lib/src/pages/implementations/video_fushi/lookup_mining.part.dart` 后台分支 `_trackBackgroundMine` 之后）。popup.js 收到 `result.queued` 把本按钮的闭包标记 `queuedLocally = true`（`fushi/assets/popup/popup.js` mine 按钮 onclick 的 `if (result.queued)` 分支），而 app 内没有宿主队列（`window.fushiIsEntryQueued` 只有浏览器扩展定义），这个标记**此后再也没有任何东西撤掉**：卡落地后宿主不通知弹窗，查重刷新 `setMineState` 也不清它。onclick 开头 `if (isEntryQueued()) { setMineState(...); return; }` 于是对这颗按钮永远成立——再点 ✓ 直接 return；「高级制卡」确认经 `fushiPopupMineEntryByIndex` 回点的是同一个 onclick，同样 return，且 promise 正常 resolve，对话框按「点到了」关窗，没有任何提示。新弹窗重新渲染按钮、没有这个标记，查重得到 ✓ → `minedCardAction` 操作单 → 覆盖成功，所以「换个弹窗就好」。
  - 本地视频（等待模式，不回 queued）与阅读器（只有 Anki 不可达进待发队列时才回 queued）走的都是已制卡的正常路径，不受影响；只有回 queued 的表面会踩到。
  - 「恢复为一键制卡的默认」：对话框控制器的 `resetToDefaults`（`fushi/lib/src/mining/advanced_mining/advanced_mining_controller.dart:734`）在同一弹窗里没有找到独立失效的代码路径——它恢复的是对话框打开时的选择，之后确认仍回点那颗被标记卡死的按钮，所以表现为「恢复默认后也制不了」。按同一根因处理，未单独改它。
- **[x] ① 已修复**（第一版 PR #2276：撤标记 + 落地通知；后续 PR：方案 B 排队覆盖 + 文案缩短）— popup.js：`setMineState(true)`（Anki 里已有这张卡）一律撤掉本弹窗的「已加入」标记；app 车道点击「已加入」的按钮时先问一次 Anki：已落地 → 撤标记、落到已制卡的正常路径（操作单 / 覆盖）；未落地 → 经新桥 `queueOverwrite` 把覆盖交给宿主排队。视频页后台落卡成功后经 `MinedStateSignal.instance.notifyWord(expression)` 通知弹窗重问。浏览器扩展（宿主持有队列）行为不变。三份 popup.js 镜像同步。
  - **所有者 2026-10-17 拍板（方案 B）**：卡还在后台写入时，从「高级制卡」或点 ✓ 发起的覆盖**排队**，对话框照常关闭；写入落地后自动覆盖并报「已覆盖」；写入失败报原因、不覆盖；同一个词连续排多次只留最后一次；弹窗关掉后排队仍有效。实现：排队簿 `fushi/lib/src/mining/pending_mine_overwrites.dart`（`PendingMineOverwrites`，纯逻辑）；视频页 `video_fushi/lookup_mining.part.dart` 的 `_onQueueOverwriteImpl` 在排队那一刻同步冻结区间 / 句子 / 覆盖项 / 查词画面，后台写入落地时 `_settleQueuedOverwrite` 结算：成功 → 按 note id（AnkiDroid 不回 id 时按词反查最新一张）用冻结的输入 `_mineVideoCard(updateNoteId: …)` 覆盖；失败 → OSD「卡没写进 Anki（原因），已取消覆盖」；换集 / 换播放器 → 不覆盖并说明。排队的覆盖执行时以 `detachedFromDialog: true` 调 `_mineVideoCard`，不借用此刻开着的另一个高级制卡对话框的锁帧 / 媒体副本，只用排队时冻结的画面。桥 `queueOverwrite` 经 `DictionaryPopupLayer` / `DictionaryPopupWebView.onQueueOverwrite` 透传，没接线的宿主回 `accepted:false`（绝不回 null，BUG-1918）。
  - 远程看片页（`video_remote_page`）不做远程覆盖，只提示「电脑端还在制卡，稍后再覆盖」（`video_remote_overwrite_pending`）。其余不走后台写入的宿主（阅读器待发队列等）提示通用的 `popup_mine_still_queued`。
  - **所有者要求提示文案改短**：`popup_mine_still_queued` 由「已加入制卡，还没确认写进 Anki，暂时不能覆盖。」改为「还在写入 Anki，稍后再试」（en / ja / zh-HK 同步改，popup.js 三份镜像的回退文案同步）；新增的 `popup_mine_overwrite_queued`「写入 Anki 后自动覆盖」、`video_mine_overwrite_cancelled*`「卡没写进 Anki，已取消覆盖」等一律短句。
- **[x] ② 已加自动化测试** — `fushi/test/mining/pending_mine_overwrites_test.dart`（写入完成自动覆盖、AnkiDroid 反查目标、写入失败不覆盖、找不到目标不覆盖、同词重复排队只留最后一次、别的词互不影响、无在途写入不收）；`fushi/test/pages/mine_entry_by_index_overrides_test.dart`（高级制卡覆盖项并进排队请求、未接线宿主回 accepted:false）；`fushi/test/utils/misc/popup_asset_behavior_test.js`（未落地点 ✓ 交宿主排队 / 宿主收下时显示宿主文案且不另制新卡 / 落地后同一弹窗走覆盖 / 宿主刷新撤标记）；宿主接线守卫 `fushi/test/pages/video_background_mine_refreshes_popup_guard_test.dart`。
- **审查补丁（2026-10-17）** — ① 同一个词可同时有两次后台写入在途（两个弹窗各点一次「+」）：排队簿改为每次写入领代号（`PendingMineOverwrites.addStarted` 返回 id），覆盖绑定在排队时最新的那次写入上，只由它的落地结算；旧实现用 `Set` 记在途，先落地的那次会清掉在途标记并把覆盖套到错的笔记上。② 赛跑窗口：弹窗回问 Anki 之后、请求到宿主之前那次写入落地 / 失败了，宿主按 `lastLanded` 回 `settled: landed | failed`，popup.js 同一次点击直接走已制卡覆盖路径或撤掉「已加入」，不再误报「还在写入」。③ `queueOverwrite` 桥只在宿主**收下**时才算读走 payload（允许对话框提前关）；拒收时「高级制卡」覆盖项留给同一次点击接着走的 `minedCardAction`。④ `land(res)` 自己抛错时也结算（`onError` 接不到 onSuccess 里的异常），在途标记不再永久残留。⑤ 写入成功但找不到目标笔记时 OSD 改报 `video_mine_overwrite_cancelled_no_target`，不再说「卡没写进 Anki」。测试：`pending_mine_overwrites_test.dart`（并发两次写入 / 重复结算 / lastLanded）、`mine_entry_by_index_overrides_test.dart`（拒收保留覆盖项）、`popup_asset_behavior_test.js`（settled landed / failed）、`video_background_mine_refreshes_popup_guard_test.dart`（land 抛错结算、settled 回执接线）。
- **备注**：未在 Android 真机 + 在线视频源复现/复验（本机无对应在线源环境）；结论来自代码路径与 popup.js 真跑行为测试。
