## BUG-4906 · 互联实时转码同一段每次请求都重新起 ffmpeg
- **报告**：2026-11-20（路线图 #3722 video-34 + video-s2-9，c34）
- **真实性**：✅ 真问题（性能 / 资源）。根因 `packages/fushi_engine/lib/sync/fushi_sync_server/video.part.dart:1389`（develop @ `7745effa2e`）：`_handleTranscodeHls` 对每个 `hlsseg.ts?n=` 请求无条件 `transcodeSegment(...)`，`live_transcode.dart` 的「一段一个进程」设计没有任何产物复用，响应注释原话「同一段再请求一次就再转一次」。client 往回拖到 mpv 向后缓冲之外（移动端只有 16 MiB，约 7 段 3 Mbps）、重连后重新请求、或同一段并发重复请求时，host 都要把 6 秒内容完整重转。实测（本机 16 线程，PATH ffmpeg N-123122，48 s 合成源）：4K HEVC 源一段 1.4～3.3 s 墙钟，1080p HEVC 源 1.1～1.9 s。
- **[x] ① 已修复** — `live_transcode.dart` 新增 `TranscodeSegmentCache`（按字节 64 MiB 的 LRU + 同键在途合流，失败 / 取消不入缓存）；`FushiSyncServer` 持有一份，`_handleTranscodeHls` 经它取段，键 = 流 token + 段号 + 输入路径；所有删 token 的路径（释放流票 / 吊销 / TTL / 上限淘汰）收进 `_dropVideoToken`，连同该 token 的段一起清，停机时清空。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/transcode_segment_cache_test.dart`（缓存契约：命中、键维度、合流、失败不入缓存、LRU、作废清理含在途段）；`fushi/test/sync/fushi_sync_server_transcode_test.dart`「同一段再请求从缓存取」「并发合流」「换档新 token 不吃旧档缓存」「上限淘汰清段」「释放流票清段」（修前 runner 调用次数 / 缓存计数断言必红）。
- **备注**：host 主动预取下一段**未做**——量过单段耗时后判定无收益（详见 PR 正文与 c34 回报）：本机单段墙钟只有段长的 22～55%，client 的 mpv 本身按 `cache-secs` 顺序预取已追得上播放；两段并发的吞吐增益 1.23～1.73x 只在 CPU 有富余时成立，而真正需要它的弱 host 恰恰没有富余，还会多占 3 个并发名额之一。（后续：维护者 2026-11-20 在拍板台 `design-nmv-transcode-prefetch` 拍「做」，host 预取下一段已补上——只用空闲名额、始终给前台留 1 个、从不排队，seek 走远时作废没人等的预取，实现在 `video.part.dart` 的 `_prefetchTranscodeSegment` 与 `live_transcode.dart` 的 `tryLeaseIdleTranscodeSlot`。）未做设备验证：互联转码 HLS 装置上回跳不重转、4K HEVC 真实片源的每段耗时。
