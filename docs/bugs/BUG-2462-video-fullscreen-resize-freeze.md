## BUG-2462 · 加载中进全屏画面冻结（引擎 resize 同步器目标钉死）
- **报告**：2026-09-12（用户：视频加载时双击全屏，画面可能整窗冻结，拖窗口 / 再进出全屏才恢复；无 HDR。用户追加要求 F11 在视频页与双击全屏行为一致）
- **真实性**：✅ 真 bug。**根因不在 Dart、不在 mpv**，是 runner 全屏几何 × Flutter Windows 引擎 resize 同步器的组合：
  - 引擎（3.44 `engine/src/flutter/shell/platform/windows/flutter_windows_view.cc:208-262`，源码核实）：子窗 WM_SIZE 后 `resize_status_=kResizeStarted` + 目标尺寸，此后 `OnFrameGenerated` **只接受尺寸恰好等于目标的帧，其余一律丢弃**；平台线程最多等 100ms（`kWindowResizeTimeout`）后返回但**不复位目标**；新尺寸 == 当前 surface 时走早退分支（`SurfaceWillUpdate==false`，`:225-229`）**只发 metrics、不更新目标**。纹理帧（mpv 每帧 `MarkTextureFrameAvailable`）走 `Animator::DrawLastLayerTrees` 重用旧树尺寸、不经 Dart build。
  - runner `fushi/windows/runner/win32_window.cpp:622` `SetFullscreen` 从最大化进全屏是两步几何：先 `SetWindowPlacement` unzoom 到显示器矩形，再超尺寸 `SetWindowPos`。本机（用户机器，主屏工作区 = 整屏）实测子窗客户区序列 `2560x1440 → 2549x1434 → 2560x1440`，两次 WM_SIZE 间隔 106/125ms = 第一步已超时（加载中 UI isolate 忙，F11 本身延迟 660ms 才被处理）。于是目标钉在 2549x1434、Dart 永远画 2560x1440 → 每帧被丢 → 整窗冻结，任何再变尺寸的操作换掉目标即恢复。退出全屏是对称的两步（SW_SHOWNORMAL → SW_MAXIMIZE），同样隐患。是否冻结取决于 UI 线程处理两条 metrics 与帧回调的交错，故「有可能」。
  - 取证：进程外 `SetWinEventHook` 记录主窗/FLUTTERVIEW 矩形序列 + 屏幕像素哈希采样（`probe_freeze.ps1`，job tmp，不入库）。
- **[x] ① 已修复** — 结构性消除触发条件，而不是改几何取巧（那只覆盖本机配置）：runner 成为 Flutter 子窗尺寸的唯一闸门 `fushi/windows/runner/child_resize_gate.h`（纯状态机）。交付尺寸后按 `MoveWindow` 耗时判定：<100ms = 引擎已在超时前呈现（超时分支不可能更早返回，判定单向精确）；≥100ms 进「待确认」，等 Dart 光栅化尺寸上报（`fushi/lib/src/utils/rasterized_frame_size_reporter.dart`：`FrameTiming.frameNumber` ↔ build 时 `frameData.frameNumber` 对齐，只在尺寸变化时经 `app.fushi/window` `reportRasterizedFrameSize` 上报）。有待确认目标时，请求 == 当前 surface 尺寸的交付**推迟**到确认后；其它尺寸照常。零尺寸（最小化）不再交付给子窗（引擎本就忽略零目标，而 0×0 metrics 会让恢复后永远画不出待确认尺寸）。覆盖任意 A→B→A 序列（进/出全屏、DPI、贴靠、快速连按），不靠计时猜测。F11 对齐：`video_player_shortcuts.dart` 解析链第三段从 global scope 只认领 `globalToggleFullscreen` 并映到 `toggleFullscreen`（与 F / 双击同一回调）。提交见本分支 `fix-fullscreen-resize-freeze`。
- **[x] ② 已加自动化测试** — C++ `fushi/windows/runner/tests/child_resize_gate_test.cpp`（每次 Windows runner 构建执行；含实测的 2560→2549→2560 超时序列、上报早于 DeliveryFinished、第三尺寸覆盖推迟、surface 未知不推迟、最小化零尺寸）；Dart `fushi/test/utils/rasterized_frame_size_tracker_test.dart`（帧号对齐、只报变化、纹理帧跳过、积压淘汰）、`fushi/test/media/video/video_f11_same_as_double_click_fullscreen_test.dart`（F11 与 F 同一执行体、其余 global 动作不截胡）。真机复测：探针脚本按同一时序 F11 进全屏，断言子窗尺寸序列与画面持续更新。
- **审查返工（同分支第二个提交）**：① 闸门只记「上次确认的 surface」有盲区——超时交付 X 后 Dart 可能已把 surface 切成 X 而上报未到（release 最长 1s），`W→X(超时)→Y(超时)→X` 仍会交付 X 撞早退分支；改为维护「候选 surface 集合」= 上次确认尺寸 ∪ 此后所有被取代但未确认的交付，pending 期间集合内尺寸一律推迟，pending 确认后集合复位；旧上报不再能确认新交付。② 两处对轴弹窗的冻结快捷键表 `exclude` 同时摘掉 `globalToggleFullscreen`。③ 加载 / 失败 / 缺资源态（无 controls 子树）F11 不消费、交回 app 根窗口全屏，失败态不再变死键。④ `globalToggleFullscreen` 入 `kVideoPressEdgeOnlyActions`，只认按下沿。
- **备注**：引擎缺陷本身（超时不复位目标 + 早退分支）无法在预编译引擎里修，本仓靠闸门保证引擎永远收不到触发序列。旧注释「最大化窗口忽略 SetWindowPos 尺寸」实测不成立（zoomed 态下 SetWindowPos 完整生效），但本次未改全屏几何，只钉住子窗交付。release 下 `FrameTiming` 上报最长积压 1s：仅在「交付超时且紧接着要求回到 surface 尺寸」这条罕见路径上，子窗最多晚 1s 跟上父窗几何。
