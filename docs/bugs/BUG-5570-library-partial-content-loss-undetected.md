## BUG-5570 · 书库内容部分丢失（哨兵还在）启动期毫无告警
- **报告**：2026-11-27（GitHub #4521 / 应用内反馈 1DaVBFXQEI：Android 受管书库 `Android/data/app.fushi.reader/files/data` 下 94 个解包书目录丢了 82 个、74 个有声书音频 / 字幕文件丢了，数据库行都在；启动时没有任何提示，用户只看到书「缺失」。删除原因尚未定案）
- **真实性**：✅ 真检测缺口。`fushi/lib/src/storage/library_sentinel.dart:237`（`check` 里 `if (sentinel == token)`）哨兵文件还在且 token 一致就直接判 intact，只刷新条目数、不看书库内容；条目数变少只在哨兵没了时才比较。所以「整树被清后部分恢复」「外部工具删掉大部分书目录」「清理工具只删了 `audiobooks`」这类部分丢失不会被检测到，不进数据位置取证环，也没有首页提示。条目数本身也不能当判据：应用内删书同样让条目变少（BUG-5492 的「应用内删书不误报」）。
- **[x] ① 已修复** — 新增书库内容对账 `fushi/lib/src/storage/library_content_audit.dart`：拿数据库当账本（`epub_books.extract_dir`（按 format 分书 / 漫画）、`audiobooks` 的音频目录 / 音频列表 / 字幕、`srt_books` 的字幕 / 音频、`video_books` 里落在数据根内的视频），只取能解析出数据根内尾段的路径（`AndroidLibraryDbWitness.libraryRelativeTail`，外部来源 / 原地播放不算），库里原样路径与「尾段接到本次书库根」各 stat 一次，任一处在就算在。不可读与真缺失分开：书库根不存在 / 列不出来 → `rootUnreadable` 不判；顶层受管目录存在却列不出来 → 其下条目记「不可读」不算缺失。成片（≥20 行，或 ≥2 行且 ≥10%）才留现场（support 根 `library_content_audit.json`，按「已提示过的缺失行数」去重：同一批不反复弹，再丢更多才再弹，恢复后清零）；零星残行只进环。`AppModel` 在哨兵之后五端都跑，读库 + stat 全在后台 isolate（只读另开 SQLite 连接），不挡冷启动；结论写进数据位置取证环（`LibraryContentAudit`，随反馈日志上传：缺失数、每类样例路径、根、时间）。首页沿用「书库文件不见了」同一入口（`maybeShowLibraryVanishedAlert`，等对账最多 10 秒）弹「书库里有些文件不见了」：说明书还在书库列表里、进度书签笔记都在，可「重新扫描来源」（逐个走首页自动扫描同一个入口 `_runAutoSourceScan`，只扫书 / 漫画来源）、「上传日志」（反馈预填带现场）或稍后。整树消失与部分缺失同时出现时只弹前者，部分缺失摘要并进反馈正文。全程不删任何行、不动任何文件。
- **[x] ② 已加自动化测试** — `fushi/test/storage/library_content_audit_test.dart`：94 本删 82 + 有声书 74 个音频与字幕全删时哨兵判 intact、对账留现场（数量、样例、行与剩余文件不动）；同批不重复提示 / 再丢重新提示 / 恢复清零；零星残行不提示；书库根不在不判；顶层目录整个不在是真缺失；旧根前缀不误报；书库外路径不参与；漫画单独计数；主库不在报 error；顶层目录列不出来记不可读；现场 JSON 往返与反馈预填。
- **备注**：「重新扫描来源」能否真的补回缺失内容取决于扫描器是否用原件重建缺失的解包目录（另一条分支 `claude/fb-scan-repair` 在做）；没有来源的书只能从同步恢复或重新导入。真机上的提示框未复测。
