## BUG-3630 · 视觉小说模式制卡句子被切屏截断成半句
- **报告**：2026-10-20（用户：应用内反馈 `UfWVqceDxa`，Android 小米 23113RKC6C，3.0.0-debug.20310：「划的句子被中间截断，和 hsa 划的不一样」「在高级制卡里面，默认制卡的句子和在 hsa 一样是完整的」。书《明智恭介の奔走》查「ひけらかす」，Fushi 卡句子是「きと同じ思考なのをひけらかされるのだからな」」，Hoshi Reader 同处是「作中の探偵役が、素人のミステリ書きと同じ思考なのをひけらかされるのだからな」）
- **真实性**：✅ 真 bug（基线 `32dfae0c48`，沿代码路径核实，真 Chrome 跑完整 VN 工厂复现）
  - 普通制卡与「高级制卡」的句子**同源**：查词时 JS `fushiSelection.buildSelectionPayload`（`fushi/lib/src/reader/reader_selection_scripts.dart:2966`）调 `getSentenceContext`（`:2354`）算句，Dart `_handleTextSelected` 写进 `currentSentence`（`fushi/lib/src/pages/implementations/reader_fushi/lookup.part.dart:197`）；直接制卡读它（`reader_fushi/mining.part.dart:27` `_prepareMiningContext`），高级制卡的句子预览也读它（`reader_fushi_page.dart:4780` `onSentenceContextPreviewFromDraft`）。两条路径之间没有第二个取句来源，所以「高级制卡完整、直接制卡截断」不是两套取句不一致——差别只能来自两次查词时 DOM 不同（见备注）。
  - 截断点：`getSentenceContext` 从点中的字往前按 `。！？.!?` 找句首，游走范围是 `findParagraph`（`:1804`）给出的块。分页 / 连续模式是整章 DOM，跨过 `<ruby>書<rt>か</rt></ruby>` 没有问题（ruby 的 `<rt>` 被 walker 跳过，句子照样从「「作中」起，新增测试 case12 钉住）。
  - **视觉小说（VN）模式**把整章搬进脱离文档的 `sourceRoot`（`reader_visual_novel_scripts.dart:1024` `detachChapterSource`），document 里只有当前一屏的**切片克隆**（`:2309` `cloneRangesWithOffsets`）。一屏装不下时 `splitScreenToViewport`（`:1584`）按量尺二分切屏，ruby 作原子单元——一句长台词（「保留对话完整」时整段「…」是一个单元）就会被切在「書」|「きと同じ…」之间。点中下一屏的「ひけらか」时，`findParagraph` 拿到的是克隆出来的那半个 `<p>`，往前游走走到屏首就没了 → 句子从「き」起，句尾照样到「」」。截断落在「書」后而不是任意字，正是因为 ruby 原子切屏后屏首就是「き」。
  - 复现：`vn_sentence_across_screen_split_bug3630_harness.mjs` 在修复前点按查词得到的句子是屏切片「のをひけらかされるのだからな」」。
- **[x] ① 根因修复** — VN 阅读器提供「当前屏克隆位置 → 源章节位置」的换算：`ReaderVnContentStream.sourcePositionForRawOffset`（章内 raw 偏移 → 源文本节点 + UTF-16 偏移）+ `fushiReader.sourceTextPosition(node, offset)`（克隆节点用 `nodeStartRawOffsets` 的章内 raw 偏移换算；不是当前屏克隆的节点返回 null）。`getSentenceContext` 开头若阅读器提供这个钩子就先换回源章节，再按同一套标点规则取句——三种阅读模式的句子边界一致（分页 / 连续没有这个钩子，行为不变）。句首 / 句尾节点随之是源节点，所以 `getNormalizedOffset`（学习单位）补「源节点用 `sourceTextOffsetForNode`」、VN `getMatchableOffset`（音频）补「源节点用 `sourceTextRawOffsetForNode`」，句子音频区间、学习区间与整句同宽；`getSurroundingSentences`（高级制卡 / 加减上下文句）从源章节游走，也能跨屏取到前后句。没有加任何特例分支或延迟。
- **[x] ② 自动化测试** — `fushi/test/reader/vn_sentence_across_screen_split_bug3630_test.dart` + `vn_sentence_across_screen_split_bug3630_harness.mjs`（真 Chrome、完整 VN 工厂 + 真选区脚本：前置条件断言「点中的屏确实切在句中」，然后点按查词 / 原生选区两条路径都得到整句、`sentenceOffset` 指向词、句子音频区间等于源章节整句区间、学习区间可解析；`getSurroundingSentences(1,0)` 跨屏取到上一句。修复前红在「tap lookup returns the complete sentence」，修复后绿）；`fushi/test/reader/reader_get_sentence_context_boundary_test.{js,dart}` 新增 case12（整章 DOM 上带 ruby 的原句取整句、偏移指向词，覆盖分页 / 连续）。
- **备注**：
  - 反馈说「高级制卡里默认句子是完整的」：按代码两者读同一个 `currentSentence`，同一次查词不可能一完整一截断。推测反馈人看高级制卡时那一屏的切点不同（换过屏 / 往回翻 / 字号或屏幕方向变化后重新切屏），未能证实；日志里没有阅读模式信息，「用户当时在 VN 模式」也是按截断形态（屏首从 ruby 后一个字开始、句尾完整）推断的。
  - 未在真机复测（本批不用真机 / 模拟器 / Mac）。待真机复测：Android 上 VN 模式、开「保留对话完整」，找一句跨屏的长台词，在第二屏查词直接制卡，卡片句子应为整句；分页 / 连续模式同句应不变。WebKit 一侧（iOS / macOS）同一份 JS，也待 Mac 上验。
