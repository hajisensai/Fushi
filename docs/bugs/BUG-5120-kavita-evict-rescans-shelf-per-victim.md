## BUG-5120 · Kavita 缓存淘汰每删一本扫两遍书架、逐本查用户数据表（O(M·N) 查询）
- **报告**：2026-11-22（外部审计 HBK-AUDIT-041，Codex 2026-11-21 PR 审查，PR #3792）
- **真实性**：✅ 真 bug（性能）。`fushi/lib/src/media/kavita/kavita_book_service.dart`（cbdc2a45ed）的 `trimCache` 每删一本都在锁内跑一次 `_trimVictims` 选目标（:469），复核时 `stillRemovable` 又跑一次 `_trimVictims`（:480）；`_trimVictims` → `_evictableEntries`（:642）每次都扫整个 Kavita 书架，对每本逐个跑 `_hasUserData`（6 张表各一次 `LIMIT 1` 查询）和 `getReaderPosition`。清 M 本、N 本缓存时约 2·M·N·8 次查询；`clearCache` 同形（每本一次全扫）。实测（内存库、上限 2、拦截器计 SELECT）：10 本缓存淘汰 8 本共 815 次查询、17 次全书架扫描；40 本淘汰 38 本 11795 次查询、77 次全书架扫描。
- **[x] ① 已修复** — 提交 9374a6f362。`trimCache` / `clearCache` 合到同一个 `_evictCandidates`：候选在锁内只拍一次快照，快照本身改成「一次书架扫描 + 每张用户数据表一条按键批量的 `IN` 查询 + 阅读位置一条批量查询」，查询数与书数无关；之后逐本删，每本删前只在锁内复核这一本（`_sameUse`：仍是缓存副本、没被打开、阅读位置没动；且仍没有用户数据）。快照作废才重拍：经本服务的打开 / 固定 / 取消固定 / 新导入会让静态代际 `_evictionEpoch` +1，或复核发现目标被改了 / 已被删。同条件实测：10 本 112 次查询、1 次扫描；40 本 502 次查询、1 次扫描，每多淘汰一本约 13 次查询（常数）。
- **[x] ② 已加自动化测试** — `fushi/test/media/kavita/kavita_book_cache_test.dart` 组「HBK-AUDIT-041 eviction query cost」：Drift 拦截器计数，断言整次淘汰只扫一次书架、每多淘汰一本的查询增量 ≤ 16（与书数无关）。原有「淘汰期间被打开 / 固定的书不删、按最新状态重新排位」等用例照旧通过。变异实测：服务换回 cbdc2a45ed 版本，该用例变红（17 / 77 次扫描）。
- **备注**：已知边界——别的子系统（阅读器加书签等）在淘汰进行中给**另一本**未入选的书加了用户数据，快照不知道，最多多淘汰一本没有用户数据、进度已保住的缓存副本，不丢本机数据，下次打开重新缓存；入选的那本自己加了数据会在复核时被拦下。
