## BUG-4764 · QRC 注音轨汉字计数口径和来源不一致（〇 〆 等），整首歌的注音全部丢失
- **报告**：2026-11-17（PR #3510 合入后的遗留项核实：QRC `[kana:]` 注音轨）
- **真实性**：✅ 真 bug。`native/fushi_music/src/lyrics/qrc.rs:387`（修前，`is_kanji`）只认 U+3400–4DBF、4E00–9FFF、F900–FAFF、20000–3134F 加 `々` `〆`：不认 `〇`（U+3007，Script=Han、Ideographic），却认 `〆`（U+3006，Ideographic 但 Script=Common），也漏了扩展 H（U+31350–323AF）。`apply_kana`（修前 `qrc.rs:467`）先比总数，`total != kanji` 整份返回 false。注音轨不分行，只要正文里有一个字的归类和来源（QQ 音乐）数法不同，整首歌一个注音都不挂，也没有提示。另外核实代理说的「漏了兼容补充区 U+2F800–2FA1F」不成立：它落在 20000–3134F 里，一直被算作汉字。
- **[x] ① 已修复** — `5feac7b56d`：`qrc.rs:382` `is_kanji` 只放一定算汉字的字（统一表意文字各区含扩展 H、兼容区、`々`）；`qrc.rs:392` `AMBIGUOUS_KANJI = ['〇', '〆']` 是随口径而变的字。来源按哪种口径数没有公开约定（没拿到带 〇 的真实 QQ 样本），`qrc.rs:457` `apply_kana` 对这两个字算 / 不算的每种取舍各调一次 `plan_kana`（`qrc.rs:492`，原有的「总数相等 + 每段落在连续汉字上 + 不跨行」完整对齐校验），只采用对得上的那一种；两种取舍都对得上但挂法不同时分不出来源口径，仍整份不挂（宁缺不错位）。`lyrics/mod.rs:42` `PARSER_VERSION` 4 → 5，旧缓存读取时重建。审查补充：上限再延到 Unicode 17 的扩展 J（U+323B0–3347F，紧接扩展 H），同一测试里钉住 U+323B0 / U+33479。
- **[x] ② 已加自动化测试** — `native/fushi_music/src/lyrics/qrc.rs` 测试模块：`kana_track_counting_ideographic_zero_attaches`（来源数 〇：「二〇二〇年」挂上）、`kana_track_not_counting_shime_mark_attaches`（来源不数 〆 / 数 〆 两种都挂上）、`kana_track_counts_extension_h_ideographs`（U+31350）、`kana_track_ambiguous_between_conventions_changes_nothing`（两种口径都对得上但挂法不同 → 不改）。变异实测：把实现改回旧口径（只算 〆、上限 3134F）时这 4 条全部变红。
- **备注**：没有带 〇 / 〆 的真实 QQ 音乐 QRC 样本，来源的实际计数口径未实测确认；本修复对两种口径都成立，不依赖这个确认。纯 Rust 解析层，未做真机验证。
