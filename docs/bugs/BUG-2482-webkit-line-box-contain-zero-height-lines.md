## BUG-2482 · WebKit 上 BUG-2472 的 line-box-contain 把嵌套 inline / 空行行盒压成零高：目录列叠印、空行消失
- **报告**：2026-09-12（用户：「mac 端無職転生 22 实测，章节列表贴在一起」，截图为目录页 17 条章节标题全部叠印在同一列）
- **真实性**：✅ 真 bug（WebKit 专属，BUG-2472 的修法引入的回归）。根因 `fushi/lib/src/reader/reader_content_styles.dart:196`（`_webKitLineBoxCss` 对 iOS / macOS 发出 `html { -webkit-line-box-contain: block replaced !important }`）。
  - 机制：EPUB 的 XHTML 被当 `text/html` 端上且多数没有 `<!DOCTYPE>`（`document.compatMode === "BackCompat"`，quirks 模式）。quirks 模式下 WebKit 只给「根 inline 盒里直接有文本节点」的行加块级 strut；`block replaced` 又把所有 inline 盒的贡献剔掉。于是凡是一行的文字**全部**住在 inline 盒里（`<p><a><span>…</span></a></p>`、`<p><span>…</span></p>`、`<p><em>…</em></p>`，甚至 `<p><span><ruby>…</ruby></span></p>`）或只有 `<br/>` 的空行，行盒高度为 0——段落块轴尺寸 0，下一段直接叠上来。
  - Mac 隐藏 runner 真书取证（`reader_mushoku22_layout_probe_itest.dart`，`[m22] SUMMARY` 行）：目录页 p-toc-002 在 `block replaced` 下 17/18 个 `<p>` 宽 0（截图与用户一致）；正文 p-002 的 63/2006 个 `<p>` 宽 0（其中 57 个是 `<p><br/></p>` 空行——段落间距在 Mac 上整体消失）；切回 `block inline replaced` 后目录 0/18、正文 6/2006（那 6 个是真空 `<p></p>`）。合成段落逐类实测：`bare` 36.3 / `span1` 0 / `span2` 0 / `a1` 0 / `a-span` 0 / `br` 0 / `mixed`（根级有文本）36.3 / `ruby` 36.3 / `span-ruby` 0 / `em-span` 0 / `nbsp` 36.3。Windows（Blink 不解析该属性）全部正常。
  - 为什么不能靠 `:has(ruby)` 收窄：`<span><ruby>…</ruby></span>` 这种行在带注音的段落里照样归零（`scoped` 候选实测 `span-ruby` = 0）。
- **[x] ① 已修复** — （提交哈希见本分支）`_webKitLineBoxCss` 删除，任何平台不再发 `-webkit-line-box-contain`；BUG-2472 改用 `_webKitRubyAnnotationCss`：Apple 端 `ruby > rt, ruby > rtc { margin-block-start: -2em !important }`，只把注音盒在流中的高度抵消掉、不动行盒 strut。Mac 真书探针：目录页零高 `<p>` 17/18 → 0/18，正文 63/2006 → 6/2006（剩下的是真空段），注音段落多出量仍为 0（横/竖 × 22/46 × 行高 1.65/1.0），注音位置逐像素不变。
- **[x] ② 已加自动化测试** — `fushi/test/reader/vertical_ruby_line_box_contain_guard_test.dart`：任何平台生成的正文 CSS 都不得含 `-webkit-line-box-contain`；iOS / macOS 必含「含 `rt` 的选择器块里有一个负的 `margin-block-start`」，Android / Windows / Linux 必不含**任何**负 `margin-block-start`。两条断言钉的都是不变式而非字面量——合入 develop 时返工过一次：原口径逐字节钉死 `ruby > rt, ruby > rtc {
  margin-block-start: -2em !important;
}`，连缩进换行一起钉，而反向断言用的是**同一个** `-2em` 串，于是「Apple 端换个数值」会同时造成正向假红 + 反向退化成恒真空壳（真把负 margin 漏发给 Blink 也照样绿）。变异实测四轮：换等价数值仍绿、Apple 端不发变红、漏发给全平台变红、**换数值且漏发**（旧口径会静默变绿的组合）也变红。真渲染：`fushi/integration_test/reader_mushoku22_layout_probe_itest.dart`（真书目录页零高段落计数 + 合成段落逐类 + 注音行盒指标，Mac 用 `tool/run_mac_itest.ps1` 跑，读 `[m22] SUMMARY`）。
- **备注**：BUG-2472 要解决的「WebKit 首行含注音的段落被撑高 ≈0.215em」仍然成立，修法要换：不再碰 line-box-contain（它在 quirks 模式下是把整条行盒的 strut 一并剔掉），改为只把 `<rt>` 注音盒自身在流中的高度扣掉（见 ① 与 BUG-2472 的追记）。
- **已知缺口（合入时记，未阻塞）**：
  - **发货值 `-2em` 本身没被真机实量过**。探针 `_candidates` 只跑过 −0.5 / −1.5 / −3，`-2em` 是被 −1.5 与 −3 夹在中间推出来的；「WebKit 把超出的负 margin 钳掉」这条也只在一台 macOS 15.7（新 ruby 实现）上观察过，**iOS 一轮都没跑**。若哪天某个 WebKit 版本不钳，多出的 0.8em(rt) 会把注音往外推、压到邻行/邻列。更自解释的写法是 `margin-block-start: -1lh`（`lh` = 注音盒自己的行高，语义上就是「扣掉它自己占的那一行」，Safari 16.4+），老 WebKit 不识别会整条丢弃、退回 BUG-2472 原状而不会更糟——换值前把 `-2em` 和 `-1lh` 一起补进探针候选实量一轮。
  - **选择器用直接子 `ruby > rt, ruby > rtc` 是有意的，别"顺手"改成后代 `rt, rtc`**。后代选择器会让 `<ruby><rtc><rt>…` 里的 `<rt>` 连同它外层的 `<rtc>` 各拿一份负 margin，抵消翻倍、注音被推出位；直接子选择器下 `rtc > rt` 拿不到，正好只抵消一次。代价是 `<ruby><span><rt>…` 这类野生标记（`<rt>` 在 HTML 里本就只能是 `<ruby>` / `<rtc>` 的子元素）拿不到抵消，BUG-2472 在那种书上会复发——真遇到再单独按 `ruby rt:not(rtc > rt)` 这类写法收，别整体换成后代。
