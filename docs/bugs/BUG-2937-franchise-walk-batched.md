## BUG-2937 · AI下视频整套：系列查不完时按预算截断交半张清单·应分批续查到走完
- **报告**：2026-10-04（用户看了 BUG-2935 / BUG-2936 的「撞上限就标清单可能不全」后：「不全不应该分片之类的吗」）
- **真实性**：✅ 真问题。`packages/fushi_engine/lib/media/video/discovery/video_franchise.dart` 的 `resolveMalFranchise`（修前 :224 `while (queue.isNotEmpty && visited.length < maxWorks)`，`kVideoFranchiseMaxMalWorks = 150`）把「等太久」这个体验问题做成了**结果截断**：撞上预算就停、交出半张清单再标 `truncated`。预算本来限的是一次等待的时长（Jikan 约 1 秒一个请求），不是清单该到哪为止——关联图是有限的（只走白名单关系、访问过不再走），完全可以接着走完。BUG-2935 / BUG-2936 只是让截断「说出来」，没让它「不发生」。
- **[x] ① 已修复** — 遍历状态收进 `_MalFranchiseWalk`，每批最多 `kVideoFranchiseMalBatch`（40）个请求，交出「到目前为止」的全部结果和续查入口 `VideoFranchise.more`（闭包，只能调一次）；**没有总上限**，走到队列空为止。`truncated` 回到本义：只表示请求 / 来源失败。`mergeVideoFranchises` 与 `loadFranchise` 的失败副本都保留 `more`，联网补全层经合并自然透传。reducer `_onFranchiseLoaded`：本批与草稿 `franchiseDraft` 合并去重，还有 `more` 就说 `franchiseProgress`（到目前为止按范围数出的剧集 / 剧场版数）并发 `VideoAcquisitionContinueFranchiseEffect`，查完才进逐部找资源；服务执行续查，续查抛异常回灌空的 truncated 批（交出已收到的、说清单不全，不卡在找系列）。取消期间迟到的批次按阶段丢弃。i18n 1 条。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/discovery/video_franchise_test.dart`（批满即交、经 `more` 续到走完且每批是累计结果、不重复请求；哆啦A梦真实形状 67 节点默认两批收全 52 部剧场版；在第 60 个请求处分批不再标 truncated；中途失败标 truncated 且无 `more`；合并保留 `more`）；`fushi/test/media/video/acquisition/video_acquisition_franchise_test.dart`（group「分批续查」：报进度 + 续查效果 + 草稿不留入口、最后一批合并去重出清单、续查失败交已收到的、取消后迟到批次丢弃）；`fushi/test/media/video/acquisition/video_acquisition_franchise_service_test.dart`（服务端到端两批走到确认清单、续查抛异常不卡死）。
- **备注**：服务对效果严格串行，所以清单仍在**整张图走完后**才开始逐部找资源；「边查边找资源」要先改服务的并发模型，没做。分批换来的是：不再截断、每批一次进度、随时可取消。哆啦A梦级别（~100 节点）约 2 分钟、2–3 次进度。
