## BUG-2600 · 视频源扩展在 lib 14 宿主 ABI 上进不去剧集或播不了
- **报告**：2026-09-19（用户：「视频源这块很多要么就是进不去列表、要么进不去源、要么都进去了播放不了……典型的就是 anidb 不能播放」；#1549 合入时明确写了「真机未做」）
- **真实性**：✅ 真 bug（用上游 overlay 构建的桌面 sidecar 直接打真实 yuzono APK 取证，脚本范式见下）
  - 野外扩展早已不是 lib 14：yuzono/anime-repo 索引里 239/254 个 `v14.x` APK 的 dex **全部**引用 `getHosterList` / `Hoster` / `seasonListParse`——它们编译的是 `komikku-app/aniyomi-extensions-lib@f5961b5`（2026-08-28，Anikku 系），公开面就是 extensions-lib 16：`Video` 是 data class `Video(videoUrl, videoTitle, resolution, bitrate, headers, preferred, …)`，老构造 `Video(url, quality, videoUrl, …)` 只作 deprecated 兼容；`SEpisode` 多了 `fillermark / summary / preview_url`，`SAnime` 多了 `background_url / fetch_type / season_number`，`AnimeSource` 多了 `getSeasonList / getHosterList / getVideoList(hoster)`。
  - 本仓 vendored 的 `third_party/m_extension_server/upstream_src/.../animesource/**`（桌面 sidecar 与 Android `prepareAniyomiSourceApi` 共用）是老 lib 14 类。实测基线 sidecar：KickAssAnime `getVideoList` → `java.lang.NoSuchMethodError: 'java.lang.String eu.kanade.tachiyomi.animesource.model.Video.getVideoTitle()'`（`sidecar.log:253`，被扩展自己的 `parallelCatchingFlatMap` 吞掉，宿主只看到 0 条视频 = 「进去了播不了」）；AniDB 的 `episodeListParse` 写 `SEpisode.fillermark`，同一类断点落在剧集列表（= 「进不去源」）；`Video.getVideoTitle()` 也是 `sortVideos` 的入口，所有按画质偏好排序的扩展一律炸在取流。
  - 额外事实：anidb.app 本身 2026-09-19 16:20 JST 整站 503「Under Maintenance」（`curl` 同样 503），所以该源当下谁都打不开；这是站点侧，与 ABI 修复无关，恢复后走同一条修好的路。AnimeParadise 热门页 404 是站点改版（扩展侧问题）。Subsplease 之类 torrent 型源返回 magnet 链接，本期播放页不吃 magnet（另立议题）。
  - 宿主侧还缺 Aniyomi 播放器在把 URL 交给 mpv 前必做的两步（Mangayomi 当前上游 sidecar 也做）：`videoUrl` 为空时 `resolveVideo` / lib 14 `getVideoUrl`，以及 lib 16 的 Hoster 展开；原 `MihonVideo.resolvedUrl` 注释「videoUrl 为空时 url 本身就是流地址」是错的。
- **[x] ① 已修复** — 宿主 anime ABI 换成 **lib 14 + lib 16 并集**：`third_party/m_extension_server/overlay/.../animesource/**`（`Video` data class + deprecated 老构造 + `url`/`quality` 兼容槽；`SAnime`/`SEpisode` 新字段；`AnimeSource`/`AnimeCatalogueSource`/`AnimeHttpSource`/`ParsedAnimeHttpSource` 的 lib 16 成员全部 `open` 带默认，`getHosterList` 按反射判「扩展是否实现了 `hosterListParse`」决定走 Hoster 请求还是把 lib 14 视频表包成 `NO_HOSTER_LIST`），新增共用取流器 `animesource/host/AnimeVideoLoader.kt`（Hoster 展开 → `sortHosters` / `sortVideos` → `resolveVideo` → `getVideoUrl`，死候选丢弃、全死才抛第一个真实异常），桌面 `DalvikHandler` 与 Android `MihonChannelHandler` 的 `getVideoList` 都改走它；通道投影加 `videoTitle / resolution / bitrate / preferred / mpvArgs`；安装门 14 / 15 / 16；Android `prepareAniyomiSourceApi` 改为 overlay 叠加 upstream_src；Dart `MihonVideo` 解码新字段、`chooseBestAnimeVideo` 改为「`preferred` 优先、否则扩展排好的第一条」（原「行数最高」会作废扩展设置里的画质偏好）。提交 `9c6c0d61fd`。
- **[x] ② 已加自动化测试** — sidecar `overlay/server/src/test/kotlin/mextensionserver/controller/AnimeVideoLoaderTest.kt`（lib 14 fake 走 `getVideoList`+`getVideoUrl`、lib 16 fake 走 Hoster + 扩展排序 + lazy 不展开、`resolveVideo` 只跑未初始化的且 null 丢弃、死 hoster 跳过 / 全死抛真因、老构造的 `url`/`quality`/未解析语义）+ `AnimeResponseTest.kt`（新通道字段、lib 门 14..16）；Dart `fushi/test/media/manga/mihon_anime_models_and_bridge_test.dart`（lib 16 wire 解码、自报行数优先）、`mihon_manager_media_kind_test.dart`（14 与 16 都装、17 拒）、`fushi/test/media/video/online/anime_source_video_client_test.dart`（`preferred` 优先、扩展顺序优先）。真实扩展取证：`AnimeVideoLoader` 版 sidecar 对 yuzono APK 走「源列表 → 热门 → 详情 → 剧集 → 取流 → 带头 Range 拉流」（探针脚本范式：起 java sidecar、`FUSHI_MIHON_TOKEN`、POST `/dalvik` 带 base64 APK 与 `__mangatan_bridge_context__` 偏好项），结果记在 PR 描述。
