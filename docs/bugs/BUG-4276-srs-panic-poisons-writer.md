## BUG-4276 · SRS 内核一次 panic 后写连接永久毒化，所有写命令报 srs writer poisoned
- **报告**：2026-11-10（内部审查：Rust 内核存储层 panic 后的锁与事务状态）
- **真实性**：✅ 真 bug（沿代码路径确认 + 测试复现，基线 develop `94317ab6295`）：
  - `native/fushi_fsrs/src/store/ffi.rs:135`–`:145`：每个 C ABI 入口 `catch_unwind` 接住 panic、返回 -100，进程不退出，库句柄照旧可用。
  - panic 时持着的连接锁被毒化。`native/fushi_fsrs/src/store/mod.rs:474`–`:479` `writer()` 把毒化映射成永久错误 `"srs writer poisoned"`：之后**所有写命令**（Drift 的 `exec` / `exec_batch`、全部 Rust 写命令、`select` 在 Drift 事务里的分支）都报这个错，直到关库重开；Dart 侧对 -100 不做任何事（`packages/fushi_srs/lib/src/store/srs_core.dart:31` 只有注释，没有重开逻辑），于是整个 app 会话里复习作答、同步、导入全部失败。
  - 读命令：`mod.rs:536`–`:542` `reader()` 同样把毒化映射成永久错误 `"srs reader poisoned"`（读命令里 panic 一次，之后所有内核读命令失败）；而且 panic 发生在 `read_visible_tx`（`mod.rs:561`–`:575`）`BEGIN` 与 `ROLLBACK` 之间时，那条读连接一直停在读事务里，钉住一份旧快照、WAL 并不回主库。`drift_write_reader`（`mod.rs:856`）、只读会话（`mod.rs:242`）、会话表（`:1113` / `:1139`）、收段阶段（`mod.rs:533`，`"ingest session poisoned"`，同步永久失败）同样是永久错误；`ReadSession::close` / `SrsCore::close`（`mod.rs:252`、`:582`–`:598`）却用 `unwrap_or_else(into_inner)` 容忍毒化——策略不一致。
  - 写连接上的残留：`native/fushi_fsrs/src/store/sync2/mod.rs:48`–`:67` `in_savepoint` 在 panic 时不执行 `ROLLBACK TO`，panic 的命令开的 SAVEPOINT（没有外层事务时就是一笔事务）留在写连接上。现在因为写锁永久毒化，没有后续命令能碰到它；但只要把毒化简单地 `into_inner` 放过，下一条命令的写入就会落进这笔半截事务，由它的提交一起交上去。
  - 复现：`native/fushi_fsrs/src/store/panic_recovery_tests.rs` 的测试在基线上全部失败（`after_a_panicking_command_through_the_c_abi_writes_still_work`：经 `ffsrs_store_sync2` 的写命令在 RELEASE 前注入 panic → -100，之后 `ffsrs_store_exec` 写入报 `srs writer poisoned`）。
- **[x] ① 已修复** — 选「库自行恢复到一致状态」而不是「进入必须重开状态由 Dart 重开」。理由：库句柄是句柄表编号，被多个 worker isolate 经 `SrsCore.fromAddress` 缓存（`packages/fushi_engine/lib/srs/srs_core_workers.dart:407`），还有 Drift 执行器、只读会话、迁移 / profile 数据各自持着；Dart 侧可靠地重开要协调所有这些持有者并在重开期间挡住在途命令，范围大且本身易错。而 Rust 侧能精确知道每把锁里的状态该恢复成什么：
  - `native/fushi_fsrs/src/store/mod.rs` `lock_recovering`：库里所有连接 / 会话状态的锁统一经它取；被毒化时先把锁里的状态恢复到命令之间应有的样子、再 `clear_poison`，之后照常可用；恢复失败就保持毒化并报错（不在状态不明的连接上跑命令）。
  - 写连接（`SrsCore::recover_writer`）：连接不在 autocommit 就整笔 `ROLLBACK`（panic 的命令自己开的事务 / SAVEPOINT 一并撤销，与命令报错时等价）；panic 时 Drift 以为有事务开着（`drift_tx`）就整笔回滚并进入 `drift_aborted`：那笔事务后续的语句（含 `COMMIT`、嵌套的 `ROLLBACK TO`）、Rust 写命令、写那一路的查询一律报 `DRIFT_TX_ABORTED`，直到 Drift 发来 `ROLLBACK TRANSACTION`（Drift 2.33 在事务体或 COMMIT 出错时都会发，`connection_user.dart` `rollbackAfterException`）——不让后续语句在 autocommit 下逐条提交，也不让 COMMIT 把半截事务交上去。panic 的正是 Drift 开事务那一条时 `drift_tx` 还没置位（`exec` 跑完才记），Drift 收到的是「开事务失败」、不会发 ROLLBACK，此时只回滚、不进待回滚状态，不会把库卡死。旧库搬迁事务（`legacy_open`）回滚并结束。恢复在取写锁时才跑，所以凡是看 `legacy_open` 的写入口（`legacy_page` / `legacy_commit` / `legacy_abort` / `exec` / `exec_batch` / `profile_purge`）一律先取写锁、再看标志——先看标志读到的是 panic 前的旧值（`legacy_commit` 会在已回滚的连接上发 COMMIT；`exec` 会一直报「legacy import in progress」且永远不取锁、不触发恢复）。`select` / `snapshot_select` 不取写锁、仍在锁外看标志：搬迁中 panic 后到 Dart 调 `legacyAbort`（`srs_legacy_store_migration.dart` 出错即调，且搬迁在任何 `SrsDbStore` 打开前进行）之间它们会报「legacy import in progress」，`legacyAbort` 一取写锁即恢复。
  - 读连接：内核读命令改走读连接池（BUG-4277），借出的连接放回时还停在读事务里就先 `ROLLBACK`，结束不了就关掉不放回（`native/fushi_fsrs/src/store/read_pool.rs` `Pooled::drop`）；`drift_write_reader` 毒化时同样结束残留读事务。只读会话（读事务本就该开着、查询只读）与会话表、写连接页缓存预算这类纯簿记：清掉毒化照常用。收段阶段：毒化时回到 `Idle`（同投递出错时作废会话）。
  - 内存缓存：复习队列会话表（`native/fushi_fsrs/src/store/queue.rs` `with_session`）与浏览会话（`native/fushi_fsrs/src/store/browse.rs` `browse_sessions`）在建 / 增量更新到一半 panic 时整份丢掉、下次整份重建（同出错时丢会话）。
  - C ABI 签名、srs.db 格式都不变；Dart 不需要改（-100 之后照常发命令即可）。
- **[x] ② 已加自动化测试** — `native/fushi_fsrs/src/store/panic_recovery_tests.rs`：经 C ABI 的写命令 panic 后写入照常；Rust 命令写了一半 panic → 半截写入被回滚、之后的命令照常提交且不捎带它（关库重开后仍不在）；Drift 事务里嵌套的命令 panic → 事务整笔回滚、后续语句 / COMMIT / ROLLBACK TO / Rust 写命令 / 写那一路查询都拒绝、ROLLBACK 之后恢复，事务里的写入一条不落库；Drift 开事务那条语句 panic 不卡死库；旧库搬迁中 panic 结束搬迁不提交、且 Dart 没来得及 abort 时 Drift 写语句不被「搬迁进行中」挡住；读快照里 panic 后之后的读看得见新提交（池化读与直接取读连接两条路径）；收段阶段毒化后回到 Idle；复习队列会话在 panic 后整份重建。注入点是仅测试构建的 `store::sync2::test_panic`（`in_savepoint` RELEASE 前、`exec` 语句之后）。
- **备注**：`SrsCore::close` 仍对毒化的锁直接 `into_inner` 后丢连接——关闭时 SQLite 自己回滚连接上没结束的事务，与恢复策略一致（都不提交半截事务）。`StudyHub` 的 `touched`（触发器记下的待重读 id）锁里只有集合插入 / 合并，panic 只可能来自内存分配失败（Rust 下是 abort 而不是 panic），没有单独的恢复。
