## BUG-2941 · 下载合集选集乱序：同步平手取远端冲掉按集号排序
- **报告**：2026-10-04（用户：视频播放器底部「选集」条顺序是 06,02,01,10,05,03,07,04,09,08,11…，截图来自「グロウアップショウ ～ひまわりのサーカス団～ (2026)」）
- **真实性**：✅ 真 bug。本机 DB 只读核对：合集 88 的 `media_collection_items.sort_index` 存的就是这个顺序，`order_updated_at=0`（用户从未手动排序），13 个 nyaa 下载任务（`video_download_jobs.collection_id=88`）的完成先后与之逐项一致，跨 2026-09-11 ~ 09-29 逐集落库，期间合集同步在跑（有配对对端 + 云同步基线）。
  - 根因：每集落库后 `VideoBookRepository.reorderDownloadedCollectionEpisodes`（`packages/fushi_engine/lib/media/video/video_book_repository.dart`）把本机排成集号序，但按设计不动 `orderUpdatedAt`；下一轮合集同步 `CollectionSyncEngine._mergeOne`（`packages/fushi_engine/lib/sync/collection_sync_engine.dart:224` 起「平手取远端」）两端都为 0 → 远端上轮的到达序整表覆盖本机，新集追加末尾 → 写回共享清单。逐集重复即得下载完成顺序。播放器 `video_fushi_page.dart:3128` 只是忠实读 `getCollectionItems` 的落库序。
- **[x] ① 已修复** — 合集清单条目加 additive 字段 `episodeOrdered`（`collection_manifest.dart`，false 不写 key，旧清单读作 false）：下载端 `loadLocalCollectionManifest` 对下载管理的合集（`downloadManagedCollectionIds`：被下载任务 / 订阅指向）打标记，合并 / 云折叠取或随清单传播。`CollectionSyncEngine.merge` 对所有分支的合并结果统一过 `_withEpisodeOrder`：带标记且 orderUpdatedAt 为 0（无人手动排序）时，视频成员按 `orderDownloadedCollectionMembers`（`packages/fushi_engine/lib/media/video/download/downloaded_collection_order.dart`）重排。该函数只依赖 wire 成员键（下载集 bookUid = `video/<文件名主干>`），各端逐字节同序，没有下载任务的设备与云通道「平手取字典序最小」的折叠也收敛；非视频成员原位不动；本机落库整理用同一函数，收敛后零改写。手动排过序（>0）照旧 LWW，非下载合集照旧平手取远端。存量乱序合集在下一轮同步即被重排。（审查发现首版「本机注入派生序钩子」在云通道 per-device 折叠下不收敛，已改为随清单传播标记。）
- **[x] ② 已加自动化测试** — `fushi/test/sync/downloaded_collection_sync_order_test.dart`：用户真实到达序 + 不补零集号（字典序≠集号序），覆盖互联单份清单与云 per-device 文件折叠两条通道；含修复前复现、三端收敛、收敛后零改写、手动序胜、非下载合集不受影响、非视频成员原位、wire 字段向后兼容。
