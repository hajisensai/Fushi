## BUG-693 · 悬浮字幕点词覆盖窗死亡后永久没反应：overlay WebView2 无 ProcessFailed 自愈
- **报告**：2026-07-10（用户：TODO-1268 第四次复诉「还是没反应」；截图为悬浮字幕条 ⏮▶⏭🔒✕+日文句）
- **真实性**：✅ 真 bug（根因 `hibiki/windows/runner/global_lookup_window.cpp` 的 `RenderJson`——修复前把渲染脚本盲发 `webview_->ExecuteScript(..., nullptr)` 且全文件 **0 处** ProcessFailed/活性处理；覆盖窗 WebView2 进程树会话中途死亡后 `webview_ready_` 恒 true、每次点词零 host 消息、READY-SAFETY 只能翻出空白窗，直到重启 app）
- **[x] ① 已修复** — `global_lookup_window.cpp/.h`：`RenderJson` 改为检查 `ExecuteScript` 的**同步 HRESULT + completion 异步 HRESULT**（JS 异常仍是 S_OK，FAILED 只可能是基础设施级死面），任一失败走新增 `RecoverDeadWebView(replay_script)`：缓存脚本进 `pending_json_`、`webview_ready_=false`、`recovering_` 防重入、释放 controller_/webview_/env_ 后 `EnsureWebView()` 原地重建（同一 hwnd_，`ConfigureWebView` 在新实例上重注册全部 handler）；`NavigationCompleted` 重臂 ready、清 `recovering_` 并 flush pending——**发现死面的那一次点词也能补渲染出真词卡**。另注册 `add_ProcessFailed`（三个基础 kind 走同一重建路径）作纵深防御——注意实测 force-kill 进程树时该事件**不触发**（见备注），所以确定性检测必须在 ExecuteScript 调用本身上。分支 `todo1268-float-sub-lookup`。
- **[x] ② 已加自动化测试** — ① CI 层源码扫描守卫 `hibiki/test/lookup/global_lookup_dead_webview_selfheal_guard_test.dart`（5 用例：禁止盲发 ExecuteScript、同步/异步 FAILED 都走自愈、RecoverDeadWebView 契约、NavigationCompleted flush、ProcessFailed 纵深防御）；② 设备层端到端门 `hibiki/integration_test/floating_lyric_tap_lookup_itest.dart`（Windows 离屏真 app：焦点驱动开有声书→原生悬浮条真 WM_LBUTTON 点词→断言 host 驱动 `reveal(box)` 非 READY-SAFETY；**阶段 2 故障注入**：按本次运行隔离 user-data-folder 精确 taskkill 覆盖窗 WebView2 全进程树→再点词→断言自愈后仍出真词卡）。
- **备注**：**为什么此前三轮修复都没解决用户的「没反应」**——BUG-598（BAL）与 BUG-633（touchSlop）只改 Android 原生 overlay，而用户的 Android 机（ColorOS，TODO-1227）连悬浮窗权限都被系统拒绝、条根本显示不出来，用户点的是 **Windows 桌面条**；BUG-578（await hide）只解决桌面连点竞态，但其自己的真机日志里「首个孤立点击（469ms 静默窗口）同样零 host 消息」已证明还有更深根因——正是本条：那份日志的失败签名（`lookupText → searched → showAt → reveal: READY-SAFETY`、零 host 消息、同会话早先热键正常）与本次离屏故障注入复现**逐字一致**。触发源不唯一（WebView2 运行时后台更新、GPU 重置、OOM、渲染崩溃——用户 AMD 机有已知弹窗 WebView WGC 崩溃史），共同点是死后无任何恢复路径。**ProcessFailed 事件在离屏 harness 中对 force-kill 实测 20s+ 不触发**（修复第一版只挂事件、注入后仍 READY-SAFETY(ready=true)，见集成测试演进），故事件只作纵深防御，不作唯一检测。
