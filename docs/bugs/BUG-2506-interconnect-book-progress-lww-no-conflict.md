## BUG-2506 · 互联书籍进度纯 LWW 无冲突判定：host 与 client 分叉时客户端被静默覆盖
- **报告**：2026-09-13（用户：「fushi 服务端和客户端书进度不一致现在好像不会显示冲突，无论是服务端快了还是慢了，客户端都被覆盖了」）
- **真实性**：✅ 真 bug（结构性，自 BUG-417 引入 live 路径起就如此，不是近期回归）。互联 / `SyncBackendType.fushiServer` 通道下，书进度真正在 host DB ↔ client DB 之间交换的是 `fushi/lib/src/sync/sync_orchestrator/books.part.dart` `_syncBookProgressLive`：纯「取较新时间戳」（`resolveBookProgressSync`），胜者直接 `upsertReaderPosition` 盖掉本地，从不产生 `report.conflicts`。而带三方冲突门的 `SyncManager._syncBookOnce`（`sync_manager.dart:229-406`）对互联比较的是 host 上 WebDAV 文件箱的 `progress_*.json`——那个文件只有 client 自己写、host 从不读回也从不写入（`fushi_sync_server/webdav.part.dart` PUT 只落平文件），所以 `remote == base` 恒成立、冲突条件结构上永远为假；冲突对比弹窗（`sync_compare_dialog.dart` `_fetchRemoteBookData`）看的同样是文件箱。雪上加霜：`reader_positions.updatedAt` 同时是书架「最近阅读」排序键，host 上只是打开再关闭这本书、位置未动也会刷新时间戳（`reader_fushi/navigation.part.dart` `_flushPosition` → `ReaderPositionRepository.save` 写 `updatedAt = now`），下一轮 sweep 就在 LWW 里胜出——正是「服务端快了慢了客户端都被覆盖」。
- **[x] ① 已修复** —（本 PR）互联 live 路径改成**按位置基线的三方判定**（不能改成「位置不变就不刷新时间戳」，那会破坏书架 recency）：
  - 引擎层纯函数 `resolveBookProgressThreeWay(local, remote, base)` → `BookProgressSyncAction{synced, pushLocal, applyRemote, conflict}`（`packages/fushi_engine/lib/sync/fushi_library_host_service.dart`）：一端无记录 → 另一端胜；两端位置相同 → 只对齐时间戳；无基线且两端不同 → 冲突（与云通道 SyncManager「无 base 且双边不等 → 冲突」同口径，只发生一次）；有基线 → 只一端偏离基线位置 → 那端胜，两端都偏离 → 冲突。基线 `BookProgressBaseline(sectionIndex, normCharOffset)` 打包成一个 int 落 `sync_baselines(bookKey, 'progress_live')`，与云通道的 `'progress'` 时间戳基线刻意分开（双通道同时启用不互相污染）。
  - 落地层 `fushi/lib/src/sync/interconnect_book_progress_sync.dart` `InterconnectBookProgressSync`（sweep 与弹窗共用）：`pushLocal` 把时间戳抬到 `max(本端, host+1)` 并同步写回本端行——host 端 `putBookProgress` 仍是防御性「取较新」，否则 host 只是重开过书时推送会被静默丢弃、每轮都推每轮都丢；`applyRemote` 落回本端；`alignSynced` 沿用旧的对齐写法；三者都记新基线。
  - `_syncBookProgressLive` 按判定分派，`conflict` 时谁都不覆盖、`report.conflicts.add(SyncConflict(assetKey: bookKey, dimension: 'progress_live', …))`，走既有 `SyncConflictPrompter` → `SyncCompareDialog(conflictsOnly: true)`。
  - 对比弹窗：`backend is InterconnectSyncBackend` 时对「本机有 ∧ host 有」的书按 live 端点取 host 进度（分批 5 并发）、按同一份纯函数得 `SyncCompareEntry.liveAction`；`hasConflict` / `isSynced` / `autoDirection` 优先按它；远端列显示 host DB 的分数与时刻（host 无记录 → 无数据，而不是文件箱里 client 自己上次导出的旧值）；Apply 在 SyncManager 之后（它对互联仍会把文件箱旧进度导回本机）用用户选的那一侧经 `pushLocal` / `applyRemote` 盖正并记基线，且不依赖文件箱那步的成败。
- **[x] ② 已加自动化测试** — `fushi/test/sync/sync_orchestrator_live_progress_test.dart`（真 server + host + client，既有 3 条改成种基线的单边场景，新增 4 条：两端都偏离基线 → 报冲突、两端 DB 都不动、不计 pulled；无基线且不同 → 冲突不静默 LWW；host 只是重开书（时间戳更新、位置在基线）+ 本端读了 → 本端胜、无冲突、推上去的时间戳严格新于 host 旧戳、两端对齐到同一时刻、基线推进；同位置不同时刻 → 对齐 + 记基线 + 无冲突）；`fushi/test/sync/sync_compare_interconnect_live_progress_test.dart`（假互联后端只实现 live 端点驱动真弹窗：分叉行显示 host DB 的 90.0% / 本机 30.0%；host 重开不算冲突→空态；无基线 → 冲突；Apply 选本机 → PUT 到 host、时间戳 > host 旧戳、本机行同时刻、基线 = 本机位置；Apply 选远端 → host 位置落回本机、不推 host、基线 = host 位置）。既有 `sync_compare_conflict_test` / `sync_orchestrator_conflict_test` / `sync_conflict_present_test` / `sync_manager_conflict_test` 全绿。
- **备注**：
  - 升级后第一轮 sweep：两端位置已一致的书直接记基线、无感；此前已分叉的书会**弹一次**冲突让用户选（无基线无法知道谁动了，宁可问一次也不再静默覆盖），之后基线就有了。
  - `SyncManager` 对互联通道的文件箱进度路径仍在跑（dead weight，host 不读），本次未拆——它与 stats / 内容方向判定纠缠在一起，拆开需单独评审。
  - 退出书的单本同步（`sync_auto_trigger.dart` `_runAutoSync`）只跑 `SyncManager.syncBook`、不跑 live 端点，与本次无关：host DB 进度只在 sweep 交换。
