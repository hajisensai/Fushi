## BUG-2085 · SGRE 游戏内卡片制卡恒失败：点击载荷 text_generation 填的是查词捕获代数而非文本行序号
- **报告**：2026-09-03（SGRE 窗口模式真机：游戏内卡片点「+」制卡，`hibiki_glookup.log` 只记 `mine: mineEntry -> reply={ankiConnect: false, noteId: null}`，Anki 没有新卡；工作台里这句台词明明已配到 game_resource 语音）
- **真实性**：✅ 真 bug。host 侧 `fushi/lib/src/lookup/gal_hook_text_overlay_controller.dart:1847` `_resolveIngameMiningLineId`：命中载荷带 `textGeneration`（>0）时按 `entry.sourceSequence == textGeneration` 精确匹配本局会话行，未命中即 fail closed（这是有意的 occurrence 身份门，不许用同文/包含关系冒充当前句）；`sourceSequence` 来自文本 IPC `TextSlot.seq`（`gal_hook_session_controller.dart:2337`）。而 `native/galgame_hook/hook/adapters/sgre_lookup.inc:1865`（修前）`PublishSgreLookupHit` 把 `publication.text_generation = capture_generation`——那是查词捕获的逻辑代数（本局 11），与该句在文本通道的写入序号（#43）是两个计数器，永远对不上。HUNEX 适配器填的是 `model.selected_text_seq`（正确契约）。
- **[x] ① 已修复** — `SgreLookupCapture` 增 `text_seq`；`PublishSgreExactText` 返回本句的文本通道 seq（新句 = 本次写入序号，重绘同文 = 保留上次序号，`g_sgre_last_text_seq`），`CaptureSgreLookupDrawState` 写进快照，`PublishSgreLookupCaptureSnapshot` / `AppendSgreLookupCapture` 透传；`PublishSgreLookupHit` 新增 `text_seq` 参数，`text_generation = SgreLookupHitTextGeneration(text_seq, capture_generation)`（有文本序号用文本序号，没有才退回捕获代数保持载荷合法）；调用点在 `IsSgreLookupPayloadCurrent` 钉住代数后取 `g_sgre_lookup_active_capture.text_seq`（本提交）。
- **[x] ② 已加自动化测试** — `native/galgame_hook/tests/sgre_adapter_test.cpp`：`SgreLookupHitTextGeneration(43, 11) == 43`、`(0, 11) == 11`（本提交）。真机复验：窗口模式点「+」后 Anki 出现新卡。
- **备注**：Siglus 适配器 `siglus_lookup.inc:1307` 同样填 `geometry_generation`，按一引擎一任务另开。
