## BUG-2508 · macOS 阅读器 Shift 悬停查词无反应（WebKit 只在 WKWebView 为最顶命中视图时才派发 mousemove）
- **报告**：2026-09-11（用户：「mac端shift不能查词」）
- **真实性**：✅ 真 bug（沿真实代码路径定位，2026-09-13 Mac 真机复现，见备注）。阅读器的 Shift-悬停查词此前**只有一条腿**：正文 WebView 文档内的 JS `mousemove` 监听（`fushi/lib/src/pages/implementations/reader_fushi/webview.part.dart:1499` → `callHandler('onShiftHover')`），门控靠 `e.shiftKey`。这条腿在 macOS 上收不到事件：
  - WebKit 把 WKWebView 的 `mouseMoved:` 交给 `WKMouseTrackingObserver`，它先对窗口 contentView 做一次 AppKit 命中测试，**只有命中视图是 WKWebView 的后代**才把事件交给页面（WebKit `Source/WebKit/UIProcess/mac/WebViewImpl.mm` `-[WKMouseTrackingObserver updateViewIsTopmostAtMouseLocation:]` / `mouseMoved:`）。
  - Flutter macOS 嵌入层把「排在平台视图之后的 Flutter 绘制」的 paint region 写进 `FlutterMutatorView._hitTestIgnoreRegion`，落在其中的点 `hitTest:` 返回 nil（`engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterMutatorView.mm`）——这是 BUG-1692 已定性的同一机制。BUG-1692 只修了「点击」并按当时的 chrome 收紧了忽略区；悬停走的是另一条更严的门（命中测试 + tracking area 仅 key window 激活），且 2026-08-17 之后阅读器 chrome 又整体改成 ッツ 形态（顶部工具栏 / 进度线 / 状态行 / 悬停热区），任何一块在 WebView 之上的绘制都会让该区域的 DOM `mousemove` 消失，而 JS 腿是**唯一**一条腿。
  - **真机坐实（2026-09-13，macOS 27.0）**：门不过的直接原因比「忽略区」更粗——desktop_drop 的 `DropTarget`（整窗 `NSView`，`third_party/desktop_drop/macos/Classes/DesktopDropPlugin.swift` `vc.view.addSubview(d)`）是 `FlutterViewWrapper` 里**最顶**的子视图，压在 `FlutterView` 与其全部平台视图之上：`contentView.hitTest` 在正文任何一点都返回 `DropTarget`（命中链 `DropTarget < FlutterViewWrapper < NSVisualEffectView < NSThemeFrame`），WKWebView 永远不是最顶视图，正文 DOM 的 `mousemove` 计数恒 0。点击不受影响：`mouseDown` 沿响应链到 `FlutterViewController` 再由引擎转发给平台视图（真 NSEvent 点击 → DOM `mousedown`=1、弹窗出现）。所以 JS 腿在 macOS 上**整窗**是死的，与 chrome 布局无关；忽略区只是第二道门。
  - Windows 不受影响：fork 的 WebView2 是 Flutter 纹理，指针先到 Flutter 再由 fork 逐个转发（`packages/flutter_inappwebview_windows/.../in_app_webview.cpp` `setCursorPos` → `SendMouseInput`），Chromium 从真实键盘状态取 `shiftKey`。
  - 附带：与视频页 BUG-880 相同的「光标停在词上不动、按 Shift 不出词」在阅读器上从未修过（两条腿都只在指针移动时派发）。
- **[x] ① 已修复（2026-09-13 macOS 真机验收通过，证据见备注）** — 给阅读器补一条**宿主（Flutter）侧**的腿，两条腿按 `hostOwnsWebViewHoverLookup`（`fushi/lib/src/focus/webview_key_bridge.dart`，**只有 macOS**）互斥（BUG-2031 纪律：一平台一条腿）。首版 PR #1450 用 `!hostOwnsWebViewPointerInput` 反推，把 Android / iOS / Linux 的 JS 腿也顺带关掉、且 Shift 按下反查在 Windows 上抹掉键盘选区，审查打回后返工为：
  - `fushi/lib/src/focus/webview_key_bridge.dart`：新增 `hostOwnsWebViewHoverLookup => isMacOSPlatform`，与鼠标按下所有权 `hostOwnsWebViewPointerInput` 同处定义、分开讲清两者机制不同（tracking-area 的 mouseMoved vs hit-test 的 mouseDown）。
  - `fushi/lib/src/reader/reader_host_hover_lookup.dart`（新）：`ReaderHostHoverLookupGate` 门控（Shift **或**「悬停即查词」）+ 8px 节流 + 静止反查锚点，语义与 JS 腿逐字对齐；`readerHostHoverPointInside` 盒内判定。
  - `fushi/lib/src/pages/implementations/reader_fushi/webview.part.dart`：**只在** `hostOwnsWebViewHoverLookup` 平台把正文 `InAppWebView` 紧包 `MouseRegion(opaque: false)`（`localPosition` == CSS 视口坐标，不改任何命中），其余平台不装、连位置都不记；引擎配置下发 `hostHoverLookup: hostOwnsWebViewHoverLookup`，文档内 `mousemove` 腿按 `window.__fushiHostHoverLookup` 让路。macOS 嵌入层在每个鼠标事件上同步修饰键（`FlutterViewController.dispatchMouseEvent` → `syncModifiersIfNeeded`），故 `HardwareKeyboard.isShiftPressed` 在 hover 时可靠，哪怕 WKWebView 持有 first responder。
  - `fushi/lib/src/pages/implementations/reader_fushi_page.dart`：`onDismissBarrierHover`（弹窗开着时唯一的 hover 入口）与正文 `MouseRegion` 共用同一把门控/节流（`_hostHoverLookupAt`）；`_applyHoverAutoLookupLive` 把开关随 `__hoverAutoLookup` 一起下发给歌词页（独立文档，`lyrics_mode_html.dart` 的 mousemove 腿同样让路）；`_triggerShiftLookupAtLastPointer`：Shift 按下在最后指针位置直接查词（对齐视频页 BUG-880），**两道门**：非宿主腿平台直接返回（Windows 按 Shift+方向 / Shift+滚轮 / 含 Shift 快捷键不得被宿主抹掉选区——JS `selectText` 命中空白 `clearSelection`、命中别的词换词）；光标模式激活（`_focusNavEnabled && _caretActive`）不查（Shift+方向是键盘扩选，按下沿正是扩选起点，视频页没有光标选区，「对齐」不能无条件）。
  - `fushi/lib/src/pages/implementations/reader_fushi/caret.part.dart`：`_handleKeyEvent` 入口处 Shift `KeyDownEvent` 触发上述反查，不消费按键。
  - `fushi/lib/src/reader/reader_engine_config.dart`：新增 `hostHoverLookup`（默认 false = 维持 JS 腿）。
- **[x] ② 已加自动化测试** — `fushi/test/reader/reader_host_hover_lookup_test.dart`：门控/节流/锚点/盒内判定的纯行为测试 + `ReaderEngineConfig` 序列化 + 接线守卫（MouseRegion 只在宿主腿平台条件包裹且 `opaque:false`、平台判据钉死 `=> isMacOSPlatform` 且两处接线文件不得出现 `!hostOwnsWebViewPointerInput`、正文/歌词 mousemove 腿入口让路、barrier 与正文共用门控、Shift keydown 反查的两道门按语句顺序钉死、exit 清位置的弹窗例外）。reader 页含真实平台视图，hover/keydown→JS 无法在 widget 测试驱动，接线部分按源扫描（与 BUG-880 守卫同范式）。
- **备注**：**macOS 真机验收（2026-09-13，Mac mini macOS 27.0，可见窗口 1470×867，`fushi/integration_test/macos_reader_shift_hover_itest.dart`，日志与正文快照存 `.codex-test/computer-use/bug-2508/`）**：输入经 Runner 的 `app.fushi.test/input` 钩子（`FUSHI_TEST_INPUT` 门控）送真实 `NSEvent`——点击 / flagsChanged 走 `NSApp.postEvent`，hover 直接交 `FlutterViewController.mouseMoved`（AppKit 只给 WindowServer 事件派 tracking area，ssh 会话又无辅助功能授权投不了 CGEvent；这一跳靠 Flutter 自身 hover 在 macOS 上普遍可用的事实兜底）。结果：⓪ 真点击 testword → DOM `mousedown`=1、弹窗出（对照）；① 按住 Shift 横扫 → 弹窗出、释义 `testword + FushiGeneratedTestDict …`、正文快照见高亮，DOM `mousemove`=0、命中视图 DropTarget；③ 松开 Shift 纯悬停不出词；② 光标停在词上按 Shift → 弹窗出；④ 「悬停即查词」开着纯悬停出词；`All tests passed`。**未在真机跑**：歌词模式（同一条 `_applyHoverAutoLookupLive` 下发、只有源码守卫）、光标模式 Shift+方向不出词（源码守卫钉两道门）、Windows 行为不变（源码守卫：不包 MouseRegion）。钩子取证时踩到两处引擎细节：`NSEvent.keyEvent(.flagsChanged)` 与鼠标事件的 Shift 必须同时带设备位 `0x2`（嵌入层按设备位分左右 Shift，只给 `0x20000` 会判成左 Shift 抬起）；`LiveTestWidgetsFlutterBinding` 默认丢弃设备来源指针事件，须 `shouldPropagateDevicePointerEvents = true` 且在 body 内 finally 复原。既有事实文档 `webview_key_bridge.dart` 写「macOS 上 Flutter 的 Listener 在 WebView 区域一个事件都收不到」——那讲的是命中测试路径的按下事件，tracking-area 的 mouseMoved 是另一条机制，推理成立但只有真机能裁决。已知取舍：弹窗开着时指针移到弹窗本体上再按 Shift，会用最后一次落在正文/barrier 的位置反查（barrier 是 `Listener` 无 exit 回调）；用 Esc 关弹窗且鼠标不动再按 Shift，会用关弹窗前的旧位置反查（弹窗关闭无现成钩子清位置，鼠标一动即刷新，可后补）。
