## BUG-4757 · MIUI 熄屏耗电检查杀进程（ScreenOffCPUCheckKill）被当成闪退
- **报告**：2026-11-12（应用内闪退报告 Z9FwhY9377，小米 Android 13，3.3.0；拍板台 Z9FwhY9377 拍「做」）
- **真实性**：✅ 真 bug。`ApplicationExitInfo` 记 `reason=OTHER`、`description="ScreenOffCPUCheckKill over +25m0s475ms used +45m1s910ms (180.07031%) threshold 6.0"`、importance=125（前台服务）——这是 MIUI / HyperOS 熄屏耗电检查主动杀进程，平台给了明确原因。根因 `fushi/lib/src/diagnostics/previous_exit_log.dart` `androidExitKind`：`OTHER` 只认 AOSP 权限变更与 OPlus `o-stop` 两种描述，MIUI 这条落到 null，交回会话标记推断；标记停在 `inactive` / `launching`（无界面引擎收不到生命周期）时按 125 判前台 →「停在前台时没了，疑似闪退」弹报告；标记停在 `paused` 时（本例；BUG-4266 之后）则判成「多半是系统回收」，同样丢了平台给的原因。
- **[x] ① 已修复** — `androidExitKind` 认开头锚定的 `ScreenOffCPUCheckKill` 描述为 `vendorStopped`（不弹闪退报告，真 CRASH / ANR 照样压过它）；新增 `androidExitSevere`，这条记录走 `log`（用户可见错误日志）而不只进诊断段，耗电问题不因不弹报告而藏起来。耗电本身（25 分钟用 45 分钟 CPU）的定位：每 30 s 的 `cpu=` 只覆盖死前最后几个窗口（本例那时全进程只有 0.1～0.2 s / 30 s，已闲），`threadCpuProbe` 加 `cpuSum=`——进程自启动以来的累计 CPU（`/proc/self/stat`，含已退出线程）与累计最多的 3 个线程组，下一份样本即可看出整段时间里是哪条线程在吃 CPU。提交见 PR。
- **[x] ② 已加自动化测试** — `fushi/test/diagnostics/previous_exit_log_test.dart`（ScreenOffCPUCheckKill + 标记 inactive / paused → vendorStopped 不上报、记录 severe、不压过真 CRASH、正则锚定正反例）；`fushi/test/diagnostics/native_attribution_probe_test.dart`（`describeCumulativeCpu`）。
- **备注**：耗电根因（CPU 花在哪条线程）本次证据不足以定位——死前采样里本进程所有线程合计几乎不吃 CPU，与 MIUI 读数矛盾，需带 `cpuSum=` 的新样本；WebView 沙箱渲染进程是独立进程，不在 `/proc/self` 里。真机复测未做。
