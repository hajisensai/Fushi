## BUG-3274 · 视频页换词时查词弹窗先闪「未找到」、滑动掉帧
- **报告**：2026-10-13（用户：群反馈，Windows 触屏设备，启用 38 本词典；「トランクルーム将近三秒才出来」「查出来太慢了有时候还能看到一会儿『未找到搜索结果』」；开发者：「我电脑都掉帧，这个查词框滑动」。附两段录屏 + 一张截图）
- **真实性**：✅ 真 bug，三段根因：
  1. **假空态**：换词复用热槽时 `DictionaryPopupController.beginTop` 把结果复位成搜索期占位单例并把层设为不可见（`fushi/lib/src/pages/implementations/dictionary_popup_controller.dart:492`）。层不可见 ⇒ `popupLookupPending` 为 false ⇒ 推给页面的是 `lookupPending=false` 的空结果，popup.js 把它当「查完为空」画成「未找到」留在 DOM 里（修复前 `fushi/assets/popup/popup.js:7030`）。结果渲染一旦超过 1.8 s 兜底（`dictionary_popup_controller.dart:262/744`），层被强制翻可见，用户看到的就是这层旧 DOM。
  2. **渲染慢 + 滑动掉帧**：真引擎 + 真词典实测（安装版词库，27 本 term + 10 freq + 1 pitch，maxTerms=10）：C++ 查询 + Dart 构建合计冷页约 0.5 s、热查询 < 60 ms，不是瓶颈。トランクルーム 的 popupJson 2.1 MB（とる/取る/摂る 各带一份『明鏡』とる 的 32 万字节释义——トラン 去屈折成 とる 的否定形，与 Yomitan 一致），渲染出约 3.9 万节点、内容高约 4 万 px。尾批每追加一块词典卡就合帧铺一次 masonry（修复前 `popup.js:5508`），相 1/相 3 的几何读把整页新内容同步排版；Chromium 4 倍降速（≈平板）下尾批 4.4 s、单帧最长 600 ms，Layout 2170 ms、样式重算 972 ms。弹窗滚轮是 JS 驱动的缓动滚动（document 级非 passive wheel 监听），主线程一忙就成块卡顿。
  3. masonry 每次问列数都走 `getComputedStyle(document.documentElement)`（修复前 `popup.js:6797`），整页样式重算，CPU profile 里占尾批主线程约 1/8。
- **[x] ① 已修复** — ① 占位单例注入 `window.lookupIdle`（`popup_settings_injection.dart` `buildPopupEntriesJs` + `dictionary_popup_webview.dart` `_pushResults`），popup.js 空闲占位只画空占位盒（`popup.js` renderPopup 占位分支）。② 已渲染内容超过两屏后，再追加的尾批词条加 `content-visibility: auto`（`popup.css` `.entry.fushi-lazy-entry` + `popup.js` `__fushiMarkLazyEntry`），屏外词条跳过样式/布局/绘制；masonry 不碰被跳过的词条（`layoutMasonry` 首行判 `__fushiBodyRenderSkipped`），`contentvisibilityautostatechange` skipped=false 时就地铺好并复报高度；历史页回退恢复滚动位时不延迟；不支持该事件的引擎行为不变。③ 列数先读内联 `--dict-columns`。实测（Chromium 4 倍降速，トランクルーム）：全部画完 4.4 s → 1.2 s，Layout 2170 → 341 ms，样式重算 972 → 53 ms，单帧最长 600 → 383 ms；1 倍速 0.79 s → 0.26 s。借りる（0.4 MB）1.3 s → 1.1 s。少量结果（不足两屏）不走延迟路径，高度上报序列与旧版逐值一致；10 个词条逐个滚到截图 + 程序化校验零重叠、零隐藏卡片，布局与旧版一致。
- **[x] ② 已加自动化测试** — `fushi/test/pages/popup_lookup_perf_bug3274_test.js`（+ `.dart` 驱动，Node 真执行 popup.js：空闲占位不画「未找到」/ 查完为空仍画；跳过渲染的词条零几何读、滚进视口后就地摆位；列数不调 getComputedStyle；修复前第一条即红）；`fushi/test/pages/dictionary_popup_lookup_pending_test.dart`（`lookupIdle` 注入与接线）。
- **备注**：
  - 已知取舍：深滚到『明鏡』とる 这类数万节点的词条时，排版成本落在它第一次进入视口的那一帧（4 倍降速约 0.75 s，旧版同样的成本在打开后的前几秒里分多帧付）。试过空闲时预渲染，巨型词条本身是不可拆的整块排版，空闲时做照样撞上用户滚动，还让每次查词在视频播放时后台烧 CPU，已撤回。真正降这部分成本要么按 id 去重同一份释义（2.1 MB 里 1.14 MB 是重复），要么巨型释义默认收起/懒建，另立项。
  - 首词条同步渲染（4 倍降速约 230 ms，含解析 2 MB 注入串）与冷页 FFI（约 0.4 s）仍在；平板上首屏可见时延主要由这两段构成。
  - 未在用户 Windows 触屏真机上复测；装置是本机 Chromium（与 WebView2 同引擎）+ 真词典导出的真实 popupJson，脚本在 `D:/hibiki-tmp/popupbench/`（不入库）。
- **第二轮（2026-10-13，PR #2110 合并后用户要求「还没解决的问题得先解决」）**：
  - 补测量：装置注入真实词典样式表（安装版 13 本带 styles.css）后，修复前 4 倍降速尾批要 9.8 s、单帧最长 1.7 s；v1（#2110）尾批 1.34 s，但滚进『明鏡』とる 这类词条单帧仍 0.8–1.8 s。
  - 根因 a（双排版）：屏外词条滚进视口时先按 CSS grid 列宽排一遍，`__fushiOnLazyEntryVisibility` 里 masonry 改成瀑布流列宽又整体重排一遍（v1 `popup.js` layoutMasonry 相 2）。修：被跳过渲染期间就把列宽预写好（只写样式不读几何，`layoutMasonry` 的 presize 分支 + `__fushiMasonryBodyWidth`），可见时只排一遍；事件处理从 ~330 ms 降到 ~60 ms。
  - 根因 b（不可拆的整卡排版）：成本是文字量本身——对照实验里去掉整份 popup.css 也只从约 470 ms 变成约 480 ms（1 倍速），不是某条昂贵选择器。修：长释义切块按需渲染（`__fushiChunkLongGlossary`）：正文 ≥300 字的卡片，把**已有的块级子元素**标成 `.fushi-lazy-chunk`（`content-visibility:auto` + 按字数估的 `contain-intrinsic-size`）；**绝不插包装**（会让词典 CSS 的 `>` / `+` / `:first-child` 失配、包进行内元素还改断行），「文字 + `<br>`」平铺正文因此不切；`li` 永不切，词典样式 / 用户 CSS / 正文内联样式含 `counter` 或 `list-item` 的整张卡不切（style containment 会把计数器圈成新实例）。段一进入浏览器预渲染区（`contentvisibilityautostatechange` skipped=false）就立刻摘类名回普通渲染（`__fushiReleaseLazyChunk`），containment 只作用于从没进过视口的部分。
  - **只在 Blink 切块**（UA 含 `Chrome|Chromium|Edg/`）：Mac 真 WebKit（macOS 27.2 WKWebView）实测摘掉 `content-visibility` 后不重建渲染对象，containment 期的独立格式化上下文残留，子元素外边距从此不向外合并——『明鏡』とる 卡内正文整体下移 1.125 px（偏差量 = 子元素外边距，换词典可达 1em），强制整页重排不恢复，只有 `display:none` 重建才恢复。Gecko 未验证，同样不切。词条级按需渲染、列宽预写、空闲预热在 WebKit 上照常生效。
  - 空闲预热（`__fushiWarmLazyContent`）：尾批建完后按字数预算（每步 800 字）自上而下把仍被跳过的词条与段转回普通渲染；用户滚动中暂停、停下 200 ms 后继续（扩展里弹窗在 shadow root，额外在弹窗根上挂 scroll 监听），换代即停；WebKit 没有 `requestIdleCallback`，走 setTimeout 回退。
  - 首屏：词条 JSON 改为 `JSON.parse(<字符串字面量>)` 注入（`buildPopupEntriesJs`，失败时 `console.warn`），2 MB 时 4 倍降速 347 → 236 ms。
  - 实测（Chromium 4 倍降速 + 真实词典样式，トランクルーム，三次中位数，最终版）：「打开 1 秒后边读边滑到底（40 次滑动、每次停 1.5 s）」最长帧 修复前 850 / #2110 1817 / 本轮 333 ms，长帧（>50 ms）总计 5884 / 3450 / 1583 ms；「打开就马上滑」最长帧 717 / 800 / 333 ms，长帧总计 3284 / 1617 / 1634 ms（这段时间主线程主要被尾批建 DOM 占着，与 #2110 持平）。本机当时有其他会话并发，单次测量噪声可达数倍，只认中位数与同时段交替对比。
  - 等价性（预热完成后逐屏截图与修复前逐像素对比）：Chromium 62 屏 61 屏完全一致、1 屏 8 个像素抗锯齿级差（最大通道差 6/255），总高 43107 px 相同；**Mac 真 WebKit**（WKWebView，锁屏下用私有 `_setWindowOcclusionDetectionEnabled:` 关遮挡检测让页面 visible、rAF 正常）68 屏**全部逐像素一致**，总高 47238 px 相同；两端 10 个词条零重叠、零隐藏卡片。只看首个词条时的高度上报 196 → 821 → 805（修复前 196 → 254 → 805），过渡值多 16 px 预估误差。
  - 测试：`popup_lookup_perf_bug3274_test.js` 增 4a–4d（块级标记 / li 不切 / WebKit UA 不切 / counter 词典与内联 counter 不切 / 平铺正文 DOM 不动 / 进预渲染区即释放 / 预热释放全部段 / 滚动中暂停预热）；`popup_kanji_card_static_test.dart` 注入字面量守卫改认 `JSON.parse`。
  - 仍有的取舍：一屏新内容第一次出现的排版成本（4 倍降速约 50–250 ms）是固有的，只能靠预热提前付；iOS / macOS 不切段，深滚到巨型词条时仍按整个词条付排版（与 #2110 相同）；「文字 + `<br>`」平铺正文（如日本国語大辞典）不切；用户在预热完成前离开历史页时，记录的滚动位基于部分预估高度，回退恢复可能有偏差（#2110 审查意见 2，影响面小，未改）。首次查某个词的冷页 FFI（按词随机 I/O）未改：启动时已有 `_warmUpSearchAfterFirstFrame` 预热索引与去屈折表。
