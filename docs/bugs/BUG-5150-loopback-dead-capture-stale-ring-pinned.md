## BUG-5150 · loopback 采集线程自行退出后，环里的旧声音仍被当成「最近 N 秒」交出去；常驻的跨应用语音缓存从此再也起不来
- **报告**：2026-11-22（审查 PR #4086 design-cross-app-audio-desktop 时沿代码路径发现）
- **真实性**：✅ 真 bug。系统混音 loopback 的采集线程在 `GetNextPacketSize` 失败（输出设备被拔掉 → `AUDCLNT_E_DEVICE_INVALIDATED`）时跳出循环、`running=false` 后退出（`fushi/windows/runner/audio_loopback_capture.cpp` 采集循环 `if (FAILED(capture->GetNextPacketSize(&packet))) break;`），但这一路仍留在注册表里、租约也还在；`GrabFromSession`（同文件 `:315`）只看 `format.ok` 与 `filled`，于是 `GrabRecent` / `PinSnapshot` 把退出那一刻之前的环（可能是几小时前的声音）当成「查词前最近 30 秒」交出去，挂到卡上当句子音频（错误结果）。同来源只有下一次 `Start` 才会走 stale 分支重起（`:660`）——galgame 会话每次都会重新 start，但 PR #4086 新增的跨应用语音缓存是整个 app 生命周期常驻的持有方，从不重新 start，拔一次耳机之后就一直交旧声音、再也恢复不了。
- **[x] ① 已修复** — `GrabFromSession` 在这一路采集线程已退出（`!running`）时什么都不给（galgame 的 `grabRecent` 同样不再拿到旧声音）；`PinSnapshot` 多一个出参 `stopped`，通道 `pinSnapshot` 回 `{error, code: stopped}`。Dart `LoopbackGalAudioSource.pinSnapshot` 返回 `({id, captureStopped})`；`CrossAppAudioCapture._snapshotDesktop` 见到 `captureStopped` 时（串行化地）对自己持有的同一个 source 重新 `start`——native 走既有的 stale 分支重起一路并把旧租约迁过去，之后的查词照常取得到声音。起不来（此刻没有输出设备）只留痕，下次查词再发现。
- **[x] ② 已加自动化测试** — `fushi/test/mining/cross_app_audio_capture_test.dart`「a capture thread that died never pins stale audio and gets restarted」（替身 `fushi/test/mining/fake_loopback_native.dart` 加 `captureDead`，语义照 native）：死掉那一路不出快照、随后重新 start、新租约到手后交回旧的、再查词有快照。native 侧 `GrabFromSession` 的 `running` 判据没有纯数据结构可单测（要真 WASAPI 线程），已用 MSVC `/W4 /WX` 编译 `audio_loopback_capture.cpp` 与 `flutter_window.cpp`。
- **备注**：默认输出设备**切换但旧设备仍在**（例如插上耳机但扬声器没被移除）时，系统混音 loopback 仍绑在启动时的旧端点上、录到的是静音（不是旧声音），`prepareCrossAppSentenceAudio` 整段静音返回 null，卡照常制、不带句子音频。跟随默认端点切换（`IMMNotificationClient::OnDefaultDeviceChanged` 重开）未做，是 galgame 会话也有的既有限制；真机未验证。
