## BUG-5087 · sync-video-sweep-tests-teardown-temp-locked
- **报告**：2026-11-21（用户：拍板台执行代理在 other-sync-peer-version-errors 分支跑定向测试时发现）
- **真实性**：✅ 在 origin/develop（77a0a0ad80）源码上 Windows 本机 `--concurrency=1` 复现：
  `test/sync/interconnect_video_resume_stale_cache_test.dart:170`、
  `test/sync/sync_orchestrator_live_progress_test.dart:198`、`test/sync/video_watched_mark_sync_test.dart`
  的 tearDown 里 `work.delete(recursive: true)` 抛 `PathAccessException`（errno 32，文件被占用）。
  断言本身都过，只是 tearDown 删临时目录时目录里还有文件被打开着；同一轮里失败的用例数在 4～5 条之间
  浮动。初判（已由下方「根因」取代）：疑为视频 sweep 路径在测试结束时仍持有临时目录里的文件句柄（server / 客户端 DB /
  某个未 close 的下载或日志文件）。
- **根因**：`FushiSyncServer` 停机不等它自己发起的视频指纹计算收尾。host 收到视频清单请求就 `_videoFingerprintWarmer?.request()`（`packages/fushi_engine/lib/sync/fushi_sync_server/video.part.dart:19`，origin/develop cbdc2a45ed），预热在 `Isolate.run` 里整文件读视频算 SHA-256，算完经 `VideoFingerprintStore.put` 往 sync-data 旁写 `video_fingerprints.json`（tmp + rename）；`/fingerprint?wait=0` 也会 fire-and-forget 开算（同文件 `:724`）。而 `stop()`（`packages/fushi_engine/lib/sync/fushi_sync_server.dart:1232`）调的 `_stopVideoFingerprintWarmup()`（`video.part.dart:1865`）只做 `VideoFingerprintWarmer.dispose()`，后者按设计「不等在算的那个」（`packages/fushi_engine/lib/media/video/video_fingerprint_warmer.dart:106`）。于是 `stop()` 返回时后台 isolate 仍开着视频文件、随后还会写缓存文件：测试 tearDown 紧接着删临时目录，Windows 上就报 errno 32（视频 / 缓存文件被占用）或 errno 145（删的期间又写进了文件）。生产上同样违约：停 host / 换端口重启后旧实例仍在读用户视频、仍可能写缓存。与 BUG-5078 同一根因（红的都是种了 host 视频文件、跑过视频清单的用例）。
- **[x] ① 已修复** — `VideoFingerprintWarmer` 新增 `close()`（`dispose()` + 等当前这一轮收尾），两文件间的歇息改成可被 `dispose()` 立即结束的 Timer；`VideoFingerprintStore` 新增 `idle()`（等在途的加载与 `put` 落盘）；`FushiSyncServer` 登记 `/fingerprint` 端点发起的每次计算（`_trackVideoFingerprintWork`），`stop()` 改为 `await _stopVideoFingerprintWarmup()`：等预热关闭 → 等登记的计算 → 把缓存从指纹实例上摘下 → 等缓存 `idle()`。返回后本 host 不再开着任何视频文件、不再写缓存。代价：停 host 最多等正在算的那一个文件（app 退出路径 `shutdownForExitFast` 本来就不等 `stop()`，不受影响）。为了能在测试里控住计算，`FushiSyncServer` 加了 `@visibleForTesting videoFingerprints` 注入口（默认仍是 `VideoSourceFingerprint.instance`）。分支 claude/fix-win-test-teardown。
- **[x] ② 已加自动化测试** — `fushi/test/sync/interconnect_video_fingerprint_test.dart` 组「BUG-5078 / BUG-5087：host 停机等指纹计算收尾」（清单触发的预热、`wait=0` 转后台的计算两条：计算卡在闸门上时 `stop()` 不得返回，放行后缓存已落盘）；`fushi/test/media/video/video_fingerprint_warm_test.dart` 两条（`close` 等在算的文件与落盘；歇息中 `close` 立即结束）。变异实测：把 stop() 改回只 dispose() 不等、VideoFingerprintWarmer.close() 改回不等当前轮，两份测试 22 条里恰好这 4 条新用例变红（+18 -4，exit 1），撤回变异后全绿。原来红的三份 sync 测试本身也是回归覆盖。
- **备注**：验证（Windows 本机，`--concurrency=1`）：修复前 origin/develop 源码上 `sync_orchestrator_live_progress_test` + `interconnect_video_resume_stale_cache_test` + `video_watched_mark_sync_test` 共 45 条 `+42 -3`，三条都红在 tearDown 删目录 errno 32；修复后这三份加两份新测试 5 个 suite 67 条全过（exit 0，json 核对 5 suite / 67 success），再单跑三份 sync 一轮：45 条全过（exit 0）。测试自己的 tearDown 顺序（先 `server.stop()` 再删目录）原本就对，没改。
- **审查补修（PR #4073）**：只登记还不够——`stop()` 先 `close(force: true)` 关监听，但已进 handler 的 `/fingerprint` 请求还在 `await svc.resolveVideoFile(...)`；它若在 `stop()` 排空登记之后才解析完文件，就会在 `stop()` 返回后再开算、再开视频文件。改为先关闸再排空：`_stopVideoFingerprintWarmup` 第一步置 `_videoFingerprintsClosed`，端点经 `_startVideoFingerprintWork`（检查闸门 + 开算 + 登记同步完成）开算，闸已关回 503（暂时不可用，不是「担保不了字节」的 unavailable 状态码）。回归测试：`interconnect_video_fingerprint_test.dart`「停机后才解析完文件的在途请求不再开算」（库查询卡在闸门上时 stop，放行后断言没开算、没写缓存；撤掉闸门即红）。
