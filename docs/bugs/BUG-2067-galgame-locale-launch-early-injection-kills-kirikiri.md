## BUG-2067 · 转区（Locale Emulator）拉起 + 早注入让 x86 KiriKiri 游戏进程随即死亡，退回附着才可用
- **报告**：2026-09-03（代理真机验证中发现；用户库里 9-nine Episode 1 的转区档位是 `auto`，Limelight 在驱动测试里也按 `auto` 拉起时复现）
- **真实性**：✅ 真 bug，但根因**不在早注入**。同一台机器上三种组合的证据：① 注入器 `--launch <exe> --workdir <dir> --hold`（不带 `--japanese-locale`）拉起 9-nine：`OK hooked`、LunaHook 连接、游戏存活；② 带 `--japanese-locale` 拉起 9-nine：注入器打 `[locale] launched with Japanese CP932 via Locale Emulator pid=…`、`[resume] pre-discovery primary thread resumed (initial suspend count=1)` 之后，进程在 0.5s 内消失，Windows 应用程序日志记 `nine_kokoiro.exe` APPCRASH `0xC0000005`、出错模块 `unknown`、偏移 `0x00fe52d0` / `0x003c52d0`（每次不同，落在动态分配的内存，即 LoaderDll 的远程装载 shellcode/`LocaleEmulator.dll` 初始化），**此时尚未做任何 hook 注入**（本地试改「转区一律先恢复、等窗口就绪再附着」后仍同样崩溃，已回退）；③ 旧构建 helper 在转区 + 早注入时打 `[inject] kernel32 … target=00000000` / `remote LoadLibraryW … exit=0xC0000005`，那是对一个正在死亡的进程做远程线程的次生现象。会话侧表现：`launch_injection_failed / readyTimeout`，3 秒后重试附着 `OpenProcess(pid) failed: 87`。注入器里 `initial suspend count=1` 也与 `ResumeLaunchedGame` 注释里「转区路径计数应为 2」不符，说明 LoaderDll 没有按预期接管这一次创建。
- **[ ] ① 未修复** — 落在 `native/galgame_hook/injector/injector_main.cpp` 的 `CreateJapaneseLocaleProcess`（LoaderDll `LeCreateProcess`）与随包 Locale Emulator 组件之间；需要在原始路径固定 LoaderDll/LocaleEmulator.dll 版本与 SHA-256、抓 APPCRASH 的 minidump 定位到 LE 的哪一段，再决定是修 LEB 环境块、换 LE 版本，还是对这两款 KiriKiri 把 `auto` 判为不转区。本轮按用户要求不动 hook/注入器代码。
- **[ ] ② 未加自动化测试** — 待根因落定后为 `resolveJapaneseLocale`（Dart）或注入器 locale 路径加守卫。
- **备注**：用户库里 Limelight / SGRE / anemoi / WA2 的转区档位都是 `off`，只有 9-nine 是 `auto`（WoH 为空）；因此**受影响的原始路径只有 9-nine**（用户 2026-09-02 有一次 76 秒的 9-nine 会话，说明 `auto` 当时可能判成了不转区，或用户随后改了设置，待复核）。Limelight 的安装目录是日文路径，不转区直接启动画布全白，是否需要转区待显示器在线后复核。真机证据：2026-09-03 03:34 / 03:51 / 04:07 / 04:18 四次拉起的会话事件与 04:06、04:18 两条 APPCRASH 事件日志。
