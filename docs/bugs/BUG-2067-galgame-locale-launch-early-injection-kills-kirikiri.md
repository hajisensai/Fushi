## BUG-2067 · 转区（Locale Emulator）拉起 + 早注入让 x86 KiriKiri 游戏进程随即死亡，退回附着才可用
- **报告**：2026-09-03（代理真机验证中发现；用户库里的 Limelight Lemonade Jam 与 9-nine Episode 1 均复现）
- **真实性**：✅ 真 bug（已复现两次、两份 helper 构建）。`GalHookSessionController.launchGame` 在 `japaneseLocaleMode = auto` 下对这两款 x86 KiriKiri 走「Locale Emulator 转区拉起 + 早注入」：注入器打 `LAUNCH pid=… arch=x86` 后，`fushi_voice_hook.dll` 的远程 `LoadLibraryW` 以 `0xC0000005` 结束（旧构建 helper 另打 `[inject] kernel32 … target=00000000`），会话报 `launch_injection_failed / readyTimeout`，3 秒后重试附着时 `OpenProcess(pid) failed: 87`——游戏进程已经死了。同一台机器上：① 直接用注入器 `--launch <exe> --workdir <dir> --hold`（不带 `--japanese-locale`）拉起 9-nine，`OK hooked`、LunaHook 连接、游戏存活；② 手动启动游戏后 `startAttachedCapture` 附着，`engine.text_hook_ready`。两款游戏都不在 `include/kirikiri_launch_profile.h` 的延迟附着表里，因此没有走「先等窗口就绪再附着」的路径。根因落在 `native/galgame_hook/injector/injector_main.cpp` 的 locale 拉起编排（`CreateJapaneseLocaleProcess` → `LoaderDll!LeCreateProcess` 双重挂起 → 早注入 `InjectDll`）：LoaderDll 需要在 kernel32 初始化前装入 `LocaleEmulator.dll`，此时对进程 `CreateRemoteThread(LoadLibraryW)` 落在未初始化的加载器上。
- **[ ] ① 未修复** — 属注入器/hook 侧改动（本轮按用户要求不改 hook 代码）。候选修法：locale 路径下把早注入改为「先 `ResumeLaunchedGame` 让 LoaderDll 完成 kernel32 初始化，再按 KiriKiri 延迟附着 profile 的 `WaitForReadyGameWindow` 方式附着」，或把这两款 exe 的 SHA-256 收进 `kirikiri_launch_profile.h` 延迟附着表；两者都要在原始路径复测 `OK hooked` + 文本 hook ready + 游戏存活。
- **[ ] ② 未加自动化测试** — 待修复时为 locale + 早注入组合加 injector 层守卫（locale 拉起必须先恢复到 kernel32 初始化完成再注入）。
- **备注**：Limelight 的安装目录是日文路径（`ライムライト・レモネードジャム`），不转区就读不到资源（手动直接启动画布全白），所以它**必须**走转区；9-nine 是 ASCII 路径，不转区可正常拉起。真机证据：2026-09-03 03:34 / 03:51 / 04:07 三次 `launch`（旧 helper 两次、本分支重建的 helper 一次）事件记录见集成驱动 `gal_realgame_driver_itest.dart` 的 `events` 输出。
