## BUG-5392 · 备份合并导入把书 / 视频的 source_id（备份库来源自增 id）原样搬进本机，挂到不相干的来源上
- **报告**：2026-11-24（用户：应用内反馈 AXlWkmbUmY，与 hfLuOcL7n0 同一场景「导入备份后库乱了」）
- **真实性**：✅ 真 bug。`fushi/lib/src/sync/backup_merge_engine.dart` 修复前的 `_insertMissingVideoBooks`（`INSERT INTO video_books (<除 id 外全列>) SELECT <同列> FROM mergesrc.video_books`）与 `_insertMissingEpubBooks`（同样整列直搬，只换 `uid`）把 `source_id` 原样搬进本机；它是 `media_sources.id` 的自增整数外键，而 `media_sources` 是设备本地、合并时整表跳过。两库来源 id 互不相干，结果是备份里的视频 / 书挂到本机碰巧同号的另一个来源上（或悬空）。挂错之后：视频分组方式改按那个来源的设置走（`video_books.video_grouping_mode` 注释「存在来源时以来源当前设置为准」，作品 / 目录两种归组互换）、来源计数与按来源刮削 / 隐私来源判定全部错到别的来源上。「从覆盖导入前的快照恢复书库」（`fillMissingOnly`）走同一条插入路径，快照里本机原来的来源 id 被落进覆盖后的库，同样错挂。
- **[x] ① 已修复** — 来源按跨库身份 `(media_kind, transport, root_path)`（与覆盖导入回填下载任务目标来源 `_insertVideoDownloadJobsFromBak` 同一判据）建 src→本机 id 映射表 `temp.merge_source_map`（`_buildSourceIdMap`），书 / 视频插入时 `source_id` 一律经它换；本机没有同一个来源就落 NULL，并按 `deleteMediaSource` 的「来源已移除」语义保留来源留下的意图：视频行落 src 来源的分组方式，src 隐私来源下的条目写作品级私密标记（本机已有该作品的私密时钟行就不动）。不建来源行：`media_sources` 是本机扫描根，备份设备的根路径在本机不存在，建出来只会是扫描报错的空来源。另加结构守卫 `_assertIntegerForeignKeysRemapped`：凡整列跨库搬行的表（`_insertMissing` 各表、`epub_books`、`video_books`、`galgames`、`audio_cues`），每个指向整数主键的外键列必须被调用方显式换过，否则整个合并事务大声失败回滚，新 schema 加了这种外键也不会再静默落错 id。
- **[x] ② 已加自动化测试** — `fushi/test/sync/backup_merge_source_id_remap_test.dart`（真 drift：本机内存库 + 备份文件库 ATTACH，两库来源 id 故意错位）。
- **备注**：其余跨库整数身份已逐一核过，原本就按身份重映射：标签 `tag_assignments.tag_id`（按标签名）、Profile 子表与段 / 会话的 `profile_id`（按 Profile 名）、合集成员 `collection_id` 与合集标签 / 作品图谱里的合集 id（按合集自然键）、游戏 id（`merge_game_map`）、网页书签 `parent_id`。`music_tracks.source_id` 所在曲目表设备本地、不合并；`music_play_events.source_id` 是文本（歌单 / 专辑键），不是来源外键。hfLuOcL7n0 的生命周期部分由 BUG-5387（PR #4364）修。
