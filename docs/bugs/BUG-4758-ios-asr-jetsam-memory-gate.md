## BUG-4758 · iOS 视频页生成字幕被 jetsam 杀（ASR 内存门槛只在 Android 生效）
- **报告**：2026-11-11（应用内反馈 EnDAyv9ouF、_4fe2p5UsT，iPhone15,4 / iOS 27.2，3.3.0，闪退报告「意外退出」共 4 次；拍板台 2026-11-16 定：做，根本性修复、别硬砍性能）
- **真实性**：✅ 真 bug。闪退报告的内存时间线：视频页 RSS 528 MB → 8 秒后 1776 MB（另三次涨到 1824 / 1901 / 1953 MB），同时 `_VideoSubtitleGenerateSheetState._onJobChanged` / `_AsrTranscribeSheetState._startTranscription` 在刷新、memoryPressure 1~2 次，随即进程没了（jetsam）。视频走 `mixedAudio` 素材，日语落到 Parakeet TDT-CTC 0.6B（int8 约 655 MB，门槛估算 ≈ 2.5 GB）。根因：`fushi/lib/src/asr_host/asr_memory_gate.dart:179`（修前）`readAndroidMemorySnapshot` 开头 `if (!Platform.isAndroid) return null;`，`MemoryGatedAsrTranscriptionService` 的默认探针就是它，iOS 上门槛恒放行，开跑前完全不看 jetsam 额度。另：崩溃报告里看不出用的哪个模型（_4fe2p5UsT 指出）。
- **[x] ① 已修复** — `asr_memory_gate.dart`：`DeviceMemorySnapshot` 改为 sealed，余量由各平台的真实被杀线给出——`AndroidMemorySnapshot`（原判据不变：min(物理内存 × 0.4 − RSS, MemAvailable)）、`IosJetsamMemorySnapshot`（`os_proc_available_memory()`，经 `DynamicLibrary.process()` 直接取 libSystem 符号，就是本进程离 jetsam 额度还差多少，按 phys_footprint 算、含视频解码的 IOSurface，不用再拿物理内存比例去猜；系统回 0 = 无额度（模拟器 / Mac 上的 iOS app）→ 不设门槛）。默认探针改为 `readDeviceMemorySnapshot()`（Android / iOS 分派，桌面 null）。放得下的照原批次、原线程数全速跑，不降性能；放不下在打开模型目录 / 起 isolate 之前抛 `AsrInsufficientMemoryException` 并建议同语言同素材里放得下的模型（复用原 UI 与文案）。诊断：开跑前写活动面包屑 `asr_transcribe`（`model=<pack id> variant profile need headroom rss`），按路记诊断行（多路并发时面包屑是仍在跑各路拼起来的，一路结束就用剩下的重写，不残留已结束那路的模型名），最后一路在事件流结束 / dispose 时清；进程死在转录里时下次启动的崩溃报告带上模型与余量，同一行也 `debugPrint` 进日志。
  - **不砍性能、让原模型跑起来**（拍板留言「别硬砍性能」）：`fushi/ios/Runner/Runner.entitlements` 加 `com.apple.developer.kernel.increased-memory-limit`（iOS 15+，抬高本进程 jetsam 额度），`.github/workflows/release-desktop.yml` 沿用 BUG-4013 那套逐项对照描述文件：授予才签、没授予就在 runner 上删掉该项并打 warning。额度抬高后 `os_proc_available_memory()` 随之变大，门槛直接放行原模型全速跑；门槛只在抬高后的额度也放不下时才拦。**App ID `app.fushi.reader` 要勾「Increased Memory Limit」并重新生成 App Store 描述文件、更新 `IOS_PROVISIONING_PROFILE_BASE64`**，否则 CI 打 warning 不签（行为退回只有门槛）。
- **[x] ② 已加自动化测试** — `fushi/test/asr/asr_memory_gate_test.dart`：iOS 余量口径、系统回 0 不设门槛、反馈场景（mixedAudio 日语默认模型在 1.6 GB 额度下被拦且建议更小模型）、额度够放行并返回带模型名的诊断行、面包屑在打开模型目录前写下 / 起转录失败时清 / 被门槛拦下不写、多路引用计数、事件流结束与 dispose 都结束面包屑、后开先结束时面包屑改回仍在跑那路、平台分派（iOS 走 jetsam 额度 / 桌面不设门槛）、生产服务默认探针就是跨平台的 `readDeviceMemorySnapshot`（修前是只认 Android 的 `readAndroidMemorySnapshot`，此用例会红）；`fushi/test/build/ios_entitlements_profile_gating_guard_test.dart` 钉住 increased-memory-limit 的请求与描述文件对照；原 Android 用例改用 `AndroidMemorySnapshot` 照旧通过。
- **备注**：未做 iOS 真机复测（门槛估算 `模型字节 × 3 + 600 MB` 是按 Android 实测标定的，iOS 上 Parakeet 的真实峰值没有数据）；有了带面包屑的崩溃报告 / 拦截日志后可按 iOS 实测重标定。降低模型装载峰值本身（如外置权重 mmap，让干净的文件页不计入 footprint）属算法层，要在上游 `hajisensai/fushi-subtitles` 做且需真机量数据，本次未做。
  - **跟进项**：① 上游 `hajisensai/fushi-subtitles` 降模型装载峰值（外置权重 mmap / 避免图优化副本常驻），需真机量数据；② App ID 勾 Increased Memory Limit 并更新描述文件 secret 后，用 TestFlight 包在 iPhone 15 上复测视频页 Parakeet 生成字幕，并按拦截日志（`need` / `headroom`）重标定 iOS 门槛。
