## BUG-1127 · app 外查词自动发音走 libmpv 慢路径且失败被静默吞掉
- **报告**：2026-07-26（用户：app 外查词单词音频总会被吞或者响应慢）
- **真实性**：✅ 真 bug。三条根因链（桌面 Windows 浮窗专属组合，多 agent 沿真实代码路径逐行核实并做过反驳复核）：
  1. **【慢】浮窗自动发音留在 Dart/libmpv 慢路径**：`9855c3e4f`（perf(lookup): 统一查词单词发音走 WebView `<audio>`）只迁了 in-app（`base_source_page.dart:457` / `dictionary_page_mixin.dart:370` → `autoReadWordUnified`，WebView 快路径 + 真实结果回报 + Dart 兜底），提交信息明示「app 外 overlay 的自动发音仍走 libmpv，作为已知剩余项本轮未动」。浮窗侧 `global_lookup_controller.dart:1075 _playWordAudio` 直接 `resolveLookupAudioUrl` → `TtsChannel.playAudioRef`（:1082）→ `DesktopAudioPlayback._play` 每播一次串行 `stop→setVolume→load→play`、libmpv 重新 demux + 开解码器、远端 URL 每次重新拉流——正是 popup.js:2168 注释自认的桌面慢根因。统一所需基础设施当时已全部就绪：`audioRefToWebViewUrl` data:/http 转换（`lookup_audio_playback.dart:156`，注释明言为 app 外 WebView2 设计）、popup.js `window.__hibikiPlayWordAudioUrl`（:2195，注释明言给宿主驱动自动发音）、host→iframe eval 通道（`global_lookup_host.js highlightFrame` :2156 模式）、浮窗 WebView2 环境 autoplay 放行（`global_lookup_window.cpp:973`，BUG-1093 时加）。
  2. **【吞】播放失败全链路静默**：:1082 的 `playAudioRef` 返回值被忽略（无兜底/无日志）；`DesktopAudioPlayback._play` 两个 preempt bail 点（`desktop_audio_playback.dart:191/:198`，galgame 试听等 4 处 `stop()` 调用点触发 `preempt()` 后在途播放静默 `return false`）零日志——与 BUG-1015 曾被误定根因同款观测盲区。
  3. **【吞·放大器】静默失败仍占 800ms 去重窗**：`lookup_auto_read_coordinator.dart:43` 播放回调无论是否真出声都保留 `_acceptedAt`，一次静音失败把同词短窗内的立即重查也一并吞掉。
- **[x] ① 已修复** — 浮窗自动发音统一到 in-app 同一契约（消分叉，零 native 改动）：
  - `global_lookup_controller.dart`：`_playWordAudio` 改为转调 `autoReadWordUnified(playInWebView: _playWordAudioUrlInOverlay)`；新增 `_playWordAudioUrlInOverlay`（token + Completer + 5s 超时，镜像 in-app `DictionaryPopupWebView.playWordAudioUrl` 的 BUG-1093 契约；`isWebViewReady` 门控防 native render 通道 not-ready last-wins 缓存把挂起的整栈渲染脚本顶掉）；`_onJsMessage` 新增 `wordAudioPlayed` 路由。
  - `global_lookup_render.dart`：新增 `buildPlayWordAudioScript`（JSON 编码 frameId/url，目标恒为稳定 root 帧 `kGlobalLookupRootFrameId`——TODO-1095 常驻复用、启动预热恒暖，音频与 realm 无关，无冷 iframe 等待）。
  - `global_lookup_host.js`：新增 `playWordAudioInFrame(frameId, url, token)`——loaded 门控，realm 内 eval `__hibikiPlayWordAudioUrl` 并经包裹桥回报真实 `audio.play()` 结果；帧缺失/未加载/eval 异常从 host realm `postToHost('wordAudioPlayed',[token,false])` 即时回报（不逼 Dart 等满 5s 超时）。
  - `lookup_audio_playback.dart`：`autoReadWordUnified` 返回 `Future<bool>`（是否真出声），兜底透传 `playAudioRef` 结果。
  - `lookup_auto_read_coordinator.dart`：`LookupAutoReadPlayback` 改 `Future<bool>`，播放明确失败即释放去重窗（消放大器）；`base_source_page.dart` / `dictionary_page_mixin.dart` 同步签名。
  - `desktop_audio_playback.dart`：两个 preempt bail 点补 `ErrorLogService.logDiagnostic`（吞音可观测）。

- **备注**：症状对照——「响应慢」= 每播一次 libmpv 重初始化 + 远端重拉流（统一后走 `<audio>`，WebView2 自带 HTTP 缓存）；「总被吞」= 失败零兜底零日志 + preempt 掐断 + 失败占窗放大。真机验收路径：Windows 冷启动 → galgame/任意 app 外划词或热键查词 → 自动发音应即刻出声；对照组 in-app 弹窗行为不变。相关但**不在本轮**（不同源，另立项）：① 串行解析死源硬等（首查最坏 14~20s，每 45s 冷却过期重演，`word_audio_resolver.dart:97`；解析层 in-app/app 外共用）；② Android 弹窗词典 :popup 副 engine 未注册 `TtsChannelHandler`，本地音频库用户 app 外查词必然无声（`PopupEngineHolder` 注册清单缺失，参照 BUG-865 先例补）。BUG-1093 备注②所记「hibikiRemote 死配对无冷却」已过时——`a2000935c` 已补 45s 冷却，本轮顺手在该文件标注。
