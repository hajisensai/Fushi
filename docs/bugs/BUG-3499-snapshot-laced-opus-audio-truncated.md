## BUG-3499 · 在线视频同步片段的音频只剩 0.2～0.4 秒且断续（缓冲副本丢音频包）
- **报告**：2026-10-17（用户：Windows 10 / 2.10.0-debug.19402，Jellyfin（Linux）在线播放，「带声音的视频片段」制卡；附 apkg、mediainfo、错误日志与视频诊断日志）
- **真实性**：✅ 真 bug，已在本机用同版 libmpv 复现。只在 mkvmerge 封装的 Opus 音轨上出现（用户《やがて君になる》BD 压制：AV1 + 双 Opus；同一用户 AAC 音轨的片子正常）。
  - 卡片证据：三张卡的 webm 画面 2.6～3.3 秒，Opus 音轨只有 0.19 / 0.27 / 0.44 秒，左右声道相同（= 先裁单声道 AAC 句子音频再合成的那条路），采样数恰为 9 / 13 / 21 个 AAC 帧。
  - 根因链：在线视频制卡先让播放器把缓冲落成本地副本（`fushi/lib/src/media/video/video_player_controller.dart` `snapshotCachedRange` → libmpv `dump-cache`）。mpv 的 mkv demuxer 对 lacing 块只给第一帧时间戳（mpv `demux/demux_mkv.c`：`if (i == 0 || track->default_duration) dp->pts = …`），源轨没有 `DefaultDuration`（mkvmerge 封装的 Opus）时同一块里其余帧 PTS/DTS 全空；随包 libmpv 的 FFmpeg 9.0.1 matroska muxer 把这些包全部拒收——用户诊断日志里 `matroska: Application provided invalid, non monotonically increasing dts to muxer in stream 1: 85 >= NOPTS` + `recorder: Failed writing packet` 共 526 条，结尾仍是 `Cache dumping successfully ended`。副本里音频每块只剩一帧，`snapshotCachedRange` 只判「文件存在且非空」、引擎只在「抽取失败」时回远端（`fushi/lib/src/mining/immersion_mining_engine.dart` 的 `mine()`），对这种副本抽取照样成功、抽出的就是 0.2 秒碎音频。
  - 不能靠 mpv 日志判失败：mpv 的 `mpv_wait_event` 先发队列事件（含命令回包）再吐日志（`player/client.c`），且日志缓冲会溢出。
- **[x] ① 已修复（根治在 libmpv）** — `third_party/media_kit_libs_windows_video/patches/mkv-laced-audio-timestamps.patch` 改 mpv `demux/demux_mkv.c` 的 `handle_block()`：轨道没有 `DefaultDuration` 时，lacing 块里第一帧之后的帧按各自时长顺推时间戳——Opus 读包头 TOC（RFC 6716 3.1）得精确帧长，其它编码在有 BlockDuration 时按帧数均分（与 FFmpeg 的 matroska demuxer 同法），都没有才保持原样；块首帧时间戳不变。上游 master 截至 2026-10-17 未修。Windows 随包 libmpv 已用 `tool/bluray/build_libmpv.ps1` 重编为 `…-lua1-mkvlace1.7z`（同一套 MSYS2 依赖，除 `libmpv-2.dll` 与两份清单外 122 个 DLL 逐字节相同）。实测（同一 mkvmerge 双 Opus 样本）：原库 dump 报 716 次写包失败、副本窗内音频 12 KiB；新库 0 次、94 KiB（满窗），副本音频包 824 个、步进恒 20 ms 无缺口，原有 108 个块首帧时间戳逐个不变；app 流程合成的 webm 音频 3.00 秒；播放起播 / 绝对与相对跳转的 avsync 与原库一致（<0.2 ms）、错误日志 0。Android（`hajisensai/libmpv-android-video-build` 分支 `fushi/mkv-lace`，CI 在私有镜像 `hajisensai/libmpv-android-build-fushi` 跑，见 BUG-3454 备注）与 Darwin（`hajisensai/libmpv-darwin-build` 分支 `fushi/mkv-lace`）加同一补丁与产物字符串校验，本仓 `tool/bluray/platforms/` 的本地构建流程同步带上；四个平台的随包 libmpv 已连同 BUG-3454 的 recorder 补丁一起重编入库（Windows 归档改名 `…-lua1-mkvlace1-mkvdts1.7z`）。
- **[x] ①b 应用层防线（保留）** — 引擎拿到副本后、需要音频时先看内容：`packages/fushi_engine/lib/utils/misc/snapshot_audio_coverage.dart` 的 `cachedSnapshotAudioCoversWindow` 把这句时间窗内的第一条音轨解成单声道 16 kHz PCM 丢弃，按收尾统计行 `audio:<n>KiB` 换算真实采样时长，不足窗长 90% 判副本不完整（进度行 `time=` 取时间戳，稀疏包照样报满窗，不能用）；`ImmersionMiningEngine._snapshotAudioUsable` 据此跳过副本、记 `Anki.cachedSnapshot.audioIncomplete` 诊断、回到既有远端抽取（ffmpeg 自己的 lavf demuxer 能正确处理 lacing）。实测：坏副本 12 KiB（≈0.38 秒）、正常副本 94 KiB（3 秒窗理论 93.75）；远端兜底对同一文件裁出 3.02 秒。
- **[x] ② 已加自动化测试** — `packages/fushi_engine/test/snapshot_audio_coverage_test.dart`：参数形状、覆盖判据、ffmpeg 失败 / 无统计行判不完整，以及真 ffmpeg 用例（`aselect` 每 8 帧留 1 帧造与坏副本同形的稀疏音轨，`time=` 仍报满窗）；`fushi/test/mining/immersion_mining_cached_snapshot_test.dart`「副本音轨不完整 → 不用副本，远端抽取」；libmpv 层 `fushi/test/build/libmpv_mkv_laced_audio_guard_test.dart`（补丁内容、构建脚本应用并验证、移动端构建流程带上、vendored provenance 与补丁逐字节一致）+ 真库验证 `tool/bluray/verify_mkv_lace_dump.py`（夹具 `tool/bluray/tests/laced-opus.mkv`，已接进 `build_libmpv.ps1` 作为重编必经的门；原库：410 次写包失败、6 秒只解出 0.86 秒 → 失败；新库：0 次、6.02 秒 → 通过）。
- **备注**：应用层的副本内容校验在根治后仍保留——它兜住补丁顾不到的情形（没有 BlockDuration 的非 Opus lacing 音轨，例如 Vorbis），以及移动端换库之前的窗口。用户另报《きみしぬ》（HEVC 10bit + AAC）片段画面花屏，是同一条 dump-cache 链路丢视频包（Matroska 无 DTS），见 BUG-3454。
