## BUG-1950 · STEINS;GATE RE:BOOT 内嵌查词对非首日构建静默失效：SGRE 适配把单个 exe 哈希当准入门，从不尝试其它构建
- **报告**：2026-08-30（用户：Windows / 「命运石之门有的用户打开没有内嵌」）
- **真实性**：✅ 真 bug。SGRE 的全部身份就是一个 exe SHA-256：`native/galgame_hook/hook/adapters/sgre_profile.h:20` 写死 `kSgreExecutableSha256 = 75a83a0e…c404b9d8`（2026-08-21 从发售首日 Steam x64 构建量得，commit `05e7bf892a`），`MatchesSgreProfile()` 逐字节比对不等即 `probe()==false`；`sgre_adapter.inc:64-95` 的 `install()` / `ProcessPendingEvents()` 全以 `probe()` 为前置，传感器 `ProcessSgreLookupTick()` 根本不跑。三个引擎内部锚点全是固定 RVA（`sgre_lookup.h:15-24`：文本绘制 `0x35aa0`、剧本文本 vtable `0x5be330`、DirectInput 鼠标设备槽 `0xA96E18`），`InstallSgreLookupSensor()`（`sgre_lookup.inc:878`）直接 `HookFn(base+RVA)` 没有任何「这里真是那个函数」的校验——所以在别的构建上根本不敢试，代码的选择是干脆不试。游戏 2026-08-20 发售、同日即有官方补丁，之后任何 Steam depot 更新、日区/海外区不同 depot、非 Steam 版，`sgre_steam.exe` 哈希都不再相等 → 文本 hook、内嵌查词传感器、点击盾、语音资源整链静默失效，UI 无任何提示（BUG-1935 的准入回显分支当时也尚未合入 develop）。与 KiriKiri 能「全适配」的差别：krkr 的锚点全挂在公开表面（`V2Link` 导出表、`wuvorbis.dll`/`textrender.dll` 导出名，`kirikiri_adapter.inc` 全是 `GetProcAddress`），SGRE 三个锚点全挂在引擎内部代码上，这才是病根。
- **[x] ① 已修复** — 身份分层 + 锚点解析（本提交）：
  - 新 `hook/adapters/sgre_anchors.h`（纯头文件、无 Windows 依赖、可离线测）：`kSgreKnownBuilds[]` 一构建一行（哈希 → 三个 RVA，首日构建为第一行）；`kSgre*Signature` 三条 IDA 风格字节签名（**当前留空，待从真实 exe 量得后补**）；`ResolveSgreAnchors()` 查表命中直接给，否则按节扫描签名，**必须唯一命中 + 结构校验**（代码锚点落可执行节 / vtable 首槽指向代码节 / 设备槽落可写数据节），任一不满足即该锚点 `unresolved`，绝不往猜的地址打 hook；每个锚点回报来源枚举（`known_build` / `signature` / `signature_empty` / `signature_missing` / `signature_ambiguous` / `structure_rejected` …）。
  - `sgre_profile.h`：`probe()` 改为家族判据 `MatchesSgreFamily()`（exe 同级 `wind3d11data\voice_body.bin`——与音频 archive 成员证明是同一份数据契约），哈希只用于查表；`ReadSgreImageSections()` 进程内解析 PE 节表，`ResolveSgreRuntimeAnchors()` 在 SEH 下解析。
  - `sgre_adapter.inc` / `sgre_lookup.inc`：音频（archive 成员证明）按家族装、任何构建可用；传感器只在 `text_draw`+`scenario_text_vtable` 解析成功时装（`InstallSgreLookupSensor` 先查 `lookup_sensor_available()` 再读 RVA），输入盾只在设备槽锚点解析成功时装（`InstallSgreDirectInputShield` 未解析时发布 Required 后 NotReady 返回，fail closed）；`adapter_registry.inc` 的 16ms 轮询改看 `lookup_sensor_available()`。
  - 回报：`voice_hook_ipc.h` 在 `xaudio_diagnostics` 剩余位加 `kXAudioDiagSgreFamilyMatched` / `kXAudioDiagSgreAnchorsResolved` / `kXAudioDiagSgreAnchorsUnresolved`（不改 `SharedHeader` 布局，避开 BUG-1935 分支的 v19）。
  - `engine-support.yaml` sgre 条目 detection/process_strategy/known_limitations 改写为家族 + 锚点模型，`docs/engine-support.md` 重生成。
- **[x] ② 已加自动化测试** — `native/galgame_hook/tests/sgre_adapter_test.cpp::TestAnchorResolution`（x64/x86 ctest 均过）：已知哈希查表得原 RVA 且 `known_build`；未知哈希 / 无哈希 + 空签名 → 三锚点 `signature_empty`、`lookup_sensor_available()==false`；模式串语法（空 / 非法字符 / 半字节 / 未分隔 / 超容量）；合成三节镜像上：唯一命中、`anchor_offset`、缺失、未知节、非法模式、RIP 契约越界、二次命中判 ambiguous、代码锚点落数据节判 rejected、RIP 相对解出 vtable 且首槽指向代码 / 指向数据 / 空指针 / 低于镜像基址四种、RIP 相对解出可写设备槽 / 指向只读节判 rejected、内置空签名表在可扫镜像上仍报 `signature_empty`。守卫：`tests/adapter_structure_test.py`（装钩点不得读裸常量、必须先查可用性；家族 probe 取代 `MatchesSgreProfile`；`sgre_anchors.h` 不得出现 exe 文件名）、`fushi/test/lookup/gal_ingame_lookup_click_swallow_guard_test.dart`（设备槽只能来自解析结果；顺序断言先 `contains` 再比 `indexOf`，堵住 -1 陷阱）。三处守卫/测试均做过变异实测：Python 2/2、C++ 4/4（第一轮 2 个存活：一个是等价变异体、一个暴露未覆盖 vtable 空槽分支，已补用例）、Dart 2/2（第一轮 M2 存活即 `indexOf` -1 陷阱，已修守卫）；变异后按 sha256 还原、基线复绿。
