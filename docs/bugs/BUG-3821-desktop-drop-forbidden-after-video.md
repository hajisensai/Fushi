## BUG-3821 · Windows 看完视频后拖书进窗口显示禁止光标
- **报告**：2026-10-26（用户：fushi-bot 代哈吉千歳提交，反馈 BUOxDR9WIJ；「看视频后或者什么时候」，触发条件不确定）
- **真实性**：⚠️ 未复现，原假设已证伪。原假设（分诊 + BUG-361 注释）：WebView2 / mpv 离场时把宿主 HWND 的 OLE drop 注册撤掉，而视频页 push/pop 不经过 `AppModel.closeMedia`（`fushi/lib/src/models/app_model.dart` 旧 :8746 `DesktopDropReinitializer.reinitialize()`），所以没人重注册。真 app 探针 `fushi/integration_test/desktop_drop_registration_probe_itest.dart`（Windows 离屏 runner，2026-10-27 跑了 3 轮，exit 0）在「基线 → 本地视频页开/关 → composition WebView2 开/关 → 窗口宿主 WebView2（网页播放器同款环境）开/关」每一步读 FLUTTERVIEW HWND 上的 `OleDropTargetInterface`：句柄全程不变，新加的原生 `status` 报告 `registered=true ours=true registerCount=1`，窗口宿主 WebView 的子 HWND 关页后也已销毁。也就是说这几条路径都不会丢注册，在视频页 pop 时补一次 reinitialize 修不了任何东西。还没排除的可能：① 进程以管理员身份运行时 UIPI 会挡掉 Explorer 拖入，光标同样是禁止；② 盖在主窗上的其它顶层窗（galgame 附着文本层 `FushiAttachedTextSurfaceWindow`、悬浮球、全局查词窗）挡住了落点；③ 拖到了打开着的窗口宿主 WebView 区域（WebView2 关了 AllowExternalDrop，会拒收）。
- **[ ] ① 未修复（加诊断 + 有证据时自修）** — `third_party/desktop_drop/windows/desktop_drop_plugin.cpp` 加只读 `status`（当前注册 / 是否仍是我们注册的那个 / 上次 RegisterDragDrop HRESULT / 注册次数 / 进程是否提权）；`fushi/lib/src/media/drag_drop/desktop_drop_reinitializer.dart` 新增 `verifyAndRepair`，确实丢了才重注册，并把前后状态写进诊断日志；进程提权写一条诊断。触发点改成挂在根 Navigator 上的 `DesktopDropRouteObserver`（`fushi/lib/main.dart`），任何 page route 离场都核对一次（视频 / 网页视频 / 阅读器 / 浏览器 / 游戏），不再只挂在 `closeMedia` 上；`closeMedia` 改调 `verifyAndRepair`。下一份带日志的反馈里搜 `DesktopDrop` 就能看出是注册丢了、进程提权了，还是两样都不是（那就是窗口遮挡类）。
- **[x] ② 已加自动化测试** — `fushi/test/media/drag_drop/desktop_drop_reinit_test.dart`（注册完好不重注册、丢失 → reinitialize + 前后状态诊断、提权诊断、未打补丁插件 no-op、原生 `status` 分派、observer 已接入 main），9 条通过；变异：去掉「完好就返回」→「healthy registration」用例变红。真 app：上面的探针断言注册全程完好、没有任何「lost」诊断。
- **备注**：「拖入只在书架页生效」是**有意设计**：拖放目标按库页分域（书架 `reader_fushi_history_page.dart` 收书、视频库 `home_video_page.dart` 收视频、游戏库收 exe…），首页 dashboard 没有拖放目标；看完视频回到的是视频库，把 EPUB 拖到那里不会进书架导入。这本身不出禁止光标（desktop_drop 的 DragEnter 不改 effect）。要不要让 dashboard / 其它库页把书转交书架导入，是产品决定，这次没改。
