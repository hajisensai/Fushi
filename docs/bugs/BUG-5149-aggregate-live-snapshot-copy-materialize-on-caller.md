## BUG-5149 · aggregate-live-snapshot-copy-materialize-on-caller
- **报告**：2026-11-22（PR #4062 独立审查：BUG-5102 / HBK-AUDIT-028 修复后的残余，审计原文要求「大块解码、快照合并和编码放在同一后台所有者，轻量结果回传」）
- **真实性**：✅ 真问题（性能 / UI 卡顿，量级比 BUG-5102 修前小一个数量级）。BUG-5102 把互联聚合的编解码与合并 / 差集挪进了 `AggregatePureRunner`，但每一步都是一次性 `Isolate.run`，整份快照要在调用方与后台之间来回拷，且下面几段整份快照的 O(N) 工作仍在调用方 isolate（app 里即 UI isolate）：
  - 每次后台计算的入参（本地 materialize 结果、合并结果、上行快照）以消息深拷贝送进新 isolate：一轮互联同步 3 次（`packages/fushi_engine/lib/sync/aggregate_sync_service.dart` `_planLiveFoldOff` / `_foldDeltaOff` / `_outgoingIfChangedOff`），4 万行 / 族实测每次 35～50 ms 停在调用方（BUG-5102 的 bench）；上行编码这一跳修前 48 ms、修后 44 ms，基本没省——拷进去的成本与编码本身同量级。
  - `materializeLocalSnapshot`（`aggregate_sync_service.dart:1322`，调用点 :348 与锁内 `foldIntoLocal` :1858）把 DB 行组装成整份快照在调用方。
  - `filterTombstoned`（调用点 :362 / :395）按墓碑逐行裁剪整份合并结果在调用方。
  - host GET（`packages/fushi_engine/lib/sync/fushi_sync_server/sync_state.part.dart:53`）`getAggregateSnapshot` 在 host（app 内即 UI）isolate 组装快照，再整份拷进后台编码。
- **[x] ① 已修复**（PR #4062 第二轮，提交 596cd7304c）— 新增后台所有者 `packages/fushi_engine/lib/sync/aggregate_sync_owner.dart`（`AggregateSyncOwner`）：一轮互联 / 云聚合同步、host 的一次 GET / PUT 各起一个所有者 isolate，经新增的 `FushiDatabase.backgroundConnection()`（`packages/fushi_core/lib/src/database/database.dart`，直接交出 `createInBackground` 那个 drift 后台 isolate 的 `DriftIsolate` 端口，语句与结果不经调用方中转；内存库退回 drift 的 `serializableConnection`）+ `FushiDatabase.shared` 接上**同一个**库。DB 读取、快照组装、报文体解码、折叠、锁内重读 + 合并 + 差集 + 写回、墓碑裁剪、上行判定与编码 / 哈希都在所有者里做，整份快照（本地、合并结果、待上传）只活在那边；调用方只收 `bool`（要不要写回）/ 报文体字节（`TransferableTypedData`）/ 哈希。写锁语义不变：调用方持 `localApplyLock` / host 的 `_runSyncStateExclusive` 期间让所有者执行「重读 → 合并 → 写回」，锁仍包住整段（drift 服务端对多个连接的语句与事务串行）。host 服务接口改为只搬字节：`getAggregateBody()` / `applyAggregateBody(body) → bool`（解码在锁外、写回在锁内；坏 JSON / 非 object / 空体回 false → 端点 400，BodyTooLarge 413 不变）。对比弹窗改用 `readingStatCountsByTitle`（后台解码，只回每本书的条数）。删掉 BUG-5102 的一次性 `AggregatePureRunner` / `_runPure` 与 `decodeWireSnapshotOff` / `encodeWireSnapshotOff`。
  - 为什么不常驻全进程 / 不进 Rust：所有者「每轮一个」——聚合同步低频、单轮状态只在本轮有效，常驻要另管与库连接同生共死、库关闭 / 热重启 / 多库实例的回收，只换来省一次同组 isolate spawn（毫秒级且不阻塞调用方）。Rust 胖核心规则针对新计算子系统；这里的状态全在 drift 管的 SQLite 里，搬进 Rust 等于再造一套 DB 访问层，且「存量 Dart 只因实测性能问题或收编才搬」——实测（下）Dart 所有者已把调用方占用压到噪声底，不需要搬。
  - 实测（`packages/fushi_engine/test/bench/aggregate_live_sync_isolate_bench.dart`，真磁盘库、生产入口，每族 4 万行 / 报文 9.8 MiB，后 3 次中位数；Windows 定时器粒度 ≈15.6 ms，只把 >20 ms 的间隔算卡顿）：client 一轮 调用方最大停顿 61→24 ms、>20 ms 停顿总和 522→88 ms；host GET 36→21 ms、89→21 ms；host PUT 51→24 ms、268→45 ms；墙钟基本不变（3.7 s / 0.45 s / 1.7 s）。修前数据是 PR #4062 头 ee0bc6bc37 同一 bench 结构。
  - 审查补修（PR #4062 独立审查）：写回挪到所有者的连接后，调用方库上的 stream 查询收不到这些写入——drift 服务端把表更新只广播到后台连接自己的 stream 存储，而主库的执行器是「惰性库 → 拦截器 → 恢复阶梯 → 后台连接」，`GeneratedDatabase` 另建了一个存储，没人转（首页 `watchDashboardDataChanges`、小组件、伴屏、收藏句监听在同步回灌后都不刷新；`FushiDatabase.shared` 文档写的「通知回其它连接」也不成立）。修法：`FushiDatabase.backgroundConnection()` 交出端口时把后台连接存储的 `updatesForSync(any)` 转进本库 `notifyUpdates`（`_forwardBackgroundTableUpdates`，恢复阶梯换连接时跟着换；本库自己的写入不经该存储，不回环）。测试 `aggregate_sync_off_ui_isolate_test.dart`「后台所有者写回的表更新会通知调用方库上的 stream 查询」；变异实测：去掉转发调用后该条超时变红（exit 1），还原后全文件 13 条全绿。
  - 云通道的残余（各后端 `getJsonAsset` / `putJsonAsset` 与对端快照缓存在调用方做 JSON 编解码，对端快照 Map 与待上传 Map 仍要拷进 / 拷出所有者）单开 BUG-5159，拍板台 `review-agg-cloud-bytes`。
- **[x] ② 已加自动化测试** — `fushi/test/sync/aggregate_sync_off_ui_isolate_test.dart`：用每个 isolate 各一份的 `debugAggregateSnapshotWorkHook` 钉住互联 client 一轮（含老 host 退化、无变化不推不进锁）、云通道一轮、host GET / PUT、对比弹窗计数在调用方 isolate **零**整份快照工作，同时断言落库 / 上行结果；锁内写回整段在写锁持有期间（进锁时未写、出锁前已写）；host PUT 坏 JSON / 非 object / 空体回 false、不进锁、不落库；所有者命令异常类型原样传回、关闭幂等、关闭后拒收命令、主库连接不受影响。变异实测：让 `AggregateSyncOwner.spawn` 永远走就地执行（等于撤掉修复），该文件 12 条里 8 条变红，exit 1；还原后全绿。界面测试 `sync_compare_interconnect_live_progress_test.dart` 跑在 FakeAsync 里推不动跨 isolate 往返，用 `debugAggregateSyncOwnerInline` 就地执行（执行位置由上面的文件钉住）。
