## BUG-5160 · 无头服务端内置 BT：上传关不住、下载被队列卡住、会话设置不可配
- **报告**：2026-11-21（用户：PVE 上的 fushi_server 经 `/api/torrent-engine` 给已配对 app 代下，默认关上传却持续上传 15～18 MB/s；未完成种子大多 0 连接、下载 0）
- **真实性**：✅ 真 bug，三个缺陷：
  - **根因一（关上传不生效）**：服务端从不执行上传 / 做种策略。`packages/fushi_server/lib/src/download_host.dart:494`（修复前）起引擎时只投递一次 `applySessionSettings`，从不 `setUploadPolicy`，也没有任何维护 tick 调 `sweepUploadPolicy` / `sweepAntiLeech`（app 侧由 `AnimeDownloadService.onTick` 驱动，服务端没有对应物）。「关上传」的原语是会话级 unchoke 槽位清零 + 已完成种子暂停（BUG-1293），两者都只在 `EmbeddedTorrentHost.sweepUploadPolicy` 里下发，于是 unchoke 槽位一直停在 libtorrent 默认值、120 个已完成种子全部 auto-managed 做种。宿主里 `_uploadConfig` 的默认值确实是 `uploadEnabled=false`，只是没人让它生效。同一处还漏了 `applyLimits` / `applyMemorySettings` / `applyAntiLeechConfig` 和周期性 resume 落盘（进程被强杀会丢续传进度）。
  - **根因二（下载被挂成 pausedDL、0 连接）**：种子一律 auto-managed，而服务端的 `maxActiveDownloads` 写死 0 → `native/fushi_torrent/fushi_torrent_ffi.cpp:795` 只在 `> 0` 时写 `active_downloads`，于是停在 libtorrent 默认 3（`active_seeds` 默认 5）。超出名额的未完成种子被队列管理器优雅暂停（不连 peer、不 announce），即线上的 `pausedDL`。用户把 122 个已完成种子全部暂停后仍是 pausedDL 6 / downloading 2，说明卡住的是下载名额本身，不是做种挤占（libtorrent 2.0 `auto_manage_torrents` 里下载与做种各有 type_limit，只共享 `active_limit` 500）。
  - **缺陷三（不可配）**：`_qbConfig`（`download_host.dart:274`，修复前）只填后端 / qB 地址 / 凭据，`ServerConfig`、admin API、WebUI 都没有任何会话设置项。
- **[x] ① 已修复** —
  - 下发序列收成一处 `EmbeddedTorrentHostClient.postConfig`（限速 → 内存预算 → 会话设置 → 反吸血 → 上传策略），app 的 `_applyEmbeddedTorrentLimits` 与服务端 `_openEmbedded` 共用；维护扫描收成 `postMaintenanceSweep`。服务端解析到内置引擎时起 20 秒维护定时器（与 app 下载服务的 tick 同周期）：策略扫描 + 反吸血 + resume 落盘，引擎没起时什么也不做。
  - `torrent:` 段新增 `upload_enabled` / `upload_limit_kbps` / `download_limit_kbps` / `limit_local_peers` / `max_active_downloads` / `max_active_seeds` / `max_connections` / `seed_ratio_limit` / `seed_time_limit_minutes`（`ServerTorrentSessionConfig`），yaml 读写、admin settings GET / PUT（`settings.torrent` 增量改，非法值整单 400）、WebUI「下载」组字段 + 英文翻译全接上；保存即经 `HeadlessHost.applyConfig` → `ServerDownloadHost.applyTorrentSessionSettings` 重铺到在跑的会话，不进重启集合（`restartRequiredKeys` 的 `torrent` 细化为 `torrent.engine` / `torrent.library` / `torrent.listen`，与 WebUI 的 RESTART 集合一致）。
  - 活跃名额新增「不限」档 `QbConnectionConfig.activeLimitUnlimited`（-1）：`libtorrentActiveLimitArg` 把它换成 int32 最大值下发（libtorrent 读这两项时本来就把负数当 int 最大值，等价），新老 DLL 都走 native 的 `> 0` 分支，不改 native。**服务端默认 `max_active_downloads: -1`**（远程任务交进来就该跑，与本引擎「add 即开始」的语义一致）；`max_active_seeds` 默认 0（libtorrent 5），关上传时已完成种子本来就被策略暂停、不占名额。其余默认值与修复前的行为相同（上传关、限速不限）。
- **[x] ② 已增加自动化测试** — `packages/fushi_server/test/download_host_embedded_policy_test.dart`（工作 isolate 里伪造 C ABI 驱动真 `ServerDownloadHost`：起引擎即 `unchoke(0)`、维护 tick 暂停已完成种子而不碰下载中的、默认活跃名额下发 int32 最大值；改会话设置后立即重铺限速 / 开上传 `unchoke(-1)` / 已完成种子恢复做种 / 名额；`_qbConfig` 逐项映射）。`packages/fushi_server/test/server_torrent_session_config_test.dart`（yaml 缺省 / 往返 / 非法值点名、`applyTo` 只覆盖这几项、admin GET 的重启集合、PUT 增量改写回 yaml 并推进 host 实时配置、非法值 400 不落盘）。
- **备注**：
  - app 侧的活跃名额语义未改（设置页仍是「0 = 引擎默认」，偏好 codec 只收非负数），app 用户同时下 4 个以上种子同样会被排队；要不要给 app 也加「不限」档或改默认属用户可见行为变化，未擅自改，待拍板。
  - 线上那 2 个已在 downloading 却 0 速度的种子：名额问题解释不了（它们已经是活跃态），可能是 swarm / 网络可达性（BT VM 直连）层面的事，本修复不覆盖；新版部署后若名额放开仍普遍 0 连接，需要在 VM 上看 `sessionStatus`（监听端口 / DHT 节点数 / 端口映射）再判。
