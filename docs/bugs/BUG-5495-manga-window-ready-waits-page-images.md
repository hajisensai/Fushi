## BUG-5495 · 漫画窗口文档就绪要等首屏页图取完，Android 上翻页被导航锁挡住
- **报告**：2026-11-26（应用内反馈 eMhRJkkQOW「拆分宽页滑动翻不了页」、wMp05jI72s「切设计系统后漫画一直转圈」、p8PxXVb-xH「换主题风格后漫画无法滑动翻页」，同一台 OnePlus PLK110 / Android 17；日志里反复出现 `MangaFushiPage.turnStall: window load pending >5s: stage=awaitDocumentGeneration … navigating=true pendingDelta=1..7`，p8PxXVb-xH 还有 `ticket.outcome.timeout(10s)` 抛出的 TimeoutException）
- **真实性**：✅ 真 bug。spread 模式每越出窗口就 `loadData` 一份新窗口文档，`_loadInitialWindow`（`fushi/lib/src/media/manga/reader/manga_fushi_page.dart:3926`）在 `awaitDocumentGeneration` 阶段持着导航锁（`_navigating = true`），翻页全进 `_turnQueue` 排队；锁只由 `_markWindowReady` 解开，而它唯一的触发点是 `onLoadStop`（`manga_fushi_page.dart:10001`）。`onLoadStop` 跟着文档的 load 事件走（Android 的 `onPageFinished` 是主帧 load 完成），要等文档里全部 eager 图片取完——窗口文档把当前 ±1 跨页的页图都标成 `loading="eager"`（`fushi/lib/src/media/manga/manga_overlay_html.dart:941`），Android 上每张都经 `shouldInterceptRequest` 过一趟平台通道、再按显示宽度转码（`_interceptRequest` → `_fitPageBytes`）。双页 / 拆分宽页时首屏要 4～6 张，转码队列一忙、或切设计系统后 WebView 重建全部重取，就超过 5～10 秒：导航锁一直挂着，用户看到的就是「滑了不翻页 / 卡好几秒才动」，满 10 秒还抛一条没人接的 TimeoutException。而 `_markWindowReady` 的收尾（装键桥、`__mangaApplyTranslate` / `__mangaScrollToSpread` 落位、OCR 命中层回填）只碰 DOM 与 JS 钩子，根本不需要页图；文档自己也会在 rAF 与 load 后各 `_reanchor` 一次。
- **[x] ① 已修复** — 就绪改由文档自报：窗口文档脚本末尾（全部 `window.__manga*` 钩子与 generation 装好之后）同步调用 `onMangaDocumentReady(generation)`（`mangaDocumentReadySignalJs`，`manga_overlay_html.dart`）；宿主在 `onWebViewCreated` 注册该 handler，走同一个 `_markWindowReady` 入口（generation 闸门不变）。`onLoadStop` 保留为兜底（桥没在文档脚本执行前注入时）。两路信号用 `MangaWindowLoadGate.claimReady` 去重：每一代加载只有先到的那路做收尾，后到的停手；收尾中途抛错经 `releaseReadyClaim` 交还认领，另一路还能接手。收尾主体拆成 `_applyWindowReady`。
- **[x] ② 已加自动化测试** — `fushi/test/media/manga/manga_window_load_gate_test.dart`（同代只认领一次、旧代 / 无在飞加载拿 null、中途失败交还后可接手、已收尾后交还无效、新旧代互不影响）；`fushi/test/media/manga/manga_document_ready_signal_js_test.dart`（node 跑真实信号脚本：带桥时以本文档 generation 调 `onMangaDocumentReady`、没桥不抛；spread / webtoon 文档里信号排在 generation 与 `__mangaApplyTranslate` / `__mangaScrollToSpread` / `__mangaReplaceOcr` / `__mangaVisiblePages` 定义之后、不挂 load 监听、只出现一次；宿主注册 handler 并经 `claimReady` 收尾的源码守卫）。
- **备注**：未在真机复测原始失败路径（本机无该设备；需在 Android 真机 spread + 拆分宽页、以及切设计系统后连续翻页各验一次，`turnStall` 不应再出现）。同一份日志里的 Java `OutOfMemoryError`（`StandardMessageCodec.readBytes` 分配 766 KB 时 256 MB Java 堆耗尽）只是压垮堆的最后一次分配，堆是被什么占满的没有 heap dump 无法定位（同簇 U9mp42sAAL 指向 OCR 模型输出张量整份过平台通道），不在本条修复范围；本修复不改变页图经 `shouldInterceptRequest` 回传的路径。
