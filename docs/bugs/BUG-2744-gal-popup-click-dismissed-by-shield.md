## BUG-2744 · 点击游戏内查词弹窗的按钮会关闭弹窗且随后数秒无法查词
- **报告**：2026-09-27（用户：《王様恋愛》Ver1.00 / KiriKiri Z，内嵌查词弹窗上点发音、制卡等按钮，弹窗直接关闭；之后点台词不再弹窗，要等一会才恢复）
- **真实性**：✅ 真 bug（日志与源码确认，未实机复验）。用户当次 `hibiki_glookup.log`：22:00:50 `global click … inside=1` 落在弹窗内部，紧接着贴附层状态变为 `suspended/shieldHandshakePending`，Dart `nativeInputAllowed=false` 并 `dismiss seq=20`；此后三次点台词都是 `rejected hit … providerAdmission=false`，直到 `gal-shield: handshake pending ended after 13016ms (neutral_wait=12516ms …)`。5 秒时的 `still pending` 行为 `request_seq=15 applied_seq=14`。根因：点弹窗时 LL 钩子以 Popup owner 发布 down/release（`low_level_mouse_hook.cpp` `BeginOverlayClickShieldTransaction`），而 `attached_text_surface_window.cpp` `EnsureShieldHandshake` 只认握手探针（NativeGlyph）与 AttachedGlyph 为自己的输入，把 Popup owner 当成「握手丢失」：先隐藏表面、置 `shieldHandshakePending`，Dart 随即 dismiss 正被点击的弹窗；Popup release 的尾巴要等游戏自己再采样左键才被注入侧放行（`generic_input_shield.inc` `release_waiting`），KiriKiri 很少采样，于是 `IsNeutralForRehandshake` 长时间为假、重新握手发不出去，这段时间所有命中都被拒。这正是 [BUG-2674](BUG-2674-gal-lookup-click-after-popup-ignored.md) 备注里「`neutral_wait` 占大头」的那条分支。
- **[x] ① 已修复** — `attached_shield_status_policy.h` 新增 `ClassifyPopupAfterHandshake`：同一 epoch、同一 HWND 的挑战已被确认后，Popup owner 的 down 与 release 尾巴都归属本宿主。`EnsureShieldHandshake` 在中立门之前按它判 Ready，`ShieldStatusBelongsToCurrentHandshake` 同样认它；注入侧 latch 仍隐藏这次点击直到游戏采样到松开，其后的字形点击照常以自己的 down 接管请求槽（发布只做 CAS，不要求中立），所以准入不必等这条尾巴。重新握手的中立门不变：尾巴未放行时仍不允许新挑战覆盖请求槽。
- **[x] ② 已加自动化测试** — `fushi/windows/runner/tests/attached_shield_status_policy_test.cpp` `TestPopupClickKeepsTheEstablishedHandshake`：尾巴待放行判 Pending、放行后 Acknowledged、尾巴期间仍非中立；未建立握手、换 epoch、换 HWND、别的窗口、allow_risk 一律 Foreign；AttachedGlyph 归属不被放宽。源码守卫要求 `EnsureShieldHandshake` 在 `IsNeutralForRehandshake` 之前做 Popup 归属，`ShieldStatusBelongsToCurrentHandshake` 也调用它。
- **备注**：注入侧放行慢（等游戏采样）本身未改；它现在只影响重新握手，不再挡查词。用户已在《王様恋愛》实机确认：弹窗内发音、制卡等按钮可用且弹窗不关闭，关闭后可立即再查词。等待握手时的 `gal-shield:` 日志附带 owner 与 request/surface 目标 HWND，供同类问题分型。
