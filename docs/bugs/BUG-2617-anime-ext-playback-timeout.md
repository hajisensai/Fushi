## BUG-2617 · Aniyomi 在线源播放必超时
- **报告**：2026-09-21（用户：现在视频 aniyomi 视频播放都会超时）
- **真实性**：✅ 真 bug。四个独立缺陷叠在同一条路径上，每一个都足以让一次起播失败；对照 Aniyomi / Mangayomi，四条全是本仓独有的收紧或遗漏。
  - **① 首开跑在 `network-timeout=5` 上**：`fushi/lib/src/media/video/video_player_controller.dart` 里网络属性（含 `network-timeout=30`）在 `player.open()` **之后**才下发，而 media_kit 建 Player 时就把它钉成 5（`media_kit-1.2.6/lib/src/player/native/player/real.dart:2394`）。在线源的每个字节都要先过 Dart 中继再到远端 CDN，首字节 5~15s 是常态，于是 loadfile 的第一个请求在 5s 被撕掉、媒体压根没打开，页面等满宽限报「播放器打不开该视频」。Aniyomi / Mangayomi 都不设这个参数（mpv 默认 60）。
  - **② `http-header-fields` 被逗号拆坏**：`video_mpv_config.dart` 的 `buildHttpHeaderFieldsProperty` 把每条头拼成 `K: V` 后裸 `join(',')`，而 mpv 的字符串列表属性按逗号分隔项。扩展给的 `User-Agent` 几乎人手一个 `(KHTML, like Gecko)`，一拆就变成半条 UA + 一条没有冒号的垃圾项；`Accept` / `Accept-Language` / `Sec-Ch-Ua` 同理。更糟的是这次下发发生在 `open()` **之后**，把 media_kit 已经用 `MPV_FORMAT_NODE_ARRAY` 安全传好的那份（`real.dart:2145-2178`）整体覆盖掉——HLS 的每个分片从此带着畸形头去要，防盗链站点一律拒。Aniyomi 显式转义（`PlayerActivity.setHttpOptions` 的 `replace(",", "\\,")`），Mangayomi 只用 `Media.httpHeaders`、从不 setProperty。
  - **③ 45 秒桥超时比宿主自己的预算还短**：`desktop_mihon_runtime.dart` 对所有 `/dalvik` 调用一刀切 45s，而两端宿主的 OkHttp `callTimeout` 都是 2 分钟。慢站必然先撞 Dart 这一层——JVM 里那次请求还在跑，用户拿到的却是一句无信息量的「桥超时」，真因（HTTP 状态、解析异常、哪个 hoster 死了）永远到不了失败页；且它经 `_describeLoadFailure` 的裸子串阶梯被报成「网络错误，请检查网络连接」，把用户指向自己的网线。Android 侧则完全没有超时，宿主卡死就无限转圈。Aniyomi 的 `EpisodeLoader` / `HosterLoader` 与 Mangayomi 到同一 sidecar 的 POST 都没有这层闸。
  - **④ 取流串行展开**：`AnimeVideoLoader.loadVideos` 串行遍历每个 hoster、再串行 `resolveVideo` 每条候选，每一步都是一次真实 HTTP 往返。**实测**（vendored sidecar + 真 KickAssAnime v14.61，单 hoster 三条候选）一集取流 **17.6s / 22.4s**——健康源尚且如此，多 hoster 的源必然越过 45s。Aniyomi 是并发展开的。
  - **⑤（同批顺带）取流结果被永久缓存**：`anime_source_video_client.dart` 的 `_resolvedCandidates` 从不失效，`resolveVideos(refresh: true)` 全仓零调用。hoster 给的是一次性 / 短 TTL 签名地址，于是「失败后点重试」重放的是同一条已经死掉的 URL，表现为「重试多少次都超时」。
- **[x] ① 已修复** — `pr/anime-ext-timeout`：网络属性前移到 `open()` 之前；`http-header-fields` 每项带 mpv 的 `%<UTF-8 字节数>%` 长度前缀（值里的逗号不再参与分隔）；桥超时抽成 `kMihonBridgeRequestTimeout = 150s` 两端共用、Android 补上同值、`BRIDGE_TIMEOUT` 在 `_describeLoadFailure` 里显式分派到「连接超时」文案；`AnimeVideoLoader` 改为在 `Dispatchers.IO` 上并发展开（`Semaphore(8)` 封顶，顺序与失败归因不变），并让没自带头的候选继承 `source.headers`；起播路径一律重新解析取流，只有「同一集换线路」复用刚才那批候选，钉住的线路改按菜单标签跨重取认回。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/video_network_timeout_before_open_guard_test.dart`（源码顺序守卫：属性必须在 `open` 之前且只下发一次）、`fushi/test/media/video/video_stream_header_fields_test.dart`（含 `(KHTML, like Gecko)` 真实 UA 与 UTF-8 字节数用例）、`fushi/test/media/manga/mihon_bridge_timeout_guard_test.dart`（从两端 Kotlin 源码读出 `callTimeout` 比对，Dart 必须更晚放手）、`third_party/m_extension_server/overlay/server/src/test/kotlin/mextensionserver/controller/AnimeVideoLoaderTest.kt`（并发用**阻塞** fake 钉死 `Dispatchers.IO`、一条候选炸了不连坐取消兄弟、headers 继承且不覆盖自带头）、`fushi/test/media/video/online/anime_source_video_client_test.dart`（换线路复用一次、其余入口重新解析、钉住的线路按标签认回）。
- **备注**：真机 UI（打包 app 内点开扩展播放）本轮未跑——本机 Windows 构建未做。宿主侧证据是 vendored sidecar 跑真实扩展的取流计时，播放器侧是源码顺序与 mpv/media_kit 的属性语义。**未做、留后续**：上游 M-Extension-Server v1.0.7 的 `MihonVideoProxy`（把取流整个收进 sidecar，cookie / Cloudflare cf_clearance / 限流 / Range / MPEG-TS 修复全部自动生效）本仓 vendored 的 ee55c65 没有，Dart 侧只在中继里重做了 HLS 改写那一小块（BUG-2609），身份层仍是「只把 `Video.headers` 丢给 libmpv」；`MihonVideo.mpvArgs` 仍全仓零消费（Aniyomi 经 loadfile 的 per-file options 下发，有扩展靠它才播得动）。
