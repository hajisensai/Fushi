## BUG-1159 · 文本线程记忆按 ctx 严格匹配掐断文本流，连带语音资源配对失败降级
- **报告**：2026-07-27（用户：截图反馈——捕获工作台里 #84/#85 音频标「已降级 · system_loopback · 5.00s · engine_utterance_unavailable」，并观察到「如果中间有一大段空白，后面的音频容易降级」）
- **真实性**：✅ 真 bug（两处独立缺陷，主因是①）。
  - **① 文本流被掐断（主因）**：`selected_text_thread_id` 存的是具体 `TextSlot::thread_id`，而 `thread_id = FNV1a(processId, addr, **ctx, ctx2**, hookcode, hookname)`（`native/galgame_hook/injector/injector_main.cpp:444-458`）含调用上下文。`LunaTextSelector::ShouldWrite` 对手动/记忆选定值做精确匹配 `manually_selected == thread_id`（`native/galgame_hook/include/luna_text_selector.h:95` 修复前），同一 hook 面换个调用路径（ctx/ctx2 变）就整行丢弃。而 Hibiki 侧 `_maybeRestoreTextThread`（`hibiki/lib/src/mining/gal_hook_session_controller.dart:1995`）会**自动**恢复上次会话记住的线程——其注释已自陈「指纹只能锚到 hook 而锚不到具体并行线程（**ctx 未透出**）」，即用 hook 粒度的记忆锁上了 thread 粒度的门。用户本次并未手动选线程。
  - **② 配对窗口两侧不一致（放大器）**：native 打标窗口 `kKirikiriFollowingTextWindowMs = 1500`（`native/galgame_hook/hook/voice_resource_pairing.h:8`），Dart 收标窗口 `eventIdToleranceMs = 1000`（`hibiki/lib/src/mining/galgame_audio_source.dart:384` 修复前）。两常数无任何交叉引用。1000~1500ms 是死区：native 判定配上并把 `TextSlot::seq` 写进资源文件名，Dart 因超差拒收，而带 marker 的资源又被明确禁止回退时间窗兜底（同文件 `:413-414`），于是**打了标反而比没打标更容易失败**。
- **真机实测证据**（`%TEMP%\hibiki_gal_voice\`，用户报告当次会话）：dump 共 146 个文件，其中 **92 个（63%）无 `_hibiki_textseq` marker**；`textseq84` / `textseq85` 根本不存在；`textseq83`（tick 568503312）之后连续 **16 句**语音资源全部无 marker，tick 间隔规整 5~8 秒（568509359 … 568597593），直到 568675843 才恢复打标。降级两句对应的资源 `568591703_yuz_001_0012.ogg` / `568597593_yuz_001_0013.ogg` 均在盘上（`yuz` = 该场景说话角色由月）——**语音抓到了，文本没到**。用户说的「中间一大段空白」即此：那 94 秒游戏一直在说话，Hibiki 只收到 2 行文本。
- **失败链**：ctx 变 → 文本行被 `ShouldWrite` 丢弃 → 文本环无候选 → `ResolveFollowingSelectedText` 1500ms 内找不到 line 事件 → `kExpired` → 资源写成无 marker 裸名 → Dart 侧只剩 `[textTs-330, textTs-130]` 这 200ms 窗口兜底 → 兜不住 → `engine_utterance_unavailable` → `_cacheLoopbackLineAudio`（`gal_hook_session_controller.dart:3608`）落 system_loopback 5.00s。
- **[x] ① 已修复** —
  - `native/galgame_hook/include/luna_text_selector.h`：新增纯函数 `LunaSelectedThreadAccepts`，把手动/记忆选择的**过滤粒度**从 thread_id 放宽到 hook 面；`LunaTextSelector` 内部维护 `thread_face_`（thread_id → face）映射，新增公开 `NoteFace` 登记入口，`ShouldWrite` 新增可选 `face_id` 参数。face 未知时退回精确匹配，语义与旧实现一致。**刻意不改 thread_id 算法**——ctx 参与 thread_id 用于诊断/区分并行调用点是有意设计，本 bug 只在于拿它做过滤。伪影门 `if (artifact) return false` 仍在选择之前，放宽粒度不会让伪影漏进来。
  - **face 只去掉 `ctx`，保留 `ctx2`**：LunaHook `ThreadParam` 的两个上下文字段语义完全不同——`ctx` 是调用点（返回地址），同一句台词换剧情分支就变，正是本 bug 的根因；`ctx2` 是 **split H 码的 split 值**，是引擎适配方显式声明的语义分类（典型就是「角色名 vs 正文 vs 选项」）。把 ctx2 一并去掉会让 split H 码引擎的角色名被当成「同一 hook 面的兄弟线程」混进正文流——那是新引入的文本污染，比原 bug 更糟。保留 ctx2 是保守方向：最差也只是对该维度维持旧的精确匹配行为。
  - `LunaTextThreadIdFrom` / `LunaTextFaceIdFrom` / `LunaFnv1a64` 从 `injector_main.cpp` 上提到 `luna_text_selector.h`，injector 侧改为委托。目的是让跨引擎负向测试能拿真实引擎的 `(addr, hookcode, hookname, ctx, ctx2)` 驱动**生产实现**，而不是手捏 face 常量自证。
  - `native/galgame_hook/injector/injector_main.cpp`：`LunaShouldWriteLine` 在**所有过滤分支之前**调用 `NoteFace` 登记 hook 面。此前登记只发生在 `LunaTextSelector::ShouldWrite` 内部，而 `preferred_hook_codes` 快路整段不进选择器——走快路的线程永远没有 face。Dart 的 `_maybeRestoreTextThread`（`gal_hook_session_controller.dart`）恰恰只从「本会话已出过 >= 3 行」的线程里挑一条写进 `selected_text_thread_id`，于是 `FaceOf` 返 0 → 退回精确匹配 → **原症状原样复现**。登记提前后，「选定线程本会话已出过行」硬性蕴含「face 已知」，跨会话恢复路径被完整覆盖。
  - `hibiki/lib/src/mining/galgame_audio_source.dart`：新增 `kGalVoicePairingWindowMs = 1500` 并让 `eventIdToleranceMs` 默认取它，消掉 1000/1500 死区。同时把 `eventDist` 从 `.abs()` 双边收窄为单边 `textTsMs - tick >= 0`——native 只保证 `resource_tick <= text_ts <= resource_tick + 窗口`（`voice_resource_pairing.h` 的 `ResolveFollowingSelectedText`），双边判定等于凭空翻倍容差、白扩大陈旧 dump 文件的碰撞面。「带 marker 的资源只认自己那条文本」这条防错配纪律保持不变。
- **[x] ② 已加自动化测试** — 两层：
  - `native/galgame_hook/tests/luna_text_replay_test.cpp`（行为层）：改用**真实引擎参数**驱动生产实现 `LunaTextFaceIdFrom` / `LunaTextThreadIdFrom`，不再手捏 face 常量。覆盖：ctx 不同必须真的分线程（32）、**跨引擎负向**——KiriKiriZ 与 SiglusEngine 两个 hook 面 face 不得相同（33）且另一引擎的行不得被并进选定线程（37）、**split H 码负向**——同 addr 同 hookcode 仅 ctx2 不同（角色名）face 必须不同（34）且必须被挡掉（39）、同 face 不同 ctx 必须放行（36，核心回归点）、伪影不得因放宽而漏入（40）、face 未知退回精确匹配（41）、**跨会话恢复路径**——只经 `NoteFace` 登记（未进过 `ShouldWrite`）的线程其兄弟线程也必须被认回（42/43）且 `Reset` 必须清 face 表（44）。
  - `hibiki/test/mining/gal_voice_pairing_window_parity_test.dart`（PR 门层）：C++ ctest 只在 `voice-hook-helper` workflow（`workflow_dispatch` + push develop）里跑，**PR 时不是门**，故补两条扫真实 C++ 源码的结构守卫——`LunaTextFaceIdFrom` 必须 hash `ctx2` 且不得 hash `ctx`；`LunaShouldWriteLine` 里 `NoteFace` 的位置必须早于 `preferred_hook_codes` 分支。另加「资源晚于文本时不得配对」的单边窗口行为测试。
- **验证**：`luna_text_replay_test.cpp` 用 MSVC 2022 x64（`cl /utf-8 /std:c++17`）本机编译并跑真 fixture，exit 0。负向验证逐条做过：face 去掉 ctx2 → 返回码 **34** 转红；`NoteFace` 置空 → **36** 转红；三处 native 改动同时回退 → Dart 三条结构守卫全部转红；`eventDist` 改回 `.abs()` → 单边窗口测试转红。全部还原后 C++ exit 0、Dart 7/7 通过。
- **边界（本次未覆盖，如实记录）**：Dart 侧的跨会话记忆存的是**弱指纹**（`textThreadFingerprint`：有 hook code 时用 `code:<hookCode>`，否则用 label），有 hookCode 时会丢掉 `threadAddress`，粒度反而比 native face **更粗**；同一 hookCode 下多个 addr 会撞成同一指纹，只能靠「已出 >= 3 行 + 行数最多」消歧。native 侧的分面修复不改变这一点。`threadAddress` 其实早已透出到 Dart（`flutter_window.cpp` 的 `pollText` 已编入 `threadAddress` / `threadContext` / `threadContext2`），但 `TexthookerTextThread` 没把它留成独立字段。要让 Dart 记忆与 native face 严格同粒度，最小改动是给 `TexthookerTextThread` 加 `threadAddress` 并把指纹改成 `code+addr`——涉及持久化格式与旧记忆兼容，不在本 PR 范围。
