## BUG-5177 · 视频暂停 OCR 点「中」查词串却从上一行「@utaskyat」的 u 开始
- **报告**：2026-11-21（应用内反馈 WgeFHwdQ65，Windows，本地视频暂停 OCR）
- **真实性**：✅ 真 bug（现象成立，原始帧的识别几何没取到，确切成因待取证）。
  - 证据：反馈截图的查词弹窗写「没有找到『utaskyat私は中2から…』」；本机 `video_diag_log.txt` 16:20:22 / 16:20:25 两次 `[lookup] begin term=utaskyat…(268)`，同一位置点了两次都落在「u」——是稳定的映射错，不是偶发。日志里没有截屏识字的 `floating_ball.screen_ocr_*`，入口是视频暂停 OCR（`video_graphic_subtitle_ocr_overlay.dart` → `video_fushi_page.dart` `_handleGraphicSubtitleOcrLookupTap` → `_handleSubtitleLookupTap`，从被点字素起扫词）。
  - 已确认的结构缺陷：`fushi/lib/src/media/video/video_graphic_subtitle_ocr_overlay.dart:470-482`（修前）每个字一个 `Positioned` + 不透明手势框，字框重叠时完全由 `Stack` 叠放顺序（后画的赢）决定点中哪个字，没有任何几何判据；截屏识字的 `screenOcrHitTest`（BUG-4069）早已改成按几何裁决。斜行的轴对齐字框、注音 / 下划线扁框盖到别的字上时，点哪个字跟点在哪无关。
  - **分诊结论有一处与代码不符**：分诊推测「表头行的框盖住了正文的『中』，叠放顺序让表头赢」。但同一块里表头行的字排在正文行之前，`Stack` 命中是后画的先测——正文「中」的框若也盖住落点，赢的本该是「中」。所以这次「u」能赢，说明落点处**根本没有正文那一格**：要么正文行的字框摆偏 / 被裁薄（识别几何），要么整层字框相对画面有偏移（坐标映射），要么识别器把两行并成一行按字数均分。这三种都需要原始帧的字框几何才能分清，而这条路径修前点字时什么都不记。
- **[x] ① 已修复（命中裁决 + 取证）** — 本 PR：
  - 点中哪个字改由整层几何裁决：`graphicSubtitleOcrHitTest`（落点在框里「最深」的那个：偏移按半宽 / 半高归一取较大一维；一样深取面积小的；再一样取排在后面的，同旧叠放顺序）。每个字框只负责「这一击归不归本层」与鼠标手形。
  - 点字诊断 `video.pause_ocr_tap`（进错误日志随反馈上传）：落点、控件 / 显示 / 帧图尺寸、fit、盖住落点的框数、命中字及其帧图 / 控件字框、离落点最近 4 个字框、整句前 32 字。下一份同类反馈可以直接回放，分清是识别几何、坐标映射还是裁决。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/video_graphic_subtitle_ocr_overlay_test.dart` 组「点字命中裁决（BUG-5177，反馈 WgeFHwdQ65）」：纯函数（与排列顺序无关、无框不归本层、并列规则）+ 真覆盖层 widget 测试（斜行下一行的高框盖住上一行行尾的字，点正中查的是上一行那个字）+ 诊断行内容。变异实测：把裁决改回「后面的框赢」，3 条变红；恢复后全绿。
