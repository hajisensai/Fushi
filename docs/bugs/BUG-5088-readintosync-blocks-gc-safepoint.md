## BUG-5088 · readintosync-blocks-gc-safepoint
- **报告**：2026-11-21（用户：「fushi 内 UI 很卡，看看是不是 SRS 把 UI 线程粘住」）
- **真实性**：✅ 真 bug，但不是 SRS。安装版 3.4.0-debug.30562 实测：对主线程（UI isolate）每 20～40 ms 挂起读栈，10 分钟 14464 个样本里在 `fushi_fsrs.dll` 的只有 0.2%；主线程约一半时间停在 `ntdll` 等待，单次最长 1.27 s。用自编引擎 PDB 符号化：`Heap::AllocateNew → GcSafepointOperationScope → SafepointHandler::WaitUntilThreadsReachedSafepointLevel → ConditionVariable::Wait`——UI isolate 要 GC，在等同 isolate group 的别的线程到安全点。当天的 `hang-2828-*.dmp`（18:33 / 18:45，主线程停 4～7 s）是同一条栈。等待时抓的全线程 dump 里，拖后腿的线程停在 `bin::Builtin_File_ReadInto → _read`。Dart VM 的 `File_ReadInto`（`runtime/bin/file.cc:238`）用 `Dart_TypedDataAcquireData` 持有目标数组，开 no-callback scope；`TransitionNativeToVM` 的析构（`runtime/vm/heap/safepoint.h:456`）在这种情况下不让线程进安全点，所以整段磁盘读期间整个 isolate group 都没法 GC。源头是 `packages/fushi_compute/lib/src/hash/ffc_hash.dart` 的 `ffcSha256FileSync` 逐 1 MiB `readIntoSync`，由当天合入的 `VideoFingerprintWarmer`（c267ac33e29）在 `Isolate.run` 里对整个视频库挨个做全文件 SHA-256（实测读盘约 6.6 MB/s，每块 100 ms 以上），UI 持续掉帧、偶尔卡死数秒。`packages/fushi_engine/lib/utils/archive/native_zip.dart` 的 `_fileCrc32` 是同形问题（4 MiB 一块，打 zip 时）。
- **[x] ① 已修复** — 整文件哈希下沉到 Rust：`native/fushi_compute/src/hash.rs` 新增 `ffc_hash_sha256_file` / `ffc_hash_crc32_file`（读盘 + 计算一次做完，IO 失败回新状态码 `IO_ERROR = -5`），Dart 以非叶 FFI 调用，线程全程处于 native 态、算安全点。`ffcSha256FileSync` 改走原生，新增 `ffcCrc32FileSync` 并替换 `_fileCrc32`；仓内不再有 `readIntoSync`。
- **[x] ② 已加自动化测试** — Rust `hash::tests::whole_file_hashes_match_in_memory_digests_and_report_errors`（跨 1 MiB 块边界 / 空文件、字节数、IO / 非 UTF-8 / 空指针错误码）；`packages/fushi_compute/test/ffi_hash_test.dart`（CRC 文件与分段结果一致、读失败抛 `FileSystemException`）；源码守卫 `fushi/test/build/read_into_sync_gc_guard_test.dart` 禁止 app 与 packages 里再写 `readIntoSync`。
- **备注**：SRS 本身另有一份 17:57 的 `hang-24156-*.dmp`，主线程在 `fushi_fsrs.dll` 里等锁。那份 DLL 是旧构建、已被覆盖，偏移对不上导出表，未定位，也不在本修复范围内。若再出现 `MainThread.hangRecovered` 且栈在 fsrs，用当时那份构建的 DLL 符号化。`dart:load_stats` 一次 50～60 s 是异步的，不占 UI 线程。
