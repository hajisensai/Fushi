## BUG-3663 · bilibili-mining-412-anonymous-api
- **报告**：2026-10-22（用户：反馈 Atbl_kOuZK，Windows 3.0.0，人在国外——B 站网页制卡全部失败，B 站接口回 412，此前一直能用）
- **真实性**：✅ 真 bug（外部风控变化触发，但把解析放在匿名请求上是我们的设计缺口）。日志 `Anki.mineImmersion.bilibili` 连续报 `bilibili view request failed`，栈 `BilibiliClipMiner._resolveNow`（`fushi/lib/src/mining/bilibili_clip_miner.dart` 约 314 行）← `_AppModelRemoteLookupService.mineImmersion`。稿件（`/video/BV...`）的 `x/web-interface/view` 与 `x/player/playurl` 由 **app 服务端**发不带 cookie 的匿名请求（`_defaultFetchJson`），B 站风控对这台机器（海外 / 代理出口）回 HTTP 412；而同一台机器上的页面本身能播放，因为页面请求带着用户会话。`_defaultFetchJson` 还把非 200 一律吞成 `null`，日志里看不出是 412。
- **[x] ① 已修复** — 扩展 `background.js` 新增 `fushiResolveBilibiliUgcPlayurl`：与番剧（BUG-2574）同一范式，在**页面主世界**里发页面自己会发的 view + playurl 请求（同源 Origin、浏览器自带 cookie，不改 UA、不伪造头，凭据不出浏览器），只回传 playurl 响应体；`AppModel.mineImmersion` 的 bilibili 段带了响应体就 `buildPgcRequest` 只挑流（`usePagePlayurl`），没带（旧扩展 / 页面注入失败）才回落服务端自己解析。服务端匿名请求非 200 改抛 `BilibiliApiHttpException`（带状态码），412 时给出单独的失败原因。没有做「缺媒体仍出卡」的降级：这条路 `requireAudio=true` 是既有不变式（`remote_mining_bilibili_branch_guard_test.dart`），静默出一张无声卡更糟。
- **[x] ② 已加自动化测试** — `fushi/test/mining/bilibili_clip_miner_test.dart`（稿件 data 顶层响应体走页面路径且零网络请求；412 带状态码上抛）、`fushi/test/mining/remote_mining_bilibili_branch_guard_test.dart`（`usePagePlayurl` 接线 + 扩展对 kind=bilibili 调页面解析 + 内置扩展副本同步）。
- **备注**：未在真实 412 网络环境复测（本机直连不触发风控），状态 implemented_unverified；需要反馈人更新到带新扩展的版本后确认。
