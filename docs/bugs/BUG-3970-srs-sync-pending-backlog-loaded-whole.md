## BUG-3970 · srs-sync-pending-backlog-loaded-whole
- **报告**：2026-11-02（用户：应用内反馈 6fSVptGebt / IUS9S0lWiZ / P8Kaf1_y0c，Android 同步一轮里 Scudo OOM SIGABRT，面包屑停在 srs_sync `start` / `downloading:ingest`，RSS 0.4–1.5 GB）
- **真实性**：✅ 真 bug（无界分配，沿真实代码路径确认；是否就是这三份闪退的唯一元凶**未坐实**，见备注）。收段会话每开一次（每轮同步、每批第一片），`Delivery::load` 把整张因果缓冲表 `sync2_pending` 的 (设备, seq, 链值) 全部读进内存队列（`native/fushi_fsrs/src/store/sync2/transport.rs:587-597`，修复前），而且会话跨片缓存这份队列、`spill` / `checkpoint` 后也不丢已落表的项。缓冲表在「某台设备依赖的段到不了这个位置」时无界堆积（relay.rs 文件头记录过的场景），每条队列项约两百字节，几十万行 = 上百 MB，并在每一轮同步开头重复整表读一次。另：投影每条修改操作为取 ID 先整份算一次 `edit_row`（解析 / 合并旧修改记录闭包 `legacy_closure`），落地时再算一次（`native/fushi_fsrs/src/store/sync2/mod.rs:818`、`semantics.rs:320`，修复前），收段时同样大小的临时分配翻倍。
- **[x] ① 已修复** — 投递队列改成按设备分窗读缓冲表：`Delivery::load` 只读各设备行数（`transport.rs:618`），队首超出已读窗口才 `Delivery::refill` 读下一窗（至多 `DELIVERY_WINDOW` = 4096 条/设备，`transport.rs:538`、`:707`），`spill` / `checkpoint` 之后 `Delivery::trim` 把已落表的项截回一窗（`transport.rs:690`）；缓冲表同一 (设备, seq) 仍以表为准，`pending` 改由行数增减维护。投影只取 ID 的地方改用不算 ctx 的 `edit_row_id`（`mod.rs:592`）。提交：（由集成方提交，见本轮合并提交）
- **[x] ② 已加自动化测试** — `native/fushi_fsrs/src/store/sync2/tests_delivery_window.rs`：B 的全部操作等着 A 时，分片收段会话里内存队列项始终 ≤ `DELIVERY_WINDOW`（测试里压到 3，积压 ≥ 40 条）、`pending` 等于缓冲表行数，下一轮会话不再整表读入，A 到了以后积压按窗放行、投影与一次收齐逐字节相同；一次收完路径同测；`edit_row_id` 与 `edit_row` 的 ID 相同。测试配置下窗口 = 3，全部 sync2 端到端用例（94 条）都反复走「读下一窗 / 截窗再读回」。
