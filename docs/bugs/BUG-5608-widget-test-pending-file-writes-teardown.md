## BUG-5608 · 反馈页 / 排行榜 widget 测试偶发 tearDown 删临时目录 errno 32（落盘写到一半就收尾）
- **报告**：2026-11-28（用户：PR #4598 分块跑测试时 `feedback_pages_test` 偶发红，要求两边对比统计并按根因修，不许判伪红）
- **真实性**：✅ 真 bug（测试侧，develop 基线同样复现）。同一批 130 个文件、并发 4、`--no-cache` 各跑 3 次：develop 合并基 `3706622ff1a` 红 2/3（一次 `leaderboard_ui_test`，一次 `feedback_pages_test` 两条），本分支红 2/3（两次都是 `leaderboard_ui_test`）。在 tearDown 里列出删不掉的文件：`feedback/tickets.json.tmp`（`FeedbackTicketStore._writeNow`，`fushi/lib/src/feedback/feedback_store.dart:223`）与 `leaderboard/profile_1.self.json.tmp`（`LeaderboardStore.writeSelf`，`fushi/lib/src/leaderboard/leaderboard_store.dart:255`）。页面发起的「临时文件 + rename」落盘是不 await 的后台写，跑在 `testWidgets` 的 fakeAsync 区里：IO 线程做完每一步后，续体（含关闭句柄）只在 pump 时推进。测试体在界面已刷新、落盘还没走完时结束，之后再没人 pump，临时文件句柄永远不关，tearDown `deleteSync` 在 Windows 上即 `PathAccessException`（errno 32）。哪条撞上取决于那一刻的 IO 快慢（机器负载高时更常见），所以单独跑总是绿。与 BUG-5604 的生命周期改动无关（基线同样红、占着的是 store 的写句柄，不是页面资源）。
- **[x] ① 已修复** — `fushi/test/helpers/pending_file_writes.dart` 的 `drainPendingFileWrites`：用例末尾先摘树（dispose 里起的落盘也算进来），再交替 `runAsync` 让真实 IO 走一步、`pump` 推进 fakeAsync 续体，直到根目录下没有 `*.tmp` / `*.lock` 且 `FeedbackTicketStore.debugHasPendingWrites`（新增，串行写队列）为空、连续两轮都满足；超过上限直接判失败并列出残留文件（真泄漏不被 tearDown 吞掉）。两个测试文件的 `testWidgets` 在 `main` 里包一层，每条用例都走它。
- **[x] ② 已加自动化测试** — 修复本身就在测试里。验证：同一批 130 个文件、同样并发、`--no-cache` 在本分支连跑 3 次，3 次全绿（exit 0，各 +1354）。收尾等落盘还顺带暴露了一处测试时序：用例在服务的 `forget` 落盘返回前就结束，先摘树会把 provider 持有的 `FeedbackService` dispose 掉、续体再 `notifyListeners` 即断言，所以 helper 先在树还挂着时等完，再摘树再等一轮。
- **备注**：生产代码不受影响（真实 app 的事件循环一直在转，写一定会走完）。别的测试若同样「页面起后台落盘 + tearDown 删临时目录」，照这个 helper 收尾。
