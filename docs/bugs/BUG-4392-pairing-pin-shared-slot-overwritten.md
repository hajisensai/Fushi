## BUG-4392 · 配对 PIN 存在全局单槽，另一个配对请求会把审批框上的 PIN 换成别人的
- **曾用号**：PR 分支 `pr/interconnect-host-auth` 的提交信息把本条写作 BUG-4281（合入 develop 前的旧号；改号提交 `080b4a41c72`、`71ab2acf8c9`）。develop 上的 BUG-4281 是另一条无关的 bug，按提交信息搜号时以本文件为准。
- **报告**：2026-11-10（用户：互联 host 安全审查 H6）
- **真实性**：✅ 真 bug。（行号按 94317ab6295）`packages/fushi_engine/lib/sync/fushi_sync_server/pairing.part.dart:150-178` 的 `_handlePairV2` 在 `onPairRequest`（app 审批串行化）之前、且对免 PIN 会话也调 `onPairPinGenerated`；app `fushi/lib/src/sync/fushi_server_controller.dart:1124-1128` 的 `_generatePairPin` 把 PIN 写进全局 `_pendingPairPin`（`:499-508`），审批框 `:1382`、`:1427` 每次 build 现读它；收起回调 `onPairSessionResolved`（`packages/fushi_engine/lib/sync/fushi_sync_server.dart:515`）不带参数，任意会话的 confirm / 过期都收起当前框（`pairing.part.dart:285,310`）；`_promptPairApproval`（`:1253-1255`）对常驻（lingering）框不看来源就取代、并把新会话 PIN 恢复进单槽。无头 `packages/fushi_server/lib/src/headless_host.dart:794-816` 的 `_pendingPairing` 同样是单槽。修复前实测（旧 API 临时测试）：S1 已允许、常驻显示 482913 时，另一来源 198.51.100.9 的 pinRequired 请求把框换成显示 771122（「免 PIN 会话调用供给器」一条按代码路径确认，修复前测试因请求构造问题未跑出断言）。
- **[x] ① 已修复**（`0fe65ed19a2`）— 引擎：`FushiPairRequest` 加 `sessionId` / `pin` / `sourceKey`；`onPairPinGenerated` 只在 pinRequired 非票据会话、锁定检查之后调用，返回值存进会话并经 `request.pin` 交给审批；`onPairSessionResolved` 改为 `void Function(String sessionId)`；`_pairSessionTtl` 公开为 `kFushiPairSessionTtl`。app：删 `_pendingPairPin` / `_generatePairPin` / `_pairDialogLingering`，不再设 `onPairPinGenerated`；弹窗捕获 `request.pin`；记 `_pairDialogSessionId` / `_pairDialogSourceKey`，收起回调只在会话 id 相符时收起；取代条件改为「同 sourceKey」（常驻框与未决框都只被同源请求取代，不同来源被拒、旧框与 PIN 保留）；`debugPromptPairApproval` 删 `seedPin`，加 `debugPairSessionResolved`；常驻兜底计时改用 `kFushiPairSessionTtl`。无头：`PendingPairing` 加 `sessionId`，改为按会话的 `LinkedHashMap`（上限 8，满了丢最旧），在 `_approvePairing` 登记；`pendingPairings`（剔除过 TTL 的）+ `pendingPairing`（最新一条，兼容）；收起只删对应会话；admin API `GET /api/admin/pairing` 加 `pendingList`（不下发 sessionId），WebUI 渲染全部待输入 PIN（缺省退回 `pending`）。
- **[x] ② 已加自动化测试** — `fushi/test/sync/interconnect_pair_pin_per_session_test.dart`（不同来源不取代常驻框、别人的 PIN 不上屏；收起回调只收起本会话；IPv6 同一 /64 换地址仍可取代、被取代会话迟到的收起不碰新框；并入原 `interconnect_pair_loopback_hint_test.dart` 的回环提醒用例）、`fushi/test/sync/fushi_sync_server_pair_v2_test.dart`（免 PIN 会话不调供给器；`onPairRequest` 收到的 pin / sessionId / sourceKey 与 confirm 一致；收起回调带本会话 id）、`packages/fushi_server/test/headless_pending_pairings_test.dart`（真 `HeadlessHost` 两次 pinRequired 配对各留一条、admin `pendingList` 两条且无 sessionId，confirm 第一条后只剩第二条）。按新 API 改写：`interconnect_repair_lingering_dialog_test.dart`、`interconnect_pending_pair_supersede_test.dart`。
- **评审修正（2026-11-11，`ea38207cdab`）**：引擎交给宿主的 `FushiPairRequest.sourceKey` 只在来源键可信时非 null（回环对端、带转发头却非可信代理的对端、`p2p:?` 给 null），app `_isSamePairSource` 对 null 判不同源——经本机 frp / cloudflared 进来的陌生人不再能以「同源」顶掉别人的常驻 PIN 框。代价：本机 127.0.0.1 上的 client 重试不再取代自己滞留的未决框（等 60 s 自动拒绝或主人手动关）。测试：`fushi_sync_server_request_origin_test.dart`「审批请求只带能区分真实来源的 sourceKey」；`fushi_sync_server_pair_v2_test.dart` 回环来源的 `sourceKey` 断言改为 null。
- **备注**：仓内 API 变化，无 wire 变化。行为变化：app 常驻 PIN 框不再被**不同来源**的请求取代（以前任意来源都能顶掉），同一 client 重新配对仍可（BUG-708 / BUG-987 不回归）。
