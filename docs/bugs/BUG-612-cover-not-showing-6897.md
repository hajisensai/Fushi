## BUG-612 · 6897书籍封面检测到却不显示回归（TODO-1319）
- **报告**：2026-07-08（用户：更新到 build 6897 后书架书籍封面不显示；重新导入也不显示，但导入过程中封面是检测到的）
- **真实性**：✅ 真 bug（针对 case-sensitive 设备的跨设备/备份恢复书）。根因 `hibiki/lib/src/media/sources/reader_hibiki_source.dart:407` `_resolveCoverUrl` 与其调用的 `coverCandidatePaths`（同文件 `:348`）把 `EpubBooks.coverPath`（导入时落库的相对封面 href）与 `extractDir` 直接 `p.join` 后 `File(...).exists()` 探测，**大小写严格**。而 `coverPath` 的值由 `hibiki/lib/src/epub/epub_parser.dart:530` `_itemRelHref` 经 `p.canonicalize(p.join(opfDir, item.href))` 生成——`p.canonicalize` 在大小写不敏感宿主（Windows / 默认 macOS）上会把整条路径**小写化**（实测 `EpubParser.parseSync` 在 Windows 产出 `coverHref=oebps/images/cover.jpg`），而解压落盘（`epub_parser.dart:237` `_safeArchivePath`，TODO-739）刻意**大小写保留**（真实文件是 `OEBPS/Images/Cover.jpg`）。同机（Windows/macOS 大小写不敏感 FS）上 `File.exists` 不区分大小写，封面照常显示，看不出问题；但当这本书带着小写化的 `coverPath` 抵达 **case-sensitive 设备（Android/Linux）** 时——路径①备份在 Windows、恢复到 Android（`hibiki/lib/src/sync/backup_service.dart:2374-2377` `insertEpubBook(coverPath: b.coverPath)` **原样写回、不重解析**），或②任何原样搬 DB+extractDir 的数据拷贝——`File(join(extractDir, "oebps/images/cover.jpg"))` 找不到大小写保留的 `OEBPS/Images/Cover.jpg`，`imageUrl` 塌成 null，封面「导入时检测到、书架不显示」。用户「重新导入也不显示」符合标题唯一去重（`resolveBookTitleConflict`）保留旧坏行、导入对话框预览只是临时解压的即时解析这一链路。互联下载路径不受影响（对端经 `EpubImporter.importFromPath` **重解压重解析**，在本机产出大小写正确的 coverPath）。**单机导入不复现**（同机 case-insensitive；纯 Android 导入 posix canonicalize 不小写）——已用 `EpubParser.parseSync` + `coverCandidatePaths` 端到端跑通验证管线在单机上工作正常。
- **[x] ① 已修复** — `hibiki/lib/src/media/sources/reader_hibiki_source.dart` `_resolveCoverUrl` 在大小写严格的直接探测（含 BUG-513 last-good 回落）全部落空后，新增最后一道 case-insensitive 兜底：调用新增纯函数 `resolveCaseInsensitive`（`@visibleForTesting`，逐段把声明封面与 `cover.jpg/jpeg/png` 兜底名在 `extractDir` 下按目录实际条目**先精确大小写、再大小写不敏感**匹配、逐层下降），命中即取磁盘上真实大小写保留的文件、写回 last-good 缓存并以 `file://` URL 返回。这样即便持久化的 `coverPath` 大小写被大小写不敏感宿主搞错，书架/详情/SRT 关联封面（都经 `MediaItem.imageUrl`）也能在 case-sensitive 设备上找到真实封面文件——把「coverPath 大小写必须与磁盘逐字符一致」这一跨平台无法保证的隐式契约，改成「按磁盘真实条目大小写容忍解析」。真实修复位置 `reader_hibiki_source.dart`（`_resolveCoverUrl` / `_listDirEntries` / `resolveCaseInsensitive`）。提交见本轮。
- **[x] ② 已加自动化测试** — `hibiki/test/media/sources/reader_hibiki_cover_case_insensitive_test.dart`：(1) 纯函数 `resolveCaseInsensitive`（mock listDir）5 例锁死逐段大小写不敏感解析、声明封面优先于兜底、声明失败回落 cover 兜底、全落空返回 null、绝对路径候选跳过——宿主无关、Windows/Linux 皆确定性绿；(2) 端到端真实解析链：`extractDir` 落盘大小写保留 `OEBPS/Images/Cover.jpg`，DB `coverPath` 存小写 `oebps/images/cover.jpg`，`mediaItemForBookKey` 解析出的 `imageUrl` 必须指向磁盘上真实存在的封面文件——**case-sensitive 平台（Linux CI）修复前直接探测按大小写落空 → imageUrl==null → 该断言红（回归守卫）**，修复后 case-insensitive 兜底命中 → 绿；case-insensitive 平台恒绿。既有 BUG-513 封面缓存单测保持全绿（本修复不改直接探测/last-good 语义，只在其后加兜底）。
- **备注**：上游次因是 `epub_parser.dart:530` `_itemRelHref` 用 `p.canonicalize` 生成 coverHref 会在 Windows/macOS 小写化（与 TODO-739 大小写保留解压不一致）。本轮选择在**读取边界**做大小写容忍解析（能治愈用户设备上已存在的坏行、无需重新导入或数据迁移，且对 case-insensitive 直接探测零影响），未改动 security-sensitive 的解析器 `_itemRelHref`。仍存一处同类未覆盖点：制卡封面 `hibiki/lib/src/pages/implementations/reader_hibiki/mining.part.dart:31` 也用 `File(p.join(_extractDir, _book.coverHref))` 直接拼，跨设备小写 coverHref 在 case-sensitive 上同样会落空（属 TODO-1299/BUG-588 领域，本轮未扩展）。真机验收口径：在 Android 设备上打开一本封面不显示的书（尤其从 Windows 备份恢复/互联而来），书架卡应显示封面；重新导入的书封面也应显示。
