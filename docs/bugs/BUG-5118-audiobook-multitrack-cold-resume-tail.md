## BUG-5118 · audiobook-multitrack-cold-resume-tail
- **报告**：2026-11-22（外部审计 HBK-AUDIT-036，Codex 2026-11-21 PR 审查，源自 PR #3846）
- **真实性**：✅ 真 bug。多文件有声书冷启动 `AudiobookPlayerController.load()`（`fushi/lib/src/media/audiobook/audiobook_controller.dart:1358`，修前 :1345）恢复存档时调 `splitGlobalMs(savedMs, _fileDurationsMs, lastFileDurationMs: _knownLastFileDurationMs)`；但 `_knownLastFileDurationMs`（:1041）要求 `_player.currentIndex == 末文件` 且 just_audio 已报时长，load 刚 `setAudioSource(preload: false)` 时恒为 null，于是末文件上界退回 cue 估算（末句 `endMs`）。存档落在末句之后的片尾静音 / 音乐里时被夹回末句，重开跳回末句。PR #3846（BUG-5006）只修了「已在播末文件时拖进度条」这条路径。新加测试在修前红：`currentFilePosition.positionMs` 期望 60000 实得 8000。
- **[x] ① 已修复** — load 改用 `splitGlobalMs(..., clampLastFile: false)`（`audiobook_controller.dart:1358`），保留目标文件与文件内偏移，不再在末文件真实时长未知时按 cue 估算夹上界；上界交给平台在载入该文件后按真实时长施加（越界落点落到文件末尾），`_updateCurrentCue` 的 `ActivationRestoreTick.unreachable` 分支（:2409）随即解除激活挡板。曾试过在 unreachable 分支再显式 seek 到真实末尾，变异实测（撤掉该 seek）测试仍绿、对外行为无差别，已删掉不留冗余代码。
- **[x] ② 已加自动化测试** — `fushi/test/media/audiobook/audiobook_multifile_global_position_test.dart` 组「cold start resumes into the last file tail (HBK-AUDIT-036)」：纯函数拆分、冷启动片尾存档（load 后与首次激活后都在文件 1 的 60000，平台 load 收到 initialIndex=1 / initialPosition=60000）、越界存档原样交平台（150000）且在平台报出真实时长后落在 100000、挡板解除。变异实测：把 load 改回按估算夹上界，两条用例都红（Expected 60000 / 150000，Actual 8000）。
- **备注**：真机验证未做（冷启动片尾续播需真实多文件书）。
