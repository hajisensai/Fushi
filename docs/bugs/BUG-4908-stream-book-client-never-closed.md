## BUG-4908 · 流媒体书客户端与来源直链解析器从不关闭（SFTP 每开一次留一条 SSH 连接）
- **报告**：2026-11-20（来源：路线图 #3722 c31 的 gap-remote-3，代码审读复核成立）
- **真实性**：✅ 真 bug。根因（基准 `origin/develop@7745effa2e`，`fushi/lib/src/pages/implementations/video_fushi_page.dart`）：
  - `:4565` 流媒体书（粘贴 URL / 来源库网络视频）现建的 `UrlStreamVideoClient` 存进 `_resolvedStreamClient` 后，`dispose`（`:7343` 只释放在线视频源客户端）从不调它的 `close()`（`fushi/lib/src/media/video/url_stream_video.dart:523`，连同 `urlResolver`）。SFTP 来源的 `SftpStreamUrlResolver` 持有 SSH 连接，每开一次片留一条。
  - `:4481` 媒体服务器入库条目现建的 Jellyfin / Plex 客户端同样从不关。
  - `:4551-4563` `buildStreamVideoLaunch` 抛出时，已建好的来源直链解析器没人关；`:4563` / `:4480` 协商途中页面已关时，刚建好的客户端直接丢掉。
  - 重试（`_retryLoad` → `_init`）直接覆盖 `_resolvedStreamClient`，前一只不关。
- **[x] ① 已修复** — 新增 `RemoteVideoClientConnections` 能力（`UrlStreamVideoClient` / `JellyfinVideoClient` / `PlexVideoClient` 实现）与 `RemoteClientTeardown`（`fushi/lib/src/media/video/remote_client_teardown.dart`）：退出收尾（`exitAfterPersist` 发起的落库 + 停止上报、controller 的远端断点写入、换集的落库 + 停止上报、停止上报本身）都登记进去，本页自建的客户端在 `dispose` 里排在 controller 之后、等这些收尾结束再关；重试换上新客户端时关旧的；解析器在交给客户端之前失败或没被客户端收下时就地关；协商途中页面已关时关掉刚建的客户端。调用方传入的 `remoteClient`（互联 host 等）不碰。提交 `6e3b58612c`（分支 `pr/video-page-load-failures`）。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/remote_client_teardown_test.dart`：无在途收尾立即关、有在途收尾等其结束再关、收尾失败照样关、关闭流客户端同时释放 http 客户端与来源直链解析器、不持连接的客户端为空操作。
- **备注**：页面级「退页后连接真的关了」没有 widget 自动化（流媒体书起播要真网络 / 真 SFTP），未做设备复测（本轮所有者定不做）。
- **复审补漏**：首版漏登记 `dispose` 里观看追踪器的离开收尾——媒体服务器入库条目看到片尾后退出，`VideoWatchTracker.stop` 的完成判定会经本页自建的 Jellyfin / Plex 客户端连发三次追番身份请求（`remoteVideoTrackingEpisode`），而 `IOClient.close` 是 `force: true`，客户端先关就把这次「看完」打勾丢掉（BUG-3491 同形回归）。现 `VideoWatchTracker.close()` 交回停表 future，页面经 `_remoteTeardown.track` 登记。测试 `fushi/test/media/video/video_watch_tracker_test.dart`「close() 等离开时的完成回调跑完才完成」，把 close 改成立即完成的变异下红（实测）。
