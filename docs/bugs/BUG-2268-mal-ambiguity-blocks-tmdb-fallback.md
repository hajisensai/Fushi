## BUG-2268 · MAL 主源歧义即终止识别链，TMDB 兜底永远不被询问，中文目录名整批记成待确认
- **报告**：2026-09-08（用户：Mac 升 2.3 后「好多番剧都识别失败」，怀疑 MAL 主源）
- **真实性**：✅ 真 bug。`fushi/lib/src/media/video/metadata/video_metadata_resolver.dart:148-151`（改前）：链 `[mal, tmdb]` 只要主源返回 `matched` **或 `ambiguous`** 就 `return`，TMDB 只在 MAL `notFound` / `providerUnavailable` 时才被问；`mal_fallback_resolver_test.dart:62` 还专门钉死了这个行为。而 Jikan 的 `titles` 只有 Default / Synonym / Japanese / English（实测 `/anime/52991`），没有中文；中文目录名在 MAL 上得到的是一堆类型、年份合格但标题不符的候选 → `reviewCandidates` 非空 → `ambiguous` → 链终止。扫描后 / 补刮等后台任务没有确认回调（`video_source_scrape_coordinator.dart` `_resolveWork` 的 `onConfirmation == null` 分支），整条记成 `pending`，用户看到就是「识别失败」。TMDB 按 zh-CN 返回中文名本可一搜即中。叠加因素：`_titleCandidates` 把 `01` 这类纯集号也当标题去搜（`video_source_scrape_coordinator.dart` 旧 `_titleCandidates`），其垃圾候选同样把整条污染成 ambiguous。
- **[x] ① 已修复** — 识别链只在「唯一精确命中」时终止：主源 ambiguous 继续问兜底源，兜底源精确命中即采用，双歧义合并候选且每条候选自带 `work.provider`（`video_metadata_resolver.dart` `resolve` / `_mergeAmbiguous`）；协调器歧义候选按各自来源取 lookup；文件派生的纯集号标签不再进 provider（`videoScrapeTitleCandidates` / `isEpisodeLabelTitle`）。同批把主源改为用户可选（全局偏好 + 来源级 `provider_override`），MAL ↔ TMDB 互为兜底。设计稿 `docs/specs/2026-09-08-scrape-provider-choice.md`。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/metadata/mal_fallback_resolver_test.dart`（「MAL review-only candidates (title mismatch) continue to TMDB」「both sources ambiguous merges candidates with their own provider」「TMDB primary falls back to MAL symmetrically」「single-source request never consults a second provider」等）、`fushi/test/media/video/metadata/video_scrape_title_candidates_test.dart`、`fushi/test/media/video/metadata/video_source_scrape_provider_override_test.dart`、`fushi/test/pages/video_source_scrape_ui_test.dart`（来源设置主源选择器写穿 `provider_override`）。
- **备注**：Jikan 搜索与分集接口本机经代理连探 6 次全 504，只有详情接口正常；504 会走 providerUnavailable → TMDB，但分集 504 就拿不到分集资料。后续批次（离线 AniDB 标题索引 → Fribb → 按 id 直拉）把识别从 Jikan 搜索上解耦，见设计稿 A2。
