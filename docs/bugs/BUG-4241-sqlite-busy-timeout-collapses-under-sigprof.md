## BUG-4241 · Linux 上 Fushi 库的 5s busy 超时被 SIGPROF 压成几十毫秒（并发迁移偶发 database is locked）
- **报告**：2026-11-08（CI：PR #3050 的 unit-tests (1/4) 偶发红，`fushi/test/anki/anki_settings_drift_store_test.dart`「两个连接（模拟主进程与 :popup 首启）并发迁移：恰好落地一次」抛 `SqliteException(5) database is locked`，语句是 `insertPrefIfAbsent` 的 `INSERT OR IGNORE`；该 PR 未碰 anki）
- **真实性**：✅ 真 bug，不在迁移逻辑、也不是测试时序假设错，而在连接的 busy 超时实现。`packages/fushi_core/lib/src/database/database.dart` `_openWithRecovery.applyPragmas`（原 :295）用 `PRAGMA busy_timeout = 5000`。SQLite 内置 busy handler（`main.c` `sqliteDefaultBusyCallback`）**按调用次数**累计名义睡眠时长判超时，假设 `nanosleep` 每次睡满；Linux 上 Dart VM 采样 profiler（`flutter test` 默认 `--enable-dart-profiling` → 引擎 `--profiler --profile_period=1000`，debug / profile 构建同样开）每 1 ms 用 `pthread_kill(SIGPROF)` 打断所有进入 isolate 的线程（`thread_interrupter_linux.cc`），包括卡在 `sqlite3_step` 里等锁的 drift 后台 isolate 线程，`nanosleep` 被 EINTR 提前返回（POSIX 规定 nanosleep 不随 SA_RESTART 重启）。约 60 次调用、几十毫秒后 handler 就认定「已等满 5s」放弃，抛 SQLITE_BUSY。并发迁移里赢家的写事务（BEGIN → INSERT → 读 / 写 prefs_version → COMMIT，三次跨 isolate 往返 + WAL fsync）在负载重的 CI 上偶尔超过这几十毫秒，输家就红。迁移本身（单条 `INSERT OR IGNORE`，事务首句即写、拿写锁时处于 TRANS_NONE、会走 busy handler）没问题，测试断言「恰好落地一次」也正确。Windows（`SuspendThread` 采样、`Sleep` 不被打断）与 macOS（`thread_suspend`）不触发，所以本机 / mac 分布式机都复现不了。release（AOT/PRODUCT）不带 profiler，正式包不受影响；debug / profile 包在 Android（`thread_interrupter_android.cc` 同样发 SIGPROF；主进程 vs `:popup`）、Linux 上同样中招。
- **[x] ① 已修复** — 新增 `packages/fushi_core/lib/src/database/sqlite_busy_timeout.dart` `installWallClockBusyTimeout`：用 `sqlite3` 的 `busyHandler` 装一个按 `Stopwatch` 墙钟计时的 handler（`count == 0` 即新的等锁事件、重置计时；退避节奏同 SQLite 默认表；睡眠用 `dart:io` `sleep`，其 Linux 实现遇 EINTR 续睡剩余时长），`applyPragmas` 改调它取代 `PRAGMA busy_timeout`（仍排在 `journal_mode=WAL` 之前，BUG-772 约束不变）。超时语义仍是 5s，只是从「次数」改回真实时间；没有加重试 / 延迟。
- **[x] ② 已加自动化测试** — `fushi/test/database/sqlite_busy_wait_wall_clock_test.dart`：①外部连接 `BEGIN IMMEDIATE` 持写锁 1s（远小于 5s）再提交，`FushiDatabase.insertPrefIfAbsent` 必须等到并成功——确定时序，修复前在 Linux CI 必红（PR #3081 首个提交 08d9ccd12f 的 unit-tests (1/4)：该用例抛 `SqliteException(5)`，同批 macOS 分布式机上则通过），，修复后全平台必绿；②锁一直不放时，装了 300ms 墙钟超时的连接必须等满 300ms 才报 SQLITE_BUSY。`fushi/test/database/db_open_pragma_order_test.dart` 守卫改为钉住 `installWallClockBusyTimeout(db)` 先于真正执行的 `PRAGMA journal_mode=WAL`，且 `applyPragmas` 里不许再出现 `PRAGMA busy_timeout`（会覆盖 handler）。
- **备注**：同类问题还在 `fushi/lib/src/utils/misc/local_audio_db.dart`（`PRAGMA busy_timeout = 10000` / `3000` 的本地音频库连接），本轮未改，影响面同样只在 debug / profile / 测试的 Linux 与 Android；需要时改调同一个 `installWallClockBusyTimeout`。
