## BUG-2801 · 排行榜 401 unknown_account：UI 读榜后本机退出是 fire-and-forget，测试按固定轮数等落盘在 CI 高负载下偶发红
- **报告**：2026-09-30（CI：上游 Linux 全量套件，PR 分支 pr/float-ocr-popup 2026-09-29 run；`fushi/test/leaderboard/leaderboard_service_test.dart:750` 「UI 读榜（签名读请求）同样触发退出」Expected disabled / Actual active）
- **真实性**：✅ 真 bug（与该 PR 无关，upstream/develop `4810d9137e9` 即可复现）。根因：`fushi/lib/src/leaderboard/leaderboard_service.dart` 的 `_onAccountGone` 用 `unawaited(_clearLocal(accountGone: true))` 触发本机退出，而 `packages/fushi_engine/lib/leaderboard/leaderboard_client.dart` `_send` 里 `_onAccountGone?.call(e); rethrow;` 不等它。`_clearLocal` 要走写队列 + `store.delete()` 的 3 次异步文件 IO 才把 `_account` 置空，所以 UI 读榜（`client.rank()` 等不经同步收尾排队的路径）的调用方接到异常时，状态是否已变 disabled 取决于文件 IO 赶没赶上。测试用 `for (i < 20) await Future.delayed(Duration.zero)` 固定让 20 轮计时器去等落盘，是把竞态写进了断言。后台同步路径碰巧不红，只因 `_sync` 失败后的收尾 `_update` 排在 `_clearLocal` 之后、`syncNow` 会等它。
  - 实测（本机 Windows，未改代码）：单跑该用例 `--plain-name "UI 读榜"` **6/6 红**（exit=1，同一行 750）；整文件跑时它排在第 31 个，绿。探针数「落盘前让出了几轮零延时计时器」：冷进程单跑 **69 轮**（> 20 → 红），整文件热进程 **3 轮**（→ 绿）。即对执行顺序 / IO 负载敏感：CI 全量 ~3 万测试并发、IO 争用时同样会越过 20 轮预算。
- **[x] ① 已修复** — 客户端 `onAccountGone` 改为 `FutureOr<void> Function(...)`，`_send` 里 `await` 它再 `rethrow`；服务端 `_onAccountGone` 返回 `_clearLocal` 的 Future（异常仍只记日志）。任何路径接到 401 unknown_account 时本机退出已落定。写队列里的 job 从不发客户端请求，等待不会死锁。
- **[x] ② 已加自动化测试** — `packages/fushi_engine/test/leaderboard/leaderboard_client_test.dart`「回调返回的 Future 完成后才抛给调用方（BUG-2801）」；`fushi/test/leaderboard/leaderboard_service_test.dart` 两条 401 用例去掉 20 轮轮询，改为异常到手即断言 disabled + 账户文件已删。
- **备注**：修后单跑该用例 5/5 绿，`test/leaderboard` 整目录 `--test-randomize-ordering-seed=random` 3 轮全绿。
