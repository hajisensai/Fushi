## BUG-3856 · macOS 导入时打开访达面板后切到别的 app 再切回来必崩（AppDelegate 对 FlutterAppDelegate 没实现的 NSApplicationDelegate 方法调 super）
- **报告**：2026-10-28（用户：导入文件时弹出系统访达选择面板，切到其他应用再切回来，应用直接崩溃；已有 2 份 `.ips` 崩溃报告。macOS 27.0.1 / Apple Silicon / debug 构建）。
- **真实性**：✅ 真 bug（客户端自己的 `super.` 调用，与访达 / file_picker 无关）。取证链：
  1. `~/Library/Logs/DiagnosticReports/fushi-2026-10-28-025752.ips` 与 `-025915.ips` 均为 `EXC_CRASH/SIGABRT`，`exceptionReason` 原文：`-[fushi.AppDelegate applicationDidBecomeActive:]: unrecognized selector sent to instance 0x…`（`NSInvalidArgumentException`）。
  2. `lastExceptionBacktrace`：`-[NSSavePanel runModal]` → `_NSTryRunModal` → `_doModalLoop` → `sendEvent` → `_handleActivatedEvent` → `CFNotificationCenter` → `AppDelegate.applicationDidBecomeActive(_:) AppDelegate.swift:31` → `_CF_forwarding_prep_0` → `objc_exception_throw`；`-[NSSavePanel runModal]` 的调用方是 `FilePickerPlugin.handleDirectorySelection`（file_picker 8.3.7 `FilePickerPlugin.swift:87`，选文件夹）。
  3. 根因：`fushi/macos/Runner/AppDelegate.swift:31` 的 `super.applicationDidBecomeActive(notification)`。`FlutterAppDelegate` 是纯 ObjC 的 `NSObject <NSApplicationDelegate, FlutterAppLifecycleProvider>`，用 `otool -oV` 导出的方法表里**只有** `applicationWillFinishLaunching:` / `application:openURLs:` / `applicationShouldTerminate:` 三个 `NSApplicationDelegate` 方法；`applicationDidBecomeActive:` / `applicationDidResignActive:` / `applicationDidFinishLaunching:` / `applicationWillTerminate:` 都是**协议声明、无实现**。`super.` 走 `objc_msgSendSuper2` 在父类找不到方法 → 转发 → 抛 `NSInvalidArgumentException`。
  4. 为什么平时不崩、只有访达面板开着才崩：`log show` 实测每次激活 / 失活都在抛（`An uncaught exception was raised` + `NSInvalidArgumentException`），普通事件循环里被 AppKit 记一条就吞掉；而 `-[NSSavePanel runModal]` 的 `_NSTryRunModal` 会把模态循环里抓到的异常**重新抛出**给 `runModal()`，file_picker 的 Swift 侧没有 catch → `_objc_terminate` → abort。
  5. 同一类错误共 4 处：`AppDelegate.swift` 的 `super.applicationDidResignActive` / `super.applicationDidBecomeActive` / `super.applicationDidFinishLaunching` / `super.applicationWillTerminate`（`super.application(_:open:)` 是**对的**，它对应 `application:openURLs:`，父类有实现）。
- **[x] ① 已修复** — 根因修：删掉上述 4 处 `super.` 调用，并在 `applicationDidBecomeActive` 上写明为什么不能调（父类只实现 3 个方法；插件生命周期事件由 `FlutterAppLifecycleRegistrar` 自己的 `NSApplicationDidBecomeActiveNotification` 等通知观察者分发，见引擎 `FlutterAppLifecycleDelegate.mm`，所以不转发不会丢事件）。**连带修好一个静默失效的功能**：`desiredLookupImeTag` 的「切回前台恢复查词输入法」写在 `super.` 之后，异常在 super 就抛了，这行此前从未执行过。
- **[x] ② 已加自动化测试** — `fushi/test/build/macos_appdelegate_super_selectors_guard_test.dart`：静态守卫，剥注释后扫 `macos/Runner/AppDelegate.swift` 的全部 `super.<name>(`，只放行 `FlutterAppDelegate` 确实实现的 `application`（= `application:openURLs:`）；附两条哨兵断言防止扫描面塌成假绿。变异实测：把 `super.applicationWillTerminate(notification)` 加回去 → 守卫红并点名 `AppDelegate.swift:504`。
- **备注**：macOS debug 实跑复测（同一台机）：修前启动即 1 条未捕获异常、每次切 app 再 +1；修后启动 0 条，连续 3 轮 Finder ↔ 本应用切换后仍 0 条、进程存活、`Lifecycle` 事件照常。**访达面板开着切 app 的原始失败路径待用户按原步骤复测**（面板需要人手点，本机无法脚本化驱动）。同机另有一份无关的崩溃报告 `fushi-2026-10-28-015237.ips`（`EXC_BAD_ACCESS` 在 `libfushidicts_ffi.dylib` 的 `get_japanese_processors()` ← `text_processor::process` ← `Lookup::lookup` ← `tokenize_corpus`，DartWorker 线程），是独立问题，未在本条处理。
