## BUG-4752 · 用其他应用打开 / 分享导入替发起方读它无权读的 content:// URI（confused deputy）
- **报告**：2026-11-17（自动安全审查，CWE-441，针对 0f326a808e）
- **真实性**：✅ 真 bug（机制成立，影响偏低）。`MainActivity` exported（`fushi/android/app/src/main/AndroidManifest.xml:60`），显式 intent 不受 MIME 过滤器约束，任何 app 都能把任意 `content://` URI 交给 `OpenWithChannel.offer`；旧实现（develop 890895f419 行号）只在 `OpenWithChannel.java:148-157`（`isOwnProvider`）排除自家 provider，然后 `copyToCache` 以 Fushi 自己的身份 `openInputStream`（`OpenWithChannel.java:167`）。于是 Fushi 凭自身权限（AnkiDroid `READ_WRITE_DATABASE`、存储权限等）能读、发起方读不了的 provider 也会被读进缓存并导入书库。另：`isOwnProvider` 拿带用户号前缀的 authority（`0@<本包>.provider`）去 `resolveContentProvider` 查不到就返回 false，而 ContentResolver 会把 `0@foo` 当本用户的 `foo` 去连，自家 provider 的排除可被绕过。影响：字节只进 Fushi 私有缓存 / 书库并在本机打开，发起方拿不回来，不是外泄；AnkiDroid 的 CardContentProvider 是 query 型、未必实现 openFile（推测，未在设备上验证），读流多半失败；实际后果是「把别处受保护内容静默塞进书库 / 本包私有文件被导入」。
- **[x] ① 已修复** — 访问判定抽成纯函数 `OpenWithUriPolicy.decide`（`fushi/android/app/src/main/java/app/fushi/reader/OpenWithUriPolicy.java`），`OpenWithChannel.mayReadOnBehalfOfSender` 取事实（去用户号前缀后的 `resolveContentProvider`、匹配路径的 path-permission、Fushi 的持久化 URI grant、所持权限是否非 normal）后裁决，复制前在后台线程执行，查询出错不读。判据：只有 Fushi 除对方 URI grant 外读不到时才读——自家 provider、Fushi 持久化 grant 覆盖的 URI、exported 且受 Fushi 持有的非 normal 读权限保护的 provider 一律拒；未 exported 的 FileProvider、`MANAGE_DOCUMENTS` 保护的 SAF DocumentsProvider、下载管理器、无读权限的公开 provider、MediaStore（`media`，公共共享存储，按设计放行）照常。不用「intent 是否带 FLAG_GRANT_READ_URI_PERMISSION」，那是发起方可伪造的位；也不用 `checkUriPermission`，它分不清 grant 与静态权限。
- **[x] ② 已加自动化测试** — JVM 单测 `fushi/android/app/src/test/kotlin/app/fushi/reader/OpenWithUriPolicyTest.kt`（判据各分支）+ 源码守卫 `fushi/test/android/open_with_uri_access_guard_test.dart`（offer 先判定后复制、判定失败不读、按去前缀 authority 查 provider；JVM 单测不在 CI 跑，守卫在 CI 跑）。
- **备注**：真机「用其他应用打开 / 分享到 Fushi」（QQ / 微信 FileProvider、系统文件管理器 SAF、下载、相册 MediaStore）未复测，待补。
