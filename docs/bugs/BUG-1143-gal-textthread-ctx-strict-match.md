## BUG-1143 · 文本线程记忆按 ctx 严格匹配掐断文本流，连带语音资源配对失败降级
- **报告**：2026-07-27（用户：截图反馈——捕获工作台里 #84/#85 音频标「已降级 · system_loopback · 5.00s · engine_utterance_unavailable」，并观察到「如果中间有一大段空白，后面的音频容易降级」）
- **真实性**：✅ 真 bug（两处独立缺陷，主因是①）。
  - **① 文本流被掐断（主因）**：`selected_text_thread_id` 存的是具体 `TextSlot::thread_id`，而 `thread_id = FNV1a(processId, addr, **ctx, ctx2**, hookcode, hookname)`（`native/galgame_hook/injector/injector_main.cpp:444-458`）含调用上下文。`LunaTextSelector::ShouldWrite` 对手动/记忆选定值做精确匹配 `manually_selected == thread_id`（`native/galgame_hook/include/luna_text_selector.h:95` 修复前），同一 hook 面换个调用路径（ctx/ctx2 变）就整行丢弃。而 Hibiki 侧 `_maybeRestoreTextThread`（`hibiki/lib/src/mining/gal_hook_session_controller.dart:1995`）会**自动**恢复上次会话记住的线程——其注释已自陈「指纹只能锚到 hook 而锚不到具体并行线程（**ctx 未透出**）」，即用 hook 粒度的记忆锁上了 thread 粒度的门。用户本次并未手动选线程。
  - **② 配对窗口两侧不一致（放大器）**：native 打标窗口 `kKirikiriFollowingTextWindowMs = 1500`（`native/galgame_hook/hook/voice_resource_pairing.h:8`），Dart 收标窗口 `eventIdToleranceMs = 1000`（`hibiki/lib/src/mining/galgame_audio_source.dart:384` 修复前）。两常数无任何交叉引用。1000~1500ms 是死区：native 判定配上并把 `TextSlot::seq` 写进资源文件名，Dart 因超差拒收，而带 marker 的资源又被明确禁止回退时间窗兜底（同文件 `:413-414`），于是**打了标反而比没打标更容易失败**。
- **真机实测证据**（`%TEMP%\hibiki_gal_voice\`，用户报告当次会话）：dump 共 146 个文件，其中 **92 个（63%）无 `_hibiki_textseq` marker**；`textseq84` / `textseq85` 根本不存在；`textseq83`（tick 568503312）之后连续 **16 句**语音资源全部无 marker，tick 间隔规整 5~8 秒（568509359 … 568597593），直到 568675843 才恢复打标。降级两句对应的资源 `568591703_yuz_001_0012.ogg` / `568597593_yuz_001_0013.ogg` 均在盘上（`yuz` = 该场景说话角色由月）——**语音抓到了，文本没到**。用户说的「中间一大段空白」即此：那 94 秒游戏一直在说话，Hibiki 只收到 2 行文本。
- **失败链**：ctx 变 → 文本行被 `ShouldWrite` 丢弃 → 文本环无候选 → `ResolveFollowingSelectedText` 1500ms 内找不到 line 事件 → `kExpired` → 资源写成无 marker 裸名 → Dart 侧只剩 `[textTs-330, textTs-130]` 这 200ms 窗口兜底 → 兜不住 → `engine_utterance_unavailable` → `_cacheLoopbackLineAudio`（`gal_hook_session_controller.dart:3608`）落 system_loopback 5.00s。
- **[x] ① 已修复** —
  - `native/galgame_hook/include/luna_text_selector.h`：新增纯函数 `LunaSelectedThreadAccepts`，把手动/记忆选择的**过滤粒度**从 thread_id 放宽到 hook 面；`LunaTextSelector` 内部维护 `thread_face_`（thread_id → face）映射，`ShouldWrite` 新增可选 `face_id` 参数并在每行登记。face 未知时退回精确匹配，语义与旧实现一致。**刻意不改 thread_id 算法**——ctx 参与 thread_id 用于诊断/区分并行调用点是有意设计，本 bug 只在于拿它做过滤。伪影门 `if (artifact) return false` 仍在选择之前，放宽粒度不会让伪影漏进来。
  - `native/galgame_hook/injector/injector_main.cpp`：新增 `LunaTextFaceId`（与 `LunaTextThreadId` 同源但**不含 ctx/ctx2**），`LunaShouldWriteLine` 增加 `face_id` 形参并透传。
  - `hibiki/lib/src/mining/galgame_audio_source.dart`：新增 `kGalVoicePairingWindowMs = 1500` 并让 `eventIdToleranceMs` 默认取它，消掉 1000/1500 死区。窗口统一后 native 保证 `0 <= textTs - tick <= 1500`，故 eventId 命中的资源必然落在容差内；「带 marker 的资源只认自己那条文本」这条防错配纪律保持不变。
- **[x] ② 已加自动化测试** —
  - `native/galgame_hook/tests/luna_text_replay_test.cpp`：新增 face 放宽四条（选定线程自身放行 / **同 face 不同 ctx 必须放行**（核心回归点）/ 不同 face 仍挡掉 / 伪影不得因放宽而漏入），以及 face 未知时退回精确匹配一条。修复前分别在返回码 25、28 处失败。
  - `hibiki/test/mining/gal_voice_pairing_window_parity_test.dart`（新增）：源码扫描守卫，读 `voice_resource_pairing.h` 解析 `kKirikiriFollowingTextWindowMs` 并断言与 `kGalVoicePairingWindowMs` 同值，防两侧再次漂移；另加「窗口上界处 eventId 命中必须被接受」（修复前失败）与「eventId 不同的带标资源仍不得被时间窗猜给本行」两条行为测试。
