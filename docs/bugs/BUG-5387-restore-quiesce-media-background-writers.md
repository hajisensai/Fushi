## BUG-5387 · restore-quiesce-media-background-writers
- **报告**：2026-11-24（用户：应用内反馈 hfLuOcL7n0「Library messed up after i import my backup」，Windows 3.4.0-debug.32189）
- **真实性**：✅ 真 bug（生命周期缺陷部分）。两次导入备份（日志 23:57:30、00:14:44）时，媒体库后台写手仍在跑，全部撞上「connection was closed」：`MediaSourcesViewState._rescan`（`fushi/lib/src/pages/implementations/media_sources_view.dart:1928` 的 finally 回读来源行）、`VideoLibraryScrapeSweep.plan`、`video.contentFullHashUpgrade`（`video_content_fingerprint.dart:315` 的事务）、`_HomeVideoPageState._maybeBackfillCovers` 回写 `video_books.cover_path`、`MusicLoudnessScanner._runOnce` 回写 `music_tracks` 响度。根因：`AppModel.closeDatabase`（`fushi/lib/src/models/app_model.dart` 的 `closeDatabase`）只等它自己构造的写手（下载管线、转录入库、SRS 等登记的 quiescer），来源扫描 / 刮削 / 补刮 / 哈希升级 / 封面回填 / 响度扫描这些由页面或引擎单例起的后台工作**没有任何登记**，关库不取消也不等它们；它们各自捕获了旧 `FushiDatabase` 或每轮重新取 `appModel.database`，读到的行身份和写入时用的库之间没有任何边界。备份导入（`sync_settings_schema/backup.part.dart` 的 `runBackupImportFlowForFile`）随后 `closeDatabase` → 换库文件 → 重启，中途被腰斩的扫描（用户刚加完 565 个视频的来源、`addLocalFolder → _rescan` 正在跑）只留下半截状态。
- **[x] ① 已修复** — 把「换库」做成有生命周期边界的操作，边界放在库实例上：`packages/fushi_core/lib/src/database/database_background_work.dart` 新增 `DatabaseBackgroundWork`（每个 `FushiDatabase` 一份，`db.runBackgroundWork(label, body)`）。后台工作在带取消令牌的 Zone 里跑；`FushiDatabase.close()` 先 `quiesceBackgroundWork()`：本库名下所有令牌置为已取消，再**等所有在跑的工作退出**才关连接；之后不再接新工作。全部构造路径的执行器都套 `DatabaseWorkInterceptor`：已取消工作 Zone 里发出的任何 SQL（哪怕发给另一个库实例）直接抛 `DatabaseWorkCancelledException`，事务半截回滚——旧库读出的行身份写不进换上来的新库。不经库的长操作（整文件哈希、FFmpeg、等用户确认刮削候选）用 `DatabaseWorkToken.guard` 等，库一关就不再等。接入：`SourceLibraryScanner.scan`（逐文件 catch 遇到取消改为整次停）、`MediaSourcesViewState._rescan`（扫描 + 扫完刮削回调整段）、`VideoSourceScrapeCoordinator.scrapeSource` / `identifyWorkWithAi`（库取消联动刮削取消令牌，翻成 `VideoSourceScrapeCancelled`）、`VideoLibraryScrapeSweep.sweepAndListPending`、`VideoContentFullHashUpgrader`、`_maybeBackfillCovers`、`MusicLoudnessScanner`（一轮绑定开轮时的那个库，不再中途重取 `appModel.database`）。`AppModel.closeDatabase` 一开头就发取消，与其它写手收尾并行停下。`ErrorLogService` 把 `DatabaseWorkCancelledException` 归入诊断段（预期内停机，不计错误）。重启后各任务按新库照常启动（备份导入成功 / 失败都会重启进程）。
- **[x] ② 已加自动化测试** — `packages/fushi_core/test/database_background_work_test.dart`（关库等在跑工作退出、取消后写入一条不落、事务回滚、旧工作写新库实例被拦、guard 不等慢操作、关库后不接新工作）；`fushi/test/sync/backup_restore_background_writers_test.dart`（文件库上扫描卡在列目录时开始关库：关库等扫描停稳，重开库零视频入库、不写扫描结果；响度测到一半换库，旧曲目身份写不进新库；整文件哈希算到一半关库不等哈希）。
- **备注**：截图里「系列：SPY×FAMILY」筛选下出现 K-ON / 一排 Frieren 封面的**具体错位机制没有复现**（没有用户库）。本修复堵住的是日志直接证明的「换库时后台写手无边界」；关库后的写入在本进程内本来就因连接已关而失败，所以错位更可能来自被腰斩的扫描 / 刮削留下的半截状态叠加合并导入。另一个待核的跨库身份来源：合并导入 `BackupMergeEngine._insertMissingVideoBooks`（`fushi/lib/src/sync/backup_merge_engine.dart`）按「除 id 外全列」直搬 `video_books`，其中 `source_id` 是备份库里的整数来源 id，而 `media_sources` 是设备本地、不随合并走——只对随包带了文件的视频 / 流媒体生效，用户的 G: 盘本地视频不在其内，但仍是一处整数身份跨库直搬，需单独核实（已作为后续任务提出）。
