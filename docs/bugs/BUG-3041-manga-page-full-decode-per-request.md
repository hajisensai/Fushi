## BUG-3041 · 漫画阅读器每次页图请求都整张解码取宽高，大图页拖慢阅读与查词
- **报告**：2026-10-05（用户「提督哈里斯」群聊：iOS 上看漫画查词「卡得受不了」，漫画来自 iOS「文件」App 的「连接服务器」(SMB) 挂载的 NAS；协作者只测过本地漫画）
- **真实性**：✅ 真缺陷（性能），但与「NAS 网络 IO」无直接因果——见备注。根因两处：
  1. `fushi/lib/src/media/manga/mihon/manga_page_provider.dart:87`（基线 c7932af5419）：`LocalMangaReaderSession.page()` 每次调用都 `mangaImageDimensions(bytes)`，后者在 `:149` 用 `Isolate.run` + `img.decodeImage` **整张纯 Dart 解码**只为取宽高（而本地会话的宽高调用方根本不用，manga.json 里本就有）。阅读器每个 WebView 页图请求（`manga_fushi_page.dart:2503` `_interceptRequest` → `pageSession.page`）、面板检测都走这里；iOS/macOS 走自定义 scheme（`webViewUsesCustomSchemeTransport`），WKURLSchemeHandler 没有 HTTP 缓存，每次装窗口文档都重付。实测 2400×3400 页：JPEG 每次 ~700 ms、PNG ~500 ms，6 个并发请求 1.59 s，期间每次还把 5~12 MB 字节拷进新 isolate、解出几十 MB 像素。
  2. `packages/fushi_engine/lib/media/manga/import/image_size_probe.dart:23`（基线）：导入用的「只读头」探测 `probeOrientedImageSize` 对 JPEG 调 `JpegDecoder.startDecode`，image 4.x 实际会解析整条扫描数据——同一张页 200~640 ms，且**同步跑在调用方 isolate**（`findDecoderForData` 也偶发 ~290 ms）。修 1 时若直接改用它会把卡顿搬到主 isolate，所以一并修。
- **[x] ① 已修复** — `image_size_probe.dart` 新增 `_jpegOrientedSize`（顺 marker 链读第一个 SOFn 高宽 + 既有 `jpegExifOrientation` 换轴）与 `_pngSize`（读 IHDR），JPEG/PNG 不再进 image 解码器；`mangaImageDimensions` 先走 `probeOrientedImageSize`，认不出（GIF/损坏头）才回退 isolate 整张解码，结果口径不变。修后同一页 `page()` 5~13 ms，6 并发 47 ms（修前 1590 ms）。提交 `2c22138d9fc`（分支 `claude/sh-manga-lookup-nas`）。
- **[x] ② 已加自动化测试** — `fushi/test/media/manga/manga_page_provider_test.dart`「page dimensions come from the header without decoding pixels」（像素段截掉 2/3、整张解码必失败的 JPEG：修前 `mangaImageDimensions` 返回 null → 红，修后给出 1600×2400；并经 `LocalMangaReaderSession.page()` 验证）；`fushi/test/media/manga/image_size_probe_test.dart`「JPEG / PNG 只读头：像素段截断也给出宽高」（含 EXIF orientation=6 换轴，与完整文件 `bakeOrientation` 结果一致）。
- **备注**：
  - **NAS 来源在 iOS 上不进阅读热路径**：iOS 目录导入走 `FushiDirectoryImport.swift` 在安全作用域窗口内把整棵树拷进 app 容器，`MangaImporter._copyAndInsert` 再拷进书目录；单文件走 file_picker import 模式（拷进 tmp）；app 不持有 security-scoped bookmark，Info.plist 也没有 open-in-place。阅读器 `_imagesDir = row.extractDir` 永远是 app 自己的书目录，点词链路（`onTextSelected` → `dispatchMangaSelection` → `_selectPageForMining` 同步解析本地路径 + `searchDictionaryResult`）没有任何文件 IO 指向原 SMB 位置。因此「NAS 漫画卡、本地不卡」更可能是**内容差异**：NAS 上的卷多为高分辨率扫描（触发本 bug 的解码开销）或是**无 mokuro 的纯图片夹**（开书后整卷 OCR 在后台跑，与查词抢 CPU）。
  - 没在 iOS 真机/模拟器复现用户原始操作；修复证据是桌面上 `page()` 耗时对比与守卫测试。需要向用户确认：卷是带 `.mokuro` 还是纯图片（是否在阅读器里跑 OCR、用哪个引擎）、单页分辨率/格式、卡是「点字到弹窗出来慢」还是翻页/滚动也卡、同一卷拷到本机再导入是否同样卡。
