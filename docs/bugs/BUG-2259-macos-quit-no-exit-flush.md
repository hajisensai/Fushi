## BUG-2259 · macOS Cmd+Q 退出不跑退出 flush（阅读位置/有声书进度/阅读统计丢最后一段）
- **报告**：2026-09-08（用户：Mac 上阅读器重新打开不会回到上次阅读的地方；并要求核对有声书播放进度是否同病）
- **真实性**：✅ 真 bug（静态定位，未在 Mac 真机复现——本轮无 macOS 设备）。根因是**退出信号漏接**：`fushi/lib/main.dart:261` 的 `windowManager.setPreventClose(true)` 只拦 NSWindow 的 `windowShouldClose:`（点红叉），而 macOS 上最常用的退出方式 ⌘Q / 菜单「退出 Hibiki」/ Dock 右键退出走的是 NSApplication 的 `applicationShouldTerminate:`，**不经过 `onWindowClose`**（`fushi/lib/main.dart:864`）。于是整条 `_flushAndExitForWindowClose`（`fushi/lib/main.dart:903`：窗口几何落盘 → `ExitFlushRegistry.flushAll()` → 关书同步 drain → `closeDatabase` 做 WAL checkpoint）在该路径上一次都不跑。`didChangeAppLifecycleState` 的 `detached` 兜底（`fushi/lib/main.dart:839`）是 `unawaited` 的，进程在 `applicationWillTerminate` 后立即终止，异步 flush 跑不完。
  - 阅读位置：`_persistPosition` 只有 500ms 去抖这一档周期落库（`reader_fushi/navigation.part.dart:1317`），退出 flush 才落「最后一帧」的缓存锚。
  - **有声书播放位置：同一缺口，同样受影响**（用户问的第二点）。周期写是 fire-and-forget 的「整秒变化才写」（`packages/fushi_audio/lib/src/audiobook/audiobook_controller.dart:894`），写库 Future 无人等待；`AudiobookPlayerController.flushPosition()`（同文件 `:925`）唯一的 await-到-落库路径就挂在退出 flush 链上（`reader_fushi/navigation.part.dart:1510`）。
  - 阅读统计：`_readLedger.leave()` + `_flushReadingStats()` 只在退出 flush 里跑（`reader_fushi/navigation.part.dart:1498`），⌘Q 丢的是整段，不是最后一秒。
  - 视频页同样注册了 `_flushAllForProcessExit`（`video_fushi_page.dart:2001`），一并受益。
- **[x] ① 已根因修复** — `fushi/lib/main.dart`：仅 macOS 注册 `AppLifecycleListener(onExitRequested: _handleExitRequested)`（`applicationShouldTerminate:` 在 Dart 侧的落点，系统会等回调的 Future 完成才终止进程），回调**复用**关窗口那条链 `_flushAndExitForWindowClose()` 后答 `AppExitResponse.exit`。复用而非另写一条精简版，是为了让「关窗口能保住的数据，⌘Q 也一定保得住」成为结构性事实；该方法自带 `_shutdownStarted` 幂等守卫，⌘Q 与红叉竞发也只跑一遍。Windows/Linux 不注册——那两个平台的关闭信号已由 window_manager 的 preventClose 完整覆盖。
- **[x] ② 已加自动化测试** — `fushi/test/tools/bug_2259_macos_exit_request_flush_guard_test.dart`（3 例源码守卫：macOS 门控下注册了 `onExitRequested`、回调走同一条 `_flushAndExitForWindowClose` 并答 `AppExitResponse.exit`、`dispose` 注销监听器）。这是本 bug 可落地的最强层：真正的行为验证要求进程真的走到 `exit(0)`，没有单测宿主能容纳；而「注册没注册、注册在哪个平台、回调是不是同一条退出链」全是源码层静态事实。
- **备注**：**未在 Mac 真机复测**（本轮无 macOS 设备）。若用户的现象在 ⌘Q 之外也成立（例如「退出书籍回书架、再打开同一本」就已经丢位置），那是另一条独立故障——保存与恢复链路本身（`_refreshProgress` → 500ms 去抖 → `ReaderPositionRepository.save` → 开书 `findByBookUid` → `initialProgress/initialCharOffset`）全程平台无关，需要 Mac 端日志（`[ReaderFushi] save position:` / `[ReaderFushi] restore lookup:` 两行）才能定位，不要凭本条推断已全部修好。
