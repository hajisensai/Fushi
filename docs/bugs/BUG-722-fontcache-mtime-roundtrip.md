## BUG-722 · 词典字体缓存测试在 Linux CI 挂：setLastModified 亚秒 round-trip 丢精度
- **报告**：2026-07-11（用户：TODO-1407「apk编译失败」）
- **真实性**：✅ 真 bug（测试 fixture 平台依赖，**非产品代码 bug**）。「Build Release APK」workflow 的「Run unit tests (main app)」step 从 develop +639 起连续 failure，失败测试 `hibiki/test/reader/dictionary_font_css_test.dart:145` 的 `BUG-712 P3: unchanged (mtime,size) hits the cache — no disk re-read`：`Expected: contains 'AAECAw=='` 实际 `...base64,CQkJCQ==...`。
- **根因**：测试构造「同 (mtime,size) 但内容不同」时，先读初始写盘的 `stat.modified`（`f.statSync().modified`）再 `File.setLastModified(它)` 恢复。但 `FileStat.modified` 由 `DateTime.fromMillisecondsSinceEpoch` 构造（`dart-sdk/lib/io/file_system_entity.dart:138`），Linux 下带亚秒毫秒分量；而 `File.setLastModified` 在 POSIX 上经 `utime()` 落到**整秒**，恢复值丢掉亚秒分量。于是恢复后 re-stat 的 `microsecondsSinceEpoch` 与初次写盘时被缓存的值不等 → 缓存键 `(mtimeUs,size)` 变化 → `DictionaryFontCss._inlineFontDataUrl`（`hibiki/lib/src/reader/dictionary_font_css.dart:120`）正确判定缓存失效并重读盘 → 返回覆写后的新字节 `CQkJCQ==`。Windows 的 `stat.modified` 本就是整秒（native 用 `st_mtime` 秒），round-trip 无损，故本地/Win CI 侥幸通过。缓存实现（键 `(path,mtimeUs,size)`）正确：真实字体文件的内容变更总会推进 mtime、且导入落盘用带时间戳的路径（换键），无 stale-serve 风险。
  - 真 Unix（Mac/APFS）探针证据：OLD 方式 `captured.us=...363000` vs `afterRestore.us=...000000`（same=false，亚秒 .363 被丢）；NEW pinned 整秒方式 `build1.us==build2.us`（same=true）。
