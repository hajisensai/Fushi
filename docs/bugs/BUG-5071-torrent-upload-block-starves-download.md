## BUG-5071 · 单种子停上传（分享率达标）用 set_upload_limit(1) 把下载一起饿死
- **报告**：2026-11-21（用户转来第三方报告 `fushi_download_stuck_bug_report.md` 的 Bug 1：已完成的种子回退重下后永久卡在 4%，`.resume` 里 `upload_rate_limit = 1`）
- **真实性**：✅ 真 bug（本地 rig 在修复前的桥上确定性复现：下载端被截停 60 s 内 0 进度；做种端被截停连元数据都拿不到）。根因 `native/fushi_torrent/fushi_torrent_ffi.cpp:960`（a11db40c13f）`h.set_upload_limit(blocked != 0 ? 1 : -1)`：libtorrent 2.0.11 的 per-torrent 限速是该种子 peer class 的上传带宽通道，连接上**所有**出向字节（握手 68 B、interested、request、ut_metadata）都排它的预算，1 B/s 等于把控制面掐死，下载随之饿死。头文件注释「piece 请求是协议消息不走上传配额」这一前提是错的。触发链：`shouldAllowUpload`（`torrent_upload_policy.dart`，fRmEhU4XIK 拍板：生命周期分享率在下载途中达标也停上传）→ `sweepUploadPolicy` 对未完成种子下发 `setTorrentUploadBlocked(true)` → 上述限速；限速还随 fastResume 落盘（`upload_rate_limit`），重启加载即生效。
- **[x] ① 已修复**（2910be5e047）— 按既有设计意图（停上传、续下载）重做原语：桥内注册 session 插件 `UploadGatePlugin`，每个种子一个闸；截停时 `peer_plugin::on_request` 吞掉对端 request（含 allowed-fast，piece 只作为 request 的应答发出），生效边沿 choke 已 unchoke 的连接、`set_max_uploads(1)` 防止 choker 把全局槽位浪费在被吞请求的连接上；解除边沿恢复名额并对已表态 interested 的 choked 连接补 `maybe_unchoke_this_peer`（本地对端 ignore_unchoke_slots，不补会永远 choked）。`ht_load_resume_dir` 清掉 resume 里的单种子 `upload_limit` 残留（本桥无 per-torrent 限速功能，残留只可能来自本 bug）。
- **[x] ② 已加自动化测试** — `packages/fushi_torrent/test/upload_off_download_test.dart`：「download completes while the torrent itself is upload-blocked」（修复前红：60 s 超时）、「upload-blocked seeder serves no payload until unblocked」（截停期间 0 payload、解除后完成；修复前红：元数据都拿不到）。
- **备注**：「下载途中达标要不要停上传」本身（第三方建议对齐 qBittorrent 只在做种阶段生效）是行为取舍，列为拍板事项 `review-torrent-ratio-during-download`，本修复不改语义。
