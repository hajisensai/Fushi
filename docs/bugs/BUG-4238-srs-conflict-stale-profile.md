## BUG-4238 · 复习同步冲突：一边采用对方 profile 解决后，另一边仍按检出时缓存的旧冲突再问一次（旧候选、旧笔记数），选了会分叉
- **报告**：2026-11-07（用户：两台设备经互联配对、各有自己的复习 profile；host 在「复习同步冲突」弹窗里采用了客户端的 profile 并入成功、两边同为 4 条笔记，之后客户端也弹了冲突，候选是 host 已经并走的旧 profile，「本设备：1 条笔记」也是旧数。证据在本机，未入库）
- **真实性**：✅ 真 bug，但不是「旧 profile 还留在同步位置、检测仍把它当活的」——host 并入后的那轮立即同步里 `SrsDbProfileLinker.link` 已经把它离开的旧 uid 目录清掉了（只有它自己写过），重新判定的结果是「本机 uid 目录里已有 host → 已关联」。客户端被问的是**检出那一刻缓存下来的冲突快照**，三层都不重新验证：
  - `fushi/lib/src/srs/srs_sync_scheduler.dart:993-998`（修前）：判出冲突后 `_linkDecided` 把这个结论复用 `kSrsProfileConflictRecheck`（30 分钟），期间后台轮次直接跳过 `linker.link`；注释前提（`:564-566`）「冲突不会因为再列一遍目录而改变」是错的——另一边解决冲突之后它就不成立了。
  - 同文件 `:1004-1024`（修前）：重新判定判不出冲突时 `profileConflict` 也从不清掉。
  - `fushi/lib/src/srs/srs_app_runtime.dart:578-594`（修前）：`_pendingConflict` 是通知那一刻抓的快照，用户之后进复习页时原样弹出（进页的同步排在弹窗之后），候选和「本设备 N 条」都是检出时的。
  - `srs_sync_scheduler.dart:1148-1196`（修前）：`adoptProfile` 不核对所选候选此刻是否还是冲突的一方。
  - **选那个旧候选的后果（已用测试复现）**：客户端把自己（含刚从 host 并进来的笔记）并进 host 已弃用的旧 uid、在同步位置上重新建出那个目录；host 留在新 uid，目录里有客户端的旧写入者 → 判成「已关联」、永不再提示。两边各同步各的 uid，客户端之后新建的笔记到不了 host（静默分叉）。没有丢数据（两边各自保有分叉前的全部笔记），但复习从此不互通，客户端还会被再问一次（候选变成 host 当前的 uid）。
- **[x] ① 已修复**（分支 `fix/srs-conflict-stale-profile`）— 冲突是对同步位置现状的判断，现状变了它就作废：
  - 调度器：冲突**不再复用**，每轮重判（与「未关联」的轮次一样本来就每轮列目录；只有「已关联」永久复用）；`kSrsProfileConflictRecheck` 改为「同一个冲突隔多久再通知」。判定收进 `_link`：判不出冲突时作废属于这个（位置, 本机 profile）的 `profileConflict`；判出时换成这一轮的（候选与笔记数都是现在的），只在候选变了或满间隔时通知。
  - 新 `SrsSyncScheduler.recheckProfileConflict`：在冲突所在的位置（通道先拿通道锁、本机目录只串行）按现状重判，返回此刻仍成立的冲突或 null。app 侧弹窗之前先重判，只问仍成立的、报现在的数。
  - `adoptProfile` 在同一把锁里先重判，所选 uid 不再是候选就抛 `SrsProfileConflictStale`、什么都不动；冲突所在位置不可用（没法重判）也不盲并。app 侧：已解决提示「这个冲突已经解决了，没有做任何改动」（新 key `srs_sync_profile_conflict_resolved`），候选变了按新的再问一次。
  - 真正未解决的冲突照常：仍成立就照常弹、照常采用 / 并入 / 暂缓。
  - **并入暂缓的窗口**（`packages/fushi_engine/lib/srs/srs_profile_link.dart` `srsDecideProfileLink`，修前 `:153` / `:159` 只看目录里有没有别的写入者）：一边采用对方的 profile 时若并入暂缓（BUG-4217：旧 profile 里有 undo 撤销的日志还没同步到），它按旧 uid 照常同步（这正是把缺的日志收进来的途径），同步位置上那个旧 profile 目录仍在、仍有它的写入者，另一边重判照样把它当候选——选了就把自己并进对方正在离开的 profile，对方并入做完后两边分叉。用户的决定在采用那一刻就已经做出，只是 srs.db 里的并入标记（`profile_merge/<旧 uid>`）只有本机看得到。改为**把决定发布出去**：`SrsDbProfileLinker.publish` 在当前 profile 有没做完的并入、且还在旧 uid 上时，往说明文件 `profile.json` 写附加键 `mergingInto: <目标 uid>`（由持久的并入标记派生：重启、离线多久都在；并入做完标记删掉、换到新 uid，旧目录随后由 `link` 清掉）；`adoptProfile` 遇暂缓时在同一把锁里马上发布，不等之后那轮同步。`srsListRemoteProfiles` 按写入者读出 `SrsRemoteProfile.mergingInto`，`srsDecideProfileLink` 只把**留下的**写入者算作 profile 的成员：离开中的写入者既不让它的旧 profile 成为候选，也不让本机判成「已关联」。旧 profile 里还有别的留下的设备时它照样是候选。
  - 没选的做法：暂缓时让这边立刻换 uid、只把本地并入推后——缺的日志要靠按旧 uid 同步才收得进来，换了 uid 就收不到，正是暂缓要等的东西；而且并入做完之前它在新 uid 下也发布不出自己的数据。
  - 兼容：`mergingInto` 是附加键（与 `device` / `notes` 同样做法），旧版本读者忽略它、照旧把那个旧 profile 当候选（与修前一样，不会更坏）；旧版本写的说明文件没有这个键，按修前那样算。
  - 已知余量：并入永远等不到缺的日志（BUG-4217 写明的代价）时这台设备一直留在旧 uid、一直声明 `mergingInto`，对方也一直不会被问起它——两边不互通，但不会再被引向分叉。两边同时互相采用对方、都暂缓（彼此的 `mergingInto` 指向对方）仍会在并入做完后交换 uid，这是修前就有的竞态，不在本修复范围。现在没有「取消暂缓的并入」的入口；以后加的话删掉并入标记，下一次发布就不再带 `mergingInto`，对方随之重新看到候选。
- **[x] ② 已加自动化测试** — `fushi/test/sync/interconnect_srs_two_way_sync_test.dart`「两边都有笔记、host 采用客户端的 profile 之后…」：真 `FushiSyncServer` + 真互联客户端 + 两台各自的 `SrsDbProfileLinker`，两边各一条笔记 → 都检出冲突；客户端再建一条后重判报 2 条（快照是 1）；host 采用客户端的 profile → 客户端后台轮次后 `profileConflict` 为 null、重判为 null、拿旧冲突采用抛 `SrsProfileConflictStale` 且 uid 不变、两边 uid 一致（修前：客户端仍挂着候选为 host 旧 uid、笔记数 1 的冲突，采用后两边分叉）。`fushi/test/srs/srs_sync_scheduler_test.dart`「profile 冲突每轮重判…」覆盖调度器层的清除 / 重判 / 拒绝 / 不重复通知。暂缓变体：`interconnect_srs_two_way_sync_test.dart`「host 采用客户端的 profile 但并入暂缓…」，host 旧 profile 里放一条撤销第三台设备复习的 undo（被撤销的那条没到）→ 采用客户端的 profile 返回暂缓、host 留在旧 uid、旧目录还在 → 客户端后台轮次后 `profileConflict` 为 null、重判为 null、拿旧冲突采用抛 `SrsProfileConflictStale` 且 uid 不变；缺的日志送到后 host 做完并入、两边同一 uid、旧目录清掉（修前：客户端仍挂着候选为 host 旧 uid 的冲突）。`packages/fushi_engine/test/srs/srs_profile_link_test.dart` 覆盖 `mergingInto` 的读写与判定（离开中的写入者不算候选 / 不算已关联，旧 profile 里还有留下的设备照样是候选，指向自身的无效值忽略）。
