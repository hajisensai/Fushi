## BUG-4356 · Android 低端机冷启动 8s ANR：WebView 预热在首帧前于主线程初始化 chromium
- **报告**：2026-11-07（应用内崩溃报告，反馈 LQhvpnzzkz；Android 14 低端机，3.3.0）
- **真实性**：✅ 真 bug（触发点按代码路径推定，ANR 栈底被截断）。ANR `Input dispatching timed out (Application does not have a focused window)`，内存采样 `frames=0`（首帧从未画出），主线程 state=D 卡在系统 WebView 首次初始化（`AwBrowserProcess` → `BrowserStartupControllerImpl` → `NewStringUTF`）。沿 develop 代码：`fushi/lib/main.dart` 启动预热段（约 838-900 行）只有桌面端在构造 `HeadlessInAppWebView` 前 `await WidgetsBinding.instance.endOfFrame`，移动端在首帧前就 `run()`；flutter_inappwebview 的 Android 插件在主线程同步初始化 chromium，而 Flutter 3.29+ Android / iOS 的 UI 线程与平台主线程合一，低端机上把首帧一起堵死。与该段注释「用户在看主页/书架时把冷启动成本吃掉」矛盾。另外即便桌面端的 `endOfFrame` 也不够：启动时 `deferFirstFrame()` 生效期间帧照样 build / layout，`endOfFrame` 会在首帧还没上屏时完成。`shouldPrewarmWebView`（`fushi/lib/src/startup/webview_prewarm.dart:8-15`）只管「要不要」，不管「何时」。
- **[x] ① 已修复** — 新增 `runWebViewPrewarmWhenIdle`（`fushi/lib/src/startup/webview_prewarm.dart`），作为所有平台唯一的预热时机门：先等 `binding.waitUntilFirstFrameRasterized`（首帧真正上屏），再等 `SchedulerBinding.scheduleTask(..., Priority.idle)`（默认调度策略下有动画在跑时不执行 idle 任务，避开首屏入场动效），然后才构造并 `run()` headless WebView。`main.dart` 预热段改走这道门，删掉只在桌面端生效的 `endOfFrame` 分支；`WebViewPrewarmSession` 的四路终点收口原样保留。
- **[x] ② 已加自动化测试** — `fushi/test/startup/webview_prewarm_gating_test.dart`：用 Completer 当 fake binding，断言首帧光栅化前不预热、也不提前申请空闲槽；首帧已上屏但未空闲时不预热；两者都到后恰好预热一次且顺序为「申请空闲 → 预热」；prewarm 抛错原样外抛。源码守卫钉住 `main.dart` 唯一的 `HeadlessInAppWebView(` 构造落在 `runWebViewPrewarmWhenIdle(` 之内，且门参数含 `waitUntilFirstFrameRasterized` 与 `Priority.idle`。
- **备注**：Feedback: LQhvpnzzkz。本分支未运行测试（统一在合并后验证），未在真机 / 低端模拟器复测冷启动。首帧之后 chromium 初始化仍在主线程上同步跑（插件行为，非本仓可控），极低端机首帧后可能有一次可感知卡顿；是否按可测量设备信号（如 `ActivityManager.isLowRamDevice` / 总内存）在低端机跳过预热留作待决策项，本修复未加。
