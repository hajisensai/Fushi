## BUG-3801 · 空 Profile 导入 APKG 撞 srs_field_edits.id 主键；删 Profile 后 SRS 数据残留
- **报告**：2026-10-27（用户：应用内反馈 8TaOy2i-lL，Windows `3.0.1-debug.20797`，提交于 2026-10-24）
- **真实性**：✅ 真 bug（两处）。
  - **现象 1（导入撞主键）**：所有 profile 共用一个 `srs.db`，`srs_field_edits` 主键只有 `id`（`native/fushi_fsrs/src/store/schema.rs:90-99`），修改记录 ID 由 dot 派生、不含 profile（`native/fushi_fsrs/src/registers.rs:205` `edit_id = uuid_v5("edit/{writer}/{seq}")`）。用户那版（同步 v2 之前）Dart 本机写入者是**每台设备一个**：`'$deviceId#$_incarnation'`（`deviceId` 来自全局 `SyncRepository.getOrCreateDeviceId()`，`fushi/lib/src/srs/srs_providers.dart:244`），而 `lastSeq` 存在**按 profile 分行**的 `srs_local_state` 里（旧 `packages/fushi_engine/lib/srs/srs_db_store.dart@5597af7cb1^:518`）。新 profile 的 `lastSeq` 从 0 起，第一条修改记录就是 `edit/<deviceId>#1/1`——正是老 profile 的第一条；旧 `_storeLocalBatch` 照搬 Dart 算的 ID 直接 `insert`（同文件 `@5597af7cb1^:1165`），于是整批回滚。
  - **当前代码**：同步 v2（`5597af7cb1`，2026-10-25，晚于用户版本）起本机写入一律经 Rust `sync2_apply_local`，非 stamped 修改记录的 dot 由 Rust 按**该 profile 的本机身份**重新分配（`native/fushi_fsrs/src/store/sync2/mod.rs:830-873` `body_of_event` 不读 Dart 给的 w/s/id；`mod.rs:376-393` `edit_row` 用 `op.id.device` / `op.id.seq`），而每个 profile 的本机身份是独立随机的 v7 设备 ID（`mod.rs:127-152` `Local::create`，`sync2_self` 按 `profile_uid` 分行）。保留旧 dot 的 stamped 路径只来自同一 profile（旧 `.fushisrs` 导入校验 `manifest.profileUid`：`packages/fushi_engine/lib/srs/sync2/srs_fushisrs.dart:133/209`；备份合并按 `bp.uid` 取事件：`srs_backup_merge.dart:300`；迁移按 profile 包旧行）。所以根因（写入者身份不分 profile、ID 命名空间与主键却跨 profile）在 HEAD 上已从结构上消失。**不改 ID 方案**：修改记录 ID 是线协议（`parse_edit` 校验 `id == edit_id(w, s)`、迁移进来的旧记录在各端按原 dot 得同一 ID），把 profile 纳进 ID 或改主键都会让已同步 / 已迁移的数据在两端 ID 不一致。
  - **现象 3（`profile rm` 残留）**：`fushi/lib/src/profile/profile_repository.dart:92-105` `deleteProfile` 只删主库 `profiles` 行（`packages/fushi_core/lib/src/database/database_tags_sync.part.dart:990`），`srs.db` 里该 `profile_uid` 的投影表（`srs_entities` / `srs_field_edits` / `srs_review_logs` / 缓存表）、同步 v2 表（`sync2_self` / `sync2_ops` / `sync2_devices` …）与 `srs_media/<uid>`、样式目录都没人清。uid 只记在被删的 `profiles` 行里，删完后再无入口找到这些数据。
- **[ ] ① 部分修复** — 现象 1：根因已由 `5597af7cb1`（同步 v2，本机写入的 dot 按 profile 本机身份分配）修掉，本条补回归测试钉住。现象 3：**待产品决策，未改**（见备注）。现象 2（CLI 自动拉起 / 控制通道超时）按任务范围不修。
- **[x] ② 已加自动化测试** — `native/fushi_fsrs/src/store/sync2/tests.rs` `second_profile_writes_never_reuse_another_profiles_edit_ids`：老 profile 留着旧写入者 seq 1..3 的旧行（并已迁移），先证实照搬同 ID 落进新 profile 就是 `UNIQUE constraint failed: srs_field_edits.id`；再让新 profile 带同一组旧 dot 的草稿经 `sync2_apply_local` 写入——全部落库、writer 是新 profile 自己的设备 ID、ID 与老 profile 不相交、老 profile 行不变。
- **备注**：
  - 现象 3 候选方案（删 Profile 是 `OpRisk.irreversible` + 用户确认，`fushi/lib/src/ops/op_descriptions_settings_more.dart:179`；确认框没提到会连带 SRS）：
    - A（推荐）**级联清理 + 确认框写明代价**：删 Profile 时在同一流程里由 Rust 胖核心一条粗粒度命令（如 `srs_purge_profile(uid)`）在一个事务里删掉该 uid 的全部 `srs_*` / `sync2_*` 行，再删 `srs_media/<uid>` 与样式目录；确认框列出「将删除 N 张卡 / M 条复习记录」。删除前自动做一次该 profile 的 SRS 备份（现有 `SrsBackupController`），作为唯一的恢复途径。已同步到远端位置的集合不动（别的设备照常），本机只是退出该集合。
    - B **软删 / 归档**：删 Profile 只摘入口，SRS 数据按 uid 保留 N 天，在「数据管理」里列出无主 SRS 数据供恢复（重新挂到新 Profile）或彻底清除。多一套 UI 与过期回收。
    - C 维持现状但提供「清理无主 SRS 数据」入口（扫 `srs.db` 里不对应任何 `profiles.uid` 的数据）。只治存量，不改删除语义。
    - 存量用户（已删过 Profile 的）无论选哪个都需要 C 那一步扫一次。
  - 日志里另有一条 `FormatException: field edit id mismatch: 6a816f65-368e-4493-… vs bf0e1adc-…`（`SrsFieldEdit.fromJson`，`allNoteViews`）：库里有一行修改记录的 ID 是 v4 随机 UUID、与 dot 不符，来源未查明（不像本仓任何写入路径产生；用户迁移过程中可能直接动过库）。不在本条范围。
