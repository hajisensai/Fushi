## BUG-5185 · Windows 退出时 LdrShutdownProcess 卸载 DLL 死锁：进程变僵尸占着单实例互斥量，之后无法再启动
- **报告**：2026-11-22（外部 PR #4042，作者 zymy8848，附现场调用栈）
- **真实性**：✅ 真 bug。根因 `fushi/lib/src/platform/app_exit_coordinator.dart` 的 `_systemExit`（原为 `io.exit(code)`）：Windows 上 `exit` → CRT `exit` → `ExitProcess` → `RtlExitUserProcess` → `LdrShutdownProcess`，内核先杀掉除主线程外的全部线程，再在持有 Loader Lock 时逐个跑 `DllMain(DLL_PROCESS_DETACH)` 与 `ucrtbase!execute_onexit_table`。进程内经 FFI 加载的 `onnxruntime_providers_cuda.dll`（GPU 运行时包，`fushi/lib/src/asr_host/gpu_runtime_pack.dart`）的 `OneDsTelemetry` 静态析构走 `WinHttpCloseHandle` → `CancelMibChangeNotify2` → `NsiRpcDeregisterChangeNotificationEx` → `NtWaitForSingleObject`，等的回调线程已被杀，永久挂起（作者现场栈，本机未复现）。runner 的 hang_watchdog 与 Dart 退出看门狗此时都已被杀，主线程一直占着 `FushiSingleInstanceMutex`，新实例在 `fushi/windows/runner/main.cpp` 等满 `kPreviousInstanceWaitMs`=20s 后静默退出 →「关掉后再也打不开」。同一机制此前已出过 BUG-255 / BUG-289（DCOMP 静态析构在 atexit 期 FailFast）、BUG-2046（LunaHook DLL_PROCESS_DETACH 访问违例）。
- **[x] ① 已修复** — 新增 `fushi/lib/src/platform/windows_process_exit.dart`：Windows 上 `AppExitCoordinator` 的唯一出口在落盘（会话标记 clean 等）完成后改用 `TerminateProcess(GetCurrentProcess(), code)`，跳过整个 loader 拆除，对任何第三方 DLL 普遍有效（不逐个 DLL 打补丁）；Win32 调用失败 / 抛异常回退 `io.exit`，非 Windows 不变。exitApp / restart / 退出看门狗 / 更新交接（生产不传 `exitProcess`，走同一默认出口）全经此出口。`terminate` 文档写明契约：持久化必须在调用前显式完成，退出期 DLL detach / atexit / `FILE*` flush 不再执行。WAIT_ABANDONED 已在 `fushi/windows/runner/single_instance_mutex.h` 视作拿到，下个实例直接接管。
- **[x] ② 已加自动化测试** — `fushi/test/platform/windows_process_exit_test.dart`：分派 / 回退单测、`_systemExit` 接线守卫；Windows 上真实拉起 Dart 子进程验证 `TerminateProcess` 退出码、其后代码不执行，以及被持有的命名互斥量变成 WAIT_ABANDONED（非 Windows 跳过）。
- **备注**：未覆盖的残余路径：runner 消息循环自然结束（`WM_DESTROY` → `PostQuitMessage` → `wWinMain` return → CRT exit）仍走 `ExitProcess`；现状下桌面端 `setPreventClose(true)` 让关窗全部进 Dart 退出链，lib/ 里也没有 `windowManager.destroy()`，此路径实际不可达，故不改 runner。修复版 PR supersedes #4042。
