## BUG-2199 · 自动补刮以进程为幂等键致本会话新入库作品永不补刮
- **报告**：2026-09-07（用户：「我用 fushi 下载的却没有刮削？」——实证「薬屋のひとりごと (2023)」24 集入库后 `media_collections.anilist_id`/`cover_path` 全 NULL、`collection_scrape_meta` 无行、`video_metadata_works` 无行，卡片封面回落到抽帧图）
- **真实性**：✅ 真 bug。根因 `fushi/lib/src/media/video/metadata/video_library_scrape_sweep.dart:52/74/78`：幂等键是进程级 `bool _swept`，且在 `try` **之前**置位——进视频 tab 那一刻库里有什么就永远只有什么，连 `subsets.isEmpty` 直接返回的空轮也把闸烧死。而内置下载管线 `video_download_pipeline_service.dart:3443` 的 import 落库**必然晚于**那一轮（生产库实测：sweep run 42 起于 23:07:39，合集 81 建于 23:07:45，差 6.4 秒），于是本次会话下载的作品结构上永远进不了自动补刮，必须重启 app——正好废掉 BUG-2004 留下的「无 AniDB 身份的下载作品由自动补刮认领」承诺。触发点只有 `home_page.dart:436`（首帧且当前是视频 tab）与 `:917`（`_selectTab` 切到视频 tab）两处，都不含「库里多出条目」。
- **[x] ① 已修复** — 幂等键从进程换成**作品**：`_attemptedWorkKeys`（`VideoSourceScrapeWork.stableKey`）+ `_sweeping` 防重入，记账推迟到真正提交批次前一刻（被互斥门挡回的作品不算已尝试）。`sweepOnce` 拆出 `sweepAndListPending()`：一次查库两用，回传待确认清单给 UI，未尝试过的作品同时进批次；总闸关/controller 忙只是不发批次，清单照常回传。触发点收口到视频页并补上第三个时机：`home_video_page.dart` 的 `initState`（首次进入，视频 tab 访问过才挂载故严格等价于旧的 `home_page.dart:436`）、`onTabActivated`（每次切回，等价旧 `:917`）、`_onVideoUidsChanged` 集合真变分支（**新增**：内置下载管线 import 落库走的就是这条 uid 流，用户停在页面不动也能等到补刮）；`home_page.dart` 两处旧调用同步删除，避免两条路径做同一件事。保守性未丢：查无/歧义的老作品仍只自动试一次，不会因触发变频繁而反复占 AniDB 的进程级限流队列。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/metadata/video_library_scrape_sweep_test.dart`：旧用例「每进程只跑一轮」按新契约改写为「同一作品每进程只自动尝试一次」（连调两次仍只发一批，且带上 plannedTitles 断言），新增「同一进程内新入库的作品会被后续 sweep 认领（BUG-2199）」（第二轮只带新作品）与「sweepAndListPending 回传待确认清单，总闸关时也照常回传」。UI 侧接线由 `fushi/test/pages/home_video_pending_scrape_banner_test.dart` 的「库里多出条目就地重算，不必切走再回来（BUG-2199）」守住——已做变异实测：摘掉 `_onVideoUidsChanged` 里那次重算，该用例立刻变红。
- **备注**：与 [[BUG-2201]] 同批：本条修「补不上」，那条修「补不上时用户看不见」。不动 BUG-2004 的 AniDB 判据——退回去就是重新引发「强制刮削→歧义→needsAttention 卡死」。
