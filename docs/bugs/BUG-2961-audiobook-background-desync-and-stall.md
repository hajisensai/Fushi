## BUG-2961 · 后台挂有声书：切回来高亮/视口与音频不同步，挂久了音频断掉且点不起来
- **报告**：2026-10-06（用户：「现在后台挂有声书的时候，切回来字幕轴很容易就乱了字幕高亮条和音频不同步。而且，挂的时间稍微长点，好像音频就被断了。」）
- **真实性**：✅ 真 bug（沿真实代码路径定位，三条独立根因；本机无 adb 设备，未做真机复现）。
  cue 索引本身**不会漂**：`_updateCurrentCue` 每个 tick 都按播放器真实位置二分（`JsonAlignmentParser.findCueIndex`），高亮 class 始终挂在正确的句子上。错的是视口与播放激活：
  1. **视口投影丢失、回前台无人重投影**。跟随音频时视口只是播放位置的投影，后台期间投影会丢：WebView 不可见被 Chromium 节流（rAF 冻结、`scrollBy({behavior:'smooth'})` 不落地）；Flutter 在 paused 时停帧，post-frame 回调积压。最狠的一条是**后台跨章**：`_onRestoreComplete`（`reader_fushi/navigation.part.dart:179`）调 `_reanchorContinuousAfterRestore`（`reader_fushi/chrome.part.dart:1376`），阶段 1 立即以 `__restoreCharOffset`（= 进章那一刻那句）为锚，阶段 2 提交挂在 `addPostFrameCallback` 上——后台不出帧，提交积压到**回前台第一帧**才执行，`scrollToCharOffset` 把视口拽回进章那一句，而高亮在真正在播的句子上（通常已在屏外）。`didChangeAppLifecycleState` 的 resumed 分支（`reader_fushi_page.dart`）只回收焦点 / 续表，没有任何按当前音频重投影的动作，只能等下一次 cue 变化（`audiobook_controller.dart` `_updateCurrentCue` 同句不 notify）才纠正。
  2. **播放激活串行尾永久卡死**。`_activateMainPlayer`（`audiobook_controller.dart`）把串行尾押在 `await _player.play()` 上；just_audio 0.9.46 的 `play()`（`just_audio.dart:937-975`）在 `audioSession.setActive(true)` 返回 false（来电 / 音频焦点被别的 App 占着）时只把 playing 回滚成 false，`playCompleter` 从未交给平台层，末尾 `await playCompleter.future` **永不完成**，pause / stop 都解不开它。此后所有经 `_activateMainPlayer` 的播放请求（播放键 / 通知栏 / 耳机 / 插图停留恢复）全部排在它后面永不执行——「音频断了且再也点不起来」，只能重开书。TODO-2369 当时只修了 reader 侧不 await，串行尾本身没修。
  3. **系统 PLAY 被当成 toggle**。`FushiAudioHandler.play()` / `pause()`（`utils/misc/fushi_audio_handler.dart:26-34`）都调同一个无方向的 `onPlayPause`，会话侧 `_controlStreams.playStream.listen((_) => controller.togglePlayPause())`（`audiobook_session.dart`）。走 `play()` 的有方向命令（通知栏 / 锁屏按钮、TransportControls：Android Auto / Assistant / 系统媒体恢复、iOS 远程命令）在播放中收到 PLAY，声音反而被暂停。
- **[x] ① 已修复** — 见本分支提交（`fix(audiobook): resync viewport after background, unstick play activation, directional media intents (BUG-2961)`）。
  1. 控制器新增 `resyncReaderToAudio()`：只在正常跟随本就会 reveal 的条件下（`shouldRevealCurrentCue`：跟随开 / 按过播放 / 正在播 / 非单句试听）且无手动翻页护栏、不在跨章过渡中时，做一次跨章检查（`_maybeEmitCrossChapter(bypassPlayGuard: true)`，后台导航超时中止后由它重新发起跨章）再 `notifyListeners()`，让 `_onCueChanged` 以正常跟随判据 reveal。**不置** `_forceNextReveal`（审查发现：强制旗会越过歌词覆盖层「跟随音频关」的自由滚动，把歌词列表拽回居中）。reader 两处调用：resumed 分支 `addPostFrameCallback`（排在积压回调——含恢复重锚提交——之后）；恢复重锚 `onAfterCommit`（重锚落定后视口归属交还给跟随音频，无论提交何时落地）。暂停态 / 手动翻页 / 跟随关闭一律不动视口，不吃用户的阅读位置。
  2. 新增顶层 `playActivationSettled(played, playingStream)`：激活在「play Future 完成」或「播放态翻回 false」任一发生时结束（流关闭也算，`orElse` 不抛 `StateError`）。`_activateMainPlayer` 改用它。串行化语义保留（播放中第二次 play 仍排到 pause 之后），Darwin / ExoPlayer「play 回调挂到 pause 才回」不受影响，`stopPlayback` 不 await 串行尾的不变式不变。
  3. `MediaPlayIntent { play, pause, toggle }`（**仅覆盖有方向的命令路径**，见备注）：handler 的 `play()` / `pause()` 发有方向意图，`click(MediaButton.media)` 覆写为 toggle（不走基类按 `playbackState` 分派——关掉媒体通知时 `playbackState` 恒为初始未播放，基类会把单击恒判成 PLAY，耳机再也停不下来）。`AudioController.playIntentStream` / `AudioControlStreams.playIntentStream` 取代无方向的 `playStream`；会话经 `applyMediaPlayIntent` 只在状态不一致时调 `togglePlayPause()`（复用其完整语义）。
- **[x] ② 已加自动化测试** — `fushi/test/media/audiobook/audiobook_background_resync_test.dart`（13 条）：`playActivationSettled` 行为（play 永不完成 + 播放态翻 false → 结束；仍在播 → 不结束；正常完成；流关闭不抛）；`mediaPlayIntentNeedsToggle` 真值表 + handler 把 play / pause / 单击 / next 分别路由；`resyncReaderToAudio` 用假 just_audio 平台跑真控制器（跟随播放中强制 reveal + notify；暂停 / 手动翻页护栏 / 跟随关闭三种都不动）；装配守卫（resumed 分支 post-frame 调用、重锚 `onAfterCommit` 调用、`_activateMainPlayer` 用 `playActivationSettled` 且不再裸 `await _player.play()`、会话按意图落控制器不再直接 toggle）。变异实测见提交说明。
- **备注**：
  - **残留缺口 A（Android 按键补发的 PLAY 仍是 toggle）**：audio_service 0.18.19 把真实的 `KEYCODE_MEDIA_PLAY` / `KEYCODE_MEDIA_PAUSE` 经 `listener.onClick(eventToButton(event))` 交给 Dart（`AudioService.java:976-981`），而 `eventToButton` 对这两个键码走 default 返回 `MediaButton.media`（`:989-998`）——方向在原生层就丢了，Dart 侧拿不回来。所以蓝牙耳机 / 车机**以按键事件**补发的 PLAY 仍落到 `click(media)` → toggle（与修复前行为一致，未退化）。根治要给 audio_service 原生层打补丁（`ci/patches/hosted/`）把 PLAY / PAUSE 键码映射到 `onPlay` / `onPause`，另开一条处理。
  - **残留缺口 B（回前台时已停播）**：若后台被抢焦点 / 来电而停播，回前台时 `shouldRevealCurrentCue` 为假，resync 不动视口；视口停在积压重锚提交的位置（进章那句），直到再按播放后的下一次 cue 变化才 reveal（`play()` 只在插图停留时 snap）。根治需让「音频驱动的跨章恢复」在重锚提交时改以当前 cue 为锚，本条未做。
  - 前台连续模式音频跨章时，视口落位从两段滚动变为三段（restore reveal → 重锚提交滚到锚的视口首边 → resync reveal 把它推回 15% 安全线）；语义与跟随一致，是否可感知待真机确认。桌面端每次窗口重获焦点（`inactive → resumed`）也会 resync，行为同跟随。
  - **真机复测未做**：本机 `adb devices` 为空。原始失败路径（Android 后台播放跨章 → 回前台看高亮与视口；来电后点播放）待在设备上补测。
  - **未在本条修、需所有者拍板**：前台服务 + `PARTIAL_WAKE_LOCK` 只在 audio_service 收到 `playing=true` 时建立（`audio_service-0.18.19 AudioService.java:705-733`），而唯一推这个状态的 `_syncMediaNotification`（`audiobook_session.dart`）被「显示媒体通知」开关门住；just_audio 的 ExoPlayer 又不持唤醒锁。**关掉媒体通知 = 后台播放没有任何保活**，熄屏 / Doze 后被系统冻结是必然的；播放中关掉通知还会 `clearNotification()` 推 idle 态，立即 `stop()` 前台服务。Android 不允许无通知的媒体前台服务，所以这是产品取舍（关通知时是否仍保留最小通知 / 还是明示「关通知则后台不可靠」），不擅自改。
  - 后台跨章兜底超时（`navigation.part.dart` `_startContentReadyTimeout` 8s）仍会在 WebView 被节流时触发，BUG-2529 已保证守卫解除；本条只保证迟到的恢复回执落地后视口归属正确。
