## BUG-2691 · Emby 杜比视界 Profile 5 片源画面紫绿反色
- **报告**：2026-09-26（用户：「emby 先发五虎 这部片有问题好像直接反色了，看看是格式识别有问题还是怎样」）
- **真实性**：✅ 真 bug（用随包 libmpv 同帧对照复现）。服务器是 uhdnow 兼容层，`PlaybackInfo` 只给直出（`SupportsTranscoding=false`），片源 `先发五虎 - S01E01 - 2160p - WEB-DL DV.mkv`：HEVC Main 10，`VideoRange=Dolby Vision`、`ExtendedVideoSubtype=DoviProfile50`——**DV Profile 5，无兼容基础层，像素是 IPTPQc2 而不是 YCbCr**。libmpv 识别是对的（`video-params/colormatrix=dolbyvision`，`bt.2020/pq`），**不是格式识别错**，错在渲染器：Windows 纹理路径是 `vo=libmpv`（gl_video 渲染器，与 `vo=gpu` 同一套），不做 DV RPU 重整，把 IPT 当 YCbCr 解就是肤色品红、整片紫绿；只有 `vo=gpu-next`（libplacebo）会重整。python-mpv 加载安装版 `libmpv-2.dll` 对同一帧（15 s，精确 seek、暂停后截 window 图）：`vo=gpu` 品红、`vo=gpu-next` 正常，宿主窗原样属性组（`gpu-context=d3d11` + `d3d11-output-format=rgb10_a2` + `target-colorspace-hint=auto` + `hwdec=d3d11va`）在 SDR 屏上同样正常。而用户偏好是 `video_hdr_output=auto`、显示器是 SDR，`shouldUseHdrHostWindow` 的 auto 分支只在「显示器 HDR ∧ 片源 HDR」时才进 gpu-next 宿主窗（`fushi/lib/src/media/video/video_hdr_output.dart` 原 `return displayHdr && sourceHdr;`），于是 DV P5 永远落在不会重整的纹理路径上。
- **[x] ① 已修复** — `requiresDolbyVisionReshape`（`video_hdr_output.dart`，只认 `colormatrix=dolbyvision`；P8.1 因 RPU `disable_residual_flag=1` 在 mpv 里很可能也被映射为 dolbyvision 而命中，未拿 P8 样片实测）作为片源第二维进 `shouldUseHdrHostWindow(sourceDolbyVision:)`：auto 下 DV P5 **不看显示器**直接进宿主窗（gpu-next 在 SDR 屏上照样重整 + 色调映射，与 always 在 SDR 屏上是同一条已有路径）；off 仍尊重用户。`VideoPlayerController._onVideoParams` 同步记 `_hdrSourceIsDolbyVision` 并传入判据。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/video_hdr_output_test.dart`：auto + DV 在 SDR / HDR 屏都进宿主窗；off 与非 Windows 仍不进；`requiresDolbyVisionReshape` 只认 `dolbyvision`，`bt.2020-ncl` / `bt.709` / null 不算。真机门 `fushi/integration_test/media_server_dolby_vision_p5_itest.dart`（新增测试钩子 `debugHdrHostActive`，凭据经 `--dart-define` 注入，人工点名才跑）。
- **备注**：
  - 只修了 Windows：其余四端没有 gpu-next 可切，DV P5 仍会紫绿（2026-09-26 查证）——macOS / iOS 随包 libmpv 是自编 mpv 0.36 + FFmpeg 6.1.6，没有 libplacebo / Vulkan，走 render API（gl_video）；Android 随包 libmpv 编译参数 `-Dlibplacebo=disabled`，`vo=gpu` 直绘 Surface。也试过让 Apple VideoToolbox 解码：把样片封成 `dvh1` + `dvcC` 的 MP4 在 Mac 上用 AVAssetImageGenerator / AVAssetReader 取帧，结果与 mpv 旧渲染器一样偏色，解出的 CVPixelBuffer 只把 RPU 以 `DolbyVisionRPUData` 附件透传——重整发生在 AVPlayerLayer 的显示合成里，mpv 链路用不上。服务器转码对 uhdnow 这类兼容层也无效（`SupportsTranscoding=false`）。
  - 兜底提示（办法 4）：`dolbyVisionColorsUnsupported`（`video_hdr_output.dart`）判「DV P5 且没有 gpu-next 可用」——非 Windows 恒真、Windows 仅 HDR 输出「关闭」时为真；控制器 `dolbyVisionColorsUnsupportedNotifier` 由 `_onVideoParams` / 模式变化刷新，播放页由假变真时弹 warning OSD（Windows 提示改成「自动」，其它平台说明本平台暂不支持）。**识别信号有两路**：新版 libmpv（Windows）报 `colormatrix=dolbyvision`；mac / iOS 的 mpv 0.36 与 Android 的 mpv 构建**不报**（0.36 的 `mp_csp_names` 里没有 dolbyvision，DV 只在 demux 的 verbose 日志里出现），所以远端流另走服务器元数据：`mediaStreamRequiresDolbyVisionReshape`（`jellyfin_video_client.dart`，Emby `ExtendedVideoSubtype=DoviProfile5x` / Jellyfin `DvProfile=5`、`DvBlSignalCompatibilityId=0`、`VideoRangeType=DOVI`）→ `RemoteVideoStreamUrls.sourceRequiresDolbyVisionReshape`（转码流为 false）→ 控制器 `setSourceDolbyVisionHint`，与 mpv 判断取或。**本地文件与互联片源在 mac / iOS / Android 上暂时识别不到**（互联 wire 的 `RemoteVideoStreamUrls` 没带这个字段），随办法 1 的 mpv 补丁一并补上。
  - 连带修的既有缺陷：播放页远端初始化 `_initRemote` 提前返回，漏读 `videoHdrOutputMode` / `videoFitMode`——Emby / Jellyfin / 互联片源恒按默认 auto / contain，用户设的「关闭」「始终」「铺满」对远端全不生效（itest 关闭段首跑即因此失败：`eval mode=auto`）。已补读，源码守卫在 `video_hdr_output_test.dart`。
  - 根治其余四端（办法 1，进行中）：给自编 libmpv（darwin + android）的 gl_video 打 DV 重整补丁（移植 libplacebo 的算法），另起 PR。注意 Android 默认硬解 `hevc_mediacodec` 不解析 RPU（帧上没有 DV 元数据），补丁对 Android 硬解无效，需另议（DV P5 降软解 / 包侧解析 RPU）。
  - 用户把 HDR 输出设成「关闭」时 DV P5 依旧紫绿——那是显式选择，不越权，只提示。
  - 真 app 验证：`fushi/integration_test/media_server_dolby_vision_p5_itest.dart`（Windows 离屏 runner，对真 uhdnow 服务器这一集）日志 `[hdr-host] params ... matrix=dolbyvision hdr=true dolbyVision=true` → `eval mode=auto display=false ... want=true` → `enter hwnd=...`，切 VO 后位置继续前进。离屏 runner 截不到宿主窗像素，颜色正确性由上面同 libmpv、同属性组的 python-mpv 对照证明。
