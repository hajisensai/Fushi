## BUG-1605 · gal 制卡：同句多个语音资源只取一个（多角色同时说话丢声）
- **报告**：2026-08-14（用户：同一句话多人同时说（女声优+男声优）时会有多个资源文件，制卡只取到某一个人的声音）
- **真实性**：✅ 真 bug。根因是整条配对链的**单资源假设**：`fushi/lib/src/mining/galgame_audio_source.dart:595` `pickPairedGameResource` 返回 `String?`，其 OGG 层 `pickPairedVoiceOgg` 在三个证据层（事件 ID / 精确 tick / 偏移窗）里各只留一个候选（`eventBest`/`exactBest`/`offsetBest`），Unity WAV 层同样只取最近一个；`_findPairedVoiceFile` 因此只落一个 `File`，`grabPairedVoiceBytes` 只转码那一个。native 侧本身没问题——`native/galgame_hook/hook/dll_main.cpp:160` `WriteVoiceOggAt` 按资源 basename 逐个 dump，同一句的多个语音会得到多个文件、且被 `ResolveFollowingSelectedText` 绑到**同一个** `TextSlot::seq`，证据已经在文件名里，只是消费端丢掉了。
- **[x] ① 已修复** — 配对层改为分证据等级的**全量**返回：`pickPairedGameResources` / `pickPairedVoiceOggs` / `pickPairedUnityVoiceWavs`（单值版委托全量版取首元素，不留第二套判据）。只有被证明属于同一句的层允许全取——事件 ID 层（native 已绑定同一条文本）与精确 tick 层（同一毫秒读入 = 同时播放）；偏移窗层和 Unity 无标时间窗是纯时间猜测，仍然单取，否则会把上一句尾音/旁白/系统音一起塞进卡。制卡侧 `grabPairedVoiceBytes` 以行上已固化的主资源为锚，用纯函数 `companionVoiceResourceNames` 沿归属证据扩出同句伴音（不重跑时间戳配对，避免推翻已冻结的主资源），再由 `transcodeVoiceResourcesToMiningAudio` 合成一段音频。合成方式是**按顺序接续**而非叠加混音：入库的 `third_party/ffmpeg-min` 白名单里没有 `amix`/`adelay`/`volume`（`tool/ffmpeg-min/build-ffmpeg-min.sh:188` 的 `FILTERS`，已实测 `ffmpeg -filters` 只有 `aresample`），要混音得改配方 + 重编三平台二进制 + 重新 vendor；而对制卡本身，两人台词分开听比叠在一起更能听清。ADTS 字节接续已实测：0.534s + 0.836s 两段拼接后 `ffprobe` 读出 1.382s、全流解码 exit 0。会话控制器与行状态零改动（多资源发现完全收在音频源内部）。
- **[x] ② 已加自动化测试** — `fushi/test/mining/galgame_multi_voice_resources_test.dart`（23 项）：事件层多资源全取与排序、别的事件 ID 不被顺带收、事件层命中不再看下层、同距按文件名排序不随枚举顺序漂、BGM/SE 排除、精确 tick 层全取、**偏移窗层仍单取**（关键负向）、Unity 带标全取 / 无标单取 / 带标仍参与时间窗兜底（防回归）、单值版恒等于全量版首元素、`companionVoiceResourceNames` 的归属判据与排序、`concatAudioStreams` / `isSelfSynchronizingAudioContainer`。
- **备注**：合成顺序固定为「主语音（离文本时间戳最近的那个）在前，伴音按文件名升序」，制卡结果可复现。m4a/mp4 等非自同步容器仍退回单段（`isSelfSynchronizingAudioContainer`），galgame 路径是 Windows 专属、恒为 `aac`，该分支只是防未来漂移。
