## BUG-4895 · 视频从首页打开后播放掉帧：被播放页盖住的首页仪表盘每秒整批重载一次
- **报告**：2026-11-17（用户：「反馈里的几个视频掉帧和卡顿问题看一下，我本地也有问题」；应用内反馈 dGh4bKRLPP「播放本地视频时经常会出现明显卡顿掉帧」、3pvunBdjll「看番比之前的版本卡很多……轻微掉帧，字幕会逐渐跟不上视频」、j2plixDqML「全屏播放视频卡顿」）
- **真实性**：✅ 真 bug。取证来自用户本机安装版（3.3.0-debug.28434）留下的 `video_diag_log.txt` 与 `session_marker.json`：
  - 同一天、同一台机器的两段播放对照。11:02–11:56 那一集：播放中 Dart 帧约 9 帧/秒、UI 线程 build p50 ≈ 1.6 ms，超预算帧每分钟 0–6 帧。11:57 起另开的一集（VCB-Studio 1080p x265，本地 mkv）：build p50 ≈ 9 ms、单帧 build 最长 80–690 ms，超预算帧每分钟约 120–150 帧（其中 severe 30–45 帧），1 秒一次的统计定时器自己都被拖到 1.5–1.6 秒才触发。两段里 libmpv 的 `vo-delayed-frame-count` / `frame-drop-count` 都是 0——解码和 libmpv 渲染没掉帧，是 Flutter UI 线程被占住：视频纹理的新帧要在 UI 线程上等到 vsync 回调才能交给 raster 线程（`Animator` 同一时间只放一帧在途），UI 线程被一段 Dart 长任务占住 40 ms 以上，24 fps 的片子就跳一帧。
  - `session_marker.json` 的 UI 活动采样点名了是谁：停在 `VideoFushiPage` 的 30 秒窗口里，`_HomeDashboardPageState._loadDashboardDataUnsafe`（`setState(() => _applySnapshot(snapshot))`）被抽到 8–22 次，连带每次重建页头触发的 `FushiShellActionsSlot._scheduleNotify` 160–247 次。播放页开着，重载的却是底下看不见的首页。
  - 根因：`fushi/lib/src/pages/implementations/home_dashboard_page.dart:976-986`（`_scheduleReload`）推迟重载的判据只有 `_isVisibleTab`（当前 shell tab 是不是首页）。从首页「继续」点开视频时首页仍是当前 tab，只是被播放页的路由盖住，判据照样放行。触发源是 `watchDashboardDataChanges`（`packages/fushi_core/lib/src/database/database_statistics.part.dart:1081` 起，表集含 `videoBooks`）：播放断点每秒落库一次——`fushi/lib/src/media/video/video_player_controller.dart:5374-5386`（`_maybeSavePosition`，整秒变化即回调）→ `fushi/lib/src/pages/implementations/video_fushi_page.dart:6964-6970`（`_persistPosition`）→ `packages/fushi_core/lib/src/database/database_video_domain.part.dart:3273`（`UPDATE video_books`）。于是播放的每一秒 → 400 ms 防抖 → `_reloadNow`：作废三个书侧 provider、七路查询 + 全量统计聚合、整页 `setState`、再补一轮远端。从视频 tab 打开的同一个视频不受影响（首页不是当前 tab，被 `_isVisibleTab` 挡住），所以表现为「有时卡有时不卡」。
  - 正式版 `v3.3.0` 的 `_scheduleReload`（`home_dashboard_page.dart:1002-1011`）是同一段判据，三条反馈所在版本都带这个缺口。**但归因只在所有者本机被证实**：三位反馈人附带的日志都没有播放 / 帧时记录（视频诊断日志默认关闭），他们是不是从首页打开的、卡顿是不是这个原因，没有证据。「代码里有这个缺口」不等于「他们的卡顿就是它」；合入后不能据此回复反馈人「已修复」，要么请对方开视频诊断日志在新版上复测，要么只说明修了一个已确认的掉帧原因。
- **[x] ① 已修复** — 「页面此刻真在用户眼前吗」收成 `BaseModuleTabPageState.isShownToUser` 一个判据（`fushi/lib/src/pages/base_module_tab_page.dart`）：取祖先 `TickerMode` 的通知器（`TickerMode.getValuesNotifier`，不建立依赖、不引起整页重建）——框架恰好在「被不透明路由完全盖住」（`Overlay` 给被盖住的条目挂 `TickerMode(enabled: false)`）和「保活 tab 被 `Offstage` 藏着」这两种情况关掉它，对话框 / 弹层不算——再叠上 `shellTab` 判定；由假变真的边沿回调 `onShownToUserAgain`。首页 `_scheduleReload` 改问 `isShownToUser`，不在眼前只记一笔（`_reloadDeferredWhileHidden`），`onTabActivated` / `onShownToUserAgain` 经 `_flushDeferredReload` 补做一次。视频库页原先自己手搓的同一机制（BUG-3610 的 `_routeWasCurrent` + `ModalRoute.isCurrentOf`）改用基类这一份。
- **[x] ② 已加自动化测试** —
  - `fushi/test/pages/home_dashboard_page_test.dart`「BUG-4895 · 首页不在用户眼前时不在后台重载」：真 `Navigator` 压一个不透明路由后连写三次统计表，首页保持盖住前的数据；路由弹走后补做重载显示新值。对照用例：上面只是对话框时照常当场重载。
  - `fushi/integration_test/video_playback_covered_home_itest.dart`（真 app、真 media_kit 播放、真断点落库）：首页 tab 当前时打开带字幕的视频播 20 秒，断言首页监听的表确实被写了多次而首页重建 0 次，播放页弹走后首页重建 ≥1 次。
  - 视频库页沿用 `fushi/test/pages/home_video_watch_progress_refresh_test.dart`「库页被详情页 / 播放页盖住时写下的进度，退回库页即刷新」（机制换成基类后原样通过）。
- **备注**：真 app 复测（Windows 离屏 runner、debug 构建、隔离的空库，同一条集成测试、同一份素材：1080p 24 fps + sidecar 字幕，首页 tab 当前时打开，播 20 秒）：修复前（runId `win-itest-20261117-154624-e6d458f0`）断点写入 20 次 → 被盖住的首页重建 52 次，UI 线程超 16.7 ms 的帧 56 帧、单帧 build 最长 317 ms，测试红（`Expected: <0> Actual: <52>`）；修复后（runId `win-itest-20261117-153710-95e1cd0f`）同样 20 次写入 → 首页重建 0 次，超预算帧 9 帧、最长 161 ms，播放页关掉后首页补载（重建 7 次），测试绿。空库上一次重载本身很轻，用户机器上是 1.6 GB 的真库，单次重载的聚合与重建更重，所以实机改善幅度只会更大；修复后剩下的 9 帧超预算来自播放页自己（debug 构建），与首页无关。未在用户的安装版 / 真库上复测（不碰生产数据根），合入后可用 `video_diag_log.txt` 的 `[frame]` 行对照 11-17 那两段。取证过程中更正过一次触发源：学习时钟的字数只在 60 秒 tick 时落库，不是每句字幕一写；真正每秒一写的是播放断点。同批另外三条反馈成因不同，分别另开：内封文本字幕抽取被总时长预算误杀（ZTDA2WQJj4）、弹幕层逐帧重录（j2plixDqML 的「开弹幕更明显」）、系列墙滚动停顿（eBQtk9r7Z2）。j2plixDqML 的「全屏不开弹幕也卡」若从首页打开则被本条覆盖，否则待弹幕那条的实测数字。
