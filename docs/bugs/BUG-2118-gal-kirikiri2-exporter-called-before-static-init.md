## BUG-2118 · 启动期过早调用 TVPGetFunctionExporter 抢在引擎静态构造之前，导出表随后被构造函数重置致插件链接全失败
- **背景**：本条属于 Hibiki 自有的 galgame 文本/语音接入组件（源码在本仓 `native/galgame_hook/`，仅 Windows）。该组件由用户在应用内为自己已安装的游戏显式开启，用途是读取当前显示的台词并生成学习卡片；边界与验证规则见 [docs/agent/galgame-hooking.md](../agent/galgame-hooking.md)。下文的「早加载」「转接」「接缝」都发生在本应用自己的模块与本应用自己拉起的游戏进程之间，代码与 CLI 里对应的既有命名是 early-inject / detour。
- **报告**：2026-09-04（ceshi 批量适配 · Fate/stay night[Realta Nua] -Fate-：KiriKiri2 2.31.2010.425 BCB，KAG 3.25 beta 10 TYPE-MOON 定制版）。经 Fushi 库内启动**必**弹「スクリプトで例外が発生しました EAccessViolation」，主窗从未出现；同日用户自己经 Fushi 启动 8 次全部同样失败，直接双击启动 5 次仅 1 次失败且能走到脚本阶段。
- **真实性**：✅ 真 bug。分型实验（同一 helper 构建，同一天）：本仓 helper `fushi_voice_injector.exe --launch`，不带 LunaHook、不开日文区域模拟 → 失败；区域模拟开/关 → 都失败；完全不加载我们的模块 → 主窗正常出现；先让游戏自己启动完成、再以 `--pid` 接入 → 不失败。失败点由 krkr 控制台日志 + 崩溃地址对照 tp_stub 上游源码定位（`%TEMP%\krkr_*\fstat.dll` 的 RVA 0xA111 落在 `TVPGetImportFuncPtr`——该函数在导入项缺失时按设计主动写空指针终止进程，是 krkr 自带的错误处理，不是我们造成的内存破坏）：**插件的 `QueryFunctionsByNarrowString` 全部查不到函数**。上游机制（krkrz `base/win32/PluginImpl.cpp`，kirikiri2 同构）：`TVPGetFunctionExporter()` 首次被调用 → `TVPInitExportFuncs()` 置 `TVPExportFuncsInit = true`，并把 653 个函数经 `TVPAddExportFunction` 填进**静态**成员 `tTJSHashTable TVPExportFuncs`。根因在 `native/galgame_hook/hook/adapters/kirikiri_adapter.inc` 的 `TryHookKirikiriVoiceStream()`：我们的 worker 在启动期早加载后立刻走 exe 直取 `ObtainExporter()`，此时 exe 自身的静态构造函数还没运行——导出表被这次过早调用填好，随后又被静态构造函数重新初始化清空，而 init 标志已经置上，于是之后每个插件链接（dirlist.dll 抛 TJS 异常、fstat.dll 走上述主动终止）都失败。我们自己那次 `TVPCreateIStream` 查询恰好落在填表与重置之间，所以诊断位 `0x10000|0x20000` 看起来一切正常（decdiag=0x02a30000，`0x40000` 转接点从未触发）。KiriKiri Z 样本（tenshi_sz / ATRI）exe 无导出，走 LoadLibrary→V2Link 路径，从未撞到。
- **[x] ① 已修复** — `TryHookKirikiriVoiceStream()` 的 exe 直取加门 `FindGameMainWindow() != nullptr`（引擎主窗由 TJS 脚本创建，远在 CRT/静态构造之后；主窗出现前只走 V2Link 路径，那时引擎自己已经调过 `TVPGetFunctionExporter`，表必然已就绪）。真机复验见台账 `docs/plans/2026-09-04-gal-ceshi-batch-classic-kag3.md`。
- **[x] ② 已加自动化测试** — `native/galgame_hook/tests/kirikiri_lookup_source_guard_test.py`：新规则 `find_ungated_exe_exporter_probe`（`TryHookKirikiriVoiceStream` 体内 `ObtainExporter()` 之前必须先出现 `FindGameMainWindow()`）；`RealAdapterTest` 对真文件断言；`MutationSelfTest` 三条变异（门删掉 / 门挪到调用之后 / 函数改名）全红。
- **第二段（同根一族，同一 commit）**：修好启动门后，该样本经 Fushi 库内启动主窗正常、exporter 经 V2Link 到手（decdiag 0x4000000）、`text_hooked=1`，但 `lookup_diag` 里没有 `sensor_installed`。原因：`RunKirikiriLookupInstallOnMainThread` 只在三个引擎转接点（V2Link / `TVPCreateIStream` 导入桩 / 内部 `TVPCreateStream`）里被调用，而 KiriKiri2/BCB 上 host 打开查词之后没有任何一个会再次触发（V2Link 只在启动期一次、BCB 桩整局不触发、内部函数只在 MSVC 分支接管）→ 安装请求置上后永远等不到主线程执行时机。已改为用 `SetWindowsHookEx(WH_GETMESSAGE)` 在目标进程主线程上取得一个与引擎构建无关的执行时机（`EnsureLookupMainThreadSeam`），装上即在回调里完成安装、完成后立即卸载。**真机复验未过**：该样本上传感器仍未安装 —— 复验时它的 `gal_lookup_surface_v1` 偏好尚未建立（没在工作台里为它选文本线程 / 接受点击风险），host 会把共享内存里的 `lookup_enabled` 维持 0，安装从不被请求；这是工作台准入流程，不是 native 缺口。下一步：在 Fushi 工作台为该样本选文本线程 + 接受点击风险，再看 `sensor_installed`。该执行时机本身按 `implemented_unverified` 记。
- **备注**：第一轮曾把日文区域模拟（Locale Emulator）当嫌疑（失败会话都先有「Documents 存档目录不存在」），关掉区域模拟后仍失败，证伪；那行只是导出表被重置后 `Storages.isExistentStorage` 同样查不到函数的连带症状。
