## BUG-3801 · 反馈详情追加截图上传中就显示「没上传成功+重试」，反馈人以为第一下必定失败
- **报告**：2026-10-27（用户：应用内反馈 #aiRZmYl5zS 的追加说明，Android，「追加图片的时候第一下必定失败，重新上传才行」；反馈内容只当证据读）
- **真实性**：✅ 真 bug（界面状态错误，不是上传本身失败；按代码路径推定，反馈未附日志、无法从日志直接证实）。追加截图的路径是 `_addShot` → `FeedbackService.addScreenshots` → `_addScreenshotsNow` **先**把字节 `_stash` 进待传区（`fushi/lib/src/feedback/feedback_service.dart:901`，`_stash` 在 `:672` 里把槽位加进 `_pending` 并 `notifyListeners`），**再** `_retryPendingNow` 上传（`:903`）。详情页 `_attachActions` 把「`pendingSlots` 非空」一律画成失败提示「还有 n 个附件没上传成功」+「重试上传」按钮（`fushi/lib/src/pages/implementations/feedback/feedback_detail_page.dart:248`，改前行号）。于是每次追加截图，在上传那一两秒（D1 预算 / 配额 / R2 写 / D1 追加，HK 移动网络）里都必定先出现失败提示；反馈人点「重试上传」，重试排在同一条附件链上、等原上传完成，接着原上传的「已上传 1 个附件」提示弹出，看起来就是「第一下失败、重传才成」。待传集合同时装着「正在传」与「上次传失败」两种状态，界面无从区分——这是状态模型的缺口。排除项：服务端 `putAttachment`（`services/leaderboard/src/feedback.js:583`）对首次请求没有状态差异（提交时 s0/s1 走同一接口一次成功，最终 s2 也在服务端）；客户端每个请求新建 `http.Client`、补传不签名、不带时刻 / nonce，没有过期凭据之说；图片压缩在 `addScreenshots` 之前 `await` 完成，不存在边压边发。
- **[x] ① 已修复** — `FeedbackService` 记每条反馈链上排着 / 正在跑的附件操作数，暴露 `attachInFlight(id)`（`_serialAttach` 入链时 +1、出链时 −1，前后都通知）；详情页在途时显示「正在上传截图… / 正在上传日志…」+ 不定进度条（`feedback-detail-uploading`），只有不在途时待传槽位才画成「没上传成功 + 重试」。提交：见本分支 `fix(feedback)` 提交。
- **[x] ② 已加自动化测试** — `fushi/test/feedback/feedback_attachment_retry_test.dart`「追加截图：上传进行中算「正在传」不算「没传上去」…」（假 http client 挂起上传，断言在途 / 成功 / 失败三态与最后一次通知）；`fushi/test/feedback/feedback_pages_test.dart`「反馈人详情：追加截图上传进行中显示「正在上传」…」（详情页 widget：上传挂起时有 uploading 卡片、无失败提示与重试按钮，放行后都消失）。
- **备注**：未在真机复测（Android 真实网络下的提示时序）。若真机上仍有真正的首传失败，需要带日志的反馈（`feedback.retry_attachment` 行）再定位，本条修的是「在途被显示成失败」这一确定的缺口。
