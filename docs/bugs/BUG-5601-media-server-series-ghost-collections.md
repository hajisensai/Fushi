## BUG-5601 · media-server-series-ghost-collections
- **报告**：2026-11-28（用户：合集页冒出几千个没建过的合集，各端都有）
- **真实性**：✅ 真 bug。根因 `fushi/lib/src/pages/implementations/home_video_page.dart:2564`（`_listRemoteSource`）：视频库页每拿到一份 Jellyfin / Emby / 飞牛 / Plex 清单，就用 `RemoteCollectionAdoptionService.adoptVideos` 把整台服务器按剧名（`mediaServerCollectionOf`，`media_server_browser.dart:183`）收养成真合集。媒体服务器的剧名归属是客户端现算的派生分组，不是谁存下的数据，收养却把它写成 `media_collections` / `media_collection_items` 行，再经合集同步扩散到所有设备。用户库副本里有 3145 个这种合集、84,487 条成员行，都是 2026-10-30 一次列目录产生的。
- **[x] ① 已修复**（方案 B「懒收养」，PR1）：对派生剧归属的来源（`DerivedSeriesGroupingSource`：Jellyfin / Plex 客户端）不再收养，清单交给 `RemoteSeriesCatalog`；`loadVideoLibraryMembership` 在后台 isolate 里按收养的同一套规则（`buildRemoteSeriesOverlay`：合集级删除哨兵、成员墓碑、同自然键真合集、手排追加、已有主归属不动）叠加出负 id 的虚拟合集。读路径（`getMediaCollectionById` / `getCollectionItems`）经 `VirtualCollectionHooks` 认负 id；用户写入口（改名、删除、排序、标签、隐私 / NSFW / 上锁、字幕 / 音轨偏好、封面、增删成员）遇到负 id 先物化：整部剧的成员按收养规则一次事务落库并钉住（`materializeRemoteCollection`）。同步应用端的裸写入口拒收负 id。「加入媒体库」改成物化并钉住成员。存量清理（schema v183 `auto_pruned`、认领、清理）在 PR2。
- **[x] ② 已加自动化测试** — `fushi/test/media/video/remote_series_overlay_test.dart`：叠加与收养的对拍（同一份目录、同样前置状态，按自然键比较折叠归属与组内序），以及虚拟 id 分配、物化、钉住、负 id 的读写解析、并发单飞、非用户意图让路、裸写入口护栏。
- **[x] ① 已修复（PR2，存量清理）**：schema v183 给 `collection_member_tombstones` 加 `auto_pruned`，wire 上 `CollectionManifestEntry.autoPruned` 是可选字段（不升清单 version）。`FushiDatabase.healRemoteSeriesCollections`（`packages/fushi_core/lib/src/database/database_remote_series_prune.part.dart`）先认领、再清理：认领把媒体服务器剧名合集里在本机有视频行的成员置 `pinned_by_user`；清理用一条 SQL 选出「没人动过」的剧名合集（判据：`playlist` / `origin=user`、合集行上没有封面 / 偏好 / 分组键 / 手排，成员全是媒体服务器条目 id 形状（`isDerivedRemoteSeriesEntryKey`：不带 `/`、`:`）、没有钉住、本机没有视频行，标签 / 刮削 / 图片 / 作品资料 / 作品关系 / 用户确认的作品图谱连接 / 下载 / 私密 · NSFW · 上锁标记 / 该自然键的墓碑 / AI 整理记录都没有，自然键无重名），一个事务里集合式删除，写 `auto_pruned` 的合集级哨兵（不带分组键，效果同 `deleteMediaCollection(userIntent: false)`），幂等。挂在三个合集同步入口（读本地清单之前）和开库后台工作。同步引擎：双死按 `deletedAt` 取新、平手取或；`autoPruned` 删除输给成员带 pinned 的活合集（`_mergeOne` 与 `combinePeers` 都是）。叠加层：`auto_pruned` 哨兵不挡临时分组，用户删除照旧挡；被动物化遇到它清掉照样建。**依赖 PR1（#4590），必须在它之后合；发版前要提醒用户先把各端都升级**（旧版本设备上「加入媒体库」过、而新设备先清掉的剧，旧设备上会散成单集，再点一次「加入媒体库」可恢复）。
- **[x] ② 已加自动化测试（PR2）** — `fushi/test/database/remote_series_prune_test.dart`：v182→v183 迁移；成员键形状 Dart / SQL 对拍；§4.1 每个信号单独出现都保留（含 AI 连接不算、用户连接算、重名、空合集）；删除效果与 `deleteMediaCollection(userIntent: false)` 一致、哨兵 `auto_pruned=1` 不带分组键、连跑两次幂等；认领钉住且之后清理保留；清理前后临时分组的归属与组内序逐项相同（用户删除哨兵照旧挡）；被动物化清自动清理哨兵、用户删除哨兵让路。`fushi/test/sync/collection_sync_auto_pruned_test.dart`：`autoPruned` 往返与旧清单兼容、双死取新 / 平手取或、pinned 否决（两个方向、多份对端折叠）、用户删除不受影响、旧闻语义不变、落库镜像与补标记、本机删除发布盖戳不丢标记。用户库副本（v182，3184 个合集）的拷贝上真跑：迁移到 v183，删 3145 个（成员 84,487 行）、留 39 个（成员 557 行），事务约 1.1 秒；第二遍候选 0。
- **备注**：性能实测（合成数据，规模同用户库：84,487 集 / 3145 部剧 / 557 条已有主归属 / 39 个真合集）：叠加在主 isolate 上 AOT 约 80–95ms、JIT 约 155–190ms；`List<RemoteVideoInfo>` 直接发给后台 isolate 要 95–130ms，列式（三列字符串 + `Int32List`）打包约 12–20ms、发送约 4ms。所以叠加放进已有的归属加载后台 isolate，输入用列式。
