## BUG-4798 · 桌面三端与无头服务端读 CP932 / GBK / Big5 / EUC-JP 字幕整份变成 U+FFFD
- **报告**：2026-11-17（视频优化清单第 35 条，复核 video-35 / video-s2-8）
- **真实性**：✅ 真 bug。根因 `packages/fushi_audio/lib/src/parsers/text_file_io.dart:252-263`（修前）：`decodeTextBytes` 的第 2 级只有平台插件 `tryPlatformCharsetDecode`（`:236-242`），而 `flutter_charset_detector` 只有 android / ios 实现——桌面三端在 `fushi/lib/src/media/audiobook/platform_charset_detector.dart:19-21` 吃掉 `MissingPluginException` 返回 null，无头服务端根本不装配——于是直接落到第 3 级 `utf8.decode(allowMalformed: true)`。本地多字节编码的正文按宽松 UTF-8 解，非 ASCII 部分几乎全是 U+FFFD（旧注释写的「少数字符」偏轻），字幕 / 弹幕 / m3u8 / 纯文本书不可读；Jimaku 远端字幕（`fushi/lib/src/sync/remote_subtitle_search_handlers.dart:171`）走同一条路。BUG-1490 当时只修了 Unicode 家族与「不再整体失败」。仓库里其实已有 Rust 的本地编码探测（`native/fushi_compute/src/legacy_text.rs`，曲库 ID3 与漫画 zip 条目名在用），`fushi_audio` 也已依赖 `fushi_compute`，只是没接到这条路上；它的判据为短字符串而调（候选必须零错误、零表外字符），整份文件直接拿来用会因一个坏字节或一个没列进表的符号判不出来。
- **[x] ① 已修复** — 提交 `0f36638d8dd`。Rust 侧新增整份文档入口 `decode_document`（`legacy_text.rs`）+ C ABI `ffc_text_legacy_decode_document`（`text.rs`）+ 绑定 `LegacyTextDecoder.decodeDocument`：候选与计分不变，容错口径按整份文件放宽（每 100 个非 ASCII 字符容一个坏字符，坏处解成 U+FFFD）；先挡掉「基本是 UTF-8、只坏了几处」的输入（否则 GBK 会把它零错误解成乱码）；分值不足 8 的不猜。间隔号 U+00B7 计入 CJK 标点（实测 GBK 样本里唯一成规模的表外字符，ID3 / zip 条目名同样受益）。`decodeTextBytes` 改为四级：Unicode 家族 → 平台插件（只在移动端有实现，覆盖韩文 / Windows-125x 等更多编码，保留并先判）→ `decodeLegacyText`（Rust）→ 宽松 UTF-8；超过 8 KB 的输入放后台 isolate（实测约 55～95 ms / MB）。口径依据：40 份日文、60 份中文真实字幕的文本转成 CP932 / EUC-JP / GBK / Big5 共 155 份（已剔掉几乎不含非 ASCII 字符的），154 份判对，其中 17 份按原来的零容错会被淘汰，判错的一份正文是保加利亚文（见备注「已知判不对的输入」）；140 份人为弄坏的 UTF-8 全部不被重解。独立审查后补三处（同一 PR 的后续提交）：(a) 放宽后的判据会把 Windows-1252 英文 / 德文字幕整份解成 Shift_JIS / GBK（`don’t` 的 0x92 与后一个字母恰好是一个合法双字节字；`latin1_plausible` 是短标签判据，一处 `…”` 就整份判否）——修前这类字幕可读（撇号处一个 U+FFFD），解成汉字后还会让 BUG-3069 的字幕语言守卫把英文字幕当中文。`DocumentAssessment` 加结构证据 `shaped_like_cjk`：解出的非 ASCII 字符多数「前后都是 ASCII 且贴着 ASCII 字母」、或半数以上是半角片假名（Windows-1256 阿拉伯文 / TIS-620 泰文落在 Shift_JIS 单字节区）就淘汰该候选；卡拉 OK / 逐字歌词里被 `{\k20}`、`<00:12.34>` 隔开的字两侧不是字母，不受影响。真实样本 155 份 + 损坏样本 278 份复测结果与加这条前逐份一致。(b) `decode_document` 入口先剥开头的 UTF-8 BOM（「UTF-8 BOM + 本地编码正文」的坏文件从前首行多出 `\uFFFD` 与半角 `ｿ`，短文件直接判不出）。(c) `ffc_text_legacy_decode_document` 的绑定不再是 leaf 调用：leaf 期间线程到不了 safepoint，后台 isolate 里解大文件时 UI isolate 触发的 GC 要等它返回。
- **[x] ② 已加自动化测试** — Rust：`native/fushi_compute/src/legacy_text.rs` 的 `document_*` / `short_input_keeps_the_zero_error_rule` / `damaged_utf8_document_is_not_reinterpreted` / `ascii_and_latin1_documents_are_left_alone` / `gbk_tag_with_middle_dot_is_recovered`，`western_single_byte_documents_are_not_decoded_as_cjk`（英文弯撇号 + `“Wait…”` / `—“`、瑞士德语 + `„Ü`、阿拉伯文、泰文；每条先断言「不看结构证据时确有候选会接受」）/ `halfwidth_kana_majority_is_rejected_but_minority_is_kept` / `cjk_isolated_between_markup_is_still_decoded` / `utf8_bom_before_legacy_body_is_stripped`，`text.rs` 的 `legacy_decode_document_through_c_abi`。绑定：`packages/fushi_compute/test/text_legacy_decode_test.dart`。纯 Dart（与无头服务端同构，不装平台插件）：`packages/fushi_audio/test/parsers/text_file_io_legacy_decode_test.dart`，夹具 `packages/fushi_audio/test/fixtures/legacy_text/`（CP932 ASS、EUC-JP / GBK / Big5 SRT，Python codec 编码，与被测的 encoding_rs 是两套独立实现），覆盖四种编码整份解回原文、后台 isolate 与就地两条路、坏字节容错、坏 UTF-8 不被重解、Windows-1252 英文字幕不被解成汉字、UTF-8 BOM + 本地编码正文、解析出 cue。Flutter 宿主（与 app 桌面端装配同构：装了插件但无平台实现）：`fushi/test/media/audiobook/text_file_io_encoding_test.dart`「readTextWithEncoding（本地多字节编码，桌面端装配）」（含「Windows-1252 的英文字幕不被解成汉字，正文语言仍判英文」：`decodeTextBytes` 后 `detectSubtitleContentLanguage` 仍为 english）；Jimaku 取回路径：`fushi/test/sync/remote_subtitle_search_handlers_test.dart`「非 UTF-8 档（Shift-JIS）解回日文正文并解析出时间轴」（原先只断言正文非空，现断言等于 `こんにちは`）。
- **备注**：
  - 待真机复测：Windows / macOS / Linux 各用播放器打开一份真实 CP932 外挂字幕；无头服务端（`fushi_server`）托管同一份字幕由客户端拉取；Jimaku 取一条 Shift-JIS 档。动了 Rust，五端原生库都要重编（CI 出包 job 自带）。
  - 已知判不对的输入：EUC-KR 韩文等其它**双字节**编码，字节按 GBK / Big5 读零错误、解出的字也成串，桌面端 / 服务端会被解成汉字乱码（修前是 U+FFFD，同样不可读）；移动端因平台插件先判不受影响。单字节西文编码（Windows-1250～1256、KOI8-R、TIS-620）不动（仍是修前的宽松 UTF-8）：多数因词尾的高位字节 + 空格在候选里是解码错误而被容错口径挡掉，剩下的靠结构证据挡。全汉字、无假名的 EUC-JP 与 GB2312 字节同形，按顺序取 GBK（既有判据的固有残余）。
  - 实测样本的出处是两个公开字幕仓库，它们都已把文件统一成 UTF-8，拿不到「原生」的本地编码文件；样本是真实字幕文本经 Python codec 转码得到的，文件级的怪癖（混合编码、编辑器写坏的片段）只用人为截断 / 插坏字节模拟过。样本不入库（第三方内容），入库夹具是自己写的句子。
