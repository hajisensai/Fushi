## BUG-1768 · 发现页搜索后点文件夹无限自嵌套（query 压过 path）
- **报告**：2026-08-22（用户：游戏→发现页选 erogame.space 搜「WHITE ALBUM2」，结果里那个同名**文件夹**点进去还是它自己，可以无限点下去，面包屑累积成 `WHITE ALBUM2 / WHITE ALBUM2 / WHITE ALBUM2 / WHITE ALBUM2`）
- **真实性**：✅ 真 bug，已在真机原始路径复现并修复后复验。根因是发现页把「有没有在搜索」直接读**搜索框的实时文本**，而 `_openFolder` 只往路径栈压一层、不动搜索框：`fushi/lib/src/pages/implementations/media_discovery_page.dart:138-139`（`browsing = _queryCtrl.text.trim().isEmpty`）+ `:151-156`（`path: browsing && ... ? ... : null`，**`browsing` 门在 `path` 前面**）→ 关键词非空时 `path` 永远送不出去。请求于是与上一次逐字节相同，`MediaDiscoveryService._invoke`（`media_discovery_service.dart:183-185`）按 `DiscoveryRequest.isSearch` 分发回 `search()`，而 `AListDiscoverySource.search()`（`sources/alist_discovery_source.dart:97-105`）恒发 `parent:'/'` + `scope:0` 全站递归搜索——命中集天然包含与关键词同名的那个目录本身，于是列表首项还是它自己。folder 的 `path` 拼接（`:160-161`）本身是对的，不是自引用，也不是漏过滤 `..`。
- **[x] ① 已修复** — 把「搜索态」与「目录栈」的优先级倒过来，并改成**已提交状态**：新增 `_query`（提交过的关键词，`_queryCtrl` 只作草稿），`_submitSearch` 提交时才写 `_query` 并清栈；`_load()` 改成先取 `path`、再由 `path == null` 决定要不要带 `query`（`media_discovery_page.dart` 的 `_load`），两者在出口处就地互斥。下钻比产生它的那次搜索更具体，`path` 非空必须赢。`_idleMode` 也改看 `_pathStack`/`_query` 而不是实时文本。另在 `DiscoveryRequest` 构造点加了 `query`/`path` 互斥断言（`discovery_models.dart`），让「两个都给、`path` 被静默丢弃」这种写法在构造时就炸；断言写成 `a == null || b == null` 而非 `query.trim().isEmpty`，因为本类有 const 构造点、const 断言只接受潜在常量表达式。**行为收益**：搜索框保留关键词、面包屑只记目录层级、「返回」弹回那次搜索的结果而不是退到源根目录。
- **[x] ② 已加自动化测试** — `fushi/test/pages/media_discovery_page_test.dart` 新增「搜到同名目录后点进去：走 browse 且带路径，不再自嵌套」。用 `_RecursiveSearchSource` 建模 AList 那类**全站递归搜索**的源（`search` 无论 path 给什么都把同名目录再吐一遍），所以「没有自嵌套」唯一可能的原因就是这次真的走了 browse；断言落在源上的调用种类、`request.path` 与列表内容上，并覆盖「返回回到搜索结果」。**变异实测**：把 `_load()` 的优先级改回旧的「query 压过 path」后该测试立刻红（其余 4 条仍绿），还原后复绿。顺带给面包屑返回按钮加了稳定 key `discovery_breadcrumb_up`（`FushiIconButton` 的 tooltip 不产生可 `byTooltip` 命中的 widget）。
- **备注**：真机验证 2026-08-22，Windows debug 构建 + 三处隔离实例（`Runner.rc` CompanyName/ProductName 改 `FushiDiscProbe`、单实例互斥体改名、`FUSHI_WEBVIEW2_USER_DATA_FOLDER` 指向临时目录），数据落全新的 `%APPDATA%\FushiDiscProbe\`，全程没碰生产库。走完用户的原始路径（游戏→发现→选 erogame.space→搜 WHITE ALBUM2→点同名文件夹）：面包屑只剩一层 `WHITE ALBUM2`，列表里不再有它自己，自嵌套消失。**但点进去显示「无结果」**——那是同一条路径上的另一个问题，见 [BUG-1770](BUG-1770-discovery-total-failure-shown-as-empty.md)：整源失败被 UI 显示成了「无结果」。（**此处原先写的「该站 `/api/fs/list` 对匿名访问在任何路径含 `/` 都返回 `object not found`、只有 `fs/search` 可用」是误判**，已被 [BUG-1771](BUG-1771-alist-search-parent-base-path.md) 的实测推翻：`fs/list "/"` 与剥掉前缀的路径都是 200，list 接口一直正常，真正的原因是把 search 返回的带 `base_path` 前缀的路径原样喂了进去。）两处是独立缺陷，本条只负责「不再自嵌套」。
