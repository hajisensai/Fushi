## BUG-3328 · 阅读器删除收藏 / 标注高亮后查词选区丢失
- **报告**：2026-10-13（用户：遗留 bug「阅读器删除高亮后丢失查词选区」；BUG-3326 第二轮返工记下的「已知未覆盖：unwrap 时 `normalize()` 合并文本节点（VN 路径不清选区）、无 CSS Highlight 旧引擎的 `extractContents` 回退分支」）
- **真实性**：✅ 真 bug，限**无 CSS Custom Highlight API 的引擎**（iOS 15.1–17.1 / macOS 13.4 上 Safari 17.2 之前的 WKWebView，以及更老的 WebView；部署下限 iOS 15.1、macOS 13.4，这条回退分支在生产里是活的）。真 Chrome 跑生产脚本复现：查词后删收藏（`_refreshSectionHighlights` → `__fushiApplyHighlights` 回退分支），查词选区 `fushiSelection.selection` 的 `startNode` / `matchedRanges[].node` 全部 `isConnected === false`。
  - 根因：查词选区与拖选锚点存的是「文本节点 + 偏移」普通对象，不是 live Range。回退分支拆收藏 `<span>` 后 `normalize()` 合并文本节点（`fushi/lib/src/media/audiobook/highlight_bridge.dart:344-350`，整个 body `root.normalize()`；单条删除 `:417-423`），被并掉的节点移出文档，选区指向的节点随之失效——拖动柄、查词高亮重画（`highlightSelection` 读 `node.textContent`）、制卡句子上下文都坏。收藏重新包裹用 `surroundContents`（`:383`）、查词高亮包裹用 `extractContents`（`fushi/lib/src/reader/reader_selection_scripts.dart:2451`）：两者都把选中的字复制进新节点、原节点截掉这段，选区偏移从此指向别的字（回退分支下查词刚高亮完 `matchedRanges` 就读出空串）。
  - 同一机制的另一处：VN 播放中懒包裹的句子 wrapper 在 cue 重新下发（`applySentenceAudioCues` → `clearSentenceAudioTargets` → `unwrap`）时同样裸 `normalize()`（`fushi/lib/src/reader/reader_visual_novel_scripts.dart:3162`），且不清查词选区——**CSS Highlight 引擎上也会丢选区**（变异实测：只回退 VN 这处，`vn / CSS highlights` 场景即红）。分页 / 连续的 `unwrap`（`reader_pagination_scripts.dart:2015`）只由 `resetSentenceAudioCues` 调，它先 `clearSelection()`，没有活的选区可丢，一并改走同一入口保持一致。
  - CSS Highlight 引擎上删收藏只改 `CSS.highlights`、不动 DOM（WebKit 的 `__fushiEnsureHighlightPaintable` 搬节点经 `moveNodes`、节点身份不变），实测选区完好，不受影响。
- **[x] ① 已修复** — `d0627094d8`（+ 测试场景加强的后续提交，见 PR）：BUG-3326 的共享保护 `window.__fushiLiveRanges` 补齐「合并」与「拆 / 包裹」三个入口，所有阅读器 DOM 手术只经它：
  - `normalize(node)`：合并前由选区拥有者 `fushiSelection.trackTextPoints()` 用折叠的 live Range 跟踪选区（`startNode`、`ranges`、`matchedRanges`）与拖选锚点的每个点；DOM 规范在 `normalize()` 里对 live Range 做的换算（并进前一节点、偏移加前面长度）正是这些点该有的换算，合并完就地写回。
  - `unwrap(wrapper)`：子节点经 `moveNodes` 原样搬回原位（live Range / 原生选区端点不塌缩），不合并；`wrapText(node, start, end, wrapper)`：首尾 `splitText`（经选区的 `noteTextNodeSplit` 换算）后把中间节点原样搬进 wrapper，节点身份不变。
  - 接线：高亮桥回退分支的包裹 / 全量拆 / 单条拆（`_unwrapFallbackHighlights`，只 normalize 被拆 span 的父节点，不再整个 body）；选区回退分支的 `highlightSelection` 包裹与 `clearHighlightWrappers`；VN 与分页 / 连续句子音频的 `unwrap`。
- **[x] ② 已加自动化测试** — `fushi/test/reader/favorite_removal_lookup_selection_test.dart` + `favorite_removal_lookup_selection_harness.mjs`：真 Chrome 跑生产脚本，**分页 / 连续 / VN 三种 shell × CSS Highlight / span 回退两种引擎**共 6 个场景：查词选 4 字（猫がいる）、弹窗高亮匹配的 2 字，收藏从选区内部开始（选区最后一段落在收藏的第一个文本节点里，拆收藏后它紧跟未匹配的「い」，正是被 `normalize()` 并掉的那个节点）→ 删一条留一条 / 删最后一条 / 加回后按 id 删 → 查词放宽重画，每步断言选区节点（`startNode` / `ranges` / `matchedRanges`）仍在文档、起点仍是查的字、`matchedRanges` 与整段 `ranges` 读出原文、查词高亮仍画着，另断言收藏确实画上 / 删掉（防空壳）；VN 额外覆盖「播放句懒包裹后 cue 重下发」。同文件第二例是源码守卫：五份脚本代码里没有裸 `.normalize()`（只有 `__fushiLiveRanges.normalize` 一处）、没有 `surroundContents(` / `extractContents(`。
- **备注**：
  - 三种 view mode：harness 对分页、连续、VN 各跑一遍（VN 用完整 factory，选区在渲染出的屏上）；三种模式都过。WebKit 真机（iOS 17.2 之前）没跑：回退分支的判据只是 `__fushiCssHighlightsSupported`，harness 把它置 false 在 Chrome 里走的就是同一份代码与同一套 DOM 规范语义（`normalize` / live Range 换算 Chrome 与 WebKit 一致）。
  - 变异实测（每次只回退一处，跑本测试，四次全红，还原后绿）：① 高亮桥整份回退 → `paginated / span fallback: favourite deleted, another one remains` 红 + 源码守卫红；② 只把桥的 `guard.normalize(parent)` 换回裸 `parent.normalize()` → 同一步红；③ 只让 `__fushiLiveRanges.normalize` 不调 `trackTextPoints` → 同一步红；④ 只回退 VN `unwrap` → `vn / CSS highlights: VN sentence audio re-wrapped` 红。
  - 同步改了两个假 DOM 的 node 测试（`reader_selection_drag_hit_behavior_test.js` / `reader_selection_viewport_behavior_test.js`）：它们只抽 `fushiSelection` 的方法、不装选区脚本顶层的 `__fushiLiveRanges`，现在给沙箱补一个按旧 DOM 步骤（搬子节点、删 wrapper、`normalize()`）实现的 `unwrap` / `normalize`；真实的换算逻辑由本条的真 Chrome 测试覆盖。
