## BUG-3855 · Windows 加密原盘菜单又打不开（fushi_aacs 文件回调把 seek 返回值当文件大小）
- **报告**：2026-10-28（用户：截图「视频加载失败 / 无法打开这张原盘的菜单，仍可直接播放其中的标题。」，`Cosmic Princess Kaguya` 加密原盘；错误日志 `Blu-ray menu: navigation-open-failed: [bd] AACS error: opening or reading of AACS files failed`，3.0.1-debug.21804）
- **真实性**：✅ 真 bug，BUG-3074 的回归。用户装的 `libaacs.dll` + 随包 `libmpv-2.dll`、按缓存 KEYDB 注册 VUK 打开 `Disc 2` 原样复现同一句 `[bd:error]`。根因 `native/fushi_aacs/src/fushi_aacs.c` `read_disc_file_cb`：把 `file->seek(file, 0, SEEK_END)` 的返回值当文件大小。libbluray 1.5.0 的 `file_posix.c` 返回 lseek 的新偏移，`file_win32.c` 返回 `fseeko64` 的「成功 = 0」，libbluray 自己的 `file_size()` 只看 seek 的正负、大小取 `tell`。Windows 上大小恒为 0 → 读不到 `AACS/Unit_Key_RO.inf` → `aacs_open_device` 返回 `AACS_ERROR_CORRUPTED_DISC`。BUG-3074 验收时模块只导出 `aacs_open2`、libbluray 走直接 fopen 路径；`1536a8afccc`（2026-10-24，远程原盘）加了 `aacs_init` / `aacs_set_fopen` / `aacs_open_device` 导出，libbluray 1.5.0 一见这组导出就改走文件回调，Windows 本地原盘从此全挂（Android / macOS 是 POSIX 语义，不受影响）。单测的内存盘 mock 只模拟了 POSIX 语义且没有 `tell`，所以没抓到。
- **[x] ① 已修复** — 新增 `file_cb_size`，照 libbluray `file_size()` 的做法：seek 只判正负，大小取 `tell`，读完回到开头。
- **[x] ② 已加自动化测试** — `native/fushi_aacs/test/fushi_aacs_test.c`：mock 补 `tell`，文件回调契约按 POSIX（返回偏移）与 Win32（返回 0）两种 seek 语义各跑一遍。旧实现在 Win32 一轮挂 7 条检查，新实现全过（ctest）。
- **验证（2026-10-28）**：同一个探针（先加载待测 `libaacs.dll` 并 `fushi_aacs_set_disc_key`，再用 `D:\APP\Hibiki\libmpv-2.dll` 以 `bluray-device` + `bd://menu` 打开）：用户安装的 DLL → `AACS error: opening or reading of AACS files failed`；修复后的 DLL → `Disc 1` / `Disc 2` 均 `Blu-ray successfully opened`，`disc-navigation-state-json` 为 `nav-active:true`，first-play 正常推进。真实 app 内复测待新包。
- **备注**：页面文案「仍可直接播放其中的标题」在这条失败路径上没有对应入口（只有重试 / 返回），另行处理。
