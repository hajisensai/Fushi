## BUG-2086 · native loopback allow 的确认超时中止注入，导致 LunaHook 文本 hook 永不安装
- **报告**：2026-09-03（代理为 WoH/HUNEX 做游戏内查词适配时，在真机上连续复现「音频全好、文本零行」；BUG-2084 第二轮的第一个未通过边界）
- **真实性**：✅ 真 bug，根因已沿真实代码路径定位到行。真机形态：Fushi 拉起 WoH.exe（x64，SHA-256 `4475cc2f…5463ada`）后，会话报 `engine.attach_recovered` + `engine.hook_ready`，`audio.game_resource_late_ready`、`tracks_refreshed count:26`、`xaudioDiagnostics 0x78080001` 全部正常，但 `TexthookerService.entries` **恒为 0**、`phase` 永远停在 `waitingSignals`；用驱动真实推进剧情 18 句以上、逐帧截图确认剧情在走，仍零行。三次 launch（PID 44220 / 49088 / 38468）稳定复现；helper 三份构建（主 checkout / gal-generic 工作树 / 本工作树）的 `fushi_voice_hook.dll` / `fushi_voice_injector.exe` / `LunaHook64.dll` SHA-256 与 `installed.sha256` 逐一相同，已排除版本错配。
- **根因（三段，全部有行号）**：
  1. **hook 侧确认发布得太晚。** `native/galgame_hook/hook/dll_main.cpp:653` 的 `InstallFallbackAdapters()` 只把 loopback worker 起出来并发布 `starting`（`hook/adapter_registry.inc:411-437` 的 `kStartWorker` 只写 state、不写 `applied_seq`）。`allow` 的 `applied/running` 确认必须等 worker 真正 `IAudioClient::Start()` 成功（`hook/adapters/loopback_adapter.inc:228-233` 才置 `kLbWorkerRunning`），而它只能由**下一轮** `PollPolicy()` 发布（`adapter_registry.inc:554`）——那一轮被 `dll_main.cpp:662-667` 的 `MH_Initialize()` + `InstallStartupAdapters()` 重量级引擎探测挡在后面。`dll_main.cpp:649-652` 那句「Apply/ack native loopback policy before potentially expensive engine probing」的承诺**此前只对 deny 成立**（deny 无 worker 时当场 `kAcknowledgeStopped`，`include/voice_hook_ipc.h:1746-1753`）。
  2. **早注入给这个确认的预算只有 5 秒。** `injector/injector_main.cpp:1798-1801`：`created_suspended` 时预算取 `SuspendedStartupWaitBudgetMs(wait_ms)`，即 `min(wait/4, 5000)`（`include/launch_failure_policy.h:95-103`），而 attach 路径拿全额 30000ms。这正是「launch 必挂、attach 能恢复」的直接解释——同一个竞态，attach 有 6 倍预算。
  3. **超时的处置把一项能力放大成整条链失败。** `injector_main.cpp:1870-1886` 在 ack 超时后直接 `return FailWith(..., kReadyTimeout, 2)`，而**这个返回点位于 `InitLunaHook` 的所有调用点之前**（`:1900` 的 guarded 路径、`:2043` 的常规路径）。音频 hook 由**游戏进程内**的 `HookWorker` 自装（`adapter_registry.inc:517-546`，HUNEX 在 `:530`），注入器进程死活与它无关，所以音频全活；而 LunaHook 文本 hook 由**注入器进程**负责加载 `LunaHost64.dll` + `bridge.connect(pid)` + `InjectDll`（`injector_main.cpp:1122-1208`），提前 return 即**一次都没装**。`header->text_hooked` 只在注入器的 `LunaConnect` 回调里置位（`:980-987`），host 侧 `parseEngineTextHookReady` 读的就是它（`fushi/lib/src/mining/galgame_audio_source.dart:178-179`），于是恒 0 → 宿主零行。
  - **附带的两处谎报**：① `injector_main.cpp:2990-2992` 打的 `[launch] hook failed; game resumed without hooks so it still starts` 与事实矛盾——DLL 在进程里且音频 hook 已就绪。② 日志里的 `exit=0xCC150000` 是 `GetExitCodeThread` 取到的**被截断的 64 位 HMODULE 低 32 位**（模块基址 64KB 对齐，低 16 位必为 0），`injector_main.cpp:196-213` 早已注释说明它不参与任何判定、`ok=true` 与它无关；本轮排障一度被它误导。
- **[x] ① 已修复** — 三处，按语义分开处置：
  - **注入器不再因 allow 的确认超时中止**（`injector/injector_main.cpp` ack gate）：新增纯判据 `NativeLoopbackAckTimeoutAbortsInjection(bool requested_allow)`（`include/launch_failure_policy.h`）。**deny 保持致命**——那是隐私边界，拿不到 stopped 的确认就不能证明没有 worker 在录；**allow 降级为能力位**，置 `kLoopbackDiagPolicyAckTimeout`（`include/voice_hook_ipc.h`，`loopback_diag` 的 `0x200`）后继续往下走，文本 hook 照常安装，worker 稍后仍会自行 ack 成 running。
  - **hook 侧把确认追平到引擎探测之前**：`hook/adapter_registry.inc` 新增只推进策略状态机、不碰引擎适配器的 `PollLoopbackPolicyOnly()`；`hook/dll_main.cpp` 在 `InstallFallbackAdapters()` 之后、`MH_Initialize()` 之前加一个**上界 1500ms** 的追平循环，用新增的 `NativeLoopbackRequestAcknowledged(header)`（`include/voice_hook_ipc.h`）判停。追不平也照常继续，绝不无界等待。这兑现了 `dll_main.cpp` 那句既有注释对 allow 的承诺。
  - **失败原因分型 + 文案纠正**：新增 `LaunchFailureReason::kNativeLoopbackAckTimeout` / token `nativeLoopbackAckTimeout`，与 `kReadyTimeout` 分开（后者是「DLL 根本没跑到通知点」，处置完全不同）；Dart 侧同 PR 补 `GalHookInjectorFailure.nativeLoopbackAckTimeout`（token 按枚举名自动解析）、判为可重试、并接 i18n `game_hook_reason_native_loopback_ack_timeout`。`[launch] hook failed ... without hooks` 改为如实说明「注入编排中止，已在进程内装好的 hook 继续有效，注入器尚未安装的部分缺失」并带上 reason token。
- **[x] ② 已加自动化测试** — `native/galgame_hook/tests/launch_failure_policy_test.cpp` 新增：deny 超时必须中止、allow 超时**必须不**中止（核心不对称），以及 `nativeLoopbackAckTimeout` 必须是与 `readyTimeout` 不同的独立 token。x64/x86 双架构 `ctest` 各 56/56 通过；`adapter_structure_test.py` / `engine_support_manifest_test.py` / `assert_liveness_guard_test.py` / `galhook_workflow_test.py` / `evidence_contract_test.py` 与两个生成器 `--check` 全绿。
- **同批收口的宿主侧谎报**：`fushi/lib/src/mining/gal_hook_session_controller.dart` 的 `_activateEngine` 此前**只由音频侧决定**是否发 `engine.hook_ready`（调用方判据是 `format != null`，`:1360` / `:1690` / `:4398`），于是「音频好、文本 hook 缺席」的会话照样打出 success 级「Engine hook and IPC are ready」——同一个函数体一边把 phase 写成 `waitingSignals`、一边宣布 ready，正是 SOP 禁止的「用前一阶段推断后一阶段」。现按 `engine.textHookReady` 拆成互斥两条：就绪仍发 `engine.hook_ready`(success)，缺席改发 `engine.audio_hook_ready_text_missing`(warning) 并写明「no lines will arrive until it is」；两支都带 `details['textHookReady']`。`engine.attach_recovered` 同样注明恢复的是不是文本侧（上游门是「或」，可能只恢复了音频）。**控制流一字未动**——文本或 PCM 晚到是常态，仍由 `_refreshReadinessThrottled` 负责升格。守卫见 `fushi/test/mining/gal_hook_session_controller_test.dart` 的两条 BUG-2086 用例（缺席不得宣称 ready + 就绪不得过度收紧），变异实测：把 code 改回无条件 `engine.hook_ready` → 缺席那条当场红。
- **[x] ③ 真机已复验（2026-09-03 14:46，原始路径 `launch WoH.exe`）** — 用本轮重建的 helper（`voice_hook_x64.zip` sha256 `619331748f665ceb…008a479c`，装进宿主旁的 `fushi_voice_hook.dll` 摘要由修复前的 `B2BBC0D0…` 变为 `6EFDFD08…`，逐哈希确认进程加载的是新件）重跑：
  - **修复前**：`fallback=launch_injection_failed` → `engine.attach_recovered` + `engine.hook_ready` → `lines=0`、`phase` 恒 `waitingSignals`，推进剧情 18 句以上仍零行（三次 launch 稳定复现）。
  - **修复后**：`fallback=engine_pcm_unavailable`（不再是注入失败）→ `audio.engine_pcm_late_ready` → `audio.game_resource_late_ready` → **`text.thread_selected {threadKey: luna:21ff6f25f172b870}`**，**`phase=running`、`lines=4`**，捕获文本与屏幕逐字一致（`青子はやれやれと肩をすくめて、古びた鉄柵に手をかける。` / `「あれ、鍵閉まったまま？` / `……有珠、まだ帰ってきてないんだ」` / `重苦しい鉄の門は静かに、この年若い少女を歓迎するように開いていった。`）。

- **备注**：`engine-support.yaml` 的 `hunex_gge` 不因本条提升，仍 `implemented_unverified`。另外记录一条**本轮未修的相邻死路**：`injector_main.cpp:1189-1206` 的 `bridge.need_inject(pid)` 为 false 时只打一行 info——若某个 injector 曾把 `LunaHook64.dll` 注入该 PID 后自己退出（管道断），后续 injector 会因模块常驻而跳过注入，而对已加载模块再 `LoadLibraryW` 不会重跑 DllMain、LunaHook 不会重连管道，该游戏进程**整局文本永久缺席**。这与本轮「手动 attach 出现 text_hook_ready 但宿主仍零行」的现象吻合，应另开一条收口为可诊断失败。
