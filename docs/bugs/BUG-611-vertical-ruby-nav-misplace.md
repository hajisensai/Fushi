## BUG-611 · 竖排滚动导航后假名跑文字中间
- **报告**：2026-07-08（用户：竖排(vertical-rl)+滚动(连续)模式，经目录/书签/搜索跳转后，振假名(ruby `<rt>`)本应在基字侧边，却塌进基字/正文中间；跳转前正常）。TODO-1308。
- **真实性**：✅ **真 bug（沿真实渲染路径 + WebView 引擎特性定位）**。根因：`hibiki/lib/src/reader/reader_content_styles.dart:382`（原）`html { -webkit-line-box-contain: block glyphs replaced; }`。这条 legacy WebKit 属性是 `feat(reader): port CSS generation from Hoshi`（`ec4abf78a`）整体搬来的，注释自陈意图「constrain line-box height so ruby/furigana won't expand it」——即命令引擎把 line-box 尺寸只按 **glyph** 算、**不为 `<ruby>` 的 `<rt>` 标注预留 leading**。现代 Blink（WebView2 v150 / 新版 Android WebView）已**完全丢弃**该属性（headless 实测 `CSS.supports('-webkit-line-box-contain','block glyphs replaced')===false`、`getComputedStyle` 为空，属性根本不被解析），故对多数用户是死代码、渲染正常（headless Chrome/Edge v150 竖排 ruby 无论滚动前后都在基字右侧、正确）。但仍解析该属性的**旧版 Android System WebView** 会据此抹掉振假名在**交叉轴（竖排=列宽方向）** 的预留空间：竖排 vertical-rl 里 `<rt>` 标注排在基字列右侧，预留被抹后无处安放 → 塌进基字列 =「假名跑到文字中间」。同类机制已在词典弹窗证实过（BUG-108：Blink 在固定 line-height 下不为 ruby 加 leading → `<rt>` 压到上一行漢字）。「导航后」才显形：`hibiki/lib/src/pages/implementations/reader_hibiki/navigation.part.dart:124` 的 `_applyChapterHighlights()` 在**每次**跳转/恢复完成（`_onRestoreComplete`）后都跑（即使零收藏，也会 `_syncHighlightVars()` 改自定义属性 + `_clearCssRubyHighlights()` + `CSS.highlights.set/delete`），强制一次样式重算/增量重排，把 glyph-only 的 line-box 约束重贴到刚滚动过的内容上 → 初次全量布局尚有预留、导航后增量重排把预留抹掉。
- **[x] ① 已修复** — 删除 `reader_content_styles.dart:382` 的 `-webkit-line-box-contain: block glyphs replaced;` 声明（原位换成记录决策的注释，防止再被搬回）。修复=让所有引擎回到会为 ruby 预留空间的**默认 line-box 行为**——正是现代 Blink 早已正确渲染的行为，故对现代引擎零回归（属性本就 no-op），对仍解析它的旧引擎则恢复竖排/横排振假名的标注预留。不动横排 ruby（默认预留本就正确）、不动分页几何（现代 Blink 上该属性无效、分页照常工作，删除后旧引擎与现代对齐）、不动 TODO-1229 章首插图 charOffset 重锚（无关的滚动锚代码）。提交 `cb4418aad6`。
- **[x] ② 已加自动化测试** — `hibiki/test/reader/vertical_ruby_line_box_contain_guard_test.dart`（CSS 生成器守卫：剥掉 CSS 注释后断言四组合 竖排/横排 × 连续/分页 生成的正文 CSS 都不再发出活的 `-webkit-line-box-contain` 声明；撤回即红）。真机竖排 ruby 渲染 headless 不可跑（现代 Blink 该属性已 no-op，无法在 headless 复现旧引擎的抹除行为），故守卫锁在 CSS 生成层。

- **⚠️ 订正（2026-07-09 · TODO-1308 重查 · 本机 Windows WebView2 真机复现）**：上一条 2026-07-08 的「Windows WebView2 不复现」结论**错了**——它用合成 ruby 测漏了真书的关键差异。用户发来他自己 Windows 电脑的截图：竖排 貫(かん)禄(ろく) 的振假名 かん 挤到两汉字之间、ろく 浮到基字右侧下方。**第二根因（真正让 Windows 复现的那个）**：真书 EPUB 自带的 legacy 振假名 CSS——`rt { display: inline-block }` / `ruby { display: inline-block }`（旧 WebKit ruby 模型的遗留写法，很多竖排轻小说这么写）——在现代 Blink（WebView2 Chromium 149）下**破坏 `<ruby>` 格式化上下文**，把 `<rt>` 从注音盒里挤出去当内联内容排，竖排 vertical-rl 下沿列**向下塌约一整字**（真机 `getBoundingClientRect` 实测 `dyRatio≈0.95` vs 正确 0）。reader 只强制了 `writing-mode`、却没强制 ruby 结构，任由书本 CSS 破坏——这是 CSS 边界契约漏洞（reader 拥有写向就该拥有 ruby 布局）。`reader_content_styles.dart` 从没设过 `ruby-position`/`display`，全靠引擎默认；`ReaderResourceSanitizer.sanitizeCss` 只改 `-epub-*` 属性，书本裸 `display` 覆盖原样透传。**真机复现证据**：`reader_vertical_ruby_probe_itest.dart` 注入真实 reader CSS 到真 WebView2，量测 8 组书本 CSS 覆盖——`rt{display:inline-block}`/`ruby{display:inline-block}`/`rt{display:inline}`/`ruby,rt{display:inline-block}` 四种 `dyRatio` 全 =0.95（复现）；干净 markup（无书本覆盖）= 0（不复现，故前次测漏）。
