## BUG-4934 · 浏览器扩展在 X 等 CSP 严格的网站第一层查词没有单词发音
- **报告**：2026-11-17（应用内反馈 8KlXeA-A0f；重复反馈 x89TzA4Tqk：X 上第一层查词无发音、连兜底都没有，第二层正常；YouTube、note.com 正常）
- **真实性**：✅ 真 bug。
  - 根因：第一层弹窗跑在 content script realm（manifest `content_scripts` 装 `bridge-shim.js` + `vendor/popup.js`），播放走 `tools/browser-extension/vendor/popup.js:4848` 的 `new Audio(audioUrl)`；这个 `<audio>` 属于**页面文档**，加载受页面 CSP 的 `media-src` 约束。实测 x.com 的 CSP 为 `media-src 'self' https://*.twimg.com … blob: data: …`，不含 sync server 的 `http://127.0.0.1:…/api/lookup/audio/file`（`bridge-shim.js` `resolveWordAudio` 拿到的 URL），于是被拦、`play()` 失败。嵌套第二层是扩展自己的 iframe（`nested-popup.html`，扩展源），不吃页面 CSP，所以正常；YouTube / note.com 没有限制 `media-src`，所以正常。
- **[x] ① 已修复** — 页面层的单词发音改在扩展自有上下文播放：`bridge-shim.js` 打开 `window.__fushiWordAudioViaHost`（popup.js 既有的「交宿主播放、失败回落 `<audio>`」契约），实现 `playWordAudioNative` → background `playWordAudio` → offscreen 文档（扩展源，只受扩展 CSP）`new Audio` 播放，新一段先掐上一段、`play()` 真开始才回 ok。`background.js` 的 `ensureOffscreen` 声明 `USER_MEDIA` + `AUDIO_PLAYBACK` 两种用途，并发调用共享一次在途 `createDocument`（同一扩展只允许一个 offscreen 文档）。无 offscreen API（部分移动端 Chromium）或播放失败回 `ok:false`，页面层照旧回落页面内 `<audio>`。词典 `sound://` 媒体链接走同一入口，一并修复。
- **[x] ② 已增加自动化测试** — `tools/browser-extension/page-word-audio-offscreen.test.js`：vm 里跑真 `bridge-shim.js` + `popup.js` 播放切片（扩展能播时页面 realm 绝不构造 `<audio>`、音量随消息带过去、失败 / 抛错回落）、真 `offscreen.js`（播放 / interrupt / 失败原因 / scheme 白名单）、真 `background.js`（并发只建一个 offscreen 文档且声明 AUDIO_PLAYBACK、无 offscreen API 回 ok:false）。旧代码下 11 项中 8 项红。
- **备注**：未在真实 Chrome + x.com 上复测（本会话无浏览器扩展真机环境）；CSP 判定依据是 x.com 实际响应头与 Chrome 对 content script 创建的媒体元素按页面 CSP 加载的行为。
