## BUG-3435 · 小说高亮条瘦身后西文上伸 / 下延字母没被包住
- **报告**：2026-10-15（反馈 `0aAZxwH6hK`：「高亮条瘦身没有考虑到英文字母的上伸部分（f, l, t 顶部）和下延部分（p, g, y 底部），导致部分字母或标点未被完全包住」，截图是横排英文小说的查词选区；相关反馈 `F-JNEJVkuC`（10-13）：「高亮条减肥最好贴字不要碰到振假名」）
- **真实性**：✅ 真 bug，BUG-3369 瘦身的直接后果。窄条层 `window.__fushiLanes` 的 `lanes()`（修前 `fushi/lib/src/reader/reader_selection_scripts.dart:746-770`）对所有文字一律画「块方向 1em、居中于文字盒中线」的条，只有含 CJK 的片段才按「国」的墨迹中线微调（`cjkShift`，修前 `:685`）。西文字形不在 1em 中心带里：盒 = 字体 ascent + descent，盒中线在基线上方约 0.35em，1em 居中条下沿只到基线下 ~0.15em，而 p/g/y 的下延到 ~0.25em。真 Chrome 实测（生产 CSS + 引擎 shell，24px 默认字体链）：修前条下沿在基线下 1.5px，下延墨迹 6px；条厚 22px，西文墨迹 24px。
- **[x] ① 已修复**（提交 6e4a6eeb4f）— 条的块方向范围改由 `blockExtent()` 按字体真实度量算（canvas `measureText`，按字体缓存，字体加载完清空）：CJK 与 CJK 标点保持 1em、按汉字墨迹中线居中（不变）；含西文等非 CJK 文字的片段从文字盒推出基线（盒顶 + 字体 ascent 占比），条盖住上伸 + 下延参考字形 `bdfhkltgjpqy` 与该段自身墨迹（重音符等），各留 0.04em，不出文字盒；竖排横躺西文按顺时针 90° 同理，竖排直立 / 纵中横仍按 CJK。同一行（盒中线一致、字号一致）的片段并成一条时块方向取并集，CJK/西文混排也是一条等厚的条。最后按 F-JNEJVkuC 把条收到这一行振假名墨迹（`annotationInk()`：rt 文本盒按注音字体汉字墨迹厚居中）之外——贴字、不碰注音，与条居中冲突时注音优先。
- **[x] ② 已加自动化测试** — `fushi/test/reader/highlight_lanes_test.dart` + `highlight_lanes_harness.mjs`（真 Chrome，内层 node 进程 100s 超时 < 用例 150s 超时）：新增西文段落 `Flight <ruby>Tokyo<rt>とうきょう</rt></ruby> gets quickly by jolly piers`，在分页 / 连续 / VN × 横竖排下断言条厚 ≥ 像素扫描出的西文墨迹厚、横排条顶在基线（零尺寸 inline-block 真值）上方 ≥ 上伸墨迹、条底在基线下方 ≥ 下延墨迹、条不出文字盒；所有条不与振假名墨迹相交。另加 6 页 Apple CSS 变体（WebKit 注音规则 + `--fushi-ruby-pull: 0.5` 把注音压进基字盒），断言条让开振假名且仍 ≥ 0.5em。变异实测：换回修前脚本后，默认页报「latin lane covers the descenders (lane bottom 1.5 below baseline, ink 6)」与「latin lane is as thick as the ink (22.0 vs 24)」，Apple 变体报 18 条「overlaps furigana ink」。
- **备注**：
  - 未在 iOS / macOS 真机（WebKit）上复测；`fushi/integration_test/reader_audiobook_ruby_highlight_joints_itest.dart` 断言 CJK 条厚 1em，若 WebKit 下 1em 条确实压到振假名墨迹，那里的条会按本修复变薄，该 itest 需要按「不碰振假名」放宽。
