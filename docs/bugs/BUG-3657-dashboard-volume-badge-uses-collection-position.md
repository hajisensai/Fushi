## BUG-3657 · dashboard-volume-badge-uses-collection-position
- **报告**：2026-10-21（用户转述第三方反馈 + 截图：「weird ui, why does it say vol 17 here when I'm on volume 2/17」；首页「继续」主角卡封面是第 2 卷，进度条右侧徽标却是 `Vol. 17`）
- **真实性**：✅ 真 bug。`fushi/lib/src/pages/implementations/home_dashboard_page.dart` 书合集续读卡把 `idx + 1`（续读目标在合集排序里的**位置**）当卷号传给 `t.home_continue_volume`。合集顺序与卷号一错位，徽标就把位置当成卷号说出来；续读目标本身（锚点 = 最近读过的那卷）是对的。会让顺序错位的形态：手动「建系列 / 并入合集」按选择顺序尾插（`addToCollection` 不排序）、缺卷、只收了部分卷。用户这套书（オーバーラップ文庫 17 卷）的 dc:title 正是混写：1、2 卷是全角空格 + 全角数字 `まで　２`，3 卷起半角 `まで 3`。
- **连带后果**：续读推进（`continueMemberIndex`，锚点读完推 `anchor + 1`）同样依赖合集顺序。第 2 卷排在最后时，读完第 2 卷后 `anchor + 1` 越界、目标仍是读完的那卷，`dashboardBookCollectionContinueIndex` 返回 null，整套书从「继续」区消失、不推第 3 卷。
- **[x] ① 已修复** — (a) 新增纯函数 `dashboardBookVolumeNumber`：合集成员都是同一系列的分卷时（`sharedBookSeriesKey`，与 `BookSeriesGrouper` 同一判据）徽标取书名里的卷号（`parseBookSeriesKey`，全角已折半角），否则（主题合集里的「Fahrenheit 451」、混了别的系列、书名没卷号）退回合集内位置。(b) 修顺序本身：`BookSeriesGrouper.groupAll` 新增 `_healSeriesOrder`，对用户没手动排过（`orderUpdatedAt == 0`）、全员是同一系列分卷且卷号能完整定序的合集，顺序不对就按卷号自动重排（`reorderCollectionItemsAutomatically`，不接手用户排序）；混了外传 / 判不出卷号成员的合集留给 AI 排序，不碰。书架每次加载都跑 `groupAll`，存量错序合集打开书架即自愈。(c) 同步收敛（审查发现的阻塞项）：(b) 的自愈刻意不动 `orderUpdatedAt`（=0），而合集同步合并 `CollectionSyncEngine._mergeOne` 的手动序 LWW 在平手时取远端序（`packages/fushi_engine/lib/sync/collection_sync_engine.dart` `localOrderWins = l.orderUpdatedAt > r.orderUpdatedAt`）→ 远端旧错序被 `_localMatches` 判成差异、落盘覆盖本机，且合并结果原样发布 → 下次打开书架又自愈、再同步又被冲回，顺序永远来回翻，正确顺序传不上共享清单。书的 wire 成员键（bookKey）不带书名，合并引擎自己排不了，不能照搬视频 BUG-2941 的 `_withEpisodeOrder`；也不能让自愈盖 `orderUpdatedAt`（那等于伪装成用户手动排序，之后新卷不再自动排入、AI 排序也不再接手）。修法：把自愈判据抽成 `BookSeriesOrder.orderOf`（`book_series_grouper.dart`，归组自愈与同步共用一份）+ `sharedBookSeriesKey`（`book_series_key.dart`）；`CollectionSyncEngine.merge` 新增可注入的 `ruleOrder`，在 LWW 取序之后、`_localMatches` 判差异与发布之前，给 `orderUpdatedAt == 0` 的活合集按本机书架定规则序（`_withRuleOrder`），`loadBookSeriesRuleOrder` 把 wire 键经 `CollectionBookIdentityIndex` 换回本地键再判、排完换回原 wire 键。放在合并里而不是「落盘后再自愈」：本机已是卷序时合并结果也是卷序，不会先写错序再写回（每轮两次写库），云通道 per-device 折叠平手取字典序最小（可能恰是错序）的陈旧文件也冲不动它。三个同步入口同在合并锁内加载并注入：云 `SyncOrchestrator.syncCollections`（`fushi/lib/src/sync/sync_orchestrator.dart`）、互联 live `_syncCollectionsLive`（`sync_orchestrator/collections.part.dart`）、host 收 POST `mergeCollectionManifest`（`packages/fushi_engine/lib/sync/local_library_host_service/sync_state.part.dart`，返回给 client 的清单因此也是卷序）。本机定不了序（合集里有本机没有的书、混了外传）就保持 LWW 结果，交给持有全套书的一端排；对端收到卷序后平手取远端 = 卷序，不再翻。另：比较键末位补成员键（同卷配多条 SRT 时并列），`Dart List.sort` 不稳定也不会让「是否变化」误判而重复写库；不用行 id，因为 id 各端不同、同步里要各端排出同一个序。
- **[x] ② 已加自动化测试** — `fushi/test/pages/home_dashboard_continue_book_test.dart` 的 `dashboardBookVolumeNumber` 组（用户原样书名、第 2 卷排在第 17 位 → 2；无卷号书名退回位置）；`fushi/test/media/collections/book_series_grouper_test.dart` 三条（用户这 17 卷按「3..17, 1, 2」手动建合集 → 归组后 1..17 且二次幂等；手动排过不动；混外传不动）。变异实测：两处修复各自改回旧行为，对应用例变红。 `fushi/test/pages/home_dashboard_continue_book_test.dart` 补主题合集「Fahrenheit 451」→ 退回位置、混系列退回位置。`fushi/test/sync/book_series_sync_order_test.dart`（7 条）：复现（不注入规则序 → 合并结果是错序且要改写本机）；「本地自愈 → 同步合并远端错序（双方 orderUpdatedAt=0）→ 发布」落盘与发布都是卷序、第二轮零写库且发布内容不变、书架重载不再需要自愈；单份共享清单三端（自愈端 / 同书错序端 / 无书透传端）收敛后每端每轮零改写；云 per-device 陈旧错序文件冲不回；三个真实入口（云 `runCollectionsOnly`、live `syncCollectionsLiveForTest`、host `mergeCollectionManifest`）各一条。
- **备注**：没有拿到该用户的数据库，无法确认他的合集具体是经哪条路径排成这样；他若手动拖过合集顺序（`orderUpdatedAt > 0`），自愈按约定不动，但徽标仍显示正确卷号。
