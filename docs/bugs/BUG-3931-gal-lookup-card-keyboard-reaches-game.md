## BUG-3931 · gal-lookup-card-keyboard-reaches-game
- **报告**：2026-11-01（用户：应用内反馈 4c0IeCpSjb）
- **真实性**：✅ 真 bug（沿代码路径确认）：游戏内查词卡（`fushi/windows/runner/global_lookup_window.cpp`）是 WS_EX_NOACTIVATE 窗，卡在屏时键盘焦点仍在游戏上；宿主只有 WH_MOUSE_LL，没有任何键盘侧屏蔽，卡片的 Ctrl+C 复制靠 `RegisterHotKey`（仅有选区时注册）——Ctrl 的 down 先照常进游戏（消息与异步键态都可见），多数 galgame 把 Ctrl 当快进 / 跳过；注入侧护盾（generic_input_shield / HUNEX adapter）也只过滤 VK_LBUTTON
- **[x] ① 已修复** — 引擎无关的宿主层：`fushi/windows/runner/low_level_mouse_hook.cpp` 新增 WH_KEYBOARD_LL（与鼠标钩子同线程、同生共死，`SyncKeyboardHook`），判据在纯状态机 `fushi/windows/runner/lookup_keyboard_shield.h`（`KeyboardShieldLatch`）：绑定游戏的查词卡在屏且游戏是前台时，**新按下**的键被吞（配对 up 与自动重复同吞，卡片中途关掉也成对吞），卡片出现前已按住的键与其 up 放行（不制造卡键）；Alt / Win / Shift 永远放行（系统键与悬停查词修饰键）。被 LL 钩子吞掉的事件不进输入队列、不更新异步键态，所以对消息型、GetAsyncKeyState、RawInput 读法同时生效，已有引擎级屏蔽的适配（HUNEX）无需另补键盘分支。Ctrl+C：吞掉的同时投 `kLowLevelKeyboardCopyMessage` 给卡片，走与原 `RegisterHotKey` 同一个复制出口。全局热键不被吞死：每个新吞的非 Ctrl 键用「试注册」探测（修饰键 + 键）是否已是任何程序的热键（含 Fushi 自己的应用外查词 / 截屏识字），是就交还并把之前吞掉的 Ctrl 与该键按原顺序带标记重放。分支 fix/feedback-galgame
- **[x] ② 已加自动化测试** — 原生单测 `fushi/windows/runner/tests/lookup_keyboard_shield_test.cpp`（CMake target `fushi_windows_lookup_keyboard_shield_gate`：Ctrl+C 吞并复制、预先按住的 Ctrl 放行、卡片中途关闭成对吞、Alt/Win/Shift 放行、热键交还）；源码守卫 `fushi/test/lookup/gal_overlay_click_shield_guard_test.dart`（键盘钩子生命周期、重放标记先于状态机、热键探测、卡片复制消息处理）
- **备注**：**真机未验**。缺的证据：① 真实游戏（反馈游戏 / 任一把 Ctrl 当快进的引擎）上查词卡在屏时按 Ctrl+C 不再快进、卡内选区照常复制到剪贴板的录屏；② 读 DirectInput 键盘的引擎是否同样看不到被 LL 钩子吞掉的键（未验证）；③ 卡片在屏时按应用外查词 / 截屏识字热键仍能触发（热键交还路径）的实机确认。状态：implemented_unverified
