## BUG-2081 · Mihon Android 通道 void 方法回 kotlin.Unit 触发 StandardMessageCodec 崩溃，Discover/Import 打开即崩
- **报告**：2026-09-03（用户：装过一个漫画扩展后，每次打开漫画 Discover / Import 页都崩；日志 `java.lang.IllegalArgumentException: Unsupported value: 'kotlin.Unit' of type 'class kotlin.Unit'`，栈顶 `StandardMessageCodec.writeValue` ← `MihonChannelHandler.register$lambda$0$1$0`）
- **真实性**：✅ 真 bug，自 `ee5f713133`（2026-07-29 Mihon 扩展生态首次提交）就在。`fushi/android/app/src/main/kotlin/app/fushi/reader/mihon/MihonChannelHandler.kt:127-151` 的 `handle()` 是 `when` 表达式，`"uninstallPrivateExtension" -> uninstall(...)`（`:212`，无返回类型）和 `"clearSourceData" -> clearSourceData(...)`（`:381`，无返回类型）两条分支的值就是 `kotlin.Unit` 单例；`:89` 把它原样 `mainHandler.post { result.success(value) }`，StandardMessageCodec 不认 Unit，在主线程 Runnable 里抛未捕获异常，进程直接死。同文件 `invalidateExtension` / `dispose` 两条分支手写了 `{ ...; null }` 才没中招——说明作者知道这个坑但没收口。
  用户看到的循环：`fushi/lib/src/media/manga/mihon/mihon_manager.dart:808-816` `_discardPreview`（预览失败 / 用户不保留时）→ `uninstallPrivateExtension` → 崩；`:744` 预览标记 `tmp/preview-pending` 已先于文件落地写下、崩溃前来不及清；之后每次进漫画 Discover / Import 触发 `MihonManager._initialise`（`:117`）→ `_recoverAbandonedPreview`（`:838`）→ 再次 `uninstallPrivateExtension` → 再崩，Dart 侧 `on Object` 兜不住进程死亡，标记永远清不掉。`manga_sources_page.dart:567` 的「清除来源数据」按钮走 `clearSourceData` 是同一个崩点。
- **[x] ① 已修复** —（本提交）`MihonChannelHandler.kt`：`handle()` 拆成纯分发的 `dispatch()` + 通道唯一出口 `handle()`，后者 `if (value === Unit) null else value` 一处收口；顺手删掉 `invalidateExtension` / `dispose` 分支手写的 `{ ...; null }`，四条 void 分支现在都是普通分支。Kotlin 侧 `flutter build apk --debug` 编译通过。
- **[x] ② 已加自动化测试** — `fushi/test/media/manga/mihon_channel_reply_codec_guard_test.dart`（仓库无 Android JVM 单测基建，可落地的最强层是源码守卫）：
  ① `handle()` 函数体（`private fun handle(` 到 `private fun dispatch(` 之间）必须含 `dispatch(call)` 与 `=== Unit) null`；
  ② `register()` 里回复值必须是 `val value = handle(call)`，且全文件每个 `result.success(<arg>)` 的实参只能是 `null` 或 `value`——任何绕过 `handle()` 出口的新回复点都红。
  变异实测：删掉 `if (value === Unit) null else value` → 守卫 ① 红；`val value = handle(call)` 改成 `dispatch(call)` → 守卫 ② 红；两次都按原串还原并 sha256 核对一致。
- **备注**：用户设备上已经写下的 `preview-pending` 标记不需要手动清：修复后 `_recoverAbandonedPreview` 第一次成功 `uninstallPrivateExtension` 就会走到 `_clearPreviewMarker`。真机复测原始路径（预览扩展→不保留→重进 Discover）本轮未做，只有编译 + 源码守卫证据。
