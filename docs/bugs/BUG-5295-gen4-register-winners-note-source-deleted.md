## BUG-5295 · gen4 迁移对拍：笔记 `source` / `deleted` 寄存器两侧胜者不同（协议 3 多出 1049 条活着的修改记录），整份撤回
- **报告**：2026-11-23（应用内反馈 EapjqHGvCl：Windows 3.4.0-debug.31707，复习库升级 `aborted` / `profileVerdict: fail`；风险标记 duplicate:RhMpA6bn8v 只是正文相同，签名不同）
- **真实性**：✅ 真 bug（报告签名已核）。四个 profile 里只有 `01a16e76…` 失败（2 台设备、`imported.applied` 1197252、闭包两台都 `same`）：
  - `edits` onlyOld 1049 / onlyNew 0：协议 3 判活着的 1049 条修改记录新代不认为活着；`canonical.registerWinners` onlyOld 1049（笔记的 `source` 902 + `deleted` 147）、onlyNew 147（同一批笔记的 `deleted`，胜者不同）；
  - `notes` 1049 行同 ID 不同：`source_title` / `source_key` 902、`source_kind` 364 新代为空，`pending_decision` 206、`deleted_at` 147；`cards` 147 行 `hidden` 1 → 0（协议 3 判删了、新代没删）；
  - 现成缓存与重建的比：同 147 条笔记 `pending_decision` 0 → 1（协议 3 重建判「删除与修改并发、待裁决」）；
  - `oldSideStaleResults` 0、卡的调度列与统计都没差：与 PR #4245 的重复日志代表不一致无关。
  - 推测（未验证）：这 1049 条修改记录在协议 3 的 `srs_field_edits` 里、却不在新代可见的操作集合里（或在新代被判被支配），集中在 `source` 与 `deleted` 两个键上；需要查这两个键的写入路径是否有不经操作直接落 `srs_field_edits` 的，或两侧对旧修改记录闭包 / 并发删除的判据不同。
- **根因**（形态已由报告逐项推定并复现；用户库里这批行是从哪条来路漏包的，报告证不出，见备注）：新代只从协议 3 的操作日志（`sync2_ops`）建库，导入计数说明全部操作都进来了（`applied` = `ops` + `voids`，没有 parked / pending / untrusted / alias），而 902 个 `source` 寄存器新代连一个胜者都没有（`registerWinners` 对这批只有 onlyOld）——新代判不活一条写入只有两种：被同寄存器里活着的写入支配（那条会是新代的胜者），或负状态（清除 / 不可信 / 扣住，这个 profile `purged` 为 0，后两种只管删除）。所以这 1049 条修改记录是**协议 3 投影里有、本 profile 的操作日志里没有**的行：协议 3 读投影，用户看得见（来源标题、删掉的笔记），换代就丢。147 条 `deleted` 同理：协议 3 的胜者是那条没进操作日志的删除，新代只剩更早的那条。两条已在代码里走通的来路：
  1. `sync2_migrate` 的「已被代表」判据不分 profile（`store/sync2/mod.rs` `enqueue_legacy_rows` :1867 与 `represented` :1983 查 `sync2_edit_ops` / `sync2_log_meta` 只按 ID）：这两张表以修改记录 / 日志 ID 为主键、全库共用，别的 profile 收到同一个旧 dot 的操作时 `index_edit`（:1338 `INSERT OR REPLACE`）就占走这一行，本 profile 迁移时这条旧行被当成「已被代表」漏包；
  2. 迁移做完之后才出现在投影里的旧行：`sync2_migrate` 对 `migrated` 的 profile 直接返回（以前的 :2315），从不再补包。
- **[x] ① 已修复** — 修数据，不改对拍：`enqueue_legacy_rows` / `represented` 的判据按 profile 分；`sync2_migrate`（:2315）对已迁移的 profile 也先查 `has_unrepresented_rows`（:1918，只读、按主键查：本 profile 投影里没被本 profile 操作代表的旧修改记录 / 日志），有就照常排队补包（`finish_migration` 不覆盖已有的 `migrated_at`）；`store/gen4/legacy.rs` `preflight` 对这种 profile 报「legacy rows are not represented in this profile's op log」，迁移前提补完（`prepare.rs`）因此在副本上把它们包成本 profile 的操作，之后新代与协议 3 读到同一批修改。身份记录 / 不认识的事件的漏包要扫操作日志才判得出，`has_unrepresented_rows` 不查，`migrate` 排队时照旧判。`idTrace` 每个 ID 补 `p3`（`store/gen4/compare.rs` `annotate_protocol_3`（:1500）：修改记录行归谁、`sync2_edit_ops` 映射归谁、映射到的操作在不在本 profile 日志里。
- **[x] ② 已加自动化测试** — `store/gen4/migrate_tests.rs` `projection_rows_no_op_of_the_profile_represents_are_wrapped_before_migrating`：① 迁移做完之后往投影里插一条笔记 `source` 与一条 `deleted` 旧修改记录；② 迁移前的旧行、`sync2_edit_ops` 里同 ID 的映射归另一个 profile。两种都跑真实迁移，断言整份提交、对拍为空。去掉修复（还原 `sync2/mod.rs` 与 `legacy.rs`）时 ① 中止，`edits` onlyOld 2、`registerWinners` onlyOld 2（`source` + `deleted`）、`notes` 列不同、卡 `hidden` 不同，与报告同签名，`p3` 写着 `"row": "self", "op": null`。
