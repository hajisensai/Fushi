## BUG-782 · 快捷面板退出按钮直接pop绕过PopScope致hero不更新且不触发同步
- **报告**：2026-07-13（用户真机 Windows：「书籍的继续阅读不会更新，我明明看了另一本书，上面的书还是没变」）；关联 2026-07-12 首报「好像也没同步远端」——同一根因两个症状。
- **真实性**：✅ 真 bug。桌面端唯一可见的退出入口是阅读器快捷设置面板的「退出」按钮。链路：
  - 面板退出按钮 `hibiki/lib/src/media/audiobook/reader_quick_settings_sheet.dart:1666-1676`：先 `Navigator.of(context).pop()` 关掉面板自身，`addPostFrameCallback` 再回调 `widget.onExitReader`。
  - `onExitReader` 由阅读器在 `hibiki/lib/src/pages/implementations/reader_hibiki/chrome.part.dart:1368`（修前 `Navigator.of(context).pop();`）提供——面板关闭后此刻栈顶是阅读器路由，于是这一句**直接 pop 阅读器路由**。
  - 阅读器路由外层是 `PopScope(canPop: false)`（`hibiki/lib/src/pages/implementations/reader_hibiki_page.dart:2224-2231`），唯一退出闸门是它的 `onPopInvokedWithResult`：`await onWillPop()` 通过才 `nav.pop()`。直接 pop 时 `didPop` 已为 true，PopScope 回调直接 return，闸门被完全绕过。
  - 被跳过的 `BaseSourcePageState.onWillPop`（`hibiki/lib/src/pages/base_source_page.dart:184-207`）依次做：① `onSourcePagePop()`——最终阅读位置 flush 落库（BUG-203 在此路径回归）；② `appModel.closeMedia()`——内部经 `onSourceExit` invalidate `hibikiBooksProvider` / `bookLastReadAtProvider`（BUG-777 修复正是靠这次 invalidate 刷新书架「继续阅读」hero 与进度）；③ `triggerAutoSyncAfterClose()`——关书触发远端自动同步。三步全跳过 = 书架 hero/进度陈旧 + 关书不同步。
  - 正确范式在 `hibiki/lib/src/pages/implementations/reader_hibiki/caret.part.dart:522-532`（键盘 ESC / 手柄 B 的 `readerDismissDict`）：`unawaited(Navigator.of(context).maybePop())`，注释已写明「Mirrors the chrome-scope and popup-scope B/Esc branches that already maybePop()」。`maybePop()` 会触发 PopScope 回调 → `onWillPop()` → 真正 `nav.pop()`。桌面唯一可见退出按钮却没跟这条范式对齐，Android 系统返回走 `maybePop` 不受影响，故仅桌面复现。
- **[x] ① 已修复** — 提交 `集成者补记`。`chrome.part.dart` 的 `onExitReader` 回调由 `Navigator.of(context).pop()` 改为 `unawaited(Navigator.of(context).maybePop())`（`dart:async` 已在 `reader_hibiki_page.dart:1` import，part 文件共享，`unawaited` 可用），并加中文注释指明根因与「同 ESC / 手柄 B 分支」同径。退出闸门从此三条路径（面板按钮 / ESC / 手柄 B）统一走 PopScope→onWillPop。对抗审查加固（同提交）：`reader_hibiki_page.dart` 的 `onPopInvokedWithResult` 加 `_popInProgress` 重入护栏——`onWillPop` 异步 flush 窗口期内第二次退出触发（ESC 连按 / 退出按钮后再 ESC）此前会并发再跑一条 onWillPop、首条 pop 掉阅读器后第二条把书架也弹掉（连退两级 + closeMedia/自动同步重复执行）；护栏把并发退出触发合并为一次，`finally` 复位保证 onWillPop 异常时可重试退出。
- **[x] ② 已加自动化测试** — `hibiki/test/pages/reader_exit_maybepop_guard_test.dart`：源码切片守卫，切出 `onExitReader` 回调块断言①含 `maybePop(`、②不含裸 `Navigator.of(context).pop(` / `Navigator.pop(context`，再加全文件级逐处窗口断言防复发变体。测试头注释记清 BUG-782 前因后果（为何直接 pop 是错的、破坏了 flush/closeMedia-invalidate/自动同步哪条链）。
- **备注**：
  - BUG-777 的修复本身正确——它依赖 `closeMedia` 的 provider invalidate 刷新书架 hero，本 bug 只是让退出根本没走到 `closeMedia`，把 BUG-777 的刷新链在最上游掐断，并非 BUG-777 回退。
  - 数据层已核实：生产 DB `reader_positions.updatedAt` 全新鲜（21:56 刚读的书写入在库），说明位置落库本身正常（面板退出前的 debounce 写已生效），陈旧的只是书架 UI 的消费链（invalidate 未触发 → provider 不重算 → hero 停在旧书）。
  - 全仓横扫（只报告未改）：阅读器其余 `Navigator.pop` 均为对话框 / sheet / 子路由自身 pop（图片查看器、插图廊、hint 对话框、导入对话框），直接 pop 正确。**错误路径** `reader_hibiki_page.dart:1523/1545` 与 `webview.part.dart:1976`（开书失败 / 文件缺失 / WebView2 创建失败）是有意直接 pop 退回书架：因 `openMedia` 在 push 路由前已置 `currentMediaSource` / immersiveSticky / wakelock / `mediaOpenNotifier=true`，绕过 `closeMedia` 会残留沉浸模式 + wakelock + macOS sidebar 隐藏态直到下次 open/close——是与本 bug 不同症状的独立潜在遗留（书未读，无需 flush/invalidate/同步，仅 UI 系统态泄漏，较轻）。视频页同族错误路径 `video_hibiki_page.dart:2633/5377`（资源缺失重导）同样直接 pop 绕过其 `PopScope`。均建议后续统一改走 `onWillPop()` / 显式 `closeMedia`，本轮按范围不动。
