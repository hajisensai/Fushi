## BUG-4910 · 沉浸制卡全进程一条串行队列，一张远端断流的卡挡住后面所有卡
- **报告**：2026-11-20（来源：路线图 `docs/plans/2026-11-17-novel-manga-video-remaining-roadmap.md` 的 video-30，c44 组；复核结论「部分成立」：队列不只是因为临时文件名写死，它是 BUG-1228 按用户要求建的，同时管临时文件争用、AnkiConnect 单端点、换集污染三件事）
- **真实性**：✅ 真 bug。`fushi/lib/src/mining/immersion_mining_engine.dart:424`、`:472`（基线 `origin/develop` 7745effa2e）：所有沉浸制卡（视频页、远端、在线源、浏览器扩展、galgame、收藏批量）共用一条进程级 `SerialJobQueue`，入队的是「抽 GIF/音频 → 上传 → add/update note」整笔事务；抽取又写死在调用方给的同一个临时目录里的固定文件名（`:719` 的 `$tempDir/immersion_clip`、`immersion_audio.*`、`immersion_frame.*` 等）。于是一张远端流断流的卡（ffmpeg 等到超时，最长约 120 秒）期间，后面连点的每一张卡都既不能抽也不能落；固定文件名又让「放开并发」本身不安全。
- **[x] ① 已修复** — 把整笔事务拆成两段：**抽取**在 `mine()` 被调用时就开跑，每个任务在调用方临时目录下建一个私有的 `immersion_job_*` 目录（不再争同名文件），由新的 `BoundedJobLimiter`（`serial_job_queue.dart`）限到同时 2 路；**落卡**仍走原来那条进程级 `SerialJobQueue`，在 `mine()` 调用的那一刻同步入队，轮到它时等自己的抽取结果再写 Anki——按点击顺序提交，同一时刻只有一张卡在写 AnkiConnect。抽取失败在点击当下收成值、轮到它落卡时原样抛给调用方，不毒化后续卡；私有目录在落卡（或抽取失败）后整个删掉。换集污染靠的本来就是入队时冻结请求（`ImmersionMiningRequest.frozen`），拆开后不受影响。提交见本文件 Git 历史。
- **[x] ② 已增加自动化测试** — `fushi/test/mining/immersion_mining_queue_test.dart` 的「video-30」组：第一张卡的 GIF 抽取卡住时第二张照常开始抽取、但不越过第一张先落卡，放开后按点击顺序落卡（修复前第二张根本不开始抽取）；同时在抽的两张卡输出目录不同、落卡后临时目录为空（修复前同一目录同一文件名）；三张卡同时卡住时只有两路在抽（防止改成不设限）；前一张抽取抛错原样抛给它的调用方、后一张照常落卡且目录收掉。`fushi/test/mining/serial_job_queue_test.dart` 补 `BoundedJobLimiter` 的名额转交顺序与抛错归还。旧的「第二张不得启动」断言随修复改写；`synchronized_video_mining_test.dart` 里两条看 temp 根的清理断言改成在落卡那一刻看私有目录（否则会因整目录事后被删而变成空断言）。
- **备注**：落卡严格按点击顺序，所以第一张卡断流到超时期间，后面的卡已经抽好但仍要等它出结果才落——总耗时从「各张之和」变成「约等于最慢那张」，但不是「后面的卡先落」。要不要允许后面的卡越过断流的卡先落，涉及 BUG-1228 当初「多次制卡进入队列」的顺序语义，交所有者拍板，未实现。
