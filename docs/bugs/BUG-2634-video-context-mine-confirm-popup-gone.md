## BUG-2634 · 视频「调整上下文」确认制卡报「查词弹窗已经关掉了」
- **报告**：2026-09-22（用户：截图视频页 toast「制卡没能开始——回点制卡按钮时查词弹窗已经关掉了。请重试。」，「这个修坏了，上下文没法制卡了，得查词框里制」；构建含 PR #1597 = BUG-2627 两轮修复 `0b3fe2718cb` + `274e274ba49`）
- **真实性**：✅ 真 bug（结构性），但**原始失败路径未在本机复现**：Windows 离屏 runner 用 `integration_test/video_ctx_mine_confirm_itest.dart` 复演「seed 字幕视频 + 生成词典 → `_lookupAt` 查词 → 点『调整上下文』→ 确认」六轮（含接上测试内假 AnkiConnect 真跑查重 → ffmpeg 抽媒体 → addNote 的完整制卡），对话框都在 0.9～1.4s 内关闭、无失败 toast、`fushiPopupMineEntryByIndex` 回 true。根因落在 BUG-2627 第二轮 `274e274ba49` 的设计上：
  - `fushi/lib/src/pages/implementations/dictionary_popup_webview.dart` `mineEntryByIndex` 用 `callAsyncJavaScript` await popup.js 的 promise 到 `mineEntry` 回执**落地**，再让 `SentenceContextDialog._confirm` 关窗；期间对话框 `_busy` 锁死、弹窗停靠屏外。「落地」= 整个制卡任务：ffmpeg 抽 GIF/音频 + Anki 往返，几秒到几十秒，还要排 `_mineVideoCard` 的共享制卡队列（连着制几张卡时更长）。
  - 超过 `_kMineRoundTripTimeout`（45s）就 `TimeoutException → false`，对话框弹的却是同一条「弹窗已经关掉了」文案（卡随后照样制出来）；弹窗在这几十秒里被关栈 / 低内存拆 WebView / renderer 重建时 promise 直接死在半路，也是同一条 toast——用户看到的就是「确认了却没制成」。同一时间的滚轮穿透（BUG-2633）说明该构建里弹窗期间指针事件也在穿到视频页，任何一条关栈入口都可能在制卡途中被触发。
  - 草稿真正需要保护的窗口其实只到「宿主开始消费 payload」：视频 `_onMineEntryImpl`（`lookup_mining.part.dart`）在首个 await 之前就 `_resolveVideoMiningRange` 读走草稿，reader `_prepareMiningContext`（`reader_fushi/mining.part.dart:27`）同样在首个 await 前 `composeText` / `composeAudioRange`。等到落地是过度保护。
- **[x] ① 已修复** — `DictionaryPopupWebViewState` 新增「确认往返接受信号」`_confirmMineAccepted`：三个制卡桥 handler（`mineEntry` / `updateEntry` / `minedCardAction`）在把 payload 交给宿主的那一刻 `_markConfirmMineAccepted()`（前两者在 `widget.onMineEntry` / `onUpdateEntry` 同步执行到首个 await 之后、await 之前；后者在宿主处置单收尾后）；`mineEntryByIndex` 改成 `Future.any([JS 落地, 已接受])`——宿主一接受制卡任务对话框就关，制卡在 Dart 侧照常跑完并自己出 toast（与直接点弹窗里的 + 一致）。45s 超时只剩「回点前」（查重 → 取音 → 组 payload）这一段，真超时才是弹窗桥半死；JS 落地在接受之后失败只落日志不再改变结局。`sentence_context_dialog.dart` `_confirm` 文档同步。提交见本文件所在修复提交。
- **[x] ② 已加自动化测试** — `integration_test/video_ctx_mine_confirm_itest.dart`（Windows runner，`-Visible`）：真 WebView2 弹窗 + 真根 Overlay + 真对话框 + 测试内假 AnkiConnect（`integration_test/support/fake_ankiconnect.dart` / `fake_ankiconnect_setup.dart`，`test/tools/fake_ankiconnect_smoke_test.dart` 用本仓真 `AnkiConnectService` 实跑全部 action 形状）走完「查词 → 调整上下文 → 确认」，断言对话框关闭、无失败 toast、假服务真收到 addNote；新增视频页测试钩子 `debugLookupAt` / `debugVolume`。既有 `sentence_context_dialog_widget_test` / `_zorder_guard_test` / `_modal_guard_test` 契约不变、照跑。
- **备注**：**未在真机复演用户的原始失败**（六轮都过），本条按「结构性根因 + 真机验证新路径」关闭；若用户更新后仍报同一 toast，先取 `ErrorLogService` 里 `DictPopupWebview.mineEntryByIndex` 那条（现在四种失败各有独立文案：无 controller / JS 拒点 / JS 抛错 / 45s 内既未接受也未落地）。BUG-2627 备注里「成功 toast 与记账不同源」一条仍未查。
- **合并审查补记（第二轮修法）**：首版把「已接受」做成**一个**信号，同时兼管「解除 45 秒超时」与「可以关窗」，两条路各出一个问题。① `minedCardAction`（这个词以前制过卡 → 弹「覆写 / 新增重复 / 取消」操作单）会**无限等用户做选择**，信号却放在 `await` 之后，45 秒照旧盖住「模态等人」——超时后报的正是用户原话那句「查词弹窗已经关掉了」，还会把用户正在用的那张操作单 `Navigator.pop` 掉（同一个 root Navigator），用户若已选「覆写」则卡照样落地、UI 却报没开始。② 但把它挪到 `await` 之前又会踩另一头：阅读器的 `onMineFromPopup` 经制卡串行队列入队（TODO-644 / BUG-357），草稿要等前一次制卡整段跑完才被读走，提前关窗 → 弹窗关栈 → `_miningDraft.clear()` → 排到的任务用空草稿合成，正是本 bug 上一轮自己写下的那个更隐蔽的症状。
  修法是把一个信号拆成两个，判据抽进纯逻辑 `fushi/lib/src/pages/implementations/confirm_mine_round_trip.dart`：`markHostEntered` **只解除超时**（那个超时本来就只为「弹窗桥半死不回」而设，宿主的 Dart 代码一旦在跑，桥就已经回过话了），`markPayloadConsumed` 才允许关窗，且**只有担保「首个 await 之前同步读走草稿」的宿主才调**——视频车道传 `releaseWhenPayloadConsumed: true`，阅读器车道传 `false`、退回「等落地」这条老路（慢一点，但绝不丢草稿）。`minedCardAction` 只发前者、且挪到 `await` 之前。超时的日志文案也改成「桥没走到宿主」，不再说成「弹窗已关」。
- **测试补强**：新增 `fushi/test/pages/confirm_mine_round_trip_test.dart`（9 条纯 Dart 用例，真异步 + 60 ms 超时）钉住「宿主接手后没有上限」「只解除超时不等于可以关窗」「拒点 / 通道异常 / 竞态同时到」等判据——把 `markHostEntered` 退化成「接手即可关窗」即三条精确变红。itest 原先只断言「没出失败 toast」，其余全在 `debugPrint` 里；现补三条机器断言：对话框真的关了、假 AnkiConnect 真收到 `addNote`、落地的卡的字段里真带着句子上下文（空草稿即红）。
