## BUG-937 · 互联视频浏览极慢：封面端点每张封面重跑整份 listVideos 清单（O(N²)）
- **报告**：2026-07-20（用户：书籍同步快、视频同步极慢，约 500+ 条视频）
- **真实性**：✅ 真 bug。根因 `hibiki/lib/src/sync/hibiki_sync_server.dart:1999`（修复前）：`_resolveVideoCover` 每处理一张封面请求就 `await service.listVideos()` 整表重算，只为线性找一条 coverPath；而 `AppModelLibraryHostService.listVideos()`（`app_model_library_host_service.dart`）每行做 1 次全目录 `listSync`（`video_sidecar.dart:77`）+ 2~3 次 position prefs 读 + 1 次行重查 + 2 次标签 LWW 查询——500 行清单一次 ≈ 2500 次 DB 往返 + 500 次目录扫描，浏览 500 张封面 = 500 × 上述全量 ≈ 25 万次目录扫描 + 上百万次 DB 查询，分钟级卡死。书籍封面 `_resolveBookCover`（`:1365`，修复前）同病但 listBooks 每行只有 stat + 批内查询，症状轻。注：清单端点逐条 `ffmpeg -i` 探测已在 BUG-814 移除，本 bug 是其后仍存的主要热点。
- **[x] ① 已修复** — 封面端点改单行直查：接口新增 `HibikiLibraryHostService.videoCoverPath/bookCoverPath`（1 次 DB 单行查询 + stat），`_resolveVideoCover/_resolveBookCover` 不再 materialize 清单；`listVideos()` 本身批量化（position prefs `getAllPrefs` 一趟、标签 LWW/墓碑 `allVideoTagAddedAtByName`/`allTagTombstonesByName` 各一趟、sidecar 同目录 listing 每次调用只扫一次），`listBooks()` 的逐书标签双查询同批改批量。另加 JSON 清单 gzip 内容协商（`_gzipTextMiddleware`，旧 client 无 Accept-Encoding 收明文，零协议破坏；文件流/Range 不压）。提交：见本分支 worktree-interconnect-refactor。
- **[x] ② 已加自动化测试** — `hibiki/test/sync/hibiki_sync_server_perf_guard_test.dart`（fake 的 listVideos/listBooks 直接抛错，封面端点仍须 200 → 源头封死 O(N²) 回归；gzip 协商三例：带头压缩可解回、不带头明文、文件流不压）；`hibiki/test/sync/hibiki_library_host_service_cover_path_test.dart`（单查与清单同源同值、缺文件/未知 id 判 null、title 兜底兼容）。
- **备注**：videos 进度 live sweep（`_syncVideoProgressLive`）本已用清单一次拉 + 仅变更 PUT，此次连带受益于 listVideos 批量化。WS/UDP 换协议对本 bug 无解——瓶颈全在应用层。
