## BUG-4275 · 离线时查词等远端 4.5 秒、服务器恢复后查词仍只出本机结果（查词与目录服务各记一份可达性）
- **报告**：2026-11-09（服务端词典场景探针 `fushi/integration_test/server_dictionaries_scenario_test.dart` 场景 5「offline」，run win-itest-20261109-225243-e6d662aa）
- **真实性**：✅ 真 bug。两个症状：
  1. host 关掉、配对里有两条地址（LAN + 学到的另一条）时，首次查词 4.5 s 才出本机结果（Windows 上每条被拒连接约 2.2 s），45 s 冷却内 254 ms，冷却一过又 4.5 s；关机（无 RST）时是 3 s × 地址数。此时目录服务早已判定 host 连不上（来源卡片已显示），查词路径却不知道。
  2. 服务器重启、目录 `refresh()` 成功、卡片显示在线后，下一次查词仍只出本机结果，要等满查词自己的 45 s 冷却。
  - **根因**：同一台 host 的可达性有**两个互不相通的追踪器**——查词路径的 `AppModel._remoteDictionaryUnreachableUntil`（原 `fushi/lib/src/models/app_model.dart:9708`，`_searchRemoteDictionary` 在 `:9851` 写冷却）与目录服务的 `RemoteDictionaryCatalogService._reachability`（原 `fushi/lib/src/sync/remote_dictionary_catalog_service.dart:114` `_noteReachability`）。查词不读目录服务的结论（症状 1：重复付连接超时），目录刷新成功也不清查词的冷却（症状 2）；`_searchDictionaryInLanguage`（原 `app_model.dart:9545`）对远端的 `await` 又让本机结果陪着等。此外查词路径的冷却到期只能由下一次查词去碰运气，没有任何后台探测。
- **[x] ① 已修复** — 新增 `fushi/lib/src/sync/remote_dictionary_reachability.dart` 的 `RemoteDictionaryReachability`：每 host 一份 `{lastOkAt, failingSince, lastAttemptAt}`，全进程唯一真相源，AppModel 持有、注入目录服务。`InterconnectPostTransport` 新增 `onCandidateOutcome`（逐候选报「拿到 HTTP 响应 / 传输层失败」），查词客户端与目录服务都经 `RemoteHostOutcomes` 按 host 归并后 `record` 进同一份；查词客户端按 `shouldSkip` 跳过判死的 host；全部查词 host 判死时 `AppModel` 不发起远端、本机结果不等。目录服务 `start()` 挂上后台探测 `probeHost`（3 s 短预算拉清单），判死后每 45 s（`kRemoteDictionaryFailureCooldown`）探一次；回前台判死的 host 不受 10 分钟节流、配对列表变化立刻再探。弹窗进程无目录服务时退回「间隔内跳过、过了间隔由查词顺带重试」。可达性改按传输层记：老 host 的 404 / 凭据被拒的 401 = 活着。提交：（待提交）
- **[x] ② 已加自动化测试** — `fushi/test/sync/remote_dictionary_reachability_test.dart`（追踪器跳过判据 / 后台再探测节奏 / 回前台立即探 / 查词客户端零请求跳过与按 host 记账）、`fushi/test/sync/remote_dictionary_catalog_service_test.dart`（传输层口径、后台自动恢复、回前台不节流、配对变化再探）、`fushi/test/models/app_model_remote_reachability_test.dart`（真 `AppModel.searchDictionary` + 真目录服务共用一份：判死后零请求、目录先判死则查词不问、目录刷新成功后下一次查词立刻合并）。
- **备注**：查词往返预算 3 s 保持不变（包住 host 查词本身 + 回包，缩短会把慢而活着的 host 误判成死的）；离线代价改为每次判死只付一次。真机端到端复测（场景 5 重跑）待补。
