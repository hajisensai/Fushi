## BUG-2887 · KiriKiri2 TCWF 语音（TSS 解码插件取流）整局抓不到，全部降级 loopback
- **报告**：2026-10-03（agent 在 ceshi 样本 Fate/stay night[Realta Nua]（KiriKiri2 2.31 / BCB）真机验收中发现：Saber 的有声台词「問おう。貴方が、私のマスターか」配对结果是 `fallback/system_loopback reason=engine_utterance_unavailable`）
- **真实性**：✅ 真 bug。两处根因，都在 `native/galgame_hook/hook/adapters/kirikiri_adapter.inc`：
  - **取流 hook 装错了边界**：BCB 分支只 hook 插件导入桩 `TVPCreateIStream`（`InstallVoiceStreamHookWithExporter` 的 `is_bcb` 分支）。KiriKiri2 的 `wu*.dll` 解码插件（这里是 `wutcwf.dll`，由引擎从 xp3 解到 temp 后加载）是 TSS 插件：引擎在 `GetModuleInstance` 时递给它一个 `ITSSStorageProvider`，插件经 `provider->GetStreamForRead` 取流。krkr2 2.32 `PluginImpl.cpp` 里 `tTVPStorageProvider::GetStreamForRead` 直接调 `TVPCreateStream(url)` 再自己 `new tTVPIStreamAdapter`——既不经导入桩，也不经内部 `TVPCreateIStream`（后者同样是 `TVPCreateStream` + adapter 的并列包装，`StorageImpl.cpp`）。三条路径唯一的汇合点是 `TVPCreateStream`。真机 `decdiag=0x02a30141`：`0x20000`（stream hook ready）与 `0x800000`（BCB）亮，`0x40000`（detour 触发过）整局恒灭；第一版修复改 hook 内部 `TVPCreateIStream` 后真机仍恒灭（Saber「問おう」仍是 loopback），据此核对源码才定位到 `TVPCreateStream`。
  - **定位器步进错位（潜在）**：`InsnLen32` 吃掉 `0x66` 前缀后不记操作数宽度，BCB try 帧序言 `mov word ptr [ebp-20h], 0`（`66 C7 45 E0 00 00`，imm16）被当 imm32 多走 2 字节，从 BCB 的 `TVPCreateIStream` 函数体找首个 call（即 `TVPCreateStream`）会错位。Fate 进程内实测该函数体：try 序言之后首个 call 就是 `mov eax,ebx; mov edx,esi; call TVPCreateStream`，其后 `push 0Ch; call new`、adapter 构造。
  - **容器不认**：语音是 KiriKiri2 自有的 TCWF（`voice.xp3` 11998 条成员全是 `.tcw`，头 `TCWF0\x1a`），入队门只收 Ogg / RIFF-WAVE 魔数，消费端也只按扩展名 / 容器认 ogg、wav。
  - 不能改成「LoadLibrary 时 hook 插件的 `GetModuleInstance`」：Fate 的插件全在启动首帧内加载完，早于 worker 装 hook（见 `TryHookKirikiriVoiceStream` 注释）。
- **[x] ① 已修复** — 实现：BCB 分支（x86）改 hook 内部 `TVPCreateStream`（KiriKiri2 不向插件导出它，地址取自内部 `TVPCreateIStream` 函数体首个通过模块范围 / 可执行 / 序言校验的 call）。它返回的是 BCB C++ 对象 `tTJSBinaryStream`，MSVC 不能安全调其 vtable，所以命中语音名且为只读开流（`flags & 0x0f == TJS_BS_READ`，写模式重开会截断存档）时，经**未 hook 的**内部 `TVPCreateIStream` 同名同 flags 重开一次、在标准 COM IStream 上读字节后 `Release`；重开会再走进 detour，线程局部闩挡住递归。两函数都是 BCB 寄存器约定（eax=name，edx=flags，返回 eax），经 naked 适配块转 `__stdcall`；原函数在任何 SEH 之外调用、本帧无析构对象，引擎自己的异常照常传播（BUG-2144）。x64 仍是导入桩 hook。指令长度解码挪到纯头 `native/galgame_hook/hook/x86_insn_len.h` 并补 `0x66` 操作数宽度。新增纯函数 `native/galgame_hook/include/kirikiri_tcwf.h`（TCWF → PCM WAV：MS ADPCM 主信号 + IMA ADPCM 误差层 + 峰值修正，按公开标准表自写），入队门放行 TCWF 魔数，worker 落盘前解码、`.tcw` 换成 `.wav`；名字粗筛补 `.tcw`。真机验证见下方备注。
- **[x] ② 已加自动化测试** — `native/galgame_hook/tests/kirikiri_tcwf_test.cpp`（手算期望值的 MS / IMA / 峰值三层、预测系数、立体声交错、按实际字节截断、魔数 / 声道 / 码流长度 / 失步 / 峰值越界 / 输出区不足全部拒绝）；`native/galgame_hook/tests/x86_insn_len_test.cpp`（`0x66` 下 C7/B8/81/3D/68 取 imm16、段前缀不改宽度、moffs 不受 `0x66` 影响；BCB try 帧形状函数体里跳过立即数中的 E8 诱饵找到首个 call、校验拒绝时取下一个、窗口截断 / 未知指令放弃）。变异实测：把 imm 宽度固定为 4，`x86_insn_len_test` 在首条 `66 C7` 断言上变红。x86 / x64 CTest 均过。
- **备注**：真机复测（同一 ceshi 样本、原始启动路径、x86 新 hook DLL）：`decdiag=0x02af0141`，`0x40000` 亮起（detour 触发）；Saber 的台词配对 `matched/game_resource`（`prg01_sav_0000.wav` 4.72 s、峰值 29180，按 TCWF 解码后落盘）；accept4 对「召喚に従い参上した。」文本 / 音频（`prg01_sav_0010.wav`）/ 查词 / 不推进 / 关卡不推进 / 再查全部 PASS，卡片带句子、句子音频与片段封面。剩余缺口见 BUG-2888（掐断用的 mute.wav 被配给旁白）。
