## BUG-5602 · 视频库页 initState 半途抛错后，后台自动刮削在停用的元素上读 ref
- **报告**：2026-11-28（代理在写视频库页 widget 测试 `home_video_lazy_series_test.dart` 时观察到 `_maybeAutoScrape` 的 `isEnabled` 闭包触发「Looking up a deactivated widget's ancestor is unsafe」）
- **真实性**：✅ 真 bug，但触发条件不是「页面正常卸载」——正常卸载时 `dispose` 会调 `_autoScrape?.dispose()` 置 `_disposed`，sweep 的每个异步缝隙都查它，`_maybeAutoScrape` 也在库查询后查 `mounted`，这条路是安全的。真正的触发是 **initState 半途抛错**：Flutter `Element.inflateWidget` 在 mount 失败时走 `_deactivateFailedChildSilently`，把元素停用却永远不 unmount，State 的 `dispose` 不会被调用、`mounted` 一直是 true。`fushi/lib/src/pages/implementations/home_video_page.dart` 的 `initState`（修复前 :1068–:1081）在同步装配的前半段就起了 `_listForShelf` / `_loadRemoteVideos` / `_maybeAutoScrape` 等后台任务，随后 :1127 `prefsRepo.addListener` 抛错；这些孤儿任务既不会被 `dispose` 停掉，`mounted` 闸门也挡不住，`_maybeAutoScrape` 的 `isEnabled: () => ref.read(appProvider).videoAutoScrape`（修复前 :5996）在停用的元素上 `ProviderScope.containerOf` 即断言；`_loadRemoteVideos` 同样在停用元素上读 ref（日志「remote video list failed … deactivated widget」）。`_scraperService`（修复前 :5981）作为自动刮削服务的工厂也是同一模式：后台服务比任何一帧都活得长，闭包却依赖元素仍挂在树上。
- **[x] ① 已修复** — ⑴ 首帧取数与全部后台任务收进 `_startBackgroundWork()`，在 initState 的同步装配全部完成后、作为最后一步调用：走到这一步 = 装配成功、本 State 保证有配对的 `dispose`，「任务随页面 dispose 停」的前提才成立；initState 半途抛错时一个后台任务都不起。⑵ 自动刮削服务的两个闭包（总闸 `isEnabled`、`_scraperService` 工厂）改读挂载时缓存的 `appModelNoUpdate`（与 `ref.read(appProvider)` 同一实例，`appProvider` 不会重建），不再在异步缝隙里去元素树上找 ProviderScope。没有用 `mounted` 挡：孤儿 State 的 `mounted` 恰恰是 true，挡不住。
- **[x] ② 已加自动化测试** — `fushi/test/pages/home_video_failed_mount_background_work_test.dart`：库里放一本兼容导入的本地视频，给页面传一个一挂监听就抛错的 `libraryRefreshSignal` 让 initState 半途抛错，断言抛的正是这个错，再推进 7 秒让后台任务走完，断言没有任何后续异常。修复前红（异步区抛出 `_maybeAutoScrape.<anonymous closure>` → `ConsumerStatefulElement.read` 的 deactivated 断言），修复后绿。
- **备注**：initState 已挂上的流订阅 / 监听在半途抛错时同样不会被 dispose 取消，它们的回调若在孤儿 State 上读 ref 仍会撞同一断言（本次未逐条核实，只在初始化之后触发、比首帧后台任务难撞得多）；彻底做法需要 initState 失败时回滚已挂的订阅，属于全页面通用的装配模式问题，本次不展开。观察到此问题的那条测试里 initState 抛错本身来自测试先 dispose 了偏好仓库再重挂页面，是测试侧的问题。
