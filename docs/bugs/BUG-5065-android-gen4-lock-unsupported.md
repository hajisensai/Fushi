## BUG-5065 · Android 上 gen4 换代锁永远拿不到，复习库打不开（`try_lock() not supported`）
- **报告**：2026-11-21（外部 PR #3984，@zymy8848：Android 打开复习库 / 桌面小组件 `WidgetSnapshotSource` 时报 `SrsCoreException(-1): gen4 lock: lock /data/user/0/app.fushi.reader/files/srs.gen.lock: try_lock() not supported`）
- **真实性**：✅ 真 bug。`native/fushi_fsrs/src/store/gen4/files.rs:86`（修复前）的 `GenLock::try_acquire` 直接调 `std::fs::File::try_lock()`；Rust 1.95.0 标准库 `library/std/src/sys/fs/unix.rs` 里 flock 实现的 `#[cfg(any(...))]` 只列 freebsd / fuchsia / hurd / linux / netbsd / openbsd / cygwin / illumos / aix / apple，**没有 `target_os = "android"`**，Android 落到返回 `ErrorKind::Unsupported("try_lock() not supported")` 的桩上，于是 `try_acquire` 恒返回 `Err`。`open_gen4`（`files.rs:158` / `:184`）、迁移（`migrate.rs:361` / `:562`）、封存（`retained.rs:231`）全经这把锁，Android 上复习模块整个打不开。CI 的 `native-fsrs-gate` Android job 只编译不跑测试，所以一直没暴露。
- **[x] ① 已修复** — 基于 #3984（@zymy8848）的提交：`try_lock_exclusive` 在 `cfg(unix)`（含 Android）直接调 `libc::flock(fd, LOCK_EX | LOCK_NB)`（`EINTR` 重试、`EWOULDBLOCK` = 已被持有），`cfg(not(unix))`（Windows）仍走 `File::try_lock` / `LockFileEx`。Linux / macOS 上标准库本来就是 `flock`，语义不变；跨进程互斥、同进程另开句柄互斥、drop / 进程退出释放与原 `GenLock` 一致。`libc` 已是 `cfg(unix)` 依赖，不加新依赖。
- **[x] ② 已增加自动化测试** — `store/gen4/files.rs`：`unix_lock_never_goes_through_std_file_locking`（源码守卫：生产代码里标准库文件锁只许出现在 `cfg(not(unix))` 分支，`cfg(unix)` 分支必须调 `libc::flock`；把生产代码换回修复前的版本即红）；`unix_lock_is_a_real_flock`（`cfg(unix)`：GenLock 持有时另一个描述符的裸 `flock` 被挡、释放后能拿到——Linux / macOS CI 跑的就是 Android 上那段 `cfg(unix)` 代码）。原有 `the_lock_excludes_a_second_handle_until_released` / `the_lock_excludes_another_process` 在 Unix CI 上也改为经新分支跑。
- **验证**：Windows `cargo test --profile quick --lib gen4::files` 退出码 0、14 passed（`unix_lock_is_a_real_flock` 是 `cfg(unix)`，Windows 上不编）；`cargo ndk -t arm64-v8a --platform 24 test --no-run --lib --profile quick` 编过（Android 目标下 `cfg(unix)` 分支与 `unix_lock_is_a_real_flock` 均参与编译）。无 Android 设备，未在真机上跑测试二进制。
- **备注**：标准库其它文件锁 API（`lock` / `lock_shared` / `try_lock_shared`）在 Android 上同样是桩，以后新加文件锁也要走 `libc::flock`。
