## BUG-708 · 公网PIN配对取消后重新配对被host常驻PIN弹窗挡成拒绝
- **报告**：2026-07-10（用户：TODO-1330 三问题之②「失败了我怎么重新配对呢」）
- **真实性**：✅ 真 bug。根因 `hibiki/lib/src/sync/hibiki_server_controller.dart:_promptPairApproval`（旧 develop 起始处 `if (_pairDialogOpen) return false;`）。
  - BUG-617 修复引入「host 点允许后弹窗不关、常驻显示 PIN 等对方 confirm」（`_promptPairApproval` 的 `lingerAfterApprove`/`approvedPhase` 分支）。但该常驻弹窗仍占着 `_pairDialogOpen=true` 直到 client 提交 confirm 或 90s TTL。
  - 公网 PIN 配对被取消 / client 从未 confirm（用户在 client 取消 PIN 输入 = `HibikiPairV2Client.pair` 返回 `'cancelled'`，不发 confirm）时，host 常驻弹窗驻留至 90s TTL；期间用户点「重新配对」→ 新 `/api/pair/v2` → `onPairRequest` → `_promptPairApproval` 开头 `if (_pairDialogOpen) return false` → server `_pairDenied('declined')` → 客户端显示「对端拒绝」。用户无法重新配对，且 host 屏还留着一枚已作废的旧 PIN，正是用户报的「失败了怎么重新配对」。
  - 与 Problem ①（LAN 测试连接）/③（令牌两端不同）区分：①的 testConnection 带指纹路径与③的 per-peer token≠共享 token 经 `interconnect_lan_pair_to_testconnection_e2e_test` 端到端证明在当前 develop 已通/属设计；本 bug 是 BUG-617 常驻弹窗自身引入的并发缺陷。
- **[x] ① 已修复** — commit：见 TODO-1330 提交。`hibiki_server_controller.dart`：区分「审批未决」与「已允许后常驻显示 PIN」两态（新增 `_pairDialogLingering`）。`_promptPairApproval` 开头：若当前弹窗只是常驻显示 PIN（`_pairDialogOpen && _pairDialogLingering`），先经 `_pendingPairPinDismiss` 收起它、`await` 其 teardown（`_pairDialogClosed` 信号）再继续，并恢复本会话刚生成、被旧 teardown 清空的 `_pendingPairPin`，杜绝新旧弹窗争用共享单值态；仍处「审批未决」的弹窗才继续拒绝新请求（防恶意叠弹审批）。`onAllow` 进入常驻阶段时置 `_pairDialogLingering=true`；`whenComplete` 复位并放行等待中的新请求。
- **[x] ② 已加自动化测试** — `hibiki/test/sync/interconnect_repair_lingering_dialog_test.dart`（widget 行为测试）：批准第一次配对→弹窗常驻显示 PIN 482913→不 confirm→发起第二次配对，断言弹出**新审批弹窗显示新 PIN 771122**、旧 482913 已收起、second 审批返回 true。已验证禁用修复分支时该测试失败（Found 0 widgets with text 771122），修复后通过。另 `interconnect_lan_pair_to_testconnection_e2e_test.dart` 端到端钉住 Problem ①/③（LAN 配对→per-peer token≠共享→带指纹测试连接成功）。
- **备注**：真正的双设备端到端（Windows host + 手机 client，LAN + 公网 PIN）需真机复验；核心并发时序 + testConnection/per-peer token 逻辑已离屏行为测试覆盖。「不重新输入 PIN 即重配」无法满足——PIN 一次性消费（安全设计），每次重配必生成新 PIN 需重输；本 bug 修的是「重配被静默拒绝」而非「免输 PIN」。
