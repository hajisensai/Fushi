## BUG-4893 · 吉祥物光晕开着冷启动：启动期 idle 任务让调度器空转，Windows 鼠标键盘全失灵
- **报告**：2026-11-16（所有者本机，安装版 3.3.0-debug.27582，Windows 11 Insider build 29704，4K 144 Hz。原话：「安装版 fushi 升级后打开无法操作界面打不开，而且 gpu 占的很高」）
- **真实性**：✅ 真 bug，BUG-4387 的同型复发。现象：主窗口正常出帧（首页内容都在），鼠标键盘全部无反应；进程 4 s 烧 6.8 s CPU，GPU 3D 引擎 20.7%。升级后连开三次都中招。
  - 根因一（直接）：`fushi/lib/src/utils/components/mascot_glow.dart:85` 的呼吸光晕是永不停止的 `repeat` 装饰动画，却用普通 `TickerProviderStateMixin`，没登记成 BUG-4387 的 ambient ticker。系统悬浮球开着（`floating_ball.system = true`）时它从启动就挂着帧回调，`ambientAwareSchedulingStrategy` 把它算成真实动画，`fushi/lib/main.dart:782`（内存首采样）与 `fushi/lib/main.dart:934`（WebView 预热）两个 `Priority.idle` 任务永远不放行。
  - 根因二（结构）：BUG-4387 只改了「什么算忙」，没改「怎么等」。`SchedulerBinding.scheduleTask` 在策略不放行时 `_runTasks` 用 `Timer.run` 零延迟重排自己，Windows 嵌入层每圈 `PostMessage(WM_NULL)`，`GetMessage` 先取 posted 消息，输入永远排不上。于是漏登记一个常驻动画、或者任何一个真实动画跑得久，都是整窗输入失灵。`ambient_ticker_test.dart` 当时的注释就写着「忙的情形不能真把 idle 任务排进去，会无限循环」。
  - 为什么是「升级后」：`preferences` 表里 `theme_mascot_glow = true` 的 `updated_at` 是 2026-11-15 22:21，开关是在上一版（27417）运行中打开的，那时两个 idle 任务早已执行完；27417 与 27582 的相关代码相同，19:10 的升级只是带来了开着光晕的第一次冷启动。
  - 证据：对卡住的实例（PID 23652）只读取证。会话标记的帧诊断每 30 s 约 4300 帧、`build=0`、要帧方全部是 `_MascotGlowState._syncBreath@mascot_glow.dart:142`；线程 CPU 4 s 内 UI 线程 3.97 s（99.2%）；用本机引擎 PDB 符号化小型转储，平台线程在 `TaskRunnerWindow::WndProc → ProcessTasks → FlutterEngineRunTask → IsolateMessageHandler::HandleMessage`；沿帧指针链回溯 Dart AOT 栈 250 次，约 120 次是同一条链，反汇编后按对象池常量认出循环体引用闭包 `_runTasks` 并调到带 `Timer interface not supported.` 的 `Timer._createTimer`，即 `_runTasks → _ensureEventLoopCallback → Timer.run`。
- **[x] ① 已修复** — `_MascotGlowState` 改用 `AmbientTickerProviderStateMixin`；`ambient_ticker.dart` 新增 `hasRealAnimations` 与 `waitForUiIdle`（忙时只挂一个帧后回调、下一帧再看，等待期间不往事件循环投任何东西；完成在独立一轮事件循环里且那一刻仍空闲），`main.dart` 两处等空闲改用它，`lib` 下不再有 `scheduleTask` 调用。以后再漏登记常驻动画，后果只是启动期空闲工作推迟，不再饿死输入。
- **[x] ② 已加自动化测试** — `fushi/test/utils/scheduling/ambient_ticker_test.dart`（假调度器 + FakeAsync：忙 200 帧期间定时器数恒为 0、帧后回调恒为 1；空闲不同步完成；完成前又起动画接着等；真 binding 下真实动画撤掉后完成、只有装饰动画时照常完成）、`fushi/test/utils/components/mascot_glow_test.dart`（光晕呼吸登记为 ambient、不算真实动画、等空闲照常完成、换忙碌档仍是 ambient）、`fushi/test/build/ui_idle_wait_guard_test.dart`（目录枚举守卫：`lib` + `packages/*/lib` 禁调 `scheduleTask`；每个 `.repeat(` 文件必须归类为 ambient 或写明跟着什么状态停，清单不许有陈旧条目）。
- **备注**：
  - 未在真机上用修复后的构建复测原始失败路径（需要带光晕偏好的数据根 + Windows Release 构建）；卡住实例上的取证与 widget 层测试覆盖了机制，合入后的调试版要在本机开着光晕冷启动确认一次。
  - 2026-11-21 收敛（拍板台 pr3569）：本条并入 develop 时，BUG-4725 的 `FramePacedTaskScheduler` 已在 binding 层根治「怎么等」（推迟时按帧重查，不零延迟空转），上面「根因二」说的 `scheduleTask` 空转在生产 binding 下已不成立，两套等待并存。收敛为只留 binding 层一套：`waitForUiIdle` 改成往调度器排一个 idle 空任务（不再自带帧后回调循环），守卫的「`lib` 禁调 `scheduleTask`」换成「`lib` 禁调裸 `WidgetsFlutterBinding.ensureInitialized()`」，并补上原先覆盖不到的入口——悬浮查词 / 弹窗 / 副屏三个副引擎改用 `FushiSecondaryWidgetsFlutterBinding`。光晕登记 ambient 与 `.repeat(` 归类守卫保留。integration_test 的 binding 不混入该 mixin，集成测试里忙时等空闲仍是框架原行为（只影响测试进程）。
  - GPU 占用本条不处理（已由 BUG-4961 处理）：光晕开着时主窗口按 144 Hz 持续出帧，60 px 的呼吸带着整个 4K 主窗口每帧重新合成（raster 线程约 47%、GPU 约 20%）。修复后输入恢复、UI 线程不再空转，但只要光晕开着这部分成本还在；与 BUG-4387 备注里的「主页常驻背景动效每帧成本」是同一类性能问题。
  - Windows 引擎只上报高对比度（`flutter_windows_engine.cc` 的 `SendAccessibilityFeatures`），系统「动画效果」开关到不了 `MediaQuery.disableAnimations`，所以关系统动画不能当临时规避。
