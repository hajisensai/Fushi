## BUG-2119 · 视频页 Esc/返回退不出去：写语句 SQLITE_BUSY 后未 reset 毒化整条连接，退出被落库绑架
- **报告**：2026-09-04（用户：「esc退不出去了」「手动也退不出去了」，Windows 2.2.4-beta.13362，窗口模式播放中，Esc / 顶栏返回箭头均无反应）
- **真实性**：✅ 真 bug。两层根因，都沿真实代码路径 + 生产实例现场证据钉死：
  1. **连接毒化**（依赖层）：sqlite3 3.3.3 的 `StatementImplementation._execute()` / `_selectResults()` 在 `sqlite3_step` 返回非 DONE/ROW 时**直接抛错、不 `sqlite3_reset`**；drift 2.33 `Sqlite3Delegate._returnStatement` 对缓存语句什么都不做（`drift/src/sqlite3/database.dart:196`），只有同一 SQL 再次执行才会 reset。一条写语句在 `OP_Transaction` 拿到 `SQLITE_BUSY` 类返回码（含 517 `BUSY_SNAPSHOT`）时 VM 是**挂起而非停机**（`vdbe.c` 里 `(rc&0xff)==SQLITE_BUSY` → `goto vdbe_return`），仍计入 `db->nVdbeWrite`。此后本连接每一次 COMMIT 都命中 `OP_AutoCommit` 的 `nVdbeWrite>0` 检查抛「cannot commit transaction - SQL statements in progress」，autocommit 写入永不落盘，而读一切正常（同连接看得见自己的未提交写）。生产实例现场：`fushi.db-wal` 按句柄读的真实 mtime 冻在 13:43:19，WAL-index 提交计数一小时零变化；`C:\Users\wrds\Documents\error_log.txt` 每 5 秒一条上述异常（栈：下载流水线 `_drain` → `claimNextVideoDownloadJob` 事务 COMMIT），14:39 起另有 7 条 `UPDATE video_books … (code 517)`。触发那条 BUSY 的是同一时段另一个进程（本机另一 agent 的「隔离」Fushi 实例，其启动脚本自注「APPDATA 环境变量隔离无效」）与生产实例共享同一个 `fushi.db`；第一现场被 `VideoDownloadLeaseGuard._renewOnce` 的 `on Object {}` 静默吞掉。
  2. **退出被绑架**（页面层）：`video_fushi_page.dart` `_handleBackOrExit` 是 Esc / 返回箭头 / 手柄 B / 系统返回四条通道的唯一汇聚点，此前 `await _controller?.flushPosition(); if (mounted) nav.pop();`——`flushPosition` → `_persistPosition` → `setPref`（事务）COMMIT 抛错 / `updatePosition` 抛 517 → 异常在 `nav.pop()` 之前冒出，四条通道一起失灵，用户被锁在视频页里。
- **[x] ① 已修复** — (a) `pubspec.lock` sqlite3 3.3.3 → 3.5.2（上游 3.4.0 起「Reset statements after `execute` and `select`」），`fushi/pubspec.yaml` 与 `packages/fushi_core/pubspec.yaml` 约束抬到 `>=3.4.0 <4.0.0` 防锁文件漂回；(b) 新增退出原语 `fushi/lib/src/media/video/video_exit_flush.dart` `exitAfterPersist`：同步发起落库、无条件 pop，落库失败只记 `ErrorLogService`，`_handleBackOrExit` 改走它；(c) `VideoDownloadLeaseGuard._renewOnce` 续期异常记 `ErrorLogService`（语义仍按租约丢失处理）。提交见本分支。
- **[x] ② 已加自动化测试** — `packages/fushi_core/test/bug2119_busy_statement_reset_test.dart`（真库 + 真第二连接 `BEGIN IMMEDIATE` 让写语句撞 BUSY，随后 `setPref` 事务必须 COMMIT 成功且跨连接可见；变异实测：锁文件翻回 3.3.3 时在 `COMMIT TRANSACTION` 抛与生产日志逐字相同的异常）；`fushi/test/media/video/video_exit_flush_test.dart`（落库挂死 / 同步抛 / 异步抛 / 成功四态下 exit 恰好一次）；`fushi/test/pages/video_exit_never_awaits_persist_guard_test.dart`（源码守卫：`_handleBackOrExit` 只经 `exitAfterPersist` 退出、不得 `await`）。
- **备注**：已在跑的实例无法自愈（挂起的 VM 只有进程重启或同一 SQL 再执行才会 reset），用户侧只能重启 app；13:43 之后的进度/下载状态本就没落盘。同一 DB 被两个进程共享是触发条件，不是本 bug 的根因——单进程下任何一次 5 秒写锁争用（备份、外部 SQLite 工具）都能触发同一条链。子代理顺带扫出的隐患另记：`video_scrape_cleanup_service.dart:186` 事务内做全库文件哈希/搬移；`_drain` 的 `await _process(job)` 无上界；Jimaku / Ajatt 字幕搜索无响应超时（同 BUG-2079 形态）。
