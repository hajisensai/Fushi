## BUG-1917 · Windows 拖边缩放帧率低：首页仪表盘每步重画整张热力图
- **报告**：2026-08-28（用户：「窗口拖动帧率很低」，追问后澄清「拖动指的是缩放 app 大小，上下左右缩放」；与 BUG-1916 同批）
- **真实性**：✅ 真 bug（app 侧可修的那一半）。根因 `fushi/lib/src/utils/components/stat_contribution_heatmap.dart:56`（`StatHeatmapModel` / `StatHeatmapCell` 只有身份相等）+ 同文件 `_HeatmapPainter.shouldRepaint` 的 `old.model != model`：桌面拖边缩放时 `StatContributionHeatmap` 的 `LayoutBuilder` 每步都重跑 `buildStatHeatmap` 造新对象 → `shouldRepaint` 永远为真 → `RepaintBoundary` 缓存层每步作废，一年 53×7=364 格 × (填充 + 空格描边) 全部重画。实测（2026-08-29，当前 develop Release 隔离实例，真仪表盘，窗口 2850×1545 物理像素，`--trace-skia` 时间线）：每步一帧里 raster 线程 `GPURasterizer::Draw` **9.7ms**，其中 `SkCanvas::drawRRect` **894 次/帧**（`CircularRRectOp` 320 批），（`drawRRect` 事件合计 3.4ms 是 4 帧累计，每帧 ~0.85ms——见①的修正）；UI 线程 LAYOUT 3.6ms / BUILD 0.3ms / PAINT 0.6ms。整体每步 `WM_SIZE` 周期 p50 **13.9ms → 72 步/s**，而同尺寸 `flutter create` hello-world 是 10ms → 98~105 步/s、空 Win32 原生窗口 8ms → 119~125 步/s（125Hz 鼠标下跟手 1:1）。
- **[x] ① 已修复** — 见 PR #1036 本提交，两层：a) `StatHeatmapCell` / `StatHeatmapModel` 改为值语义相等（内容没变就是相等，`shouldRepaint` 不再恒真，Dart 侧 PAINT 0.62→0.25ms）；b) **只做 a 不够**——修后时间线 `drawRRect` 仍 879 次/帧、raster 9.3ms 纹丝不动：`RepaintBoundary` 保留的只是 picture，raster 线程每帧照样逐 op 回放，这版引擎（Flutter 3.44 / Skia Ganesh）不把它缓存成纹理。所以 `_HeatmapPainter.paint` 改成按等级把格子 `addRRect` 进一条 `Path` 一次 `drawPath`（5 等级 + 1 空格描边 + 选中框 ≤ 7 个 op，几何不变），不加防抖、不加「缩放中跳过」特例。修复后同一测法：仪表盘 **77~79 步/s、步间 p50 13.0~13.2ms**（修前 72 步/s、13.8ms），raster 8.7→7.5~8.0ms/帧；时间线复核 `drawRRect` 从 879 次/帧降到 0（op 计数守卫）。收益有限是因为最初把时间线里 `drawRRect` 的「3.4ms」误读成单帧——那是 4 帧合计（~0.85ms/帧），raster 的真正大头是 `FlutterCompositorPresentLayers`（每帧 p50 6.7~7.1ms，swapchain 重建 + present，引擎侧，hello-world 同样承担）；UI 线程 LAYOUT ~4ms 经 CPU 采样是 `_RenderLayoutBuilder.performLayout` 18.5%（仪表盘与热力图的 `LayoutBuilder` 每步在布局期重建子树，响应式布局固有）+ `buildStatHeatmap`/`DateTime` ~10%（≈0.4ms，不值得加缓存）。
- **[x] ② 已加自动化测试** — `fushi/test/widgets/stat_contribution_heatmap_repaint_test.dart`：① 模型值相等三条单测（同输入相等 / 改一天值不等 / 改周数不等）；② op 计数守卫——一年 371 个真实日全有值时用 `paints..everything` 数 canvas 调用，`drawPath` 1..6 次、`drawRRect` 0 次（变异：改回逐格 `drawRRect` → Actual 371，红）；③ widget 守卫——宿主重建（换底色 + 宽度 600→605 列数不变）后只推进到「构建 + 布局」，断言网格 `RenderCustomPaint.debugNeedsPaint == false`，真改一天值则必须为 true。变异实测：把 `==` 改回身份比较，单测与 widget 守卫同时红（第一版守卫用 `RenderRepaintBoundary.debugSymmetricPaintCount` 在变异下照样绿——`flushPaint` 按深度先单独画边界层，父级再合成干净层时不计数——已换成直接量 `debugNeedsPaint`）。
- **备注**：
  - **探针陷阱（本轮三次误判）**：a) 探针采样线程 `Thread.Sleep(1)` 在未 `timeBeginPeriod(1)` 的进程里是 15.6ms，之前「缩放 22~31 次/s、拖动 65 次/s」全是采样伪像；b) 探针边采样边 BitBlt 数色会把采样堵到 30~40ms；c) 注入鼠标的循环同样受 15.6ms 粒度影响（8ms 档实际是每 15.6ms 两下）。可信测法 = `SetWinEventHook(EVENT_OBJECT_LOCATIONCHANGE)` 事件驱动 + 探针进程 `timeBeginPeriod(1)`，所有被测窗口先 `SetWindowPos` 到同一尺寸（raster 成本随像素面积走，不同尺寸不能互比），并截图确认页面（新 test root 起来是新手引导页，不是仪表盘）。
  - 剩余差距（修后 vs hello-world）属于页面本身的 LAYOUT（~3.6ms，整页文本/卡片重排）与 Flutter Windows 同步缩放的固有成本（hello-world 也只有 ~10ms/步），不在本 bug 范围；老 8 月 16 日包在同页上是 68~79 步/s 且双峰（p90 21~25ms、最大 36ms），develop 已无那类周期性卡顿。
  - 集成测试 harness（`IntegrationTestWidgetsFlutterBinding`）下缩放只有 8.8 步/s，是 harness 掌管帧节奏所致，不能用它测缩放节奏；视频页在隔离实例下 argv 不开（被引导页拦），阅读器/视频页缩放本轮未测。
