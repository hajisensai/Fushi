## BUG-4957 · TTS 朗读 / 多文件有声书建 ConcatenatingAudioSource 时 just_audio 默认 ShuffleOrder 逐个随机 List.insert，O(n²) 占满主线程到 ANR
- **报告**：2026-11-17（应用内自动闪退报告 `NJ9sFIcvve`：3.3.0+1002443602，OnePlus PLQ110 / Android SDK 37；进程启动 32 秒后 `Input dispatching timed out`，主线程 state=R、utm=1198 约 12 秒 CPU，栈全是 base.apk 内未符号化原生帧，BuildId `8193417a9f73648902f85bce92fd705e`；上一轮运行有 `TtsFailure(cancelled)`）
- **真实性**：✅ 真 bug。符号化过程：v3.3.0 release 的 `fushi-3.3.0-arm64-v8a.apk` 里 apk 偏移 0x664000 正是 `lib/arm64-v8a/libapp.so`，BuildId 与报告一致；本机在同一提交 `a2638e0`、同一 Flutter 3.47.6 上 `flutter assemble android_aot_bundle_release_android-arm64` 出未 strip 的 `app.so`（带 `.symtab`），把手机上的返回地址前后指令按窗口（屏蔽 BL/ADRP/PP 偏移等立即数）在本地 `app.so` 里匹配后取符号，前 13 帧：`List.insert+0x168` ← `DefaultShuffleOrder.insert+0x1d0` ← `new ConcatenatingAudioSource+0xb8` ← `AudiobookPlayerController.load+0x380` ← `_SuspendState` 异步续体（`_rootRunUnary` / `_Future._propagateToListeners` …）。根因：`fushi/lib/src/media/audiobook/audiobook_controller.dart:1253`（TTS 朗读分支，另两处 `:1282` 多文件、`:1854` 换声音同理）直接 `ConcatenatingAudioSource(children: …)`，just_audio 0.9.42 构造时 `shuffleOrder.insert(0, children.length)`，默认 `DefaultShuffleOrder.insert`（`just_audio.dart:3506`）对每个新下标做一次随机位置的 `List.insert`，整体 O(n²)。TTS 朗读每句一个流式源，长篇小说十几万句，这一步在 Android 合并平台 / UI 线程上算十几秒，触摸 5 秒无响应即 ANR。播放器从不开随机播放，这份随机顺序只在 `setAudioSource` 里算一遍、不被使用。
- **[x] ① 已修复**（见本分支提交）— 新增 `fushi/lib/src/media/audiobook/linear_shuffle_order.dart`：`LinearShuffleOrder` 与默认实现同语义（插入位置均匀随机、`shuffle` 把当前项放队首），但 `insert` 用选择抽样一趟重建、`removeRange` 一趟过滤，都是 O(n + count)；`concatenateAudiobookSources` 是建多源播放列表的唯一入口，`audiobook_controller.dart` 三处都改走它。
- **[x] ② 已加自动化测试** — `fushi/test/media/audiobook/linear_shuffle_order_test.dart`：插入 / 中间插入保持原序并后移 / removeRange / shuffle 队首语义；二十万句一次 `insert` 用 Stopwatch 断言 < 3 秒（计算是同步的，test `Timeout` 打断不了，最初用 Timeout 写的版本变异后照样绿、只是跑了 578 秒，已改成量耗时；变异实测：把 `insert` 换回逐个随机 `List.insert` 后该用例红）；源码扫描守卫 `lib/` 里除入口文件外不得直接构造 `ConcatenatingAudioSource`。
- **备注**：未在真机上复测修复后的包（要等 CI 出包）。同栈下 just_audio 还会把每个子源 `_toMessage()` 发给平台层，属 O(n)，不在本栈上。
