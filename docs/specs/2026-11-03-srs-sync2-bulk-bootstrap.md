# SRS 同步 v2：新设备批量收段通道（bulk bootstrap）

> 状态：方案稿（2026-11-03），待拍板 §7。
> 前置：`docs/specs/2026-10-25-srs-sync-v2-design.md`（下称「v2 设计」）；BUG-3993（新设备收段慢，分支 `pr/srs-ingest-defer-cache-refresh`）。
> 约束不变：不引入快照、不新增信任路径、本机持有每台设备从 seq 1 起的完整前缀（v2 设计 §7.1）。

## 1. 问题

真实库（1.5 万笔记 / 4.5 万卡 / 30 万复习）新设备首次收齐：Xiaomi Pad 5 约 44 分钟，桌面 release 13.6 分钟。
同一份数据用 Anki 整库下载是几十秒的量级。目标：**新设备收齐 ≈ 下载时间 + 几十秒**。

## 2. 实测（桌面 release，同一份真实同步文件夹，交替运行）

数据：57 段 / 74 MB，683,706 条操作，载荷解压后 428 MB。
种类：字段修改 315,553、复习日志 303,779、媒体 33,904、实体 15,246、整列表标签 15,027、其它 197。

| 路径 | 耗时 | 每条 |
|---|---|---|
| 生产分片投递（BUG-3993 修复前） | 814 s（投递 706 + 收尾 104） | — |
| 逐条投递一次收完 + 全量重建缓存 | 530 s（486 + 44） | 0.71 ms |
| 前 6 段（99,788 条）逐条一次收完 | 42.0 / 43.8 s | 0.43 ms |
| 同上，只换执行环境：删摘要 / 学习 / 浏览触发器、`synchronous=OFF`、大页缓存，收完一次重建摘要 | 29.5 / 29.6 s | 0.30 ms |
| **批量下限**（全量）：验签解码 3.1 + 解析 0.75 + 生产的 `edit_row`/`log_row` 5.5 + 按实体一次 `land_stored` 2.1 + 有序批量写 8.5 | **≈ 20 s** | 0.03 ms |

探针：`native/fushi_fsrs/src/store/sync2/bootstrap_probe.rs`（`probe_fold_floor` / `probe_oneshot_env`，`#[ignore]`）。
平板 / 桌面耗时比约 3.2（44 min / 13.6 min），批量下限换到平板约 60–70 s。

几条由数据得出的事实：
- **传输、验签、解码不是瓶颈**：全部段验签 + 解压 + 解码 3 s。
- **瓶颈是逐条增量投影的常数**：一条字段修改要十几条 SQL（`sync2_ops` / `sync2_edit_ops` / `sync2_ent_ops` 插入、清除与挂起判定、读同实体现存行、
  删被支配行、`srs_edit_pack` 插入、`srs_event_local`）加约五遍 JSON 序列化 / 解析，外加摘要与浏览触发器逐行维护。只换执行环境省约三成，
  逻辑本身仍是 0.27 ms/条，且随库变大上涨（随机键 B 树、回读）。BUG-3993 的分片修复只能把 814 s 往 530 s 那条线上压。
- **正文几乎都是现存值，不是旧历史**：31.5 万条字段修改按实体折叠后仍存活 31.5 万条（2.35 万实体，笔记平均约 24 KB 释义 HTML）。
  压缩 / 跳过旧历史不会有收益，写入量要靠「正文只存一份」降（§4.3）。
- 取段与收段严格交替（`srsFetchInBatches`：消费方收完才开下一批），网络与计算不重叠。

## 3. 方案总览

新设备（及后续：大量追赶）不再走逐条增量投影，改走**同一批已验证的操作、同一套纯函数语义、不同的执行策略**：
先把操作全部按 `(device, seq)` 追加进操作日志，再按实体一次性折叠出最终投影，主键有序批量写，最后一次性建索引、算摘要、重放、建缓存。

不变的东西：段格式、验签与链校验、`sync2_ops` 完整前缀、操作语义、摘要定义。变的只是「投影怎么算出来」。

## 4. 设计

### 4.1 触发条件

- 第一期：本 profile 投影为空（只有身份 / 本机操作为零）且待收操作 ≥ 1 万条。覆盖新设备、重装、清数据后重连。
- 第二期：待收 ≥ 5 万条且 ≥ 本机已有操作的 2 倍（长期离线设备）。此时先把被触及实体的现存寄存器读进内存再一起折叠。
- 其余情况照旧走逐条投递（日常同步一轮几十上百条，逐条路径毫秒级，不需要改）。

### 4.2 流程（全在 Rust 内核，一条粗粒度命令 + 进度事件）

1. **下载与解码交叠**：Dart 端 `srsFetchInBatches` 改为双缓冲预取（收第 n 批时下载第 n+1 批，内存多一批 8 MB）。内核流式验签解码，
   操作原样追加进 `sync2_ops`（本来就按 `(profile, device, seq)` 有序，B 树尾部追加）；转发留原段（`relay::keep`）照旧。
2. **分区**：按 `sync2_ent_ops` 同样的「实体」划分。实体上有 `deleted` 写入或 `Purge` 的，连同经卡↔笔记、移入牌组关联到的实体，
   归入「复杂集」；其余归入「简单集」（本数据集几乎全部）。
3. **简单集一次折叠**：每个实体按因果序把全部修改喂给 `registers::land_stored(items, 0)`（与逐条到达结果相同：`land` 本来就支持一批依次到达），
   标签 OR-Set、媒体 MVR、LWW 标量同理按实体一次算；复习日志是只增集合，直接成行。
4. **复杂集走现有逐条路径**（`project` / 挂起 / 清除语义原样复用），在简单集写完之后、同一事务内按因果序投递。
5. **一次写**：单个写事务；写前删投影表二级索引与摘要触发器，主键有序批量插入，写后重建索引、装回触发器；摘要 `digest::rebuild` 一次算
   （摘要是按桶的可加和，一次算与逐行维护逐位相同）。`srs_event_local` / `sync2_edit_ops` / `sync2_log_meta` / `sync2_ent_ops` 同样有序批量写。
6. **重放与缓存**：受影响卡一次全量 FSRS 重放（v2 设计 §4.2：百万步亚秒级）；缓存行直接用折叠结果生成，不再按卡回读日志
   （现在全量 `rebuild_caches` 一次 44 s）。
7. **崩溃安全**：bootstrap 期间 profile 记 `bootstrapping` 标记。中断后下次打开：丢掉该 profile 的投影表行、保留已落的 `sync2_ops`，从步骤 2 重来，不重新下载。
   期间 UI 显示进度，不提供复习（新设备本来没有可复习的东西）。

性能取向：`edit_row` 每条都查一次 `legacy_closure`，按 `deps` 去重缓存（`deps` 本来就是驻留的）；JSON 只构造一次。

### 4.3 第二期：写入量瘦身（平板的主要剩余项）

批量下限里写库 8.5 s / 1.1 GB 是最大一项：正文存了两份（`sync2_ops.payload` 解压原文 + `srs_field_edits.jslim`），另有每条操作一行的
`srs_event_local` 等。目标「正文只存一份」：投影行改为引用操作（按 `(device, seq)` 读回载荷），或操作日志改存压缩形态。
这是存储格式改动，要迁移、单独 PR，不阻塞第一期。

### 4.4 预期

| | 现在 | 第一期 | 第二期 |
|---|---|---|---|
| 桌面（不含下载） | 13.6 min | ≈ 20–30 s | ≈ 15 s |
| 平板（含约 1 min 下载，交叠后） | 44 min | ≈ 1.5–2 min | ≈ 1–1.5 min |

平板数字是按 3.2 倍换算的推算，以第一期落地后的真机实测为准。

## 5. 正确性守卫

1. **等价性质测试（Rust，必须先于实现落地）**：随机多设备操作集（含删除、清除、并发字段写、标签增删、媒体、分叉后重签发），
   `bulk(ops)` 与「乱序分批逐条投递」后全部投影表逐行相同、摘要相同。沿用 `tests_cache_pending.rs`「分片收齐与全量重建逐行相同」的范式。
2. **真实数据回归**：用这份 68 万条真实段，批量与逐条两路收完后逐表比对（桌面跑一次，结果写进 PR）。
3. **生产自检与回退**：收完后若有某台设备 head 的 `ack` 等于本机已应用版本向量，比对该 head 的 `digest`；不同 → 丢掉投影、退回逐条路径重算并上报。
   最坏情况就是现在的速度，不会错。

## 6. 对 BUG-3993 在途分支（`pr/srs-ingest-defer-cache-refresh`）的意见

- 五处修复都是真问题（分片刷缓存近平方、还页缓存、整实体回读、`Deferred` 段内平方、每片并回 WAL），A/B 交替测过、测试齐全，**应合**。
  逐条路径在日常同步和第一期之外的追赶里继续用，修好有价值。复核过的两点：窄化查询与 `land` 语义等价（支配只在同字段键比，同 ID 由 `OR f.id` 兜住）；
  `Later` 峰值不超过预算加一段（≤ 16 MB 原文）。
- **它不是追平 Anki 的路线**：逐条一次收完本身就要 0.71 ms/条，分片修复的上限是往 530 s 那条线压，对平板「8–10 分钟」的推算即使达成也差一个数量级。
- 它列的下一项「字段修改落库路径五遍序列化 / 解析」建议**不做**：日常同步一轮几十条，省下的是几毫秒；冷启动由本方案整体绕开。
- 小提醒：缓存刷新推迟到收尾对所有会话生效。正在复习的老设备追赶时，整个会话期间被触及的卡显示收段前的状态、新卡不可见，
  可以接受（多出的复习也是事实，重放会算对），但可考虑只对大会话推迟。srs.db v20 目前只有它占用，没有撞号。

## 7. 待拍板

1. 是否做批量通道第一期（§4.1–4.2，新设备）。
2. 第二期范围：长期离线设备的大量追赶（§4.1）与写入量瘦身（§4.3）是否进计划。
3. 快照方案维持不做（v2 设计 §7.1）。第一期达标就不再考虑；只有实测不达标时，才评估「快照只作加速缓存、后台按日志校验摘要」的变体。
