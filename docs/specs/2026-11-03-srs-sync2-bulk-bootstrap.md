# SRS 同步 v2：新设备批量收段通道（bulk bootstrap）

> 状态：已实现（2026-11-03，所有者拍板「两期都做」）。§3–§4 是落地的设计，§8 是实测；方案稿里与实现不同的地方在 §3.1 说明。
> **实测没达到目标**：全量数据 521 → 414 s（−21%，主要来自新设备长片），批量投影本身在全量上没有可靠收益；追平 Anki 仍需方案稿的独立通道（§8）。
> 前置：`docs/specs/2026-10-25-srs-sync-v2-design.md`（下称「v2 设计」）；BUG-3993（新设备收段慢，分支 `pr/srs-ingest-defer-cache-refresh`）。
> 约束不变：不引入快照、不新增信任路径、本机持有每台设备从 seq 1 起的完整前缀（v2 设计 §7.1）。

## 1. 问题

真实库（1.5 万笔记 / 4.5 万卡 / 30 万复习）新设备首次收齐：Xiaomi Pad 5 约 44 分钟，桌面 release 13.6 分钟。
同一份数据用 Anki 整库下载是几十秒的量级。目标：**新设备收齐 ≈ 下载时间 + 几十秒**。

## 2. 实测（桌面 release，同一份真实同步文件夹，交替运行）

数据：57 段 / 74 MB，683,706 条操作，载荷解压后 428 MB。
种类：字段修改 315,553、复习日志 303,779、媒体 33,904、实体 15,246、整列表标签 15,027、其它 197。

| 路径 | 耗时 | 每条 |
|---|---|---|
| 生产分片投递（BUG-3993 修复前） | 814 s（投递 706 + 收尾 104） | — |
| 逐条投递一次收完 + 全量重建缓存 | 530 s（486 + 44） | 0.71 ms |
| 前 6 段（99,788 条）逐条一次收完 | 42.0 / 43.8 s | 0.43 ms |
| 同上，只换执行环境：删摘要 / 学习 / 浏览触发器、`synchronous=OFF`、大页缓存，收完一次重建摘要 | 29.5 / 29.6 s | 0.30 ms |
| **批量下限**（全量）：验签解码 3.1 + 解析 0.75 + 生产的 `edit_row`/`log_row` 5.5 + 按实体一次 `land_stored` 2.1 + 有序批量写 8.5 | **≈ 20 s** | 0.03 ms |

探针：`native/fushi_fsrs/src/store/sync2/bootstrap_probe.rs`（`probe_fold_floor` / `probe_oneshot_env`，`#[ignore]`）。
平板 / 桌面耗时比约 3.2（44 min / 13.6 min），批量下限换到平板约 60–70 s。

几条由数据得出的事实：
- **传输、验签、解码不是瓶颈**：全部段验签 + 解压 + 解码 3 s。
- **瓶颈是逐条增量投影的常数**：一条字段修改要十几条 SQL（`sync2_ops` / `sync2_edit_ops` / `sync2_ent_ops` 插入、清除与挂起判定、读同实体现存行、
  删被支配行、`srs_edit_pack` 插入、`srs_event_local`）加约五遍 JSON 序列化 / 解析，外加摘要与浏览触发器逐行维护。只换执行环境省约三成，
  逻辑本身仍是 0.27 ms/条，且随库变大上涨（随机键 B 树、回读）。BUG-3993 的分片修复只能把 814 s 往 530 s 那条线上压。
- **正文几乎都是现存值，不是旧历史**：31.5 万条字段修改按实体折叠后仍存活 31.5 万条（2.35 万实体，笔记平均约 24 KB 释义 HTML）。
  压缩 / 跳过旧历史不会有收益，写入量要靠「正文只存一份」降（§4.3）。
- 取段与收段严格交替（`srsFetchInBatches`：消费方收完才开下一批），网络与计算不重叠（已改，§4.4）。

## 3. 方案总览

收段投递不再「一条操作一次增量投影」，而是**同一批已验证的操作、同一套纯函数语义、按窗批量落库**：
字段修改与复习日志攒成一窗（2048 条 / 8 MiB），按寄存器一次 `registers::land_stored`，关掉摘要触发器后批量写，摘要桶增量
自己算、一次并进桶表。其余种类与「不简单」的实体照旧逐条投。

不变的东西：段格式、验签与链校验、`sync2_ops` 完整前缀、操作语义、摘要定义、收段会话（分片、让出、断点续收、收尾重放）。
变的只是「投影怎么写进去」。

### 3.1 与方案稿的差异

方案稿设想一条独立的「新设备 bootstrap」命令（先全部追加操作、再按实体整体折叠、删索引批量写、`bootstrapping` 标记做崩溃恢复）。
落地时改成**在现有投递路径里按窗批量**：

- **不另立状态机**：仍是同一个分片、可让出、可断点续收的收段会话（`transport.rs` `Delivery`），崩溃安全、复习写入让行、`spill` / `resume`
  全部沿用，不需要 `bootstrapping` 标记与「丢投影重来」。
- **大量追赶自动覆盖**（原第二期 §4.1 那半）：批量对每次投递都生效，没有「投影为空」「≥ 1 万条」之类的触发阈值；日常同步一轮几十条，
  窗在片尾（`checkpoint`）冲刷，行为与逐条相同。
- **等价靠构造而不是事后自检**：能攒的只有「结果只取决于同一寄存器现存行」的那几类（§4.1），别的全部先冲再逐条投；随机对拍测试
  逐表逐行比（§5）。方案稿 §5.3 的「收完比对 head 摘要、不同就退回」没有做——它只在恰好有 head 的 ack 等于本机版本向量时才能比，
  而批量与逐条同一套语义，没有需要它兜底的分叉。

**事后看这个取舍错了**（§8）：按窗批量只省掉投影里「读现存行 + 判定 + 触发器」那一截，每条操作的记账、随机键索引写入和每片的提交 /
检查点都还在，全量数据上批量投影本身没有可靠收益。方案稿的独立通道才拿得到 §2 的下限。

## 4. 设计

### 4.1 什么能攒（`store/sync2/bulk.rs`）

- **攒**：实体「简单」（没有过 `deleted` 写入、没被清除）上的普通字段修改（不是 `tags`、不是 `deleted`、不是合成写入者），
  以及卡、笔记都简单的复习日志。它们的投影只看同一 (种类, 实体, 字段键) 的现存行与同 ID 的行，逐条落与「同一寄存器的一批依次到达
  一起交给 `land_stored`」结果相同。记账表（`sync2_edit_ops` / `sync2_ent_ops` / `sync2_log_meta`）照旧当场逐条写。
- **当场投、不冲**：身份记录、媒体、检查点、不认识的种类、简单笔记上的标签操作——它们不读也不写攒着的那几类行。
- **先冲再逐条投**：其余一切（删除、清除、不简单实体上的操作……），投完清掉「简单」判定缓存。

### 4.2 冲刷

0. 投影行（`edit_row`）在**到达时**算：v2 写入的 ctx 并上旧修改记录闭包，闭包读 `sync2_legacy`，攒着还没写回的那几行读内存里的
   （攒的时候在内存里并，与 `note_legacy` 同一算法）。不能挪到冲刷时：那时 `upto` 已被同窗更晚的旧记录推过去，闭包改走逐条读操作日志
   的那一支，遇到已清除的旧记录结果就与逐条投影不同（审查 F1）。
1. 旧修改记录闭包先写回。攒得少于 16 条（多半是「先冲再逐条投」冲出来的零头）就逐条落、不切触发器开关：切开关会让这条连接上全部
   预编译语句失效、下次执行重编译（审查 F2），窗小时得不偿失。冲刷只在操作边界上调用，那时写连接上没有执行中的语句。
2. 按寄存器读现存行。到达的 ID 若已在别的寄存器、或同一窗里两个寄存器撞了 ID（迁移来的同一条旧记录被几台设备各包了一次），
   这几个寄存器整体退回逐条 `land_edit`（按到达顺序，触发器照常）；其余寄存器之间 ID 与行都不相交，先后无关。
3. 关掉主库触发器（`SQLITE_DBCONFIG_ENABLE_TRIGGER`）后按寄存器一次 `land_stored`，删被支配的、插存活的；摘要按触发器同一个行哈希
   记增量（`digest::Deltas`），最后一次 UPSERT 进桶表。TEMP 触发器（复习队列 / 浏览的待重读）照常触发——SQLite 3.35 起这个开关
   不管 TEMP 触发器，`tests_bulk.rs` 钉住这条。触发器开关用守卫恢复，出错也不会漏开。
4. 每片（`checkpoint`）与收尾（`finish`）前必冲，攒着的东西不跨事务；跨片复用会话时清缓存（依赖向量行号、简单判定）。

### 4.3 第二期：写入瘦身（srs.db v21）

`sync2_ops.payload` 改存 zstd 压缩（1 档，线程内复用压缩上下文），新列 `pz`（0 原样 / 1 = `[原长 u32][zstd 帧]`），省不下八分之一或
短于 128 字节的原样存。读载荷的地方一律经 `snapshots::unpack_payload`（解压再拼回配置快照原文）。v21 升级只加列、不重写旧行：旧行
`pz = 0` 照读，之后收到的操作才压。

只压操作日志、不压投影的 `jslim`：投影是复习 / 浏览的热读路径，操作日志只有内核在取操作、旧闭包、时间线时读。实测压缩把操作日志
写入量减半（§8），`jslim` 再压的收益要以每次读解压为代价，不做。方案稿里「投影行改为引用操作」同理不做。

### 4.4 Dart：下载与收段交叠

`srsFetchInBatches` 交出一批的同时开始读下一批（只预读一批，内存最多两批 + 内核一批，仍在百兆以内）。收段在 worker isolate 上跑
（`SrsCoreLane.bulk`），下载与投影真正重叠。预读那一批失败时，之前的批照常交出、交到它时才抛；消费方停止监听后，预读那一批读完就停。

### 4.5 新设备的收段片长

收段会话开头判定「新设备」：本机身份在这个 profile 里从没写过复习日志（`sync2_ops` 主键前缀上一次范围扫描）。这样的会话把默认片长
150 ms 拉到 1 s（`CommitBudget::stretch`，只对默认片生效；测试显式给的 `sliceMs` / `sliceOps` 不动）。片越短，每片提交时同一批
随机键索引页被反复写进 WAL、检查点越频繁；新设备上没人等写锁，真有写入排队，让出请求照样在做满 64 条后收片。判据跟着本机操作走：
第一次追赶被打断、下次接着收仍算新设备；本机一复习就回到 150 ms。

## 5. 正确性守卫

1. **等价性质测试**（`store/sync2/tests_bulk.rs`）：随机多设备世界——三台设备 + 两台迁移来的旧设备：同一批旧修改记录与旧复习日志被两台
   各包一次、旧记录带服务器时刻、同一个旧 ID 在两边落在同一笔记的不同字段（撞 ID → 逐条退回）、一台分两批迁移而别的设备在中间写了一条
   （闭包走「部分」分支）；加上并发字段写、删除 / 恢复、卡移牌组、标签、复习、牌组改名、清除。新设备收齐、老设备从中途追赶、按 2 段一批 ×
   7 条一片的分片会话三种形态，批量与逐条（`bulk::sequential`）两路收完后**全部表**逐行相同、摘要桶等于全表重扫、待重读集合相同。
   测试构建里窗口压到 5 条、逐条落的门槛压到 3 条，全部既有的同步端到端测试也都在反复走「窗满批量冲刷」与「零头逐条落」；覆盖计数
   （`bulk::Coverage`）让对拍测试断言批量冲刷、零头冲刷、逐条退回、闭包部分分支都真的走到了——随机世界改了没覆盖到，测试直接红。
2. **真实数据回归**：`bootstrap_probe.rs` `probe_sliced`，同一份 68 万条真实段按生产形态收两遍（批量 / 逐条），逐表比行数与内容哈希（§8）。

## 6. 对 BUG-3993 在途分支（`pr/srs-ingest-defer-cache-refresh`）的意见

- 五处修复都是真问题（分片刷缓存近平方、还页缓存、整实体回读、`Deferred` 段内平方、每片并回 WAL），A/B 交替测过、测试齐全，**应合**。
  逐条路径在日常同步和第一期之外的追赶里继续用，修好有价值。复核过的两点：窄化查询与 `land` 语义等价（支配只在同字段键比，同 ID 由 `OR f.id` 兜住）；
  `Later` 峰值不超过预算加一段（≤ 16 MB 原文）。
- **它不是追平 Anki 的路线**：逐条一次收完本身就要 0.71 ms/条，分片修复的上限是往 530 s 那条线压，对平板「8–10 分钟」的推算即使达成也差一个数量级。
- 它列的下一项「字段修改落库路径五遍序列化 / 解析」建议**不做**：日常同步一轮几十条，省下的是几毫秒；冷启动由本方案整体绕开。
- 小提醒：缓存刷新推迟到收尾对所有会话生效。正在复习的老设备追赶时，整个会话期间被触及的卡显示收段前的状态、新卡不可见，
  可以接受（多出的复习也是事实，重放会算对），但可考虑只对大会话推迟。srs.db v20 目前只有它占用，没有撞号。

## 8. 实测

桌面 release，`bootstrap_probe.rs` `probe_sliced`，与生产同形：8 MiB 一批 `ingest_prepare` + 分片 `ingest_commit`，批内写连接自动检查点
16384 页 + `SrsWalCheckpointPacer` 另开连接并回，批末并回，收尾 `ingest_finish` + `replay_pending`。数据同 §2（57 段、68 万条）。
**每组只跑了一次，机器上同时有别的负载**（几个 GB 的 Dart 进程等），相差 10% 以内的不算数。

| 形态 | 总耗时 | 投递（commit） | WAL 检查点 | 收尾（重放 + 缓存） | 片数 |
|---|---|---|---|---|---|
| 逐条 + 150 ms 片（≈ #2796 合入后） | 521 s | 247 s | 177 s | 93 s | 1228 |
| 批量 + 150 ms 片 | 549 s | 250 s | 200 s | 95 s | 621 |
| 逐条 + 新设备 1 s 片 | 458 s | 285 s | 82 s | 88 s | 219 |
| **批量 + 新设备 1 s 片（本 PR 的生产形态）** | **414 s** | 260 s | 58 s | 92 s | 158 |

（预处理：验签、解压、解码，四组都是 3.2 s。）

结论：

- **本 PR 合计 521 → 414 s（−21%）**，主要来自新设备长片（§4.5）：WAL 检查点 177 s → 58–82 s。
- **批量投影本身在全量数据上没有可靠收益**：150 ms 片时慢 5%，1 s 片时快 10%，都在单次测量的噪声里。前 12 段子集（18.6 万条，
  字段修改全是迁移来的旧记录）上快 15%（120 → 102 s），没有在全量上复现。子集的计时分解说明了原因：投递的大头不是攒得起来的那部分
  投影，而是每条操作都要做的部分——`sync2_ops` 插入约 47 µs、记账 / 依赖 / 服务器时刻约 40 µs、「简单」判定约 17 µs，不能攒的
  种类（实体、媒体、标签、删除……）逐条约 300 µs，外加每片的提交与检查点 I/O。按窗批量只省掉了「读现存行 + 判定 + 触发器」那一截。
- 收尾（重放 + 缓存重建）约 90 s，本 PR 没动。
- **离目标（下载 + 几十秒）仍差一个数量级。** §3.1 那个取舍（在现有投递路径里按窗批量，而不是方案稿的独立新设备通道）是落地时做的，
  实测证明它拿不到 §2 的批量下限（约 20 s）：下限的前提是「操作全部追加完，再按实体整体折叠、无索引顺序写、最后建索引」，按窗方案
  每条操作仍走完整的记账与随机键索引写入，每片仍要提交、并回 WAL。要追上 Anki，下一步得做方案稿原来那条独立通道。
- **写入瘦身**：操作日志载荷 428 MB → 192 MB（zstd 1 档，`probe_ops_store`；3 档 190 MB 但多 3.5 s，不值）。
- **正确性**：四组收完后逐表比行数与内容哈希，43 张表全部一致；不同的只有每次运行本来就会变的三张——`sync2_self` / `sync2_devices`
  （每次新建本机身份）与 `srs_notes_cache`（带刷新时刻）。两组逐条之间也正好差这三张。
- Dart 预读（§4.4）：探针从本地目录读段，测不到下载与收段交叠的收益；真实网络下它把下一批的下载藏进当前这批的收段时间里。
