# Fushi SRS 同步 v2 设计（从零设计，不沿用旧 SRS 同步代码）

> 状态：设计稿（2026-10-25），待用户拍板「待决问题」一节后进入实现计划。
> 约束：本稿刻意**不参考**仓库里现有的 SRS 同步实现，只从第一性原理和本仓的传输现实出发。
> 实现须遵守 CLAUDE.md「Rust 胖核心、Flutter 薄 UI」：同步引擎与合并逻辑归 Rust，Dart 只做传输适配与 UI。

## 0. 一句话

**复习是事实，不是状态。** 同步只交换不可变的操作（尤其是「某设备在某时刻对某卡按了某个评分」），
卡片的调度状态永远是「全部复习事实按确定顺序重放 FSRS」的纯函数。于是复习**永远不会冲突**，
多台设备离线各刷各的，合并后每一次复习都算数，结果在所有设备上逐比特一致。

## 1. 为什么 Anki 的同步是垃圾（我们要逐条避开的东西）

| Anki 的做法 | 后果 | v2 的对策 |
|---|---|---|
| 卡片调度状态按「对象 mtime + USN」做最后写入者胜 | 两台设备离线都复习了同一张卡，合并后一方的调度直接被覆盖；revlog 两条都在，但调度只认一条，间隔算错 | 调度状态不同步，只同步复习事实，合并后**重放**（§4） |
| schema 变动 / 某些操作触发「需要完整同步」，让用户选「上传覆盖」或「下载覆盖」 | 二选一必丢一边的数据，用户最恨的弹窗 | **没有完整同步这回事**。任何状态都由操作并集推出，不存在需要整体覆盖的情形（§8） |
| 必须有中心服务器（AnkiWeb）维护 USN | 不能用自己的网盘 / 局域网 / P2P | 设计面向**哑存储**（只会读写文件的网盘），服务器与 P2P 只是更快的同一协议（§6） |
| 同步是手动的、整库加锁的一次性事务 | 刷卡中途不能同步，忘了同步就分叉 | 后台持续增量同步，单卡粒度，刷卡不阻塞 |
| 每日新卡上限按设备本地计数 | 手机刷了 20 张新卡，电脑还能再刷 20 张 | 每日计数从合并后的复习日志推出，**天然跨设备全局**（§4.4） |
| 笔记字段冲突静默 LWW | 两边同时改同一字段，一边的修改悄悄消失 | 并发改同一字段**保留两版并提示**，非并发修改自动合并（§5） |
| 撤销 = 改回旧状态 | 撤销在另一台设备上无从表达 | 撤销 = 追加一条「撤回某次复习」的操作（§4.3） |

## 2. 现实约束（决定了协议形态）

- **传输后端**：`SyncBackendType` = Google Drive / WebDAV / OneDrive / Dropbox / FTP / SFTP / fushiServer，外加互联（LAN / P2P 隧道）。
  前六个是**哑存储**：没有事务、没有锁、没有原子比较交换，列目录可能最终一致（GDrive）、可能出现同名重复文件。
  → 协议必须做到：**每台设备只写自己的文件；所有文件写一次后不可变；读者能容忍任何中间状态。**
- **离线优先**：手机长期离线是常态，重新上线必须无损合并，不能要求「先同步再刷」。
- **设备数**：个人使用，2~6 台，长尾有被抹掉 / 重装 / 从备份恢复的「僵尸设备」。
- **数据量级**：重度用户 5 万卡、100 万次复习、若干 GB 媒体。
- **五平台**：Android / iOS / macOS / Windows / Linux，加无头 `fushi_server`。

## 3. 数据模型：操作日志 + 派生状态

### 3.1 标识

- `DeviceId`：128 位随机，每次安装生成。**从备份恢复、克隆数据目录、检测到分叉时必须重新生成**（§7.3），否则序号复用会撕裂因果。
- 实体 ID（note / card / deck / preset / notetype / media）：128 位，本地生成，全局唯一，不需要协调。派生规则（2026-10-25 定，趁未发布改）：
  1. **本地新建的一律随机 UUIDv7**（时间前缀利于存储局部性）。
  2. **确定性 UUIDv5 只允许从「不可变的外部来源身份」派生**：Anki 笔记 guid、Anki 笔记类型 / 字段 / 模板的 id、Anki revlog id、卡片 = (笔记, 模板, 填空序号)。好处是同一个 apkg 在两台设备上各导入一次得到同一批 ID，合并时自然幂等去重。
  3. **禁止从可变属性（牌组全名、字段名、模板名）派生 ID**。反例：设备 X 把牌组「A」改名为「B」，设备 Y 离线时新建「A」→ Y 按名字派生出的正是 X 那个牌组的 ID → 合并后 Y 的新卡掉进「B」。现存的「名字派生 + 撞名时取备选 ID」只在 Y 已经看到改名时成立，离线并发下必错。
     替代：牌组随机 ID；合并后若两个**存活**牌组全名相同（离线各建了同名牌组），自动合并为一个（保留 ID 较小者，另一个记为别名，后续指向它的操作按别名重定向）。因为判定看的是合并时刻的全名，上面「改名 + 新建旧名」的例子两者全名已不同，不会误合。字段 / 模板同理：本地新建随机 ID，导入时无来源 id 的旧格式才按名字派生，且只用于导入去重。
  4. 内置实体（默认牌组、内置笔记类型）用固定常量派生，所有设备天然同一 ID。
- **存储与 wire 都用 16 字节二进制**（SQLite `BLOB(16)`，不再存 36 字符文本）：100 万复习的日志表连同索引省约一半空间，Rust 内核按 `[u8; 16]` 比较不必解析字符串；只在跨 FFI 给 UI 展示时转成文本。
- `OpId = (DeviceId, seq)`：设备内单调递增、无空洞。这是幂等与去重的唯一依据。

### 3.2 时钟：混合逻辑时钟（HLC）

每条操作带 `hlc = (wall_ms, logical, DeviceId)`，全序可比。
- 用途：同一字段的并发写决胜、重放时的稳定排序。
- 每收到远端操作就 `hlc = max(local, remote) + 1`，保证因果不倒挂，即使某台设备时钟快了一小时也不会让它「永远赢」——HLC 的 wall 分量被限制为 `max(本机墙钟, 已见最大 wall)`，并对「远端 wall 超出本机墙钟 > 24h」的操作打标告警而不是吞掉。
- **复习的调度时刻**另存真实墙钟 `reviewed_at`（FSRS 需要真实流逝时间），与 HLC 分离：时钟错的设备只会让自己那几次复习的间隔算偏，不会污染排序。

### 3.3 操作种类（全部不可变、可交换）

| 类别 | 操作 | 合并语义 |
|---|---|---|
| 复习 | `Review{card, reviewed_at, rating, duration_ms, kind(new/learn/review/relearn/cram), client_ctx}` | **只增集合**（G-Set），永不冲突 |
| 复习 | `RetractReview{review_op_id}` | 2P-Set 的移除端：被撤回的复习不参与重放 |
| 调度干预 | `Reschedule{card, mode(forget/set_due/reset), at}`、`Suspend/Unsuspend`、`Bury{card, until_day}` | 作为「特殊事件」插入该卡事件流，按 HLC 位置参与重放 |
| 内容 | `CreateNote{id, notetype, fields, deck}`、`SetField{note, field, value}`、`SetNotetype…` | 字段级多值寄存器（§5） |
| 内容 | `TagAdd/TagRemove{note, tag}` | 加胜 OR-Set |
| 组织 | `MoveCard{card, deck}`、`SetDeckName`、`SetDeckParent` | LWW 寄存器（HLC） |
| 配置 | `SetPresetField{preset, key, value}`、`SetFsrsParams{preset, params, trained_on: VersionVector}` | 键级 LWW |
| 删除 | `Delete{entity}` | 墓碑，带因果上下文（§5.3） |
| 媒体 | `MediaRef{note, sha256, size, mime}` | 只增；内容另存（§6.4） |
| 历史 | `Checkpoint{name, reason}` | 只增；时间线上的还原点（§10.2） |
| 历史 | `Purge{entity}` | 唯一改写历史的操作：各设备抹去该实体内容载荷（§10.5） |
| 未知 | 新版本客户端产生的未知 kind | **原样保存并转发**，不丢弃；升级后重放即生效 |

操作在磁盘上是紧凑二进制（建议 postcard / 自定义 varint 编码），一条 `Review` 约 30~40 字节。

### 3.4 派生状态

本地 SQLite（srs.db）里的「卡片当前 due / stability / difficulty / 队列」**全部是缓存**：
- 可随时从操作日志重建（`rebuild_all()` 是一等公民命令，也是自检手段）。
- 不参与同步，不出现在 wire 上。

## 4. 复习合并：重放而非覆盖

### 4.1 规则

一张卡的调度状态 = 对该卡的事件流（`Review` 去掉被撤回者 + 调度干预事件）
按 `(reviewed_at 或 at, hlc)` 排序后，从初始状态依次喂给 FSRS 的结果。

两台设备离线各复习同一张卡：
```
手机  10:00 Good   10:30(第二天) Again
电脑  12:00 Hard
合并 → 10:00 Good → 12:00 Hard → 次日10:30 Again，三次都算，间隔由真实历史推出
```
这正是「一个人分别在两台设备上学了同一张卡」的真实语义——Anki 会丢掉其中一条的调度影响，我们不会。

### 4.2 增量重放（性能）

- 收到的远端复习若全部晚于该卡本地最后一次事件：直接前推，O(新增条数)。
- 若插入到历史中间（离线设备补交旧复习）：只重放**这张卡**从插入点起的尾部。FSRS 单卡单步是常数时间，单卡几百次复习 < 0.1 ms。
- 只有「FSRS 参数变更」需要全卡重放：5 万卡 × 平均 20 次复习 = 100 万步，Rust 内核约 100~300 ms，后台 isolate 跑，结束后一次性推快照给 UI。

### 4.3 撤销

撤销 = 追加 `RetractReview`。被撤回的复习在所有设备上同步退出重放。本地 UI 的「撤销上一张」只是这条操作的语法糖。

### 4.4 每日计数与上限

「今天已学新卡 / 已复习数」= 合并后日志里 `day(reviewed_at, 用户时区与日界线) == 今天` 的计数。
所以手机刷了 20 张新卡，电脑同步后看到的剩余配额就是 0——这是**一致的结果，不是要协调的状态**。
离线期间两边各自用掉配额导致超额，属于可接受的有界超额（上限 × 离线设备数），合并后不回滚任何复习。

### 4.5 确定性（必须逐比特一致）

- FSRS 只在 Rust 内核里算，固定 `f64`、固定运算顺序，禁止依赖平台 `libm` 的超越函数差异（`exp/ln/pow` 用内核自带的确定性实现或经测试锁定的平台等价性）。
- 间隔 fuzz 的随机源 = `hash(card_id, review_op_id)`，不用 RNG。
- 学习步 / 埋卡 / 兄弟卡推迟等所有「看起来像状态」的东西都必须是事件流的纯函数。
- 每台设备定期对派生状态算 **Merkle 摘要**（按卡 ID 分桶），随 head 发布；两台设备在相同版本向量下摘要不同 = 确定性 bug，自动上报日志（不是让用户处理）。

### 4.6 重放用「作答那一刻」的配置，改配置不追溯（2026-10-25 审查修正）

- 每条本机新写的派生日志（评分、手动改期 / 重置、立即重排、移交）在落库时由内核记下**那一刻这张卡的生效排程配置快照**
  （日志 JSON 的 `sc`：学习 / 重学步长、期望保留率、最大间隔、算法、参数、fuzz；`native/fushi_fsrs/src/store/sync2/mod.rs`
  `stamp_config`）。快照是操作载荷的一部分，随签名同步，所以所有设备重放同一条日志用的是同一份配置。
- 重放（`replay.rs`）按每条日志**自己的** `sc` 算，与「此刻」的牌组配置无关。所以：
  - 改牌组配置 / 换牌组 / 改参数**只影响之后的复习**，已经发生的复习的结果一字不变，也**不触发任何重放**（以前每改一次配置
    就把整棵牌组子树重放一遍、追溯改写全部历史到期日）；
  - 并发复习仍然按事实合并：两台设备离线各复习同一张卡，合并后每条复习在「重放出的前一状态」上、按它自己的配置重算。
- **没有 `sc` 的日志按作者结果照抄**：迁移来的旧日志、旧备份并入的日志（stamped）。它们的结果就是当时的事实。
  因此**迁移不改任何一张卡的到期日**，迁移后也不做全量重放。
- 评分预览按此刻的配置算，与作答落库时记下的 `sc` 是同一份。
- 取舍：另一种做法是「重放时按操作的 HLC 去配置历史里查当时的配置」，但配置本身也是并发写的多值寄存器，按 HLC 截取
  在多设备下并不唯一；把配置随操作一起记下更简单、逐位确定。代价是每条派生日志多约 300 字节（压缩后很小）。
- 本地存储按内容去重（srs.db v16，2026-10-30）：快照原文只在 `sync2_snapshots` 存一份，操作日志载荷剪掉原文、记
  （哈希, 位置）读时拼回（逐字节还原，段与签名不变），日志投影存 `"sc":"<哈希>"`、读侧与摘要按展开后的原文算
  （`native/fushi_fsrs/src/store/sync2/snapshots.rs`）。线格式不变。

## 5. 内容合并：只有真冲突才打扰用户

### 5.1 因果判定

每个可写寄存器（笔记字段、牌组名、配置键）记录最后一次写入的 `OpId` 及写入者当时见过的版本向量摘要（dot）。
- 新写入**因果上覆盖**旧写入（写入者已见过旧值）→ 直接替换，无冲突。
- 两次写入**并发**（互不可见）→ 多值寄存器保留两个值。

### 5.2 并发写的处理

| 寄存器 | 并发时 |
|---|---|
| 笔记字段（用户可见文本） | 保留两版，界面显示「此笔记在两台设备上被同时修改」，默认显示 HLC 较大者，用户可一键选另一版或手工合并。**绝不静默丢弃**。 |
| 牌组名、配置项、FSRS 参数等低价值标量 | HLC 大者胜，不打扰用户（另一值留在历史里可查） |
| 标签 | OR-Set 加胜：一边加标签、一边删同一标签 → 保留 |

冲突本身也是数据：选定某版 = 追加一条新的 `SetField`（因果覆盖两个并发值），于是冲突解决也会同步到其它设备，不会在别处重新冒出来。

### 5.3 删除与其它「破坏性并发」：一律进冲突中心等用户定（用户 2026-10-25 拍板）

- `Delete` 携带删除者当时见过的版本向量。
- 删除**之后**（因果上）没有别的写入 → 删除直接生效，不打扰。
- 删除与别的写入**并发** → 不自动判输赢，生成一条**冲突项**进冲突中心，并发通知（非阻塞，不打断刷卡）。
  冲突未处理前采用**保守的临时态**：实体保持可见、可复习（多留一张卡不会丢任何东西），卡片上带「待确认」标记。
  用户选「删除」或「保留」后追加一条新操作（因果覆盖双方），结论同步到所有设备，别处不会再冒出同一冲突。
- 同类（一方的操作会让另一方的修改失去意义）全部走这条路：

| 并发组合 | 冲突项文案要点 |
|---|---|
| 删除笔记 / 卡 ⟂ 编辑字段、加减标签 | 「A 设备删了它，B 设备改过它」 |
| 删除卡 ⟂ 复习这张卡 | 「删除后又在另一台设备上复习了 N 次」 |
| 删除牌组 ⟂ 往该牌组移入 / 新建卡 | 列出受影响的卡，选「一起删」或「移到默认牌组」 |
| 更改笔记类型（字段映射） ⟂ 编辑旧字段 | 显示旧字段新值将落到哪个新字段，或被丢弃 |
| 重置 / 遗忘卡片 ⟂ 复习这张卡 | 选「以重置为准」或「保留复习进度」 |
| 合并重复笔记 ⟂ 编辑被吸收的笔记 | 显示被吸收笔记的新改动，选是否并入 |

- 被删卡的复习操作仍保留在日志里（统计与恢复要用），只是不再出现在队列。
- 低价值标量（牌组名、配置项）的并发写仍按 HLC 自动决胜、不弹冲突，但在设置里的「同步历史」可查被覆盖的值。

### 5.4 重复笔记（两台设备各自制了同一个词）

ID 不同的两条笔记不会自动合并（自动判重会误伤）。合并后由「重复检测」按笔记类型的首字段 + 读音给出**合并建议**；用户确认后产生 `MergeNotes{keep, absorb}` 操作：被吸收笔记的卡片复习历史并入保留卡（重放后得到合并后的调度），被吸收者墓碑化。

## 6. 存储与传输

### 6.1 哑存储上的目录布局

```
fushi-srs/v2/
  meta.json                         # 协议版本、加密参数（盐 / KDF 参数）、集合 ID；创建后只读
  devices/<DeviceId>/
    head-<seq>.json                 # 该设备的 head：最新 seq、段哈希链尾、已应用版本向量(ack)、状态摘要、协议版本
    seg-<firstSeq>-<lastSeq>.bin    # 不可变操作段，zstd + AEAD 加密，内容含上一段哈希
  media/<sha256前2位>/<sha256>      # 内容寻址媒体，不可变（「媒体」「归档」用途的位置）
```
每个存储位置（§6.5）按自己勾选的用途只出现其中一部分目录。

**写入纪律**
1. 先写段（新文件名，写完即不可变；支持 rename 的后端先写临时名再 rename）。
2. 段写成功后再写新的 `head-<seq>.json`；旧 head 保留最近 2 个再删。
3. 媒体先于引用它的段上传。

**读取纪律**
- 列 `devices/*/head-*.json`，取每台设备 seq 最大且其引用段都可读的 head。
- head 指向的段暂时列不到（GDrive 最终一致）→ 本轮跳过该设备，下一轮再来；**任何时刻读到的都是某个一致前缀**，不会读到半截状态。
- 同名重复文件（GDrive 特有）按内容哈希去重，内容不同 = 有设备 ID 冲突，进入 §7.3 分叉处理。

因为没有任何文件被两台设备写，**不需要锁，也不存在写竞争**。

### 6.2 一轮同步

```
1. 本地未上传操作 → 打包成段（按压缩后约 4 MB 切分，§7.1）→ 上传 → 写 head
2. 读所有设备 head → 对比本地版本向量 → 只拉缺的段（老历史在少数几个大段里，落后多少都只是十几个文件，§7.1）
3. 校验哈希链与签名 → 去重（OpId）→ 交给 Rust 内核 apply_ops(batch)
4. 内核增量重放受影响的卡、合并内容寄存器 → 一次性推新快照给 UI
5. 更新本地 ack 写进下一次 head
```
发件分批（BUG-3849，2026-10-27）：第 1 步按批产出（每批 ≤ 8 MiB / 64 段，内核 `OUTBOX_BATCH_BYTES` / `OUTBOX_BATCH_SEGMENTS`），每批写成后 `outbox_ack` 把该位置的上传水位（`sync2_locations.uploaded`，含义不变：seq ≤ 它的本机段都已在该位置）持久化，下一批 / 下一轮从水位续发；head 仍在全部批次写完后才写，对读者透明、线协议不变。
读、写、删同时最多 6 个请求在途（段之间无先后约束，只有 head 必须等全部段写完）；同一命名空间并发写会锁冲突的后端（Dropbox）写 / 删逐个来。
触发：本地有新操作后防抖 10 s、App 回前台、定时（前台 5 min / 后台按平台允许）、手动按钮。刷卡时每张卡的复习立即本地落盘，上传在后台，**不阻塞翻卡**。

### 6.3 互联 / fushiServer / P2P：同一协议的快速通道

- 对端之间做**反熵**：交换版本向量 → 互发对方缺的操作。操作格式、去重、合并代码与网盘路径完全同一套。
- 在线时 host 推送实时操作流，另一台设备几百毫秒内看到复习结果（手机刷、电脑上进度条跟着走）。
- fushiServer 只是「有通知能力的段存储」：同样按设备分目录存段，额外提供 WebSocket 新段通知。服务器**不理解也不改写**操作内容（可以端到端加密）。
- 多通道并存安全：同一操作经网盘和 P2P 各到一次，按 OpId 幂等。

### 6.4 媒体

内容寻址、不可变、只增。拉取策略：笔记被打开或卡片进入今日队列时按需拉取，Wi-Fi 下后台预取今日 + 明日队列。
媒体只在「仅被已删除笔记引用、且删除已满 90 天」后由任一设备清理（§10.5）；归档位置永不清理。

**位置上有什么记在日志里，不列目录（BUG-3869，2026-10-28）**：重度用户一个位置上有数万个媒体，每轮对账都把媒体目录整个列一遍
要几分钟，且跑在全局同步锁里、挡住书同步。改为操作 `MediaAt{location, flags, names}`（kind 12，`location` = 位置身份 +
媒体目录，加密媒体按密钥指纹分目录）：
- 设备上传 / 下载成功、逐个查到，或读取时确认不在，就记一条（`flags` 的 PRESENT 位区分在 / 不在）；每个（位置, 名字）按
  HLC 大者胜，投影 `sync2_media_at`。与投影一致的事实不重复记；单条最多 2000 个名字。
- 日志里还没有任何设备对某位置完整列举过（`sync2_media_seeded` 无行）时，对账列一次目录，结果带 SEEDED 位写进日志；之后
  **全系统**对这个位置只读投影，只对投影里没有的名字逐个查（老版本设备传的、别的设备刚传还没随段到达的）。
- 投影说在、读取时不在（外部删了 / 网盘丢了）→ 记不在，持有它的设备下一轮补传，自愈。
- 已知局限：记为「不在」之后、由**老版本**设备补传上去的文件，要等某台新版本设备本机有它时才会重新记成「在」。
- 本地文件夹位置（§6.5）仍每轮列目录（本机文件系统调用，不走网络），不记日志。

### 6.5 存储位置：一个位置默认全包，「＋」可加任意多个（用户 2026-10-25 拍板）

**概念只有一个：存储位置（Storage Location）**。一个位置 = 一个后端（本地文件夹 / Google Drive / WebDAV / OneDrive / Dropbox / FTP / SFTP / fushiServer）+ 一个根目录 + 勾选的**用途**：

| 用途 | 放什么 | 多个位置时的语义 |
|---|---|---|
| 同步 | `devices/` 操作段与 head | **互为副本**：写入所有勾了同步的位置，从任意可达的位置读、按 OpId 去重合并。一个位置离线 / 被删不影响同步，恢复后自动补齐。 |
| 媒体 | `media/` 内容寻址文件 | **互为镜像**：新媒体写入所有媒体位置；读取时本地文件夹优先，其次最快的可达位置；缺的从别处补。 |
| 归档 | 全部操作段、媒体（§10.3） | **只写不删**：与同步位置同布局，但永不执行删除；多个归档位置各自独立完整。 |

**默认（普通用户零配置）**
- 加第一个位置时「同步」「媒体」**默认勾上**——一个网盘账号就是全部，用户只需要选「加 Google Drive」并登录。「归档」默认不勾。
- 本机始终保留完整操作日志（§10.2），即使从没配置过任何云端，时间线恢复也可用。
- 已在 App 其它同步设置里登录过的网盘账号，在「＋」菜单里直接列出可复用，不必重新登录。

**进阶（按需拆分）**
- 例：同步放 Google Drive（小、需要快），媒体放 NAS 的 WebDAV（大），归档放 U 盘文件夹。
- 每个位置卡片显示：后端、用途标签、加密开关、已用空间、最近一次成功时间、落后多少条操作 / 多少个媒体。
- 取消某位置的某个用途 = 停止往那里写；位置里已有的文件**不删**，用户另点「清理此位置」才删（二次确认）。
- 同一后端 + 同一根目录不能重复添加（按规范化路径 / 账号 + 文件夹 ID 判重）。

**本地文件夹位置（「＋ 本地文件夹」）**
- Windows / macOS / Linux：任意目录，含 U 盘、NAS 挂载盘。
- Android：通过 SAF 选目录（持久化 tree URI 权限）；iOS：Files 选目录（security-scoped bookmark）。权限失效时位置标红并提示重新授权，不静默跳过。
- 附带收益：把本地文件夹设为 Syncthing / 坚果云 / iCloud Drive 同步目录，也能当同步位置用——因为每台设备只写自己的文件、文件不可变，这类文件同步工具**不会产生冲突副本**；万一产生（`*.sync-conflict-*`），按 §6.1 的重复文件规则以内容哈希去重。

**一致性要点**
- 所有同步位置的协议与目录布局完全相同（§6.1），所以「新加一个同步位置」只是把本地已有的段写过去，不需要任何迁移。
- 小段合并后删旧段（§7.1）在每个位置独立判定，但都以「全部同步位置中能看到的 ack」为准，防止某个位置落后时被提前删除。
- 媒体清理只针对「被删笔记独占、且已过 90 天」的媒体（§10.5），归档位置不清理。

## 7. 压缩、垃圾回收与异常设备

### 7.1 大段与分层合并（取代原「快照」，2026-10-27）

哑存储上一次请求的固定延迟（几百毫秒）远大于传几 MB 的时间，所以首次提交 / 新设备 / 落后很多的设备慢在**文件个数**，
不在字节数。原设计用 64 KB / 2000 条切段 + 落后太多时拉快照；实现改为：

- **按压缩后体积切段**：目标约 4 MB 一段（`SEGMENT_TARGET_BYTES`；条数上限 25 万只是解码内存保险）。体积是按 4096 条 / 256 KB
  一块各自压缩求和的上界，切段器流式喂入、不攒整段。几万条操作的首次提交 = 1 个文件（旧上限下 6000 条复习就是二十多个）。
- **分层合并本机的段**：每轮同步切出的小段按体积分层（16 KB 起每 4 倍一层），同层相邻攒够 4 个就合成一个更高层的段，像二进制
  进位；≥ 目标一半的满段不再动。任何时刻本机的段 = 满段 + 每层不到 4 个（实测上界 15 个小段），每条操作一生被重写约 4~5 次
  （都是小段，字节量可忽略）。合并 = 同一 seq 区间、同样的操作重新切、重新签名；新段写成功、其它活跃设备 ack 越过后再删旧段；
  归档位置不删，保留原段。升级前切的老段体积记 0，下一轮补算后照常合并。
- 于是新设备 / 落后的设备要拉的是「每台设备十几个文件」，读写再并发（§6.2），不需要另一种文件。
- **不做快照**：复习事件不能压掉（它们是调度的源头），快照省下的只是内容编辑历史，传输上与合并后的段同一量级；而它要引入
  第二条信任路径（快照由任意设备写、包含别的设备的数据，无法像段一样逐设备验签与验链），并打破「本机持有每台设备从 seq 1
  起的完整前缀」这一不变式（导出 `.fushisrs`、分叉检测、链校验都依赖它）。
- 收端因果投递在内存里按设备排队，每一遍只看各设备队首（O(操作数 + 遍数 × 设备数)），不再每遍重扫整张缓冲表——
  新设备追赶两台来回同步过上千轮的设备时，旧做法是平方级。
- **历史操作不删**（§10.2）。

### 7.2 长期离线设备

设备 head 超过 90 天未更新视为「休眠」，只影响状态面板与媒体清理的判定。它回来时：
- 拉它缺的段（老历史已合并成少数大段，历史一直都在），与本地合并。
- 它本地积攒的未上传操作照常上传——操作是可交换的，晚到多久都能正确合并（复习插入历史中间、内容按因果判定）。

### 7.3 设备身份分叉（必须处理的坑）

场景：用户把整个数据目录拷到新手机 / 从手动导出文件恢复 → 两台设备持有同一个 DeviceId 和 seq，开始各自追加，seq 撞车。
- 检测：本地记录自己最后上传段的哈希；远端同一 DeviceId 的哈希链与本地不一致，或本地 seq 落后远端 head → 判定分叉。
- 处理：本设备立即**换新 DeviceId**，把分叉点之后本地的操作以新身份重新签发（新 OpId，内容不变），旧身份在本机冻结。无数据丢失。
- 预防：导入 `.fushisrs`（§10.4）流程主动重新生成 DeviceId。

### 7.4 段损坏 / 被篡改

段用设备 Ed25519 密钥签名并嵌入前段哈希。校验失败 → 不应用该段及其后续，记录告警，向该设备的下一次 head 请求重传（网盘场景下就是等它下次同步重写）；其它设备的数据照常合并。

## 8. 版本演进：永远不需要「完整同步」

- 操作信封带 `kind` 与 `schema_ver`。旧客户端遇到未知 kind：保存、转发、不应用；遇到已知 kind 的新字段：保留原字节。
- 需要语义变更时**新增 kind**，不改旧 kind 的含义。派生状态的 schema 改了 = 本地重建缓存，与同步无关。
- `meta.json` 与 head 里写 `min_reader_ver`：只有真正不兼容（极少）时，旧客户端停写并提示升级——**仍然不会让任何一方覆盖另一方**。

## 9. 安全与隐私

- **端到端加密是每个存储位置的可选开关，默认关**（用户 2026-10-25：无所谓 → 取「少一步操作」）。开启时集合密钥由用户口令经 Argon2id 派生（参数存该位置的 `meta.json`），或在互联配对时由已有设备直接下发；网盘只见密文和文件大小。本地文件夹位置一般不必开。
- 不加密时段文件仍带校验哈希与签名（防损坏 / 防注入），只是内容明文。
- 设备签名密钥对在加入集合时生成，公钥写入 head；不认识的设备公钥需要已有设备确认（防止拿到网盘写权限的第三方注入操作）。
- 口令丢失 = 网盘数据不可解，但任一设备本地仍有完整日志，可用新口令重建集合（`reseal`）。
- **加密不会被悄悄降级**（2026-10-25 审查修正，`srs_location_crypto.dart` `srsLocationHandshake`，同步轮次与只做媒体的位置共用）：
  - 本机开过加密的位置，`meta.json` 上的 `kdf` 不见了（被删 / 被别的版本整份重写）→ 报「加密设置不见了」停下，一个段也不传；
    界面上点一下用本机这把密钥（同一份盐与校验值）把 `kdf` 写回去。
  - `meta.json` 读不到（最终一致的网盘还没列到 / 被删）或解析不了，而位置上已经有设备数据 → **不重写**（以前会整份重写、
    盖掉一份其实存在的加密 meta），这一轮不同步。只有全新的空位置才新建 meta；本机此时有密钥就连 `kdf` 一起写。
  - 上传进度按「位置 + 密钥指纹」记（`<位置>#e<指纹>`），加密媒体放 `media-e/<指纹>/`：两台设备同时开加密、后写的 `kdf` 胜出时，
    输掉的那台输入正确口令后密钥指纹变了，进度归零、段与媒体全部按新密钥重传，其它设备收得到。
  - `kdf` 的参数来自不可信的 `meta.json`：Argon2id 内存 8–256 MiB、迭代 1–10、并行 1–4、盐 16–64 字节，越界报错不派生
    （Dart `SrsKdf.fromJson` 与内核 `KdfParams::checked` 同一组上下限）。

## 10. 备份 = 时间线 + 归档 + 手动导出（用户 2026-10-25 拍板）

不再有「定时拍快照、留 N 份」的独立备份系统。数据只增不改，备份要做的只是**别删历史**，再加冗余副本。

### 10.1 防什么

| 风险 | 由谁兜底 |
|---|---|
| 误操作（批量删除、导错包、改坏笔记类型）且已同步到所有设备 | 时间线（§10.2） |
| 合并 bug / 某设备写入坏数据 | 时间线：回到出事之前 |
| 网盘账号或文件夹丢失 | 每台设备本机有完整日志；多个同步位置互为副本（§6.5） |
| 全部设备丢失 | 网盘上的同步目录本身即可完整恢复 |
| 某台设备 bug 删掉同步目录里的文件 | 归档位置（§10.3）：只写不删 |
| 离线保存 / 不连同步地搬家 | 手动导出（§10.4） |

### 10.2 时间线（主要的备份）

- **操作日志默认永久保留**：任何位置都不因「腾空间」删除历史操作。段合并（§7.1）只改切法，不删任何操作。体积：100 万次复习压缩后约 10 MB，加上多年笔记编辑，重度用户几十 MB。
- **没有「多久备份一次」**：每条操作同步出去即已备份，粒度是单次操作。
- **自动还原点**：批量删除、导入、更改笔记类型、重设 / 重训 FSRS 参数、按时间点恢复之前，自动追加 `Checkpoint{name, reason}` 操作（几十字节）。时间线 UI 还按天显示刻度（由日志推出，不另存）。
- **恢复**：选时间点 → Rust 内核按「版本向量截断的操作集」算出那一刻的状态 → 与当前状态求差 → 生成一批补偿操作（字段改回、复活被删实体、删除之后新建的实体、配置改回）。之后的复习**默认保留**，用户可勾选一起撤回（追加 `RetractReview`）。补偿操作正常同步到所有设备，不覆盖任何设备；恢复前自动打还原点，所以恢复本身可再撤销。
- 每张卡、每个字段的完整修改历史（谁、哪台设备、何时）可直接展示。

### 10.3 「归档」用途

- 存储位置的第三种用途（§6.5）：接收全部操作段与媒体，**永不执行任何删除**（不参与段合并、媒体清理、彻底清除之外的一切删除）。
- **默认不开**：普通用户已有「本机 + 第一个同步位置」两份完整历史。想多一层保险的人「＋」一个 U 盘 / NAS 并勾「归档」。
- 归档位置的目录布局与同步位置相同，所以它随时可以被改成同步位置直接用来恢复。

### 10.4 手动导出

- 单文件 `.fushisrs`：全部操作历史（每台设备从 seq 1 起的完整前缀 + 公钥），媒体可选（默认勾选）。用于离线保存、或完全不连同步时搬到新设备。
- 只有手动导出，不定时（归档位置已覆盖定期备份的需求）。导入 `.fushisrs` = 把其中的操作并入（不覆盖），并按 §7.3 生成新 DeviceId。

### 10.5 媒体保留与彻底清除

- **被删笔记的媒体**：同步 / 媒体位置上保留 90 天后清理；归档位置永久保留。超过 90 天恢复：文字回来，媒体显示缺失（若有归档位置则从归档补回）。
- **彻底清除**（隐私）：历史永久保留意味着删掉的内容在时间线里仍可找回。需要真正抹掉时用 `Purge{entity}`：所有设备收到后，从本机日志中抹去该实体的内容载荷（保留操作骨架以维持序号与哈希链），并在各同步 / 媒体 / 归档位置重写受影响的段、删除相关媒体。这是全系统**唯一允许改写历史**的操作，二次确认，且仅在线可达的位置立即生效，离线位置下次连上时执行。

### 10.6 可观测性

同步面板：每台设备最后见到的时间、落后多少条操作、待解决冲突数、确定性摘要是否一致；每个位置的已用空间与历史起点。

## 11. 模块划分（遵守胖核心规则）

| 层 | 归属 | 职责 |
|---|---|---|
| `native/fushi_srs_sync`（或并入 SRS Rust store crate） | Rust | 操作编解码、HLC、版本向量、哈希链 / 签名 / AEAD、段打包（按体积切段、分层合并）与校验、`apply_ops` 合并、增量 FSRS 重放、Merkle 摘要 |
| C ABI | Rust ↔ Dart | 粗粒度命令：`pending_segments() -> bytes`、`ingest_segments(bytes[])`、`sync_status()`；一次同步轮次个位数 FFI 调用，大块走 `TypedData` |
| 传输适配 | Dart（`fushi_engine`，纯 Dart） | 只把「列文件 / 读字节 / 写字节」映射到各后端与互联通道；不理解操作语义 |
| UI | Flutter | 同步状态、冲突中心、重复合并建议、设备管理 |

传输适配层是现有七种后端的薄封装，新增后端只需实现 `list / get / put / delete` 四个方法。

## 12. 验证计划

1. **性质测试（Rust，proptest）**：随机生成 N 台设备的操作序列，以任意顺序、任意重复、任意分批投递，断言所有副本最终派生状态与 Merkle 摘要逐比特相同（交换律 / 结合律 / 幂等）。
2. **重放等价**：同一组复习，「一次性顺序喂入」与「乱序分批到达后增量重放」结果相同。
3. **哑存储故障注入**：模拟 GDrive 列目录延迟、同名重复文件、上传中断、head 先于段可见（违反写入纪律的后端），断言无损坏、最终收敛。
4. **分叉**：拷贝数据目录后双端写入，断言自动换身份、零丢失。
5. **跨平台确定性**：固定向量集在五平台 + server 上跑 FSRS 重放，输出哈希必须一致（CI 矩阵）。
6. **规模**：100 万复习 / 5 万卡的冷启动（新设备一轮收齐全部段）、全量重放、增量一轮的端到端耗时（含 FFI 与拷贝），写进实现 PR。

## 13. 拍板记录（用户 2026-10-25）

1. **端到端加密**：用户无所谓 → 每个存储位置可选、默认关（§9）。
2. **破坏性并发（删除 ⟂ 编辑等）**：一律进冲突中心手动确认，未确认前保守保留（§5.3）。
3. **离线超额**：接受多设备离线时每日上限的有界超额，不回滚复习（§4.4）。
4. **按时间点恢复**：默认只恢复内容，是否撤回之后的复习由用户勾选（§10）。
5. **旧数据迁移**：首次 v2 同步时**弹窗确认一次**：首台设备导出创世快照，其余设备的本地集合以操作形式并入（不是二选一覆盖），重复笔记走 §5.4 合并建议。
   实现补充（2026-10-25 审查修正）：迁移只给旧行补操作与元数据，**旧投影行原样留着**（唯一的改写是旧的整列表 `tags` 行换成等值的
   OR-Set 合成行），迁移来的日志没有配置快照、按作者结果照抄（§4.6），所以**不改任何卡的到期日**、迁移后不重放；中途中断不丢旧数据，
   这就是迁移的回退手段（不另存迁移前快照）。迁移**分批、可续跑**：第一批把旧行按确定顺序排进 `sync2_migrate_queue`，每批（2 万条）
   一个独立提交的 savepoint，进程被杀 / 关库只丢正在做的那一批，下次打开接着做；从迁移到一半的备份快照恢复出来的新身份也接着做完。
6. **旧版自动备份**（2026-10-25 审查修正）：新版能导入旧格式 `.fushisrs`（魔数 `fushi-srs-backup`：`events.jsonl` 按已盖戳事件并入，
   媒体取包内或旧备份媒体池）；本机旧备份目录的 30 天宽限期从**本机升级到 v2 后第一次看到它**起算（目录里的标记文件），不是从目录里
   最新文件的修改时间起算。
7. **存储位置**：同步 / 媒体默认放同一个位置，可拆分；每种用途（同步 / 媒体 / 归档）都能用「＋」挂 N 个位置，含本地文件夹（§6.5）。
8. **备份**：不设独立快照备份；操作历史默认永久保留（时间线恢复）、「归档」用途默认不开、被删笔记的媒体在同步位置保留 90 天、只留手动导出不定时（§10）。
