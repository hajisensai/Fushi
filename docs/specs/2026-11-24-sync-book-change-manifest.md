# 云同步书阶段：书级变更清单 + 本地一致指纹（只同步变了的书）

- 日期：2026-11-24
- 来源：拍板台 `wiO0nN8aiG`（做）· GitHub issue #4332 · 前序 [BUG-4054](../bugs/BUG-4054-sync-unchanged-books-slow.md)
- 范围：云通道（Google Drive / Dropbox / WebDAV / OneDrive / FTP / SFTP / Fushi 服务器文件箱）的书阶段
  `SyncOrchestrator.run` → `SyncManager.syncAllBooks`。互联通道不跑这一段（书进度走 live 端点），不在范围内。

## 1. 现状与问题

每轮自动同步都对**每一本**本地书走一遍逐本阶段：`ensureBookFolder` → 列书文件夹（无整树快照的后端每本 1 次
往返，BUG-4054 已改为并发 4 预取）→ 读本地进度 / 基线 → 三方判定。100+ 本书、只开统计同步、远端一字未变时，
WebDAV / OneDrive / FTP / SFTP 每轮仍是 100+ 次列举；有快照的后端（Drive / Dropbox / 服务器）网络只付 1 次，
但进度条照样逐本走过 100+ 本「同步中」。

关键事实（决定了「能安全跳过什么」）：

1. 一本书的同步结果只由三样东西决定：本地阅读位置时间戳 `L`、同步基线 `B`、远端 `progress_*` 文件名（时间戳 +
   进度分数）`R`；统计 / 有声书断点跟着进度方向走（`_syncBookProgress`），`synced` 时什么都不传。开了「上传书籍
   文件」时另有「远端缺书文件就补传」这一项。
2. 所以「上一次亲眼看到两端一致（`synced`）之后，`L` 没变、远端书文件夹没变、内容开关没变」⇒ 这一轮逐本阶段必然
   还是 `synced`、什么都不做。这是**精确等价**，不是启发式。
3. 难点只在「远端书文件夹没变」怎么不逐本列举就知道。

## 2. 方案

### 2.1 本地一致指纹（每本书一行，设备本地）

一本书在本轮逐本阶段得到干净的 `synced`（无错误、无内容错误）时，记一个指纹：

```
fp = H(mode, L, remoteKey, contentChecked) 的 52 位，左移一位，最低位 = 这次列举里看到了有声书包
```

- 存 `sync_baselines`，dimension = `bookfp|<进度基线存储维度>`（基线维度本身已按远端账号 / 服务器分槽，
  BUG-4434；换账号 / 换服务器自然不命中）。`sync_baselines` 是设备本地表，不进备份（`table_rules`）。
- **只在亲眼看到两端一致时记**：导入 / 导出后的那一轮不记，下一轮再逐本确认一次（多付一次列举），换来
  「指纹永远只描述观测到的一致状态」，不需要推算写后的远端文件名。
- 冲突、失败、跳过一律不记：冲突书每轮照旧报。

### 2.2 两种「远端没变」的判据（`remoteKey`）

| 模式 | 适用 | remoteKey | 跳过条件的可信度 |
|---|---|---|---|
| snapshot | 本轮拿到整树快照（Drive / Dropbox / 服务器） | 快照里这个书文件夹全部文件名排序后的哈希 | 精确：快照就是远端实情；任何写入者（旧版 Fushi、ッツ网页版）改了文件名都会命中 |
| manifest | 无快照（WebDAV / OneDrive / FTP / SFTP，或快照本轮失败） | 各**对端**书级清单里这本书的条目拼成的摘要 | 只覆盖写清单的客户端；靠 2.4 的回退兜住其余写入者 |

快照模式下不读清单：快照已经精确，清单只为无快照后端服务（但所有设备照样发布清单，因为同一远端在快照失败的
那一轮会落到清单模式）。

### 2.3 书级变更清单（每设备一份）

- 位置：同步根下保留命名空间 `__book_manifests__/books-<deviceId>.json`。`__x__` 形状的名字旧版客户端一律当保留
  命名空间、不当书文件夹（`isReservedSyncNamespaceName`），旧客户端看不见它也不受影响。
- 内容：`{"v":1,"device":"<id>","books":{"<assetKey>": <本机该远端的进度基线>}}`，即本机
  `sync_baselines` 在进度存储维度下的全部行。每设备只写自己那份，不存在并发覆盖。
- 为什么是「基线」：本机对一本书的每一次进度写入（自动导出、对比弹窗选本地、退出书同步）都把基线推进到写入的
  时间戳（`_handleExport` 内，BUG-201）；导入同样推进基线。于是「某对端条目变了」⇔「那台设备对这本书写过或
  读过一次新状态」。对端只是导入时我们多确认一次（一次列举，结果 `synced`），不会漏。
- 发布时机：每轮书阶段之后；退出书 / 对比弹窗单本同步落地导入或导出之后（读完这本马上换设备是最常见的路径，
  不能等下一轮）。发布前按内容哈希去重（本地偏好记「上次发布成功的哈希」），没变不发请求。同进程内串行化。
  发布失败只记日志：本地哈希不更新，下次发布时自动重发。

### 2.4 manifest 模式的全扫回退（不跳过任何书）

出现下列任一情况，本轮不跳过任何书（等同改动前的全扫），全扫完整跑完才更新「上次全扫时间」与旧客户端活动标记：

1. **首次**：本书没有指纹（升级后第一轮自然全扫）。
2. **本机清单不在 / 与上次发布的不一致**：远端被清空、换了目录、被人手动删改。
3. **任一对端清单读不出**（损坏 / 下载失败）。
4. **旧版客户端在活动**：`__aggregate__` 下有某台设备的聚合快照，但它没有书级清单（= 旧版本，只写书文件不写
   清单），且它的快照版本标记（`revision`，没有时用修改时间 + 大小）与上次全扫时记下的不同（或拿不到任何标记）。
5. **兜底周期**：距上次完整全扫超过 24 小时（覆盖崩溃窗口、ッツ网页版等不写清单也不写聚合快照的写入者、
   只开进度不开统计的旧客户端）。

### 2.5 为什么跳过不会丢数据

被跳过的书本机**一定没动过**（`L` 与指纹一致）。跳过的唯一后果是「对端的新进度晚一点导入」，不会有写入：
本机之后一旦读了这本书，`L` 变了，下一轮它必走逐本阶段、现列文件夹、按共同祖先三方判定——对端改过就报冲突，
不会用本地旧进度覆盖远端。这与 TODO-2656 里「快照说没变就跳过是单边不安全的」那段论证不冲突：那里担心的是
本地有改动时凭陈旧结论走 LWW，这里跳过的前提恰恰是本地无改动。

### 2.6 附带

- 进度 UI：`onBookProgress` 的总数只算真正进逐本阶段的书；全部未变时整段不逐本走过。`SyncRunReport` 新增
  `booksUnchanged`，计时诊断里带上（区分「真有变化」和「只是检查」）。
- 有声书包阶段：被跳过的书若指纹最低位记着「上次见过有声书包」，就把这个观测喂给同轮的
  `BookFolderListingObservations`，不退回 BUG-4054 修掉的逐本 HEAD 探针。
- 只做已缓存 title→folderId 的书的观测种子；未缓存的照旧现场确认。

## 3. 胖核心评估

架构硬规则要求新计算型子系统进 Rust。这里**不是新子系统**：书阶段的方向判定、基线、后端抽象、列举快照、
清单镜像全部是现存 Dart（`sync_manager.dart` / `sync_orchestrator.dart` / 七个 Dart 后端），本改动是在它们之上加
一层「哪些书需要进逐本阶段」的筛选，计算量是 O(书数) 的哈希比较，没有实测性能问题需要搬 Rust。把它单独搬进
Rust 只会造成「判定在 Dart、筛选在 Rust」的跨边界镜像状态，违背「Dart 不存镜像状态」的初衷。整个书同步核心若
将来收编进 Rust 胖核心，这一层随之整体搬，不单独先搬。

## 4. 测试

`fushi/test/sync/sync_book_change_gate_test.dart`（真实 `SyncOrchestrator.run` + 内存资产库假后端，两台设备共用
一份远端）：

- 无快照后端稳态：第二轮 0 次逐本列举，进度回调 0 次，`booksUnchanged == N`。
- 多设备：A 读一本导出 → A 发布清单 → B 下一轮只列那一本并导入；B 的导入让 A 多确认一次后收敛。
- 退出书单本同步也发布清单，B 不必等 A 的下一轮。
- 旧客户端混跑：只写书文件、写聚合快照、不写清单的设备 → B 回退全扫并导入；聚合快照没再变的下一轮恢复跳过。
- 清单损坏 / 本机清单被删 / 超过 24 小时 → 全扫。
- 快照后端：任何写入者改了书文件夹（包括不写清单的）都精确命中，只同步那一本。
- 本地读过的书即使远端没变也进逐本阶段；冲突书每轮照报。
