# AI 库管家：把 AI 从「按功能点调用」提到统管整库的一层（设计稿）

> 状态：设计稿 v1，2026-11-18。**未实现**，§10 的决策点等所有者拍板。
> 起因（所有者 2026-11-17）：「我打算让 ai 的权限高一点，我觉得 ai 层级应该更上一层，现在是那种刮削层级，能自动调整所有媒体的层级，这样可以帮忙分类，刮削之类的。并且可以管理各种媒体的关系。」
> 相关：[AI 整理库](2026-10-20-ai-library-organize-design.md)、[作品图谱](2026-10-24-cross-media-links.md)、[AI 助手与操作目录](2026-10-26-ai-operations-agent-design.md)。

## 1. 要解决什么

现在 AI 是一组互不相干的功能点，每个只管自己那一段，没有谁对「整个库整理好了没有」负责：

| 已有能力 | 管什么 | 现在的限制 | 位置 |
|---|---|---|---|
| AI 整理库（`libraryOrganize`） | 把散条目归进合集 | 只在单个书架域内（书 / 漫画 / 视频 / 游戏），不跨域；可自动跑 | `packages/fushi_engine/lib/media/collections/library_organize/` |
| 合集排序（`collectionOrder`） | 合集内顺序 | 只排规则排不出的成员 | `ai_collection_order_assistant.dart` |
| 作品图谱裁决（`mediaLinks`） | 跨模块「同一作品 / 改编」关系 | **AI 结论一律只是建议**，用户逐条确认才生效；只在用户点「查找相关作品」时跑 | `ai_feature.dart:124-129`、`media_link_inference.dart` |
| 视频身份消解（`videoIdentify`） | 刮削候选里选一个 | 只有视频；书 / 漫画 / 游戏的刮削没有 AI | `ai_video_identity_assistant.dart` |
| AI 助手（`agent`） | 一句话代办操作目录里的任何操作，写操作带撤销 | **只在用户开口时动**，单轮 25 次调用 | `packages/fushi_engine/lib/ai/agent/` |

所有者书库里的实际后果（2026-11-17 只读查本机库）：

- 「十歳の最強魔導師」小说 11 卷和漫画 18 话、「週に一度クラスメイトを買う話」小说 / 漫画 / 特典册、「魔法少女ノ魔女裁判」小说和画集、「志乃と恋」漫画 / 小说 / 在线漫画，各自分散在不同书架，库里没有任何一处把它们表示成同一部作品。
- 作品图谱（`media_links`）有表、有推断、有操作（`links.infer` / `links.accept` / `links.add`，都带撤销），但要用户对每个条目点一次「查找相关作品」再逐条确认，实际没人会这么做。
- 存量合集全部是 `origin=user`（v124 迁移把分不出来源的一律回填成用户的；本机 96 个合集成员全在 `user` 合集里）。AI 整理库的规则是「用户的合集只能往里加」，所以对老库它几乎什么都改不了。

## 2. 目标与边界

目标：

1. **一趟流程管完**：新条目入库后，归合集、认身份并刮削、连跨媒体关系、打分类标签，由一个编排器按顺序跑完，不需要用户逐项触发。
2. **多一层「作品」**：同一部作品的小说 / 漫画 / 动画 / 游戏 / 有声书 / 音乐能作为一个整体被看到和操作。
3. **AI 在关系上的权限从「建议」提到「直接生效、可撤销」**，与 `fushi/CLAUDE.md` §13（所有者 2026-10-26：AI 写操作可以直接落库，但必须能回滚）一致。

不变的边界：

- 用户亲手做的决定永远赢：手动连接、手动否决、用户所有的合集，AI 不覆盖。
- 每一处 AI 写入都记账、可按条或按整趟撤销。
- 联动不用 Bangumi（[作品图谱](2026-10-24-cross-media-links.md) D-L1）。
- 不发文件内容、封面、完整路径、阅读 / 观看记录给模型，口径同 AI 整理库 §11。
- 功能黑名单不受本稿影响（阅读器接 AI、AI 翻译字幕等仍不做）。

## 3. 总体结构

```
触发（入库 / 扫描后去抖 · 手动「整理整个库」· AI 助手技能 · CLI）
   │
   ▼
库管家（确定性编排，不是自由发挥的 agent）
   ├─ ① 规则归组          BookSeriesGrouper / VideoFolderGroupCoordinator        不花钱
   ├─ ② AI 归合集         library.organize.run（四个域各一次，只看新条目）       已有
   ├─ ③ 认身份 + 刮削     缺外部 id 的作品 → 各域刮削；多候选交 AI 选            部分已有
   ├─ ④ 连关系            确定性候选（共享 id / MAL 原作 / 标题）+ AI 裁决       已有，改权限
   ├─ ⑤ 作品层重算        图谱连通分量（纯派生，不落库）                          新
   └─ ⑥ 分类标签          刮削到的类型 → 标签（见 §7，需拍板）                    新
   │
   ▼
每一步都经操作目录（OpInvoker，调用方身份 = model）执行 → 记进 ai_agent_actions
   → 「AI 操作记录」页按整趟 / 按条撤销
```

两个关键取舍：

**编排是代码，不是模型。** 步骤顺序、每步喂什么、什么置信度落盘全部写死，模型只在每一步内部回答一个受限问题（这几个是不是一组、这个候选是不是它、这两个是不是同一作品）。这是 [AI 助手设计](2026-10-26-ai-operations-agent-design.md) §6.3「组合技能」的形态：自动路径不能依赖模型自己规划几十次工具调用，既贵又不稳定。

**不另写一套执行与撤销。** ②④ 已经是带 `undo` 的操作（`library.organize.run`、`links.infer`、`links.accept`），③ 的视频刮削也是（`video.scrape.*`）。库管家以 model 身份经 `AiAgentToolbox` 调它们，记账、凭据脱敏、撤销、可用性判定（iOS 合规门、模块门）全部沿用，会话 id 记成 `curator:<趟 id>`，「撤销整趟」就是现成的会话级撤销。

## 4. 作品层：建在作品图谱上，不做合集嵌套

### 4.1 为什么不嵌套合集

- `media_collection_items.mediaType` 的值域没有 `collection`，合集表是四个库页共用的一张表，自然键 `(name, collectionType)` 是同步 wire 契约。加嵌套要动成员表、合集同步清单、收敛规整（[AI 整理库](2026-10-20-ai-library-organize-design.md) §8）、四个库页的渲染，是风险最集中的一类改动。
- 嵌套表达不了有方向的关系（原作 → 改编）、也表达不了音乐专辑这种不在合集体系里的端点。
- 作品图谱已经解决了跨端身份（各端点用本模块现有的稳定键）、同步（`media_link_sync.dart`）、备份合并、否决墓碑。

### 4.2 作品 = 图谱的连通分量

「作品」不建表，是算出来的：

- 节点：`media_links` 的端点，外加合集成员关系带进来的条目。
- 边：**已生效**的 `same_work` 与 `adaptation` 连接（主题曲 / 原声 / 声优不算，它们连的是附属物，否则一位声优会把半个库连成一部作品）；以及「条目 ∈ 系列合集」（`origin` 为 `rule` / `ai` / `user` 的 playlist，目录合集与主题型 collection 不算）。
- 一个连通分量 = 一部作品。建议态与已否决的连接不参与。

用合集成员关系当边，是因为书的端点粒度是单本（`MediaLinkKind.book` 的键是 bookKey），视频的端点是合集。有了这条边，「小说第 1 卷 ↔ 动画合集」一条连接就能把整套小说带进同一部作品，不需要给每一卷各连一次，也不需要新增端点种类。

作品的展示属性确定性地取，各端结果一致：

| 属性 | 取法 |
|---|---|
| 身份键 | 分量内 wire 端点键字典序最小者（只用于界面状态，如折叠 / 置顶；不落库、不进 wire） |
| 名字 | 优先级：有外部 id 的视频合集刮削标题 → 成员最多的系列合集名 → 最小端点的标题 |
| 封面 | 同名字取到的那个端点 |
| 原作 | `adaptation` 边的源头（入度为 0 的端点）；有环或多个源头就不标 |

计算放 `packages/fushi_engine/lib/media/links/`（纯 Dart 并查集，几万节点线性时间，同 `person_identity.dart` 的做法），结果随 `media_links` / 合集成员表的 `tableUpdates` 失效重算，不持久化。

### 4.3 界面（范围刻意收窄，其余要设计图）

第一期只做不需要新页面的两处：

- 各详情页已有的「同一作品」区块：从「只列直接相连的条目」改成列整个分量，按媒体种类分组。
- 库页合集卡与单本卡上加一个「另有：漫画 · 动画」角标，点了进同一区块。

「作品」作为库页的一种分组视图（一张卡代表整部作品，展开看各媒体）是更大的界面改动，新页面要按规则带动效（`FushiEntranceScope` + `fushiStaggeredItemBuilder`，MD3 与 Apple 两套），先出设计图再做，见 §10 D4。

## 5. AI 在关系上的权限

### 5.1 现状

`applyMediaLinkCandidates`（`media_link_inference.dart:252`）已有 `autoConfirm` 参数：候选有共享外部 id 佐证、且 AI 高置信时直接确认，默认关。其余 AI 结论写成 `source=ai` 的建议。

### 5.2 改成

| 证据 | 现在 | 改后（自动路径） | 改后（手动触发） |
|---|---|---|---|
| 共享外部 id（Wikidata 桥、ISBN 命中） | 建议 | **生效** | 生效 |
| MAL 原作关系 + 标题强匹配 | 建议 | 生效 | 生效 |
| 只有标题匹配，AI 判高置信 | 建议 | **生效** | 生效 |
| AI 判中置信 | 建议 | 建议 | 生效 |
| AI 判低置信 | 建议 | 丢弃 | 建议 |

门槛与 AI 整理库 §7.7 同一口径：没有人工确认的自动路径只落高置信。

### 5.3 「AI 生效」必须和「用户确认」分开存

现在一条连接只有 `isUserConfirmed` 一个布尔。AI 直接生效后如果也写成 `true`，就分不清哪些是用户亲手定的，「用户永远赢」无从执行。所以：

- `media_links` 加一列 `confirmed_by`（`user` / `ai` / NULL）。迁移：`is_user_confirmed = 1` 的行回填 `user`。
- 状态判定：`confirmed_by` 非空 = 已生效；`user` 压过 `ai`。
- 用户在界面上移除一条 AI 生效的连接 = 否决墓碑，任何设备的 AI 不再重提（沿用现有墓碑）。
- 用户确认过的连接 AI 不改关系类型、不改方向、不删除。
- 同步：wire 加可选字段，缺省按旧语义（`confirmed == true` → `user`）。两端对同一对条目一边是 `user` 一边是 `ai` 时取 `user`；一边否决一边 AI 生效时，否决晚于对端基线则否决胜（与合集成员墓碑同一条判新闻规则）。这一段要有多端随机性质测试，做法同 `collection_organize_convergence_test.dart`。

### 5.4 同一部作品被错连的代价与兜底

错连一条 `same_work` 会把两部作品并成一个分量。兜底：

- 作品层是派生的，撤销那条连接分量立刻拆回去，没有需要回滚的派生数据。
- 一条连接让分量规模翻倍以上、或把两个都带外部 id 且 id 不同的视频合集连到一起时，自动路径不落，降为建议。外部 id 不同是「不是同一作品」的硬证据，口径同 AI 整理库 §7.8 第 6 条。

## 6. 刮削：把 AI 消歧从视频扩到书 / 漫画 / 游戏

现状：视频刮削有完整的「候选 → AI 选唯一 → 待确认队列」；书的元数据刮削（`book_metadata_scraper.dart`）与游戏刮削只有手动选候选。

库管家的 ③ 步：

1. 找出「系列合集或单本没有任何外部 id」的作品单元（按合集，不按卷：一套书刮一次）。
2. 用各域现有的搜索入口取候选，不新增元数据主源；动画刮削仍守 [anime-scraping.md](../agent/anime-scraping.md) 的白名单与限流。
3. 单候选且标题强匹配 → 直接认领；多候选 → 交 AI 在候选下标里选（复用 `videoIdentify` 的提示词结构，AI 不产生任何 id）；选不出 → 留在待确认队列。
4. 认领必须可撤销。视频侧现在没有「清除作品身份、退回待确认」的路由（[AI 助手设计](2026-10-26-ai-operations-agent-design.md) §12.2 记录的偏离），这是本步的前置工作：先把认领补成可撤销，否则自动认领违反 §13。

刮到外部 id 之后 ④ 步的确定性候选才多得起来（共享 id 是最强的连接证据），所以 ③ 在 ④ 之前。

## 7. 分类

所有者说的「帮忙分类」有两种可能的含义，做法差别很大，需要拍板（D3）：

- **A. 类型标签**：把刮削到的类型（百合、恋爱、奇幻…）写成标签，库页已有按标签筛选。标签池是用户的（`BookTags`），AI 往里加新标签会污染用户自己的标签体系，所以 AI 的标签要能和用户的区分开，并且用户删掉 / 改名之后 AI 不再写同一个。
- **B. 归到哪个库**：一个条目该在小说书架还是漫画书架、是正篇还是画集 / 特典 / 同人。这是修正导入时判错的 `format`，改的是条目自身属性。

本稿默认只设计 A，且放在最后一期；B 目前没有看到足够多的错判实例，不做。

## 8. 存量合集全是「用户的」怎么办

`origin` 只升不降是多端收敛的前提（AI 整理库 §5.1），不能加一个「降回 AI 管理」的开关：一端降、另一端同时在编辑，两端永远对不齐。

所以不改所有权，改交互：手动触发时，AI 对用户合集的改动建议（并两个合集、把某几卷挪走、改名）不直接执行，汇总成一张确认卡（`ui.ask_choice`），用户勾选后由用户身份执行。这样它是一次用户写入，所有权语义不变。自动路径照旧不碰用户合集。

## 9. 触发、费用、隐私、多端

- **触发**：自动（设置项，默认关，开启时的披露文案沿用 AI 整理库的做法，副标题即完整披露）；手动「整理整个库」按钮；AI 助手技能 `curate_library`；`fushi_cli library curate`；无头服务端 yaml `ai.library_curate`。
- **自动路径只看新条目**：水位沿用 AI 整理库的做法（`local_added_at` 晚于上次跑完的时刻）。④ 步另外把「上一趟之后新拿到外部 id 的作品」也算进来。
- **费用**：一趟的请求数 = 各域分桶数 + 待消歧作品数 + 连接候选批数。手动触发前显示估算（`estimateCost`），跑完在记录页显示 token 用量。不设本地次数上限，口径同 AI 整理库 §10.2（2026-11 删除每日预算）。
- **提供商指派**：不新增 `AiFeature`。每一步用它自己的指派（`libraryOrganize` / `videoIdentify` / `mediaLinks`），库管家只是编排。某一步没指派提供商就跳过那一步，其余照跑。
- **隐私**：发出去的只有标题、作者 / 品牌、年份、卷数 / 集数、视频文件夹末级名、已知外部 id 的种类（不含 id 值）。
- **多端**：合集归组靠分组键收敛（已有）；连接靠 §5.3 的合并规则；作品层是派生的，各端从同步后的同一份数据算出同一个结果，不需要同步。自动开关是设备本地的，文案提示只在一台设备打开，原因同 AI 整理库（省钱，不承担正确性）。
- **iOS**：③ 步用到的在线刮削源按 `StoreRestrictedCapability` 过滤，判据只认 `store_compliance.dart`；经操作目录执行时可用性谓词自动生效，库管家不写平台判断。

## 12. 有意不做

- 合集嵌套、独立的「作品」表。
- 让模型自由规划整库整理（自动路径的步骤全部由代码编排）。
- AI 改条目的文件、文件名或磁盘目录结构。
- 把 `origin` 从 `user` 降回 AI 管理。
- 用 Bangumi 做联动判据。

## 13. 已知风险

- **错连扩散**：见 §5.4。门槛宁严勿松，自动路径漏连的代价只是用户手动点一次，错连的代价是两部作品混在一起。
- **`confirmed_by` 的旧版对端**：旧版不认识这一列，会把 AI 生效的连接当成未确认的建议显示，并可能在同步时用 `confirmed=false` 回写。合并规则必须把「缺字段」当成「未知」而不是「清空」，口径同 AI 整理库 §5.4 对 `origin` / `organizeKey` 的处理。
- **认领撤销是前置工作**（§6 第 4 点）：它没做完之前 P4 不能上自动认领。
- **本稿没有核对的事实**：书 / 游戏刮削写回是否已经从对话框里抽成可编程入口（AI 助手设计 §2.2 当时记为「要先抽出来」，之后有 `ctl_book_metadata_routes.dart`，未读其内容）；`library.organize.undo` 与 `ai_agent_actions` 的撤销是否已经打通成一条。P3 开工前先查这两点。
