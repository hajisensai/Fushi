# SRS 同步 v2：新设备收段通道（先追加、后折叠）

> 状态：已实现（本 PR，叠在 #2802 上）。前置：`docs/specs/2026-11-03-srs-sync2-bulk-bootstrap.md`（下称「第一步」，问题与基线见其 §1–§2）、
> `docs/specs/2026-10-25-srs-sync-v2-design.md`（下称「v2 设计」）。
> 约束不变：不引入快照、不新增信任路径、本机持有每台设备从 seq 1 起的完整前缀（v2 设计 §7.1）；段格式、验签、链校验、操作语义、
> 投影写法、摘要定义都不变。**投影结果与逐条投递逐表相同**（§5）。

## 1. 为什么要独立通道

第一步之后新设备收齐全量真实数据（68 万条操作）仍要 413 s（§6；第一步 spec 记的 458 s 是测试常量下量的，见 §8），大头是逐条投影：每收一条字段修改就读同寄存器的现存行、判清除 / 挂起、
插入、记账，摘要触发器再逐行维护，约十几条 SQL 加几遍 JSON 编解码。新设备的投影是空的，而且收段期间的投影本来就要到收尾才完整
（缓存推迟到收尾刷新，BUG-3999），所以不必一条一条地投：先把操作全部收进日志，最后按实体一次性折叠，结果相同、写入是有序批量。

## 2. 什么时候走

收段会话开始（`sync2_ingest_begin`）时这个 profile 的操作日志与三张摘要投影（`srs_entities` / `srs_field_edits` / `srs_review_logs`）
都是空的——也就是新设备第一次同步。其它一切（日常同步、老设备追赶、一次收完 `ingest`、导入）照旧逐条投递。

## 3. 四个阶段（`native/fushi_fsrs/src/store/sync2/channel.rs`）

1. **追加**（收段的每一片）：投递队列、链 / 因果 / 分叉校验都不变，只把「`insert_op` + `project`」换成：写进操作日志，记下投递顺序
   （`sync2_boot_order`：序号 + 折叠分区）。旧修改记录闭包（`sync2_legacy`）按 `note_legacy` 同一算法在内存里更新、每片写下；
   复杂实体的种子与移卡记录另存。
2. **折叠**（收尾）：64 个分区逐个折。按投递顺序读出这个分区的操作：
   - 字段修改按实体一次交给 `land_stored`（「依次到达」与逐条落用同一判据）；
   - 复习日志与 `sync2_log_meta` 先到先得、`sync2_edit_ops` 后到者胜、`sync2_ent_ops` 先到先得、服务器时刻取落库那几份的最小值、
     `received_at` 取第一次落库那一片的时刻——与逐条投递的 INSERT OR IGNORE / REPLACE / MIN 合并逐条对应；
   - 身份记录同 ID 内容不同取规范文本小者（`project_entity` 的规则）；
   - 算出的投影行按存储形态（ID 已编码、`jslim` 已打包）追加进暂存表 `sync2_boot_rows`（rowid 表，按分区顺序追加），摘要按
     触发器同一个行哈希记增量（`digest.rs` `Deltas`）。
3. **归并**（收尾，各分区折完之后）：暂存的行按表、每步至多 `MERGE_CHUNK`（65536）行写进投影，写过的暂存行同一步删掉。三张摘要
   投影关掉主库触发器写，TEMP 触发器（复习队列 / 浏览的待重读）照常触发。
4. **逐条**（收尾，归并之后）：标签、媒体、清除、检查点等，以及**复杂实体**上的一切，按投递顺序走生产的逐条投影。它们碰的
   实体 / 寄存器与折叠写的不相交，先后无关；但要读折叠写出的行（牌组的挂起判定读移进来的卡），所以排在归并之后。

收尾的推进按分发器的时间片切（`ingest_finish` 返回 `more`，Dart 照旧循环 `replay_pending`）：一个分区在一片里折完，归并一片一块，
逐条阶段按条切；通道做完才开始重放与缓存刷新。Dart 一行没改。

### 3.0 为什么要暂存再归并

投影几张大表的键都是散列 ID（修改记录 ID 是 UUIDv5，日志 / 实体 ID 随机），二级索引按实体 / 卡排。按分区直接写，每个分区
一次提交都要把这些索引的大部分页重写进 WAL 一遍：真实全量数据 64 个分区折叠 205 s，其中写入 92 s、提交与检查点约 80 s。
暂存表是顺序追加，折叠只剩 63 s；归并时一块只碰一张表的索引，留在页缓存里，每块写一遍（41 s）。

块的大小：一步一个事务，提交前 WAL 要装下这一步写的全部页，而内核的检查点是 PASSIVE、不截短 WAL 文件。整张表一次写完时
WAL 涨到 418 MB；全部归并完才清暂存时，归并写的新页用不上暂存腾出的页，库文件涨到 1813 MB。每块 65536 行、同一步删掉写过的
暂存行之后，库文件与 WAL 都与逐条投递相同（1152 MB / 128 MB）。

### 3.1 复杂实体

种子：有过 `deleted` 写入的实体、被清除的实体、带合成写入者的旧修改记录所在的实体（合成写入者的旧 `tags` 整列表除外——它走标签
路径、本来就逐条）。追加结束时补一层：移进复杂牌组的卡也算复杂。

理由：删除的挂起判定（`semantics.rs` `evaluate_holds` / `should_hold`）读的是「到这一刻为止」碰过这个实体的操作；清除让之后到的旧写入
当场清掉、改写操作日志里的载荷——都与投递顺序交错，不能折。牌组的挂起判定要看移进来的卡（`#move`），所以移进复杂牌组的卡要逐条；
卡不会让别的实体变复杂（日志按卡与笔记两边判），一层就够。真实全量数据里复杂实体只有 2 个牌组和少量笔记。

### 3.2 旧修改记录闭包为什么能在折叠时算

v2 写入的投影行要并上作者见过的旧修改记录闭包（`legacy_closure`）。折叠时按追加完的最终 `sync2_legacy` 算，与逐条投递时按「到达那一刻」
算结果相同：作者见过某设备到 seq s，那台设备 s 以内的操作在它之前都已投递，两种算法都等于「那台设备 seq ≤ s 的旧记录之并」。

唯一的例外：其中有旧记录后来被清除（部分覆盖的那一支跳过已清除的载荷）。这要同时满足「迁移进来的旧记录被清除」与「v2 写入只见过
那台设备迁移操作的一部分」——而逐条投递在这种情形下**本身就随到达顺序而变**（同一批操作在两台设备上可能算出不同的 ctx），通道的结果
是其中一种合法顺序的结果。真实全量数据里部分覆盖的闭包为 0 次。

## 4. 与其它命令的交互

- **进度表（srs.db v22）**：`sync2_boot`（阶段、下一个序号、游标）、`sync2_boot_order`、`sync2_boot_complex`、`sync2_boot_moves`、
  `sync2_boot_rows`（暂存）。通道做完五张表的行全删；删 profile 时随 `profile_tables` 一并删。
- **断点续收**：追加阶段被打断（App 被杀），下一次 `ingest_begin` 接着追加；折叠 / 归并阶段被打断，下一次 `ingest_begin` 先把它
  做完，这一轮按逐条投递收；中间 Dart 调 `replay_pending` 也会推进它。归并的进度就是「暂存里还剩什么」：一块写进投影与删掉
  暂存行在同一个事务里。
- **通道没做完时的其它命令**（`ffi.rs` `sync2_dispatch`）：会改投影或依赖完整投影的命令先把通道做完（`CHANNEL_TRANSPARENT` 白名单之外的
  一律如此，漏列只多花时间、不会错），之后这一轮按逐条投递收。白名单里是收段命令本身、只读命令、不碰投影的传输记账。`digest` /
  `digest_buckets` 不在白名单：摘要按已应用的版本向量发布，投影不全时算出来的会被别的设备当成分歧。Dart 的同步一轮里 `digest` / `head`
  都在收段收尾之后，不会提前触发。
- **一次收完 `ingest`、导入、换身份**：先把通道做完再投递 / 换。
- **读命令**在通道做完之前看到的投影是空的（逐条收段途中看到的是部分的），收尾后一致。新设备第一次同步时本来就没有可复习的内容。
- **本机在追加途中写入**（作答等）：分发器先把通道做完——那一次写入要等折叠完已收的部分，之后逐条投递。

## 5. 正确性守卫

- `tests_channel.rs`：伪随机多设备世界（并发改字段、删除 / 恢复与挂起、清除、整列表标签、复习、移卡、删牌组、两台设备迁移同一个旧库、
  合成写入者的旧标签、分两批迁移造成的部分闭包），经生产分发器的分批会话收完，一边走通道、一边关掉通道，**全部表逐行相同**（缓存表的
  `updated_at` 是刷新时的墙钟，不比），复习队列 / 浏览的待重读相同，摘要桶与整表扫描一致。覆盖计数断言随机世界走到了折叠、复杂实体
  逐条、折叠里「落了又被支配」、移进复杂牌组四条分支。中途打断四组：追加到一半重开会话、追加到一半本机写入、折叠到一半重开会话、
  归并到一半（一张表分几块，测试里一块 4 行）重开会话。
- 只有新 profile 走通道；有操作日志的 profile 照旧逐条。
- 真实全量数据：§6。

## 6. 实测

真实全量数据（68.4 万条操作，投递 64.9 万条），桌面 Windows，`probe_sliced`：生产分发器、8 MiB 一批、按节奏并回 WAL，
`--cfg srs_probe` 构建（§8）。两种收法同一份代码，`PROBE_SEQ=1` 关掉通道。

| | 逐条投递 | 通道 |
|---|---|---|
| 收段（各片） | 279 s（218 片） | **37 s**（38 片） |
| 并回 WAL | 64 s | 2.4 s |
| 收尾（`ingest_finish` + `replay_pending`） | 66 s（74 次） | 187 s（225 次） |
| **合计** | **413 s** | **229 s** |
| 库 / WAL | 1151 MB / 78 MB | 1152 MB / 128 MB |

结束后逐表比行数与内容哈希：46 张表全部相同（不比本机身份 `sync2_self` / `sync2_devices`、带墙钟的 `srs_notes_cache` /
`srs_meta`）。

通道的收尾按阶段（`probe_channel_finish`，从收尾前存下的库起）：

| 阶段 | 耗时 | 调用 | 单次最长 |
|---|---|---|---|
| 折叠（64 个分区） | 63 s | 64 | 3.2 s |
| 归并（7 张表，每块 65536 行） | 41 s | 43 | 3.7 s |
| 逐条（整列表标签 1.5 万条 + 2 个复杂牌组） | 12 s | 39 | 0.5 s |
| 重放（17386 张卡） | 20 s | 34 | 1.7 s |
| 缓存刷新（3.5 万实体，每块 512） | 44 s | 40 | 1.7 s |

暂存之前（折叠直接写投影）同一份库的收尾是 301 s，其中折叠 205 s（§3.0）。

## 7. 还能再快的地方（没做）

按 §6 的收尾分解：

- 缓存刷新（44 s，40 块）与重放（20 s）在通道之后照旧做。下限探针（`probe_finish_floor`：日志与笔记修改记录各顺扫一遍、
  内存里算）15 s；新设备可以把它们与折叠合成一遍日志顺扫。
- 折叠本身（63 s）：读回操作并解压 9 s、算行 8 s、写暂存 27 s（含 `jslim` 打包）。暂存可以省掉打包，归并时再打包。
- 归并（41 s）：三张摘要投影的二级索引仍是散列键随机插入。
- 整列表标签（真实数据 1.5 万条）仍逐条投（12 s），可以按笔记折。
- 追加阶段的压缩与解码可以并行。

这条路能到多快：不引入快照，本机要把 68 万条操作各验签、各写进日志、各投进投影、再重放与刷新缓存。各段在桌面实测的下限相加
——验签解码 + 折叠 + 有序批量写约 20 s（第一步 spec §2 `probe_fold_floor`）、只写操作日志约 30 s（`probe_ops_store`）、重放 + 缓存
约 15 s（`probe_finish_floor`）——约 1 分钟，平板约 3 倍。要到 Anki 下载整库的量级（十几秒、与条数无关），只能换成「下载对端整理
好的投影、只验证不重放」，那是新的信任路径（v2 设计 §7.1 排除的），要另立设计。

## 8. 探针的常量（`--cfg srs_probe`）

冷启动探针（`bootstrap_probe.rs`）跑在测试构建里，而测试构建把几个切片 / 缓冲常量压得很小，好让端到端用例走遍分支：投递窗口
3 条（生产 4096）、缓冲 2 KiB（16 MiB）、预处理留存 4 KiB（2 段）、收尾缓存每块 5 个实体（512）、归并每块 4 行（65536）。拿它
量耗时，数字比 app 慢很多（收尾的缓存一项就是 4188 块 / 198 s，生产是 40 块 / 44 s）。探针改用 `RUSTFLAGS="--cfg srs_probe"`
单独构建，这几处取生产值；第一步 spec 与本 spec 早先的数字是测试常量下量的，两种模式之间可比，绝对值偏大。

## 10. 2026-11-12 复测：时间花在哪、两处提速

起因：通道合入后，Dart 端到端基准（`srs_sync2_ingest_bench_test.dart`）仍是 16 s，看起来「通道没让首次同步变快」。

### 10.1 先把数字对上

- 「内核探针 2.5 s」与「Dart 端到端 16 s」不是同一份数据：前者是本机一份真实小文件夹（2.5 万条操作），后者是合成的 2 万条
  笔记（每条一个约 8.4 KB 的长字段，8 万条操作、正文约 170 MB）。同一份数据上两者几乎相等：Windows 上 Dart 端到端
  12.7～13.5 s（5 次），其中内核命令 11.7 s（`ingest_prepare` 0.3 + `ingest_commit` 1.0 + `ingest_finish` 0.2 +
  54 次 `replay_pending` 10.2），Dart 那一侧（列目录、读 13 个文件 0.9 MB、跨 FFI、写锁外并回 WAL）合计约 1 s。
  时间全在内核的收尾里。基准里加了 `INGEST_TRACE` 三行（各步骤时刻、宿主各入口、内核命令账本）可以直接看到。
- §6 的 229 / 413 s 本身就是内核探针的时间，而且含两笔 app 里没有的开销（那份数据不在本机，没有重测，§6 的表保留原样）：
  - **ID 绑定审计**（store/ids.rs，测试构建才有）：每条语句执行前把绑定参数展开成 SQL 文本。采样里占 17%，逐行执行的语句
    越多越吃亏。探针构建（`--cfg srs_probe`）现在不在写连接上装它。
  - **收尾各片的 WAL 并回**：探针的收尾原先照缺省的 1000 页自动并回（每片提交都在写连接上并一遍 + fsync），生产的
    `SrsDbStore.sync2IngestFinish` 是 `bulkWrites`（16384 页）+ `SrsWalCheckpointPacer` 在写锁外按节奏并回。探针改成同一
    做法（`PROBE_FINISH_AUTOCKPT=1` 还原旧做法作对照）。「收尾 187 s」是在旧做法下量的。
- 合成的日志型数据（`ingest_mem_bench.rs` `SRS_BENCH_OUT`）原先有两处不像真实文件夹，量出来的阶段占比是歪的：
  - 复习日志的结果是占位值，收方重放把每一条日志改写一遍（真实作答的结果由内核预览算出，重放不改写）：重放阶段一半时间
    花在这上面。`SRS_BENCH_ANSWERS=1` 生成与重放一致的结果。
  - 测试用的桶不删被合并取代的小段，950 个文件里只有 16 个是现行的，同一条操作在很多段里重复出现（126 万条 / 实际 32.8 万）。
    落盘时只写现行的那条链（`current_segments`）。

### 10.2 分布（改之前）

`probe_sliced`（生产分发器、8 MiB 一批、按节奏并回、不带审计），Mac mini M4、空闲（负载 2），每项 5 次取中位数。
日志型 = 8000 张卡 × 35 次复习 + 每条笔记一条整列表标签（32.8 万条操作，库 421 MB）；笔记型 = 上面那 2 万条长字段笔记。

| 阶段 | 日志型 | 笔记型 | 主要在做什么 |
|---|---|---|---|
| 预处理（解密、解压、验签、解码） | 0.5 s | 0.3 s | 后台线程，不占写锁 |
| 追加（操作日志 + 暂存顺序） | 3.7 s | 0.9 s | 逐条压缩载荷（zstd）占日志型全程约 9% |
| 折叠（64 个分区 → 暂存表） | 5.1 s | 2.3 s | 写暂存行 2.7 s / 1.4 s |
| 归并（暂存 → 投影，按表成块） | 4.1 s | 1.7 s | 写页最多（14 万页 / 5.6 万页） |
| 逐条（整列表标签） | 1.2 s | — | |
| 重放（8000 张卡） | 6.5 s | — | 算调度 5.3 s，读日志分组 0.9 s |
| 缓存刷新 | 2.7 s | 1.0 s | 有效复习投影 1.5 s、笔记行 1.2 s |
| 并回 WAL | 0.8 s | 0.3 s | |
| **合计** | **24.7 s** | **6.4 s** | |

没有哪一段是「卡住」的：最大的一段也只占四分之一，SQLite 的执行占全程约 57%，其余是 JSON、压缩与调度计算。

### 10.3 改了什么

1. **重放的记忆状态接着上一条日志的算**（`sync2/replay.rs` `MemoryMemo`）。重放一张卡时，每条派生日志都要「作答前」的记忆
   状态，原先每条都把前面的评审从头走一遍（一张复习 n 次的卡走 1 + 2 + … + n 次 `Model::step`）。同一归属组里下一条的输入
   几乎总是上一条的输入再多一次评审：记下上一次的输入与结果，是延伸就只算多出来的那几次；起点、任何一次的评分或间隔
   （按 f32 位模式比）不同就从头算，模型换了也重来。结果与从头算逐位相同（`carried_over_memory_state_matches_recomputing_on_random_histories`：
   120 份随机历史对拍）。重放的计算 5.3 s → 3.8 s。
2. **归并不再把暂存行物化进临时表**（`channel.rs` `ROW_TRIGGERS` / `RowTriggerOff`）。目标表上只要有行触发器，SQLite 的
   `INSERT … SELECT` 就先把 SELECT 的结果整份写进临时表、再逐行插；修改记录、复习日志、到达戳三张表上有复习队列 / 浏览
   会话的 TEMP 插入触发器（queue.rs）。笔记型数据的修改记录一块 6 万行、500 MB 载荷，等于多写、多读一遍临时文件。归并这
   三张表时把触发器拿掉、写完对同一批行成块登记、再装回去（同一个 savepoint 里，失败一起回滚）。登记的集合与逐行触发相同
   （各条「通道 ≡ 逐条投递」对拍比较待重读集合），`merge_statements_never_materialize_their_rows` 按 `EXPLAIN` 守着每张
   目标表的写入语句不开临时表。修改记录的归并 1.10 s → 0.87 s，进程峰值内存 364 MB → 256 MB。

### 10.4 试过、不成立的

归并改成自己读暂存行、逐行绑定单行 `INSERT`（也不物化）：复习日志那一步 1.7 s → 5.6 s。每行一条带触发器的语句就要一份语句
日志（事务里改过的页每条语句再抄一遍进子日志，采样里占这一步的 54%），单条语句的固定开销又占一份。`INSERT OR FAIL` 没能
免掉语句日志。物化比逐行便宜，所以改成上面「拿掉触发器」的做法。

| Mac M4，`probe_sliced` | 日志型 | 24.69 s（24.59～25.29） | 23.04 s（22.96～23.86） | −6.7% | 501 → 460 MB |

### 10.6 剩下的（量过，没做）

- **暂存再归并是每行写两遍**（折叠写暂存 2.7 s + 归并 4.1 s，日志型）。§3.0 的理由（投影的二级索引是散列键）还在，
  不暂存更慢；要省只能省暂存的那一遍编码，或让日志 ID 有序——后者是协议层面的事。
- **重放要算四个按钮**（`next_states`，占日志型全程约 10%）：`plan_answer` 里四个评分的间隔互相约束，FSRS-7 的间隔是迭代求根，
  超越函数走确定性的软件实现（各平台逐位一致的前提）。只算用到的那几个评分的间隔能再省约 1 s，要改 `plan_answer` 的结构。
- **最外层是 SAVEPOINT**（`in_savepoint`）：pager 给它开保存点，事务里第一次改的每一页都先抄进子日志（约 6%）。最外层改用
  `BEGIN` 能免掉，但它是全部 sync2 命令共用的事务边界，要单独评估。
- **逐条压缩载荷**（约 9%，其中 zstd 6%）与追加阶段的解码可以挪到后台预处理线程（§7 已列）。
- 整列表标签逐条投、缓存刷新与重放各读一遍日志（§7 已列）。
