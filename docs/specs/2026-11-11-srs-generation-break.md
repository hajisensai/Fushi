## 0. 一句话

**操作日志是唯一的真相，其余全是能从它重建的索引和缓存；历史靠「逐条、确定、只看这条操作自己」的转译过界，所以不需要谁先谁后，也不会出现第二份历史。**

三件事一次做完：

1. **存储**：本机只留一层真相（操作），旧事件投影和笔记 / 卡片缓存之间那一层删掉；真实库 1.75 GB → 新代文件实测 0.42 GB（真相层、索引、别名、语义摘要、笔记 / 卡片缓存与统计行全部在内，G6c 跑了 2 次，§2.6）。
2. **格式（协议 4）**：新写入不再携带、不再生成任何 v1 形状的因果数据；媒体「在不在」不再是永久操作；head 自带按位置签名的加密标记；
   旧设备日志变成冻结的「承袭日志」。
3. **身份**：集合与 profile uid 脱钩；ID 规则表去掉 uid 这个盐；存量带盐 ID 不改写，在派生层当别名归一；并入 = 操作并集，不再重算 ID、不再追加副本。

代价也要先说：换代是一次全设备、含服务端的同版本升级（§9 第 1 项）；别名归一是本稿风险最高的一块（§5.3、§10）。

## 1. 现状与体积去向（实测）

### 1.1 三层存储

| 层 | 表 | 说明 |
|---|---|---|
| 操作日志 | `sync2_ops`（`native/fushi_fsrs/src/store/sync2/schema.rs:28`） | 每设备哈希链，载荷是操作的线格式字节，每行另存 32 B 链值 |
| 旧事件投影 | `srs_entities` / `srs_field_edits` / `srs_review_logs` / `srs_event_local`（`native/fushi_fsrs/src/store/schema.rs:133-177`） | v1 时代的「事件表」，v2 迁移时原样留下（v2 设计 §13 第 5 条），之后每条操作都再投影成一行 |
| 缓存 | `srs_notes_cache` / `srs_cards_cache` / `srs_stat_reviews`（`schema.rs:191-255`） | 出卡、浏览、统计实际读的表 |

三层之间还有一批「谁对应谁」的映射表：`sync2_ent_ops`、`sync2_edit_ops`、`sync2_log_meta`（`sync2/schema.rs:82-106`）。
写入路径是 `sync2_apply_local` → `project_body` → `land_edit` / `project_log` / `project_entity` → 缓存刷新
（`native/fushi_fsrs/src/store/sync2/mod.rs:1252`、`:1397`、`:1495`、`:2165`）。**没有「从 `sync2_ops` 全量重建投影」的入口**：
投影层丢了就回不来，所以它事实上也是真相——这是体积与复杂度的根。

出卡（`store/queue.rs`）、学习（`store/study.rs`）、浏览正文（`native/fushi_fsrs/src/store/browse.rs:1317-1320` 整列读
`srs_field_edits.jslim`）、统计、摘要（`store/sync2/digest.rs:109-113` 覆盖的是投影表的 JSON）读的都是下面两层；`sync2_ops`
只在发件、收件判重、时间线里读。远程复习搬给客户端的也是投影层的修改记录（§7）。

### 1.3 结论：同一份内容存了几遍

1. **字段正文两份**：操作载荷里一份，`srs_field_edits.jslim` 里一份（`edit_row_with`，`store/sync2/mod.rs:977-1027`）。
   活着的修改记录正文合计 303.5 MB（其中两个大字段 5,913 条就占 201.1 MB，平均 34 KB、互不相同），表本身 399.6 MB。
2. **复习日志三份半**：操作载荷 104.6 MB、`srs_review_logs` 174.6 MB、`sync2_log_meta` 52.7 MB、`srs_stat_reviews` 27.0 MB。
3. **副本骨架**：580,100 行（占操作行数 43%）是 `purged = 1` 的骨架。它们是旧并入把另一个 uid 的数据重算 ID、改写入者名字后
   追加进来的副本，之后被去重作业判为「某条的副本」留下的壳（`Op::duplicate`，`native/fushi_fsrs/src/sync2/op.rs:97`），约 85 MB 载荷。
   核验实测：308,420 条修改骨架与它指向的原件**旧写入者全部不同**（骨架是 `merged-…`，原件是原写入者），把两者连起来的只有骨架里的 `of` 指针。
4. **v1 因果上下文**：351,228 条修改记录带 `LegacyStamp`，合计 75.2 MB，其中 `ctx_json` 34.8 MB、写入者名字 16.2 MB、HLC 文本 22.1 MB。
   上下文本身很小：95.5% 只有一个条目，文本体积几乎全是写入者名字（46 字符的旧写入者、`merged-<uuid>`、`sync2:tags:<note>`）。
5. **映射表与死列**：`sync2_ent_ops` + `sync2_edit_ops` + `sync2_log_meta` 170.1 MB；`srs_event_local` 105.7 MB，
   它的 `outbox_seq` 现在只写 NULL（`store/sync2/mod.rs:1039`），真正被读的只有 `server_time` 一列。
6. **每条操作一份链值**：32 B × 133.7 万 ≈ 42.8 MB，实际只在切段处、日志尾部和判分叉时用得到。

### 1.4 v1 因果嵌在 v2 里的四处

1. 每条修改操作可带 `LegacyStamp{writer, seq, ctx_json, hlc, server_time}`（`sync2/op.rs:294`）；
2. 投影行的 `ctx`：v2 原生写入的修改记录也要拼一个 v1 形状的上下文——作者的依赖向量并上「旧修改记录闭包」
   （`edit_row_with`，`store/sync2/mod.rs:977-1005`；闭包存在 `sync2_legacy`，`sync2/schema.rs:192`）；
3. 寄存器判定走 v1 规则：谁的 `ctx` 含对方的 dot 谁支配，剩下的按 `(physical, counter, hlc_writer, id, server_time)` 取最大
   （`native/fushi_fsrs/src/registers.rs:143-163`、`:458-496`）；
4. 合成写入者 `sync2:tags:<note>`（`registers.rs:42`）与对应的剥离函数（`store/sync2/mod.rs:389`、`:598`）。

媒体绑定、`MediaAt`、标签顺序三类寄存器已经用了 v2 自己的规则（`native/fushi_fsrs/src/store/sync2/mvr.rs:1-15`：因果优先、
并发才比 HLC），字段修改没有。摘要覆盖的投影 JSON 里含 `ctx`，所以摘要也绑在 v1 形状上。

### 1.5 身份建在随机 uid 上

- 每台设备第一次打开复习时随机生成 `profiles.uid`（UUIDv7）；集合标识 = `v5(NS, "sync2/collection/{uid}")`
  （`collection_of`，`native/fushi_fsrs/src/store/sync2/mod.rs:111`），同步目录是 `fushi-srs/<uid>/v3/`。
- 规则表里凡是根上的 ID 都拿 uid 当盐（`packages/fushi_srs/lib/src/ids.dart:117-195`）：笔记 `uid/note/<guid>`、笔记类型
  `uid/notetype/<ankiNum>`、牌组 `uid/deck/<全名>`、内置默认牌组 `uid/builtin-deck/default`；字段 / 模板由笔记类型 ID 派生，
  卡 = `v5(noteId, templateId/clozeOrd)`，导入的日志与锚点由卡 ID 派生。profile 级设置（日界等）挂在一个 ID 就是 uid 的实体上。
- 于是两台各自生成过 uid 的设备要成为「同一个库」，只能把一边的全部数据按新 uid 重算 ID 再追加成新操作
  （`packages/fushi_engine/lib/srs/srs_profile_merge.dart` 文件头注释，1234 行）：能还原派生输入的重算，还原不出的走兜底
  `v5(NS, profile-merge/<newUid>/<旧 ID>)`，写入者改名成 `merged-…`，undo 的目标没到就暂缓整次并入。
  BUG-4011 / 4217 / 4218 都出在这条路上；§1.3 第 3 条的 58 万条骨架是它的直接产物。
- 投影与缓存表的主键是全库唯一的 `id`，不带 profile（`store/schema.rs:133-231`），同机两个 profile 靠「ID 里带 uid」才不相撞；
  这也是 v2 设计 §3.1「内置实体固定常量」至今没法照字面做的原因。
- `profiles.uid` 会被改（采用对方 uid、并入后切换），而它同时是备份 / 还原 / 统计 / 媒体目录的键，主库与 srs.db 两个文件
  不能一起提交（`srs_profile_merge.dart` 文件头「原子性」一节的四步顺序）。
- Dart 侧到处「用 uid 现算一个 ID 再拿去比」：带盐派生的调用点约 58 处，例如远程复习客户端现算默认牌组与内置类型 ID
  （`fushi/lib/src/srs/srs_remote_store_client.dart:325-329`）；内核重放也用 `default_deck_id(profile)`（`store/sync2/config.rs:21`）。
  同步目录路径同样由 Dart 按 uid 拼。

## 2. 目标存储模型

### 2.1 三类表，只有一类是真相

- **真相**：操作（每个集合、每台设备一条日志）。本机不可再生、同步时交换的只有它。
- **派生**：索引与缓存。全部能由一条内核命令从操作重建，口径变了就重建，不参与同步、不参与备份。
- **本机状态**：设备密钥、信任表、位置进度、待投递队列这类「不属于集合、别的设备也不该知道」的东西，量很小，原样带过去。

每个集合有一个本机集合号 `col`（小整数，对应 §5.1 的绑定表）。设备用全库唯一的小整数下标（`devs(dev, col, id, …)`），下标本身就带着所属集合；
按操作寻址的表，键是一个整数 `k = dev << 40 | seq`（下标 < 2^22，seq < 2^40）：点读与顺序扫都是一次 B 树下降，行里不再重复存 `col` 与 `dev`。
集合号只出现在 `collections`、`devs` 与按实体寻址的派生表上。同机多个 profile / 多个集合天然不相撞，不再依赖「ID 里带盐」。本机状态现在按 profile 分行（例如 `sync2_self` 每个 profile 一行），换代后按 `col` 分行，含义不变。

### 2.2 表（示意，定名随实现 PR）

| 类 | 表 | 键 | 内容 |
|---|---|---|---|
| 真相 | `ops` | `k` | 一条操作：HLC、依赖（内部化的版本向量号）、种类、标志、操作体，操作体只存这一份；承袭操作另带 8 B 原链值指纹（§3.2）与转出它的 T 版本。原样件（§3.1）按协议 3 的原字节存、单独标记。本机存储编码见表后 |
| 真相 | `op_alias` | `k` | 副本记录：这个操作号是另一条 `(设备, seq)` 的副本；带种类、HLC 与它自己的旧戳（可无）（§3.1）。标志里有一位记「这个槽现在的样子是本机推进出来的」（收来的没有） |
| 真相 | `op_voids` | `(dev, first)` | 空洞区间：这段 seq 没有内容（已清除、不过界的种类）。承袭空洞每个 seq 留 8 B 链指纹；原生日志的空洞每个区间留区间末的 32 B 链值，用来接上后面的链（附录 B 第 9 条），区间内部没有链值。相邻的空洞存成一个区间，但本机清出来的与收来的不并在一个区间里（同样有「本机推进」的标志位） |
| 真相 | `op_pending`、`op_forks` | `k` / `(k, fp)` | 待投递的槽，带前一环的链指纹 `prev_fp`（§3.1）；旧设备分叉的另一支，不参与派生（§3.2） |
| 真相 | `devs`、`op_deps`、`writers`、`log_marks`、`snapshots` | | 设备表（承袭日志记它的来源集合）；依赖向量内部化表；旧写入者名字内部化表（存紧凑名字字节形，不是文本）；链值记号——原生日志每 1024 条一个，承袭日志存**完整原链值**（迁移时每 4096 条与日志末尾各记一个，写入时核对它与该处槽的链指纹相符）；日志引用的调度配置快照（v2 设计 §4.6） |
| 派生 | `ent_ix` | `(col, id, k)` | 实体的身份记录。同一个 ID 可以有多条（两台设备各建一条），带胜者标记的那条是定义 |
| 派生 | `reg_ix` | `(col, 实体种类, ent, key, k)` | 寄存器的全部写入 + 状态：被支配（或同 dot 的非代表）/ 没被支配但不是胜者 / 胜者 / 胜者且冲突（时间线读全部，正文读胜者）。`key` 存修改键的紧凑字节形 |
| 派生 | `log_ix` | `(col, card, at, k)` | 日志索引，带日志 ID 与胜者标记；按日志 ID 查走它上面的一条索引 `(col, id, k)`，不另设表。统计列不在这里：它们是逐卡重放的输出，在缓存层的 `stats` |

| 本机状态 | `media_local`、`media_at` | | 本机媒体文件登记；各位置「有哪些媒体」的缓存（§4.5） |

本机存储编码（压缩、写入者内部化）与线格式分开定版本：线上是规范字节（链与签名算它），本机怎么存是存储细节，以后可以再改而不动协议。
G6 第一部分（#3379）的编码做三件事，三件都**写时核对**——存储形态解回来与规范字节逐字节比一遍，不等就整条原样存，可逆性不靠相信编码器：

1. 承袭修改的旧戳从操作体尾部摘下来另存一列，名字换成表下标；摘掉之后的主体仍是一条合法的、不带旧戳的修改，整列读正文不必碰旧戳；
2. 日志的配置快照原文剪出来按内容存一份；
3. ≥ 256 B 的存储字节 zstd，省不下八分之一就原样存。

写入者名字在线格式里**内联**在每个旧戳里（操作体自包含，T 只看这一条）；「名字表 + 下标」只是本机存储的内部化，§2.6 的两种旧戳体积口径由此而来。

真相表的键里没有规范 ID：`ops` 按 `(设备下标, seq)` 寻址，实体 ID 只出现在操作体里；索引按操作里写的原值 ID 建，规范 ID 是其上的一层映射（§5.3）。
所以别名规则怎么改都只动派生表，不动真相。

**同一个 ID 有多条时取哪一条**不能依赖到达顺序（协议 3 的日志是「先到的留」，存量重复再靠去重作业收敛到设备 ID 小的那份）：
身份记录取规范文本最小者，内容相同取操作号最小者；日志取操作号（设备 ID 字节序，再 seq）最小者。两条都只看集合内容，
`rebuild_all` 与逐条维护因此逐行相同。同一个日志 ID 有两份内容不同的、而协议 3 的去重作业还没跑完时，两边选的可能不是同一份；
对拍按日志 ID 集合比不受影响，按内容比时要按这条规则解释差异。

**清除分两步**（G6c-1）：派生层只给已清除的操作打逻辑标记（`reg_ix.state = -1` / `tag_ix.state = -1`），它们不参与任何判定；
把它们在真相层落成空洞是另一步（`Index::execute_purges`，本机执行）。落不落，派生表（含别名表、语义摘要）都一样，所以一台落了一台没落不是分叉（唯一的例外来自「闭包随清除变小」，见 §3.4 末）。
规则：实体 E 上生效的 Purge 记为 P，E 的内容操作 x 只要有一条 p ∈ P 是 x 的作者没见过的就是已清除；见过全部清除的是清除之后的写入，照常生效。
日志、身份记录、媒体绑定、`deleted` 不受清除影响。`Truth::advance_purge` 是本机把完整内容推进成空洞的唯一入口，遇到 `Salts` / `Join` 报错、整个事务回滚（§10 第 17 条）。

**派生表的宿主输入** `derive_cfg(col, key, value)`：派生表是「真相 + 本机信任状态 + 宿主输入」的函数。宿主输入只剩一项 `caches`——缓存配置，
含内置笔记类型的完整默认定义（字段名、模板、默认牌组等，样本配置 136 KB），随应用版本走；没设就不物化缓存，配置变了由调用方调 `rebuild_caches`。
别名判定用的内置笔记类型表已进内核（§5.3），不再是宿主输入。存进库里是为了重建与逐条维护读同一份。

**查询计划是 schema 的函数**（G6c-2 后续提交）：派生表的键都以 `col` 打头，没有统计时 SQLite 把「`col` 相等」估成只剩 10 行，按键查询退化成整集合扫描
（样本库上语义摘要重建因此要 1,150.8 s）。新库不跑 `ANALYZE` / `PRAGMA optimize`：schema 安装时写一份只表达形状的 `sqlite_stat1`，统计随 schema 发布；
守卫测试 `lookups_with_a_key_never_walk_the_whole_collection` 把派生层全部语句在空库上 `EXPLAIN` 一遍（整份物化那类按设计扫整集合的列白名单）。

**读命令的顺序契约**（G5a 的教训）：读命令的结果凡是有顺序语义的，一律显式写 `ORDER BY`，不依赖查询计划恰好给出的顺序。
G5a 给读加上 profile 条件后规划器换了索引，`edits` 的记录顺序（决定物化后的字段顺序）随之变了，修法是显式 `ORDER BY f.entity_id, f.rowid`；

### 2.5 重建是一等命令

`rebuild_all(col)`：清空派生表 → 顺序扫 `ops` 建索引 → 别名表整表重算 → 语义摘要整个重算 → 物化笔记 / 卡片缓存与统计行（逐卡重放）。
G6 第一部分实现了建索引；其余各步 G6c 实现（#3383 → #3393），全程已在样本库上跑过（§6.5）。迁移时不逐条维护索引（每个带旧戳的槽都会让闭包变、
多写入的寄存器全部重判），灌完真相层后调一次 `rebuild_all`；`rebuild_all` 期间摘掉摘要的触发器，最后整个重算。
逐条维护的收尾（`Index::settle`）只重算这一批碰到的部分：缓存层按「前身 ↔ 后继」连通分量重放，摘要只算 `dg_dirty` 里的实体，别名表见 §5.3「重算与增量」。
样本库上「逐条维护（一条一条落、每批收尾）」与「从空重建」的 20 张派生表逐表逐行相同（G6c，2 次）。它同时是：

- 迁移的核对手段（§6.1 第 5 步）；
- 派生口径变化时的升级方式（现在散在 Dart 的 `_upgradeCaches`）；
- 「索引是不是真的只是索引」的常设测试：任何测试库 `rebuild_all` 前后派生表逐行相同。

**相对协议 3 的有意行为差别**（G6 + G6c 汇总，出自 #3383 / #3386 / #3390 正文）。都出自同一个要求：派生结果是「操作集合（+ 本机信任状态 + 宿主输入）」的函数，
与到达顺序无关；协议 3 在这些点上依赖顺序，或依赖落库那一刻的状态。

| # | 哪一处 | 协议 3 | 新存储 | 对拍怎么处理 |
|---|---|---|---|---|
| 1 | 寄存器的判定时机 | 落库时裁剪 | 留全部写入，对全集判（§3.4） | 比「活着的修改记录」集合；样本库与全部内核测试上差 0 |
| 2 | 同一个日志 ID 的多条 | 先到的留，再靠去重作业收敛 | 操作号最小的那份（§2.2） | 按日志 ID 集合比 |
| 3 | 同一个 ID 的多条内容相同的身份记录 | 先到的留 | 操作号最小的 | 按实体 ID 集合 + 内容比，差 0 |
| 4 | 旧闭包 | `sync2_legacy` 只增不减 | 从槽重建，清除带旧戳的修改后变小（§3.4，协调方先行、所有者可改） | 样本库上逐台相同 |
| 5 | 旧设备分叉的日志 | 先收到的那一支留，另一支拒收 | 每个操作号上链指纹字节序最小的槽在日志里（§3.2） | 现有测试没有分叉后继续应用的场景 |
| 6 | 清除后的残留 | 载荷换骨架、投影删行；顺序提示与「把卡挪进被清除牌组的修改」的投影行留着 | 已清除的一律不参与任何判定 | 清除过的实体不比扣住集合 |
| 7 | 判扣住时的已清除操作 | 骨架仍算并发操作（骨架留着依赖向量） | 不算（空洞没有依赖向量） | 同上 |
| 8 | 重判扣住的时机 | 有操作碰到实体时；标签顺序提示不触发 | 对全集判 | — |
| 9 | 被扣住的删除盖不盖掉它见过的写入 | 取决于到达顺序（扣住先发生则不盖，先落投影再被撤出则已盖掉、不回来） | 一律盖掉，扣住的删除自己不生效（待所有者确认，§9 第 16 项） | 有删除被扣住的实体不比它 `deleted` 寄存器里的修改记录 |
| 10 | 不可信设备带来的盐 | 没有这个概念 | 只算受信作者的带盐操作（§5.1，待所有者确认，§9 第 16 项） | — |
| 11 | 摘要覆盖什么 | 投影表 JSON（含旧上下文），前缀 `5:` | 语义状态（§2.3），前缀 `6:`；两代永不互比 | — |
| 12 | 笔记行的 `updated_at` | 写缓存行那一刻的本机时钟，重建一次就变 | 活着的写入里最大的 HLC 物理时刻（内容最后被改的时刻） | 不比 |
| 13 | 日志的 `server_time` | 本机收到的时刻 | 只取承袭来的那份，原生操作没有就不钳位 | — |
| 14 | 身份记录不成形（缺 `noteTypeId`、字段类型不对、笔记 ID 不是 UUID） | 整次重建缓存失败 | 只有这条笔记没有缓存行 | 协议 3 因此失败时缓存三类不比 |
| 15 | 同一个旧修改记录 ID 下两条不同修改（拷出的两份旧库用同一个写入者续写同一个 seq） | 按 ID 只存一行 | 两条都进视图 | 这些笔记、它们的卡与归属这些卡的统计行不比 |
| 16 | 重放范围 | 只重放碰到的部分 | 对整个连通分量按链尾 ID 升序重放 | — |

不是差别、但容易被当成差别的：同一个 dot 的多份迁移副本算一次写入（协议 3 按 dot upsert；新存储取操作号最小的当代表、`server_time` 取最小——同义）；
笔记的 `tags` 整列表写入不进寄存器、进标签 OR-Set（与协议 3 相同）。对拍时协议 3 一侧先在 SAVEPOINT 里跑完欠着的收尾（`replay_pending`、`refresh_tags_row`）
再全量重建缓存，读完回滚。`KNOWN` 白名单里另有一条测试自己把库弄得不自洽的场景（`tests_digest::diverged_devices_locate_the_differing_bucket`）。

## 3. 历史过界：逐条转译与承袭日志

### 3.1 转译 T

T 是一个纯函数：输入一条旧操作与它在原协议 3 链上的链值，输出承袭日志里的一个**槽**——操作、原样件、副本记录、空洞四种之一。
**只看这条操作自己**，不看库里别的东西、不看是哪台设备在转、不看时间。

T 的输入是协议 3 的线格式字节，也就是 `load_op` 还原出来的那份（本机存储把日志里的配置快照剪出去另存、对载荷做过本地压缩，
`native/fushi_fsrs/src/store/sync2/snapshots.rs:1-12`；必须先拼回）。输出是协议 4 的规范字节。旧代读入器逐条重算链并与库里存的链值比，
对不上就报错——「喂给 T 的是作者当初成链的字节」在运行时核对，不靠相信库。T 的输入只有协议 3 的操作：协议 1 的旧根（`v2/`）
先经现有的旧根读入代码变成协议 3 的操作（§6.3）。

T 先拒掉不满足协议 3 自身不变量的输入：seq 为 0、HLC 写的是别的设备、依赖向量里有作者自己或有 0 分量（协议 3 的 `Op::read`
与段解码器本来就拒收这些）。所以它的形状是 `translate(op, chain) -> Result<槽, 错误>`；满足这些不变量的输入一律有输出。

规则（T 版本 1，冻结；自上而下取第一条命中的）：

| 旧操作 | 槽 |
|---|---|
| MediaAt（12），**不论是不是骨架** | 空洞（§4.5 改成位置上的清单） |
| 副本骨架（`Op::duplicate` 的产物） | 副本记录：种类、HLC（墙钟与逻辑计数）、`of`、它自己的旧戳（可无；现有闭包按它算，`sync2/op.rs:93-121`）。骨架的依赖向量与载荷哈希不留 |
| 其余骨架（已清除的；解不开的也算） | 空洞（不带时间） |
| `schema == 1`、协议 3 解得开、种类认识、**解码再编码等于原字节**、转出的操作体过得了协议 4 的严格解码 | 操作：信封（操作号、HLC、依赖向量、种类）原值，操作体按下表 |
| 其余：不认识的种类、解不开的载荷、`schema != 1`、带尾字节 / 非最短 varint / 未知标志位的载荷、转出的操作体过不了协议 4 严格解码往返的（例如内容恰好是规范 UUID 文本的文本引用、同一个 seq 出现两次的 Dedup） | 原样件：整条旧操作原样带过来（信封原值、`schema` 原值、载荷原字节） |

MediaAt 必须排在骨架之前：否则被认成副本的 MediaAt 会转成副本记录，没认成副本的同一条是空洞，同一条旧操作在两台设备上的两种状态并不到一起。

操作体的对应：

| 旧 | 新 |
|---|---|
| Entity、Tag 增删、标签顺序、Media、Checkpoint、Purge、DeckAlias、LegacyUnknown | 载荷字节不变（两代布局相同） |
| Edit，带 `LegacyStamp` | 旧写入者、旧序号、旧上下文、旧 HLC、`server_time` **全部保留**，换成紧凑编码；上下文只留语义（归一后的前缀 + 零散 dot），其中的合成写入者条目按现有剥离规则去掉 |
| Edit，不带戳（协议 2 / 3 的原生写入） | 字段原值（它的依赖向量是真实的因果） |
| Log | 字段一一对应（紧凑编码）；`legacy_hlc` / `legacy_server_time` 保留；`res` / `extra` 的 JSON 原文不动（含拼回的配置快照） |
| Dedup（13） | 载荷字节不变（「谁是谁的副本」的唯一依据，样本库 32 条、2 MB） |

**原样件**是「未知字段保留原字节」在承袭方向的出口。协议 3 的解码器是宽松的（只读已知前缀、不看 `schema`、收非最短 varint、
Edit 的标志位只取用到的位），协议 4 的解码器是严格的（一个值只有一种字节形，否则「同号同字节」的幂等判定不成立）。
T 不把「解得开但字节不规范」的旧操作重新编码成规范操作——那会丢掉没人交代过的字节，而 T 丢的东西必须是有限的一张表（§3.5）。
原样件**应用与否跟协议 3 相同**：协议 3 解得开、种类认识的，派生层按冻结的协议 3 解码器解出的值应用；解不开 / 不认识的不应用，只保存、转发。
协议 3 自己的写者不产生这类字节，样本库里是 0 条。

每个槽带 `fp` = 原链值的前 8 B（§3.2 判分叉用），空洞也逐个 seq 带。

T **不改任何 ID、不做任何归一**（§5.3 说明为什么），不合并、不重排、不改 `(设备, seq)`，不做任何「谁赢」的判断。它丢掉的东西是有限的一张表（§3.5）；
谁是胜者、谁和谁是同一个实体，都放在派生层：派生层错了能改、能重建，T 错了是永久的。T 带版本号，用黄金向量冻结；
规则有任何变化都必须升版本。「同一条操作谁转出来都逐字节相同」只在**同一个 T 版本内**成立：承袭段头带 T 的版本，一段只含同一个版本转出的槽（§3.2）。
出 T 下一个版本的那个 PR 必须同时写明它对「秩变了的槽」的规则（§3.2、§10 第 22 条；协调方先行、所有者可改）。

待投递队列里还没应用的远端操作（样本库 2,582 条，前面缺一段）同样转译，过界后仍是待投递。与已应用的同号、链值也相同的待投递行是残留，跳过；
链值不同的是分叉的一支，照常交出（§3.2）。待投递操作的链值是收段时按段里声明的前一环算的，协议 3 在投递时才核对。过界后的核对（G6 第一部分）：待投递槽带一个「前一环的链指纹」`prev_fp`。

- 迁移时旧代读入器还拿得到协议 3 的原操作与链值，能在协议 3 的口径下验「这条紧接在上一条之后」；验得出的记上一条的链指纹，验不出的（前面缺着）留空；
- 存储层只交出「正好接在本机末尾、且 `prev_fp` 等于本机末尾那个槽的链指纹」的待投递槽（8 字节的核对；因果上该不该投是同步轮的事）；
- `prev_fp` 为空的永远不自己投递：转译之后已经没有办法重算协议 3 的链。它只等同一个操作号经承袭段到达——链指纹相同就是确认（待投递行删掉），
  不同就是分叉的一支（挪进分叉表）。

样本库的 2,582 条待投递里，2,580 条验出了前一环的链指纹，2 条没有。

样本库实测（G2，Rust release，桌面 Windows）：旧操作 1,339,162 条（5 台旧设备；已应用 1,336,580 + 待投递 2,582）→ 操作 758,935 /
原样件 0 / 副本记录 580,100 / 空洞 127（全部来自 MediaAt）。全量转译 24.2–35.7 s（两次，机器负载不同），进程峰值工作集 20 MB。

### 3.2 承袭日志

每台旧设备的日志转译后成为一条**承袭日志**，按（来源集合、旧设备、seq）定位，每个 seq 一个槽。操作号与依赖向量里只有 `(设备, seq)`，
来源集合记在本机的设备表上；同一个集合里同一个旧设备 ID 又以另一个来源集合出现时，存储层报错，不静默并成一条日志（§10 第 21 条）。

- `(设备, seq)` 不变，所以别的操作对它的依赖、本机的信任表 / 暂扣表 / 检查点里引用的操作号都还指向同一条；
- 它是冻结的：原设备换代后不再往里写（§3.3），不再成链、不带原设备签名，由上传者签名。承袭段头带所在集合、来源集合（这段旧日志当初所属的
  协议 3 集合标识）、旧设备、上传者、T 的版本、区间首尾的完整原链值。完整原链值本机只在两类地方有：迁移时记了记号的 seq（§2.2），
  与收到的承袭段的首尾——**一台设备只能在自己知道完整链值的 seq 上切承袭段**（G8 的约束，§10 第 10 条）；
- **任何升级过的设备**都可以上传自己手里那一段。链指纹相同的同一条操作，同一个 T 版本下谁转出来都逐字节相同，按操作号幂等；
  `T(S1) ∪ T(S2) = T(S1 ∪ S2)`，不存在「谁先换代、别人以它为准」的角色；
- 没升级的设备之后再升级，把自己多出来的尾巴转译上传即可——承袭日志在它的主人升级之前是开口的；
- 同一个 `(设备, seq, 链指纹)` 来了两个 T 版本转出的槽：**秩相同**时高版本换掉低版本（逐字节相同只把版本标签抬上去）；同版本、同秩而字节不同是异常，
  报出来、不落库。**秩不同时本机一律不动**——本机分不清「对方的新版本把这条旧操作改判了」与「对方应用了一条本机不执行的 Purge」，
  后者照下面第 1 种情况必须不动。T 现在只有版本 1，这种相交还不会发生；出下一个版本时的规则由那个 PR 写明（§3.1）。

同一个操作号的槽在两台设备上不一样，有两种情况，处理不同：

1. **链指纹相同，一边是完整内容（操作 / 原样件）、一边是副本记录或空洞**（那台设备已经应用了 Dedup / Purge，这台还没有，或者这台不执行）。
   属于正常，规则是：
   - **本机的槽只由本机自己应用 Purge / Dedup 推进。** Purge / Dedup 操作本身过界；本机按自己的信任状态应用到它时，把目标槽变成空洞 / 副本记录
     （与协议 3 的 `Op::purge` / `Op::duplicate` 逐条对应：已经是空洞 / 副本记录的不动，同一条操作只认第一次）。
   - **收到别人的空洞 / 副本记录、而本机手里是完整内容时，不动本机的槽。** 清除与认副本在协议 3 里都是「本机应用到那条操作时才生效」，
     而且受本机的信任状态管：不可信 / 已拒绝的设备发来的 Purge 进日志但不执行（`native/fushi_fsrs/src/store/sync2/trust.rs:123`）。
     无条件以来的为准，会让本机拒绝过的清除经别人上传的承袭段生效，而且不可逆。
   - 「完整 < 空洞 < 副本记录」的并只用在两处：**本机还没有这个槽**（收什么留什么），以及**位置上同一个操作号留哪一份**（留靠后的）。
     空洞与副本记录之间取副本记录：协议 3 在这里依赖应用顺序（先清除后认副本留清除骨架，反过来留副本骨架），两台设备可能各持一种；副本记录带旧戳，闭包要用。
   - 同秩而内容不同（两个不同的完整内容、两条不同的副本记录）是冲突：同一个 T 版本下诚实的设备造不出来，报出来、不落库。

   于是操作集合相同、信任状态也相同的设备最终逐条相同；信任状态不同的设备，槽本来就该不同（它对别名判定的影响见 §10 第 18 条）。
   代价：本机还没有某个槽、收到的是空洞时，内容永远拿不到，即使本机并不信任发清除的那台设备——与协议 3 相同，骨架同步过来时内容已经没了。
   所有者 2026-11-12 批准（§9 第 14 项）。G6 第一部分已实现：落库时同指纹、秩不同一律本机不动；推进的入口只有「本机执行了 Purge」「本机应用了 Dedup」两个。
   本机存储给副本记录与空洞各留一位标志，记「这个槽现在的样子是本机推进出来的」（收来的没有）：本机随时列得出「我这里是空洞 / 副本记录、
   而且是我自己清的」的操作号，以后定 T 新版本的规则或 §10 第 18 条时判据已经在库里，不用再迁移。
2. **链指纹不同 = 那台旧设备的身份分叉过**（数据目录被拷到另一台机器上各自继续写；现有代码用链值判这种情况并拒收其中一支，
   `native/fushi_fsrs/src/store/sync2/transport.rs:975-980`、`:1000-1015`，分叉的设备换身份重签发，`:2012-2118`）。
   这时两份内容不同，**绝不能「先到先得」**：两支按 `(设备, seq, 链指纹)` 各存一份，本机把它记成该设备的分叉、照现有做法报出来，两支都不丢。
   存储上：本机日志里每个操作号只有一个槽，其余的存进分叉表，**不参与派生**。**日志里留哪一个由全集决定**（G6c-2 #3386，取代 G6 第一部分的「本机先应用的那一支」）：
   每个操作号上，见过的所有槽（链指纹不同）里链指纹字节序最小的那个在日志里，其余在 `op_forks`。只看「这个操作号上有哪些槽」，与谁先到无关，
   所以操作集合相同的设备日志逐槽相同。
   - 逐操作号选、而不是「选一整支」：转译之后本机无法重算协议 3 的链，两个相邻槽是不是同一支验不了，手里只有各槽自己的链指纹。
     后果是分叉点之后日志可以是两支**交错**的（seq 4 取 X 支、seq 5 取 Y 支）。派生按操作号取槽、不看链，不受影响；
     链值检查点 `log_marks` 只在链指纹对得上日志里那一条的 seq 才记——对调时删掉该 seq 的记号，导入收尾的记号也先核指纹。
   - 实现：`Truth::rebalance(col, dev, seq)` 在两处调：同号槽作为分叉落下时；新槽接在日志末尾而同号的待投递 / 分叉槽已在场时。对调要拆空洞区间。
     落库结果多两种：`Replaced`（来的这条指纹更小、换进了日志）、`Yielded`（来的这条接在末尾但让位给已在场的同号槽）。
   - 测试：三种到达顺序（含待投递）日志逐槽相同；两种到达顺序派生表逐行相同。
   分叉表里的槽不被本机推进，同一支来了两份按「完整 < 空洞 < 副本记录」留靠后的。仍没解决的：依赖向量 `(设备, seq)` 分不出两支——
   确定性选择让所有设备对「`dev:5` 是谁」答案一致，但不保证那就是作者当时见的那一条（§10 第 2 条）。

副本的归并只靠显式的副本记录（Dedup 的结论），不靠「旧修改记录 ID 相同」：并入副本的旧写入者是改过名的，ID 本来就不同（§1.3 第 3 条）。

### 3.3 设备换新身份

换代时每台设备给自己生成新的设备 ID，原生日志从 seq 1、新链开始；签名密钥沿用。新 head 里带
`prev = {旧设备 ID, 旧日志的末尾 seq, 该处的完整链值}`，用同一把密钥签，别的设备据此把对旧设备的信任与设备名带到新身份上，不重新弹确认。
带链值是为了在旧身份分叉过时分清新身份接的是哪一支。读者验 `prev` 时要核对旧设备已登记的公钥：同一把钥匙签的才带信任（G8）。

为什么不沿用旧设备 ID 接着编号：回退到旧版本继续用、之后再升级一次时（§6.4），旧库会在旧编号上继续长，如果新代的原生日志也用同一段
编号就会相撞。换新身份后，回退期间多出来的旧操作只是承袭日志的又一截尾巴。

### 3.4 去掉 v1 因果：去掉的是机制，不是历史数据

推荐方案（§9 第 2 项的 B）：**寄存器的判据与现在逐位相同**（判据代码一行不改），变的是数据从哪来，以及判据作用在写入的全集上、
不再作用在按到达顺序裁剪过的行上（本节末「与协议 3 的差别」）。

- 承袭的带戳修改自带 dot（旧写入者 + 旧序号）与旧上下文，彼此之间照现规则：上下文含对方的 dot 就支配；
  活着的按 `(physical, counter, hlc_writer, id, server_time)` 取最大；多条活着且值不同就是冲突（`registers.rs` 现有逻辑，冻结）。
- 原生写入（换代后的，以及换代前不带戳的）对别的写入：依赖向量覆盖对方的操作号就支配（`store/sync2/mvr.rs:40` 的 `covers`）；
  对带戳的承袭修改，再加上「依赖向量覆盖到的承袭操作与副本记录的旧戳闭包」——就是现在 `legacy_closure` 的定义，只是闭包从
  「存着的真相」变成由操作重建的派生索引。
- **换代后的新写入不携带、也不生成任何 v1 形状的数据**：没有旧戳、没有拼出来的上下文、没有合成写入者；摘要不再含上下文。

这样「v1 因果从 v2 里拿掉」落在三处：格式里它只存在于冻结的承袭操作与副本记录上（原生段里的 Edit 带旧戳，打包与打开两侧都拒）；
存储上，操作上的旧戳从 75.2 MB 降到 7.4 MB，连同副本记录上的旧戳与名字表合计约 14.2 MB（实测，§2.6）；
代码上给原生写入拼 v1 上下文、存闭包、摘要绑上下文这些都删掉，只留一段只读的、只对承袭数据生效的判定。

判定不变的依据：寄存器判定只用 dot（写入者 + 序号）、「上下文含不含某个 dot」、HLC 三元组与 `server_time`。紧凑旧戳逐字保留 dot、HLC 与 `server_time`；
上下文归一（删已被前缀覆盖的、把接得上的并进前缀、删 ≤ 0 的分量）不改「含不含」这个谓词。G2 用现有的寄存器裁决当预言机钉住
（原旧戳对紧凑形还原的旧戳），样本库 659,648 个旧戳逐个核对不一致 0 个。

冻结判定从操作体读（G6 第一部分已实现；判据代码一行不改，只给 `registers.rs` 加了一个不带逻辑的入口）：

1. 带旧戳的修改：dot / 上下文 / HLC 取旧戳。排序键里的 HLC 按现有 `parse_hlc` 对旧戳的 HLC 文本取，不按紧凑形「拆成三元组 / 存原文」的变体分流
   （`+5:0:w` 存的是原文，但 `parse_hlc` 解得开）；坏文本原样交给判据——判据报错就是整个寄存器报错，与协议 3 相同，不吞；
2. 同一个 dot 的多条（同一条旧修改被两台设备各迁了一遍、还没认副本）是一次写入：代表取操作号最小的，`server_time` 取最小值
   （协议 3 的 `srs_event_local` 这么做）；
3. 旧戳闭包从槽重建：每台承袭设备「它日志里全部旧戳（修改上的 + 副本记录上的）的 dot 与上下文之并」，另记带旧戳的最大 seq；空洞不带旧戳。
   只覆盖到一台设备旧戳的一部分时逐条并到那个 seq（与协议 3 的 `legacy_closure_with` 同义）；
4. 不带旧戳的修改的上下文 = 作者见过的各设备前缀 ∪ 这些前缀覆盖到的旧闭包。闭包可达上万个写入者，**不物化成每条写入一份上下文**：
   判据只问「这条写入的上下文含不含同一寄存器里别的 dot」，索引只回答这些问题、把答案拼成上下文交给判据。

**与协议 3 的差别：对全集判，不在落库时裁剪。** 协议 3 在落库时裁剪（被支配的删掉；原生写入的上下文按落库那一刻的闭包定死），结果依赖到达顺序——
两台设备收到的顺序不同就可能留下不同的行。新存储留全部写入，状态是集合的函数。由此有两处结果可以与协议 3 的落库结果不同：

- 后到的旧戳会改变「原生写入见过什么」，协议 3 里不会；
- 支配关系不传递的病态集合上，「活着」的集合可以与协议 3 落库留下的不同。

样本库上的对拍（只跑成 1 次）：活着的修改记录除 `tags` 键外 322,796 个 ID 两边完全相同，只在旧库的 0 个；只在新库的 30,054 个全部是 `tags` 键
（协议 3 把这个键的行换成合成的 OR-Set 行）。日志 ID 两边 352,979 个、差 0（新库另有 422 行是同 ID 的另一份）；
实体 ID 15,315 个、差 0。寄存器状态：胜者 337,538、冲突胜者 147、活着的非胜者 15,165（其中 `tags` 14,999）、被支配 248；多写入的寄存器 15,280 个全部过判据。
G6c 接上标签 OR-Set、扣住、清除与缓存层之后（#3393 头，wight-mac 2 次）：与协议 3 投影逐类对拍（含 `tags`、扣住、清除，`notes` / `cards` / `stats` 逐列）
差异类别 **0**，`tags` 那 30,054 个的差由标签语义消掉。

**闭包随清除变小**（协调方先行、所有者可改）：清除一条带旧戳的修改之后，从槽重建的闭包会变小；协议 3 的 `sync2_legacy` 是持久累计的，只增不减。
差别只影响「不带旧戳的写入是否支配某条已清除的旧修改、而那个 dot 只经它才被知道」。先行方向是**接受闭包随清除变小，不改线格式**。
这是推理：样本库的空洞全部来自 MediaAt、不带旧戳，没有这种情形，**没有实测**；样本库上 4 台承袭设备的闭包与旧库 `sync2_legacy` 逐台相同
（覆盖到的 seq 344,473 / 525 / 648,716 / 32）。要闭包只增不减，就得把被清除槽的旧戳留在空洞上——那是线格式改动（G1 的空洞没有内容）。
存储层两种都能做（闭包是派生的），没有焊死（§10 第 14 条）。
这个方向的一个后果（G6c-2）：逻辑标记阶段（§2.2「清除分两步」）什么都不变；落成空洞时拿走那条旧修改的旧戳，一条原生写入若只经那条旧戳的上下文
才「见过」另一条活着的旧修改，落空洞之后就不再支配它——胜者、进而语义摘要会变。也就是说「落不落成空洞派生结果都一样」在这一种情形下不成立。

为什么不干脆丢掉旧上下文、承袭修改之间只比 HLC（§9 第 2 项的 A）：

- 「因果在后」推不出「HLC 更大」。HLC 不跟随超前过多的远端时钟（`native/fushi_fsrs/src/sync2/hlc.rs:6-8`、`:130-134`）。
  手机日期快了两天改了字段，桌面收到后把它改回来——现在桌面那条支配手机那条；只比 HLC 的话换代后手机的旧值赢，而且没有任何提示。
- 样本库上两种规则的结果相同（附录 A 的 `probe_lww3.py`：337,519 个只留一条记录的寄存器里 0 个不一致，其中 15,114 个有被支配的历史；166 个留着多条的寄存器，HLC 最大的那条都在留下的集合里），但这只说明这份库没有那样的时钟历史。
- 保留的代价实测是本机存储约 14.2 MB、线格式 30.3 MB（§2.6），不值得为它改结果。

### 3.5 不过界的东西（T 的不可逆清单）

1. 已清除操作的骨架信封，含它的时间（Purge 操作本身过界，清除语义不变）；
2. 副本骨架的依赖向量与载荷哈希（副本记录留种类、HLC、`of` 与旧戳）；
3. MediaAt 操作——由位置清单替代，本机「各位置有哪些媒体」的缓存用旧表播种；
4. 旧链值（每个 seq 只留 8 B 指纹，承袭段头留区间首尾的完整值）与旧设备对旧段的签名——承袭段由上传者签名。旧同步根原样留在位置上（§6.2），需要追溯时它还在；
5. 旧上下文里的合成写入者条目（现有代码读的时候本来就剥掉）；
6. 旧上下文 JSON 原文的写法（多余的键、≤ 0 的分量、能并进前缀的 dot）——只留语义；
7. 旧载荷的文本编码（写入者名字、HLC 文本、JSON 形状）——信息不丢，换成紧凑编码。HLC 文本只有「解析得出且重新格式化逐字节相同」才拆成三元组，否则存原文。

解码再编码不等于原字节的旧操作不在这张表里：它们走原样件，一个字节不丢（§3.1）。

### 3.6 否决过的做法

- **单设备创世快照**（一台设备把当前状态拍成新代的起点，别的设备以它为准）：哑存储没有比较并交换，两台同时升级会各拍一份；
  落后设备没上传的操作无处安放；与 BUG-4011 同类的「同一份历史两条流」风险。它也违背 v2 设计「不做快照」。
- **不转译，只叠一层别名**：投影层、映射表、每条链值永远留着，体积只能降一半。
- **转译时把存量 ID 重算成无盐 ID**：字段 / 模板 / 卡 / 日志的 ID 层层派生，重算要知道「这个 ID 当初是由什么算出来的」，
  这要看别的操作（笔记类型的字段定义史、卡属于哪条笔记哪个模板）；各设备手里的操作集合不同，同一条操作就可能转出不同结果——
  而转译结果是永久的。这正是现在 `srs_profile_merge.dart` 的 1234 行与那几个 bug 的来源，不能搬进一次性的转译里。
- **把副本骨架与 Dedup 当空洞丢掉、靠内容身份归并**（本稿初版）：核验实测副本与原件的旧写入者不同，内容身份对不上（§11.1 第 3 条）。

| 操作种类 | 1–13（`sync2/op.rs:18-33`）；信封带「已清除」位 | 12 MediaAt 退役，编号永不复用。信封没有「已清除」位：骨架不再是操作，日志里改用**槽**表示——空洞、副本记录，承袭日志另有原样件（§3.1）。新增 14 `Join`（§5.4）与 15 `Salts`（携带盐集合，§5.1；G1b，#3382），两者只出现在原生日志：承袭段拒 15 已随 G1b 定，拒 14 是 G1b 对 G1 的收紧、**待所有者确认**（§10 第 20 条）。13 Dedup 只出现在承袭日志里（原生段打包时拒），新代不再产生。其余种类语义不变 |

| 文件名 | 自写 head `head-…`、段 `seg-…` | 原生段与自写 head 的前缀不变（互联 host 的长轮询唤醒与设备名补全认这两个前缀，`packages/fushi_engine/lib/srs/sync2/srs_host_directory.dart:26-28`）。**承袭段不能用 `seg-` 前缀放在 `devices/<旧设备>/` 下**：互联 host 把那里的 `seg-…` 当成那台设备自己写的段，并据此认定写段的对端就是这台设备（`srs_host_directory.dart:16-28`）。承袭段的文件名与目录由 G8 定（§10 第 10 条） |
| 链 | 每条操作一份链值 | `blake3(域前缀 ‖ 前一环 ‖ 信封 ‖ blake3(载荷))`：比协议 3 多一个域前缀 `fushi-srs-chain/4\n`，其余相同；链不含集合标识（并入时只需重封段头，§5.4）；本机只在切段处与尾部存链值 |
| head | 字段见 `sync2/segment.rs`；被中继原样转发 | 文件字节是规范 JSON（解码时重新规范化不等于原字节即拒）；签名覆盖除 `sig` 外的全部键（含本版本不认识的），签名原文带域前缀；段清单键改名 `segs`；增加 `loc` + `seal`（按位置签的加密标记，§4.4）、`prev`（§3.3）、派生口径版本 `derive`。**故意不做成协议 3 解得开的形状**（§4.3）；被转发的 head 不当作位置证据（§4.4） |
| 摘要 | 4096 桶，覆盖投影表 JSON（含 `ctx`），前缀 `5:` | 4096 桶，覆盖语义状态（寄存器活着的写入的内容身份、标签集合、每卡日志 ID 集合），新前缀 |
| 媒体「在不在」 | MediaAt 操作，永久留在日志里 | 位置上的每设备清单文件（§4.5） |
| `meta.json` | `v, minReader, collection, createdAt, kdf?`（握手 `srsLocationHandshake`，`packages/fushi_engine/lib/srs/sync2/srs_location_crypto.dart:324`） | **内容是纯函数**：集合标识 + 从旧根原样抄来的 `kdf` + 媒体目录所在的根，不含任何时间戳；`kdf` 只当参数载体，不再是「这个位置加密了」的唯一证据 |
| 远程复习 | 能力位 `srsRemoteStoreV1`，搬投影行 | 能力位 `srsRemoteStoreV2`，搬新代的物化输入；新旧互相明确拒绝（§7） |

操作体、段、head 的字节细节在附录 B（G1 定，#3376）。

`meta.json` 为什么必须是纯函数：没有一种传输提供原子的「不存在才写」（都是先查后写；互联 host 的 PUT 不认条件头；Google Drive 允许同名文件），
现有 meta 还带时间戳。两台设备同时建新根时，只有内容逐字节相同才无所谓谁覆盖谁。读到已有 meta 时按字段比较，不一致就停下报错。

### 4.2 不变的机制

每设备一个目录、只增文件 + 两段式删除、按体积切段与分层合并、段的压缩 / 加密 / 签名构造、HLC、原生操作的因果投递与依赖向量、
标签 OR-Set、Purge / Checkpoint / 时间线恢复、设备信任纯本机（首次信任 + 待确认）、中继（`FSRL`）、新设备收段通道、发件分批、
`min_reader` 握手、未知种类原样保存转发、身份分叉的检测与换身份重签发、`.fushisrs` 的容器形状（清单改记集合标识与来源盐）。

两处要跟着换代动、G1 没有覆盖的：协议 4 自己的中继件格式还没有定义（§10 第 16 条）；`.fushisrs` 导出包的清单版本 `v` 与内核导出魔数
（现为 `FSRS2EXP`，`native/fushi_fsrs/src/store/sync2/transport.rs:3326`）必须换，旧版本才不会把新包当成自己的格式来读（G11）。

### 4.3 旧根围栏

升级过的设备在新根就绪后，**在本轮读到了旧根 `v3/meta.json` 的前提下**把它改写成合法 JSON：`minReader: 4`，原样保留 `collection` / `kdf`，
加一个指向新根的提示字段。协议 2 / 3 的客户端读到 `minReader` 大于自己就整位置不碰、提示需要升级
（`packages/fushi_engine/lib/srs/sync2/srs_folder_location.dart:211-213`、`srs_location_crypto.dart:391`；这条检查在协议 2 发布之前就有，
所有协议 ≥ 2 的版本都认）。协议 1 的旧根 `v2/` 早在 2026-10-30 的断代里就有魔数行围栏
（`packages/fushi_engine/lib/srs/sync2/srs_location_migration.dart:54`）。

新根里的文件在结构上就不是协议 3 读得懂的东西，不依赖「恰好验不过签名」（G1 的测试钉住四个方向）：协议 3 的段解码器读协议 4 的段
在魔数上失败（`FSG4` / `FSH4` ≠ `FSG2`）；协议 3 的 `Head::decode` 读协议 4 的 head 在结构上失败（缺 `segments`，签名原文另有域前缀）；
反方向，协议 4 的解码器同样拒协议 3 的段与 head。所有者的要求是旧版本不得把新代文件当成自己的格式解析。
因此旧版本「需要升级」的提示**不来自新代文件被读懂**——协议 3 的读者遇到解不开的 head 是跳过
（`native/fushi_fsrs/src/store/sync2/transport.rs:489`），不是报升级——而来自旧根里的围栏：上面的 `meta.json`，以及旧根里另放的一个
协议 3 形状、`minReader 4` 的墓碑 head。墓碑 head 是**必需**的第二道围栏（所有者 2026-11-12 定）：用现有的协议 3 编码器写，
协议 3 的读者见到它整轮报需要升级（`transport.rs:493-496`）；由 G8 实现，它放在旧根的哪个位置随 G8 定（§10 第 11 条）。

协议 3 的代码里已知还有两处会把协议 4 的东西当成自己的来读，是 G8 / G11 的硬输入（§8）：

- `packages/fushi_engine/lib/srs/srs_profile_link.dart:259-276` 列集合目录时，把 `v3` / `v2` 以外的子目录一律当成 v1 写入者目录——
  新根 `v4/` 会被旧版本当成一个名叫 `v4` 的写入者；
- `.fushisrs` 导出包（§4.2）。旧版本还原新版本做的备份会怎样没有核实（§12）。

围栏只是「让旧版本停下并提示」，**不是正确性的依据**，它至少有三个口子：

1. 云盘的覆盖写是先删后传，中间 meta 不存在的那一刻，旧客户端会重建一份 `minReader 3` 的 meta；
2. 旧客户端一轮之内不复查 meta，已经开始的那一轮照样上传、合并小段、两段式删除；
3. 旧客户端的 profile 关联步骤在握手之前跑，某些情况下会删掉旧根下的目录，连带围栏。

所以正确性靠 §6.2 的捡漏：升级过的设备每轮核对旧根（清单指纹、围栏是否还在），把新出现的、被同名重写的旧段转译并入，围栏不在就重立。

### 4.4 head 加密标记（原 PR-D）

现状的洞（v2 设计 §9 末尾）：本机从没见过这个位置加密、`meta.json` 又恰好丢了 `kdf`、位置上一时列不到任何密封文件的那一轮，
分不出「加密位置」和「明文位置」。台账里它被定成「不断代做不到」，因为 head 会被中继原样转发到明文位置，head 里的标记不能当证据。

协议 4：

- 设备在每个位置上写的 head 带 `seal`（密钥指纹；明文位置为空串）与 `loc`（位置标识），两者都进签名；
- 读者只把 `loc` 与本位置相符的 head 当作「本位置是否加密」的证据：被原样转发到别处的 head，`loc` 对不上。
  转发的 head 是否另换文件名前缀由 G8 定；
- 读者只要在位置上见到任何一个本位置自写、带 `seal` 的 head，就按加密位置处理：没有密钥就停，绝不写明文；
- 本机对「这个位置见过加密」的记忆保留（不降级）。

`loc` 取什么值、谁生成、与位置目录名是什么关系还没定（§10 第 8 条）。G1 的 head 只负责带着它、签住它；`loc` 定下来之前，本节的保证还不成立。

剩下分不出的只有「位置上一个文件都没有、本机也从没见过它」——这与一个全新的空位置无法区分，属于固有情况；
之后任何记得它加密过的设备回来都会发现并拒绝（§10 第 5 条）。

### 4.5 媒体「在不在」

- 每台设备在每个位置上维护自己的清单文件：我确认过这个位置上有哪些内容哈希（增量文件，可合并回收）。读者取并集。
- 本机 `media_at` 只是缓存，丢了重新列一遍；迁移时用旧的 `sync2_media_at` 播种。
- 媒体文件本身不动：存量集合继续用 `fushi-srs/<U>/v3/media` 与 `media-e/<指纹>/`，新根的 `meta.json` 记下这个位置，**不重传**
  （样本库 34,069 个媒体绑定、632 MB）。
- 媒体名 → 内容的绑定（Media 操作）仍是操作，属于集合内容。

## 5. 集合身份模型

### 5.1 集合与 profile uid 脱钩

- 内核持有绑定表 `collections(col, profile_uid, 集合标识, 位置目录名, salts, …)`。Dart 仍然用 profile uid 调内核，内核查绑定；
  `collection_of(profile)` 这种「由 uid 算集合」的函数消失，Dart 也不再自己拼同步目录（现在按 uid 拼，
  `packages/fushi_engine/lib/srs/sync2/srs_location_runner.dart:39-47`），改成向内核要。
- **`profiles.uid` 从此不再改变。** 采用对方 uid、并入后切 uid 这两条路都改成「改绑定」，只动 srs.db 一个文件，一次事务。
  备份、还原、统计、媒体目录、偏好键后缀、AI 会话这些按 uid 存的东西键不用动。
- 一个集合有两个对外的值，**存量集合两者都取现值，不改任何已经写出去的字节**：
  - 集合标识（段头 / head / `meta.json` 里的 `collection`）：存量 = 现有的 `v5(NS, "sync2/collection/{U}")`；
  - 位置目录名（`fushi-srs/<它>/`）：存量 = 旧 uid 的值 U。
  新集合在第一次有内容要写时随机生成一个 UUIDv7，两个值相同；加入已有集合的设备不生成，直接绑定对方的。
- `salts`：这个集合里出现过的旧 uid，只给 §5.3 的别名验算用。**盐集合是集合的共享状态，不是本机状态**：别名表是「操作集合 + 盐集合」的
  纯函数，盐集合各设备不同，各设备算出的规范 ID 就不同，换代后各按各的规范 ID 写新操作，就是永久分叉。所以盐由受信设备签名的操作携带，
  别的设备从操作里取：
  - 迁移的那台设备写一条 `Salts`（种类 15，G1b #3382，附录 B 第 13 条）携带初始盐集合——`{U}` 与本机记着的已退役 uid
    （`srs_meta.srs_retired_profile_uids`）——写在这台设备换代后的原生日志里；本机的退役列表只是写这条操作时的输入；
  - 并入时 `Join` 的盐表带上被并入集合的盐（§5.4）。`Join` 的 `from` / `dir` 不自动算盐；
  - 集合的盐集合 = 本机算数的操作里全部 `Salts` 的盐 ∪ 全部 `Join` 盐表里的盐：并集，与到达顺序无关、重复无害，没有删盐的操作。
    盐是不透明的文本，相等 = 字节相等。「本机算数」= 作者是本机**信任的**设备（G6c-2 #3386）：盐集合是「操作集合 + 本机信任状态」的纯函数。
    所以「只增不减」的含义是**对操作集合单调**（操作只增 ⇒ 受信作者的盐只增），**对信任状态不单调**：作者被拒 / 待确认时它独有的盐不算，放行后算回来。
    这一点超出了 §9 第 11 项批准时的字面（「只增不减」），待所有者确认（§9 第 16 项、§10 第 17 条）；
  - 盐的读入点只有一处（`derive.rs::salts_of`，`Salts` 与 `Join` 的盐表两种）。带盐的操作逐条记进派生表 `salt_ix`（重建时清空重灌），
    绑定表里的 `salts` 一列只是「`salt_ix` 里作者受信的那些之并」的缓存，由 `Index::settle_salts` 整体替换（取代 G6 第一部分只增的 `add_salts`）；
    信任变了（`trust_changed`）跟着重算，`rebuild_all` 真的从操作重算，逐条维护与重建逐行相同不再靠「不清空」。
    `Index::withheld_salts()` 列出「只有本机不信任的作者带来的盐」及带它的操作号，上层据此知道与信任那个作者的设备相比本机少认哪些盐。
  样本库实测：2,856 个兜底卡 ID 全部要靠一个**只出现在本机退役列表里**的 uid 才验得上（库里的 `profile_uid` 列只有当前 uid）——
  没有这份本机记录的设备（后加入的、重装过的）单靠自己算不出同样的结果。
  所有者 2026-11-12 批准（§9 第 11 项）。
- 同机两个 profile 不能绑定同一个集合（现在也禁止，`srs_profile_merge.dart:281-296`）；内核拒绝这种绑定。
- 改绑定时本机状态怎么办：信任、暂扣、检查点跟着 `col` 走，不变；位置进度与段清单是「某个根」的进度，换了根就从头对账（幂等）。
- **「向内核要」的入口现在是无状态的，G7 要让它连到 store。** G5b（#3396）的入口：内核 `ffsrs_call` 的 `ids`（`gen4_ids/derive.rs`，一批请求一次 FFI）
  是不碰库的纯函数，`salt_of` / `location_dir_of` 都按 profile uid 答（G7 之前结果与改造前逐字节相同）；Dart 侧是 `SrsKernelIds(profileUid)`，同步调用、不带 store。
  本节要求 G7 起查绑定，绑定在 srs.db 里，届时：`ids` 改成连到 store 的命令；`SrsKernelIds` 要拿到 `SrsCore`（或一份绑定快照）；
  `SrsDbStore` 里一次算好就缓存的 `kernelIds` / `defaultDeckId` / `lapisNoteTypeId` / `fushiCardNoteTypeId`（`late final`）在绑定变化时要能失效。
- **反方向（目录名 → profile）还没改。** G5b 只把「profile → 目录」改成问内核；`srs_profile_link.dart` 的 `srsListRemoteProfiles` 与
  `srsRemoveOwnProfileFolder` 仍把 `fushi-srs/<名字>/` 下的目录名直接当 profile uid 读。目录名与 uid 脱钩之后，列远端集合要按 `meta.json` 里的
  `collection` 认、不能按目录名；这两个函数随旧的 profile 关联流程一起归 G9 改造（§5.6）。

### 5.2 ID 规则：现有规则表去掉盐

新写入的实体一律按现有规则表、去掉 `<profileUid>/` 前缀：

| 实体 | 规范 ID |
|---|---|
| 笔记 | `v5(NS, note/<guid>)` |
| 笔记类型 | `v5(NS, notetype/<ankiNum>)`；内置类型的 `ankiNum` 本来就是固定常量（`ids.dart` 的 `builtinNoteTypeAnkiNum`），于是**内置笔记类型自然成为所有设备、所有集合相同的常量** |
| 字段 / 模板 | 由笔记类型 ID 派生，公式不变 |
| 卡 | `v5(noteId, templateId/clozeOrd)`，公式不变 |
| 牌组 | `v5(NS, deck/<规范全名>)`，备选规则同理去盐 |
| 内置默认牌组 | `v5(NS, builtin-deck/default)`（现有规则去盐，常量） |
| profile 级设置实体 | `v5(NS, "profile")`（常量；存量 ID 是 uid 本身，每个盐都是它的别名） |
| 导入的日志、锚点、修改记录 | 公式不变 |
| 给事件副本补的 undo | `v5(NS, event-copy-revoke/<副本日志 ID>)`，公式不变（`store/sync2/mod.rs:469`）；它点名的日志归一了，它跟着重算 |
| fushi-ext 导入时重映射的日志 | `v5(新卡, fushi-log/<原日志 ID>)`，公式不变；原日志 ID 没存，不参与别名 |
| apkg 导入时与已有类型重名的副本笔记类型 | 先算一个「副本 `ankiNum`」：`hash53("notetype-dup/<来源 ankiNum>/<规范 JSON {cloze, fields, tmpls}>")`，各项是配置 ID 或 `"name:<名字>"`；再经上面笔记类型那一行的规则变成笔记类型 ID。原是 Dart 的 `_duplicateAnkiNum`，G5b 搬进规则表（`rules.rs` 的 `duplicate_note_type_anki_num`）。冻结向量在 `derive.rs` 的测试与 fushi_srs 的 `kernel_ids_test.dart`，两处都对照改造前的 Dart 公式（不在 `golden_ids.json` 里） |

同一个 apkg 在两台互不相识的设备上各导入一次，得到同一批 ID；同机两个集合里出现相同的 ID 不相撞，因为所有主键带 `col`（§2.1）。
这与 v2 设计 §3.1 的差别见 §9 第 6 项。**Dart 不再现算任何带盐的 ID**：根上的规则（笔记、笔记类型、牌组、备选牌组、内置默认牌组，加上副本笔记类型、
旧并入的兜底 ID 与改名写入者哈希）一律向内核要（G5b #3396：`SrsKernelIds`，守卫 `srs_kernel_ids_guard_test` 钉住生产代码里没有带盐派生、
不拿命名空间现算 ID）。由父 ID 派生、不带盐的规则——字段、模板、卡、导入日志、锚点、fushi-ext 日志重映射、修改记录 ID——仍在 Dart 的 `SrsIds` 里：
它们的公式换代后不变，不影响别名判定，搬不搬只是「规则只在一处」的整洁度问题；要搬就在 G12 收尾时搬，并删掉 Dart 那份（§8）。

规则表只在内核一处（G3，#3374 的 `native/fushi_fsrs/src/gen4_ids/rules.rs`），与 Dart 的 `SrsIds` 各自对同一份冻结向量重算对拍；
Dart 侧不加规范规则的产品代码。G3 黄金向量测试改成经 Dart 入口重算（G5b）。G3 取了值而本稿没有定的常量与枚举上限列在附录 C，待确认。

### 5.3 存量带盐 ID：不改写，在派生层当别名

操作里的存量 ID 一个字节都不动。派生层给每个实体算**规范 ID**，是「这个集合的操作集合 + 盐集合」的纯函数（不依赖到达顺序，随时能重建；
盐集合本身由操作携带，§5.1）。只认规范形状（小写、带连字符）的 UUID 文本：别的写法在存储层是另一个值，没有别名，规范 ID 是它自己。
规则分两种。

**反向验算**（拿自然键按带盐规则重算，对上了才认）。最后一栏是 G3 在样本库上的实测（#3374 的只读探针，§1.2 那份库，盐 2 个）：

| 实体 | 自然键从哪来 | 样本库：验上 / 总数 |
|---|---|---|
| 笔记 | 身份记录里的 `guid` | 15,251 / 15,251 |
| 笔记类型（含内置） | 身份记录里的 `ankiNum` | 10 / 10 |
| 字段 / 模板 | `fieldDef/` / `tmplDef/` 寄存器的**全部历史值**，按 `ankiNum` 与按名字两条规则各试；两条规则给出的是两个 ID，不互并 | 280 / 280（字段 246 + 模板 34） |
| 牌组 | 身份记录只有创建时刻；用名字与父牌组两个寄存器、连同祖先的全部历史值拼全名，再试备选序号。父牌组的候选**总含「没有父牌组」**：建牌组时只在有父牌组的情况下才写 `parent`（`packages/fushi_engine/lib/srs/srs_db_store.dart:3337`，apkg 导入同理），顶层建、后来挪进别的牌组的，历史里没有「空」这个值 | 54 / 54 |
| 内置默认牌组、profile 级设置实体（ID = uid） | 直接对每个盐验算 | 样本库没有 profile 级设置实体 |
| 活着的卡 | 笔记的每个别名 × 它的笔记类型出现过的每个模板别名 × 序号 | 45,055 / 45,055 |
| 不在缓存里的历史血统卡 | 同上；其中一半是兜底 ID，走下面的正向计算 | 5,568 / 5,568（派生 2,784 + 兜底 2,784） |
| 导入的复习日志 | 卡 + `ankiId`（`anki-revlog/<id>`） | 332,143 / 332,143 |
| 导入锚点 | 卡 + 发生时刻（`anki-anchor/<时刻>`） | 17,233 / 17,233 |

全部观察到的卡 ID 50,767 个 = 派生 47,911 + 兜底 2,856，验不上 0。修改记录 337,940 条全部满足 `id == v5(edit/<写入者>/<seq>)`。
样本库里没有的：填空笔记类型、profile 级设置实体、非 UUID 形状的 ID、两条规则给出不同结果的 ID——这几条只有单元测试（§12）。

**正向计算**（旧并入留下的痕迹，由已知 ID 直接算出，只认哈希相等）：

- **兜底 ID**：对每个已知 ID X 与每个盐 h，`v5(NS, profile-merge/h/X)` 若出现在集合里，它就是 X 的别名（`srs_profile_merge.dart:870`）。
  「已知 ID」= 集合里出现过的 ID ∪ **自然键验上的实体在每个盐下的 ID（含由它们派生的字段 / 模板 / 卡）**。后一半不能省：旧并入删了原行，
  X 自己不在集合里，只能由「自然键 × 每个盐」算出来。样本库的 2,856 个兜底卡 ID 全部是这种情形（X = 同一条笔记在另一个 uid 下的卡）：
  只枚举集合里出现过的 ID 时一个也验不上，并上后一半全部验上。仍然只认哈希相等，零误判。链式并入（A→B→C）每多一跳多一轮迭代，
  样本库 2 轮收敛。所有者 2026-11-12 批准（§9 第 12 项）。
- **改名的写入者**：`merged-v5(NS, profile-merge/h/writer/w)`（带与不带 `~原写入者` 后缀的两种格式都按哈希验）。哈希验上只说明
  「这个名字是从 w 改来的」；**归到 w 还要同时满足**：两个名字下在这个集合里有同 seq 的同一条记录（同 seq、同 HLC 物理时刻与计数——
  旧并入 `_Writers.alias` 用的同一个判据），且没有同 seq 的不同记录。一个 seq 都不重合也不归。否则保持原名。
  - 原因：v1 的写入者名是 `设备#代次`、按设备取，`lastSeq` 却按 profile 存（`srs_db_store.dart:886-892`），同一个名字在两个 uid 下
    各自从 1 数 seq，是两套互不相干的 dot。旧并入正是为此改名，并有一道一一对应检查（`srs_profile_merge.dart:1011-1022`）。
    只按哈希归回去，两条不同的修改记录就同 dot、同 ID。旧上下文又是「seq ≤ n 都见过」的区间断言：seq 不重合时归并，
    一边的 `{w: n}` 会把另一边 seq ≤ n 的不相干记录判成已被覆盖。
  - 归并时一条修改记录里的三处一起换：dot 的写入者、HLC 的写入者、旧上下文的键。内核要求修改记录的 ID 等于 `edit/<dot 写入者>/<seq>`
    （`native/fushi_fsrs/src/registers.rs:282-286`），只换 ID 会被当成坏数据。中间名字不在集合里的链式改名要追链才验得上（G3 追 3 跳）。
  - 样本库：`merged-*` 8 个名字。1 个归回（5,712 条修改记录，全部与最初写入者同 seq、同 HLC 物理时刻与计数；归一后实体、键、值全部相同）；
    6 个哈希验上、但最初写入者在本集合 0 条记录（共 1,112 条，保持原名）；1 个哈希验不上（35 条）。危险情形（同名字、两套 seq）样本里没有出现，
    条件由构造推出，单元测试造了这个情形。
  - 所有者 2026-11-12 批准（§9 第 5 项）。

**验算不上的**：规范 ID 就是它自己，行为与现在的兜底 ID 相同（不合并、不丢）。同一个 ID 两条规则给出不同规范 ID（只可能是哈希碰撞）
也按验不上处理并计数，不在两个里挑。没归回去的改名写入者保持原名，是有效的写入者，不当坏数据清掉。已知永远落在这一类的：

- 原 ID 已不在集合里、又不能由自然键算出来的兜底 ID。样本库的原生日志里有 1,520 条 review + 26 条 undo 的 ID 是 v5、哪条规则都算不出（实测）；
  推断是旧并入给随机 ID 的原生日志取的兜底 ID，没有逐条追；
- 旧并入沿用目标写入者名的修改记录（`srs_profile_merge.dart:941-946`）：没有改名痕迹，无从认；
- 旧并入第 7 步 c 沿用目标日志 ID 的日志（`srs_profile_merge.dart:674-678`）；
- fushi-ext 重映射的日志（原日志 ID 没存）；
- 备选序号超过枚举上限的牌组、候选全名超过上限的牌组（附录 C）；
- apkg 导入时的副本笔记类型（§5.2 最后一行）：规则现在在内核、算得出，但证据是来源 apkg 里那个类型的结构，派生层手上没有，所以仍验不上；
- 填空序号超过枚举上限、又不在证据里的卡：别名层没有装 `NoteEv.cloze_ords`（填空序号 > 500 的卡验不上，G6c-2）。

历史血统卡不在这一类：样本库的 5,568 张全部验上。归一后 2,856 个规范卡各合并了 2 个观察到的卡 ID（同一条笔记在 U 下的那张历史卡与它的兜底副本），
其上 47,228 个规范日志 ID 各合并 2 条日志，存储内容逐字节相同 47,228 对、不同 0 对。所以读侧成组键与迁移对拍都按「规范卡 + 规范日志 ID」
（§6.1）；按旧 ID 逐条对会多出 47,228 条「重复」。活卡上的 `historyFrom/<旧卡 ID>` 键照旧起作用。

别名表怎么用：

- 内核对外只给规范 ID；命令入参接受任何别名（偏好里存的制卡牌组 / 笔记类型 / 字段映射、AI 撤销记录里的旧 ID 都照常能用）。
  Dart 侧持久化过 ID、又自己拿去做相等比较的地方，升级后做一次幂等的归一（至少 `srs_mining_deck_id`、`srs_mining_note_type_id`、
  `srs_mining_field_mappings`；完整清单是 G9 的验收项）；
- 换代后的新操作一律写规范 ID；一个寄存器的写入按实体的整个别名类归并；日志的读侧成组键（`native/fushi_fsrs/src/history.rs` 的
  `EventKey`）改用规范卡 ID 与规范日志 ID；
- 存储上，索引里的 ID 都是操作体里的原值，归一发生在读侧成组的时候。别名层的读接口（G6c-2）：`canonical` / `members` / `canonical_key`（键里嵌的 ID）/
  `canonical_writer` / `logs_of_class`（按「规范卡 + 规范日志 ID」成组，组内按操作号升序、第一份是代表）。缓存层（`notes` / `cards` / `stats`）现在按原值 ID 建、
  与协议 3 缓存表逐行可比；接到别名层上属于 G9 的「别名层接线」，`cache.rs` 文件头列了还差的 5 件事（应有的卡按规则算规范 ID、寄存器按别名类归并属于索引层判定、
  标签按类内成员合并 `tag_ix`、别名变化时把受影响的规范 ID 记脏等）。语义摘要按原值 ID 记、不过别名表：两台设备的别名表可以不同（§10 第 18 条），摘要不能跟着不同；
- 内嵌的 ID 同样过别名表：键里的 `f/`、`fieldDef/`、`tmplDef/`、`fieldDesc/`、`historyFrom/`，JSON 值里的牌组 / 笔记类型 / `revokes` /
  模板文本里的 `{{fld:<id>}}`，`noteTypeId`。样本库里这些引用全部验得上；
- 某台设备暂时没收到某实体的身份记录或定义史，就暂时不归一，收到了重算该实体的索引——盐集合相同（§5.1）时不存在永久分叉；
- 反方向也成立：证据变少，规范 ID 会退回它自己。Purge / 去重清除把操作变成空洞 / 副本记录之后，如果名字史、`guid` 这类自然键随之没了，
  已经按规范 ID 写下的新操作会与旧操作脱钩（推断，未核实，§10 第 19 条）；信任状态不同的设备槽不同（§3.2），手里的证据也就不同（§10 第 18 条）；
- 内置笔记类型的字段 / 模板表只能追加：删掉一个内置字段，它在存量库里的带盐 ID 就再也归不了一。别名判定把这张表当输入，
  **已搬进内核**（G6c-4 #3393，`native/fushi_fsrs/src/gen4_ids/builtins.rs`：key / 字段种子 / 模板键），别名表因此只是「操作集合 + 盐集合」的函数，
  不再吃宿主输入。两个守卫：`the_table_only_grows` 对冻结的第一版逐项比，`the_table_matches_the_frozen_vectors` 对由 Dart 表生成的 `golden_ids.json` 逐项比——
  两边改了不同步总有一个红。**没搬的是缓存层要的完整默认定义**（字段名、模板、默认牌组等，`CacheConfig.builtins`）：它随应用版本走，是宿主经
  `derive_cfg("caches")` 给的输入（§2.2），配置变了调 `rebuild_caches`；若要连它一起进 Rust，归 G7，同时删 Dart 那份（§9 第 16 项）；
- 别名规则写错了可以改、可以重建，**不需要再断代**。这是把身份判断放在派生层而不是转译里的理由。

对一个从未并入过别人的存量集合，归一是一一对应（每个存量 ID 恰好换一个名字），卡的调度状态逐张不变——迁移对拍会核对
（有单元测试；样本库并入过，一一对应没有在真实库上验过）。

相对旧并入的一处行为变化：旧并入按牌组**此刻的全名**验算（`srs_profile_merge.dart:922-936`），改过名的牌组落到兜底 ID；
这里按名字史验算，会把它归到「原名」的规范 ID 上，与另一边同原名的牌组成为同一个。这与集合内的语义一致；所有者 2026-11-12 批准（§9 第 13 项）。

代价（G3 实测，桌面 Windows，release）：全量判定 2.6 s、堆峰值 77 MiB（结果常驻 27.5 MiB、45 万条，4,206,655 次 v5）；
从旧库装证据 24.4 s（探针代码，没有优化）。卡的候选数 ∝ 笔记别名数 × 模板别名数，随盐数平方增长。
G6c 在新存储上的正式实现：别名表整表重算 10.2 / 4.3 s（389,474 行，wight-mac 2 次），峰值内存见 §6.5。

**证据**（G6c-2）= 盐集合 + 内置表 + 身份记录 + **没被清除的**修改记录里的证据键（`fieldDef/`、`tmplDef/`、笔记的 `noteType`、牌组的 `name` / `parent`、
卡的 `historyFrom/`）的全部历史值 + 日志（ID 与卡都是规范 UUID 的；`ankiId`、锚点时刻、`revokes` 读操作体）+ 旧戳的 dot（只在闭包里出现过
`merged-…` 形状的名字时才扫）。证据按「已清除」的**逻辑标记**排除，不看落没落成空洞：操作集合相同、信任状态相同的两台设备别名表逐行相同。
身份记录不受清除影响（笔记的 `guid`、笔记类型的 `ankiNum` 清除后还在）；丢的是定义史、`noteType` 史、牌组名字与父牌组史——这时由它们派生的卡退回自己的原值 ID，
测试钉了这个行为（§10 第 19 条）。

**重算与增量**（G6c-2 + G6c-4，`store/gen4/alias.rs` 文件头）。逐条维护分三档：

1. 不改证据的不动：ID 是随机的日志落在出现过的卡上（且它在任何盐下的兜底 ID 都不是一个「出现过却没验上」的 ID、undo 点名的日志已出现过）；
   对已在同种类证据里的实体改非证据键；标签、媒体、Checkpoint、Purge 操作本身；不是 UUID 的实体与日志；拿走一条已清除的修改。
2. 只添了笔记、牌组、卡或日志的证据：收尾时用**同一个** `resolve` 在一小份证据 P 上跑一次，证得出就只写这一批自己的行。
   P = 盐 + 内置表 + 全部笔记类型与牌组 + 这一批的笔记与新卡的提示笔记（日志里的 `note`）+ 新卡 + 这一批的日志 + 表里全部候选行（`how` = 兜底 / 验不上，
   经部分索引 `alias_pool` 取，样本库约 4.4k 行）。证得出的四个条件：候选行在 P 里不变；这一批自己的 ID 都验上（随机 ID 除外）；P 里笔记的别名类是全的；
   借来的上下文的规范 ID 与表里的相同。正确性论证（根规则逐 ID、派生只随父类变、新兜底必出自候选行）写在文件头；不追求哈希碰撞下与整表重算一致
   （整表重算本身也只是记冲突）。覆盖原生新建笔记、新卡的第一条复习（日志带 `note`）、新建 / 改名牌组。`Settled.aliases_proven` 报这一批是不是证出来的。
3. 其余整表重算：笔记类型 / 字段 / 模板定义变了、卡先于笔记到达、与带盐成员同 guid、日志不带 `note` 的新卡、拿走 / 清除 / 盐 / 信任变化、写入者证据。
   大批灌入用 `Index::hold_aliases(true)` 攒到最后算一次。

测试 `new_native_entities_are_proven_without_a_full_recompute` 覆盖证得出与证不出（含兜底 ID 的反例）两种，两条路的结果都与从空重建逐行相同。
样本库（wight-mac 2 次）：拿 50 条已有笔记各证一次，平均 18.1 / 12.8 ms，50/50 证出、表不变；对比整表重算 4.3–10.2 s。
据此建议 §10 第 13 条按「增量证明 + 整表重算兜底」关闭，不再做按实体的增量引擎（§9 第 16 项）。**给 G7 的要求**：原生日志写上 `note`，否则新卡的第一条复习走整表重算。

**分叉的可检测**（§10 第 18 条答法 A 的落法，G6c-2）：`Index::hollowed()` 列出本机有生效清除的笔记类型 / 笔记 / 牌组（带 Purge 的操作号、还没落成空洞的证据条数），
`Index::key_evidence(kind, entity)` 回答「这个实体在本机还算数的自然键证据有几条」，`Index::withheld_salts()` 见 §5.1。上层拿一台设备的清单去另一台问，
答案不是 0 的就是会分叉的集合。落成空洞之后本机数不出「它带没带过证据」，所以清单是保守的超集。

### 5.4 并入：操作并集

两个集合 A、B 被用户确认为同一个库：

1. 方向恒定：位置目录名较大的并入较小的。两台设备同时从两边发起，结果相同（现有规则同向，
   `packages/fushi_engine/lib/srs/srs_profile_link.dart:192-196` 按 uid 排序取最小）。下面设 B 并入 A。
2. 本机把绑定改到 A，`salts` 取并集；B 的操作**原样**归到 A 名下——操作号全局唯一，不重编号、不重签内容、不追加副本；
   本机原生日志只需把已上传的段重封段头再传到 A 的根。
3. 在 A 里写一条 `Join{from: B 的集合标识, dir: B 的位置目录名, B 的盐集合}`（受信设备签名的操作）：带 `dir` 与盐，跟随的设备才知道去哪个根找 B，
   盐集合也由此成为操作集合的纯函数（§5.1）。`from` / `dir` 不自动算盐：存量集合的位置目录名就是旧 uid，B 的 uid 要进盐集合，必须写在这条 `Join` 的盐表里——
   写 `Join` 的一侧负责把 B 当前的盐集合整份带上（盐表可以为空）。B 的根里留一个指向 A 的提示。
   别的持有 B 的设备**不凭提示自动跟随**：提示写在没有签名的 `meta.json` 里，谁能写这个存储位置谁就能伪造；它只告诉设备去哪找。
   跟随的依据是在 A 的根里读到受信设备签名的 `Join`；跟随前是否再问一次用户是签字项（§9 第 10 项）。
4. 之后全靠 §5.3：两边同 guid 的笔记、同 `ankiNum` 的笔记类型、同名牌组、内置实体、profile 级设置归到同一个规范 ID；
   两边都改过的同一个字段按 §3.4 的现规则成为冲突。**结果与现在的并入一致**（`srs_profile_merge.dart` 文件头最后一段：
   同 guid 自然合一，同词不同 guid 是两条、交给重复笔记建议），但不重算 ID、不产生第二份历史、没有「暂缓并入」。
5. 本机没有用户数据时，就是只做第 2 步的绑定（先加入）；在途身份链 #3271–#3273 的「先加入」语义由此吸收。
6. 还原备份、导入旧备份里的复习数据，本质上也是一次并入（备份按 uid 存），分两种情形：备份来自**另一个集合**的，写 `Join`；
   备份只是**同一个集合在另一个旧 uid 下**的数据（没有可指的 `from` / `dir`）的，只写一条 `Salts` 把那个 uid 加进来。两条路的盐进同一个并集。
7. 两个被并的集合里若有相同的旧设备 ID，依赖向量区分不了两条承袭日志（§3.2）；存储层现在的行为是拒绝（§10 第 21 条）。

BUG-4011 的拍板不变：首次同步的确认弹框没回答之前不绑定、不并入、也不拉。

### 5.5 存量数据逐类怎么处理

| 存量情况 | 处理 |
|---|---|
| 一个集合、多台设备共用同一个 uid | 标识与目录名取现值，操作转译过界，ID 当别名归一。用户无感 |
| 多台设备各自一个 uid、从没关联过 | 各是各的集合；用户确认后按 §5.4 并入 |
| 已经用旧办法并入过的库（样本库就是） | 并入后的内容本来就在目标 uid 下；副本靠已有的 Dedup 结论归并；兜底 ID 靠 §5.3 的正向计算归到原件；改名写入者只在原件也到了这个集合（同 seq 同记录）之后才归回去，在那之前副本保持改名后的名字（没有东西可并）——这样另一台还停在旧 uid 上的设备之后按 §5.4 并进来时，原件与副本不会成为两条笔记 |
| 并入做到一半（srs.db 里有 `profile_merge/<旧 uid>` 标记或被暂缓） | 旧 uid 的行还在库里，是完整的一个集合：两个集合各自转译，然后按 §5.4 并入。未决：见 §10 第 1 条 |
| 本机去重作业没做完 | 迁移前用冻结的旧代码做完（§6.1 前提）。别的设备没做完的，它们升级时各自做完；永不升级的设备留下的副本靠 §5.3 的正向计算归并 |
| 同机多个 profile | 各自一个 `col`，互不影响 |

### 5.6 Dart 两个文件还剩什么

- `srs_profile_merge.dart`：整个删除。
- `srs_profile_link.dart`（1062 行）：只剩「在位置上发现候选集合、读对方的名字、请用户确认是不是同一个库」，决定之后调一条内核命令（绑定或并入）。
  `_switchUid`、`_resumePendingMerges`、暂缓并入的续跑、`srs_backup_merge.dart` 里的 `srsAdoptProfileUid` 都不再需要。

## 6. 迁移

### 6.1 本机

**谁能迁移**：只有持有换代锁（数据目录里的一个文件锁）的主进程。内核给其它打开方一个「不建库、不迁移」的打开模式：
查词弹窗进程今天会自己打开 srs.db 并跑完整升级阶梯（`native/fushi_fsrs/src/store/schema.rs` 的 `migrate`，内核以可创建方式打开），
换代后它遇到「没有新代文件」或「换代进行中」一律不打开复习，提示去主界面。主进程内的写入方（AnkiConnect、互联 host 的远程复习、后台同步、制卡）
在迁移完成前同样拿不到库。

**文件**：新代用新的文件名，旧 `srs.db` 在整个迁移过程中保持可用——任何时刻都不存在「没有库文件」的窗口。

**前提**（都用冻结的旧代码在旧库上做完，做不完就不开始迁移）：v1 事件 → 操作的旧迁移；本机去重作业；缓存的待办
（收段会话被打断留下的待刷新、缓存口径落后）。旧代读入器开始前自己再查一遍（G2 的 `preflight`）：没启用协议 3、旧事件没迁完、
迁移队列非空、去重作业在跑、收段通道开着，任何一项都拦下——没做完的库里有一部分数据还不在操作日志里，读入器看不见它们，那是丢数据。

1. **空间检查**：需要约「旧库 × 0.3」的空闲空间加余量（现有 `check_upgrade_space`，`store/schema.rs:449`，改成按本节估算）。不够就不开始，说明要多少。
2. **取锁**：换代锁 + 旧库的写锁，持到第 6 步结束。
3. **旁路建新文件**：只读旧库，按（集合、设备、seq）顺序流式转译，写进临时文件；每 2 万条或 32 MiB 提交一批并记下水位。
4. **重建**：对新文件跑 `rebuild_all`。
5. **对拍**。基准不是旧库里现成的缓存表（它允许过期），而是**冻结的旧代码对旧库全量重建出来的缓存**（建在临时库里，不写旧文件）：
   - 每张卡：队列、到期、稳定度、难度、复习次数、遗忘次数；
   - 每个寄存器活着的写入与胜者值；每条笔记的标签集合；每张卡（含不在缓存里的历史血统卡）的有效日志条数；媒体绑定；
   - 口径按规范 ID：卡按规范卡、日志按规范日志 ID 成组后再比。样本库有 2,856 个规范卡各吃进 2 个旧卡 ID，47,228 个规范日志 ID 各对应
     2 条内容相同的旧日志，归回去的写入者的 5,712 条修改记录落在原件上（§5.3）——这些在对拍里合成一条，不是丢了；
   - **任何不等：中止**，不带病换名。临时文件留作诊断，旧文件原样可用。后果见 §9 第 8 项。
6. **提交**：给临时文件做检查点、确认没有残留 WAL，写入「已核对」标记，改成新代文件名——这是提交点。之后封存旧文件：
   在旧 `srs.db` 的 `srs_meta` 里把 `schema` 写成一个远大于 29 的值（一行、一次事务），再尽力把它改名为保留副本。
   提交点之后任何一步中断，下次启动接着做完（都幂等）。
7. **收尾**：生成新设备身份（§3.3）；在新身份的原生日志里写一条 `Salts`（`{U}` + 本机已退役 uid，§5.1——这一步不做，单机对拍全绿而多设备会分叉）；
   偏好里的 ID 归一（§5.3）。G1b 的建议：这条 `Salts` 先于这台设备任何一条按规范 ID 写的新操作——同一台设备的操作按 seq 到达，盐排在前面，
   别的设备应用到它后面的操作时已经有这几个盐（由 G7 落实）。

为什么封存要写旧文件的 `schema`：旧内核把 `srs_meta.schema` 当文本读，读不到就当 0、从头建表（`store/schema.rs:503-512`），
大于自己就拒绝（`:526-530`）。所以「旧版本拒绝打开」只在旧文件里有一个它读得懂、又比它大的 `schema` 时才成立；
改名可能因为别的进程占着句柄而失败，不能只靠改名。新代文件自己也保留 `srs_meta(key TEXT, value TEXT)` 与文本形式的 `schema`，
以防被旧版本当成它的库打开。取值的万位是代：G6 第一部分是 `40001`，之后每次结构变化直接换号——G6c-1 `40002`、G6c-2 `40003`、G6c-3 `40004`、
G6c-4 `40005`（新索引 `alias_pool`）。新代文件没发布过，换号只是让开发期的旧探针文件打不开；**第一次发布时冻结**，定值随 G7。
协议 3 的内核打开它报「比本版本新」、不建表；新代的打开函数在动任何 PRAGMA 之前先判文件种类，协议 3 的库报「不是新代库」、什么都不改（两个方向都有测试）。

G7 接线时的前置（G6c 交接）：第一次 `rebuild_all` 之前写 `derive_cfg(col, "caches", <CacheConfig JSON>)`，否则缓存层为空；
`Settled` 新增 `cache_notes` / `cache_cards` / `cache_stats` 与 `aliases_proven`；`Truth::advance_purge` 对 `Salts` / `Join` 报错说明调用方有 bug，不能吞。

中断续做：第 3 步按水位接着转；第 4、5 步从头重跑；第 6 步见上。提交点之前旧文件一个字节不改。

### 6.2 同步位置

每轮同步，对每个位置：

1. 新根不存在：先用旧代读入器把旧根拉到最新（转译并入承袭日志），再建新根（`meta.json` 是纯函数，§4.1）。新根已存在：按字段核对后加入。
2. 上传：**先**补齐位置上缺的、自己持有的承袭区间，**再**传自己的原生段——位置上任何原生操作依赖的承袭操作因此一定也在位置上。
   位置上同一个操作号已有的槽与自己手里的状态不同时，位置上留靠后的那一份（完整 < 空洞 < 副本记录）；本机的槽不因此改变（§3.2）。
3. 本轮读到了旧根的 meta，就给旧根立围栏（§4.3）；没读到就不写（否则会写出不带 `kdf` 的围栏）。
4. 之后每轮核对旧根：清单指纹变了（新文件、同名重写、被删又重建）就把相关旧段转译并入并上传；围栏不在了就重立。

旧根不删。媒体留在原地。

### 6.3 各种先后顺序

| 场景 | 结果 |
|---|---|
| 两台先后升级，后一台离线期间还在旧版本上写 | 后一台被围栏挡住、不再同步，本机照常用；升级后本机转译，把多出来的尾巴当承袭操作上传。不丢、不分叉 |
| 两台同时升级 | 各自本机转译结果逐字节相同（同一个 T 版本）；新根的 `meta.json` 内容相同；重叠上传的承袭段幂等 |
| 有一台永远不升级 / 已经丢了 | 它已经上传到旧根或已被别的设备收到的部分，由升级过的设备转译上传；只存在于那台设备本机的操作，和现在一样拿不到 |
| 一台**新装**的新版本设备加入一个全是旧版本的位置 | 它照样建新根、立围栏——其余旧版本设备从此停止同步，直到各自升级。这是「任何一台新版本接触位置就触发换代」，不只是老用户升级时 |
| 升级时旧根还在被旧版本写 | 围栏挡不住已经开始的那一轮；§6.2 第 4 步每轮捡漏 |
| 升级中途断电 | §6.1 的续做；位置上的每一步都幂等 |
| 回退到旧版本 | 旧文件已封存，旧版本拒绝打开，不会在旧数据上悄悄继续；位置被围栏挡住。见 §6.4 |
| 旧设备身份分叉过 | §3.2 第 2 种情况：报出来、两支都不丢，不静默取一支 |
| 一台设备不信任 / 拒绝过另一台设备的 Purge | 本机那个操作号的槽保持完整内容；执行了清除的设备上传的承袭段里它是空洞，本机收到后不跟着清；位置上留空洞那一份（§3.2） |
| 加密位置 | 同一把密钥、同一个 `kdf`（原样抄进新 meta）；承袭段用同一把密钥密封；`media-e` 不动 |
| 只有协议 1 旧根（`v2/`）的位置 | 现有的旧根读入代码作为旧代读入器的入口保留（§9 第 4 项） |
| 旧 `.fushisrs` / 旧备份里的复习数据 | 经旧代读入器转译，按 §5.4 第 6 条并入当前集合 |
| 同机多 profile | 逐集合迁移；一个集合对拍不过，整个文件不提交 |
| 服务端先升级，客户端还是旧版本 | 服务端启动时迁移，第一轮同步就在自己的目录上立围栏：经它同步的旧客户端全部停止同步；旧客户端的远程复习被能力位拒绝 |
| 客户端先升级，服务端还是旧版本 | 客户端经服务端同步时在服务端磁盘上立围栏；服务端自己那一轮读到后进入「需要升级」状态，而它的库只在就绪状态才对外提供（`packages/fushi_server/lib/src/server_srs.dart:95`、`:151-155`）——**这份 profile 在服务端上的全部复习服务（远程复习、AnkiConnect、互联制卡）停掉**，直到服务端升级 |
| 服务端一直不升级 | 同上，停到升级为止。它作为纯文件 host 仍能转存新代文件 |

### 6.4 备份与回滚

- 换代前不另做整库备份：提交点之前迁移不写旧文件，旧文件本身就是回退点（与 v2 设计 §13 第 5 条同一思路）。
- 保留副本留多久是签字项（§9 第 3 项）。它很大（样本库 1.75 GB，整理前 3.3 GB）。
- **不支持降级**：与任何一次 schema 升级相同。保留副本只用于灾难恢复——真要回去，把 `schema` 改回原值、文件改回原名、装回旧版本；
  回去之后旧版本被围栏挡住不能同步；再次升级时迁移重做一遍，回退期间的操作成为承袭日志的尾巴，第一次升级后已同步出去的新代操作从位置收回来，
  只有「第一次升级后产生、又没同步出去」的那部分留在被替换下来的新代文件里，需要手动导入。

## 9. 需要签字的取舍

只列改变产品行为或有数据风险的。

1. **断代的范围与触发条件。**
   - 任何一台新版本设备（包括新装的）接触一个同步位置，这个位置就换代；没升级的设备从此不能同步（提示升级），本机照常可用，升级后数据不丢。
   - 服务端与客户端**必须同版本发布**：谁先升，另一侧经它的复习同步就停；客户端先升时，旧服务端上这份 profile 的远程复习、AnkiConnect、
     互联制卡全部停到服务端升级为止；远程复习新旧互相拒绝。
   推荐：接受，发布说明与应用内提示写明；不做跨代兼容层。
   **所有者 2026-11-11 批准**，附硬要求：检测到旧版本就不能让它同步，否则会坏库。落到合并条件上：G7 / G8 / G11 用冻结的真实旧版本二进制实测（§8）——
   旧版本对着换代后的本机文件、同步位置、导出包与备份，一律是报错 / 提示升级，且不写任何一个字节；围栏的三个口子（§4.3）靠每轮捡漏兜住，
   同样要在真实旧版本上演一遍。
   实测的版本范围（**默认口径，所有者可改**）：最后一个只认协议 2 的正式版、最早带协议 3 的正式版、当前最新正式版、
   当前最新 debug-rolling 各一份——围栏声称挡住的每一代协议（§4.3「所有协议 ≥ 2 的版本都认 `minReader`」）都要有一份真实二进制作证；
   具体版本号随 G7 / G8 / G11 的 PR 给出。
2. **v1 因果数据怎么处理。**
   A 彻底丢掉，承袭修改之间只比 HLC：格式最干净；样本库上结果不变，但时钟错过的库会静默换值，现有的 v1 并发冲突（样本 166 个寄存器）不再提示。
   B 保留成承袭操作与副本记录上的紧凑数据（样本库实测：本机存储约 14.2 MB，线格式 30.3 MB，§2.6），判据与现在逐位相同，样本库上活着的修改记录除 `tags` 键外零差异（§3.4）；代价是内核里留一段只读的旧判定。
   注意判据作用在写入的全集上，协议 3 是按到达顺序落库时裁剪：有两类情形结果可以与协议 3 的落库结果不同（§3.4「与协议 3 的差别」），签字时一并看。
   推荐：B。
3. **本机旧库副本与旧同步根留多久。** 副本很大（样本库 1.75–3.3 GB）。
   推荐：本机副本保留到「新代第一次同步成功之后 14 天」自动删，设置里可提前删并显示大小；从不同步的用户保留 30 天。位置上的旧根不自动删，
   提供手动清理（只删段与 head，不碰媒体）。
4. **旧代读入器保留多久**（v1 事件迁移阶梯、schema 1→29 阶梯、去重作业、协议 1 旧根读入、旧段解码、旧 `.fushisrs` / 旧备份）。
   它是冻结代码，带黄金向量，不再改。推荐：旧包 / 旧备份 / 旧段的只读读入长期保留（用户的备份可能放很多年）；
   「从很老的版本直接升到新代」的整条 schema 阶梯保留 6 个月，之后要求先经过一个中间版本。
5. **旧并入留下的重复怎么合。** 推荐：
   - 兜底 ID 按哈希自动归一，零误判（已知 ID 的范围见第 12 项）；
   - 改名写入者按「哈希 + 同 seq 同记录、且没有同 seq 的不同记录」归一（§5.3）。
     只按哈希归的后果：同一个写入者名在两个 uid 下是两套互不相干的 seq 时，两条不同的修改记录会同 dot、同 ID，
     其中一条被当成另一条、或被对方的上下文判成已覆盖——静默丢修改，换代后的新操作还会建在错的判定上。样本库里没有这种情形（只按哈希归也撞不上 0 条），
     条件是按构造推出来的。代价：原件没到这个集合的副本保持改名后的名字（样本库 7 个名字、1,147 条），原件到了再归；
   - 验不上、只是「内容相同」的不自动合，照旧由读侧按内容身份去重（BUG-4218 的现状）。

   备选：全都不动（另一台停在旧 uid 的设备并进来时会出现双份笔记）。
   **所有者 2026-11-12 批准推荐做法。**
6. **ID 规则取「现有规则表去盐」，而不是 v2 设计 §3.1 写的「本地新建随机 ID + 同名牌组事后自动合并」。**
   去盐保持现在的行为（两台设备离线各建同名牌组，合并后是同一个）且存量 ID 能验算归一；§3.1 的写法要再加一套「同名事后合并」的机制。
   推荐：去盐。
7. **服务端配置与远程复习里 `profile` 的含义。** 键名与存量值不变；`srs.profiles` 仍是服务端本机的 profile uid。
   需要服务端维护者确认「同版本发布」与新能力位。
8. **迁移的体验与失败后果。**
   - 时机：推荐升级后第一次进复习前阻塞式迁移，带进度、可中断续做；空间不足或电量低时推迟并说明；重度库在手机上可能要十几分钟（估算）。
   - 对拍不过就中止：**此时新版本里复习完全不可用**，没有自动恢复；退路是装回上一个版本（旧文件没被动过）并导出诊断包。
   - 为了把这种情况挡在换代之前，推荐先发一个只带「预演」的版本（G4b）：后台只读地把迁移和对拍跑一遍，不过的库提前暴露。
     备选：不做预演，直接发。
9. **不过界的清单**（§3.5）：已清除操作的壳、MediaAt 历史、旧链与旧签名（只留指纹）。承袭段由上传它的设备签名而不是原设备——
   一台受信设备理论上可以伪造另一台旧设备的历史（受信设备都是用户自己的设备；旧根留档可对照）。推荐：接受。
10. **别的设备见到并入后是否自动跟随。** A 再问一次用户（推荐，与 BUG-4011「确认之前不并入」一致）；
    B 已确认过同步的 profile 见到受信设备签名的 `Join` 自动跟随（省一次弹框，并集不破坏数据）。
11. **盐集合是集合的共享状态。** 盐由受信设备签名的操作携带、只增不减，本机的已退役 uid 列表只是写这条操作时的输入（§5.1）。
    **所有者 2026-11-12 批准**，并定了载体：迁移的那台设备写一条专门的操作携带初始盐集合，协议 4 为此新增操作种类 15 `Salts`（G1b，#3382）；
    `Join` 盐表里的盐与它取并集。各设备取本机退役列表的后果：盐集合各设备不同 → 同一个存量 ID 的规范 ID 各设备不同 →
    换代后各按各的规范 ID 写新操作，成为永久分叉；单机对拍全绿，多设备才暴露。样本库就是这种情形：2,856 个兜底卡 ID 依赖一个只在本机退役列表里的 uid。
    代价：协议 4 多一个操作种类；没有本机退役记录、又还没收到这条操作的设备暂时验不上那部分别名，收到后重算。
12. **兜底 ID 的「已知 ID」并上「自然键 × 每个盐」算出的 ID。**（§5.3）**所有者 2026-11-12 批准。**
    只枚举集合里出现过的 ID 的后果：样本库 2,856 个兜底卡 ID 验不上，同一张卡的原件与副本成为两张规范卡，
    其上 47,228 对内容相同的日志只能靠读侧内容身份去重（BUG-4218 的现状）。并上之后：兜底卡与同一条笔记在 U 下的那张历史卡归到同一个规范卡，
    两边同一条 Anki 日志的规范 ID 相同，读侧成组键与迁移对拍按规范 ID。仍然只认哈希相等，零误判。
    代价：别名判定的 v5 次数约翻倍（样本库 218 万 → 421 万次，0.84 s → 2.6 s），并随盐数平方增长。
13. **牌组按名字史验算（相对旧并入的行为变化）。**（§5.3）旧并入按牌组此刻的全名验算，改过名的牌组落到兜底 ID、不与任何牌组合一；
    新规则按名字与父牌组的全部历史值验算，改过名的牌组归到「原名」的规范 ID，与另一边同原名的牌组成为同一个牌组（两边的卡进同一个牌组）。
    **所有者 2026-11-12 批准。** 只按此刻的全名验的后果：改过名的牌组的带盐 ID 永远归不了一，
    两个集合里同源、各自改过名的牌组并入后仍是两个。代价：用户可能看到一个改过名的牌组与对方一个沿用原名的牌组合成了一个。
14. **承袭槽由谁推进。** **所有者 2026-11-12 批准**：槽的状态只由本机自己应用 Purge / Dedup 推进；收到别人的空洞 / 副本记录而本机是完整内容时，
    不动本机的槽；「完整 < 空洞 < 副本记录」的并只用于本机还没有该槽、以及位置上同一个操作号留哪一份（§3.2）。
    随之接受的代价：本机还没有某个槽、收到的是空洞时内容永远拿不到（与协议 3 相同）；信任状态不同的设备，同一个操作号的槽可以长期不同（§10 第 18 条）。
15. **G1b / G6 带出、等所有者定的四处。** 前三处正文已按协调方的先行方向写，都可改：
    - T 出下一个版本时，对「秩变了的槽」的规则由那个 PR 写明（§3.1、§10 第 22 条）；
    - 信任状态不同 → 别名分叉：先按「接受分叉 + 可检测并提示」，五种答法的对比在 §10 第 18 条；
    - 旧戳闭包随清除变小：先按「接受，不改线格式」；是推理，没有实测（§3.4、§10 第 14 条）；
    - 承袭段把 `Join`（14）也一并拒掉：G1b 对 G1 的收紧，待确认（§10 第 20 条）。

16. **G5 / G6c / 写路径第 15、16 步带出、等所有者定的几处。** 正文都先按协调方的方向写了，都可改：
    - 被扣住的删除是不是一律盖掉它见过的写入（§2.5 第 9 条）；
    - 「只增不减」的盐集合碰到信任状态变化怎么办：现按「对操作集合单调、对信任状态不单调」写（§5.1、§10 第 17 条）；
    - 旧设备分叉时日志留哪一支：由全集定，取链指纹字节序最小的槽（§3.2、§10 第 2 条）；
    - 别名表的增量重算按「增量证明 + 整表重算兜底」关闭，不再做按实体的增量引擎（§5.3、§10 第 13 条）；
    - 缓存层要的完整默认定义要不要也搬进 Rust（§5.3，搬就在 G7 搬并删 Dart 那份）；
    - 迁移的内存目标改成「灌入 150 MB、重建 350 MB」，还是把 `rebuild_all` 的证据改成流式收（§6.5、§10 第 15 条）；
    - G5 的验收范围收窄为「带盐」的规则；由父 ID 派生、不带盐的规则留到 G12 再搬（§5.2、§8 的 G5 / G12 行）。
    已批准、不用再签的：死状态与死表死列随 G7 换 schema 一起删（所有者 2026-11-12 批准，§2.4、§8 的 G7 行）。

## 10. 未决

1. **并入做到一半的库。** 按 §5.5 处理后是否与「先并完再换代」逐卡相同，只有推理。另外，孤儿清扫如果恰好在旧并入第 3、4 步之间跑过，
   会把旧 uid 的行与标记当无主数据删掉（`fushi/lib/src/srs/srs_profile_cleanup.dart:93-120`），「旧 uid 的行还在」不成立。
   需要按旧并入四个步骤各断一次的测试矩阵；定不下来就退回「换代版本里保留冻结的旧并入代码先把它做完」。
2. **分叉过的旧设备。** 已定的：两支按 `(设备, seq, 链指纹)` 各存一份、并的结果是「分叉」、报出来、都不丢（§3.2，G2）；新身份的 `prev`
   带旧日志末尾的完整链值，分得清接的是哪一支（§3.3，G1）。没定的：两支在依赖向量里怎么区分、重签发副本（HLC 是重签发时刻）与原支怎么归并，
   要对着 `transport.rs:975-1015`、`:2012-2118` 设计，归 G8。G6 第一部分的存储取「本机先应用的那一支是主支，另一支不参与派生」（§3.2）：
   两台设备先应用的若不是同一支，派生状态就不同——与协议 3 拒收另一支的现状相同，但与「操作集合相同则各设备逐条相同」不合，要在这里一并定。
   样本库没有分叉，这条分支只有合成输入覆盖。
3. **承袭段谁都能传与 Purge 重写的交互。** 一台设备两段式重写含已清除内容的承袭段时，落后的另一台可能看到区间「缺失」而把未清除的原文重新传上去；
   读者会作废它，但内容会在位置上再留一阵。核验的推测，没有复现。§3.2 定了位置上同一个操作号留靠后的一份，但不执行那条 Purge 的设备手里长期是完整内容：
   它上传承袭区间时怎么避开位置上已是空洞的操作号、合并回收怎么保证留下的是靠后的一份，要在 G6 / G8 设计并测试。
4. **历史血统卡的别名。** 样本库已量：按 §9 第 12 项的规则，5,568 张全部验上（§5.3）。两个集合并入之后的情形仍没有真实样本。
5. **§4.4 剩下的那个分不出的情况**（空位置 + 从没见过它的设备）是否需要额外手段（例如添加位置时声明「这是加密位置」）。
6. **别名规则的验上率。** 字段 / 模板 / 牌组 / 活卡已在样本库上量过，全部验上（§5.3）。仍没有数据的：填空卡的序号枚举、
   profile 级设置实体（样本库里都没有）、别的库。验上率不够时的后果是「该合的没合」（出现重复），不是丢数据。
7. **新旧缓存是否本来就逐卡相同。** 现有缓存与「从操作全量重放」是否在样本库上逐张相同没有量过；如果旧代码自己重建都与现存缓存不同，
   对拍基准（§6.1 第 5 步）要先在旧代码里对齐。
8. **`loc` 的取值**（§4.4）。谁生成、与位置目录名是什么关系，G1 没有定，只带着它、签住它。G8。
9. **空洞没有时间。** 真相层保证的只有：完整内容与副本记录有 HLC，空洞没有（承袭空洞只有链指纹，原生空洞只有区间末链值）。
   按时刻取前缀的读者（`timeline.rs` 的 `cut_at`）只能用「前后最近的有时间的槽」夹出一个区间，不能给空洞编时间；要精确就得在空洞上留 HLC（线格式改动）。
   G6 第一部分的索引都不按操作的 HLC 排（寄存器按旧判定的排序键、日志按 `at`），所以还没有读法依赖空洞的时间；谁先需要（时间线界面 / 检查点回滚）谁定。G7。
10. **承袭段的文件名、目录与切点。** G1 没有提供文件名函数；约束见 §4.1（不能是 `devices/<旧设备>/seg-…`）。切点另有约束：
    一台设备只能在自己知道完整原链值的 seq 上切承袭段（§3.2）。G8。
11. **协议 3 的代码把协议 4 的东西当成自己的来读的入口。** 已知两处（§4.3：`srs_profile_link.dart:259-276`、`.fushisrs` 导出包），
    没有系统地查过是否还有别的；旧版本还原新备份没有核实。旧根里的墓碑 head 是必需的（§4.3），放在旧根的哪个位置没定。G8 / G11，都要在真实旧版本二进制上验（§8）。
12. **待投递槽的链核对。** 已由 G6 第一部分定：待投递槽带前一环的链指纹，存储层只交出接得上本机末尾的；验不出前一环的只等同号槽经承袭段到达确认（§3.1）。
    本条只为不改动后面的编号而保留。
13. **别名表的增量重算。** 证据变了（收到新的身份记录、定义史、名字史）要重算受影响的实体；G3 只有全量判定（样本库 2.6 s）。
    G6c 的正式实现分三档（§5.3「重算与增量」）：证据不变的不动、只添了笔记 / 牌组 / 卡 / 日志证据的用增量证明只写这一批、其余整表重算。
    样本库上增量证明 50 条平均 18.1 / 12.8 ms（2 次），整表重算 4.3–10.2 s。据此建议按「增量证明 + 整表重算兜底」关闭本条，
    不再做按实体的增量引擎——待所有者定（§9 第 16 项）。
14. **从槽重建的旧戳闭包与老设备累计的闭包是否相同。** 空洞不带旧戳，而老设备的 `sync2_legacy` 含后来被清除的旧修改的旧戳（§3.4）。
    样本库上已量（G6 第一部分，1 次）：4 台承袭设备的闭包与 `sync2_legacy` 逐台相同。但这份库没有被清除的带旧戳修改，「清除后闭包变小」在它上面没有表现。
    仍要所有者定：**接受闭包随清除变小**，还是**空洞保留旧戳**（线格式改动）。先行方向是前者（协调方先行、所有者可改）；它是推理，没有实测（§3.4）。
15. **迁移的内存目标。** §6.5 的 150 MB 对存储层成立（灌入、建索引实测峰值 45–53 MB，1 次）；与它相抵的仍是两个探针实测（装别名证据约 216 MiB、
    打包 162 MB）。G6c 的正式实现量出来了（2 次，`cargo test --release`）：`rebuild_all` 全程峰值 **238 / 327 MB**，**在目标之外**，
    主因是别名证据整份装进内存。两条路：遍历操作时流式收证据、把段切小，或者把目标改成「灌入 150 MB、重建 350 MB」——待所有者定（§9 第 16 项）。
16. **协议 4 的中继件。** §4.2 把中继列为不变的机制，但 G1 没有定义协议 4 的中继件格式（协议 3 的 `FSRL` 转发件 G2 的旧段读入能读）。G8。
17. **盐集合：载体已定（`Salts`，种类 15，§5.1），还剩三件没定。**
    - 已退役 uid 是否已经出现在某种同步出去的数据里，没有核实；
    - **「只增不减」与信任状态变化**：盐只从本机算数的（受信作者的）操作里取。一台设备先受信、它的 `Salts` 进了盐集合，后来被拒绝——那几个盐留不留？
      留，则盐集合是「历史上受信过的作者」的函数，与各设备信任变化的先后有关；不留，则违反只增不减，靠它验上的别名会退回去。G1b 只给并集函数，不回答这个；
      G6 第一部分的绑定表缓存在重建时不清空、只再并一遍，等于默认了「留」，没有人拍过板。它与第 18 条是同一类问题；
    - **带盐的操作不能变成空洞**：原生日志的空洞不带操作体，一条 `Salts` / `Join` 若在某台设备上被清成空洞，没拿到原件的设备就少这几个盐。
      它们不属于任何实体，现有的 Purge 指不到它们；存储层要保证整理 / 压缩也不清它们（G6c）。
18. **信任状态不同的设备，别名证据不同。** §3.2 允许两台设备对同一个操作号一边是完整内容、一边是空洞（一台不执行另一台信任的 Purge）；
    别名表是「操作集合 + 盐集合」的函数，而自然键（guid、名字史、定义史）就在操作内容里。被清除的内容若恰好带着某个实体的自然键，
    两台设备对它的规范 ID 就会不同，之后各按各的规范 ID 写新操作。盐集合同样随信任状态走（第 17 条）。这种情形在协议 3 里是否构造得出来，没有核实。
    五种答法，以及各自落到 G6 的表上要改什么：

    | 答法 | 存储层要动的地方 | 现在的结构是否支持 |
    |---|---|---|
    | A. 接受分叉，只做检测与提示 | 无。别名表是派生表，两台设备各算各的 | 支持 |
    | B. 别名证据在清除之后仍然保留（本机清除一个槽之前，把它带的自然键抄进一张「证据」表） | 加一张**真相**表（证据比它来源的操作活得久，不能再算派生）；写入点只有本机推进槽的那一处。本机**收来**就是空洞的槽没有内容可抄——这种答法单靠存储层补不齐，还得让证据随段走 | 写入点已经是唯一的一处；表要新加 |
    | C. 别名判定改成显式操作（像 Dedup 那样，由某台受信设备把「X 是 Y 的别名」写成操作，别的设备照抄结论） | 无新表：新种类的操作照常进 `ops`；别名表从这些操作建，不再从自然键现算 | 支持（加一个操作种类即可） |
    | D. 槽的状态不再随信任状态分叉（改已批准的 §3.2 规则） | 只改落库时「秩不同」那一个分支 | 规则集中在一个函数里 |
    | E. 规范 ID 只取「所有受信设备都不会清掉」的证据（例如只认身份记录，身份记录不参与 Purge） | 无。是别名规则（G3）与 Purge 语义的事 | 支持 |

    先行方向是 **A：接受分叉 + 可检测并提示**（协调方先行、所有者可改），存储结构不为任何一种答法焊死：真相表的键里没有规范 ID（§2.2），别名规则怎么改都只动派生表；
    「本机推进过」的标志位（§3.2）让本机随时列得出自己清掉的操作号——答法 B / D 需要的清单已经在库里。检测的落法见 §5.3「分叉的可检测」
    （G6c-2：`hollowed` / `key_evidence` / `withheld_salts`）；提示与处置归 G9。
19. **证据变少时规范 ID 退回它自己。** Purge / 去重清除之后，名字史、`guid` 这类自然键是否一定还在（身份记录与定义 / 名字寄存器的历史值在转译后是否一定保留），
    没有核实（§5.3）。不保留时，已经按规范 ID 写下的新操作会与旧操作脱钩。与第 18 条是同一个问题的另一面。G2 / G6c。
20. **承袭段拒 `Join`（14）。** G1（#3376）的承袭段不拒 `Join`；G1b（#3382）把 14 与 15 一并拒掉（打包与打开两侧，不论格式号）。理由：承袭段由上传者签名，
    放带盐的操作进去等于上传者以旧设备的名义改盐集合，转译也从不产生它们。拒 15 随盐的载体已定；**拒 14 是对 G1 的收紧，待所有者确认**。
    不同意就只留 15 那一半（实现里删一行检查、测试里删一项）。
21. **同一个旧设备 ID 出现在两个来源集合里。** 承袭日志按（来源集合、旧设备、seq）定位，但操作号与依赖向量里只有 `(设备, seq)`。两个被并的集合里若有相同的
    旧设备 ID，依赖向量区分不了两条日志。协议 3 的设备 ID 按 profile 生成，同一台设备参加过两个协议 3 集合时会不会重复，没有核实。
    G6 第一部分的存储层遇到这种情形是报错、不静默并成一条。G8 / G9。
22. **T 的下一个版本遇到秩不同的槽。** §3.2 的「高版本胜」与「本机的槽只由本机推进」在秩不同时相交：本机手里是版本 1 转出的槽，来了下一个版本转出的
    同号同指纹的槽，而且秩不同（新版本把某种旧操作改判了，或本机的槽已被本机推进过）。现在的实现是秩不同一律本机不动。T 只有版本 1，这种情形还不会发生。
    先行方向（协调方先行、所有者可改）：不现在定规则，只要求出下一个版本的那个 PR 同时写明它对这种槽的规则（§3.1）；「本机推进过」的标志位已为届时的判据留好。
23. **G6c 与收段通道 #3314 合在一起时的对拍有 5 条红。** 两条链各自绿；合起来（集成预演 #3344 的做法）跑样本对拍时，差异类别有 5 条非空。
    是两边语义的出入，还是对拍装置对 #3314 收段通道的假设不成立，没有定位。G7 要把两者合到一起（§8 的 G7 行），合之前要查清。

## 附录 B：协议 4 线格式细节（G1 / G1b 定）

本稿正文没有定死、G1（#3376，`native/fushi_fsrs/src/gen4/`）与 G1b（#3382）实现时定下的字节层细节。逐字节的布局以各文件头的文档注释为准，这里只列规则。

1. **严格解码。** 协议 4 的一切解码只收规范形：最短 varint、引用的唯一字节形、升序无重复的表、位图「置位 ⇔ 不等于默认值」。
   `fmt == 4` 的操作体必须恰好是定义的字节；`fmt > 4` 才只读已知前缀；`fmt < 4` 拒。协议 3 的宽松读法不动。
2. **操作信封。** `device[16] | seq | wall | logical | deps | kind | fmt`，没有「已清除」位（协议 4 没有骨架，已清除 = 空洞槽）。
3. **链。** `chain_next4 = blake3("fushi-srs-chain/4\n" ‖ prev ‖ envelope ‖ blake3(payload))`。
4. **Edit。** `ent_kind | entity | key | flags | value | [旧戳]`。键把 `f/`、`fieldDef/`、`tmplDef/`、`historyFrom/` + UUID 压成 1 + 16 字节，
   其余留文本，不建固定键名码表（码表是又一份要永久冻结的清单）。原生段里的 Edit 不许带旧戳，打包、打开两侧都拒。
5. **Log。** 位图 + 省略默认值；`res` / `extra` 的 JSON **保留原文**（不二进制化：浮点文本的往返依赖序列化器实现，不同版本输出不同文本会让派生状态分叉）。
   `legacy_hlc` / `legacy_server_time` 只有承袭日志带。
6. **Join（种类 14）。** `from（被并入集合的集合标识）| dir（它的位置目录名）| 盐表（被并入集合的盐，可以为空）`。盐表的字节形见第 13 条。
7. **种类 12 退役**，永不复用；13（Dedup）只许出现在承袭日志；**14（Join）与 15（Salts）只许出现在原生日志**——承袭段的操作槽打包与打开两侧都拒，
   不论格式号（承袭段由上传者签名，放它们进去等于上传者以旧设备的名义改盐集合；转译也从不产生它们）。其中拒 14 是 G1b 加的限制，
   #3376 的承袭段不拒 `Join`，待所有者确认（§10 第 20 条）。协议 3 日志里种类号恰好是 14 / 15 的旧操作转出来是原样件，不应用。
8. **紧凑旧戳。** `flags | 写入者名字 | seq | 上下文（归一后的前缀 + 零散 dot，按写入者字节序）| hlc（三元组或原文）| [server_time 增量]`。
   名字有六种形（UUID / 文本 / `merged-<uuid>` / `merged-<uuid>~<uuid>` / `<base64 公钥>#<代次>` / `sync2:tags:<uuid>`），一个文本只有一种字节形。
   HLC 文本只有「解析得出且重新格式化逐字节相同」才拆成三元组，否则存原文。旧戳是冻结数据，未知标志位一律拒。
9. **原生段 `FSG4`。** 槽 = 操作 | 空洞（条数 + 区间末的链值）。空洞处的链值是作者签名担保的陈述，读侧验不了，所以含空洞的段只能由作者签出，
   非作者只能原样转发作者的字节；空洞在段边界处截断。相邻空洞必须合并；依赖向量的「同上一条」标志读侧强制。
10. **承袭段 `FSH4`。** 段头带所在集合 / 来源集合（原协议 3 集合标识）/ 旧设备 / 上传者 / T 的版本 / 首尾 seq / 首尾的完整原链值，上传者签名，不成链；
    读侧核对签名、槽覆盖的区间、末槽的链指纹。槽 = 操作 | 原样件 | 副本记录 | 空洞，**每个 seq 一个 8 字节链指纹，空洞也逐条带**。
    一段只含同一个 T 版本转出的槽。另有槽的独立规范编码（绝对 HLC、完整依赖向量），「同号同字节」的幂等判定比的是它，不是段内的增量编码。
11. **head。** 规范 JSON（键按字节序、无空白、只许整数、无重复键），解码时「重新规范化 ≠ 原字节」即拒；签名覆盖除 `sig` 外的全部键（含不认识的）；
    新字段 `gen / loc / seal / derive / prev{device, seq, chain} / ext`；段清单键 `segs`，仍要求连续覆盖 `1..=seq`；签名原文带域前缀 `"fushi-srs-head/4\n"`；
    `minReader > 4` 在验签之后、读其余字段之前报「需要升级」。
12. **黄金向量。** 操作体每种、操作与链、段体与段头的未压缩字节（编码方向）、整段文件（解码方向——zstd 的输出不是跨库版本的契约）、
    head 文件（两个方向）、T 的每条规则各一条旧操作转出的槽。加上 `Salts` 之后操作体的向量是 17 个。
13. **Salts（种类 15）与盐表**（G1b）。`Salts` 的操作体就是一张盐表，至少一项（空的拒）。盐表 = `项数 | 项数 × 文本`，按 UTF-8 字节严格升序（于是无重复），
    不超过 65,536 项；`Join` 与 `Salts` 共用同一张表、同一种字节形。盐是不透明的文本，相等 = 字节相等：不折叠大小写、不做 Unicode 归一、不剪空白、
    不解析成 UUID、不特判空文本。集合的盐集合 = 本机算数的操作里全部 `Salts` 的盐 ∪ 全部 `Join` 盐表里的盐——并集，与到达顺序无关、重复无害、只增不减，
    没有删盐的操作；`Join` 的 `from` / `dir` 不算盐。
