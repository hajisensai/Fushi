## 0. 一句话

**操作日志是唯一的真相，其余全是能从它重建的索引和缓存；历史靠「逐条、确定、只看这条操作自己」的转译过界，所以不需要谁先谁后，也不会出现第二份历史。**

三件事一次做完：

1. **存储**：本机只留一层真相（操作），旧事件投影和笔记 / 卡片缓存之间那一层删掉；真实库 1.75 GB → 约 0.32 GB（实测试算，§2.6）。
2. **格式（协议 4）**：新写入不再携带、不再生成任何 v1 形状的因果数据；媒体「在不在」不再是永久操作；head 自带按位置签名的加密标记；
   旧设备日志变成冻结的「承袭日志」。
3. **身份**：集合与 profile uid 脱钩；ID 规则表去掉 uid 这个盐；存量带盐 ID 不改写，在派生层当别名归一；并入 = 操作并集，不再重算 ID、不再追加副本。

代价也要先说：换代是一次全设备、含服务端的同版本升级（§9 第 1 项）；别名归一是本稿风险最高的一块（§5.3、§10）。

## 1. 现状与体积去向（实测）

### 1.1 三层存储

| 层 | 表 | 说明 |
|---|---|---|
| 操作日志 | `sync2_ops`（`native/fushi_fsrs/src/store/sync2/schema.rs:28`） | 每设备哈希链，载荷是操作的线格式字节，每行另存 32 B 链值 |
| 旧事件投影 | `srs_entities` / `srs_field_edits` / `srs_review_logs` / `srs_event_local`（`native/fushi_fsrs/src/store/schema.rs:133-177`） | v1 时代的「事件表」，v2 迁移时原样留下（v2 设计 §13 第 5 条），之后每条操作都再投影成一行 |
| 缓存 | `srs_notes_cache` / `srs_cards_cache` / `srs_stat_reviews`（`schema.rs:191-255`） | 出卡、浏览、统计实际读的表 |

三层之间还有一批「谁对应谁」的映射表：`sync2_ent_ops`、`sync2_edit_ops`、`sync2_log_meta`（`sync2/schema.rs:82-106`）。
写入路径是 `sync2_apply_local` → `project_body` → `land_edit` / `project_log` / `project_entity` → 缓存刷新
（`native/fushi_fsrs/src/store/sync2/mod.rs:1252`、`:1397`、`:1495`、`:2165`）。**没有「从 `sync2_ops` 全量重建投影」的入口**：
投影层丢了就回不来，所以它事实上也是真相——这是体积与复杂度的根。

出卡（`store/queue.rs`）、学习（`store/study.rs`）、浏览正文（`native/fushi_fsrs/src/store/browse.rs:1317-1320` 整列读
`srs_field_edits.jslim`）、统计、摘要（`store/sync2/digest.rs:109-113` 覆盖的是投影表的 JSON）读的都是下面两层；`sync2_ops`
只在发件、收件判重、时间线里读。远程复习搬给客户端的也是投影层的修改记录（§7）。

### 1.3 结论：同一份内容存了几遍

1. **字段正文两份**：操作载荷里一份，`srs_field_edits.jslim` 里一份（`edit_row_with`，`store/sync2/mod.rs:977-1027`）。
   活着的修改记录正文合计 303.5 MB（其中两个大字段 5,913 条就占 201.1 MB，平均 34 KB、互不相同），表本身 399.6 MB。
2. **复习日志三份半**：操作载荷 104.6 MB、`srs_review_logs` 174.6 MB、`sync2_log_meta` 52.7 MB、`srs_stat_reviews` 27.0 MB。
3. **副本骨架**：580,100 行（占操作行数 43%）是 `purged = 1` 的骨架。它们是旧并入把另一个 uid 的数据重算 ID、改写入者名字后
   追加进来的副本，之后被去重作业判为「某条的副本」留下的壳（`Op::duplicate`，`native/fushi_fsrs/src/sync2/op.rs:97`），约 85 MB 载荷。
   核验实测：308,420 条修改骨架与它指向的原件**旧写入者全部不同**（骨架是 `merged-…`，原件是原写入者），把两者连起来的只有骨架里的 `of` 指针。
4. **v1 因果上下文**：351,228 条修改记录带 `LegacyStamp`，合计 75.2 MB，其中 `ctx_json` 34.8 MB、写入者名字 16.2 MB、HLC 文本 22.1 MB。
   上下文本身很小：95.5% 只有一个条目，文本体积几乎全是写入者名字（46 字符的旧写入者、`merged-<uuid>`、`sync2:tags:<note>`）。
5. **映射表与死列**：`sync2_ent_ops` + `sync2_edit_ops` + `sync2_log_meta` 170.1 MB；`srs_event_local` 105.7 MB，
   它的 `outbox_seq` 现在只写 NULL（`store/sync2/mod.rs:1039`），真正被读的只有 `server_time` 一列。
6. **每条操作一份链值**：32 B × 133.7 万 ≈ 42.8 MB，实际只在切段处、日志尾部和判分叉时用得到。

### 1.4 v1 因果嵌在 v2 里的四处

1. 每条修改操作可带 `LegacyStamp{writer, seq, ctx_json, hlc, server_time}`（`sync2/op.rs:294`）；
2. 投影行的 `ctx`：v2 原生写入的修改记录也要拼一个 v1 形状的上下文——作者的依赖向量并上「旧修改记录闭包」
   （`edit_row_with`，`store/sync2/mod.rs:977-1005`；闭包存在 `sync2_legacy`，`sync2/schema.rs:192`）；
3. 寄存器判定走 v1 规则：谁的 `ctx` 含对方的 dot 谁支配，剩下的按 `(physical, counter, hlc_writer, id, server_time)` 取最大
   （`native/fushi_fsrs/src/registers.rs:143-163`、`:458-496`）；
4. 合成写入者 `sync2:tags:<note>`（`registers.rs:42`）与对应的剥离函数（`store/sync2/mod.rs:389`、`:598`）。

媒体绑定、`MediaAt`、标签顺序三类寄存器已经用了 v2 自己的规则（`native/fushi_fsrs/src/store/sync2/mvr.rs:1-15`：因果优先、
并发才比 HLC），字段修改没有。摘要覆盖的投影 JSON 里含 `ctx`，所以摘要也绑在 v1 形状上。

### 1.5 身份建在随机 uid 上

- 每台设备第一次打开复习时随机生成 `profiles.uid`（UUIDv7）；集合标识 = `v5(NS, "sync2/collection/{uid}")`
  （`collection_of`，`native/fushi_fsrs/src/store/sync2/mod.rs:111`），同步目录是 `fushi-srs/<uid>/v3/`。
- 规则表里凡是根上的 ID 都拿 uid 当盐（`packages/fushi_srs/lib/src/ids.dart:117-195`）：笔记 `uid/note/<guid>`、笔记类型
  `uid/notetype/<ankiNum>`、牌组 `uid/deck/<全名>`、内置默认牌组 `uid/builtin-deck/default`；字段 / 模板由笔记类型 ID 派生，
  卡 = `v5(noteId, templateId/clozeOrd)`，导入的日志与锚点由卡 ID 派生。profile 级设置（日界等）挂在一个 ID 就是 uid 的实体上。
- 于是两台各自生成过 uid 的设备要成为「同一个库」，只能把一边的全部数据按新 uid 重算 ID 再追加成新操作
  （`packages/fushi_engine/lib/srs/srs_profile_merge.dart` 文件头注释，1234 行）：能还原派生输入的重算，还原不出的走兜底
  `v5(NS, profile-merge/<newUid>/<旧 ID>)`，写入者改名成 `merged-…`，undo 的目标没到就暂缓整次并入。
  BUG-4011 / 4217 / 4218 都出在这条路上；§1.3 第 3 条的 58 万条骨架是它的直接产物。
- 投影与缓存表的主键是全库唯一的 `id`，不带 profile（`store/schema.rs:133-231`），同机两个 profile 靠「ID 里带 uid」才不相撞；
  这也是 v2 设计 §3.1「内置实体固定常量」至今没法照字面做的原因。
- `profiles.uid` 会被改（采用对方 uid、并入后切换），而它同时是备份 / 还原 / 统计 / 媒体目录的键，主库与 srs.db 两个文件
  不能一起提交（`srs_profile_merge.dart` 文件头「原子性」一节的四步顺序）。
- Dart 侧到处「用 uid 现算一个 ID 再拿去比」：带盐派生的调用点约 58 处，例如远程复习客户端现算默认牌组与内置类型 ID
  （`fushi/lib/src/srs/srs_remote_store_client.dart:325-329`）；内核重放也用 `default_deck_id(profile)`（`store/sync2/config.rs:21`）。
  同步目录路径同样由 Dart 按 uid 拼。

### 1.6 Dart 直接读写内核的表

Drift 声明了 10 张 srs.db 的表（`packages/fushi_core/lib/src/database/srs_database.dart:14-26`），`SrsDbStore`
（`packages/fushi_engine/lib/srs/srs_db_store.dart`，6125 行）经 FFI 在 Rust 的写连接上跑 SQL；缓存口径版本在 Dart
（`_kCacheRevision`，`srs_db_store.dart:612`）。在途的写路径链做完第 13、14 步后写站点归零，但仍有一批读站点「暂留 Drift 只读」。
**物理表要换，Dart 就不能再认得任何一张表**——这是本次换代对在途链的硬依赖（§8）。

## 2. 目标存储模型

### 2.1 三类表，只有一类是真相

- **真相**：操作（每个集合、每台设备一条日志）。本机不可再生、同步时交换的只有它。
- **派生**：索引与缓存。全部能由一条内核命令从操作重建，口径变了就重建，不参与同步、不参与备份。
- **本机状态**：设备密钥、信任表、位置进度、待投递队列这类「不属于集合、别的设备也不该知道」的东西，量很小，原样带过去。

所有表的主键都带本机集合号 `col`（小整数，对应 §5.1 的绑定表），设备用小整数下标。同机多个 profile / 多个集合天然不相撞，
不再依赖「ID 里带盐」。本机状态现在按 profile 分行（例如 `sync2_self` 每个 profile 一行），换代后按 `col` 分行，含义不变。

### 2.2 表（示意，定名随实现 PR）

| 类 | 表 | 键 | 内容 |
|---|---|---|---|
| 真相 | `ops` | `(col, dev, seq)` | 一条操作：HLC、依赖（内部化的版本向量号）、种类、标志、操作体。操作体只存这一份；≥ 256 B 的字段值本机用 zstd 压；承袭操作另带 8 B 原链值指纹（§3.2） |
| 真相 | `op_alias` | `(col, dev, seq)` | 副本记录：这个操作号是另一条 `(设备, seq)` 的副本，带它自己的旧戳（§3.1） |
| 真相 | `op_voids` | `(col, dev, first)` | 空洞区间：这段 seq 没有内容（已清除、不过界的种类）。原生日志的空洞另留 32 B 哈希以便验链 |
| 真相 | `op_deps`、`writers`、`log_marks`、`snapshots` | | 依赖向量内部化表；旧写入者名字内部化表；切段处与尾部的链值；日志引用的调度配置快照（v2 设计 §4.6） |
| 派生 | `ent_ix` | `(col, id)` | 实体 → 定义它的操作 |
| 派生 | `reg_ix` | `(col, ent, key, dev, seq)` | 寄存器的全部写入 + 当前胜者标记（时间线读全部，正文读胜者） |
| 派生 | `log_ix` / `log_id` | `(col, card, at, dev, seq)` / `(col, id)` | 日志索引，并入统计要的列（原 `srs_stat_reviews`） |
| 派生 | `tag_ix`、`media`、旧闭包索引 | | 标签 OR-Set、媒体名 → 内容绑定、§3.4 用的闭包 |
| 派生 | `alias` | `(col, id)` | 存量带盐 ID → 规范 ID（§5.3） |
| 派生 | `notes`、`cards` | `(col, id)` | 出卡 / 浏览 / 统计读的缓存，列与现在的两张缓存表相同 |
| 本机状态 | 设备身份、信任、暂扣、位置、段清单、待投递、检查点、中继 | | 现有 `sync2_self` / `sync2_trust*` / `sync2_held` / `sync2_locations` / `sync2_segments` / `sync2_pending` / `sync2_checkpoints` / `sync2_relay_*` 的内容 |
| 本机状态 | `media_local`、`media_at` | | 本机媒体文件登记；各位置「有哪些媒体」的缓存（§4.5） |

本机存储编码（压缩、写入者内部化）与线格式分开定版本：线上是规范字节（链与签名算它），本机怎么存是存储细节，以后可以再改而不动协议。

### 2.3 读路径

| 读者 | 现在读 | 以后读 |
|---|---|---|
| 出卡、到期计数、牌组树 | `srs_cards_cache` / `srs_notes_cache` | `cards` / `notes`（列相同） |
| 浏览列表、排序、筛选 | 两张缓存表 | 同上 |

| 整列读正文（浏览全文搜索） | `srs_field_edits.jslim` 顺序扫（`store/browse.rs:1317-1320`） | `reg_ix` 扫胜者 → 逐条取操作体（代价见 §2.6） |
| 评分时重放一张卡的历史 | `srs_review_logs` + `sync2_log_meta`（`store/sync2/mod.rs:1654`） | `log_ix` 按卡 → 操作体 |

| 远程复习的客户端 | 主机搬来的投影行，客户端本机物化 | 主机搬新代的物化输入（§7） |
| apkg 导出、备份、还原、`.fushisrs` | Drift 直读（`packages/fushi_engine/lib/srs/apkg/srs_apkg_export.dart:206` 等） | 内核命令 |

### 2.4 删掉什么

- 旧事件投影：`srs_entities`、`srs_field_edits`、`srs_review_logs`、`srs_event_local`、`srs_unknown_events`、`srs_sent_batches`；
- 映射表：`sync2_ent_ops`、`sync2_edit_ops`、`sync2_log_meta`、`sync2_card_deck`；
- v1 形状的中间产物：投影行的 `ctx`、把闭包当真相存的 `sync2_legacy`（改成可重建的派生索引）、给原生写入拼 v1 上下文的代码、
  摘要对 `ctx` 的依赖、`sync2_mvr` 里 `MediaAt` 的寄存器；
- 逐条投影与收段通道两条写法合成一条（索引本来就是事后建的，`sync2_boot*` 的「先追加、后折叠」成为唯一写法）；
- Dart：Drift 的 srs.db 执行器与 `srs_database.dart`，`SrsDbStore` 里的 SQL，`_kCacheRevision`（口径版本只在内核一条阶梯），
  所有「用 uid 现算 ID」的调用点（§5.3）。

去重作业（`store/sync2/dedup.rs`）换代后不再运行；它已经得出的结论（Dedup 操作）过界保留（§3.1）。

### 2.5 重建是一等命令

`rebuild_all(col)`：清空派生表 → 顺序扫 `ops` 建索引 → 归一别名 → 物化笔记 / 卡片缓存（逐卡重放）。它同时是：

- 迁移的核对手段（§6.1 第 5 步）；
- 派生口径变化时的升级方式（现在散在 Dart 的 `_upgradeCaches`）；
- 「索引是不是真的只是索引」的常设测试：任何测试库 `rebuild_all` 前后派生表逐行相同。

## 3. 历史过界：逐条转译与承袭日志

### 3.1 转译 T

T 是一个纯函数：输入一条旧操作，输出一条新操作、一条副本记录或一个空洞。**只看这条操作自己**，不看库里别的东西、
不看是哪台设备在转、不看时间。

T 的输入是协议 3 的线格式字节，也就是 `load_op` 还原出来的那份（本机存储把日志里的配置快照剪出去另存、对载荷做过本地压缩，
`native/fushi_fsrs/src/store/sync2/snapshots.rs:1-12`；必须先拼回）。输出是协议 4 的规范字节。

| 旧 | 新 |
|---|---|
| Entity | 原样（重新编码） |
| Edit，带 `LegacyStamp` | 旧写入者、旧序号、旧上下文、旧 HLC、`server_time` **全部保留**，换成紧凑编码；上下文里的合成写入者条目按现有剥离规则去掉；标 `heritage` |
| Edit，不带戳（协议 2 / 3 的原生写入） | 原样（它的依赖向量是真实的因果） |
| Log | 原样（紧凑编码）；`legacy_hlc` / `legacy_server_time` 保留 |
| Tag 增删、标签顺序、Media、Checkpoint、Purge、DeckAlias、未知种类 | 原样 |
| Dedup（13） | 原样（「谁是谁的副本」的唯一依据，样本库 32 条、2 MB） |
| 副本骨架（`Op::duplicate` 的产物） | 副本记录：`of` + 它自己的旧戳（现有闭包按它算，`sync2/op.rs:93-121`） |
| 已清除骨架 | 空洞 |
| MediaAt（12） | 空洞（§4.5 改成位置上的清单） |

每条承袭操作另带原链值的前 8 B（§3.2 判分叉用）。

T **不改任何 ID**（§5.3 说明为什么），不合并、不重排、不改 `(设备, seq)`，不做任何「谁赢」的判断。它丢掉的东西是有限的一张表（§3.5）；
谁是胜者、谁和谁是同一个实体，都放在派生层：派生层错了能改、能重建，T 错了是永久的。T 带版本号，用黄金向量冻结。

待投递队列里还没应用的远端操作（样本库 2,582 条，前面缺一段）同样转译，仍留在待投递队列。

### 3.2 承袭日志

每台旧设备的日志转译后成为一条**承袭日志**：

- `(设备, seq)` 不变，所以别的操作对它的依赖、本机的信任表 / 暂扣表 / 检查点里引用的操作号都还指向同一条；
- 它是冻结的：原设备换代后不再往里写（§3.3），不再成链、不带原设备签名，由上传者签名；
- **任何升级过的设备**都可以上传自己手里那一段。链指纹相同的同一条操作，谁转出来都逐字节相同，按操作号幂等；
  `T(S1) ∪ T(S2) = T(S1 ∪ S2)`，不存在「谁先换代、别人以它为准」的角色；
- 没升级的设备之后再升级，把自己多出来的尾巴转译上传即可——承袭日志在它的主人升级之前是开口的。

同一个操作号在两台设备上不一样，有两种情况，处理不同：

1. **一边完整、一边是副本记录或空洞**（那台设备已经应用了 Dedup / Purge，这台还没有）。链指纹相同，属于正常：
   Dedup / Purge 操作本身也过界，这台设备收到并应用后同样把它变成副本记录 / 空洞。收到时本机是完整操作、来的是副本记录或空洞，
   就以来的为准；反过来不动。于是只要操作集合相同，各设备最终逐条相同。
2. **链指纹不同 = 那台旧设备的身份分叉过**（数据目录被拷到另一台机器上各自继续写；现有代码用链值判这种情况并拒收其中一支，
   `native/fushi_fsrs/src/store/sync2/transport.rs:975-980`、`:1000-1015`，分叉的设备换身份重签发，`:2012-2118`）。
   这时两份内容不同，**绝不能「先到先得」**：本机把它记成该设备的分叉、照现有做法报出来，两支都不丢。
   两支在依赖关系里怎么表示是未决项（§10 第 2 条）。

副本的归并只靠显式的副本记录（Dedup 的结论），不靠「旧修改记录 ID 相同」：并入副本的旧写入者是改过名的，ID 本来就不同（§1.3 第 3 条）。

### 3.3 设备换新身份

换代时每台设备给自己生成新的设备 ID，原生日志从 seq 1、新链开始；签名密钥沿用。新 head 里带
`prev = {旧设备 ID, 旧日志的末尾 seq}`，用同一把密钥签，别的设备据此把对旧设备的信任与设备名带到新身份上，不重新弹确认。

为什么不沿用旧设备 ID 接着编号：回退到旧版本继续用、之后再升级一次时（§6.4），旧库会在旧编号上继续长，如果新代的原生日志也用同一段
编号就会相撞。换新身份后，回退期间多出来的旧操作只是承袭日志的又一截尾巴。

### 3.4 去掉 v1 因果：去掉的是机制，不是历史数据

推荐方案（§9 第 2 项的 B）：**寄存器的判定结果与现在逐位相同**，变的是数据从哪来。

- 承袭的带戳修改自带 dot（旧写入者 + 旧序号）与旧上下文，彼此之间照现规则：上下文含对方的 dot 就支配；
  活着的按 `(physical, counter, hlc_writer, id, server_time)` 取最大；多条活着且值不同就是冲突（`registers.rs` 现有逻辑，冻结）。
- 原生写入（换代后的，以及换代前不带戳的）对别的写入：依赖向量覆盖对方的操作号就支配（`store/sync2/mvr.rs:40` 的 `covers`）；
  对带戳的承袭修改，再加上「依赖向量覆盖到的承袭操作与副本记录的旧戳闭包」——就是现在 `legacy_closure` 的定义，只是闭包从
  「存着的真相」变成由操作重建的派生索引。
- **换代后的新写入不携带、也不生成任何 v1 形状的数据**：没有旧戳、没有拼出来的上下文、没有合成写入者；摘要不再含上下文。

这样「v1 因果从 v2 里拿掉」落在三处：格式里它只存在于冻结的承袭操作上；存储上它从 75.2 MB 降到 约 7.5 MB（旧戳 5.8 MB + 写入者名字表 1.7 MB）；
代码上给原生写入拼 v1 上下文、存闭包、摘要绑上下文这些都删掉，只留一段只读的、只对承袭数据生效的判定。

为什么不干脆丢掉旧上下文、承袭修改之间只比 HLC（§9 第 2 项的 A）：

- 「因果在后」推不出「HLC 更大」。HLC 不跟随超前过多的远端时钟（`native/fushi_fsrs/src/sync2/hlc.rs:6-8`、`:130-134`）。
  手机日期快了两天改了字段，桌面收到后把它改回来——现在桌面那条支配手机那条；只比 HLC 的话换代后手机的旧值赢，而且没有任何提示。
- 样本库上两种规则的结果相同（附录 A 的 `probe_lww3.py`：337,519 个只留一条记录的寄存器里 0 个不一致，其中 15,114 个有被支配的历史；166 个留着多条的寄存器，HLC 最大的那条都在留下的集合里），但这只说明这份库没有那样的时钟历史。
- 保留的代价实测只有 约 7.5 MB（旧戳 5.8 MB + 写入者名字表 1.7 MB），不值得为它改结果。

### 3.5 不过界的东西（T 的不可逆清单）

1. 已清除操作的骨架信封（Purge 操作本身过界，清除语义不变）；
2. MediaAt 操作——由位置清单替代，本机「各位置有哪些媒体」的缓存用旧表播种；
3. 旧链值（只留 8 B 指纹）与旧设备对旧段的签名——承袭段由上传者签名。旧同步根原样留在位置上（§6.2），需要追溯时它还在；
4. 旧上下文里的合成写入者条目（现有代码读的时候本来就剥掉）；
5. 旧载荷的文本编码（写入者名字、HLC 文本、JSON 形状）——信息不丢，换成紧凑编码。

### 3.6 否决过的做法

- **单设备创世快照**（一台设备把当前状态拍成新代的起点，别的设备以它为准）：哑存储没有比较并交换，两台同时升级会各拍一份；
  落后设备没上传的操作无处安放；与 BUG-4011 同类的「同一份历史两条流」风险。它也违背 v2 设计「不做快照」。
- **不转译，只叠一层别名**：投影层、映射表、每条链值永远留着，体积只能降一半。
- **转译时把存量 ID 重算成无盐 ID**：字段 / 模板 / 卡 / 日志的 ID 层层派生，重算要知道「这个 ID 当初是由什么算出来的」，
  这要看别的操作（笔记类型的字段定义史、卡属于哪条笔记哪个模板）；各设备手里的操作集合不同，同一条操作就可能转出不同结果——
  而转译结果是永久的。这正是现在 `srs_profile_merge.dart` 的 1234 行与那几个 bug 的来源，不能搬进一次性的转译里。
- **把副本骨架与 Dedup 当空洞丢掉、靠内容身份归并**（本稿初版）：核验实测副本与原件的旧写入者不同，内容身份对不上（§11 第 3 条）。

## 4. 目标同步格式（协议 4）

### 4.1 相对协议 3 的改动

| 项 | 协议 3 | 协议 4 |
|---|---|---|
| 集合根 | `fushi-srs/<profile uid>/v3/` | `fushi-srs/<位置目录名>/v4/`（存量集合的目录名不变，§5.1） |
| 操作体 | Edit 可带文本形状的 `LegacyStamp`；键是文本 | 原生 Edit 没有任何旧戳；承袭 Edit 带紧凑旧戳；键二进制；Log 紧凑编码。操作体带格式版本，未知字段保留原字节（v2 设计 §8 不变） |
| 操作种类 | 1–13（`sync2/op.rs:18-33`） | 去掉 12 MediaAt 与「已清除」骨架；副本骨架改成副本记录；新增空洞区间记录与 `Join`（§5.4）。13 Dedup 只出现在承袭日志里，新代不再产生。其余种类语义不变 |
| 段 | `FSG2`，每设备成链（`sync2/segment.rs`） | 原生段：新魔数，结构与构造不变（zstd + 可选 XChaCha20-Poly1305 + Ed25519，按体积切段、分层合并）。承袭段：不成链，由上传者签名，头里带来源集合、T 的版本、区间首尾的完整原链值 |
| 文件名 | 自写 head `head-…`、段 `seg-…` | 前缀不变（互联 host 的长轮询唤醒与设备名补全认这两个前缀，`packages/fushi_engine/lib/srs/sync2/srs_host_directory.dart:26-28`） |
| 链 | 每条操作一份链值 | 算法不变；链不含集合标识（并入时只需重封段头，§5.4）；本机只在切段处与尾部存链值 |
| head | 字段见 `sync2/segment.rs`；被中继原样转发 | 增加 `seal`（按位置签的加密标记，§4.4）、`prev`（§3.3）、派生口径版本；被转发的 head 换文件名前缀，不当作位置证据 |
| 摘要 | 4096 桶，覆盖投影表 JSON（含 `ctx`），前缀 `5:` | 4096 桶，覆盖语义状态（寄存器活着的写入的内容身份、标签集合、每卡日志 ID 集合），新前缀 |
| 媒体「在不在」 | MediaAt 操作，永久留在日志里 | 位置上的每设备清单文件（§4.5） |
| `meta.json` | `v, minReader, collection, createdAt, kdf?`（握手 `srsLocationHandshake`，`packages/fushi_engine/lib/srs/sync2/srs_location_crypto.dart:324`） | **内容是纯函数**：集合标识 + 从旧根原样抄来的 `kdf` + 媒体目录所在的根，不含任何时间戳；`kdf` 只当参数载体，不再是「这个位置加密了」的唯一证据 |
| 远程复习 | 能力位 `srsRemoteStoreV1`，搬投影行 | 能力位 `srsRemoteStoreV2`，搬新代的物化输入；新旧互相明确拒绝（§7） |

`meta.json` 为什么必须是纯函数：没有一种传输提供原子的「不存在才写」（都是先查后写；互联 host 的 PUT 不认条件头；Google Drive 允许同名文件），
现有 meta 还带时间戳。两台设备同时建新根时，只有内容逐字节相同才无所谓谁覆盖谁。读到已有 meta 时按字段比较，不一致就停下报错。

### 4.2 不变的机制

每设备一个目录、只增文件 + 两段式删除、按体积切段与分层合并、段的压缩 / 加密 / 签名构造、HLC、原生操作的因果投递与依赖向量、
标签 OR-Set、Purge / Checkpoint / 时间线恢复、设备信任纯本机（首次信任 + 待确认）、中继（`FSRL`）、新设备收段通道、发件分批、
`min_reader` 握手、未知种类原样保存转发、身份分叉的检测与换身份重签发、`.fushisrs` 的容器形状（清单改记集合标识与来源盐）。

### 4.3 旧根围栏

升级过的设备在新根就绪后，**在本轮读到了旧根 `v3/meta.json` 的前提下**把它改写成合法 JSON：`minReader: 4`，原样保留 `collection` / `kdf`，
加一个指向新根的提示字段。协议 2 / 3 的客户端读到 `minReader` 大于自己就整位置不碰、提示需要升级
（`packages/fushi_engine/lib/srs/sync2/srs_folder_location.dart:211-213`、`srs_location_crypto.dart:391`；这条检查在协议 2 发布之前就有，
所有协议 ≥ 2 的版本都认）。协议 1 的旧根 `v2/` 早在 2026-10-30 的断代里就有魔数行围栏
（`packages/fushi_engine/lib/srs/sync2/srs_location_migration.dart:54`）。

围栏只是「让旧版本停下并提示」，**不是正确性的依据**，它至少有三个口子：

1. 云盘的覆盖写是先删后传，中间 meta 不存在的那一刻，旧客户端会重建一份 `minReader 3` 的 meta；
2. 旧客户端一轮之内不复查 meta，已经开始的那一轮照样上传、合并小段、两段式删除；
3. 旧客户端的 profile 关联步骤在握手之前跑，某些情况下会删掉旧根下的目录，连带围栏。

所以正确性靠 §6.2 的捡漏：升级过的设备每轮核对旧根（清单指纹、围栏是否还在），把新出现的、被同名重写的旧段转译并入，围栏不在就重立。

### 4.4 head 加密标记（原 PR-D）

现状的洞（v2 设计 §9 末尾）：本机从没见过这个位置加密、`meta.json` 又恰好丢了 `kdf`、位置上一时列不到任何密封文件的那一轮，
分不出「加密位置」和「明文位置」。台账里它被定成「不断代做不到」，因为 head 会被中继原样转发到明文位置，head 里的标记不能当证据。

协议 4：

- 设备在每个位置上写的 head 带 `seal = {密钥指纹}`（明文位置为空），连同位置标识一起进签名；
- 中继转发的 head 用另一个文件名前缀，读者不拿它判断「本位置是否加密」；
- 读者只要在位置上见到任何一个本位置自写、带 `seal` 的 head，就按加密位置处理：没有密钥就停，绝不写明文；
- 本机对「这个位置见过加密」的记忆保留（不降级）。

剩下分不出的只有「位置上一个文件都没有、本机也从没见过它」——这与一个全新的空位置无法区分，属于固有情况；
之后任何记得它加密过的设备回来都会发现并拒绝（§10 第 5 条）。

### 4.5 媒体「在不在」

- 每台设备在每个位置上维护自己的清单文件：我确认过这个位置上有哪些内容哈希（增量文件，可合并回收）。读者取并集。
- 本机 `media_at` 只是缓存，丢了重新列一遍；迁移时用旧的 `sync2_media_at` 播种。
- 媒体文件本身不动：存量集合继续用 `fushi-srs/<U>/v3/media` 与 `media-e/<指纹>/`，新根的 `meta.json` 记下这个位置，**不重传**
  （样本库 34,069 个媒体绑定、632 MB）。
- 媒体名 → 内容的绑定（Media 操作）仍是操作，属于集合内容。

## 5. 集合身份模型

### 5.1 集合与 profile uid 脱钩

- 内核持有绑定表 `collections(col, profile_uid, 集合标识, 位置目录名, salts, …)`。Dart 仍然用 profile uid 调内核，内核查绑定；
  `collection_of(profile)` 这种「由 uid 算集合」的函数消失，Dart 也不再自己拼同步目录（现在按 uid 拼，
  `packages/fushi_engine/lib/srs/sync2/srs_location_runner.dart:39-47`），改成向内核要。
- **`profiles.uid` 从此不再改变。** 采用对方 uid、并入后切 uid 这两条路都改成「改绑定」，只动 srs.db 一个文件，一次事务。
  备份、还原、统计、媒体目录、偏好键后缀、AI 会话这些按 uid 存的东西键不用动。
- 一个集合有两个对外的值，**存量集合两者都取现值，不改任何已经写出去的字节**：
  - 集合标识（段头 / head / `meta.json` 里的 `collection`）：存量 = 现有的 `v5(NS, "sync2/collection/{U}")`；
  - 位置目录名（`fushi-srs/<它>/`）：存量 = 旧 uid 的值 U。
  新集合在第一次有内容要写时随机生成一个 UUIDv7，两个值相同；加入已有集合的设备不生成，直接绑定对方的。
- `salts`：这个集合里出现过的旧 uid（存量集合初始为 `{U}` 加上本机记着的已退役 uid，并入时取并集）。只给 §5.3 的别名验算用。
- 同机两个 profile 不能绑定同一个集合（现在也禁止，`srs_profile_merge.dart:281-296`）；内核拒绝这种绑定。
- 改绑定时本机状态怎么办：信任、暂扣、检查点跟着 `col` 走，不变；位置进度与段清单是「某个根」的进度，换了根就从头对账（幂等）。

### 5.2 ID 规则：现有规则表去掉盐

新写入的实体一律按现有规则表、去掉 `<profileUid>/` 前缀：

| 实体 | 规范 ID |
|---|---|
| 笔记 | `v5(NS, note/<guid>)` |
| 笔记类型 | `v5(NS, notetype/<ankiNum>)`；内置类型的 `ankiNum` 本来就是固定常量（`ids.dart` 的 `builtinNoteTypeAnkiNum`），于是**内置笔记类型自然成为所有设备、所有集合相同的常量** |
| 字段 / 模板 | 由笔记类型 ID 派生，公式不变 |
| 卡 | `v5(noteId, templateId/clozeOrd)`，公式不变 |
| 牌组 | `v5(NS, deck/<规范全名>)`，备选规则同理去盐 |
| 内置默认牌组、profile 级设置实体 | 固定常量 |
| 导入的日志、锚点、修改记录 | 公式不变 |

同一个 apkg 在两台互不相识的设备上各导入一次，得到同一批 ID；同机两个集合里出现相同的 ID 不相撞，因为所有主键带 `col`（§2.1）。
这与 v2 设计 §3.1 的差别见 §9 第 6 项。Dart 不再现算任何 ID：要默认牌组、内置类型的 ID 就向内核要。

### 5.3 存量带盐 ID：不改写，在派生层当别名

操作里的存量 ID 一个字节都不动。派生层给每个实体算**规范 ID**，是「这个集合的操作集合 + 盐集合」的纯函数（不依赖到达顺序，随时能重建）。
规则分两种。

**反向验算**（拿自然键按带盐规则重算，对上了才认）：

| 实体 | 自然键从哪来 | 样本库抽查 |
|---|---|---|
| 笔记 | 身份记录里的 `guid` | 15,251 / 15,251 验上 |
| 笔记类型（含内置） | 身份记录里的 `ankiNum` | 10 / 10 |
| 字段 / 模板 | `fieldDef/` / `tmplDef/` 寄存器的**全部历史值**，按 `ankiNum` 与按名字两条规则各试 | 没跑 |
| 牌组 | 身份记录只有创建时刻；用名字与父牌组两个寄存器、连同祖先的全部历史值拼全名，再试备选序号 | 没跑 |
| 内置默认牌组、profile 级设置实体（ID = uid） | 直接对每个盐验算 | — |
| 活着的卡 | 笔记的每个别名 × 它的笔记类型出现过的每个模板别名 × 序号 | 没跑 |
| 导入的复习日志 | 卡 + `ankiId`（`anki-revlog/<id>`） | 332,143 / 332,143 |
| 导入锚点 | 卡 + 发生时刻（`anki-anchor/<时刻>`） | 17,233 / 17,233 |

**正向计算**（旧并入留下的痕迹，能由已知 ID 直接算出，哈希对上才认，零误判）：

- 兜底 ID：对集合里每个已知 ID X 与每个盐 h，`v5(NS, profile-merge/h/X)` 若也出现在集合里，它就是 X 的别名
  （`srs_profile_merge.dart:870`）；
- 改名的写入者：`merged-v5(NS, profile-merge/h/writer/w)` 归到 w（带与不带 `~原写入者` 后缀的两种格式都按哈希验）。

**验算不上的**：规范 ID 就是它自己，行为与现在的兜底 ID 相同（不合并、不丢）。已知一定落在这一类的：不在缓存里的历史血统卡——
核验在样本库上实测，26.8% 的日志（94,460 条）挂在 5,568 张这样的卡上，其中 2,784 张穷举 643 个模板候选后一张也没验上。
它们现在靠活卡上的 `historyFrom/<旧卡 ID>` 键继承历史，换代后照旧；迁移对拍必须覆盖这些卡上的日志（§6.1）。

别名表怎么用：

- 内核对外只给规范 ID；命令入参接受任何别名（偏好里存的制卡牌组 / 笔记类型 / 字段映射、AI 撤销记录里的旧 ID 都照常能用）。
  Dart 侧持久化过 ID、又自己拿去做相等比较的地方，升级后做一次幂等的归一（至少 `srs_mining_deck_id`、`srs_mining_note_type_id`、
  `srs_mining_field_mappings`；完整清单是 G9 的验收项）；
- 换代后的新操作一律写规范 ID；一个寄存器的写入按实体的整个别名类归并；日志的读侧成组键（`native/fushi_fsrs/src/history.rs` 的
  `EventKey`）改用规范卡 ID；
- 某台设备暂时没收到某实体的身份记录或定义史，就暂时不归一，收到了重算该实体的索引——不存在永久分叉；
- 别名规则写错了可以改、可以重建，**不需要再断代**。这是把身份判断放在派生层而不是转译里的理由。

对一个从未并入过别人的存量集合，归一是一一对应（每个存量 ID 恰好换一个名字），卡的调度状态逐张不变——迁移对拍会核对。

### 5.4 并入：操作并集

两个集合 A、B 被用户确认为同一个库：

1. 方向恒定：位置目录名较大的并入较小的。两台设备同时从两边发起，结果相同（现有规则同向，
   `packages/fushi_engine/lib/srs/srs_profile_link.dart:192-196` 按 uid 排序取最小）。下面设 B 并入 A。
2. 本机把绑定改到 A，`salts` 取并集；B 的操作**原样**归到 A 名下——操作号全局唯一，不重编号、不重签内容、不追加副本；
   本机原生日志只需把已上传的段重封段头再传到 A 的根。
3. 在 A 里写一条 `Join{from: B}`（受信设备签名的操作）。B 的根里留一个指向 A 的提示。
   别的持有 B 的设备**不凭提示自动跟随**：提示写在没有签名的 `meta.json` 里，谁能写这个存储位置谁就能伪造；它只告诉设备去哪找。
   跟随的依据是在 A 的根里读到受信设备签名的 `Join`；跟随前是否再问一次用户是签字项（§9 第 10 项）。
4. 之后全靠 §5.3：两边同 guid 的笔记、同 `ankiNum` 的笔记类型、同名牌组、内置实体、profile 级设置归到同一个规范 ID；
   两边都改过的同一个字段按 §3.4 的现规则成为冲突。**结果与现在的并入一致**（`srs_profile_merge.dart` 文件头最后一段：
   同 guid 自然合一，同词不同 guid 是两条、交给重复笔记建议），但不重算 ID、不产生第二份历史、没有「暂缓并入」。
5. 本机没有用户数据时，就是只做第 2 步的绑定（先加入）；在途身份链 #3271–#3273 的「先加入」语义由此吸收。
6. 还原备份、导入旧备份里的复习数据，本质上也是一次并入（备份按 uid 存）：写 `Join`、取盐的并集，走同一条路。

BUG-4011 的拍板不变：首次同步的确认弹框没回答之前不绑定、不并入、也不拉。

### 5.5 存量数据逐类怎么处理

| 存量情况 | 处理 |
|---|---|
| 一个集合、多台设备共用同一个 uid | 标识与目录名取现值，操作转译过界，ID 当别名归一。用户无感 |
| 多台设备各自一个 uid、从没关联过 | 各是各的集合；用户确认后按 §5.4 并入 |
| 已经用旧办法并入过的库（样本库就是） | 并入后的内容本来就在目标 uid 下；副本靠已有的 Dedup 结论归并；兜底 ID、改名写入者靠 §5.3 的正向计算归到原件——这样另一台还停在旧 uid 上的设备之后按 §5.4 并进来时，原件与副本不会成为两条笔记 |
| 并入做到一半（srs.db 里有 `profile_merge/<旧 uid>` 标记或被暂缓） | 旧 uid 的行还在库里，是完整的一个集合：两个集合各自转译，然后按 §5.4 并入。未决：见 §10 第 1 条 |
| 本机去重作业没做完 | 迁移前用冻结的旧代码做完（§6.1 前提）。别的设备没做完的，它们升级时各自做完；永不升级的设备留下的副本靠 §5.3 的正向计算归并 |
| 同机多个 profile | 各自一个 `col`，互不影响 |

### 5.6 Dart 两个文件还剩什么

- `srs_profile_merge.dart`：整个删除。
- `srs_profile_link.dart`（1062 行）：只剩「在位置上发现候选集合、读对方的名字、请用户确认是不是同一个库」，决定之后调一条内核命令（绑定或并入）。
  `_switchUid`、`_resumePendingMerges`、暂缓并入的续跑、`srs_backup_merge.dart` 里的 `srsAdoptProfileUid` 都不再需要。

## 6. 迁移

### 6.1 本机

**谁能迁移**：只有持有换代锁（数据目录里的一个文件锁）的主进程。内核给其它打开方一个「不建库、不迁移」的打开模式：
查词弹窗进程今天会自己打开 srs.db 并跑完整升级阶梯（`native/fushi_fsrs/src/store/schema.rs` 的 `migrate`，内核以可创建方式打开），
换代后它遇到「没有新代文件」或「换代进行中」一律不打开复习，提示去主界面。主进程内的写入方（AnkiConnect、互联 host 的远程复习、后台同步、制卡）
在迁移完成前同样拿不到库。

**文件**：新代用新的文件名，旧 `srs.db` 在整个迁移过程中保持可用——任何时刻都不存在「没有库文件」的窗口。

**前提**（都用冻结的旧代码在旧库上做完，做不完就不开始迁移）：v1 事件 → 操作的旧迁移；本机去重作业；缓存的待办
（收段会话被打断留下的待刷新、缓存口径落后）。

1. **空间检查**：需要约「旧库 × 0.3」的空闲空间加余量（现有 `check_upgrade_space`，`store/schema.rs:449`，改成按本节估算）。不够就不开始，说明要多少。
2. **取锁**：换代锁 + 旧库的写锁，持到第 6 步结束。
3. **旁路建新文件**：只读旧库，按（集合、设备、seq）顺序流式转译，写进临时文件；每 2 万条或 32 MiB 提交一批并记下水位。
4. **重建**：对新文件跑 `rebuild_all`。
5. **对拍**。基准不是旧库里现成的缓存表（它允许过期），而是**冻结的旧代码对旧库全量重建出来的缓存**（建在临时库里，不写旧文件）：
   - 每张卡：队列、到期、稳定度、难度、复习次数、遗忘次数；
   - 每个寄存器活着的写入与胜者值；每条笔记的标签集合；每张卡（含不在缓存里的历史血统卡）的有效日志条数；媒体绑定；
   - **任何不等：中止**，不带病换名。临时文件留作诊断，旧文件原样可用。后果见 §9 第 8 项。
6. **提交**：给临时文件做检查点、确认没有残留 WAL，写入「已核对」标记，改成新代文件名——这是提交点。之后封存旧文件：
   在旧 `srs.db` 的 `srs_meta` 里把 `schema` 写成一个远大于 29 的值（一行、一次事务），再尽力把它改名为保留副本。
   提交点之后任何一步中断，下次启动接着做完（都幂等）。
7. **收尾**：生成新设备身份（§3.3）；偏好里的 ID 归一（§5.3）。

为什么封存要写旧文件的 `schema`：旧内核把 `srs_meta.schema` 当文本读，读不到就当 0、从头建表（`store/schema.rs:503-512`），
大于自己就拒绝（`:526-530`）。所以「旧版本拒绝打开」只在旧文件里有一个它读得懂、又比它大的 `schema` 时才成立；
改名可能因为别的进程占着句柄而失败，不能只靠改名。新代文件自己也保留 `srs_meta(key TEXT, value TEXT)` 与文本形式的 `schema`，
以防被旧版本当成它的库打开。

中断续做：第 3 步按水位接着转；第 4、5 步从头重跑；第 6 步见上。提交点之前旧文件一个字节不改。

### 6.2 同步位置

每轮同步，对每个位置：

1. 新根不存在：先用旧代读入器把旧根拉到最新（转译并入承袭日志），再建新根（`meta.json` 是纯函数，§4.1）。新根已存在：按字段核对后加入。
2. 上传：**先**补齐位置上缺的、自己持有的承袭区间，**再**传自己的原生段——位置上任何原生操作依赖的承袭操作因此一定也在位置上。
3. 本轮读到了旧根的 meta，就给旧根立围栏（§4.3）；没读到就不写（否则会写出不带 `kdf` 的围栏）。
4. 之后每轮核对旧根：清单指纹变了（新文件、同名重写、被删又重建）就把相关旧段转译并入并上传；围栏不在了就重立。

旧根不删。媒体留在原地。

### 6.3 各种先后顺序

| 场景 | 结果 |
|---|---|
| 两台先后升级，后一台离线期间还在旧版本上写 | 后一台被围栏挡住、不再同步，本机照常用；升级后本机转译，把多出来的尾巴当承袭操作上传。不丢、不分叉 |
| 两台同时升级 | 各自本机转译结果逐字节相同；新根的 `meta.json` 内容相同；重叠上传的承袭段幂等 |
| 有一台永远不升级 / 已经丢了 | 它已经上传到旧根或已被别的设备收到的部分，由升级过的设备转译上传；只存在于那台设备本机的操作，和现在一样拿不到 |
| 一台**新装**的新版本设备加入一个全是旧版本的位置 | 它照样建新根、立围栏——其余旧版本设备从此停止同步，直到各自升级。这是「任何一台新版本接触位置就触发换代」，不只是老用户升级时 |
| 升级时旧根还在被旧版本写 | 围栏挡不住已经开始的那一轮；§6.2 第 4 步每轮捡漏 |
| 升级中途断电 | §6.1 的续做；位置上的每一步都幂等 |
| 回退到旧版本 | 旧文件已封存，旧版本拒绝打开，不会在旧数据上悄悄继续；位置被围栏挡住。见 §6.4 |
| 旧设备身份分叉过 | §3.2 第 2 种情况：报出来、两支都不丢，不静默取一支 |
| 加密位置 | 同一把密钥、同一个 `kdf`（原样抄进新 meta）；承袭段用同一把密钥密封；`media-e` 不动 |
| 只有协议 1 旧根（`v2/`）的位置 | 现有的旧根读入代码作为旧代读入器的入口保留（§9 第 4 项） |
| 旧 `.fushisrs` / 旧备份里的复习数据 | 经旧代读入器转译，按 §5.4 第 6 条并入当前集合 |
| 同机多 profile | 逐集合迁移；一个集合对拍不过，整个文件不提交 |
| 服务端先升级，客户端还是旧版本 | 服务端启动时迁移，第一轮同步就在自己的目录上立围栏：经它同步的旧客户端全部停止同步；旧客户端的远程复习被能力位拒绝 |
| 客户端先升级，服务端还是旧版本 | 客户端经服务端同步时在服务端磁盘上立围栏；服务端自己那一轮读到后进入「需要升级」状态，而它的库只在就绪状态才对外提供（`packages/fushi_server/lib/src/server_srs.dart:95`、`:151-155`）——**这份 profile 在服务端上的全部复习服务（远程复习、AnkiConnect、互联制卡）停掉**，直到服务端升级 |
| 服务端一直不升级 | 同上，停到升级为止。它作为纯文件 host 仍能转存新代文件 |

### 6.4 备份与回滚

- 换代前不另做整库备份：提交点之前迁移不写旧文件，旧文件本身就是回退点（与 v2 设计 §13 第 5 条同一思路）。
- 保留副本留多久是签字项（§9 第 3 项）。它很大（样本库 1.75 GB，整理前 3.3 GB）。
- **不支持降级**：与任何一次 schema 升级相同。保留副本只用于灾难恢复——真要回去，把 `schema` 改回原值、文件改回原名、装回旧版本；
  回去之后旧版本被围栏挡住不能同步；再次升级时迁移重做一遍，回退期间的操作成为承袭日志的尾巴，第一次升级后已同步出去的新代操作从位置收回来，
  只有「第一次升级后产生、又没同步出去」的那部分留在被替换下来的新代文件里，需要手动导入。

### 6.5 耗时与内存

实测（附录 A，§1.2 的真实库，桌面 NVMe，Python 单线程）：转译 + 建索引 133.7 万条操作 两次试算差得很远：早一版 24–28 s，按设计格式重跑的那次 251 s（当时机器上同时跑着别的重活，没有拆清是格式多出来的工作还是抢占），复制缓存 4–64 s（同上）。
脚本进程峰值常驻内存 约 335 MB，其中大部分是 Python 自己的字典，不代表内核。

估算（依据写在后面，**必须真机复测**）：

- 桌面：转译 + 建索引不慢于上面的 Python 数；重建缓存参考收段通道的实测（`docs/specs/2026-11-03-srs-sync2-bootstrap-channel.md` §6：
  重放 17,386 张卡 20 s、缓存刷新 44 s）；对拍还要让旧代码全量重建一遍旧缓存，再加两次顺序扫。合计 3–5 分钟。
- 手机：按桌面的 3–5 倍估，这份库 10–25 分钟。这是 1.3 百万条操作的重度库；普通库按比例小得多。
- 峰值内存：流式处理，一批不超过 32 MiB；写连接页缓存按现有预算 16–64 MiB（`native/fushi_fsrs/src/store/mem_budget.rs`）；
  单条最大的操作体是几十 KB 的字段值。目标是内核侧增量不超过 150 MB。迁移用的连接不做内存映射（现有写连接映射 256 MiB，
  `native/fushi_fsrs/src/store/mod.rs:447`；iOS 的地址空间已经吃紧过）。

## 9. 需要签字的取舍

只列改变产品行为或有数据风险的。

1. **断代的范围与触发条件。**
   - 任何一台新版本设备（包括新装的）接触一个同步位置，这个位置就换代；没升级的设备从此不能同步（提示升级），本机照常可用，升级后数据不丢。
   - 服务端与客户端**必须同版本发布**：谁先升，另一侧经它的复习同步就停；客户端先升时，旧服务端上这份 profile 的远程复习、AnkiConnect、
     互联制卡全部停到服务端升级为止；远程复习新旧互相拒绝。
   推荐：接受，发布说明与应用内提示写明；不做跨代兼容层。
2. **v1 因果数据怎么处理。**
   A 彻底丢掉，承袭修改之间只比 HLC：格式最干净；样本库上结果不变，但时钟错过的库会静默换值，现有的 v1 并发冲突（样本 166 个寄存器）不再提示。
   B 保留成承袭操作上的紧凑数据（样本库 约 7.5 MB（旧戳 5.8 MB + 写入者名字表 1.7 MB）），判定结果与现在逐位相同；代价是内核里留一段只读的旧判定。
   推荐：B。
3. **本机旧库副本与旧同步根留多久。** 副本很大（样本库 1.75–3.3 GB）。
   推荐：本机副本保留到「新代第一次同步成功之后 14 天」自动删，设置里可提前删并显示大小；从不同步的用户保留 30 天。位置上的旧根不自动删，
   提供手动清理（只删段与 head，不碰媒体）。
4. **旧代读入器保留多久**（v1 事件迁移阶梯、schema 1→29 阶梯、去重作业、协议 1 旧根读入、旧段解码、旧 `.fushisrs` / 旧备份）。
   它是冻结代码，带黄金向量，不再改。推荐：旧包 / 旧备份 / 旧段的只读读入长期保留（用户的备份可能放很多年）；
   「从很老的版本直接升到新代」的整条 schema 阶梯保留 6 个月，之后要求先经过一个中间版本。
5. **旧并入留下的重复怎么合。** 推荐：哈希能验上的（兜底 ID、改名写入者，§5.3 正向计算）自动归一，零误判；
   验不上、只是「内容相同」的不自动合，照旧由读侧按内容身份去重（BUG-4218 的现状）。备选：全都不动（另一台停在旧 uid 的设备并进来时会出现双份笔记）。
6. **ID 规则取「现有规则表去盐」，而不是 v2 设计 §3.1 写的「本地新建随机 ID + 同名牌组事后自动合并」。**
   去盐保持现在的行为（两台设备离线各建同名牌组，合并后是同一个）且存量 ID 能验算归一；§3.1 的写法要再加一套「同名事后合并」的机制。
   推荐：去盐。
7. **服务端配置与远程复习里 `profile` 的含义。** 键名与存量值不变；`srs.profiles` 仍是服务端本机的 profile uid。
   需要服务端维护者确认「同版本发布」与新能力位。
8. **迁移的体验与失败后果。**
   - 时机：推荐升级后第一次进复习前阻塞式迁移，带进度、可中断续做；空间不足或电量低时推迟并说明；重度库在手机上可能要十几分钟（估算）。
   - 对拍不过就中止：**此时新版本里复习完全不可用**，没有自动恢复；退路是装回上一个版本（旧文件没被动过）并导出诊断包。
   - 为了把这种情况挡在换代之前，推荐先发一个只带「预演」的版本（G4b）：后台只读地把迁移和对拍跑一遍，不过的库提前暴露。
     备选：不做预演，直接发。
9. **不过界的清单**（§3.5）：已清除操作的壳、MediaAt 历史、旧链与旧签名（只留指纹）。承袭段由上传它的设备签名而不是原设备——
   一台受信设备理论上可以伪造另一台旧设备的历史（受信设备都是用户自己的设备；旧根留档可对照）。推荐：接受。
10. **别的设备见到并入后是否自动跟随。** A 再问一次用户（推荐，与 BUG-4011「确认之前不并入」一致）；
    B 已确认过同步的 profile 见到受信设备签名的 `Join` 自动跟随（省一次弹框，并集不破坏数据）。

## 10. 未决

1. **并入做到一半的库。** 按 §5.5 处理后是否与「先并完再换代」逐卡相同，只有推理。另外，孤儿清扫如果恰好在旧并入第 3、4 步之间跑过，
   会把旧 uid 的行与标记当无主数据删掉（`fushi/lib/src/srs/srs_profile_cleanup.dart:93-120`），「旧 uid 的行还在」不成立。
   需要按旧并入四个步骤各断一次的测试矩阵；定不下来就退回「换代版本里保留冻结的旧并入代码先把它做完」。
2. **分叉过的旧设备。** §3.2 只定了底线（检测、报出、两支都不丢）。两支在依赖向量里怎么区分、重签发副本（HLC 是重签发时刻）与原支怎么归并，
   要对着 `transport.rs:975-1015`、`:2012-2118` 在 G2 里设计。
3. **承袭段谁都能传与 Purge 重写的交互。** 一台设备两段式重写含已清除内容的承袭段时，落后的另一台可能看到区间「缺失」而把未清除的原文重新传上去；
   读者会作废它，但内容会在位置上再留一阵。核验的推测，没有复现。
4. **历史血统卡的别名。** 验算不上的卡保持原 ID 是安全的回退，但两个集合并入后，同一张血统卡的原件与副本（卡 ID 不同、都验不上）
   上的日志只能靠读侧内容身份去重。够不够，要在 G3 用样本库量。
5. **§4.4 剩下的那个分不出的情况**（空位置 + 从没见过它的设备）是否需要额外手段（例如添加位置时声明「这是加密位置」）。
6. **别名规则对字段 / 模板 / 牌组 / 活卡的验上率**没有实测（§5.3 表里标「没跑」的四行）。这是 G3 的第一个验收项；
   验上率不够时的后果是「该合的没合」（出现重复），不是丢数据。
7. **新旧缓存是否本来就逐卡相同。** 现有缓存与「从操作全量重放」是否在样本库上逐张相同没有量过；如果旧代码自己重建都与现存缓存不同，
   对拍基准（§6.1 第 5 步）要先在旧代码里对齐。

## 12. 没查清 / 没验证的事

- 耗时与内存只有桌面上的 Python 试算和别的实测数的类推，没有 Rust 实现、没有真机数据。
- 样本只有一个库（做过旧并入、当前一个 profile）。多 profile 的库、并入到一半的库、分叉过的库都没有真实样本。
- 字段 / 模板 / 牌组 / 活卡的别名验算没有在样本库上跑过（未决 6）。
- `srs_event_local.server_time` 的全部读者没有逐个核对，本稿按「随操作保留」处理。
- 旧 head 文件的删除规则在哪一层、`.fushisrs` 的导出魔数、云盘 / 互联账号配置里是否存着 uid，没有核对。
- 整列读正文在 Rust 里到底慢多少没有量（§2.6 只有 Python 相对值，且用的是早一版试算文件）。
- 「约 58 处带盐派生调用」「去重作业的阶段」等来自核验的说法，本稿作者只抽查了其中的关键证据，没有逐条复核。
