# 复习（Fushi SRS）自动全量备份与按时间点恢复

> 状态：2026-10-17 实现（分支 `pr/srs-auto-backup`，基于 PR #2282 `pr/srs-wave2`）。
> 对标 AnkiMobile / Anki 桌面的「备份」：用来恢复数据的定期全量快照，不是查重。
> SRS 数据模型与合并语义见 [2026-10-14-fushi-srs-design.md](2026-10-14-fushi-srs-design.md)（铁律 A / B / F / H）。

## 为什么需要它

- 通用备份（设置 › 同步与备份 › 「复习」类别）只能手动、整 app 打包，复习里没有入口。
- 多设备同步会把删除也同步过去，误删 / 误操作之后没有「回到某个时间点」。

## 用户可见的行为

- 入口：复习牌组列表顶栏 ⋯ →「备份」（`srs_backups_page.dart`，MD3 / Apple 两套，列表错峰进场 + 按压缩放）。
- 自动备份（默认开）：复习库有变动后最多每 30 分钟一份；离开复习页时有变动、且距最近一份满 5 分钟就备一份
  （`kSrsBackupLeaveMinIntervalMinutes`，与设置的间隔取小：频繁进出复习页不堆一串全量备份）；启动时补一份
  （上次退出前的改动还没备份、且已满间隔）。没有变动一律不备份；没有用户笔记的 profile 不备份。
  「有没有变动」看库指纹 = 本机状态纪元 + 单调修订号（`SrsDbStore.changeFingerprint`）：任何事件真正落库（本机写、
  同步来的、导入）修订号 +1。不用 (行数, 最大 rowid)：修改记录落库先删被支配旧行再插新行，TEXT 主键表复用最大 rowid，
  同一字段连改两次两者都不变。纪元在本机状态被清空重建（覆盖恢复）时换新，修订号从 0 重数也撞不上旧指纹。
- 高频触发（每次评分都会 bump）不碰磁盘：定时器在等就直接返回，最近一份的时刻按 profile 缓存在内存里。
- 保留策略：**照搬 Anki**（rslib `collection/backup.rs` 的 `BackupFilter`，默认值见该文件测试里的「config defaults」）：
  今天和昨天的备份全部保留；更早的按日保留 12 份、按周 10 份（周一开始，`(公元日序号 - 1) / 7`）、按月 9 份，其余自动删除。
  间隔与三个份数在备份页可调（设备本地偏好 `srs_backup_auto` / `srs_backup_limits`）。
- 列表按时间从新到旧，每份显示种类（自动 / 手动 / 恢复前）、笔记数、复习数、大小（备份文件 + 它引用的媒体）。
- 点一份 → 确认 → 恢复到那个时间点；恢复前自动给当前状态存一份「恢复前」备份，恢复它就撤回了这次恢复。
- 「立即备份」；每份可另存 / 分享（桌面「另存为」，移动端系统分享面板：iOS「存储到文件」/ iCloud 云盘 / AirDrop）；
  「从文件恢复」选一份 `.fushisrs`。
- 别的 profile 的备份：
  - 本机已有那个 profile（同 uid）→ 提示切到那个配置再恢复（`profiles.uid` 唯一，不能再让当前配置采用它）；
  - 当前 profile 没有用户笔记、也从未同步发布过（新装的设备）→ 采用备份的 profile 身份（铁律 E 同一条件），
    重开 store 后换一个新的写入者化身（化身号跳到「当前秒数」量级，`afterRestore(freshIncarnation: true)`，
    不沿用这台设备以前可能在同一 profile 下用过的 `设备ID#小号`），再恢复；采用之后任何一步失败都把 uid 换回去、
    重开 store（采用与恢复要么都成、要么都不成）；
  - 否则拒绝，提示新建一个空配置在其中恢复，不把别人的数据混进有数据的 profile。

## 备份格式（`srs_backup_store.dart`）

zip，扩展名 `.fushisrs`：

| 条目 | 内容 |
|---|---|
| `manifest.json` | 魔数 `fushi-srs-backup`、`formatVersion`、`minReaderVersion`、创建时刻、种类、profile uid / 名称、计数、事件条数与 SHA-256、库指纹、媒体清单（文件名 → SHA-256 / 大小）、`mediaEmbedded` |
| `events.jsonl` | 该 profile 的全部事件（身份记录 / 修改记录 / 复习日志 / 不认识的事件），每行一条规范 JSON，与同步批次同一种编码。事件不可变，备份也不改它们 |
| `server_times.json` | 已知的「事件 ID → 发布时服务器时间 S」（铁律 F 的排序键要用） |
| `media/<sha256>` | 媒体正文，只在**导出的自包含文件**里有 |

- 版本：读方只认 `minReaderVersion ≤ 本机支持版本`（当前 1），否则拒绝「来自更新版本」；清单里多出的字段忽略（前向兼容）；
  事件里不认识的类型按 `SrsUnknownEvent` 原样保留。
- 校验：不是 zip / 没有本格式清单 → 「不是复习备份」；事件摘要或条数对不上、事件解析失败 → 「已损坏」。任何一种都不碰库。
  外部文件不可信：清单 64 MiB、服务器时间表 512 MiB、事件正文 1 GiB、单个内嵌媒体 2 GiB 为解压上限；媒体文件名拒绝
  路径分隔符、`:`、首尾空格 / 结尾的点、控制字符与 Windows 保留设备名。
- 一致性：指纹、事件、服务器时间、计数在同一个数据库事务里读（同一个快照）；事件规范行直接取库里存的规范编码拼外层
  （不解析再编码），按 rowid 键集分页（`forEachCanonicalLinePage` / `forEachServerTimePage`）流式写进隐藏暂存文件，
  内存只占一页；计数走 COUNT 查询，只解码 undo 日志拿被撤销的 ID。算摘要、裸 deflate（流式）、组 zip 在后台 isolate，
  压好的条目按块拷进 zip，不整份读入；zip 写完 flush 再改名，暂存文件一律清掉。
- 本机布局（2026-10-17 第二版，对齐 Anki「备份放在用户看得到、卸载 / 换设备能带走的地方」）：
  备份根 = **数据根的 documents 根**下 `srs_backups/`（`AppPaths.srsBackupsDirectory`）。
  - `<profileUid>/fushi-review-<YYYY-MM-DD>_<HHMMSS>-<auto|manual|before-restore>.fushisrs`（本地时间 + 种类，
    文件管理器 /「文件」App 里一眼能看懂；撞名加 `-2`），旁边隐藏的 `.<同名>.json` 是清单副本（列表不用解压）；
  - `media/<sha256>`：所有备份共享的媒体池，同一个文件只存一份，哈希按 (文件名, 大小, 修改时间) 缓存；
    清理 / 删除备份后，没有任何清单引用的媒体随之回收。
  - 清单里只存相对名（文件名 + 哈希），没有绝对路径，数据根迁移无需 rebase；`srs_backups` 登记在
    `AppPaths.fushiOwnedDocumentsEntries`，老安装扁平布局下的白名单迁移也会搬它。
  - 不进同步；通用备份按类别显式收文件，不会收这个目录。
  - 旧位置兼容：第一版放在 `<支持目录>/srs_backups`。打开备份库时若旧位置存在：新位置不存在 → 同卷改名，
    跨卷则复制到 `<新位置>.relocating`、核对文件数与字节数、改名就位后再删旧位置；新位置已存在 → 逐个搬新位置没有的文件，
    同名不覆盖、留在旧位置。任何失败都不丢文件：临时目录清掉、旧位置原样保留、记错误日志，下次打开再试
    （`srsRelocateBackupRoot`）。

  各平台最终位置：

  | 平台 | 位置 | 用户可见 / 卸载 |
  |---|---|---|
  | Windows / macOS / Linux | `<数据根>/…/srs_backups`（默认 `<文档>/Fushi/data/srs_backups`，老安装扁平布局为 `<文档>/srs_backups`；设了自定义数据根就在那里） | 文件管理器可见；备份页有「打开文件夹」「更改存储位置」（跳到现有的「数据存储位置」设置，随书库一起迁移）；卸载不删 |
  | iOS | `<App Documents>/Fushi/data/srs_backups`（老安装 `<App Documents>/srs_backups`） | 「文件」App 不可见（**不开** `UIFileSharingEnabled`，理由见下）；进 iCloud 整机备份；卸载 app 会删除（iOS 沙盒规则）。带走用每份备份的「另存为 / 分享」（系统分享面板 → 存储到文件 / iCloud 云盘 / AirDrop），恢复用「从文件恢复」（系统文件选择器） |
  | Android | `/data/data/<包名>/app_flutter/Fushi/data/srs_backups`（应用私有内部存储） | 文件管理器不可见、卸载即删。现有「数据存储位置」设置只在桌面提供，Android 没有可跳转的改位置入口；备份页明确说明，并引导用每份备份的「另存为 / 分享」另存到别处（没有另造一套存储选择） |

  iOS 刻意不开「文件」App 共享（2026-10-17 审查）：iOS 只能整份共享 Documents，打开后书（EPUB 解压正文）、有声书、视频与封面、
  字幕、词典资源、卡片来源回写草稿、未脱敏的 `error_log.txt` 等全部可见且可被用户删改，删改会让库条目指向丢失的文件。
  备份可携带的需求由导出 / 从文件恢复满足（守卫 `test/ios/info_plist_file_sharing_guard_test.dart` 钉死两个键不出现）。
- 恢复媒体：本机同名文件的内容哈希与清单一致才跳过；否则先从共享池取、哈希不符（池文件损坏）就删掉坏池文件改从文件内嵌正文取，取到后连同池文件一起修好，都取不到才记缺失；本机多出来的文件不删（媒体删除本来就不跨设备传播）。

## 恢复的语义（核心）

### 为什么不能「把库换成备份」

SRS 是事件溯源：事件只追加、按 ID 取并集，可编辑字段是带因果上下文的修改记录（被支配的丢弃）。
把本机库整个换成备份（通用备份的覆盖恢复就是这样，见设计文档【修9】「备份恢复语义」）在多设备下回不到过去：
备份之后的事件还在别的设备和同步目录里，下一轮同步按 ID 取并集就全回来了——删掉的笔记又被删、新建的笔记又出现。

### 做法：把「回到过去」写成新事件（`srs_point_in_time_restore.dart`）

一个事务里三步：

1. **并入备份事件**（与多设备同步同一套合并函数）。本机缺了备份里的数据（新装、清过数据、别的设备拷来的备份）
   在这一步补回；本机原来没有、落下来的事件重新进发件箱，会被发布出去。
2. **可编辑字段（铁律 H）**：逐个字段键比较「当前生效值」与「备份时的生效值」，不同（或当前有冲突）就写一条新修改记录，
   值取备份时的值。新记录的 ctx = 本机已应用的全部记录（含闭包），所以**支配**本机见过的一切记录，包括别的设备在备份之后
   写的、已同步到本机的那些。
   - 备份之后新建的笔记 / 牌组 / 笔记类型 → 写删除（软删除）；内置行每台设备都有，不算「之后才出现」。
   - 备份之后被删的 → `deleted` 写回备份时的空值 = 恢复。
   - 备份里没有、之后才出现的字段键 → 写「不存在」对应的值：一般是 null；笔记类型的字段 / 模板定义写软删除
     （null 会被读成一个空名字的项），内置笔记类型的项写回代码里的定义。
   - 被删笔记的卡片不逐张写（生成门已经挡住），少一批无意义的同步行。
3. **复习日志（铁律 A / B）**：日志不可变、只追加、不删。
   - 当前有效、但不在备份里的日志一律写 undo（按 sortKey 从新到旧）。备份最后一条之后的那段就是连续撤销；
     夹在备份日志之间的（备份那一刻本机还没收到的别的设备的复习）同样撤销。恢复后有效日志集合 = 备份时的有效日志集合。
     这是协议里唯一允许撤销「非最后一条有效日志」的地方：合并语义对任意 revokesId 本来就有定义（`valid_logs.dart`），
     「只许撤销末条」是交互层的限制，用来避免撤销别人基于它做的后续复习；恢复的语义正是「之后的都不算」，不冲突。
   - 备份内的日志后来被撤销了（撤销不能再被撤销：有效日志的定义只看 revokesId），卡片状态仍与备份时不同 →
     `srsPlanStateRestore` 两级补回（2026-10-17 审查改）：
     1. **重放副本**（首选）：被撤销的恰好是备份时有效历史的一段尾巴（交互层只许撤销末条，这是常态）→ 按原顺序给尾巴
        写副本，照抄种类 / 评分 / 复习类型 / 发生时刻 / 结果，只换新 ID 与新 HLC（`extra.replayOf` 记原日志 ID）。
        写完核对「有效历史与备份时逐条同构 + 状态一致」（`srsSameEffectiveShape`）。同构的历史在任何版本的规则下算出的
        卡片状态与记忆状态都相同，**不依赖 ③′，旧版本（≤ 2.10.0）不分歧**；这些复习也回到统计与训练集（副本有效、原日志仍被撤销，不重复计数）。
     2. **照抄状态的 manual 日志**（兜底）：不是尾巴（例如备份时有效的导入日志后来被判与原生日志等价）→ 写一条 manual 日志照抄备份时的状态。
   - 恢复写出的日志在 `extra.restoreOf` 记备份 ID；旧版本原样保留。

- `deleted` 字段按「删除优先」取备份时的状态（`srsEffectiveDeletedAt`），不取排序赢家：备份时并发的「删 / 未删」两条记录
  都没被支配时，行是已删的。
- 记忆状态起点（铁律 A ③′，只对兜底的 manual 日志生效）：照抄状态的 manual 日志（`extra.restoreOf`）在 `srsCollectMemoryInput` 里与导入锚点同样处理——
  以它结果里的记忆状态为起点（同算法直接用，`extra.memAlg` 记它是哪种算法算的；否则 SM-2 换算），之后的评分接着算。
  不这样做的话，被撤销的评分已不在有效历史里，下一次评分会从零重算，与备份时那张卡对不上。
  **版本兼容的剩余缺口**：不认识 ③′ 的旧版本读得出同样的卡片状态（结果在日志里），但若**这张卡的下一次评分发生在旧版本设备上**，
  旧版本会从剩下的有效评分重算 S/D，与新版本不同；结果写进日志后各端读到的又是同一个状态（分歧只在「哪台设备算这一次」）。
  范围只限兜底分支的卡（罕见）。SRS 协议没有能力位 / 最低读者版本门（日志 `fv` 只作原样保留，旧版本不会拒收高版本日志），
  所以在协议层彻底消除需要先引入版本门，超出本 PR。
- 复习日志只处理**受影响的卡**：有不在备份里的日志的卡（加上经「前身」链接继承了它们历史的卡）；其余卡的日志与备份时
  完全相同，状态必然一致，不逐卡读历史。
- 失败：整个恢复一个事务；事务回滚不回滚内存里已前进的写入者因果上下文 / 时钟 / 发件箱序号，所以失败后从库重读本机状态
  （`SrsDbStore.reloadLocal`），否则 applied 里留着回滚掉的 dot，之后真正同步来的同一批记录会被误判为已看见而支配丢弃。

恢复不换写入者化身（本机状态保留），与覆盖恢复不同。同一份备份再恢复一次：字段全是 no-op，日志没有可撤销的，不再写事件。

### 逐条回答

| 情形 | 本机 | 其它设备 |
|---|---|---|
| 备份之后新建的笔记（本机或别的设备建、恢复时本机已收到） | 写删除，消失 | 收到删除记录（支配它们见过的记录）→ 消失 |
| 备份之后被删的笔记 | `deleted` 写回空值，恢复 | 收到这条记录，它支配那条删除 → 恢复；若另一台设备在恢复之后（或与恢复并发）又删了，按「删除优先」仍是已删 |
| 备份之后改过的字段 / 标志 / 设置 | 写回备份时的值 | 同上，旧值被支配，回不来 |
| 备份之后的复习（恢复时本机已收到） | undo，卡片回到备份时的状态，统计与优化器训练集排除这些复习 | undo 随同步传过去，同样排除；日志本身留在表里 |
| 恢复那一刻本机**还没收到**的别的设备的复习 | 与恢复并发：照常有效，同步过来后若排在最后就成为卡片状态 | 同左 |
| 恢复那一刻本机还没收到的别的设备的字段修改 | 与恢复写的记录并发：内容类进「待裁决」，标志 / 设置类最后修改生效并进同步冲突记录（铁律 H） | 同左 |
| 之后又有旧数据回来（退役设备、旧快照、合并旧的通用备份） | **恢复那一刻本机已见过的**记录全部被恢复写的记录支配，状态不变；本机当时没见过的记录（例如一台一直离线、从没同步过的设备上的改动）与恢复并发，按上一行处理 | 同左 |
| 撤回恢复（恢复「恢复前」那份） | 笔记、字段、卡片状态全部回来；被第一次恢复撤销的复习不能「撤销撤销」，改为重放副本补回：卡片状态、记忆状态与统计都回到恢复前 | 同左 |
