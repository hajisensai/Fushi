> 状态：**已拍板**（2026-07-12 用户挨个决策：①混排+撤独立分区+开关默认开
> ②离线=**只剩本地**（先选快照缓存，同日用户改回只剩本地）③云视频也可下载
> ④手动序整合集 LWW）。本稿为一次交付的完整范围，无分期。
> 源头：用户群聊——书架跨客户端显示一致；缺的书占位可下载；没网保持现状；
> 客户端专有书照常；「参照 git 那样搞？我想让他远端书籍/视频混合进正常里面」。

## 0. Linus 三问

1. **真问题吗？** 真。远端书/视频现在挤在独立分区，和本地库割裂；合集与
   手动序完全不跨端。用户要的是「一个库 = 本地 ∪ 远端」。
2. **「书架摆放位置同步」是伪需求。** 排序重设计后，显示顺序 =
   f(排序模式, 条目元数据)。要同步的是**目录、合集、手动序（sortIndex）**
   这三样数据，不是「位置」。
3. **「参照 git」对一半。** 对的：本地永远可用、离线照改、联网合并——现有
   同步已是这个模型（newer-wins + 墓碑 + bookKey 跨端身份）。错的：全历史/
   分支/三方合并不引入；排列（手动序）上的逐项合并是灾难，整表 LWW。

## 2. 完整方案

### 2.1 联合目录视图：远端条目混排主网格

- remote-only 条目（远端有、本地无）渲染成**主网格占位卡**：正常卡尺寸 +
  远端封面（RemoteCoverImage 已有）+ 云角标 ☁；两端都有的条目只显示本地卡。
- 排序键：占位卡用远端进度时间戳（`positionUpdatedAtMs`）/远端目录序退化，
  参与当前排序模式；散卡与合集行的既有布局规则不变。
- 独立远端分区去留、「显示远端条目」开关 → 决策点 ①。

### 2.2 内容获取

- **书占位卡**：点击 → 走现有下载链（进度徽章原样），完成后原地变正常卡。
- **视频占位卡（已拍板：云视频也可下载；2026-07-12 用户追拍：真·云视频）**：
  互联在线 → 直接远端流播（现有能力接进主网格卡）+ 可选下载入库；云后端
  视频 → 点击下载整文件入库（进度徽章同书），下载完成原地变正常卡。
  **云端视频来源 = 新「上传视频文件」开关**（见 §2.6）——用户原话「开启了
  上传视频就要有」：开关开启的设备把本地视频资产上传云端，云目录才有视频。

### 2.6 云视频资产同步（用户追拍新增）

现状云同步从不上传视频（目录里没有视频可列）。新增：
- `SyncRepository` 开关 `sync_video_files`（**默认关**——视频体积/流量大，
  显式 opt-in），同步设置页加行（沿 `syncAudioBookFiles` 同款 gate 范式）。
- 开启后 SyncOrchestrator 上传阶段把本地视频文件推到云 `__videos__/`
  命名空间（按 bookUid 键控，已存在跳过，upload-only——远端不删本地、
  删除不传播，与书内容同律），并维护 `__videos__/videos.json` 目录清单
  （uid/title/封面缩略/大小/importedAt），供其它端渲染云视频占位卡与下载。
- 下载：云视频占位卡 → 拉文件落本地视频目录 → 走既有视频导入链入库。

### 2.3 合集联合（唯一含 schema/接口改动的部分）

1. **目录归属**：host API / 云目录清单携带每条目的合集归属（合集名 + 类型 +
   该条目的 sortIndex），远端占位卡归进对应合集行（合集行内成员占位卡）。
2. **合集双向同步**（自动/手动同步管线新增阶段，云后端走 sync 根下
   `__collections__` JSON 清单，互联走 host API）：
   - 合集按 (name, collection_type) 自然键对齐（复用备份合并的成熟语义）；
   - 成员**并集 + 成员移出墓碑**（新表 `collection_member_tombstones`，
     复合键 collection自然键+media_type+entry_key+removed_at；无墓碑则 A 端
     移出的成员被 B 端并集复活——与书删除墓碑同一律）；重新加入清墓碑。
   - 合集删除：合集级墓碑（同一张表，entry_key 空哨兵或独立列），防复活。
3. **手动序跨端**：`MediaCollections` 加列 `order_updated_at`（schema v40，
   `reorderCollectionItems` 落盘时 bump）；同步比时间戳，**新者整表覆盖**
   （成员 sortIndex 全表跟随）。不做逐成员位置合并——两个排列不存在有意义
   的「合并」。A 端拖完序，B 端同步后详情页/合集行/播放器换集三处跨端同序。
   是否同步手动序 → 决策点 ④。

### 2.4 离线语义（已拍板：只剩本地）

离线/未配对/后端不可达时远端占位卡**不出现**，只剩本地库（零新状态、零缓存
表）；重新联网拉取成功后占位卡自动回来。不做「离线可见但不可点」的灰占位
——点了也下载不了，假可用性。

### 2.5 客户端专有内容

本地有、远端无 → 照常显示（同步是并集，不删本地）；是否上传由既有
`syncContent` 等开关决定，不改语义。

## 3. 不做的事

- git 式历史/分支/逐项三方合并（LWW + 墓碑覆盖全部需求）。
- 「摆放位置」同步（不存在该状态）；排序模式偏好保持每端本地。
- 库级手动摆位复活（已拍板砍掉，手动序只活在合集详情页）。

## 3.5 已知限制（LWW + 自然键身份的固有代价）

以下是当前设计（无 vector clock、合集身份=自然键、成员无 per-成员 addedAt 列）的已知窗口，
不是 bug，是「简单 LWW + 墓碑」换来的可接受折衷；列出以免日后误当回归重查：

1. **改名 = 删旧建新，会吞掉对端在旧名下、基线之后的并发新增成员。**
   合集改名走「旧自然键写删除墓碑 + 新自然键建活合集带原成员」。若 A 改名 `S→S2` 的同时
   B 在旧名 `S` 下新增成员 m（尚未同步），A 的旧名删除墓碑会把整条旧名连同 m 一起删掉——
   B 那次对 `S` 的新增被吞。窗口 = 「A 改名发布」到「B 同步看到改名」之间 B 对旧名的写。
   - 影响面：仅改名与并发新增撞车时，且只丢那次并发新增（不丢已收敛成员）。
   - **follow-up**（未排期）：给改名加 `renamedTo` 指针列（旧名墓碑携带新名），同步时把旧名
     下基线后的新增成员**转发**到新名，而非直接吞掉。需 schema 加列 + 引擎转发逻辑，本轮不做。

2. **成员活/死用文件级 `lastWrittenAt`（非 per-成员 addedAt），并发跨成员移出可能误判重加。**
   折叠对端清单时（`combinePeers`），一个活成员是否算「看过墓碑后的有意重加」用其**所在文件**
   的 `lastWrittenAt` 对比墓碑 publishedAt。文件级时戳比 per-成员 addedAt 粗：设 A、B 已收敛
   `{x,y}`，A 移出 x 的同时 B 移出 y（都未互相同步），A 回写的文件把**未改动的** x 仍列为活、
   盖上 A 本轮 `lastWrittenAt`；该时戳晚于 B 的 x 移出墓碑 publishedAt 时，折叠会判 x 是「重加」
   而复活 x。
   - 影响面：仅两端**并发移出不同成员**且各自回写抬高了对方待移出成员的活文件时戳时；这是
     LWW 在缺 per-成员因果戳下的固有取舍，远优于旧实现「每次二轮同步都复活自己刚移出的成员」。
   - **follow-up**（未排期）：加 per-成员 `addedAt` 列，用成员级因果戳替代文件级 `lastWrittenAt`
     裁决，可消除此窗口。需 schema 加列 + 清单/引擎载荷扩展，本轮不做。
