# 蓝光原盘交互菜单

原盘菜单由盘内 HDMV / BD-J 程序决定背景、按钮、章节、字幕和跳转。
Fushi 的标题列表仍用于直接播放；进入原盘菜单时，由 libbluray 执行导航，
mpv 在原视频纹理内合成菜单图层，Flutter 只提供进入、返回和输入转发。

## 原盘会话与标题身份

打开菜单不是打开合集第一条电影。菜单会话以盘根定位，从原盘导航入口启动；
未确定正片时不加载代表书的字幕、不保存其进度、不累计学习时间。
菜单选中标题后，由原生读取到的 MPLS 编号定位真实播放列表，再绑定库中条目。
短花絮可能被扫描筛选规则过滤，仍允许在用户实际播放时按完整 MPLS 路径入库。
不同盘的同名 `00001.mpls` 不共享书目、进度或字幕。

原生与 Dart 使用版本化 `disc-navigation-state` 快照，关联导航是否启用、
菜单交互、菜单域、真实标题、MPLS、切换代数、呈现位置与稳定状态。
不得把 mpv edition 下标当作 MPLS；不得从画面消失猜正片已开始。
库查询、字幕加载和制卡任务必须捕获当前标题代数，迟到结果不能写入新标题。
纯 BD-J 顶层菜单可以只绘制 Java／IG 图层、不启动播放列表；此时没有正片时间轴。
已显示的交互顶层菜单可以接收输入，但不得绑定书目、累计学习或提取媒体。
有播放列表的菜单继续等待呈现稳定，未就绪时不绕过盘上 Top 调用权限。

PGS 字幕和原盘菜单是两个图层。字幕出现不应抢方向键；菜单可交互时才把
方向、确认、返回和视频内容区域内的鼠标位置交给原盘。Flutter 弹窗与设置
面板仍优先接受输入。菜单关闭后恢复普通播放器操作。
菜单替换常规 media_kit 控制条时，需要显式承载同一个视频焦点节点；Video
本身只保存焦点参数，不是焦点宿主。窗口与全屏仍通过既有焦点门保证单一挂载。

## 播放、提取与时间轴

原盘会话继续使用既有 media_kit Player 和 Flutter texture。
用户显式打开的单个 `bd://` / `bluray://` Media 经播放器的 `loadfile` 路径，
不能再包装成临时播放列表：mpv 将蓝光流标记为不允许从列表间接打开，普通
`loadlist` 会在真正读盘之前拒绝它。补丁保留 media_kit 的状态和 hook 接线，
普通 Playlist 与外部播放列表仍走原来的安全规则，不全局放开不安全协议。
菜单进入正片后，进度和字幕使用呈现时间，不能使用 libbluray 已预读到的位置。
制卡与字幕提取仍基于当前 MPLS 的片段顺序和 IN/OUT，复用
`BlurayFfmpegBackend`，不可直接截取第一个 M2TS 代替整条标题。

可播放与可提取分别判断。读取后端可能向播放器提供明文，但磁盘上的原始
M2TS 仍为密文；此时可靠标题仍能保存进度，FFmpeg 提取不能直接使用密文路径。
原盘读取失败应明确报错，不能悄悄降成最长片并声称已进入菜单。

盘模式默认由原盘控制音轨和主字幕，标题绑定不自动恢复数据库中的外挂或
关闭设置。用户在 Fushi 显式选轨时可以接管；进入真正的交互菜单时恢复
`aid/sid=auto` 并清除活动外挂，持久化来源仍作为候选保留。原生同步除了比较
盘选择值，还比较实际当前轨道，避免“手动覆盖后恢复 auto，盘值没变便不生效”。
`media_kit.state.track` 的 `auto` 是请求模式，实际 AID/SID 与 codec 从
`current-tracks` 读取；异步读取前后复核原盘代次与标题。制卡使用实际音轨的
序号映射，未知选择不能当作第一轨，以免界面、播放和导出各用不同音轨。

## 原生依赖

原 Windows pin `mpv v0.41.0-923-g7b8915bc1` 能读蓝光标题，但没有菜单命令。
菜单后端需要支持导航命令、菜单渲染和上述快照契约；仅探到 `bd://` 不算支持。
`index.bdmv` 解析提供 first-play、top-menu 和 BD-J 需求，主索引损坏时尝试
BACKUP 索引，元数据大小与各段边界必须校验。

HDMV 与 BD-J 分别验收。BD-J 还需要匹配的 libbluray Java 组件和可用 JVM；
缺失时必须报告，不得自动切入正片。每个平台的实际制品都要做能力探测，
共享 Dart 代码通过不等于该平台的原生制品支持菜单。

AACS / BD+ 读取与菜单导航相互独立。项目不得把个人激活状态、密钥或商业盘
内容放进源码或测试制品。用户用于验证的原始备份不修改，测试副本单独存放。

Windows 的可选 BD-J Java 组件按随包清单固定版本与 SHA256，由应用网络入口
下载以遵守代理设置；安装器只接收已验证的本地归档。组件不修改系统 Java。
每次安装使用独立 staging；PowerShell 在宿主发出启动信号前不启动 Java。
宿主先把它加入私有 Windows Job，取消时终止整个进程树并等到 ActiveProcesses
为零，再清理本次 staging，防止子 JVM 遗留文件锁。原有 Mihon helper 复用同一个
公共进程容器，保留旧 factory 与同步 close 契约。

## AACS 加密盘（2026-10-09，BUG-3074）

菜单会话里 libbluray 自己读盘，必须能加载 libaacs。Fushi 随包自写的
`native/fushi_aacs`（libaacs ABI 子集）：打开前 app 用 KEYDB 按盘 ID 精确取 VUK
并注册给模块，与标题直放同一密钥策略与解密算法；无钥且码流加密时在打开前
就报 KEYDB 提示，明文副本按无钥注册。首个导航快照之前的 `bd` / `stream`
原生错误一律判打开失败并记录 libbluray 原文。有钥的加密标题允许制卡。
总线加密、AACS 2、BD+ 不支持；Linux 依赖系统 libaacs。

## 验证边界

- 索引解析：HDMV、混合 BD-J、无菜单、截断、越界、主索引损坏与备份回退。
- 导航状态：菜单与字幕区分、真实 MPLS 身份、切换代数、旧任务迟到结果。
- 原生：导航命令、快照 ABI、图层合成、TrueHD 与既有渲染兼容。
- 应用：进入菜单、方向与鼠标选择、进入正片/花絮、弹出/返回菜单、进度恢复。
- 媒体：所选音字幕轨、PGS 显示、当前标题片段提取和最终制卡内容同轴。
- 缺少运行库、Java、读取条件或测试盘时分别报告，跳过不计入通过。

### 2026-10-08 实测结果

- Windows 与 Android 都使用 Disc 2 的真实 HDMV 菜单完成应用集成测试：进入菜单、
  日语字幕 ON、正片播放、Fushi 关闭字幕并写入 `off:`、返回原盘菜单、键盘确认
  同一标题复播、恢复 PGS、进度隔离与退出。Windows 108 秒、Android 149 秒，
  各 1 个完整业务场景通过，退出码均为 0。前后 36.2 秒截图均核对到真实日语 PGS。
- Windows 使用完整可读测试副本；Android API 34 x86_64 使用完整菜单与正片前缀，
  不能据此宣称 Android 整片跳转或结尾已验收。两端测试均使用隔离数据与测试包。
- Windows 原生另验菜单／电影往返、PG／IG 分离、用户选轨后交还原盘、真实 TrueHD
  解码及旧 OpenSSL／libplacebo／pthread／Vulkan 已加载时的私有 DLL 共存。
- Android 四 ABI 原生构建通过，验证 8 个 ELF 的哈希、架构、16 KB 对齐与依赖闭包。
  macOS／iOS 构建通过，验证 100 个 Mach-O slice；Mac arm64 实际加载探测到导航、
  TrueHD 和渲染 API。Apple 设备菜单画面与 Dolby Vision 画面对比尚未实测。
- Windows 私有 BD-J 组件经过安装、取消／进程树回收与 JNI／AWT 探测；本张测试盘
  是 HDMV，不能据此宣称商业 BD-J 盘完整验收。Android／Apple 包不捆绑 JVM／JAR，
  Linux 仍取决于系统 libmpv 的实际能力。
- 全屏、触摸／手柄、Android SAF 导入及最终 Anki 卡片写入不在本次已完成的实测范围。
  本次没有把商业盘内容、字幕、个人密钥或激活状态加入仓库。
