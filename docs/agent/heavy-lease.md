# 本机重活租约（tool/heavy.dart）

> 2026-10-14 从根 `CLAUDE.md`「验证」原样迁出；CLAUDE.md 只留一行规则。

- **本机重活一律走租约（2026-10-01 起，用户拍板「测试不能影响我正常用电脑、也不能互相冲突」）**：本地 `flutter test` / `flutter analyze` / `flutter build` / `gradlew` / `run_windows_itest.ps1` 一律在 `fushi/` 下写成 `dart tool/heavy.dart -- <原命令>`（**用 `dart` 直接跑、不加 `run`**：`dart run` 会先跑整个 workspace 的 build hooks 去 GitHub 下 pdfium）；`pre_push_check.dart` 与 `flutter_test_failures.dart` 已内置同一租约，不用再包。租约 = 机器级 OS 文件锁槽位（默认每 20 GB 内存 1 个，64 GB 机器 3 个；进程一死锁就释放，没有陈旧占用；**不看实时可用内存**——2026-10-03 用户拍板删除：忙碌的桌面上「可用内存高于预留」常年不成立，一个 agent 守着空槽排队几十分钟、后面的 agent 全被挡住）+ **按内存上限记账**（2026-10-19 用户拍板：3 个槽位 × 12–16 GB 上限最多许出 48 GB，64 GB 桌面上再加十几个 agent 会话把提交内存吃光、一批进程一起崩）：持槽者登记的上限（test 12 GB / analyze 记 4.5 GB（上限 8 GB，见下）/ build·其它 16 GB / `--cap-mb=N` 覆盖值）之和加上新任务的不得超过预算，默认 = 内存取整到 GB 的一半（64 GB → 32 GB：两条 test + 一条 analyze，或 build + test，绝不三条 test 并跑），`FUSHI_HEAVY_BUDGET_MB` 可覆盖；机器空闲时单条任务总能放行；旧版本工具没登记上限的持有者按 16 GB 记（旧版本工具自己不做这道记账，只有带本规则的 checkout 才受预算约束）；记账枚举状态目录里实际存在的全部 `slot-*.lock`，别的会话用更大 `FUSHI_HEAVY_SLOTS` 占的高号槽位同样计入（但不算本进程可拿的槽）；`heavy.dart` 包住自带租约的仓库工具（`dart [run] tool/pre_push_check.dart` 按 test 12 GB、`--parallel` 再加 analyze 8 GB；`tool/flutter_test_failures.dart` 按 test）时按该工具自己的上限记账并封顶——内层见到外层租约不再取票、自己的 Job 嵌在外层 Job 里受外层上限约束，所以既不双计也不少计 + 同一 worktree 写 `build/` 的运行互斥（根治互抢 `sqlite3.dll` / 结果文件）+ Windows Job Object（整棵进程树**低于正常优先级**、内存封顶、包装器一退出残留的 `flutter_tester` / gradle daemon 全部被杀）。等待者按先来后到排队（`<状态目录>/queue/` 下持锁的票，只有队首能拿空槽，等待者死了票自动失效），**默认一直排到放行、不会因为等太久而放弃**（用户 2026-10-03 拍板「应该丢进队列，而不是直接停掉放弃」）；显式 `--wait-max-min=N`（`flutter_test_failures` 同名、`pre_push_check` 是 `--gate-timeout-min=N`）才设上限，超时退出码 75、**绝不照跑**；`--status` 同时列出槽位占用（含每条的记账上限与预算合计）与排队顺序；`--max-minutes`（默认 120）超时杀树退出码 124；末尾一行报峰值内存，撞上限会明说「MEMORY CAP HIT」——那种红先当资源问题收窄范围再判，不是代码红。`dart tool/heavy.dart --status` 看谁占着槽位和当前内存（只显示，不参与放行）。CI（`CI=true`）与 `FUSHI_HEAVY=off` 不取租约；嵌套（如被包住的 `pre_push_check`）经 `FUSHI_HEAVY_LEASE` 自动不重复排队。实现 `fushi/tool/test_flow/heavy_{budget,lease}.dart`，测试 `fushi/test/tools/heavy_{budget,lease}_test.dart`。
- **analyze 是轻量任务（2026-10-25，用户反馈「不怎么吃 cpu 但会开很多个 dart 运行时浪费内存、占住任务槽拖慢测试」）**：analyze **不占测试槽位、不排队**，拿的是另外 2 个「轻量槽」（`slot-100.lock` / `slot-101.lock`，最多 2 条 analyze 同跑），只需放得进内存预算；记账 **4.5 GB**（本机 1004 次实测峰值 p50 3.4 / p90 4.0 / max 7.8 GB，零次撞上限；analysis server 平均不到 1 核），Job 内存上限仍是 8 GB。以前它占一个完整槽位并按 8 GB 记账，测试在它后面累计排了 11 小时。test / build 的记账与「绝不三条 test 并跑」不变。旧版本工具不认轻量槽、但会把 `slot-1xx.lock` 照常计入预算。
- **SDK 版本不对直接拒跑（2026-10-25）**：`heavy.dart` 把裸 `flutter` / `dart` 按仓库工具同一顺序解析（`FUSHI_FLUTTER` → `FLUTTER_ROOT` → 跑 heavy.dart 的那个 SDK → `PATH`），读该 SDK 的 `bin/cache/flutter.version.json` 与 `fushi/.fvmrc` 比对，不一致**排队前**退出码 2。以前 PATH 上的 3.44 照样排队拿槽、编译 155 秒后整批 suite 装载失败，还把 `.dart_tool/hooks_runner` 写成旧格式，连累下一次用对的 SDK 也报 `Invalid kernel binary format version`。实现 `fushi/tool/test_flow/heavy_sdk_check.dart`，测试 `fushi/test/tools/heavy_sdk_check_test.dart`。
