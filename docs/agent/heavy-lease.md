# 本机重活租约（tool/heavy.dart）

> 2026-10-14 从根 `CLAUDE.md`「验证」原样迁出；CLAUDE.md 只留一行规则。

- **本机重活一律走租约（2026-10-01 起，用户拍板「测试不能影响我正常用电脑、也不能互相冲突」）**：本地 `flutter test` / `flutter analyze` / `flutter build` / `gradlew` / `run_windows_itest.ps1` 一律在 `fushi/` 下写成 `dart tool/heavy.dart -- <原命令>`（**用 `dart` 直接跑、不加 `run`**：`dart run` 会先跑整个 workspace 的 build hooks 去 GitHub 下 pdfium）；`pre_push_check.dart` 与 `flutter_test_failures.dart` 已内置同一租约，不用再包。租约 = 机器级 OS 文件锁槽位（默认每 20 GB 内存 1 个，64 GB 机器 3 个；进程一死锁就释放，没有陈旧占用；**不看实时可用内存**——2026-10-03 用户拍板删除：忙碌的桌面上「可用内存高于预留」常年不成立，一个 agent 守着空槽排队几十分钟、后面的 agent 全被挡住）+ **按内存上限记账**（2026-10-19 用户拍板：3 个槽位 × 12–16 GB 上限最多许出 48 GB，64 GB 桌面上再加十几个 agent 会话把提交内存吃光、一批进程一起崩）：持槽者登记的上限（test 12 GB / analyze 记 4.5 GB（上限 8 GB，见下）/ build·其它 16 GB / `--cap-mb=N` 覆盖值）之和加上新任务的不得超过预算，默认 = 内存取整到 GB 的一半（64 GB → 32 GB：两条 test + 一条 analyze，或 build + test，绝不三条 test 并跑），`FUSHI_HEAVY_BUDGET_MB` 可覆盖；机器空闲时单条任务总能放行；旧版本工具没登记上限的持有者按 16 GB 记（旧版本工具自己不做这道记账，只有带本规则的 checkout 才受预算约束）；记账枚举状态目录里实际存在的全部 `slot-*.lock`，别的会话用更大 `FUSHI_HEAVY_SLOTS` 占的高号槽位同样计入（但不算本进程可拿的槽）；`heavy.dart` 包住自带租约的仓库工具（`dart [run] tool/pre_push_check.dart` 按 test 12 GB、`--parallel` 再加 analyze 8 GB；`tool/flutter_test_failures.dart` 按 test）时按该工具自己的上限记账并封顶——内层见到外层租约不再取票、自己的 Job 嵌在外层 Job 里受外层上限约束，所以既不双计也不少计 + 同一 worktree 写 `build/` 的运行互斥（根治互抢 `sqlite3.dll` / 结果文件）+ Windows Job Object（整棵进程树**低于正常优先级**、内存封顶、包装器一退出残留的 `flutter_tester` / gradle daemon 全部被杀）。等待者按先来后到排队（`<状态目录>/queue/` 下持锁的票，只有队首能拿空槽，等待者死了票自动失效），**默认一直排到放行、不会因为等太久而放弃**（用户 2026-10-03 拍板「应该丢进队列，而不是直接停掉放弃」）；显式 `--wait-max-min=N`（`flutter_test_failures` 同名、`pre_push_check` 是 `--gate-timeout-min=N`）才设上限，超时退出码 75、**绝不照跑**；`--status` 同时列出槽位占用（含每条的记账上限与预算合计）与排队顺序；`--max-minutes`（默认 120）超时杀树退出码 124；末尾一行报峰值内存，撞上限会明说「MEMORY CAP HIT」——那种红先当资源问题收窄范围再判，不是代码红。`dart tool/heavy.dart --status` 看谁占着槽位和当前内存（只显示，不参与放行）。CI（`CI=true`）与 `FUSHI_HEAVY=off` 不取租约；嵌套（如被包住的 `pre_push_check`）经 `FUSHI_HEAVY_LEASE` 自动不重复排队。实现 `fushi/tool/test_flow/heavy_{budget,lease}.dart`，测试 `fushi/test/tools/heavy_{budget,lease}_test.dart`。
- **analyze 是轻量任务（2026-10-25，用户反馈「不怎么吃 cpu 但会开很多个 dart 运行时浪费内存、占住任务槽拖慢测试」）**：analyze **不占测试槽位、不排队**，拿的是另外 2 个「轻量槽」（`slot-100.lock` / `slot-101.lock`，最多 2 条 analyze 同跑），只需放得进内存预算；记账 **4.5 GB**（本机 1004 次实测峰值 p50 3.4 / p90 4.0 / max 7.8 GB，零次撞上限；analysis server 平均不到 1 核），Job 内存上限仍是 8 GB。以前它占一个完整槽位并按 8 GB 记账，测试在它后面累计排了 11 小时。test / build 的记账与「绝不三条 test 并跑」不变。旧版本工具不认轻量槽、但会把 `slot-1xx.lock` 照常计入预算。
- **SDK 版本不对直接拒跑（2026-10-25）**：`heavy.dart` 把裸 `flutter` / `dart` 按仓库工具同一顺序解析（`FUSHI_FLUTTER` → `FLUTTER_ROOT` → 跑 heavy.dart 的那个 SDK → `PATH`），读该 SDK 的 `bin/cache/flutter.version.json` 与 `fushi/.fvmrc` 比对，不一致**排队前**退出码 2。以前 PATH 上的 3.44 照样排队拿槽、编译 155 秒后整批 suite 装载失败，还把 `.dart_tool/hooks_runner` 写成旧格式，连累下一次用对的 SDK 也报 `Invalid kernel binary format version`。实现 `fushi/tool/test_flow/heavy_sdk_check.dart`，测试 `fushi/test/tools/heavy_sdk_check_test.dart`。
- **能外包的重活先自动外包给别的机器（2026-10-30，用户「我电脑上好卡，但是其他电脑上很闲」）**：`heavy.dart` 排本机槽位**之前**，先看命令能不能交给 dist_test 的其它 worker（判定是纯函数 `fushi/tool/test_flow/heavy_offload.dart`，测试 `fushi/test/tools/heavy_offload_test.dart`）：
  - **外包**：
    - `fushi/` 下的 `flutter test`（只含 `test/` 下的文件 / 目录，或不带路径 = 整个 `test/`）→ `dist_test.dart --offload`：其它机器先跑，它们跑不了的 suite（平台 / 能力钉死、机器中途掉线）才由本机 `local` worker 在租约下补跑。
    - `packages/<name>/` 下的 `flutter test` / `dart test`（2026-10-30 第二轮）→ `dist_test.dart --offload --package=packages/<name>`：纯 Dart 包在 worker 上用 `dart test` 跑（与 CI 一致，按 pubspec 有没有 `sdk: flutter` 判断），其余同上。
    - `--coverage`（只限 `flutter test`）：每批在 worker 上写 lcov，随事件流以 `{"type":"fushiCoverage",...}` 一行带回，本机校验（只收该包 `lib/` 下的记录）后合并，写到 `--coverage-path` 或默认的 `<包>/coverage/lcov.info`，末尾打 `DIST COVERAGE: <路径>`。**coverage 每个测试进程有约 10 分钟固定开销**（flutter tool 合并整个 app 的覆盖报告，测试本身再小也一样），所以外包时每台机器只领一批、`--concurrency=1`、超时按这笔开销放宽；一次 coverage 至少十几分钟是正常的，不是挂住。`dart test --coverage=<目录>`（VM json）与 `--merge-coverage` 仍在本机。
    - `flutter analyze`（整个 app 或 `lib/ test/ tool/ integration_test/ test_driver/ bin/` 下路径，只透传 `--[no-]fatal-infos|warnings`）→ `dist_test.dart --analyze`：按 config 顺序找第一台能 prepare 且接活的机器跑完，输出回本机终端。
    - **编译检查要显式写 `--check-only`**：`dart tool/heavy.dart --check-only -- flutter build apk|appbundle|windows|macos ...`（在 `fushi/`）或 `dart ../tool/heavy.dart --check-only -- .\gradlew.bat :app:assembleRelease`（在 `fushi/android/`）→ `dist_test.dart --build`：只回传构建日志和退出码，**产物留在那台机器上**，所以只用于「还能不能编过」（CLAUDE.md 要求的 Android 资源 / manifest / Gradle 改动后的 `assembleRelease` 就是这种）；要拿 APK 装真机、要跑出来的 exe，就不加 `--check-only`，照旧本机构建。能外包的参数是白名单（`--debug|--profile|--release`、`--split-per-abi`、`--target-platform=android-*`、`--[no-]tree-shake-icons`；gradle 只认 `:app:assemble*` / `:app:bundle*` 与 `-Ptarget-platform=`）；带 `--dart-define`、`-t`、`--obfuscate` 等会把值带出去或影响产物的参数，以及 iOS / ipa、非 `--debug` 的 macOS（要签名）都留在本机。Android release 构建在 worker 上用一次性生成的签名 key（真 key 永不离开本机），所需的 Rust `.so` 按 ABI 在 worker 上编并缓存。**远端编译红了，heavy 会在本机再编一次确认**（对方机器的 SDK / NDK / VS 可能和本机不同），本机的结果才算数。
    - 外包用的是工作区快照（HEAD + 未提交改动，密钥按 HEAD），和 dist_test 一样。
  - **不外包、照旧本机**：不带 `--check-only` 的 `flutter build` / `gradlew`、`run_windows_itest.ps1` / 集成测试、`dart analyze`，以及带 `--update-goldens`、`--merge-coverage`、`--file-reporter`、分片参数、含空格或特殊字符的名字过滤等只能在本机落地或 shim 传不过去的参数。golden 基线钉平台（只有本机标了 `golden`），集成测试要占对方的屏幕，所以不外包。
  - **回退**：没配 worker（`FUSHI_DIST_CONFIG` 环境变量，否则 `fushi/tool/dist_test/workers.local.json`）、远端全都不可达 / 忙（每台只再问 2 次、30 秒一次）/ 暂停 / 平台不符 / 没有对应工具链时，dist_test 以退出码 75 表示「没人接」，`heavy.dart` 打一行 `dist_test did not run it elsewhere ...; running it here` 后按原样在本机排队跑（输出格式也是原样）。**基础设施类失败同样走回退、不判红（2026-10-31）**：worker 配置缺失 / 无效 / 不是 JSON、工作区快照建不出来、dist_test 自身拒收参数或内部异常，外包模式下一律退 75 并打一行 `DIST OFFLOAD: declined: <原因>`（以前分别退 64 / 1，`workers.local.json` 写错就让所有外包的 test / analyze 零执行判红）；只有测试真失败 / analyze 真报问题才是红。外包前 `heavy.dart` 已经加入自己的 Job Object（低于正常优先级、内存封顶、退出时杀残留进程树），dist_test、它的本机兜底 worker 以及回退后的本机运行都在同一个 Job 里。CI、`FUSHI_HEAVY=off`、嵌套租约内不外包。`--here` 或 `FUSHI_HEAVY_OFFLOAD=off` 强制本机。
  - **按名字 / tag 过滤（`--name` / `--plain-name` / `--tags` / `--exclude-tags`）**：外包时某一批的文件一个都没匹配上（`flutter test` 退 79「no tests ran」、`done: success`、无错误）不算这批红，只要求**整次运行**至少执行 1 条测试（与本机一次 `flutter test` 跑多个文件的口径一致）；不带过滤时零执行照旧判红。
  - **显式 `-j N` / `--concurrency=N`**：作为 dist_test `--concurrency=N` 带过去，给每台 worker 的并发封顶（取 worker 配置与 N 的较小值）；heavy 自己补的默认 `--concurrency=4` 只管本机，不外传。
  - **中断与超时**：`--max-minutes` 由 dist_test 自己执行（`heavy.dart` 把它作为 `--max-minutes=N` 传过去），到点先 abandon 各 worker 的 prepare、杀掉远端正在跑的批次 / analyze / 构建（worker_kill.sh / shim `kill`）、释放 checkout 锁与租约，再退 124；Ctrl-C 同样处理后退 130（`heavy.dart` 收到 Ctrl-C 会等 dist_test 收尾而不是先死）。`heavy.dart` 只在超出上限 5 分钟仍没退时强杀作兜底。124 / 130 都不会回退到本机再跑。
  - **编译检查的口径**：远端红 → 本机再编一次，以本机结果为准；远端绿直接采信——worker 在 prepare 时按 `fushi/.fvmrc` 核对 Flutter 版本、Android 构建按 `build.gradle` 的 `ndkVersion` 找同版本 NDK，快照与本机同一份源码，绿了只剩 VS / Xcode 小版本这类差异，不值得在本机再编一遍（那就失去了外包的意义）；最终仍以 PR CI 为准。
  - **判绿**：外包时退出码是 dist_test 的（测试：全绿 0；analyze：远端 `flutter analyze` 的退出码），末行分别是 `DIST TEST VERDICT: ...` / `DIST ANALYZE: ran on <worker> ... -> exit N` / `DIST BUILD: <构建> ran on <worker> ... -> exit N`；日志在 `.codex-test/dist/<runId>/`。`--max-minutes` 同样管外包的整段运行（由 dist_test 自己收尾、退出码 124，见上「中断与超时」）。
  - **朋友机器上的 analyze 需要对方更新 shim**：shim 新增 `analyze <slot> [--[no-]fatal-*]` 动词（路径走 stdin，由 `fushi/tool/dist_test/worker_analyze.sh` 逐条校验），旧 shim 会拒绝该动词，协调者把它当「这台不接」跳过，不算 analyze 红。对方重跑一次 `worker_setup.sh` / `worker_setup.ps1` 即更新。
