# 漫画本机 OCR：用人工真值量现状、修版面处理、复测候选模型（2026-11-17）

起因：用户报「ocr的效果太差了」，要求找一份有原图和文字真值的数据来优化，并看看哪种模型好。此前的对拍（[2026-09-30](2026-09-30-manga-ocr-select-speed.md)、[2026-10-15](2026-10-15-manga-ocr-model-bench.md)）参照都是 Google Lens，不是人工真值，只能横向比较。

## 数据与方法

- **数据**：JMangaBench_Read v1.3.3（Hugging Face `muscgab`，CC BY-NC-SA）：7,789 个文字框裁图 + 人工复核的真值。只有裁图、没有整页，所以量的是「块内行检测 → 定方向 → 去注音 → 合并 → 逐列识别」这一段，量不到整页的块检测与切块。数据集是同人漫画，注音很少，注音回归另用用户书库的页做。
- **评分**：数据集自带的 `eval/score.py`（RIN v1.2 归一化），指标 EM（整框全对）与 CER。
- **被测管线**：真实 Dart 引擎，`fushi_server ocr screen <图…> --mode text --repeat 1 --json`（即 `recognizeTextImage` → `CtcColumnOcrRecognizer`，Kellenok PP-OCRv6_manga rec v0.3），FFI ORT 1.24.4 CPU。
- **候选模型**：Python ORT CPU 4 线程，按各模型参考实现写预处理；固定抽样 1,500 框。自写预处理的输出与作者公开的预测逐框对比，charspot small / nano 各 1499 / 1500 一致，作者自报数字可信。
- 评测工作区（数据、脚本、预测）在仓库外，不入库。

## 1. 现状的错在哪

前 1,480 框，基线 EM 83.99% / CER 5.86%。按「预测与真值的差」归类：

| 类别 | 框数 | 占字错 | 说明 |
|---|---:|---:|---|
| 丢列 | 85 | 约四成 | 正文短列被当注音整列删掉 |
| 方向误判 | 25 | 四分之一强 | 竖排读成横排，逐行读出串列的字 |
| 替换 | 55 | | 识别器认错字 |
| 标点 | 50 | | 省略号、长音、感叹号一类 |
| 多读进注音 | 7 | | |

前两类都在识别之前，占了字错的大半；根因与修复见 [BUG-4891](../bugs/BUG-4891-manga-ctc-body-column-dropped-as-ruby.md)。

## 2. 修复后的数字

| 前 1,480 框 | EM | CER | 印刷体 CER | 丢列 | 方向误判 | 多读进注音 |
|---|---:|---:|---:|---:|---:|---:|
| 基线（develop `8d58da51da`） | 83.99% | 5.86% | 5.21% | 85 | 25 | 7 |
| 修复后 | 87.43% | 3.27% | 2.30% | 48 | 2 | 8 |
| charspot-small（作者公开预测，同批框） | 92.70% | 1.21% | 0.54% | | | |

全量 7,789 框修复后 EM 87.66% / CER 3.24%（丢列 268 框、方向误判 14 框、多读进注音 26 框）；全量基线没有跑完，所以改前改后的对比只有前 1,480 框那一行。加「只量候选框独占段」之前全量是 87.85% / 3.15%——这一步为了不把注音读进来，在这份几乎没有注音的数据上让出了约 0.2 个点。

页级回归（`--mode page`，改前改后逐块对比文本）：

| 素材 | 页 / 块 | 变化 |
|---|---|---|
| 用户截图页（《世界で一番おっぱいが好き！１》p9） | 1 / 13 | 「は~~ / 癒やされる~」两列都读出；「揉ませて」没有读进注音 |
| 《ドラえもん 第1巻》（全注音） | 20 / 226 | 1 块，补回「…。」 |
| 《魔法少女にあこがれて 2》《十歳の最強魔導師 第1話》（无注音） | 44 / 286 | 2 块，都是改对（串列的「べ甘 / ぜね」→「甘いね / ベーゼ…」，补回「え~」） |

全注音那一卷第一版改动曾把 16 个块的注音读了进来（「せいかつ / 生活」）：注音框压着正文列的边，整框量墨迹量到了邻列。改成只量独占段后消失——JMangaBench 注音太少，这类回归只有注音密集的页能抓到。

试过没留的：按投影判方向（比按行长投票差很多）；检测前把文字尺度归一化（消融几乎没有净收益，还改坏若干大字块）。

## 3. 候选模型

固定抽样 1,500 框，ORT CPU 4 线程：

| 模型 | EM | CER | 每框 | 体积 | 备注 |
|---|---:|---:|---:|---:|---|
| Hayai v2.7 | 95.93% | 0.50% | | 634 MB | 只用作者公开预测评分，没复测；Apache；要 `trust_remote_code`、没有 ONNX，端侧不现实 |
| **charspot-small**（muscgab） | 93.07% | 1.06% | 27 ms | 44 MB | 字符检测式，自带逐字框；横排偏弱；**CC BY-NC-SA 4.0** |
| CPT-flex | 92.27% | 1.10% | 97 ms | 233 MB | |
| nar-small（muscgab） | 92.00% | 1.09% | 88 ms | 213 MB | |
| charspot-nano（muscgab） | 90.27% | 1.80% | 5.8 ms | 6.9 MB | **CC BY-NC-SA 4.0** |
| 现用 Manga CTC（Kellenok v0.3，修复后，前 1,480 框） | 87.43% | 3.27% | | 约 40 MB | |
| manga-ocr-base-2025 | 81.67% | 4.94% | | | |

全量上 charspot-small composite 97.17、nano 95.75，与榜单一致。

结论：

- 现用模型修完版面后剩下的差距（替换 55 框、标点 49 框、手写小字）是识别器本身的，继续调版面追不上。
- 端侧能用的里 **charspot-small 最准**（CER 约为现用的三分之一），比现用模型大 4 MB、每框慢几毫秒，还自带逐字框。要拍的只有许可：CC BY-NC-SA 4.0（非商用、相同方式共享），应用不打包、由用户从作者仓库下载。
- charspot 的接入已在外部 PR [hajisensai/Fushi#3466](https://github.com/hajisensai/Fushi/pull/3466) 里（拍板台 `pr3466`），不在本次改动范围。

## 4. 缺口

- **整页级人工真值没有**：Manga109 系数据要登录 Hugging Face 申请，本机没有凭据，块检测与切块那一段没法用真值量。
- 用户机器上装的还是 Kellenok v0.2（`ocr_models/manga-ctc`），v0.3 没下；本次数字都是 v0.3。
