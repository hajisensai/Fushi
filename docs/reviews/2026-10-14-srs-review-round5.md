## A 档 · PR2 冻结前必须改（协议层，会不收敛或算错）

### A-1 「整批拒收」与「cursor 只推进无缺口前缀」冲突，且修法不能写进事件内容

**问题：**
- 批次 b 被拒后，若 cursor 不越过它，这个写入者后面的批次永远读不到，目录也永远清不掉。
- 若越过它，写入者自己本地仍有这些事件、其它端没有，两边永久分叉。
- 快照是完整状态，不经过批次级拒收判断。从快照起步的新设备会拿到这些事件，老设备拿不到，又是一种分叉。

**v6 的修法有漏洞：** v6 建议「冻结时把发布时服务器时间 S 写进每条事件的内容，拒收只看事件自身」，同时 A-2 要求「任何外流前先冻结」。但备份 / 导出可以发生在发布之前，甚至离线，那时拿不到 S。按 A-2 冻结的事件没有 S，按 A-1 就无法判定。两条一起落地，会产生新的分叉。

**建议统一改为：**
1. **事件创建即不可变。** `occurredAt` / HLC 取创建时的本地值，此后任何环节（包括发布门）都不再修改事件内容，事件 ID 与哈希只覆盖这份内容。
2. **不拒收，只钳位。** 取消「整批拒收」。cursor 照常推进，不存在被跳过的批次。
3. **S 是带外元数据，不进事件内容。** 发布时服务器时间 S 记在批次信封上，按事件 ID 关联。同一事件出现在多个批次时，以 cursor 序最早的那份为准。
4. **排序键是派生值。** `sortKey = (min(hlc, S + 容差), writerId, eventId)`。S 未知时（只经备份 / 快照拿到、还没见到批次）先按 `hlc` 临时排序，见到批次后重算。只要每条事件最终都会被发布，所有端最终拿到同一个 S、算出同一个顺序。
5. **快照写入 S 映射。** 快照带上它已知的「事件 ID → S」，快照起步的设备与老设备口径一致。

这样 A-1、A-2 共用同一条规则：批次、快照、备份三条路径都不改事件、都按同一派生键排序，写入者自己也一样。剩下要定义的只有「永远不会被发布的事件」（写入者退役前没发出去）怎么收尾，见 A-6 的模拟器用例。

### A-2 发布门修改未发布事件，但「未发布」不等于「没离开过本机」

**问题：**
- 备份（`createBackup`）、写快照、导出 .apkg 都可能带走未发布的 wall 事件。之后发布门再改它的 `occurredAt` / HLC，就会出现同 ID 不同内容。
- 这时按「取哈希小的」规则可能选到修正前那份。导出到 Anki 的那份时间也对不上，铁律 B 的 1 秒等价判定失效，复习被重复计入。

**修法：** 采用 A-1 的「事件不可变 + 派生排序键」，发布门不再修改事件。「取哈希小的」规则只剩兜底作用，不再是常规路径。

### A-3 importAnchor 用 Anki 卡片的 mod 时刻，往返时会覆盖 Fushi 的状态（前提待实测）

**问题：** v6 的推理是：Anki 导入会把 mod 设成导入时刻，改旗标、移牌组也会更新 mod。于是 Fushi 导出 → Anki 导入（没复习）→ 回导，锚点的 HLC 晚于 Fushi 最后一次复习，成了最后一条有效日志，还按「从最近锚点起算」截断了 S/D 的历史。往返一次本应是空操作，结果状态被改写了。

**⚠ 待实测：** 「导入 .apkg 会把 mod 改成导入时刻」是这条的唯一依据，v6 没有给证据。改计划前，先在当前 Anki 版本上做一次 导出 → 导入 → 回导，记录卡片 mod 的前后值。即使导入不改 mod，「改旗标 / 移牌组会改 mod」这半条成立的话，结论仍然成立。

**修法（实测后定稿）：**
- 锚点时刻取来源里最后一条排程相关 revlog 的时刻，锚点 ID 也按它派生。
- 来源的最后一条 revlog 若已等价于某条原生日志，就不写锚点。

### A-4 S/D「从最近锚点起算」和 Anki 口径不一致

**问题：** rslib 的做法是：revlog 完整时用完整 revlog 重建；只有 revlog 不完整（第一条不是学习类）时，才用 SM-2 换算起点。计划会在导入时丢掉全部历史，第 0 步「与 Anki 数值一致」这项一定对不上。

**修法：** 锚点只决定队列和到期；S/D 的输入按 rslib 的规则选。

### A-5 几处定义缺口

- **模板删除后的卡：** 生成门只挡了「笔记已删」。模板被删的卡、条件模板变空的卡还会进队列。
- **新卡出卡顺序没有定义：** 多台设备看到的新卡顺序不同。建议按 `(note createdAt, cardId)` 确定性排序。
- **导入事件没有最终排序键：** 所有导入事件的 writerId 都是 `"anki"`，同毫秒并列时无法区分。建议 HLC 之后按日志 id 比较（A-1 的派生键已包含 eventId）。
- **导出与等价判定的范围：** 导出要排除已被撤销的日志；等价判定只针对评分类 revlog，不含 Manual、Filtered 等类型。

### A-7 同一字段的并发编辑没有定义：默认会变成「晚写静默覆盖」

**问题：** 复习日志是只追加的事件，两端并发复习都保留、按序重放，不存在覆盖。但计划里还有一类**可修改的状态**，原计划与 v6 都没定义它们的合并规则：

- 笔记内容（各字段文本）；
- 卡片的旗标 / 暂停 / 埋藏 / 所属牌组；
- 牌组选项与 FSRS 参数。

如果把这些修改也当成普通事件、按 A-1 的派生键排序取最后一条，两台设备在两次同步之间改了同一个字段时，较晚的那次会静默覆盖较早的那次，用户看不到任何提示。A-1 的钳位还会让「较晚」不再等于「真实较晚」：时钟走快的设备被截短，胜负对用户更不可预测。仓库现有同步里正有这种问题（互联视频 / 有声书播放位置，PR #2177 刚修），SRS 不应再引入一份。

**修法：** 用计划里已有的版本向量判定**因果关系**，不用时间判定胜负：

- 每次字段修改事件带上修改时所见的版本向量。
- 两次修改有因果先后（一方的版本向量支配另一方）→ 后者胜出，无需提示。
- 两次修改是**并发**的（互不支配）且值不同 → 判为冲突。两个值都保留，状态标记「待裁决」，在复习页 / 编辑页提示用户选择；裁决本身作为一条新事件，支配双方。
- 按字段分级，避免过度打扰：
  - **笔记内容**：并发冲突必须提示，这是用户写的东西。
  - **旗标 / 暂停 / 牌组**：可以定确定性规则（如「暂停优先于取消暂停」），但要写进计划，不能隐式依赖时间。
  - **牌组选项 / FSRS 参数**：属于设置，可以接受「最后一次显式修改胜出」，但要在 UI 上显示「已被另一台设备的修改替换」。

这条也要进 A-6 的模拟器：断言「并发修改同一字段时，不会有任何一端的值在没有冲突记录的情况下消失」。

### A-6 停止第 6 轮人工反例审查，改用确定性模拟器

五轮都是靠推演找反例。建议在 `fushi_srs` 里写一个确定性的多设备模拟器，随机组合：

- 各设备的操作序列；
- 投递顺序；
- 时钟偏差；
- 备份恢复（含「备份在发布之前做」）；
- 清理旧目录、设备退役后回归（含「退役前有未发布事件」）。

断言五件事：最终收敛、删除不复活、cursor 不越过缺口、同一事件 ID 在所有端内容一致、并发修改同一字段不会静默丢值（A-7）。

v6 的第 1、2 条，以及 v6 两条修法之间的矛盾（A-1），都属于这个模拟器跑几分钟就能撞出来的反例。**A-1 的新方案也应先过模拟器再冻结。**

## B 档 · PR2 冻结时一并定下的数据契约

只定数据形状和接口签名，不要求在 PR2 实现功能。目的是避免冻结后再改 wire 格式。

### B-1 出处做成有类型的一等字段

- `MinedSentences` 已有 bookKey / sectionIndex / 字符偏移，视频存的是 startMs；`collections_page.dart` 已经实现了跳回原文。
- 计划只写了「可选出处」。建议定成有类型的出处引用，为复习页的「回到原文」以及播放视频 / 有声书原声片段预留。
- 冻结前要确认两件事：
  - `bookKey` 在不同设备上是否是同一个身份，否则同步过去的卡跳不回去；
  - `MinedSentences` 没有 profileId，批量导入时需要一个归属规则。

### B-2 学习统计的来源种类与「今天」口径

- `StatSourceKind` / `ActivityMediaKind` 现在只有 book / video / game。复习时长要加新的种类，这会牵动同步 wire、`media_kind_mappings.dart` 和各处穷尽 switch，属于数据契约。
- SRS 的翻日点（凌晨 4 点、profile 时区）要和统计页的「今天」统一，否则两边对「今天复习了多少」的计数会不一样。

### B-3 词状态查询接口（只定签名）

- 现状：仓库没有 known / learning / new 的词状态。查词弹窗只有 AnkiConnect 查重的 ✓ / +（`popup.js` 的 `duplicateCheck` → `ankiconnect_repository.dart`）。
- PR2 只预留「按词查卡片状态 / 到期时间 / 卡片 ID」的查询接口签名，实现放到 C-1。
- v6 曾建议把这部分整体塞进 PR2，会拖慢协议冻结，本版改为只定签名。

## C 档 · 实现阶段

### C-1 词状态回流到阅读和查词（第一期的产品重点）

- 第一期就让 SRS 实现与 AnkiConnect 查重同一个桥：弹窗显示「已在复习、状态是什么、到期时间」，点击直接打开那张卡。
- 阅读器里按卡片状态给词着色、批量「标为已知」放第二期。
- 不做这一步，SRS 就只是一个内嵌的 Anki 复刻，「为什么不用 Anki」就站不住。

### C-2 同步层做成通用层，不做成 SRS 私有

- 这会是仓库里第四套同步模型。现有三套：
  - **aggregate**：每设备一个文件，统计取 MAX、收藏取并集、学习段按 uid 墙钟 LWW；
  - **文件箱**：三方基线加冲突弹窗；
  - **互联 live**：host 为真相源。书籍进度是三方判定；视频 / 有声书播放位置原为纯 LWW，已在 PR #2177 改为三方判定。
- 建议把「批次 + 快照 + 版本向量 + HLC」做成 `packages/fushi_engine/lib/sync/` 下的通用层，服务端和互联能复用，以后别的域也能迁过来。单写者文件的模式可以直接照 `pending_mine_relay.dart` 做。

### C-3 服务端时间几乎都能拿到

「拿不到服务器时间就不提供 SRS 同步」这条退路大概率用不上。7 个后端的列目录元数据里都已有服务端时间，只是没映射进 `AssetEntry`：

| 后端 | 现成来源 |
|---|---|
| Google Drive | `modifiedTime`（列目录的 fields 里补上） |
| OneDrive | `lastModifiedDateTime` |
| Dropbox | `server_modified` |
| WebDAV | `getlastmodified`（PROPFIND 里补上） |
| FTP / SFTP | 条目修改时间（FTP 用 MDTM，见下） |
| 互联 | 响应头 |

- 统一做法：写一个探针文件，再读回它的 mtime。
- 坑：FTP 的 LIST 对新文件只到分钟精度，时区也不确定，要用 MDTM。

### C-4 iOS 直接上伞形 staticlib

两个由同一工具链编出的 Rust staticlib 同时 `-force_load`，std 的符号几乎必然重复，结论基本可以预判，不必在第 0 步「验证会不会撞」。直接做伞形库，还能少一份 std 的体积。

### C-5 服务端与交互的接入点

- **服务端：** 服务端只发 Linux x64 和 Windows x64。PR1 的 prebuilt 要进 `release-server.yml` 的随包步骤，按 `bin/../lib/<裸名>` 定位。
- **空格键：** 全局的 `_neutralizeBareSpace`（`fushi/lib/src/shortcuts/global_navigation.dart:595`）会在没有文本框聚焦时吞掉空格。Anki 用户习惯用空格翻面或评 Good，复习页要显式接管空格；计划里只写了手柄 A 键。
- **模块注册：** 新模块要在 `ModuleId` 和 module_registry 里注册。
- **动效：** 新页面按仓库规则必须带动效，并接 MD3 与 Apple 两套设计系统。
- **新手引导：** 现在教的是「去 Anki 里打开 FSRS」（`onboarding_wizard_page.dart`），要同步改。

### C-6 计划文档本身

- 修订依据引用的 `docs/reviews/2026-10-14-project-review.md` 不存在，写成 spec 前要补上或改成正确路径。
- 内置 Lapis：模板和 `LapisNoteType.defaultFieldMappings` 都在 `packages/fushi_anki/lib/src/lapis_note_type.dart`，挖词的字段映射也在那边。内置 Lapis 的 fieldId 应由这些字段键派生，不要再复制一份模板。
- 计划里写明 Lapis 是 GPL-3.0、本仓也是 GPL-3.0，许可兼容。
- 计划与本审查定稿后，都放进 `docs/specs/`，让后续 PR 有可引用的单一来源。

## 建议顺序

1. **A-3 先实测** Anki 导入是否改 mod，十分钟的事，决定 A-3 的写法。
2. **改 A-1 ～ A-5、A-7。** A-1 / A-2 按「事件不可变 + 带外 S + 派生排序键」统一处理；A-7 用版本向量判并发，可编辑字段不再按时间取胜。
3. **做 A-6 的模拟器**，把 A-1 的新方案连同 v6 的原反例一起验掉。
4. **冻结 PR2 的数据契约**，同时定下 B-1 ～ B-3。
5. 实现阶段按 C 档推进。PR3b 是否后移，倾向保留，但第一版只做 legacy 格式。

**结论：** 协议层有 6 处缺陷需要在 PR2 冻结前改（含 v6 两条修法之间的矛盾，以及可编辑字段的晚写静默覆盖）；有 3 处契约要随冻结一起定下；集成点里最重要的是词状态回流和跳回原文。
