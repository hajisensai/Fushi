这份集合版 8 的大方向没问题，前五轮的反例也基本都堵上了。但新加的铁律 H 和铁律 F 的钳位方案带进来几处会导致各端不收敛的协议问题。按计划自己定的规矩，这些都应该在 PR2 冻结前修掉，而且应该先写成模拟器的固定用例。下面按严重程度排，括号里是计划文件的行号。

一、协议层：会导致各端不收敛或数据错，PR2 冻结前必须改

1. 铁律 H 的支配关系不能传递，「被支配就立即丢弃」会让各端结果不同（505–515）
ctx 定义成「本机 cursor 已应用的批次前缀」，但批次只含本机改动、不转发，所以没有因果投递保证。
- 反例：A 写了 a（A:1）。B 收到 a 后写 b（ctx {A:1}）。C 只读到了 B 的批次、还没读 A 的，写了 c（ctx {B:1, A:0}）。
- 设备 1 依次收到 a、b、c：a 被 b 支配、b 被 c 支配，丢到只剩 {c}。
- 设备 2 先收到 c 再收到 a：c 的 ctx[A]=0，支配不了 a，a 作为并发候选留下来，结果是 {c, a}。
- 两端不收敛，还凭空多出一条冲突。第 514 行「以后再收到也能当场判出被支配」不成立。

改法二选一：
- ctx 取本机 vv 与所有已应用记录的 ctx 的并集（因果闭包）；
- 或者批次头带写入者的 vv，读方等依赖满足后才应用（因果投递）。

2. ctx 用 vv 表示，装不下「不连续的 dot」，和计划里另外三处规则冲突
- 恢复备份、退役设备回归时，未发布的事件由新化身重新发布（448、948 行），但事件不可变，dot 仍是旧 writerId 的 changeSeq。旧目录里永远没有这些批次，所以任何设备的 ctx[旧writer] 都到不了它们。结果是这些记录永远不会被支配，变成永久冲突；内容类的会一直挂着「待裁决」。
- 第 529 行「改回 / 确认时写一条 ctx 覆盖全部候选的记录」，本身就要求 ctx 能包含具体的 dot，和「ctx = cursor 前缀」的定义矛盾。
- 备份合并（415 行）拿到的记录不经过 cursor，之后本机的修改会被误判为和它们并发。

建议改用 dotted version vector（vv 加上额外 dot 集合），并且 vv 按「已应用的记录」统计，不按「已读的批次」统计。

3. 收到对端 HLC 时不钳位，时钟走快 422–423）
「收到对端数据时用对端 HLC 推进本机时钟」：一台设备时钟快了一年，所有收到它数据的设备 HLC 物理部分都会被推到一年后。之后所有人的事件都被钳到 S+10 分钟，排序退化成「按批次 S」。这正是 006
想解决的问题，换了个形式又回来了。

应该用钳位后的值 min(远端 HLC, S(e)+10min) 推进；S 未知时不推进，或只推进到本机可信时间加容差。

4. 钳位在「离线久、发布晚」时失效（450–456）
时钟快 1 天的设备离线 5 天才发布，S 会被钳。它会排在其它设备那 1天内的真实事件前面，timeUncertain 也判不出来。
- 第 455 行「不可能长期压住之后的正常修改」，实际只在「发布延迟小于时钟偏差」时成立。
- 建议把保证写准确：领先量上限是时钟偏差，不是 10 分钟。另外在 anchored 时间可用时，用它来判定 timeUncertain。


- 判断「第一条是学习类评分」（256 行）需要知道日志类型，但只有导入日志有 ankiRevlogType，原生日志没有。
- 导出 Anki revlog 的 type 字段同样需要它。
- 如果靠「上一条有效日志的 queue」推导，S(e) 知道之后排序会变，推导结果也跟着变。
- 建议在事件内容里存复习前的 queue（即 reviewType）。

7. 「找不到 config.id 就按名字匹配本机已有项」让 ID 依赖本机状态（326–329）
- 两台设备导入同一个不带 config.id  了；B 还没同步到，按名字派生出新ID。同步后同一个笔记类型里出现两个同名字段。
- 本机字段是按名字派生的，之后来了 Num 派生出另一个 ID，也会重复。
- 这违反了铁律 C「算出来的 ID 和本机状态无关」。按名字的回退应该只用纯函数 UUIDv5(noteTypeId, "field-name/"+名字)，不看本机已有项；字段后来带上 ankiNum 时，要写一条「别名」记录，不能换 ID。

8. 内置 Lapis 的 ID 规则和通用规则 is（309–313、321、325） Lapis 都会来一次。

内置模板应该版本化：用户没改过的内置模板不写修改记录，直接跟随代码；用户改过之后才变成普通内容。

二、设计缺口

10. 自动优化会经常往冲突列表里加条目（848）
两台设备在同一份数据上各自自动优化，结果按设置类冲突处理，于是「同步时有 N
处冲突」会经常出现。这和目标1「后台自动、不弹提示」冲突。建议机器产出的参数组不进冲突列表，或者指定一台设备负责优化。

11. 跨算法比较用的是训练集内评估（833–835、841）
FSRS-7 有 34 个参数，在自己的训练数

另外，「训练条数 ≥ 当前参数组的条数才采用」：用户删掉子牌组或改了 paramsMode 之后条数会变少，参数就再也更新不了。

12. FSRS-7 的 elapsed 粒度没定
铁律 A 的 elapsed 按天写（13 天的例子），前提 4 的接口只写了 next_states，而修订依据记的是 6.6.2 的 next_states 吃 days_elapsed。选 FSRS-7 的理由是它在含当天复习那张表上更好，如果 C ABI 仍然传整数天，这个优势用不上。这一点应该在第 0 步的签名核对里明确列出来。

此外，benchmark 比的 log loss 是预测拟合度，Fushi 的学习步长又是固定的，log loss 好多少不能直接等同于排程效果好多少。

13. 生成门要在查询层渲染模板（390–3
在 PR4，PR2 的查询用不上。大牌组每次建队列都渲染一遍也太慢。需要一个本机缓存列（比如 isEmpty，不同步、可重建）。

14. 卡片行由多台设备按需生成，初始 deckId 不确定（386）
两台设备各自为新模板生成同一张卡，初始 deckId 用谁的、算不算一条修改记录，计划没写。需要规定确定性的初始值，或者定义「首次生成」的语义。

15. 铁律 E 改 uid 会把已同步的 profile 和其它设备断开（411、416）
「没有用户笔记就采用对方的 uid」：已经和别的设备同步过（发布过内置行和设置记录），改 uid
后旧目录成了孤儿，已关联的其它设备条规则会在没提示的情况下做这件事。条件应该加上「从未发布过批次」。

16. 日界的统一不完整（485–490）
- stats_day_reset_hour 现在是本机偏好（preferences_repository.dart:4566，默认
  0），改成同步值之后，谁覆盖谁没有

现有的 StatSourceKind.book 把漫画也算在内，但漫画的定位方式是章节加页码，不是 sectionIndex 加字符偏移。漫画 OCR 制卡、LNReader 在线小说、Aniyomi 在线视频的定位形状都需要单独定义。

19. PR7 的安全问题（868–878、884）
- 现在的 API 服务只在字体路由上发 Access-Control-Allow-Origin: *，但根路径的 AnkiConnect POST 一旦用 text/plain 发送，就不触发预检。没设 key 时「只接受本机」并不等于「只接受本机程序」：任何网页都能通过本机浏览器调 addNote。
- storeMediaFile 的 path 参数可以读本机任意文件，url 参数可以让 Fushi 去请求任意地址（SSRF）。
- 需要一份 Origin 白名单（AnkiConnect 自己有 webCorsOriginList），让 requestPermission
  真正生效，并且默认禁用 path 参数
- 无头服务端没有「当前 profile」，Ple 没有定义。

20. 词状态的 termKey 只按词形，没区分读音（685、717–721）
「上手（じょうず / うわて）」这类同形异读词会合并成一条。SrsTermStatus 也没有卡数字段，和第 720
行「带上卡数」对不上。1 就把合并内核写在最终会用的那个包里，模拟器直接测这份代码。

三、小问题与前后不一致

- 探针文件的位置（460 行）：没写放在哪。必须放在写入者自己的目录里，否则违反「一个文件只有一个写入者」。互联后端一处写「取响应头」（195 行），另一处写「统一用探针文件」，前后不一致。另外，Nextcloud 的 WebDAV 接受客户端用 X-OC-MTime 设置修改时间，这时 modifiedAt 不是服务器时间。
- handOff 卡回导（239、1027 行）：如果 Anki 里复习过，锚点会把 scheduler 改回 fushi，卡片被收回；如果没复习过，锚点不写，卡片仍然只读。同一个操作两种结果。
- Anki 里「遗忘」的卡回导（348 行） 会保留旧状态，忽略了 Anki里更晚的重置。这违反「真实发生更晚的事件赢」。
- utcOffsetMin 和翻日时刻：1089 行要求每条日志另存这两项，但 PR2 的 srs_review_log 列表（698–705）里两项都没有，711 行只补了 utcOffsetMin。
- 复习时长谁来写：第二期（911 行） s」，B-2 又说契约在 PR2
- fushi-ext 导入另一个 profile（1046 行）：日志 id 会重新派生，revokesId 必须用同一个函数一起重映射。
- 第 0 步「一天左右」（546 行）：内容包括 iOS 伞形库、七个后端的探针、五个平台的单调时钟、三端优化器测量、Lapis 跑 WebView、fork 导出包、Anki 导入兼容。一天做不完，估算需要改。
- 依赖 fushi_anki 的限制（313 行）：fushi_srs 引用 LapisNoteType 本身可以，fushi_server 已经在依赖 fushi_anki。但只能通过零 Flutter 的 fushi_anki_core.dart 引入，要受纯度守卫约束，计划里应该写明。
