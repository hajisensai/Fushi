#### HBK-AUDIT-001：删除旧 writer 目录后，新设备仍可能漏掉唯一的数据副本

- severity：P1
- status：open，确定的协议反例
- 位置：计划 L386–399、L405–406。
- 根因：删除条件只要求某一活跃快照覆盖旧 writer，而启动读取只根据各 writer 自己的增量序号推进。接收别人的数据不会增加本机序号，因此快照可以新增第三方数据而本机序号完全不变。
- 反例：A 发布到 A:1；B 已读 A:1 并制作快照。之后 A 读取退役 W:1，制作 `vv={A:1,W:1}` 的快照，按规则删除 W 目录。新设备 N 从 B 的快照起步，已经有 A:1，A 没有新批次，W 也已不可发现；N 没有触发读取 A 新快照的条件。即使选「覆盖最广」，版本向量也可能互不支配：B 可以包含更多其他 writer，却仍缺 W。
- 影响：文件仍存在于 A 的快照，但新设备同步成功后仍缺笔记或复习历史；这不是哈希校验能发现的问题。
- 修复建议：保留可发现的退役/覆盖记录，明确 W 的替代快照与最低版本向量，并在起步时闭包补齐；或先采取合并所有保留 writer 最新快照的保守策略。快照的新颖程度不能只由所属 writer 的本机序号表达。
- 验证方式：构造 A/B/W/N 四端，A 接收 W 前后自身序号不变；删除 W 后让 N 从不含 W 的 B 快照起步，断言 W 的行与日志完整出现。

#### HBK-AUDIT-002：墓碑回收与旧备份并集合并会复活已删数据

- severity：P1
- status：open，确定的协议反例
- 位置：计划 L177–180、L403–408。
- 根因：所有活跃设备 ACK 只能约束当前参与者，不能约束旧备份与退役设备。物理删除墓碑以后，「缺失」在按 ID 并集的合并中不代表删除。
- 反例：备份含 X；A 删除 X，全部活跃设备确认；90 天后 X 的墓碑被回收，新快照也不含 X。再合并同 uid 的旧备份，X 被作为不存在的新行插入。退役端携带旧行回归有同类风险。
- 影响：已删除的笔记、模板或卡片恢复，且原删除时钟已经丢失，无法自动裁决。
- 修复建议：MVP 可先保留墓碑；若要回收，需要持久删除摘要或带 GC epoch/因果删除上下文的压缩状态，且所有备份与退役端输入必须经过同一边界。换 writer 化身或下载新快照本身不能解决并集合并的复活。
- 验证方式：删除、全端 ACK、推进 90 天、回收、合并删除前备份，断言 X 不复活；再覆盖退役端携带未发布旧修改回归的场景。

#### HBK-AUDIT-003：确定性日志 ID 没有确定性内容，导入合并不能保证收敛

- severity：P1
- status：open，确定的规则冲突
- 位置：计划 L120–133、L185–196、L268–271、L292–294、L353。
- 根因：importAnchor 的 ID 根据来源确定，但通用日志协议仍含本机 HLC、writerId，并按该 HLC 选最终状态。计划没有为同一来源日志规定规范化的排序键和不可变内容，也没有规定同 ID 异内容的处理。
- 反例：A 导入锚点 `X@10` 后评分 `R@20`；B 在较晚时刻离线导入同一文件，生成同 ID 的 `X@30`。同 ID 保留已有内容时，A 的最后日志是 R，B 的是 X；改成同 ID 取最大 HLC，又会用旧导出锚点覆盖 A 的新复习，并改变原本只追加的事件。
- 影响：重复导入测试即便证明「没有重复行」，仍可能出现两端排程永久不同或历史状态倒退。
- 修复建议：明确导入历史/锚点的规范化内容、来源排序信息与确定性校验；本机发布元信息与不可变事件分离。若用户主动要求以导入数据覆盖当前排程，应创建独立的显式操作事件，不能通过同一锚点重写达到效果。
- 验证方式：相同导出在不同时刻、不同 writer 导入，比较完整事件内容；加入一端已复习的情况，以所有接收顺序合并，断言状态一致且旧来源不会无意覆盖新复习。

#### HBK-AUDIT-004：笔记类型结构哈希会改变卡片身份，缺少既有笔记迁移规则

- severity：P1
- status：open，确定的身份契约缺口
- 位置：计划 L127–130、L137–138、L145–168、L295。
- 根因：noteTypeId 包含结构哈希，fieldId/templateId 又由 noteTypeId 派生；同 guid 的 noteId 却保持不变。结构变化时，这两种身份策略没有可兼容的映射规则。
- 反例：导入 Front/Back 类型并复习卡 C；Anki 中增加 Extra 字段，再导入并选择更新已有笔记。新结构会产生新的 noteTypeId 和全部 field/template ID。切换类型会使旧字段值和卡片引用失配，新 cardId 接不上旧历史；不切换则不能正常接纳新结构。
- 影响：普通字段增加、模板变更可能造成内容不可见、重复卡或复习历史断开。
- 修复建议：区分类型身份和结构版本；对既有 guid 指向的笔记执行明确的字段/模板映射，保持未变项身份。无法可靠映射时应明确拒绝或进入用户确认流程，不能静默重新生成全部 ID。
- 当前证据：锁定 Anki 源码 `rslib/src/import_export/package/apkg/import/notes.rs:357–400` 有独立的笔记类型冲突与字段/模板映射；416–420 行在不合并且类型不同的情况下记录冲突而非直接更新。
- 验证方式：新增字段、重命名、调序、新增模板后重复导入，分别断言旧字段保留、既有 cardId 和复习历史不变。

#### HBK-AUDIT-005：Fushi 自建笔记导出再导入不能按当前规则回到原身份

- severity：P1
- status：open，确定的往返身份冲突
- 位置：计划 L130、L135–142、L262–273、L297、L444–446。
- 根因：Fushi 自建笔记是 UUIDv7；导入身份无条件按 profileUid + ankiGuid 派生 UUIDv5。已有 ankiGuid 与导出映射未被定义为优先于派生规则的反向身份依据，也没有清楚规定映射同步。
- 反例：N 使用 UUIDv7，导出时关联 guid G；同设备或另一设备回导时按铁律得到 UUIDv5(profile,G)，不等于 N，卡片身份也跟着改变。
- 影响：往返导入出现重复笔记和独立复习历史；现有「按 guid 匹配」文字与「由 guid 确定性生成 noteId」在此存在冲突。
- 修复建议：统一双向身份规则，或明确可跨设备恢复的 `guid → 原 noteId` 关联及优先级，同时保留字段/模板的往返身份。不能仅增加一次本机判重来掩盖跨端问题。
- 验证方式：Fushi 新建 → 导出 → Anki 修改/复习 → 同端回导及另一端回导，断言唯一笔记、原卡片和历史连续。

#### HBK-AUDIT-006：未来 HLC 仍参与胜负比较，接收上限不能防止错误状态长期占优

- severity：P1
- status：open，确定的时钟反例
- 位置：计划 L188–200、L221–222。
- 根因：超过本机时间 24 小时的远端 HLC 不推进本机物理部分，但合并时仍照常参与字典序比较。计数器在物理时间之后比较，无法弥补物理时间差。
- 反例：无法取得服务器时间的端发布未来一年的修改 F。正常端接受 F 为当前字段/卡片状态，却只增加自己的计数器。正常端随后产生任意多个本年修改 E，始终有 `E.physical < F.physical`，所以 F 一直赢。
- 影响：正常端明明做了更晚的编辑或评分，结果却持续被未来事件压住；这正是 L187 声称不会发生的情况。
- 修复建议：选定一致的异常时钟处置规则，明确异常事件是否可进入权威状态及如何恢复；不能同时宣称限制物理推进、接受未来事件胜出、又保证后来操作可覆盖。可对异常输入暂停应用并保留可诊断状态，或设计不依赖异常物理值的因果优先规则，并验证多端一致性。
- 验证方式：注入未来一年 HLC，随后正常端连续编辑/评分；断言按修订后的规则能够恢复，而非等待一年或任意堆计数器。

#### HBK-AUDIT-007：按当前偏差平移全部未发布事件会损坏原本正确的时间

- severity：P1
- status：open，确定的时间修正反例
- 位置：计划 L189–192、L196、L248、L270。
- 根因：当前时钟偏差不等于所有未发布历史事件的偏差；HLC 物理部分还可能来自已接收的远端时钟，并不是原始墙钟。计划同时只改 hlc/occurredAt，没有同步定义日志到期结果的处理。
- 反例：离线时第一条复习发生在真实第 0 小时，设备时间正确；之后设备时钟跳快 24 小时，真实第 1 小时的复习记录为第 25 小时。同步时统一减 24 小时，记录变成 -24 和 1 小时，间隔仍错误地是 25 小时。学习卡的 dueAt 若仍是原先写下的错误绝对时间，修正 occurredAt 也不会修好选卡。
- 影响：统计日期、FSRS 训练间隔和日志顺序被进一步损坏，时钟修正后仍可能无法按时复习。
- 修复建议：记录原始时间、观测偏差/时钟跳变分段及事件的因果信息，明确哪些时间可校正；不要使用当前偏差统一重写历史。必须同时定义到期结果、缓存、HLC 单调性和发布身份在修正中的一致性。
- 验证方式：混合时钟正确、快跳、慢跳、已有远端 HLC 的未发布事件；检查真实间隔、因果顺序、dueAt 与重复同步修正的幂等性。

#### HBK-AUDIT-008：日志结果不完整，无法按既定唯一事实规则恢复上次真实复习时刻

- severity：P1
- status：open，确定的数据契约缺项
- 位置：计划 L84–95、L103–105、L266–272、L292。
- 根因：计划要求「上次复习时刻」取最后有效日志的结果，但结果列不包含 lastReviewedAt；日志 occurredAt 是操作时刻。卡片缓存还含 reps/lapses，却未定义从结果直接恢复还是从有效历史累计的口径。
- 反例：卡片 10 月 1 日最后评分，10 月 14 日导入或手动重排。锚点/重排发生于 14 日，但记忆状态对应的真实上次评分仍是 1 日。用操作时刻替代会把 elapsed 从 13 天变成 0；仅删除缓存再读最后日志，也无法按当前结果列恢复该信息。
- 影响：导入后第一次评分和手动重排后的评分输入错误；恢复缓存与保留缓存的设备可能行为不同。
- 修复建议：为每种事件明确完整结果载荷，至少保留 lastReviewedAt（与操作时间分离），并明确 reps/lapses 和 scheduler 的恢复规则。若选择从历史推导某些值，应将这类推导正式写入铁律 A，不能仍声称只读最后一条即可恢复全部缓存。
- 当前证据：锁定 fsrs 6.6.2 `src/inference.rs:353–371` 的 next_states 明确消费 days_elapsed；其 memory_state 接受独立 starting_state。锁定 Anki `rslib/src/card/mod.rs:92–103` 分别持有 reps、lapses、last_review_time；`scheduler/fsrs/memory_state.rs` 的重排从 last_reviewed_at 计算 elapsed。
- 验证方式：评分后隔 13 天导入/重排，立即评分；清空缓存重建后再次比较，断言 lastReviewedAt、elapsed、计数和排程归属符合同一规则。

#### HBK-AUDIT-009：自校验未规定 cursor/vv 必须表示连续完整前缀

- severity：P2
- status：open，协议未规定；不认定实现必然有 bug
- 位置：计划 L374–382、L391、L398–402。
- 根因：自校验只能判断单个文件完整，不能证明前序批次都已应用。文本没有定义批次编号与 changeSeq 的覆盖关系，或 cursor 越过缺口的禁止条件。
- 反例：批次 10 上传中断、11 已完整可见。若跳过 10 后把 cursor/vv 提升到 11，10 修复完成后也不会再读，快照还会错误宣称覆盖到 11，并进一步满足清理条件。
- 修复建议：定义连续批次编号或 seqStart/seqEnd/prevSeq，cursor/vv 只表示无缺口的已应用前缀；可提前应用后续数据，但不得越过缺口 ACK/GC。补充同一逻辑批次上传失败后的重试规则，保证序号、内容和发布确认一致。
- 验证方式：模拟截断、乱序可见、上传已成功但响应丢失、重启重试和快照清理，断言不会遗漏或把未应用数据确认成已覆盖。
