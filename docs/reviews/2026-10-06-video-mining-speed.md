# 视频片段制卡耗时优化

## 改动

本地视频、同源音频且音轨明确时，直接一次 FFmpeg 导出带音频的片段，省去
`原视频 → 中间 AAC → 带声音的视频` 的串行中间步骤。音轨选择沿用
`resolveAudioMapIndex`，未知默认多轨仍走既有音频提取器。保留用户的声道下混设置。
外部音频、独立音频源、远端 host 裁音频均保留原流程；快路导出失败时再并行补裁
句子音频和封面降级。卡片仍使用同一个带声音的视频文件。

同步片段导出器只在路径、时间起点、请求头和 TLS pin 全部相同时复用输入；
先筛选目标帧率，再缩放，避免对即将丢弃的帧做缩放。编码器、质量值、目标尺寸
和帧率不变。禁止把源章节复制进短片段，避免源章节撑长输出容器的时长。

## Windows 原生对比（2026-10-06）

- 编码器：仓库 `third_party/ffmpeg-min/windows/ffmpeg.exe`，n7.1.5。
- 输入：仓库 `docs/static-assets/screenshots/fushi-readme-anki-mining-demo.mp4`，
  3840×2160，约 60fps，带 AAC 音频；截取 1.000–4.500 秒。
- 输出：960×540、24fps；H.264 veryfast/CRF23 或 VP9 realtime/cpu-used8/CRF34。
- 旧链：单声道 64k AAC 中间音频，然后音视频合成；旧滤镜先 scale 后 fps。
- 新链：同源单输入、直接单声道输出；先 fps 后 scale。
- 同机器各 4 次交替运行，耗时包含旧链的两次进程启动，取中位数。
  全部运行经 `fushi/tool/heavy.dart` 的资源租约。

| 格式 | 旧链耗时 ms | 新链耗时 ms | 中位数变化 | 输出字节（旧 → 新） |
|---|---|---|---|---|
| MP4 | 780, 720, 712, 795 | 532, 550, 555, 578 | 750 → 552.5，减少 26.3% | 105090 → 110468 |
| WebM VP9 | 778, 852, 831, 812 | 600, 554, 670, 530 | 821.5 → 577，减少 29.8% | 119102 → 127277 |

新链少一代有损音频编码，最终固定编码档位不变；此样本文件体积增加约 5%–7%。
两种格式新旧产物均能完整解码，84 帧、3.5 秒，MP4 新旧解码画面逐帧 MD5 相同。
WebM 容器显示约 3.51 秒（Opus 封装），新旧一致。

## 验证与边界

- 回归覆盖同源输入复用、不同请求凭据/起点仍分开输入、音轨选择、时间偏移、
  外部/分离/host 音频排除快路、失败后懒提音频与降级、导入后清理。
- `synchronized_video_mining_test.dart` 内原生测试用真实引擎和 FFmpeg，验证实际
  MP4/WebM、导入时完整解码、帧数/尺寸/时长及没有中间 AAC，导入后清理输出。
  运行时设置 `FUSHI_TEST_FFMPEG` 为所测 FFmpeg 绝对路径。
- 该对比是短片段媒体生成阶段；不是用户安装包端到端制卡、Anki 写入或手机实测。
  样本为屏幕录制，不能代表所有影片复杂度、磁盘、设备和远程网络。
- 未改变硬件编码方案，也未并发整张卡的事务队列。
